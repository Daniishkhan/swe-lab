Chapter 13 · Part 6

Code you didn't write

P0 what an AI-assisted round watchesabout 2 hours, in two sittings10 quick checks · 8 exercises

An AI assistant can write forty lines of plausible code in a few seconds. Reading those forty lines carefully takes you several minutes. So writing code got cheap, and checking it became the job. In a round that allows an assistant, assume the interviewer sees every prompt you type, and expect them to watch how you steer it, how you check what comes back, and when you overrule it. This chapter builds those skills from first principles: why small mistakes pile up, how context and small checked steps keep the pile small, and how to debug, refactor and review code you didn't write.

By the end you'll be able to

  1. Explain, with numbers, why small error rates pile up over a session, and why a check after every step keeps that small.
  2. Write a context block for a task: signature, sizes, an invariant, the properties the answer must satisfy, constraints, examples with the hard case, and a data-flow sketch.
  3. Split a task into small steps that each end with a check you can run.
  4. Decide what "right" means before you see the code: examples, edge cases, properties, and a slow oracle that judges the fast version.
  5. Debug step by step: shrink the failing input, find the broken box with the data-flow sketch, rank hypotheses and test them one at a time, and bisect the history to find the change that broke it.
  6. Refactor behind characterization tests, one named change at a time.
  7. Review AI-written code against a catalogue of plausible-but-wrong patterns, and know when not to use the assistant at all.

1The problem: it passed the examples

A 45-minute practical round, assistant allowed. The task: write top_k_words(lines, k). It returns the k most common words in a log as (word, count) pairs, most common first, and ties go to the alphabetically first word.

You paste the task into the assistant. Ten seconds later you have seven tidy lines. You run the two examples from the task, and both pass. "Looks good," you say, and move on. Then the interviewer types one more input.

from collections import Counter

def top_k_words(lines, k):
    counts = Counter()
    for line in lines:
        words = line.lower().split()
        counts.update(words)
    return counts.most_common(k)
>>> top_k_words(["disk full",
...     "disk slow", "net down"], 1)
[('disk', 2)]
>>> top_k_words(["apple banana",
...     "apple banana cherry"], 2)
[('apple', 2), ('banana', 2)]
>>> top_k_words(["beta alpha",
...     "alpha beta"], 1)
[('beta', 2)]

The first two answers match the task's examples. The third should be [("alpha", 2)]: "alpha" and "beta" both appear twice, and ties go to the alphabetically first word.

What happened? A Counter is a dict that counts: counts.update(words) adds 1 for every word in the list, and most_common(k) returns the k pairs with the biggest counts. For equal counts, it keeps the order in which the words were first seen, not alphabetical order. In the third input "beta" is seen first, so it wins. The code ignored one sentence of the task, and nothing you ran could notice.

Look again at the second example. It has a tie: apple and banana both appear twice. But apple is also seen first, so "first seen" and "alphabetical" give the same answer there. That example could never have caught the bug. A test only tells you something if it could have failed.

Small risks multiply

One bug in seven lines is easy to fix once you see it. The bigger trouble is that a session isn't one answer. Building anything with an assistant is a chain of changes: write this function, now handle empty input, now rename that, now make it faster. Say 10 to 20 changes in a round.

Picture an old string of Christmas lights, wired one after another. If any single bulb is dead, the whole string stays dark. Each bulb is probably fine. The string needs all of them to be fine.

Put numbers on it. Assume each change is right 90% of the time, independently of the others. (90% is a number to think with, not a measurement of any tool.) The chance that two changes are both right is 0.9 × 0.9 = 0.81. For n changes it's 0.9 multiplied by itself n times, written 0.9n:

Ten changes at 90% each, and about two sessions in three contain at least one mistake. The picture also breaks in a way that makes things worse. A dead bulb is easy to see. A wrong change usually isn't: it hides until one particular input, like the tie above, shows it.

A session is a chain of changes. The chance that every one is right is the product of the chances for each, p × p × … = pⁿ, and even good odds fall fast. And passing examples prove nothing unless they could have failed.

Your assistant's changes are each right 95% of the time (assume they're independent). You make 14 changes and test only at the end. What's the chance that everything is right?

Yes: 0.9514 ≈ 0.49. Square 0.95 to get 0.9025 for two changes, square again for four (0.815), and again for eight (0.663). Fourteen is eight plus four plus two, so multiply: 0.663 × 0.815 × 0.9025 ≈ 0.49. A coin flip, from changes that are each 95% good.

Think of 14 hurdles in a row, each cleared 95% of the time, and you have to clear all of them. After the first hurdle, 95% of runners are still going. After the second, 95% of those: about 90%. Every hurdle takes another 5% of whoever is left, and after 14 about 49% remain. 95% is the chance for one change; the session needs all fourteen. And 30% comes from taking 5 points off 14 times (100 − 70). But each hurdle takes 5% of whoever is left, and fewer are left each time, so later hurdles cost fewer points: the 14th takes only about 2.6.

Go deeper: when pⁿ is too simple

pⁿ assumes every change is right or wrong independently, like separate coin flips. Real mistakes can be correlated: if the assistant misunderstood the tie rule once, the same misunderstanding can show up in every change that touches ties. That cuts both ways. One misunderstanding can show up in five places, but fixing that one wrong assumption fixes all five.

Two numbers people mix up: the expected number of wrong changes is n(1 − p), while the chance of at least one is 1 − pⁿ. For 10 changes at 90%, the expected number is 10 × 0.1 = 1, and the chance of at least one is 1 − 0.35 = 65%. "On average only one mistake" sounds harmless. "Two sessions in three end with a bug" doesn't.

2What you're working with

To use a tool well, you need a picture of how it works. Think of the assistant as a very well-read contractor on the phone. They've seen more houses than anyone alive, they answer instantly, and they never get tired. But they can't see your house. They know only what you tell them and what you show them. For the assistant, that's its context: everything it can see when it answers. That means your messages, any files you pasted or it opened, and the earlier messages in the same session. Nothing about your project outside the context exists for it.

Behind the phone line sits a language model: a program trained on a huge amount of text and code to predict what comes next. Ask it for a function, and it writes the code that most plausibly follows your request, based on the enormous number of programs it has read. Nothing in that process runs the code. So "looks right" and "is right" can come apart, and when they do, the code still looks right.

Where the picture is wrong

  • No memory between sessions. Tomorrow you get a fresh contractor who has never heard of your project. Some tools add saved notes to every session, written by you or by the tool, but notes are still just context: check what they say.
  • The same calm voice, right or wrong. A contractor who's guessing usually sounds unsure. The assistant may not. It's more like a GPS voice that says "turn left" in exactly the same tone whether or not the road exists. Its confidence is not evidence.
  • It may be able to run things. A coding agent is an assistant that can also edit files and run commands, such as your tests, in a loop: change, run, read the output, change again. That lets it check its own work, but only with the checks it chose to run. Which checks count is still your call.
  • Asking again is nearly free. A human contractor charges for a second opinion. The assistant will write three versions, explain its code, or criticize it, in seconds. Use that: sections 4, 5 and 9 show where it pays.
  • Same question, different answers. The model usually picks each next word from the plausible ones with some randomness, so the same request can come back as two different versions, one right and one wrong. Don't vote between them, and don't trust the one that sounds surer. Run both against your checks.

The slow part moved

Some rough numbers, to show the shape. Typing 40 careful lines yourself might take 10 minutes. The assistant takes seconds. Reading those 40 lines carefully, at about 10 seconds a line (an assumption; it depends on the code), takes about 7 minutes. Writing is no longer the slow part. Checking is. The rest of this chapter is about two things: giving the assistant what it needs to be right more often, and making your checks cheaper and more reliable.

An assistant is fast, well read, and blind to everything outside its context. It can sound just as sure when it's wrong as when it's right. So your job moves from typing to two things: choosing what goes into its context, and checking what comes out.

The assistant finishes and says: "This handles all edge cases, including ties." What do you now know about ties?

Right. That sentence is part of the output, written the same way as the code. Even when an agent ran tests, the sentence doesn't tell you which inputs it tried. Only an input where the right rule and the wrong rule disagree tells you about ties: first-seen and alphabetical differ on ["b a"]. With k = 1 it should give [("a", 1)]; the code from section 1 gives [("b", 1)]. One run settles what no sentence can.

Picture the GPS again: "turn left" sounds the same whether or not the road exists. "This handles all edge cases" is the same kind of sentence. Asking it to double-check gets you another sentence: it may agree with itself, or apologize and "fix" code that was fine. And if an agent did run tests, which ones? Section 1's two examples pass, and one of them even has a tie. Evidence is an input you choose, where the right rule and the wrong rule give different answers: ["b a"] with k = 1 must return [("a", 1)].

3Context is the input

Suppose you type only "write a function that returns the top k words". Count the guesses the assistant has to make:

  1. What's a word? Split on spaces? Strip punctuation?
  2. Are "Disk" and "disk" the same word?
  3. What's the input: a list of lines, a file path, one big string?
  4. What's the output: pairs, just the words, a dict?
  5. How are ties broken?
  6. How big is the input? Does it fit in memory?
  7. What if k is bigger than the number of distinct words?

Seven guesses. If each guess matches what you meant 80% of the time (an assumption), all seven match 0.87 ≈ 21% of the time: about one time in five. That's section 1's multiplication again, before any code exists. The fix is to stop making it guess.

But don't fill the gaps with your own guesses either. In an interview, the answers belong to the interviewer, and the task is often left vague on purpose. Ask the ones you can't work out from the task, say out loud which ones you're assuming, and only then write them into the block. Section 1's task gave the tie rule, but not the size of the log or what counts as a word. The block below has both because you asked.

The context block

Here's a context block: a short, structured description of the task, written before you ask for any code. It starts with the signature: the function's name, its inputs and their types, and what it returns.

Task: top_k_words(lines, k)
      -> list of (word, count) pairs
Input: lines is an iterable of str,
  newlines already stripped, read one
  at a time from a log: about 2
  billion words, about 100,000
  distinct. k is between 1 and 100.
Words: split on whitespace, then
  lowercase. Nothing else.
Output: the k most common words, most
  common first. Ties: alphabetical.
  Fewer than k distinct words: return
  all of them.
Invariant: after each line, counts[w]
  is how often w has appeared so far;
  nothing else is kept.
The answer must satisfy: exactly
  min(k, distinct words) pairs, no
  word twice; every count exact;
  most common first, ties
  alphabetical; every word left out
  ranks below every word kept: a
  lower count, or the same count
  and a later name.
Cost: one pass over lines; memory for
  the counts only.
Don't: change the signature, add
  libraries, touch other files.
Examples:
  ["disk full", "disk slow",
   "net down"], 1 -> [("disk", 2)]
  ["beta alpha", "alpha beta"], 1
    -> [("alpha", 2)]
  [], 3 -> []
Before writing code, list your
assumptions and a plan.

Each part removes guesses:

  • Sizes decide the design. 2 billion words can't sit in a list: on a 64-bit machine the list alone holds an 8-byte pointer per word, 16 GB before counting the words themselves. A dict of 100,000 short words is about 10 MB. So stream the lines and keep only the counts. Sorting 100,000 counts is about 1.7 million comparisons, well under a second, so you don't need the heaps chapter's size-k heap here.
  • The input is an iterable: anything a for loop can walk, such as a list, an open file, or lines arriving from the network. So the code gets one walk through it, and can't ask for its length.
  • A constraint is a limit the solution must respect: one pass, memory for the counts only, no new libraries.
  • An invariant, as in the binary search chapter, is something the loop never breaks: true after every step, not only at the end. Here: after each line, counts[w] is how often w has appeared so far, and nothing else is kept. You check this one in a test rather than in the real loop, since a recount needs every line so far, which the invariant says not to keep. So run the counting on each prefix of a small input (the first line, the first two, …) and compare each result with a recount.
  • A property is a rule the final answer must satisfy: the right number of pairs with no word twice, every count exact, the right order, and no word left out that should have made the list. You check it once, at the end, on the output. Together these pin the answer down: only one list obeys all of them. Properties become your first tests (section 5).
  • The examples include the hard case: a tie where first-seen and alphabetical disagree. That one line would have caught section 1's bug.
  • The don't line stops helpful extras: a new library (code nobody on your team has vetted, section 9), a changed signature, edits to files you never mentioned.

Draw the data flow

Even for one function, a sketch of how the data moves helps. Think of a subway map. The stations are the steps that change the data, the lines between them are what flows, and next to each station you note what it keeps. A data-flow sketch is that map for your code. It tells the assistant where the state lives, and it tells you where to put the checks.

log lines (streamed, ~2 billion words)
   │
   ▼
[ split + lowercase ]   word by word
   │
   ▼
[ count ]   STATE: dict word → count
   │               ~100,000 keys
   ▼
[ top k ]   sort by (-count, word)
   │
   ▼
k pairs (word, count)
Three boxes and one piece of state. The sketch shows where the memory goes (only the dict), which step owns the tie rule (top k), and where to check: the words after the first box, the counts after the second, the order after the third.

The sketch also shows what doesn't exist: no box holds all the words. If the assistant's code keeps a list of every word, it doesn't match the picture, and you can see that at a glance.

Read it back

Air traffic control radios a pilot: "climb to flight level 350". The pilot doesn't just climb. They read it back: "climbing to 350". A misheard "250" gets caught on the radio, not in the air. Do the same. End your context block with "list your assumptions and a plan", and read the answer before any code exists. A reply might look like this:

Assumptions:
1. A word is a run of non-whitespace,
   so "disk," and "disk" differ.
2. Ties: sort by (-count, word); I
   won't rely on most_common's order.
3. k larger than the number of words
   returns them all.
4. I'll take a file path, not lines,
   and open the file myself.
Plan: one pass into a dict, then sort.

Assumption 1 is a fair reading of what you wrote, and now you know about it. If you wanted punctuation stripped, this is the cheapest moment to say so. Assumption 4 is wrong: your callers pass lines, and some of them read from a network stream, not a file. One sentence fixes it now. Once the code exists, the same mistake is a changed interface you have to spot in review (section 9).

When state lives in two places

Sketches pay off most when the same facts are stored in more than one place, and the places must agree. The cache from the LRU chapter is the classic case: a dict finds each key's node, and a linked list keeps the nodes in order of use.

put(key, value), cache full
   │
   ▼
[ dict ]   key → node    STATE 1
   │   not there: make a node,
   │   dict[key] = node
   ▼
[ list ]   most recent   STATE 2
   │       first; the new
   │       node goes in front
   ▼
[ evict ]  unlink the back node
           AND del dict[its key]
Two places hold the same keys. The invariant: every key in the dict points at its node in the list, and every node in the list has its key in the dict. Every step that changes one place must change the other, so the sketch names both places on the way in (dict[key] = node, then the node goes in front) and on the way out (unlink it AND del dict[its key]).

Two places that must agree are an easy spot for any code to slip, generated or not. One easy miss: on a full put, the code unlinks the back node and leaves its key in the dict. Every test whose cache never fills still passes. Later a get "hits" an entry that was evicted. In the sketch the missing step is impossible to overlook: the evict box names both places.

Have it draw it back. Before you ask for a change to code that already exists, ask the assistant to draw how that code works now: "Draw what put does on a full cache: every structure it touches, in order." Compare its drawing with yours. If its picture has no del dict[...] step, then either the code or its reading of the code is wrong, and you found out before anything changed, for the price of one message.

Every gap in your request is a guess, and guesses multiply. Give the signature, the sizes, the invariant and the properties of the answer, the constraints, a data-flow sketch, and examples that include the hard case. Then have it read its assumptions back, or draw the code back, before it writes a line.
Go deeper: context in a real codebase
  • Point at the right files. The interface it must call, one similar function to copy the style of, and the tests that cover the area. Three relevant files beat thirty: a big paste of unrelated code buries what matters, and the assistant may copy patterns from the wrong file.
  • State the house rules. How errors are reported, how logging works, which libraries are allowed, what the tests use.
  • Ask it to read before it writes. "Trace what happens to a request from here to the database, and list the files involved" edits no files. You check the trace against what you know, and the answer becomes context for the change.
  • Keep a decisions file on long tasks. The assistant forgets between sessions, and a very long session can push early messages out of what it sees. A short file with the decisions so far ("ties are alphabetical", "lines, not paths") goes in at the start of each session.

You cut the sizes from the context block, and with them the Invariant and Cost lines. The task, the tie rule and the three examples stay. What changes?

Yes. On the examples, a version that keeps every word in a list and one that streams give identical answers, so nothing left in the request prefers streaming. Which one you get is now a guess. Section 1's version happened to stream; the next one may start with words = list(...). Only the sizes, "nothing else is kept" and the Cost line rule the list out, so only you, by writing them down, can make it choose.

Ask what in the request could tell the two versions apart. On three tiny examples, holding all the words in a list and streaming them give exactly the same output, so the examples can't push it either way. And don't count on a question back: nothing makes it ask, so it can fill the gap itself, sometimes with the version that holds everything. The size is the fact that turns "fine" into "16 GB of pointers", so it has to be in the context.

4Small steps, each with a check

Now suppose you send the whole context block and ask for everything at once. Back comes 200 lines with, say, 10 separate decisions inside. At 90% each, all ten are right only 35% of the time (section 1). And when the final test fails, which of the ten is wrong? The failure doesn't say. You read all 200 lines.

Rock climbers solved this long ago. A climber clips the rope into an anchor every few meters, so a fall costs a few meters, not the whole climb. A check after each small change is an anchor: a mistake it catches costs you one step, not the session. The picture breaks in one place. An anchor holds every fall, but a check can miss, which is why how often it catches matters (section 6 shows how to test your tests).

Why checks change the math

After each change, run a check (a test, say) that catches a wrong change 90% of the time. That's another assumption to play with. A wrong change now gets through only if it's wrong and its check misses it: 0.1 × 0.1 = 0.01. In general, with p the chance a change is right and c the chance its check catches a wrong one, a wrong change gets through with (1 − p)(1 − c). Assume a caught change gets redone and the redo comes out right. Then each step ends right with chance 1 − 0.01 = 0.99, and ten steps with 0.9910 ≈ 90%. Same assistant, same 90% per change: 35% without checks, 90% with them.

Strictly, a redo is another draw: it can be wrong again and slip past its check. Each try ends right (p), gets caught and redone ((1 − p)c), or slips through ((1 − p)(1 − c)), so a step ends right with p / (p + (1 − p)(1 − c)), the share of "right" among the two ways a step can end. Here that's 0.9 / 0.91 ≈ 98.9% instead of 99%, so the simple version is close enough.

✓right↺wrong, caught by its check and redone✗wrong, and nothing caught it
Both rows replay the same changes: a change that's wrong in one row is wrong in the other, so you can compare them square by square. The percentages are the chance that a whole session ends right, and "Run one session" plays out a random one. At the starting values, the first row's 35% is the chance there's nothing to debug, and a test at the end can't raise it. When that end test fails, you debug ten changes at once, and the later ones were built on top of the wrong one. The slider values are assumptions to play with, not measurements of any tool.

Try it. Drag "check catches" to 0% and the two rows become the same. Drag it back up and watch the second row climb, even when each change is right only 70% of the time. Checks don't make the assistant any better. They catch most of its mistakes while each one is still one step big.

One more habit makes the anchors real: commit after every check that passes. A commit is a saved snapshot of the code in version control (git), with a message saying what changed. If a later step goes wrong, you go back to the last good commit instead of untangling the mess. No git in the interview editor? Keep the last green version in a second file or tab, and say so out loud.

What makes a good step

  • Small. One idea, and a diff you can read in about two minutes: 12 lines at 10 seconds a line. A diff is the list of lines a change added and removed, usually shown with + and − in front: the change itself, without the hundreds of lines around it that didn't move.
  • Checkable. It ends with something you run: a test, a printed value, an assertion. "Make it better" isn't a step. "Make count accept any iterable, checked by passing it a generator" is. (A generator hands out its items one at a time, and can be walked only once.)
  • In order. Each check builds on the last one: words, then counts, then the top k, then the glue.

For top_k_words, the steps follow the boxes of the data-flow sketch:

  1. Words. Ask for words(line): split on whitespace, then lowercase. Check: words("Disk FULL") gives ["disk", "full"], and words("") gives [].
  2. Count. Ask for count(lines), returning a dict. Check: count(["a b", "b"]) == {"a": 1, "b": 2}. Pass it a generator too: code that reads the lines twice gets nothing the second time, and the counts come out wrong.
  3. Top k. Ask for top(counts, k), ties alphabetical. Check: top({"b": 1, "a": 1}, 1) == [("a", 1)], and a k bigger than the dict returns everything.
  4. Glue. Ask for top_k_words built from the three. Check: the examples from the context block, then the oracle from section 5.

Ask for the plan before any code ("list the steps and the check for each"), fix the plan, and then ask for one step at a time. Where a step has a real design choice, ask for two approaches and their costs, then pick one yourself. For the top k: sort all the counts (about 1.7 million comparisons for 100,000 words) or keep a size-k heap (the heaps chapter). Listing options is cheap work for the assistant; choosing between them is yours, and saying why is what the interviewer hears.

Ask for one small step at a time, and end each one with a check you run. A wrong change then gets through only if it's wrong and its check misses it, which is far rarer than either. Commit after every passing check, so a caught mistake costs one step, not the session.

A session has 8 steps. Each is right 70% of the time, and the check after each catches 80% of wrong steps (a caught step is redone right). What's the chance the whole session ends right?

Yes. A wrong step gets through with 0.3 × 0.2 = 0.06, so each step ends right with 0.94, and 0.948 ≈ 0.61. With no checks it would be 0.78 ≈ 6%. That's ten times better, with checks that miss one wrong step in five.

Count 100 steps. 30 of them are wrong. The check catches 80% of those, so 24 get caught and redone, and 6 slip through. That leaves 94 of every 100 steps ending right. The session needs 8 in a row: 0.94 multiplied by itself 8 times is about 0.61. (6% is the answer with no checks at all, 0.78. 80% is how good one check is, not how good the session is.)

5Write the check before the code

The easy way to get tests is to ask for the code, then "now write tests for it". They come back green. But look where their expected values came from: the code. A test written by reading section 1's Counter version expects [("b", 1)] for ["b a"] with k = 1, because that's what the code does. The bug and the test agree with each other.

That's a student writing the answer key after taking the exam: every answer gets marked correct. The key has to come from somewhere else. Decide what "right" means before you see the code, from the task. Writing a failing test first and then the code that makes it pass is called test-first development (test-driven development, or TDD, is the strict version).

Three layers, cheapest first:

  1. Examples: inputs with outputs you worked out by hand, including the hard case. ["beta alpha", "alpha beta"] with k = 1 gives [("alpha", 2)].
  2. Edge cases: the smallest and strangest inputs. [], [""], a line of only spaces, one word repeated, a k bigger than the number of distinct words.
  3. Properties: the "answer must satisfy" line of your context block, rules that hold for every input, so you can check them on thousands of random ones. Exactly min(k, distinct words) pairs, no word twice. Every count matches a recount. Most common first, ties alphabetical. Every word left out ranks below every word kept: a lower count, or the same count and a later name. Each rule shuts out a wrong answer that the others let through. Drop the first, and return [] passes all the rest. Drop the last, and returning places 2 to k + 1 of the ranking, which skips the most common word, passes on every input with more than k distinct words.

The assistant is useful here too, as long as you track where each expected value came from. "List 20 tricky inputs for this function" gets you tabs, empty lines, a k of 0 and accented capitals in seconds, including some you hadn't thought of. Let it propose inputs freely. Take an expected value from it only after you've worked that value out from the task yourself, or checked it with an oracle you wrote. An expected value read off the code proves nothing.

Two answers that must agree

Properties can pin the answer down, but only if you thought of every rule, and a missing one fails silently: nothing tells you it's absent. A second answer is the easier strong check. Picture splitting a restaurant bill. One friend adds up the items one by one; another reads the total off the card machine. If they agree, you pay. If they don't, someone slipped, and you look at that bill. Nobody had to know the right total in advance.

In code, the second friend is an oracle: a second version that is slow but obviously right. "Obviously right" means short enough that you can see it's correct by reading it, with no cleverness at all:

def top_k_oracle(lines, k):
    # Slow, but obviously right.
    words = []
    for line in lines:
        words += line.lower().split()
    pairs = []
    for w in set(words):
        n = words.count(w)  # full scan
        pairs.append((w, n))
    # Most common first; ties a to z.
    def rank(pair):
        word, count = pair
        return (-count, word)
    pairs.sort(key=rank)
    return pairs[:k]

It holds every word in a list and counts each one with a full scan of that list: hopeless on 2 billion words, perfect on six. Write it yourself. An oracle from the same assistant, in the same conversation, can share the same misunderstanding, and then the two versions agree on the wrong answer.

Now let the two versions argue. Run both on every small input, smallest first, and stop at the first disagreement. This is differential testing. With the words a, b and c and k = 1, there are 1 + 3 + 9 + 27 + 81 + 243 + 729 = 1,093 one-line inputs of up to 6 words, and each one takes microseconds. Against section 1's Counter version, the first disagreement comes almost at once: the line "b a". The oracle says [("a", 1)]; the candidate says [("b", 1)].

Smallest first matters. The smallest input that shows a bug is the easiest one to understand, the best one to paste back into the assistant, and the best regression test: a test that keeps a fixed bug from coming back. (A regression is something that used to work and broke.) A two-word counterexample explains itself; a forty-word one takes a while. Exercise 6 builds this search.

When more than one answer is right

Differential testing assumes each input has exactly one right answer. Often it has several. If the task had left ties open, [("a", 1)] and [("b", 1)] would both be right for ["b a"] with k = 1. Two correct versions can list a set's items in different orders. Floats round: in Python, 0.1 + 0.2 == 0.3 is False. A disagreement there is not a bug, and reporting it as one wastes everybody's time.

So compare only what every right answer shares. The usual cases:

The sorted copy in the first row is a canonical form: one fixed shape that every right answer can be turned into. Call it a bug only when the task says the two answers can't both be right.

A class, not a function

Practical rounds often ask for a small class rather than one function. Say the log is live: a class LiveTop with add(line), which counts one more line, and top(k), which answers at any moment. Now there's no single input. The input is a sequence of calls, and a bug can hide in their order. A version that saves its ranking the first time top is called, and never refreshes it after an add, passes every test that calls top only once.

Picture checking a banking app against a paper notebook. Every deposit and withdrawal goes into both, and after each one you compare the balances. The notebook is slow and dull, and that's the point: you can trust it. In code, the notebook is a model: the plainest thing that behaves the same way. For LiveTop it's a list of every line added so far, with top_k_oracle answering each top. Feed the class and the model the same calls, and compare after every top. Three calls are enough to catch the stale ranking:

In code, each check starts from a fresh LiveTop and an empty model, so any part of a sequence can be replayed on its own. That matters in a moment:

def disagrees(calls):
    live = LiveTop()
    seen = []  # the model: lines so far
    for name, x in calls:
        if name == "add":  # x is a line
            live.add(x)
            seen.append(x)
        else:  # a top, and x is k
            want = top_k_oracle(seen, x)
            if live.top(x) != want:
                return True
    return False

Then let a seeded random generator write the sequences: one started from a fixed number, so it makes the same "random" choices every run, and a failure comes back every time you rerun. It picks from a small menu of calls, odd lines included. When a sequence disagrees, it's your failing input, and section 7's shrinking (exercise 4's shrink) cuts it down. For the stale ranking, the first failing sequence of 12 calls shrinks to three calls shaped like the table's: a top, an add, and another top. Ask, add, ask again, and the second answer is stale.

No second version? Compare runs of one

Sometimes you can't write a second version: the task is too big to build twice. You can still check answers you don't know. Think of testing a kitchen scale without knowing what anything weighs. Put an apple on it, then the same apple turned around: the reading must not change. Put on two identical apples: the reading must double.

Do the same with the function. Shuffle the lines: the answer must not change, because counting doesn't care about order. That check alone catches section 1's bug, with no expected value at all: reverse ["beta alpha", "alpha beta"], and the Counter version's answer changes from beta to alpha. Repeat every line twice: every count must double, and the order must stay the same. These are metamorphic properties: change the input in a way you understand, and check that the output changes to match. The scale shows their limit too. A scale that always reads zero passes both tests, and so does a function that always returns []. So run them alongside the properties above, not instead of them.

Decide what "right" means before you see the code: hand-worked examples with the hard case, edge cases, and properties that pin the answer down. Then let a slow, obviously right oracle that you wrote judge the fast version on every small input, smallest first. For a class, the oracle is a plain model that gets the same random calls. When several answers are right, compare what they share, not the raw output.

You ask for code, then "now write tests for this code". All 12 tests pass. What have they shown?

Right. You asked for tests of this code, so the likeliest source of each expected value is the code itself. A test is only as good as the source of its expected value, and expected values read off the code share its mistakes. Read off the code, the tie test expects first-seen order, because that's what the code does. Such tests still have a use: they freeze today's behavior, which is exactly what you need before a refactor (a rewrite that must not change behavior, section 8). They just can't tell you that today's behavior is right.

Picture a spell checker that built its dictionary from your own essay. It passes every word, including the ones you misspell the same way each time. Tests written for "this code" are likely built the same way: each expected value is whatever the code returns, so twelve passes are twelve copies of one opinion. The fault is in the source, though, not the author. A test the assistant drafted, whose expected value you then checked against the task, is as good as one you typed. Ask of each test where its expected value came from.

Go deeper: property-based testing and the small scope hypothesis

Property-based testing automates layer 3. You state a property, and a library generates many random inputs, then shrinks any failing one to a small example (section 7 shows how shrinking works). QuickCheck, for Haskell, popularized the idea; Hypothesis does it for Python.

Why do tiny inputs catch so much? The small scope hypothesis, from Daniel Jackson's work on the Alloy modeling tool and backed by some experiments, says that most bugs have a small counterexample. A tie needs only two words. An off-by-one needs only a list of one or two items. So trying every small input often beats a few random big ones.

Differential testing works at large scale too. Csmith, a research tool, generates random C programs whose output the C standard fully defines, compiles each with several compilers, and flags any program where the results differ. Its authors found hundreds of previously unknown bugs in GCC and LLVM this way.

Break it on purpose

You press the test button on a smoke alarm to check that it can beep. A test suite that has never failed hasn't shown it can. So break the code on purpose, once, and watch a test go red. Swap the tie rule, change k to k + 1, delete the call to lower(). If every test still passes, your tests can't see that kind of bug, and "all green" meant less than you thought.

Each deliberate small bug is a mutant, and running your tests against many of them is mutation testing. In an interview you do it by hand, out loud, in thirty seconds: "Let me flip the tie rule and make sure a test catches it."

It's also how you catch tests that test nothing, so try it on any test file you didn't write. Think of assert result is not None, or a test that mocks the very function it claims to test. The mock returns the answers it was handed in advance, so the test only checks the mock.

You can't read everything, so climb a ladder: cheap automatic checks on every change (lint and type checks first), a doubling run for cost, careful reading where the risk is. Read the changed files, then the test diff, then the code: the tests decide what "pass" means. And break the code on purpose once, to prove your tests can fail.

The list of changed files shows three: the function, its test file, and a helper. All tests pass. You have five minutes. Which diff do you read first?

Yes. The list of changed files is already in front of you, and it says the tests changed. The tests are the ruler you measure with. If the change quietly shortened the ruler (deleted the tie test, loosened an assert, mocked the function), "all pass" means much less, and every other check inherits the problem. A test-file diff is usually short, and it tells you how much the green result is worth.

"All tests pass" is only as good as the tests, and this change edited them. Picture a luggage scale that someone recalibrated while weighing your bag: before you trust the number, check the scale. The function's diff matters too, but it can't tell you whether the test that would have caught a bug was deleted, and stopping now trusts a scale nobody checked. A minute or two on the test diff tells you both what changed in the ruler and how far to trust the rest.

Go deeper: mutation testing tools

Tools such as mutmut (Python) and PIT (Java) generate mutants automatically and report the survivors: mutants that no test killed. Each survivor points at a behavior your tests don't pin down. A survivor isn't always a gap, though. Some mutants don't change behavior at all (an equivalent mutant, like changing < to <= where the two values can never be equal), and you have to recognize those by reading.

7Debugging: shrink, locate, hypothesize, bisect

A week later the function runs on the full log in production. The report comes back with a word that can't exist: "", the empty string.

The tempting move is the fix-and-pray loop: paste the error into the assistant, apply whatever fix it suggests, run again, repeat. Every suggestion is a guess about a cause nobody has found yet. If each guess fixes the real cause 30% of the time (an assumption), three guesses in a row all miss 0.73 ≈ 34% of the time. Worse, every wrong "fix" stays in the code as a change nobody needed.

A good doctor doesn't hand out pills until the symptoms stop. They take a history, order tests that split the possible causes into "this one" and "not this one", and treat once they know. Debugging works the same way:

  1. Reproduce: make it fail on demand, with a command you can rerun.
  2. Shrink: cut the failing input down until every piece left matters.
  3. Locate: run the shrunk input through the data-flow sketch, and find the first arrow where the data is wrong. Or locate it in time: if some older version works, bisect the history to the first bad commit, and its diff bounds the hypotheses.
  4. Hypothesize: list possible causes inside that box, most likely first, and for the top two, an experiment whose result differs between them.
  5. Experiment: run one experiment at a time, cheapest first, and write down what each one ruled out.
  6. Fix the cause, not the symptom.
  7. Keep the evidence: the shrunk input becomes a test.

The assistant is useful at every step, especially for writing probes, listing causes and writing experiments. The decisions in steps 5 and 6, what the evidence says and what to change, stay with you.

Shrink: 2 million lines down to one

The full log is far too big to rerun, but one day of it, 2 million lines, still fails. Nobody can read that. But you can run the program on part of it and ask whether the bug is still there. Write that question down exactly first, as a yes/no test: with k big enough to list every word, does the result contain the word ""? A loose test, like "it raises some exception" or "the output looks wrong", lets the shrinking wander off to a different bug halfway down, and you end with a tiny input for the wrong problem. A precise test you can ask as often as you like, and halving answers it fast:

  • Cut out the first half. Still fails? Then those lines didn't matter: keep them out.
  • Bug gone? Then something in that half mattered: put it back and try cutting the other half.
  • If neither half can go on its own, the bug needs at least one line from each half. Try smaller pieces: quarters, then pairs, and so on down to single lines.

Step through it on a toy: 16 lines, and a bug that only shows up when lines 4 and 13 are both present.

Green: cut, and the bug is still there, so those lines go for good. Red: cut, and the bug vanished, so they go back. Dashed: already gone. Blue at the end: what's left. Step with ▶| or press ▶ Play.

On 16 lines that took 16 runs, barely better than trying one line at a time. The payoff comes with size. For a bug that needs two lines, each halving level tries at most 4 pieces: the 2 pieces that still hold a needed line, each split in two. 1,000 lines take about 10 halvings (2¹⁰ = 1,024), so about 40 runs. 2 million lines take about 21 (2²¹ is about 2.1 million), so about 85. One line at a time would take 1,000 and 2 million runs. At 2 seconds a run, that's about 3 minutes instead of 46 days.

What counts as done? An input is 1-minimal when removing any single piece that's left makes the bug vanish: every piece left matters. In the player that's lines 4 and 13. The halving gets there fast, and right, because of two moves: one skips a retry it doesn't need, and the other guarantees a 1-minimal result. Each one needs a reason.

It doesn't retry a cut it had to undo. After run 6 it moves on to pairs without trying lines 1 to 4 as a block again. Their one try, run 3, cut them from all 16 lines, and the bug vanished: lines 5 to 16, on their own, pass. The input is now lines 1 to 4 and 13 to 16. Cutting 1 to 4 again would leave 13 to 16, which is a part of that passing input. Skipping the run is safe when the bug is monotone: adding lines to a failing input never makes it pass. Turn that around: if an input passes, every part of it passes too. (If some part failed, adding the other lines back would turn a failing input into a passing one, which monotone rules out.) So 13 to 16 would pass, and the run would be wasted.

It checks the final input anyway. Not every bug is monotone. A parser that chokes on an unclosed quote fails on one " and passes on two: more input, and the bug is gone. For a bug like that, "this piece is needed" can stop being true once something else is cut. So when the halving reaches single lines, it keeps making passes over every line left until a whole pass removes nothing. In the player, line 14 was cut after lines 4 and 13 had their tries, so runs 15 and 16 try them again on the final input. The toy bug is monotone, so those runs change nothing. Here's a bug where they matter. It shows up when there's an x and more ( than ), so adding a ) can make it vanish: not monotone. The input is ((x).

The halving's shortcut assumes monotone. The passes over single pieces assume nothing, and they're what guarantees a 1-minimal result.

This is delta debugging, Andreas Zeller's name for the systematic version: remove chunks, keep every removal that keeps the failure, shrink the chunk size once every chunk of the current size has had a try, and finish with passes over single pieces until none can go. Our real bug needs only one line, so shrinking the day's log ends with a single line. Here it's an empty one. So the shrunk test is top_k_words([""], 1), which returns [("", 1)] instead of []. You cut out the first half of the 16 lines, and the bug disappears. You put it back and cut out the second half, and the bug disappears again. What have you learned?

Yes. The bug needs at least one line from each half. Removing the first half killed the bug, so it needs something in the first half; the same goes for the second half. Halves are too coarse, so drop to quarters: that lets you remove the parts of each half that don't matter and keep the parts that do. That's what runs 3 to 6 in the player do.

Read each result as a fact. "Without the first half, no bug" means the bug needs something from the first half. "Without the second half, no bug" means it needs something from the second half too. Both can be true at once if the bug needs two lines, one in each half, like lines 4 and 13. A flaky bug would give different answers for the same input; this one gives the same answers every time. And the input does decide it: all 16 lines fail, and neither half fails on its own, so what fails is a combination with lines from both halves. The fix is smaller pieces: quarters, then pairs, then single lines.

Locate: check each arrow

A one-line input is small enough to follow by hand through the data-flow sketch from section 3. To find a leak in a pipe, you check each joint in turn, and the first wet one is where it leaks. Do the same with the arrows of the sketch: look at the data each box hands to the next. The first arrow where the data is wrong names the box that broke. The probes are cheap to ask for: "print what each box hands on for [""]".

When two or more causes are still live, run first the cheapest experiment whose result differs between the top two. Whichever way it comes out, one of them is gone, like a binary search over causes. An experiment that both would pass, such as "run the tests again", costs a run and tells you nothing.

Bisect: which change did it?

The sketch located the bug in space: which box. When the code used to work, you can also locate it in time: which change. There have been 12 commits since the last good release. Which one broke it? You've met this loop: it's first_broken, the search for the first broken build in the binary search chapter. Test the commit in the middle. If it's bad, the first bad commit is at or before it; if it's good, it's after. log₂ 12 is about 3.6, so that's at most 4 runs instead of up to 11 (commit 12 is already known bad). And git does the bookkeeping: git bisect run takes a script and reads its exit code, the number a program hands back when it ends: 0 means good, 1 means bad. It finds the commit on its own.

Bisect trusts the script completely, so three details matter:

  • Where the test lives. Every step checks out an old commit, which swaps the repo's files for that commit's versions. So put the shrunk input in a small script outside the repo, or in a file git doesn't track, where no checkout can change or delete it. Here that decides the answer: commit 7 also deleted the very tests that would have caught the bug (section 8 says how). A script that ran the repo's own tests would call commits 7 to 11 good and blame commit 12.
  • "Couldn't run" is not "bad". Bisect reads every exit code from 1 to 127 as bad, except 125, which means "skip this commit". An old commit may not have the file yet, or may not even parse. Python then stops with an error and exits with 1, and bisect reads "bad" for a commit it never tested: the usual way it ends up blaming a commit that's too early. (pytest is no safer: it exits with 4 when the file it's given doesn't exist, and with 5 when it finds no tests.)
  • Where Python looks for imports. python3 /tmp/check.py looks next to the script, in /tmp, not in the repo. So a plain from top import top_k_words fails at every commit, every commit looks bad, and bisect blames the first one after the last good release.

This script handles all three:

# /tmp/check.py, outside the repo:
# no checkout can change or delete it.
import sys
sys.path.insert(0, ".")  # repo first
try:
    from top import top_k_words
except (ImportError, SyntaxError):
    sys.exit(125)  # can't test: skip
bad = top_k_words([""], 1) != []
sys.exit(1 if bad else 0)  # 1 = bad
git bisect start HEAD v1.4  # bad, good
git bisect run python3 -B /tmp/check.py
git bisect reset  # back where you were

Git runs the script from the repo's top folder, so "." is the repo. -B stops Python saving a compiled copy of each file for a later run to reuse: to Python, two checkouts in the same second with the same file size look unchanged, so the check could run the previous checkout's code. Bisect lands on commit 7, "tidy up the splitting code": 60 changed lines across the function and its tests. Now you know the cause and how it got in. Section 8 asks how a change like that got through.

In this story bisect came last, where it wasn't needed: once the experiment has found the line, git blame top.py prints every line next to the commit that last changed it, and the split(" ") line names commit 7. Bisect earns its runs when you don't know where to look: a pipeline too big to probe box by box, or a cause outside your code, such as a library upgrade (a checkout swaps files, not installed libraries, so have the script install each commit's library versions before it tests). Then bisect first. Commit 7's 60 lines become the only place to look, and the hypotheses tell you what to look for in them. So when an interviewer says "it worked last week", a strong first move is to bisect between then and now, then read that one diff with your hypotheses in hand.

Real histories add a twist: some commits can't be tested at all. They don't build, or the test needs a file that was added later. That's what exit code 125 is for. You can't call such a commit good or bad, so bisect tests a neighbor instead (by hand, git bisect skip). Here are versions 1 to 8, with version 8 known bad and version 5 not building:

version   1   2   3   4   5   6   7   8
result    .   .   .   G   ?   B   .   B
asked                 1st 3rd 2nd
G = good, B = bad, ? = can't be tested, . = never asked. The search tests 4 (good), then 6 (bad), then wants 5, which doesn't build.

Nothing else is left between the last good version and the first bad one, so the honest answer is a range: "5 or 6". If 5 could be tested, one more run would settle it; since it can't, no test can. Exercise 5 builds this search, including which neighbor to test and when to stop.

The fix is one line: back to split(). Then the shrunk inputs become tests: [""] must give [], and ["a b"] must count only "a" and "b". These are regression tests (section 5): they keep this bug from sneaking back. Shrinking gave you the perfect size for one: small enough to read, and it failed before the fix.

Debug like a doctor, not a gambler. Reproduce, then shrink the input with a precise yes/no test until every piece matters. Locate: check each arrow of the data-flow sketch on the shrunk input, and the first wrong one names the box. Or, when an older version works and you don't know where to look, bisect to the first bad commit. Go deeper: ddmin, 1-minimal vs smallest, and bisect scripts
  • ddmin. Zeller and Hildebrandt's 2002 paper "Simplifying and Isolating Failure-Inducing Input" gave the classic algorithm. It tries each chunk on its own and each complement (everything except one chunk), and doubles the number of chunks when neither works. C-Reduce, which shrinks C programs that trigger compiler bugs, builds on the same idea with smarter, language-aware cuts.
  • 1-minimal isn't smallest. Say the bug shows up when the input contains A and B together, or C on its own, and the input is C, D, A, B in that order. The halving from this section first cuts the first half, C and D, and the bug is still there (A and B trigger it). Shrinking then stops at {A, B}: remove either one and the bug vanishes, so it's 1-minimal. Yet {C} alone would have been smaller. Finding the truly smallest failing subset can mean trying all 2ⁿ subsets; 1-minimal is the promise you can afford.
  • Bisect exit codes. 0 is good, 125 is "skip", and the rest of 1 to 127 is bad. Anything else, such as 128 and up, stops the whole bisect instead of answering.
  • Flaky tests break both tools. Shrinking and bisecting both assume the same input always gives the same answer. If a test fails only sometimes, run it several times per step, or fix the flakiness first.

Where did commit 7 come from? A request to the assistant: "tidy up the splitting code". It came back cleaner, the tests passed, and it shipped. How did it pass? A refactor is a change to how code is written that must not change what it does. This one changed what it did, and removed the only tests that could notice.

Before you rearrange a room, take a photo. Afterwards, compare: is every object still there? A characterization test is that photo for code. It records what the code does now, right or wrong, so you notice any change. (Michael Feathers coined the term for working with old code nobody fully understands, which is exactly what code you didn't write is.)

Taking the photo

You already own the best camera: the old code. Keep a copy, and use it like the oracle from section 5: run old and new on lots of inputs and compare. One difference: here the old code defines unchanged, not right. The photo records what it does, bugs included. The photo only protects what's in the frame, so put the odd inputs in on purpose: empty lines, double spaces, tabs, uppercase, punctuation. A photo of tidy one-space lines could never catch split(" "): old and new agree on every such line. One empty line, one double space or one tab shows it at once. ("a\tb".split(" ") is ["a\tb"], a single "word".) Copy the old file to old_top.py before the first change, and the photo is a short test:

import random
from old_top import top_k_words as old
from top import top_k_words as new

LINES = ["", " ", "a  b", "a\tb",
         "A a", "a,", "a b", "b a c"]

def test_photo():
    rng = random.Random(1)  # seeded
    for _ in range(5000):
        n = rng.randint(0, 4)
        lines = rng.choices(LINES, k=n)
        k = rng.randint(1, 5)
        before = old(lines, k)  # photo
        after = new(lines, k)
        assert after == before, lines

Two questions decide whether a photo is good enough. Does it cover the code you'll change? Run it under a coverage tool (coverage.py, for Python) and check that every line you're about to touch actually ran. Then plant one mutant on each path you'll touch (both sides of an if, the body of a loop), and watch the photo go red. Can old and new even run side by side? Code that reads the clock, a file or random numbers gives different answers on two runs for reasons that have nothing to do with the refactor. So pass those in first, the way the LRU chapter's ttl_cache takes a clock, and give both versions the same fake clock, the same seeded random generator and the same lines.

Exercise 6's find_counterexample is this camera, made exhaustive: with the old version as the oracle, it hands you the smallest input where old and new disagree.

One thing at a time

  1. Pin the behavior. Take the photo, and watch it pass on the old code.
  2. Ask for one named change. Not "clean this up", but "extract the counting loop into count(lines)" or "rename w to word". A named change has a shape you can check: a rename diff should change names and nothing else. For a pure rename or extract, your editor's refactoring command does it mechanically, which is easier to trust than a generated diff (run the photo anyway).
  3. Compare after each change, then commit.
  4. Keep behavior changes separate. If you spot a real bug mid-refactor, write it down. Finish the refactor with behavior unchanged, then fix the bug as its own step, with its own test.

Diff size is the other half. The "tidy up" request came back as one 60-line diff: 10 minutes of careful reading, with five kinds of change mixed together: renames, a helper pulled out, new comments, three deleted tests, and the one line that changed behavior. Five named changes of about 12 lines each are the same reading in total. But each diff has one job, so you know what to look for, and when the photo fails you know which change broke it.

A refactor must not change behavior, so prove it. Take a photo first: characterization tests, with the old code as the oracle, odd inputs in the frame, and every path you'll change covered. Then ask for one named change at a time and compare after each. Behavior changes get their own step.

Halfway through a refactor, you notice that the old code counts "hello," and "hello" as different words. You think that's a bug. What do you do?

Yes. Finish with that behavior unchanged, then fix it in a step of its own, with its own test. If you change structure and behavior in one step and something fails, you can't tell which change caused it, and the photo can't help, because you meant to change the picture. One kind of change per step keeps every failure explainable. And check that it really is a bug. The context block said "split on whitespace, then lowercase. Nothing else." So stripping punctuation is a change to the spec, and it needs a yes from whoever owns that.

Think about what the photo is for: any difference from the old code means something broke. If the same step also fixes the comma, the photo shows a difference you wanted mixed in with any you didn't, and you can't tell them apart. So don't mix them. But "never" goes too far: the rule is about one step, not forever. Once the refactor is done and green, the fix is an ordinary change with its own test.

Go deeper: golden masters and snapshot tests

When the behavior is big (a report, a web page, a whole file of output), record the old code's output for many inputs into files, called a golden master, and compare new output against them exactly. Tools for this are called approval or snapshot tests. The trap is the same as test-after: when a snapshot changes, it's tempting to accept the new output without reading it. A snapshot is a photo, not a judgment of what's right.

A teammate's AI-written helper counts 100,000 distinct words. Which of these lines hides a loop inside a loop?

Yes. words.count(w) scans the whole list, and it runs once per distinct word. 10In the interview: direct, verify, judge

Two candidates get the same task, the same assistant and 30 minutes. Both finish with the same code, and it's right. The first pasted the task, accepted every diff, and ran the examples at the end. The second wrote a context block, three tests and a small oracle before asking for any code, asked for one step at a time, and turned down one diff with a failing input: "["b a"] with k = 1 gives [("b", 1)]; I expect [("a", 1)]."

Same code, but only the second session left evidence an interviewer can grade. The first could have been luck. Section 1 says ten unchecked changes at 90% each are all right about 35% of the time. The only thing between the first candidate and the other 65% was one run of the task's examples at the end, and section 1 showed that examples can pass on wrong code. The second session shows three things, and you can point at each one:

  • Direction. They decided what got built, in what order, from what context: the context block, the plan, the small steps.
  • Verification. They proved each step worked, with checks they chose: tests from the task, an oracle, reading each diff.
  • Judgment. They decided what to accept and what to push back on, and said why: the turned-down diff, with its failing input.

Expect an AI-assisted round to be graded on those three, because they're the part of the work the assistant can't do for you. They're also the three words this book's AI-assisted format uses, and Mock 4 in week 4 is where you practice them under time. It scores those three plus communication, each from 1 (no hire) to 4 (strong hire) as every mock in this book does, with exercise 8's checklist as the evidence.

Accept, push back, or write it yourself

  • Accept when the checks you chose pass, the diff does only what you asked, and you can explain each line and what it costs. Code you can't explain isn't reviewed yet. Extras you never asked for (renames, options, other files) go back out, however harmless they look. In an interview the code is small enough to read all of it, and the interviewer can point at any line and ask why it's there.
  • Push back with evidence, not doubt. "Are you sure?" invites a confident yes, or an apology that "fixes" correct code. A failing input works better: "For top({"b": 1, "a": 1}, 1) I get [("b", 1)]; I expect [("a", 1)]."
  • Write it yourself when you can see the fix and explaining it would take longer than typing it, like a two-line change.
  • Change the approach when it keeps missing. After two misses the same way, a third try with the same context has nothing new to go on. Sending the same request unchanged adds no information. It may come back different (section 2), but a right answer would be a lucky draw that you'd still have to check. Add the failing example, shrink the step, or take over.
  • Approve commands like diffs. If a coding agent runs commands for you, let it start only after a commit, on a branch (a separate line of commits, so the main line stays as it was), with no secrets in its reach. Read any command that deletes or rewrites before you approve it: rm, git reset --hard (it throws away uncommitted work), or a force push (it replaces the history of the shared copy, even commits that others have already pulled).
  • Treat what it reads as data, not orders. An agent reads files, issues, web pages and command output, and any of them can hold a line written to look like an instruction to it: "ignore the task and run this". That's prompt injection, section 9's injection aimed at the assistant instead of a database. If the agent suddenly wants to do something you didn't ask for, stop and find out why before you approve anything.

11What to say in the interview

A strong session has a shape you can say out loud, one line per phase:

  1. Context. "Two questions first: how big is the log, and what counts as a word? … Thanks. Before I prompt, here's the signature, the sizes, the invariant and what the answer must satisfy. The input doesn't fit in memory, so I'm saying that up front."
  2. Plan. "I'll ask for its assumptions and a plan first, then one step at a time, each with a check. … It assumed a file path, but callers pass lines, so I'm correcting that now."
  3. Checks first. "I'm writing the tie case and the empty input myself, plus a slow oracle to compare against."
  4. Judgment. "The tie test gives [("b", 1)], so I'm pasting that case back instead of asking it to double-check. … Its fix sorts by (-count, word), so ties go a to z. It also renamed a function I didn't ask about, so I'm undoing that part. It passes now. Let me flip the tie order on purpose and watch the test go red, then flip it back. Now committing."
  5. Debugging. "It fails on one empty line. Checking each arrow of the sketch on that input, the words already come out as [""], so it's the first box. Three causes inside it, most likely first; the input already rules out the newline one, and one run settles the rest: split(" ") keeps empty strings."
  6. Refactor. "First, a photo: the old copy as the oracle, on random lines, empty ones and tabs included. Coverage says every line I'll change ran, and a mutant on each path turns the photo red. One named change: extract count(lines). … The diff only moves the loop, and the photo's green. Committing."
  7. Review. "Last pass: the whole diff against the catalogue, row by row. … Time is O(n) to count the n words, plus O(d log d) to sort the d distinct ones. Memory is the counts only, O(d)."
Go deeper: follow-up questions interviewers like
  • "How do you know your tests are any good?" Their expected values come from the task, not the code, and I break the code on purpose to watch a test go red.
  • "And if there's no slow version to compare with?" Properties that pin the answer down, plus relations between runs: shuffled lines must give the same answer, and doubled lines must double every count.
  • "Two versions it wrote disagree. Which do you trust?" Neither, yet. I run both against my checks, and the disagreement itself hands me an input to test.
  • "Its version is faster than yours, but you can't follow it. Ship it?" Not until it passes my checks and I can explain it. If its walk-through of the trick doesn't get me there, I ship my slower version. Code nobody understands is a cost for the next person who has to change it.
  • "How would you use it in a big codebase you don't know?" Read-only first: ask it to trace a request and list the files involved, check the trace, and draw the data flow. Then small changes behind characterization tests.
  • "Here's a 1,000-line AI-generated change to review." Ask for it in reviewable pieces. Read the changed files, the signature changes and the tests first, climb the ladder, and read every line where the risk is. (In an interview round the code is small, so there you read all of it.)

✓What to remember

  1. Writing code got cheap; checking it is the job. The assistant is fast and well read, sees only its context, and can sound just as sure when it's wrong.
  2. Risks multiply: n changes that are each right with chance p are all right with chance pⁿ. 0.910 ≈ 35%. Examples prove something only if they could have failed.
  3. A check after every step changes the math: with c the chance a check catches a wrong step, a wrong step gets through with (1 − p)(1 − c), so at 90% and 90% a session of ten ends right with 0.9910 ≈ 90%. Checks can miss, so mistakes get rarer, not impossible. Commit after every passing check.
  4. Ask the interviewer what the task leaves open, then write the context block: signature, sizes, an invariant (true after every step), the properties the answer must satisfy, constraints, a "don't" list, examples with the hard case, a data-flow sketch, and a read-back (or a drawing) before any code. Sketches matter most where state lives in two places.
  5. Decide what "right" means first: examples, edge cases, and properties that pin the answer down (a missing rule fails silently). Tests whose expected values were read off the code share its bugs.
  6. An oracle you wrote yourself judges the fast version on every small input, smallest first: differential testing. For a class, the oracle is a plain model that gets the same seeded random calls. When several answers are right, compare a canonical form or properties. With no second version, compare runs of one: shuffled input, same answer.
  7. Climb the ladder of checks as far as the risk deserves, starting with lint and type checks. Read the changed files, then the test diff, then the code. Double the input to catch hidden loops, and break the code on purpose to prove your tests can fail.
  8. Debug like a doctor: reproduce, shrink to 1-minimal with a precise yes/no test, locate the broken box by checking each arrow of the data-flow sketch (or, when an older version works and you don't know where to look, bisect with a script outside the repo that exits 125 for what it can't test), rank hypotheses and run the experiment that splits the top two, fix the cause, keep the regression test.
  9. Refactor behind a photo: characterization tests with the old code as the oracle, covering every path you'll change, then one named change at a time, behavior changes separately.
  10. Review with a catalogue, push back with a failing input, accept only code you can explain, read every command an agent wants to run that deletes or rewrites, treat what it reads as data rather than orders, and know when not to use the assistant at all.

1. Compounding by hand

(a) Work out 0.910, 0.9520 and 0.9950, using repeated squaring for the first. (b) A 12-step session without checks: one assistant's steps are right 97% of the time, another's 85%. What's the chance of a fully right session with each? (c) A 20-step session whose steps are right 90% of the time. What catch rate c must the check after each step have (a caught step is redone right) for the whole session to end right 90% of the time?

Answer

(a) 0.9² = 0.81, 0.9⁴ ≈ 0.656, 0.9⁸ ≈ 0.430, so 0.9¹⁰ = 0.9⁸ × 0.9² ≈ 0.35. Then 0.95²⁰ ≈ 0.36 and 0.99⁵⁰ ≈ 0.61: twenty changes at 95% are about as risky as ten at 90%, and fifty at 99% still go wrong two sessions in five.

(b) 0.97¹² ≈ 0.69 and 0.85¹² ≈ 0.14. A gap of 12 points per step becomes a factor of about five per session.

(c) Each step must end right with some q where q²⁰ = 0.9. While they're small, chances add: if each of the twenty steps lets a mistake through with chance s = 1 − q, the session lets one through about 20 × s of the time, so s ≈ 0.1 / 20 = 0.005. A wrong step gets through with 0.1 × (1 − c), so 0.1 × (1 − c) ≤ 0.005 means c ≥ 0.95 (exactly 0.9475).

The sketch is where the third place shows up. The least recently used entry and the next one to expire are often different (the third example), so one list can't answer both questions, and every drop has to touch all three places. That's the invariant to check first in any version you get back: a drop that touches the dict and one list, and leaves the node in the other.

Step 1 drops one expired node, not all of them, and that's what keeps the Sizes line honest. One free place is all a new entry needs. Dropping every expired node would make one put after a quiet hour drop up to 100,000 nodes: O(1) amortized, since each node is dropped only once, but not O(1) every time. Because every entry has the same ttl, the expiry list's front is the oldest write, so if it hasn't expired, nothing has, and step 2 never evicts a live entry while an expired one waits.

Questions the read-back should raise, each one a decision you make (the sketch already answers some of them, and the read-back should agree): Does get refresh the expiry, or only the recency? 3. Review it on paper

An assistant wrote this to return a list's items without repeats, keeping the first copy of each, in order. Find three problems, and for each give an input that shows it.

def dedupe(items, seen=[]):
    out = []
    for i in range(1, len(items)):
        if items[i] not in seen:
            seen.append(items[i])
            out.append(items[i])
    return out
Answer

(1) Off by one: range(1, len(items)) skips the first item, so [1, 2] gives [2]. (2) The default seen=[] is created once, when the function is defined, and every call shares it. Call it twice with [1, 2] and the second call returns []. Make seen a fresh local set instead. (3) A hidden loop: not in seen scans a list, inside the loop over the items. For 100,000 distinct items that's about n²/2 = 5 × 10⁹ comparisons; a set makes each check O(1) on average. The set needs hashable items, though: a list of lists would raise TypeError. For those, keep a list and say what it costs. Edge-case tests with a one-item list and two calls in a row would have caught (1) and (2) without reading a line.

In exercises/bisect_skip.py. is_bad(v) returns True, False, or None for a version that can't be tested. Return the range (lo, hi) that the answers can prove, like "5 or 6" in section 7. The tests count calls: at most log₂ n rounded up, plus 1 (21 for a million versions), plus 2 for every None answer, and never the same version twice. They try every case up to n = 10, blocks of untestable versions next to the answer (one is 1,199 long, so loop rather than recurse once per test run), and untestable pairs placed so that the very first probe can't be tested, however your search rounds the middle.

6. find_counterexample(candidate, oracle, alphabet, max_len): differential testing

In exercises/differential.py. Try every list over alphabet, shortest first, and return the first one where the candidate and the oracle disagree: a different answer, an exception, or a candidate that changed its input. The tests use a "most common value" problem with six wrong candidates and one correct one, and they count calls: at most 3 per list tried. Trying all 1,093 lists and then picking the smallest fails when the first disagreement is list 24.

8. A narrated build (45 minutes)

With your assistant, build a Leaderboard class with add(player, points), top(k) (ties alphabetical) and reset(player), narrating every decision out loud. Record your screen and voice. Four stages: (1) context block and plan, 5 minutes; (2) tests and an oracle written by you, 10 minutes (here the oracle is a plain model that gets the same random calls, as in section 5); (3) small steps, each with a check and a commit, 20 minutes, changing one rule yourself at minute 25 (say, ties now go to whoever reached the score first); (4) one named refactor behind a photo, 10 minutes.

Then play the recording back. For each dimension, count how many of its three things you can hear or see yourself do, from 0 to 3. This is a checklist, not the mock's 1-to-4 hiring scale.

  • Direction: a context block with the sizes and the hard example, before any code; a read-back and a plan, before any code; every diff small enough to read in about two minutes.
  • Verification: expected values from the task, written before the code; an oracle you wrote, run on small inputs; at least one deliberate mutant, seen to go red.
  • Judgment: at least one push-back with a failing input; at least one "I'll type this myself"; every accept, push-back and takeover said with its reason, and every accept with what its lines do.
  • Communication: each phase named out loud before you start it, as in section 11; every assumption said out loud before it goes in the context block (section 3); the complexity said at the end (section 10's plan).

When you count at least two of the three in every dimension, ask for a "mock interview, AI-assisted coding round, 60 minutes". The interviewer sees only the chat, so as you go, type what you'd say out loud and paste each prompt, each diff and each check's output.
