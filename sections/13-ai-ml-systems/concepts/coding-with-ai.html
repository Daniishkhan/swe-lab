Chapter 13 · Part 6

Code you didn't write

P0 what an AI-assisted round watchesabout 60 minutes10 quick checks · 8 exercises

An AI assistant can write forty lines of plausible code in a few seconds. Reading those forty lines carefully takes you several minutes. So writing code got cheap, and checking it became the job. In a round that allows an assistant, assume the interviewer sees every prompt you type. They're watching how you steer it, how you check what comes back, and when you overrule it. This chapter builds those skills from first principles: why small mistakes pile up, how context and small checked steps stop them, and how to debug, refactor and review code you didn't write.

By the end you'll be able to

  1. Explain, with numbers, why small error rates pile up over a session, and why a check after every step stops that.
  2. Write a context block for a task: signature, sizes, invariants, constraints, examples with the hard case, and a data-flow sketch.
  3. Split a task into small steps that each end with a check you can run.
  4. Decide what "right" means before you see the code: examples, edge cases, properties, and a slow oracle that judges the fast version.
  5. Debug step by step: shrink the failing input, test one hypothesis at a time, and bisect the history to find the change that broke it.
  6. Refactor behind characterization tests, one named change at a time.
  7. Review AI-written code against a catalogue of typical mistakes, and know when not to use the assistant at all.

How to read this: top to bottom, like a book. It builds on How fast is your code? Warm-up 2 uses What to forget first (the LRU cache). You don't need any particular AI tool until the stretch exercises. 1The problem: it passed the examples

A 45-minute practical round, assistant allowed. The task: write top_k_words(lines, k). It returns the k most common words in a log as (word, count) pairs, most common first, and ties go to the alphabetically first word.

You paste the task into the assistant. Ten seconds later you have six tidy lines. You run the two examples from the task, and both pass. "Looks good," you say, and move on. Then the interviewer types one more input.

from collections import Counter

def top_k_words(lines, k):
    counts = Counter()
    for line in lines:
        counts.update(line.lower().split())
    return counts.most_common(k)
>>> top_k_words(["disk full",
...     "disk slow", "net down"], 1)
[('disk', 2)]
>>> top_k_words(["apple banana",
...     "apple banana cherry"], 2)
[('apple', 2), ('banana', 2)]
>>> top_k_words(["beta alpha",
...     "alpha beta"], 1)
[('beta', 2)]

The first two answers match the task's examples. The third should be [("alpha", 2)]: "alpha" and "beta" both appear twice, and ties go to the alphabetically first word.

What happened? Counter.most_common breaks ties by the order in which words were first seen, not alphabetically. In the third input "beta" is seen first, so it wins. The code ignored one sentence of the task, and nothing you ran could notice.

Look again at the second example. It has a tie: apple and banana both appear twice. But apple is also seen first, so "first seen" and "alphabetical" give the same answer there. That example could never have caught the bug. A test only tells you something if it could have failed.

Small risks multiply

One bug in six lines is easy to fix once you see it. The bigger trouble is that a session isn't one answer. Building anything with an assistant is a chain of changes: write this function, now handle empty input, now rename that, now make it faster. Say 10 to 20 changes in a round.

Picture an old string of Christmas lights, wired one after another. If any single bulb is dead, the whole string stays dark. Each bulb is probably fine. The string needs all of them to be fine.

Put numbers on it. Assume each change is right 90% of the time, independently of the others. (90% is a number to think with, not a measurement of any tool.) The chance that two changes are both right is 0.9 × 0.9 = 0.81. For n changes it's 0.9 multiplied by itself n times, written 0.9n:

changes in the sessionchance all of them are right (0.9 each)
190%

Ten changes at 90% each, and about two sessions in three contain at least one mistake. The picture also breaks in a way that makes things worse. A dead bulb is easy to see. A wrong change usually isn't: it hides until one particular input, like the tie above, shows it.

A session is a chain of changes. The chance that every one is right is the product of the chances for each, p × p × … = pⁿ, and even good odds fall fast. And passing examples prove nothing unless they could have failed.

Your assistant's changes are each right 95% of the time (assume they're independent). You make 14 changes and test only at the end. What's the chance that everything is right?

Yes: 0.9514 ≈ 0.49. Square 0.95 to get 0.9025 for two changes, square again for four (0.815), and again for eight (0.663). Fourteen is eight plus four plus two, so multiply: 0.663 × 0.815 × 0.9025 ≈ 0.49. A coin flip, from changes that are each 95% good.

Think of 14 hurdles in a row, each cleared 95% of the time, and you have to clear all of them. After the first hurdle, 95% of runners are still going. After the second, 95% of those: about 90%. Every hurdle takes another 5% of whoever is left, and after 14 about 49% remain. 95% is the chance for one change; the session needs all fourteen.

Go deeper: when pⁿ is too simple

pⁿ assumes every change is right or wrong independently, like separate coin flips. Real mistakes are often correlated: if the assistant misunderstood the tie rule once, it tends to misunderstand it in every change that touches ties. That cuts both ways. One misunderstanding can show up in five places, but fixing that one wrong assumption fixes all five.

Two numbers people mix up: the expected number of wrong changes is n(1 − p), while the chance of at least one is 1 − pⁿ. For 10 changes at 90%, the expected number is 10 × 0.1 = 1, and the chance of at least one is 1 − 0.35 = 65%. "On average only one mistake" sounds harmless. "Two sessions in three end with a bug" doesn't.

2What you're working with

To use a tool well, you need a picture of how it works. Here's the one-paragraph version. An AI coding assistant is built on a language model: a program trained on a huge amount of text and code to predict what comes next. Ask it for a function, and it writes the code that most plausibly follows your request, based on the enormous number of programs it has read. Nothing in that process runs the code. So "looks right" and "is right" can come apart, and when they do, the code still looks right.

Think of it as a very well-read contractor on the phone. They've seen more houses than anyone alive, they answer instantly, and they never get tired. But they can't see your house. They know only what you tell them and what you show them. For the assistant, that's its context: everything it can see when it answers. That means your messages, any files you pasted or it opened, and the earlier messages in the same session. Nothing outside the context exists for it.

Where the picture is wrong

  • No memory between sessions. Tomorrow you get a fresh contractor who has never heard of your project. Some tools let you keep a notes file that gets added to every session, but that's still context you wrote.
  • The same calm voice, right or wrong. A contractor who's guessing usually sounds unsure. The assistant often doesn't. It's more like a GPS voice that says "turn left" in exactly the same tone whether or not the road exists. Its confidence is not evidence.
  • It may be able to run things. A coding agent is an assistant that can also edit files and run commands, such as your tests, in a loop: change, run, read the output, change again. That lets it check its own work, but only with the checks it chose to run. Which checks count is still your call.
  • Asking again is nearly free. A human contractor charges for a second opinion. The assistant will write three versions, explain its code, or criticize it, in seconds. Use that.

The slow part moved

Some rough numbers, to show the shape. Typing 40 careful lines yourself might take 10 minutes. The assistant takes seconds. Reading those 40 lines carefully, at about 10 seconds a line (an assumption; it depends on the code), takes about 7 minutes. Writing is no longer the slow part. Checking is. The rest of this chapter is about two things: giving the assistant what it needs to be right more often, and making your checks cheaper and more reliable.

An assistant is fast, well read, and blind to everything outside its context. It can sound just as sure when it's wrong as when it's right. So your job moves from typing to two things: choosing what goes into its context, and checking what comes out.
Explain it another way: the brilliant new hire

Imagine a new hire who has read every programming book ever written and types faster than anyone on the team. Two quirks: they forget everything about your project every night, and they hardly ever say "I'm not sure". You'd brief them every morning, give them small tasks you can check, and then check them. You wouldn't let them push a week of unreviewed work on their second day. Same here.

The assistant finishes and says: "This handles all edge cases, including ties." What do you now know about ties?

Right. That sentence is part of the output, produced the same way as the code: it's what plausibly comes next, not a report of a test that ran. ["b a"] with k = 1 should give [("a", 1)]; the code from section 1 gives [("b", 1)]. One run settles what no sentence can.

Picture the GPS again: "turn left" sounds the same whether or not the road exists. "This handles all edge cases" is the same kind of sentence. Asking it to double-check gets you another sentence: it may agree with itself, or apologize and "fix" code that was fine. Neither is evidence. Evidence is an input you choose, where the right rule and the wrong rule give different answers: ["b a"] with k = 1 must return [("a", 1)].

3Context is the input

Suppose you type only "write a function that returns the top k words". Count the guesses the assistant has to make:

  1. What's a word? Split on spaces? Strip punctuation?
  2. Are "Disk" and "disk" the same word?
  3. What's the input: a list of lines, a file path, one big string?
  4. What's the output: pairs, just the words, a dict?
  5. How are ties broken?
  6. How big is the input? Does it fit in memory?
  7. What if k is bigger than the number of distinct words?

Seven guesses. If each guess matches what you meant 80% of the time (an assumption), all seven match 0.87 ≈ 21% of the time: about one time in five. That's section 1's multiplication again, before any code exists. The fix is to stop making it guess.

The context block

Here's a context block: a short, structured description of the task, written before you ask for any code. It starts with the signature: the function's name, its inputs and their types, and what it returns.

Task: top_k_words(lines, k)
      -> list of (word, count) pairs
Input: lines is an iterable of str, read
  one at a time from a log: about
  2 billion words, about 100,000
  distinct. k is between 1 and 100.
Words: split on whitespace, then
  lowercase. Nothing else.
Output: the k most common words, most
  common first. Ties: alphabetical.
  Fewer than k distinct words: return
  all of them.
Must stay true: at most k pairs; every
  count exact; lines not stored.
Cost: one pass over lines; memory for
  the counts only.
Don't: change the signature, add
  libraries, touch other files.
Examples:
  ["disk full", "disk slow",
   "net down"], 1 -> [("disk", 2)]
  ["beta alpha", "alpha beta"], 1
    -> [("alpha", 2)]
  [], 3 -> []
Before writing code, list your
assumptions and a plan.

Each part removes guesses:

  • Sizes decide the design. 2 billion words can't sit in a list: on a 64-bit machine the list alone holds an 8-byte pointer per word, 16 GB before counting the words themselves. A dict of 100,000 short words is about 10 MB. So stream the lines and keep only the counts. Sorting 100,000 counts is about 1.7 million comparisons, well under a second, so you don't need the heaps chapter's size-k heap here.
  • A constraint is a limit the solution must respect: one pass, memory for the counts only, no new libraries.
  • An invariant, as in the binary search chapter, is something that must stay true the whole time. Here: never more than k pairs, every count exact, lines not stored. Invariants are also the first tests you'll write.
  • The examples include the hard case: a tie where first-seen and alphabetical disagree. That one line would have caught section 1's bug.
  • The don't line stops helpful extras: a new library, a changed signature, edits to files you never mentioned.

Draw the data flow

For anything bigger than one function, add a sketch of how the data moves. Think of a subway map. The stations are the steps that change the data, the lines between them are what flows, and next to each station you note what it keeps. A data-flow sketch is that map for your code. It tells the assistant where the state lives, and it tells you where to put the checks.

log lines (streamed, ~2 billion words)
   │
   ▼
[ split + lowercase ]   word by word
   │
   ▼
[ count ]   STATE: dict word → count
   │               ~100,000 keys
   ▼
[ top k ]   sort by (-count, word)
   │
   ▼
k pairs (word, count)
Three boxes and one piece of state. The sketch shows where the memory goes (only the dict), which step owns the tie rule (top k), and where to check: the words after the first box, the counts after the second, the order after the third.

The sketch also shows what doesn't exist: no box holds all the words. If the assistant's code keeps a list of every word, it doesn't match the picture, and you can see that at a glance.

Read it back

Air traffic control radios a pilot: "climb to flight level 350". The pilot doesn't just climb. They read it back: "climbing to 350". A misheard "250" gets caught on the radio, not in the air. Do the same. End your context block with "list your assumptions and a plan", and read the answer before any code exists. A reply might look like this:

Assumptions:
1. A word is a run of non-whitespace,
   so "disk," and "disk" differ.
2. Ties: sort by (-count, word); I
   won't rely on most_common's order.
3. k larger than the number of words
   returns them all.
4. I'll take a file path, not lines,
   and open the file myself.
Plan: one pass into a dict, then sort.

Assumption 1 is a fair reading of what you wrote, and now you know about it. If you wanted punctuation stripped, this is the cheapest moment to say so. Assumption 4 is wrong: your callers pass lines, and some of them read from a network stream, not a file. One sentence fixes it now. Once the code exists, the same mistake is a changed interface you have to spot in review (section 9).

Every gap in your request is a guess, and guesses multiply. Give the signature, the sizes, the invariants and constraints, a data-flow sketch, and examples that include the hard case. Then have it read its assumptions back before it writes a line.
Go deeper: context in a real codebase
  • Point at the right files. The interface it must call, one similar function to copy the style of, and the tests that cover the area. Three relevant files beat thirty: a big paste of unrelated code buries what matters, and the assistant may copy patterns from the wrong file.
  • State the house rules. How errors are reported, how logging works, which libraries are allowed, what the tests use.
  • Ask it to read before it writes. "Trace what happens to a request from here to the database, and list the files involved" changes nothing. You check the trace against what you know, and the answer becomes context for the change.
  • Keep a decisions file on long tasks. The assistant forgets between sessions, and a very long session can push early messages out of what it sees. A short file with the decisions so far ("ties are alphabetical", "lines, not paths") goes in at the start of each session.

Your context block leaves out one thing: the sizes. Which result is most likely?

Yes. On the examples, the list version and the streaming version give identical answers, so nothing in the examples pushes it toward streaming, and holding everything is often the shorter way to write it. Only the size makes one version wrong, so only you, by stating the size, can make it choose.

Ask what in the request could tell the two versions apart. On three tiny examples, holding all the words in a list and streaming them give exactly the same output, so the examples can't steer it. Assistants rarely refuse an underspecified request; they fill the gap with a guess, often the shorter version that holds everything. The size is the fact that turns "fine" into "16 GB of pointers", so it has to be in the context.

4Small steps, each with a check

Now suppose you send the whole context block and ask for everything at once. Back comes 200 lines with, say, 10 separate decisions inside. At 90% each, all ten are right only 35% of the time (section 1). And when the final test fails, which of the ten is wrong? The failure doesn't say. You read all 200 lines.

Rock climbers solved this long ago. A climber clips the rope into an anchor every few meters, so a fall costs a few meters, not the whole climb. A check after each small change is an anchor: a mistake costs you one step, never the session.

Why checks change the math

After each change, run a check (a test, say) that catches a wrong change 90% of the time. That's another assumption to play with. A wrong change now gets through only if it's wrong and its check misses it: 0.1 × 0.1 = 0.01. Assume a caught change gets redone and comes out right. (It may take a second try; that costs time, not correctness.) Then each step ends right with chance 0.99, and ten steps with 0.9910 ≈ 90%. Same assistant, same 90% per change: 35% without checks, 90% with them.

rightwrong, caught by its check and redonewrong, and nothing caught it
Both rows replay the same changes: a change that's wrong in one row is wrong in the other, so you can compare them square by square. The percentages are the chance that a whole session ends right, and "Run one session" plays out a random one. The slider values are assumptions to play with, not measurements of any tool.

Try it. Drag "check catches" to 0% and the two rows become the same. Drag it back up and watch the second row climb, even when each change is right only 70% of the time. Checks don't make the assistant any better. They stop its mistakes from piling up.

One more habit makes the anchors real: commit after every check that passes. A commit is a saved snapshot of the code in version control (git), with a message saying what changed. If a later step goes wrong, you go back to the last good commit instead of untangling the mess.

What makes a good step

  • Small. One idea, and a diff you can read in about two minutes: 12 lines at 10 seconds a line.
  • Checkable. It ends with something you run: a test, a printed value, an assertion. "Make it better" isn't a step. "Make count accept any iterable, checked by passing it a generator" is.
  • In order. Each check builds on the last one: words, then counts, then the top k, then the glue.

For top_k_words, the steps follow the boxes of the data-flow sketch:

  1. Words. Ask for words(line): split on whitespace, then lowercase. Check: words("Disk FULL") gives ["disk", "full"], and words("") gives [].
  2. Count. Ask for count(lines), returning a dict. Check: count(["a b", "b"]) == {"a": 1, "b": 2}. Pass it a generator too: code that reads the lines twice gets nothing the second time, and the counts come out wrong.
  3. Top k. Ask for top(counts, k), ties alphabetical. Check: top({"b": 1, "a": 1}, 1) == [("a", 1)], and a k bigger than the dict returns everything.
  4. Glue. Ask for top_k_words built from the three. Check: the examples from the context block, then the oracle from section 5.

Ask for the plan before any code ("list the steps and the check for each"), fix the plan, and then ask for one step at a time.

Ask for one small step at a time, and end each one with a check you run. A wrong change then gets through only if it's wrong and its check misses it, which is far rarer than either. Commit after every passing check, so a mistake costs one step, never the session.

A session has 8 steps. Each is right 70% of the time, and the check after each catches 80% of wrong steps (a caught step is redone right). What's the chance the whole session ends right?

Yes. A wrong step gets through with 0.3 × 0.2 = 0.06, so each step ends right with 0.94, and 0.948 ≈ 0.61. With no checks it would be 0.78 ≈ 6%. That's ten times better, with checks that miss one wrong step in five.

Count 100 steps. 30 of them are wrong. The check catches 80% of those, so 24 get caught and redone, and 6 slip through. That leaves 94 of every 100 steps ending right. The session needs 8 in a row: 0.94 multiplied by itself 8 times is about 0.61. (6% is the answer with no checks at all, 0.78. 80% is how good one check is, not how good the session is.)

5Write the check before the code

The easy way to get tests is to ask for the code, then "now write tests for it". They come back green. But look where their expected values came from: the code. A test written by reading section 1's Counter version expects [("b", 1)] for ["b a"], because that's what the code does. The bug and the test agree with each other.

That's a student writing the answer key after taking the exam: every answer gets marked correct. The key has to come from somewhere else. Decide what "right" means before you see the code, from the task. Writing a failing test first and then the code that makes it pass is called test-first development (test-driven development, or TDD, is the strict version).

Three layers, cheapest first:

  1. Examples: inputs with outputs you worked out by hand, including the hard case. ["beta alpha", "alpha beta"] with k = 1 gives [("alpha", 2)].
  2. Edge cases: the smallest and strangest inputs. [], [""], a line of only spaces, one word repeated, a k bigger than the number of distinct words.
  3. Properties: rules that hold for every input, so you can check them on thousands of random ones. At most k pairs. Counts never go up as you read down the list. Equal counts are in alphabetical order. Every count matches a recount.

Two answers that must agree

Properties catch a lot, but not everything: a list can obey every rule above and still hold the wrong words. The strongest check is a second answer. Picture splitting a restaurant bill. One friend adds up the items one by one; another reads the total off the card machine. If they agree, you pay. If they don't, someone slipped, and you look at that bill. Nobody had to know the right total in advance.

In code, the second friend is an oracle: a second version that is slow but obviously right. "Obviously right" means short enough that you can see it's correct by reading it, with no cleverness at all:

def top_k_oracle(lines, k):
    # Slow, but obviously right.
    words = []
    for line in lines:
        words += line.lower().split()
    pairs = []
    for w in set(words):
        pairs.append((w, words.count(w)))
    pairs.sort(key=lambda p: (-p[1], p[0]))
    return pairs[:k]

It holds every word in a list and counts each one with a full scan of that list: hopeless on 2 billion words, perfect on six. Write it yourself. An oracle from the same assistant, in the same conversation, can share the same misunderstanding, and then the two versions agree on the wrong answer.

Now let the two versions argue. Run both on every small input, smallest first, and stop at the first disagreement. This is differential testing. Using three words, there are 1 + 3 + 9 + 27 + 81 + 243 + 729 = 1,093 lines of up to 6 words, and each one takes microseconds. Against section 1's Counter version, the first disagreement comes almost at once: the line "b a" with k = 1. The oracle says [("a", 1)]; the candidate says [("b", 1)].

Smallest first matters. The smallest input that shows a bug is the easiest one to understand, the best one to paste back into the assistant, and the best regression test. A two-word counterexample explains itself; a forty-word one takes a while. Exercise 6 builds this search.

Decide what "right" means before you see the code: hand-worked examples with the hard case, edge cases, and properties. Then let a slow, obviously right oracle that you wrote judge the fast version on every small input, smallest first.

You ask for code, then "now write tests for this code". All 12 tests pass. What have they shown?

Right. A test is only as good as the source of its expected value. Read off the code, the tie test expects first-seen order, because that's what the code does. Such tests still have a use: they freeze today's behavior, which is exactly what a refactor needs (section 8). They just can't tell you that today's behavior is right.

Ask where each expected value came from. If it came from reading the code, the test checks the code against itself, like grading an exam with an answer key the student wrote afterwards. But assistant-written tests aren't worthless either: any test whose expected value you checked against the task is as good as one you typed. The question is never who typed a test, only where its expected value came from.

Go deeper: property-based testing and the small scope hypothesis

Property-based testing automates layer 3. You state a property, and a library generates hundreds of random inputs, then shrinks any failing one to a small example (section 7 shows how shrinking works). QuickCheck, for Haskell, popularized the idea; Hypothesis does it for Python.

Why do tiny inputs catch so much? The small scope hypothesis, from Daniel Jackson's work on the Alloy modeling tool, is the observation that most bugs show up on some small input. A tie needs only two words. An off-by-one needs only a list of one or two items. So trying every small input often beats a few random big ones.

Differential testing works at large scale too. Csmith, a research tool, generated random C programs and compiled each one with several compilers. Whenever the compiled programs printed different results, at least one compiler had a bug. It found hundreds of previously unknown bugs in GCC and LLVM.

6Checking you can afford

You can't read everything slowly. At 10 seconds a line, a 200-line change takes 33 minutes: most of a 45-minute round. So spend your checking the way airport security does. Everyone walks through the scanner: cheap, fast, automatic. A few bags get opened by hand, chosen by what the scanner showed. Nobody hand-searches every bag, and nobody skips the scanner.

To review a change, read its diff: the list of lines it added and removed, usually shown with + and − in front. It's the change itself, without the hundreds of lines around it that didn't move.

Here's the ladder, cheapest rung first. Climb as far as the risk deserves:

Break it on purpose

You press the test button on a smoke alarm to check that it can beep. A test suite that has never failed hasn't shown it can. So break the code on purpose, once, and watch a test go red. Swap the tie rule, change k to k + 1, delete the call to lower(). If every test still passes, your tests can't see that kind of bug, and "all green" meant less than you thought.

Each deliberate small bug is a mutant, and running your tests against many of them is mutation testing. In an interview you do it by hand, out loud, in thirty seconds: "Let me flip the tie rule and make sure a test catches it."

It's also how you catch tests that test nothing, a classic in generated test files. Think of assert result is not None, or a test that mocks the very function it claims to test. A mock is a fake stand-in for a real part (a file, a network call, another function) that returns answers chosen in advance. A test that swaps the function under test for a mock only checks the mock.

You can't read everything, so climb a ladder: cheap automatic checks on every change, careful reading where the risk is. And break the code on purpose once, to prove your tests can fail.

The assistant changed three files: the function, its test file, and a helper. All tests pass. You have five minutes. What do you read first?

Yes. The tests are the ruler you measure with. If the change quietly shortened the ruler (deleted the tie test, loosened an assert, mocked the function), every other check inherits the problem. A test-file diff is usually short, and it tells you how much the green result is worth.

"All tests pass" is only as good as the tests, and this change edited them. Picture a luggage scale that someone recalibrated while weighing your bag: before you trust the number, check the scale. Reading the function from the top is the expensive rung, and it can't tell you whether the test that would have caught a bug was deleted. Five minutes on the test diff can.

Go deeper: mutation testing tools

Tools such as mutmut (Python) and PIT (Java) generate mutants automatically and report the survivors: mutants that no test killed. Each survivor points at a behavior your tests don't pin down. A survivor isn't always a gap, though. Some mutants don't change behavior at all (an equivalent mutant, like changing < to <= where the two values can never be equal), and you have to recognize those by reading.

7Debugging: shrink, hypothesize, bisect

A week later the function runs on the full log in production. The report comes back: the most common word is "", the empty string, counted 18,342 times.

The tempting move is the fix-and-pray loop: paste the error into the assistant, apply whatever fix it suggests, run again, repeat. Every suggestion is a guess about a cause nobody has found yet. If each guess fixes the real cause 30% of the time (an assumption), three guesses in a row all miss 0.73 ≈ 34% of the time. Worse, every wrong "fix" stays in the code as a change nobody needed.

A good doctor doesn't hand out pills until the symptoms stop. They take a history, order tests that split the possible causes into "this one" and "not this one", and treat once they know. Debugging works the same way:

  1. Reproduce: make it fail on demand, with a command you can rerun.
  2. Shrink: cut the failing input down to the smallest piece that still fails.
  3. Hypothesize: list possible causes, each with an experiment that would rule it in or out.
  4. Experiment: run them one at a time, and write down what each one ruled out.
  5. Fix the cause, not the symptom.
  6. Keep the evidence: the shrunk input becomes a test.

The assistant is useful at every step, especially for listing causes and writing experiments. The decisions in steps 4 and 5, what the evidence says and what to change, stay with you.

Shrink: 2 million lines down to one

The failing input is 2 million lines. Nobody can read that. But you can run the program on part of it and see whether the bug is still there. That's a yes/no question you can ask as often as you like, and halving answers it fast:

  • Cut out the first half. Still fails? Then those lines didn't matter: keep them out.
  • Bug gone? Then something in that half mattered: put it back and try cutting the other half.
  • If neither half can go on its own, the bug needs at least one line from each half. Try smaller pieces: quarters, then pairs, and so on down to single lines.

Step through it on a toy: 16 lines, and a bug that only shows up when lines 4 and 13 are both present.

Green: cut, and the bug is still there, so those lines go for good. Red: cut, and the bug vanished, so they go back. Dashed: already gone. Blue at the end: what's left. Step with ▶| or press ▶ Play.

On 16 lines that took 16 runs, no better than trying one line at a time. The payoff comes with size. For a bug that needs two lines, this method takes about 40 runs on 1,000 lines and about 85 on 2 million. One line at a time would take 1,000 and 2 million runs. At 2 seconds a run, that's about 3 minutes instead of 46 days.

This is delta debugging, Andreas Zeller's name for the systematic version: remove chunks, keep every removal that keeps the failure, and shrink the chunk size when no chunk can go. It ends with a 1-minimal input: removing any single remaining piece makes the bug vanish, so every piece left matters. Our real bug needs only one line, and shrinking the log ends with exactly one: an empty line. So the shrunk test is top_k_words([""], 1), which returns [("", 1)] instead of []. Exercise 4 builds the shrinker.

You cut out the first half of the 16 lines, and the bug disappears. You put it back and cut out the second half, and the bug disappears again. What have you learned?

Yes. Removing the first half killed the bug, so it needs something in the first half; the same goes for the second half. Halves are too coarse, so drop to quarters: that lets you remove the parts of each half that don't matter and keep the parts that do. That's what runs 3 to 6 in the player do.

Read each result as a fact. "Without the first half, no bug" means the bug needs something from the first half. "Without the second half, no bug" means it needs something from the second half too. Both can be true at once if the bug needs two lines, one in each half, like lines 4 and 13. A flaky bug would give different answers for the same input; this one gives the same answers every time. The fix is smaller pieces: quarters, then pairs, then single lines.

Hypotheses, one experiment each

A one-line input is something you can reason about. Now ask for causes, not fixes:

top_k_words([""], 1) returns [("", 1)];
I expect []. The function is below.
List 3 possible causes. For each, give
one experiment that would rule it in
or out. Don't write a fix yet.

A useful answer looks something like this:

1. split(" ") keeps empty strings:
   "".split(" ") is [""].
   Try top_k_words(["a  b"], 3), with
   two spaces. A "" in the result
   confirms it.
2. Lines still end in "\n", so the
   blank line isn't really "".
   Try printing repr(line) for each.
3. lower() changes something.
   Try the same input without lower().

Run experiment 1 and you get [("", 1), ("a", 1), ("b", 1)]: an empty string, counted from between the two spaces. Cause found, in one run. In Python, "".split(" ") is [""] and "a b".split(" ") is ["a", "", "b"]. But split() with no argument splits on runs of any whitespace and never returns empty strings: "".split() is []. Hypothesis 3 was never likely (lowercasing can't create an empty string), but listing it cost nothing, and ruling causes out is half the work.

Bisect: which change did it?

The function used to work, and there have been 12 commits since the last good release. Which one broke it? You've met this loop: it's the first-bad-version search from the binary search chapter. Test the commit in the middle. If it's bad, the first bad commit is at or before it; if it's good, it's after. log₂ 12 is about 3.6, so that's 4 runs instead of up to 12, and git does the bookkeeping: git bisect run takes a script that exits with 0 for good and 1 for bad, and finds the commit on its own.

Here it lands on commit 7, "make splitting explicit": six changed lines, one of which turned split() into split(" "). Now you know the cause and how it got in.

Real histories add a twist: some commits can't be tested at all. They don't build, or the test needs a file that was added later. You can't call such a commit good or bad, so you test a neighbor instead (git bisect skip; in a script, exit code 125). Here are versions 1 to 8, with version 8 known bad and version 5 not building:

version   1   2   3   4   5   6   7   8
result    .   .   .   G   ?   B   .   B
asked                 1st 3rd 2nd
G = good, B = bad, ? = can't be tested, . = never asked. The search tests 4 (good), then 6 (bad), then wants 5, which doesn't build.

Nothing else is left between the last good version and the first bad one, so the honest answer is a range: "5 or 6". If 5 could be tested, one more run would settle it; since it can't, no test can. Exercise 5 builds this search, including which neighbor to test and when to stop.

Fix, then keep the evidence

The fix is one line: back to split(). Then the shrunk inputs become tests: [""] must give [], and ["a b"] must count only "a" and "b". This is a regression test. A regression is something that used to work and broke, and the test keeps this one from sneaking back. Shrinking gave you the perfect size for one: small enough to read, and it failed before the fix.

Debug like a doctor, not a gambler. Reproduce, shrink the input until every piece matters, list hypotheses with one experiment each, and bisect the history to find the change that did it. Then fix the cause and keep the shrunk input as a test. The assistant can propose causes and write experiments; you decide what the evidence says.
Go deeper: ddmin, 1-minimal vs smallest, and bisect scripts
  • ddmin. Zeller and Hildebrandt's 2002 paper "Simplifying and Isolating Failure-Inducing Input" gave the classic algorithm. It tries each chunk on its own and each complement (everything except one chunk), and doubles the number of chunks when neither works. C-Reduce, which shrinks C programs that trigger compiler bugs, builds on the same idea with smarter, language-aware cuts.
  • 1-minimal isn't smallest. Say the bug shows up when the input contains A and B together, or C on its own. Start from {A, B, C, D}. Shrinking can remove C first (A and B still trigger the bug), then D, and stop at {A, B}: remove either one and the bug vanishes, so it's 1-minimal. Yet {C} alone would have been smaller. Finding the truly smallest failing subset can mean trying all 2ⁿ subsets; 1-minimal is the promise you can afford.
  • Bisect scripts. For git bisect run, the script's exit code is its answer: 0 means good, and 1 to 127 means bad, except 125, which means "can't test this one, skip it". Any other exit code stops the bisect.
  • Flaky tests break both tools. Shrinking and bisecting both assume the same input always gives the same answer. If a test fails only sometimes, run it several times per step, or fix the flakiness first.

8Refactoring behind a photo

Where did commit 7 come from? A request to the assistant: "tidy up the splitting code". It came back cleaner, the tests passed, and it shipped. A refactor is a change to how code is written that must not change what it does. This one changed what it did, and nothing noticed.

Before you rearrange a room, take a photo. Afterwards, compare: is every object still there? A characterization test is that photo for code. It records what the code does now, right or wrong, so you notice any change. (Michael Feathers coined the term for working with old code nobody fully understands, which is exactly what code you didn't write is.)

Taking the photo

You already own the best camera: the old code. Keep a copy, and use it as the oracle from section 5: run old and new on lots of inputs and compare. The photo only protects what's in the frame, so put the odd inputs in on purpose: empty lines, double spaces, tabs, uppercase, punctuation. A photo with no double spaces in it could never catch split(" "). One with a tab would catch it too, since "a\tb".split(" ") is ["a\tb"], a single "word".

One thing at a time

  1. Pin the behavior. Take the photo, and watch it pass on the old code.
  2. Ask for one named change. Not "clean this up", but "extract the counting loop into count(lines)" or "rename w to word". A named change has a shape you can check: a rename diff should change names and nothing else.
  3. Compare after each change, then commit.
  4. Keep behavior changes separate. If you spot a real bug mid-refactor, write it down. Finish the refactor with behavior unchanged, then fix the bug as its own step, with its own test.

Diff size is the other half. The "tidy up" request came back as one 60-line diff: 10 minutes of careful reading, with five kinds of change mixed together, one of which changed behavior. Five named changes of about 12 lines each are the same reading in total. But each diff has one job, so you know what to look for, and when the photo fails you know which change broke it.

A refactor must not change behavior, so prove it. Take a photo first (characterization tests, with the old code as the oracle and odd inputs in the frame). Then ask for one named change at a time and compare after each. Behavior changes get their own step.

Halfway through a refactor, you notice that the old code counts "hello," and "hello" as different words. You think that's a bug. What do you do?

Yes. If you change structure and behavior in one step and something fails, you can't tell which change caused it, and the photo can't help, because you meant to change the picture. One kind of change per step keeps every failure explainable. And check that it really is a bug: the context block said "split on whitespace, nothing else", so stripping punctuation is a change to the spec, and it needs a yes from whoever owns that.

Think about what the photo is for: any difference from the old code means something broke. If the same step also fixes the comma, the photo shows a difference you wanted mixed in with any you didn't, and you can't tell them apart. So don't mix them. But "never" goes too far: the rule is about one step, not forever. Once the refactor is done and green, the fix is an ordinary change with its own test.

Go deeper: golden masters and snapshot tests

When the behavior is big (a report, a web page, a whole file of output), record the old code's output for many inputs into files, called a golden master, and compare new output against them exactly. Tools for this are called approval or snapshot tests. The trap is the same as test-after: when a snapshot changes, it's tempting to accept the new output without reading it. A snapshot is a photo, not a judgment of what's right.

9Reviewing code you didn't write

When you proofread your own essay, you read what you meant to write, not what's on the page, so typos slip past. A fresh reader sees the page. AI-written code sets a different trap: it's fluent, well named and neatly formatted, which is how code from a careful person looks. Fluency isn't correctness, so don't let it set your trust.

The fix is a checklist: a catalogue of the mistakes that come up again and again, so you look for each one on purpose instead of hoping it jumps out at you.

A teammate's AI-written helper counts 100,000 distinct words. Which of these lines hides a loop inside a loop?

Yes. words.count(w) scans the whole list, and it runs once per distinct word. With 100,000 words, all different, that's 100,000 × 100,000 = 10¹⁰ steps: about 17 minutes at 10 million steps a second. Section 5's oracle counts the same way, and there it's fine, because the oracle only ever sees tiny inputs. The same code can be right in a test and wrong in production.

Look for a loop you can't see. Counter(words) walks the list once: O(n). sorted costs O(d log d) for d distinct words, about 1.7 million comparisons for 100,000. But inside the dict comprehension, words.count(w) is itself a full scan of the list, run once for every distinct word: n × d steps, 10¹⁰ when both are 100,000. A method call that hides a loop is the "know what Python hides" rule from the complexity chapter.

10In the interview: direct, verify, judge

When a round allows an assistant, its typing isn't what's being assessed. Your decisions are what the interviewer can see. This book's interview-formats section sums them up in three words (topic 15.09, the AI-assisted round):

  • Direction. You decide what gets built, in what order, from what context. It shows as a context block, a plan before code, and small steps.
  • Verification. You prove each step works, with checks you chose. It shows as tests before code, an oracle, breaking things on purpose, and reading the diff.
  • Judgment. You decide what to accept, what to push back on, and when to put the assistant away. It shows as reasons you say out loud.

Accept, push back, or write it yourself

  • Accept when the checks you chose pass and the diff does only what you asked.
  • Push back with evidence, not doubt. "Are you sure?" invites a confident yes, or an apology that "fixes" correct code. A failing input works better: "For top({"b": 1, "a": 1}, 1) I get [("b", 1)]; I expect [("a", 1)]."
  • Write it yourself when you can see the fix and explaining it would take longer than typing it, like a two-line change.
  • Change the approach after two attempts that miss the same way. A third try with the same context tends to miss the same way too. Add the failing example, shrink the step, or take over.

When not to use it at all

  • The rules say no. Some rounds don't allow assistants. If it isn't clear, ask at the start; using one where it isn't allowed can end the interview.
  • Code or data that isn't yours to share: secrets, customer data or private code, unless the tool is approved for it.
  • You can't check the answer. If you couldn't tell a right answer from a wrong one, the answer is worth nothing to you. Learn enough to check it first.
  • The point is to learn. The exercises in this book exist to build the skill in your own head. An assistant that writes them skips the part you came for.
  • Tiny changes. If typing it is faster than describing it, type it.

Here's what it sounds like, narrated as you work:

"First the context: the signature, the sizes, the tie rule, and one example where ties matter. I'm asking for its assumptions before any code. … It assumed a file path, but callers pass lines, so I'm correcting that now. … Step 3 is the tie rule. Before I run its version, I'm writing the tie test myself: {"b": 1, "a": 1} with k = 1 should give [("a", 1)]. … It returned [("b", 1)]. I'll paste that case back instead of asking it to double-check. … It passes now. Let me flip the tie order on purpose and make sure the test goes red. Good. Committing, then step 4."

You're judged on your decisions, not on the assistant's typing: direction (context, plan, small steps), verification (checks you chose, run before you trust), and judgment (accept, push back with evidence, or do it yourself). Say each decision out loud, with its reason.

The assistant's top fails your tie test. Which reply is best?

Yes. It gives the assistant exactly what it was missing: a concrete input, the wrong output, the right output and the rule. It also limits the change, so the next diff is small and checkable. The interviewer hears the same thing: you found a bug with evidence and kept the fix contained.

Picture a mechanic. "Are you sure the car's fine?" gets you a shrug. "It squeals when I brake at low speed" gets you a fix. "Double-check" adds no information, and the reply may defend the code, or change something else, as easily as fix it. "Rewrite from scratch" throws away the steps that already passed their checks. A failing input with the expected output and the rule is the smallest message that can't be misread.

11What to say in the interview

A strong session has a shape you can say out loud, one line per phase:

  1. Context. "Before I prompt: here's the signature, the sizes, and what must stay true. The input doesn't fit in memory, so I'm saying that up front."
  2. Plan. "I'll ask for its assumptions and a plan first, then one step at a time, each with a check."
  3. Checks first. "I'm writing the tie case and the empty input myself, plus a slow oracle to compare against."
  4. Judgment. "That step passed, so I'm committing. This diff also renamed a function I didn't ask about, so I'm undoing that part."
  5. Debugging. "It fails on one empty line. Three hypotheses, one experiment each. Experiment 1 shows split(" ") keeps empty strings."
Go deeper: follow-up questions interviewers like
  • "How do you know your tests are any good?" Their expected values come from the task, not the code, and I break the code on purpose to watch a test go red.
  • "Its version is faster than yours, but you can't follow it. Ship it?" Not until I can explain it, or my checks are strong enough to trust it anyway: the oracle on every small input, plus properties at full size. Code nobody understands is a cost for the next person who has to change it.
  • "How would you use it in a big codebase you don't know?" Read-only first: ask it to trace a request and list the files involved, check the trace, and draw the data flow. Then small changes behind characterization tests.
  • "It keeps making the same mistake. Now what?" Change the input, not the volume: add the failing example, shrink the step, or write that part myself.
  • "Here's a 1,000-line AI-generated change to review." Ask for it in reviewable pieces. Read the signature changes and the tests first, climb the ladder, and read every line only where the risk is.
  • "When does it hurt more than it helps?" When I can't check the output, when the hard part is a decision rather than typing, and when the code or data can't be shared.

✓What to remember

  1. Writing code got cheap; checking it is the job. The assistant is fast and well read, sees only its context, and can sound just as sure when it's wrong.
  2. Risks multiply: n changes that are each right with chance p are all right with chance pⁿ. 0.910 ≈ 35%. Examples prove something only if they could have failed.
  3. A check after every step changes the math: a wrong step gets through with (1 − p)(1 − c), so 0.9910 ≈ 90%. Commit after every passing check.
  4. Context block: signature, sizes, invariants, constraints, a "don't" list, examples with the hard case, a data-flow sketch, and a read-back of its assumptions before any code.
  5. Decide what "right" means first: examples, edge cases, properties. Tests whose expected values were read off the code share its bugs.
  6. An oracle you wrote yourself judges the fast version on every small input, smallest first: differential testing.
  7. Climb the ladder of checks as far as the risk deserves. Break the code on purpose to prove your tests can fail.
  8. Debug like a doctor: reproduce, shrink to 1-minimal, hypotheses with experiments, bisect (and skip what can't be tested), fix the cause, keep the regression test.
  9. Refactor behind a photo: characterization tests with the old code as the oracle, one named change at a time, behavior changes separately.
  10. Review with a catalogue, push back with a failing input, and know when not to use the assistant at all.

Warm-up · pen and paper

1. Compounding by hand

(a) Work out 0.910, 0.9520 and 0.9950, using repeated squaring for the first. (b) A 12-step session without checks: one assistant's steps are right 97% of the time, another's 85%. What's the chance of a fully right session with each? (c) A 20-step session whose steps are right 90% of the time. What catch rate c must the check after each step have for the whole session to end right 90% of the time?

Answer

(a) 0.9² = 0.81, 0.9⁴ ≈ 0.656, 0.9⁸ ≈ 0.430, so 0.9¹⁰ = 0.9⁸ × 0.9² ≈ 0.35. Then 0.95²⁰ ≈ 0.36 and 0.99⁵⁰ ≈ 0.61: twenty changes at 95% are about as risky as ten at 90%, and fifty at 99% still go wrong two sessions in five.

(b) 0.97¹² ≈ 0.69 and 0.85¹² ≈ 0.14. A gap of 12 points per step becomes a factor of about five per session.

(c) Each step must end right with some q where q²⁰ = 0.9, so q = 0.91/20 ≈ 0.99475. A wrong step gets through with 0.1 × (1 − c), so you need 0.1 × (1 − c) ≤ 0.00525, which means c ≥ 0.9475. The checks must catch about 95% of wrong steps.

Warm-up · pen and paper

3. Review it on paper

An assistant wrote this to return a list's items without repeats, keeping the first copy of each, in order. Find three problems, and for each give an input that shows it.

def unique_in_order(items, seen=[]):
    out = []
    for i in range(1, len(items)):
        if items[i] not in seen:
            seen.append(items[i])
            out.append(items[i])
    return out
Answer

(1) Off by one: range(1, len(items)) skips the first item, so [1, 2] gives [2]. (2) The default seen=[] is created once, when the function is defined, and every call shares it. Call it twice with [1, 2] and the second call returns []. Make seen a fresh local set instead. (3) A hidden loop: not in seen scans a list, inside the loop over the items. For 100,000 distinct items that's about n²/2 = 5 × 10⁹ comparisons; a set makes each check O(1) on average. Edge-case tests with a one-item list and two calls in a row would have caught (1) and (2) without reading a line.

Core · code

4. shrink(items, fails): delta debugging

In exercises/delta_debug.py. Return a sub-list of items, in the original order, that still fails and is 1-minimal (section 7). The tests count calls to fails, since each one stands for a slow run. With 4,000 items, a bug that needs 1 of them must take at most 100 calls, one that needs 2 at most 600, and one that needs 3 at most 1,000. Removing one item at a time costs about 4,000, so it fails. The tests also check that you remove by position (values repeat, and one bug needs three copies of the same value), keep the order, leave the input list alone, and cope with a test that isn't monotone.

Core · code

5. first_bad(n, is_bad): bisect with versions you can't test

In exercises/bisect_skip.py. is_bad(v) returns True, False, or None for a version that can't be tested. Return the range (lo, hi) that the answers can prove, like "5 or 6" in section 7. The tests count calls: at most log₂ n rounded up, plus 1 (21 for a million versions), plus 2 for every None answer, and never the same version twice. They try every case up to n = 10, blocks of untestable versions next to the answer, and every 4,096th version untestable, which is exactly where a binary search over 2²⁰ versions probes first.

Core · code

6. find_counterexample(candidate, oracle, alphabet, max_len): differential testing

In exercises/differential.py. Try every list over alphabet, shortest first, and return the first one where the candidate and the oracle disagree: a different answer, an exception, or a candidate that changed its input. The tests use a "most common value" problem with six wrong candidates and one correct one, and they count calls: at most 3 per list tried. Trying all 1,093 lists and then picking the smallest fails when the first disagreement is list 24.
