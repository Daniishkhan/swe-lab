Who goes next?

P0 in most coding roundsabout 55 minutes11 quick checks · 8 exercises

Stacks, queues and linked lists look like the easy part of a data structures course. Interviews use them anyway, for two reasons. First, picking the wrong one quietly turns O(n) code into O(n²), and interviewers watch for that. Second, a stack that keeps its items in sorted order (a monotonic stack) solves a whole family of "next bigger thing" problems in one pass, and most people never see it coming. This chapter builds all of them from one question: which item comes out next, and what does it cost to get it?

  2. Build a linked list in your head, and say when it beats an array (rarely) and why.
  3. Reverse a linked list and find a cycle with two pointers, and explain why they work.
  4. Pick a stack, queue or deque from the order a problem needs, and know the Python type for each.
  5. Explain a ring buffer, and why real systems bound their queues.

1The problem: a queue that falls behind

You run the job queue for a video site. Every uploaded video becomes a job: "make a 720p copy". Workers take jobs in the order they arrived, first come, first served. The jobs sit in a Python list. New jobs go on the end with jobs.append(job). A worker takes the oldest with jobs.pop(0).

On launch day, a backlog builds up: 1 million jobs waiting. Workers try to take 3,000 jobs a second. Each pop(0) on a million-item list takes about 0.35 milliseconds (measured on a laptop; your numbers will differ a little). 3,000 × 0.35 ms is about 1 second of work every second, spent doing nothing but taking jobs out of the list.

The server is now spending all its time on bookkeeping. Swap the list for collections.deque and popleft() takes about 60 nanoseconds, whether the backlog holds ten jobs or ten million. That's thousands of times faster, from changing one line.

Why? Both hold the same jobs in the same order. The difference is how they're laid out in memory, and that decides which end is cheap. This chapter is about that one idea.

2Why the front of an array is expensive

Recall from the hash map chapter: an array is a row of equal-sized slots, side by side in memory, with no gaps. Reading slot i is one step, because its address is arithmetic: start + i × slot size. A Python list is an array of references.

Now picture the job queue as a line of people standing on numbered floor tiles: tile 0, tile 1, tile 2, and so on. The rule of an array is that tile 0 always holds the first person. There are no gaps.

before pop(0):   tile  0    1    2    3    4
                     [ A ][ B ][ C ][ D ][ E ]

A leaves. Tile 0 must not stay empty, so everyone steps forward one tile:
                     [ B ][ C ][ D ][ E ]
                       ←    ←    ←    ←          4 moves for 5 people

With a million people: 999,999 moves to serve one person.

Where the picture breaks: the computer doesn't move people one at a time. It copies the whole block of references in one bulk memory copy (memmove), which is very fast per item. That's why it costs 0.35 ms and not seconds. But the copy still grows with the line: twice the backlog, twice the time.

Removing the person at the back is free: nobody behind them has to move. That's why append and pop() (from the end) are O(1), and pop(0) and insert(0, x) are O(n). Inserting or deleting in the middle is O(n) too: everyone after that spot shifts.

Python list operationCostWhy
a[i], a[i] = xO(1)address arithmetic
a.append(x), a.pop()O(1) (append is amortized)nobody behind the end has to move
a.pop(0), a.insert(0, x)O(n)everyone shifts one tile
a.insert(i, x), del a[i]O(n − i)everyone after i shifts

So the front of an array is expensive because of one rule: "slot 0 is the first item". Everything that follows in this chapter is a different way to break that rule.

An array is fast at the end and slow at the front. Removing or inserting near the front shifts every item behind it: O(n). If you need to take items from the front, you need a different layout.

You build a list of 100,000 log lines by calling lines.insert(0, line) for each one, so the newest is first. Roughly how many item moves does that take in total?

Right. Insert number k shifts the k items already there, so the total is 0 + 1 + … + 99,999 ≈ n²/2 = 5 × 10⁹. The fix: append them all (O(1) each), then reverse once at the end (O(n)). Or use a deque and appendleft.

Picture the people on tiles. Each new person goes on tile 0, so everyone already in line steps back one tile first. The 1st insert moves nobody, the 2nd moves 1 person, the 100,000th moves 99,999. Add them up: about 100,000 × 100,000 / 2 = 5 billion moves. Nothing is halved here, so there's no log; every insert pays for the whole line.

3Stop moving people: the linked list

The array's rule is "position in memory = position in line". What if we drop that rule? Let each item live wherever there's free memory, and give each one a note saying where the next item is.

That's a scavenger hunt. You don't get a list of every location. You get the first clue, and each clue says where the next one is hidden. The clues can be scattered all over town; the order lives in the clues, not in where they sit.

head
 │
 ▼
┌───┬───┐    ┌───┬───┐    ┌───┬───┐    ┌───┬────┐
│ A │ ●─┼───►│ B │ ●─┼───►│ C │ ●─┼───►│ D │None│
└───┴───┘    └───┴───┘    └───┴───┘    └───┴────┘

Each box is a node: a value plus a pointer (in Python, a reference) to the next node. The list itself only remembers the first node, the head. The last node points to None. That's a singly linked list.

class Node:
    def __init__(self, val, next=None):
        self.val = val
        self.next = next      # the clue: where the next node is

head = Node("A", Node("B", Node("C")))   # A → B → C
head = head.next                          # pop the front: O(1), nobody moves

Now look at what's cheap. Removing the front is one pointer change: head = head.next. Inserting after a node you're already holding is two pointer changes, no matter how long the list is. Nobody shifts, because nobody has a tile to keep.

What we gave up

The scavenger hunt has a price: to reach clue number 500,000, you must follow 499,999 clues first. There's no arithmetic to jump with, because nodes aren't in a row. So reading item i is O(i), and so is finding a value. A linked list is only fast at places you're already holding a pointer to.

Go deeper: why arrays usually win anyway (cache misses)

Big-O says a linked list and an array both scan n items in O(n). Real hardware disagrees. When the CPU reads memory, it pulls in a whole 64-byte chunk (a cache line) and guesses that you'll want the next chunk too. An array's items sit side by side, so a scan rides those guesses and runs at full speed. A linked list's nodes are scattered, so each .next can be a fresh trip to main memory, about 100 ns, while a cached read is about 1 ns.

That's why C++ experts say "use std::vector by default", and why Python's own deque is not one node per item but a linked list of blocks of 64 items: you get O(1) at both ends and most of the array's cache-friendliness. A senior answer mentions this when someone proposes a linked list "for performance".

A linked list holds 1 million songs. You need the song at position 500,000. How many steps?

Right. You start at the head and follow 499,999 next pointers. Halving needs to jump to the middle, and only an array can jump.

Think scavenger hunt: clue 500,000 is somewhere in town, and the only way to learn where is to read clue 499,999, which you find by reading clue 499,998… An array can compute an address (start + i × size), which is why it can jump, and why binary search needs one. A linked list only knows its head, so you walk: about 500,000 steps.

4Two-way links and dummy nodes

Here's a job a singly linked list can't do fast. You're holding a pointer to some node X in the middle, and you want to delete X. To unhook it, the node before X must point past it. But X only knows who comes after it. Finding who's before means walking from the head: O(n).

The fix is to give each node a second pointer, prev, to the node before it. Now X can tell its neighbors to point at each other:

        ┌──────┐      ┌──────┐      ┌──────┐
 ... ◄──┤  W   │◄────►│  X   │◄────►│  Y   ├──► ...
        └──────┘      └──────┘      └──────┘

 delete X:   X.prev.next = X.next      (W now points forward to Y)
             X.next.prev = X.prev      (Y now points back to W)
 Two pointer changes. O(1), even in a list of a billion nodes.

That's a doubly linked list. It costs one more pointer per node and gives O(1) removal of any node you're holding. It's the reason an LRU cache (a hash map pointing into a doubly linked list) can move an item to the front in O(1); you'll build one in the LRU cache topic.

Dummy nodes remove the special cases

Those two lines above crash when X is the first node (no X.prev) or the last (no X.next). The usual code fills up with if node is head branches, and that's where bugs hide in an interview.

The trick: put a permanent dummy node, called a sentinel, at each end. It holds no data. Real nodes always live between the two sentinels, so every real node has a real prev and a real next, and the two-line delete always works. An empty list is just the two sentinels pointing at each other.

empty:   [HEAD] ◄──► [TAIL]
3 items: [HEAD] ◄──► A ◄──► B ◄──► C ◄──► [TAIL]

first real item = HEAD.next      last real item = TAIL.prev

A prev pointer buys O(1) deletion of a node you hold. Sentinel nodes at both ends buy code with no edge cases: every real node has neighbors on both sides.

You keep a hash map from key to the node holding it, so you can find any node in O(1). Why does an LRU cache still need a doubly linked list instead of a singly linked one?

Exactly. The hash map hands you the node; the prev pointer lets you unhook it without walking from the head.

Picture a conga line where everyone holds the shoulders of the person in front, but nobody knows who's behind them. To pull out Sam, the person behind Sam has to grab whoever was in front of Sam. If Sam doesn't know who's behind, you walk the line from the start to find them. That walk is O(n). The prev pointer is Sam knowing who's behind, so the removal is two pointer changes. It costs memory, not saves it.

5Two linked list moves interviewers love

Linked list questions in interviews are mostly about moving pointers without losing anything. Two moves cover most of them.

Reverse a list in place

Picture a row of people each pointing at the person to their right. You want everyone pointing left instead. Walk along the row. At each person, you need to remember three things: the person you just turned around (prev), the person you're turning now (cur), and who cur was pointing at before you turned them (nxt). If you forget nxt, the rest of the row is lost: nobody else knows where it is.

Reversing 1 → 2 → 3 → 4 → 5 with three pointers. Watch the order inside each step: save nxt first, then turn cur's arrow around, then move both pointers right. Press ▶| to step.

Each node is visited once and gets one pointer change: O(n) time, O(1) extra memory. The new head is the old tail, which is where prev ends up. A recursive version is shorter to write but uses one stack frame per node, so on a 100,000-node list Python stops with RecursionError (its default limit is 1,000).

Fast and slow pointers

Two runners start at the head. The slow one moves one node per turn; the fast one moves two. Two things follow from that one rule:

  • Finding the middle. When the fast runner falls off the end, the slow one has gone half as far: it's at the middle. One pass, no need to count the length first.
  • Finding a cycle. A bad pointer can make the last node point back into the list, so walking it never ends. If there is a loop, both runners end up going round it, like runners on a circular track. Each turn, the fast one gains exactly one node on the slow one. The gap shrinks 1 at a time, so it can't skip past zero: the fast runner lands exactly on the slow one. If there's no loop, the fast runner reaches None instead. This is Floyd's cycle detection, also called "tortoise and hare".

Why not just remember every node you've seen in a set? That works, in O(n) time, but it uses O(n) memory: a million-node list means a million entries in the set. The two runners use two variables. When an interviewer says "in O(1) extra space", this is what they're after.

Explain it another way: why the fast runner can't jump over the slow one

Once both are in the loop, measure the gap: how many nodes the fast runner is behind the slow one, going forward around the loop. Each turn, slow moves 1 and fast moves 2, so the gap goes down by exactly 1. If the gap is 5, it goes 4, 3, 2, 1, 0. It can't go from 1 to −1, because it only ever drops by one. At 0 they're on the same node. The gap starts below the loop length L, so they meet within L turns after the slow runner enters the loop. Total: O(n).

Do other speeds work? Yes: if fast moves 3 per turn, the gap drops by 2 and can skip from 1 to −1 on one lap, but the runners still meet on a later lap. So 2 isn't the only speed that works. It's the usual choice because it reads the fewest .next pointers per turn, and because the 2:1 ratio makes the follow-up question easy (next aside).

Go deeper: where does the cycle start?

The common follow-up: return the node where the loop begins. Say the loop starts μ steps from the head and has length L. When the runners meet, slow has walked some distance s and fast exactly 2s, and the extra s is a whole number of laps. Some algebra shows that the meeting point is exactly μ steps (plus whole laps) short of the loop's start. So: leave one pointer at the meeting point, put another back at the head, and move both one step at a time. They meet at the start of the loop. Still O(n) time and O(1) memory. To get L, keep one pointer still and walk the other around until it comes back.

Reversal: keep prev, cur, nxt, and save nxt before you change cur.next. Fast/slow pointers: the speed difference of one node per turn finds the middle in one pass, and catches a cycle in O(1) memory.

An interviewer asks you to detect a cycle in a linked list of unknown length (it could be billions of nodes), using O(1) extra memory. What do you do?

Right: O(n) time and two variables of memory. Say why they must meet (the gap shrinks by exactly one per turn), not just that they do.

Both other answers have a hidden cost. The set holds every node, which is O(n) memory, exactly what was forbidden. Counting steps needs you to know the length in advance; a list with 10 million and one nodes and no cycle would fool it, and the length is unknown. Two runners on a circular track settle it with no memory: the faster one gains one node per turn, so if there's a loop it lands on the slower one; if there's no loop it reaches the end.

6The stack: last in, first out

Back to the question from the start: which item comes out next? The simplest answer is "the one you put in most recently". Picture a stack of plates in a cafeteria. You add plates on top and take plates from the top. The plate at the bottom has been there longest and comes out last.

That rule is called LIFO: last in, first out. A structure that only allows it is a stack, with three operations: push (put on top), pop (take the top), and peek (look at the top without taking it).

Notice that a stack only ever touches one end. That's the cheap end of an array! So a Python list is already a perfect stack:

stack = []
stack.append("a")    # push: O(1) amortized
stack.append("b")
top = stack[-1]      # peek: "b"
stack.pop()          # pop: "b", O(1)
if not stack: ...    # empty check

When a problem wants a stack

Reach for a stack whenever the most recent unfinished thing is the one to deal with next:

  • Undo: the last edit is the first one undone.
  • Function calls: the call stack from the complexity chapter. The most recent call finishes first.
  • Matching brackets: in ( [ { } ] ), each closer must match the most recent opener that isn't closed yet.
  • Depth-first search: go deep, and back up to the most recent fork when stuck (chapter 2).

Let's run the bracket check on {[()]}. Push each opener. On each closer, pop and check that it matches:

read  {   stack: {
read  [   stack: { [
read  (   stack: { [ (
read  )   pop ( → matches )   stack: { [
read  ]   pop [ → matches ]   stack: {
read  }   pop { → matches }   stack: (empty)   → valid, because the stack ended empty
Go deeper: a stack that knows its minimum in O(1)

A classic: support push, pop and get_min, all O(1). Scanning for the min is O(n). The trick is to push pairs: each entry stores its value and the minimum of everything at or below it, (x, min(x, previous_min)). Popping restores the old minimum automatically, because it's stored in the entry underneath. It's the same "remember what you'd otherwise recompute" trade as everywhere else: O(n) extra memory for O(1) answers.

A stack gives you the most recent item first (LIFO). It only uses one end, so a Python list with append and pop() is already an O(1) stack. Think "stack" when the latest unfinished thing must be handled first.

Using the stack method, is ( [ ) ] valid?

Right. After ( [ the top is [, and ) doesn't match it. Counting gets this wrong, which is exactly why the problem needs a stack and not counters.

Counting only checks that each kind of bracket is balanced, not that they nest. Trace the stack: push (, push [. Now ) arrives and must close the most recent open bracket, which is [. They don't match, so the string is invalid. Picture nested boxes: you can't close the outer box while the inner one is still open.

7The queue: first in, first out

The job queue from section 1 wants the opposite rule: the item that has waited longest comes out next. That's the line at a coffee shop. People join at the back and are served from the front. The rule is FIFO: first in, first out. A queue has enqueue (join at the back) and dequeue (leave from the front).

A queue uses both ends: one for adding, one for removing. With a plain Python list, one of those ends is the expensive front. That was the bug in section 1. There are two ways out.

Way 1: a linked list with a tail pointer

Keep a pointer to the head (where people leave) and one to the tail (where people join). Both operations are a pointer change or two: O(1). It works, but it pays the linked list's prices: an object per item and scattered memory.

Way 2: the ring buffer

Here's a cleverer fix that keeps the array. The problem was the rule "slot 0 is the front". So don't make people walk to the front; move the front. Keep a head index that says which slot holds the first person. Dequeue just moves head forward one slot. Nobody shifts.

That leaves empty slots behind the head. When the back reaches the end of the array, wrap around and reuse them. Picture the slots arranged in a circle, like seats around a round table, with a "front" marker that moves around the table. The next person to join sits size seats after the front (the last person in line is one seat before that):

next free slot  =  (head + size) % capacity      the % wraps it around the circle

When every seat is taken, get a bigger table: make an array twice the size and copy the items over in line order, starting from head. That copy is O(n), but it only happens when the size doubles, so it's amortized O(1) per enqueue, exactly like list append.

A ring buffer with 4 slots. Watch the front marker move instead of the items, the back wrap around to slot 0, and, when all 4 slots are full, the copy into 8 slots in line order. Press ▶| to step.

This is a ring buffer (or circular buffer). It's everywhere in real systems: network cards hand packets to the operating system through ring buffers, audio drivers stream sound through them, and Linux's io_uring is built from two of them. Those versions usually don't grow: a fixed-size ring is a bounded queue, and what to do when it's full is a design decision (more on that in section 11).

In Python: collections.deque

You don't need to build either one in an interview unless asked. Use collections.deque: append to enqueue, popleft to dequeue, both O(1). The one thing to avoid is list.pop(0). (queue.Queue is a different tool: a thread-safe queue with locks, for passing work between threads. It's slower and only for that.)

A queue serves the oldest item first (FIFO) and needs both ends. A Python list's front is O(n), so use collections.deque. Inside, the trick is either a linked list or a ring buffer: move the front marker instead of moving the items.

A ring buffer has 8 slots. head is 6 and it holds 4 items. Which slot does the next enqueue write to?

Right: (6 + 4) % 8 = 2. The items sit in slots 6, 7, 0, 1, so the next free seat around the table is 2.

Count around the table. The front is seat 6. Four people sit in seats 6, 7, then the table wraps around to 0, 1. The next person sits in seat 2. The formula says the same: (head + size) % capacity = (6 + 4) % 8 = 10 % 8 = 2. Slot 10 doesn't exist, and slot 4 is what you'd get by forgetting that the front moved.

8The deque: both ends, both ways

Sometimes you need to add and remove at both ends. A deque (say "deck", short for double-ended queue) allows all four: add front, add back, remove front, remove back, each O(1). A ring buffer does it naturally: adding at the front moves head one slot backwards, (head − 1) % capacity, and writes there. (In Python, -1 % 8 is 7, as wanted. In Java, C and JavaScript, % of a negative number is negative, so write (head − 1 + capacity) % capacity.)

Python's collections.deque is one, with append, appendleft, pop and popleft. It's also the right tool for "keep the last 1,000 log lines": deque(maxlen=1000) drops the oldest item automatically when you add a new one.

What a deque is not good at: the middle. d[i] on a Python deque is O(n) in general (it's fast near either end). If you need both ends and fast indexing, a ring buffer you write yourself gives you both.

Go deeper: a queue from two stacks

A classic interview question: build a queue using only two stacks. Push new items onto an in stack. To dequeue, if the out stack is empty, pop everything from in and push it onto out. Pouring reverses the order, so the oldest item ends up on top of out. Then pop from out.

One dequeue can cost O(n) (a big pour). But follow a single item: it's pushed onto in once, poured once, and popped from out once. Three moves per item, ever. So n operations cost at most about 3n moves: amortized O(1), the same accounting as list append. This is also how some functional languages build queues out of immutable lists.

A breadth-first search explores a graph level by level: it always expands the node that was discovered earliest. Which Python code keeps its to-do list?

Right. Earliest discovered first is FIFO, a queue, and popleft is O(1). pop(0) gives the same order but turns a graph search into O(V²) on big graphs.

Ask the chapter's question: which item comes out next? "Discovered earliest" means the one that has waited longest: a line at a counter, FIFO. pop() takes the newest (that's a stack, and it turns the search into depth-first). pop(0) takes the oldest, which is the right order, but every call shifts the whole list. With a million nodes in the to-do list that's the section 1 bug again. deque.popleft() gives the right order in O(1).

9The monotonic stack: who's taller to my right?

Now the idea that interviews love most, and that people find hardest. Here's the problem:

You have the daily high temperatures for the next 8 days: [73, 74, 75, 71, 69, 72, 76, 73]. For each day, how many days until a warmer one? If there's none, write 0.

The obvious way: for each day, look right until you find a warmer day. That's a loop inside a loop. With a year of data it's instant. With 10 years of hourly readings (87,600 values), if warm days are rare, it's up to about 3.8 billion comparisons. We want one pass.

The picture: people in a line, looking right

Line up 8 people whose heights are the temperatures. Each one is asking: "who is the first person to my right taller than me?" Now walk along the line from left to right, and keep a group of people who are still waiting for their answer.

When a new person arrives, look at the waiting group. Anyone in it who is shorter than the newcomer has their answer: it's the newcomer! They leave the group. Then the newcomer joins the group and waits too.

Here's the key observation. After each arrival, every waiter shorter than the newcomer has left, and the newcomer has joined at the end. So the waiting group, read from oldest to newest, always goes from tallest to shortest (equal heights can sit side by side). The shortest waiter is always the newest one.

That means a newcomer checks the newest waiters first, and can stop at the first one that's at least as tall: everyone older than that one is taller still, so none of them gets an answer today. Newest first, and only ever touching that end: that's a stack.

Next warmer day, one pass, left to right. The stack holds indexes of days still waiting (shown with their temperatures), and always reads warmest at the bottom to coolest at the top. When a warmer day arrives, every cooler day on top gets its answer and pops. Press ▶ Play.
def days_until_warmer(temps):
    answer = [0] * len(temps)
    waiting = []                              # indexes; temps go down from bottom to top
    for i, t in enumerate(temps):
        while waiting and temps[waiting[-1]] < t:
            j = waiting.pop()                 # day j has waited for a warmer day: it's today
            answer[j] = i - j
        waiting.append(i)                     # today waits too
    return answer                             # days still waiting keep 0

Why it's O(n), even with a loop inside a loop

The while loop sits inside the for loop, so it looks like n². Use the trick from the complexity chapter: don't count loops, count how many times each item is touched. Every index is pushed exactly once. Once popped, it's gone for good, so it's popped at most once. That's at most n pushes and n pops in the whole run, so the while loop runs at most n times in total. O(n) time, O(n) space for the stack.

This is a monotonic stack: a stack whose items are kept in sorted order (here, decreasing from bottom to top) by popping anything that would break the order before you push. "Monotonic" just means "only goes one way".

Explain it another way: a to-do pile of unanswered questions

Think of each day as a sticky note that says "tell me when it gets warmer than 71°". You stack the notes as the days go by. A new day at 72° walks up to the pile and reads the top note: 69°? Answered, throw it away. Next: 71°? Answered too. Next: 75°? Not answered, and every note under it asks about something even warmer, so stop. Put a "warmer than 72°" note on top.

A note is written once and thrown away once. Nobody ever reads a note, leaves it, and comes back to it later, except for the single note that makes them stop. That's why the total work is about two looks per note: O(n).

Flip the comparison and you get the other three variants. Which way the stack is sorted follows from the question:

Question for each itemPop while the top is…Stack from bottom to top
next greater to the rightsmaller than the newcomerdecreasing
next smaller to the rightbigger than the newcomerincreasing
previous greater to the left≤ the newcomer; the top left over is the answerdecreasing

The same move is behind "largest rectangle in a histogram", "stock span" and "trapping rain water". When a problem asks, for every item, about the nearest bigger or smaller item, think monotonic stack. Watch duplicates: "pop while smaller" and "pop while smaller or equal" give different answers for equal values, and problems like "sum of subarray minimums" need one strict and one non-strict side so equal values aren't counted twice.

A monotonic stack holds the items still waiting for an answer, kept in sorted order. A newcomer pops (and answers) everything it beats, then waits itself. Each item is pushed once and popped at most once, so the whole pass is O(n).

On 1 million temperatures, what's the most times the inner while loop body (the pop) can run, added up over the whole pass?

Right. Each pop removes an index that was pushed once and never comes back. A million pushes can feed at most a million pops. That's the whole proof of O(n).

Follow one day instead of one loop. Day 500 is pushed once, when we reach it. Later, at most one pop removes it, and it's never pushed again. So each of the million days causes at most one pop: a million pops in total, however they're spread out. One iteration of the for loop can pop many, but then the next ones have little left to pop. It's the same "count per item" trick as two pointers.

For each item, you want the next smaller item to its right. Scanning left to right, how should the stack be ordered from bottom to top?

Right. A newcomer answers every waiting item that's bigger than it, so those pop off. What's left underneath is smaller than the newcomer, so the stack goes up from bottom to top.

Run it on [5, 7, 3]. 5 waits. 7 arrives: is 7 smaller than 5? No, so 5 keeps waiting and 7 joins on top. Stack: 5, 7 (going up). 3 arrives: it's smaller than 7 and 5, so both get their answer (3) and pop. The waiting items are the ones nothing smaller has reached yet, and they sit in increasing order. The temperature stack was decreasing because it asked for greater.

10The monotonic deque: the max of a sliding window

One more problem, and it needs both ends of a deque. You monitor a server's CPU load, one reading per second. The dashboard shows the maximum over the last 60 seconds, updated every second. That's the "sliding window maximum": the max of every window of k consecutive items.

The obvious way recomputes max of 60 items every second: n × k work. For a day of readings with a 1-hour window, that's 86,400 × 3,600 ≈ 311 million comparisons. We want O(n).

Who can never be the max?

Picture the window as a group of job candidates. Each has a score (the reading) and a contract that ends when they slide out of the window. Now a new candidate arrives with a score of 90. Anyone already in the group with a score below 90 is now hopeless: the newcomer beats them, and the newcomer will stay in the window longer than they will. They can never be the max again. Drop them.

Keep the candidates who still have a chance in a deque, in arrival order. After dropping the hopeless ones, the scores in the deque go down from front to back, so the front is always the current max. Two rules:

  1. Back: when a reading arrives, pop from the back everything smaller than it (they're hopeless), then push it. That's the monotonic stack move.
  2. Front: if the front's contract has run out (its index has slid out of the window), pop it from the front.
Window of size 3 over [4, 3, 2, 1, 5, 3, 6, 2]. Green cells are in the window. The deque holds indexes of candidates; scores go down from front to back, so the front is the max. Watch 4 expire from the front at index 3, then 5 arrive and wipe out every candidate from the back.

Same accounting as before: each index enters the deque once and leaves once (from one end or the other). O(n) total, whatever the window size. Space is O(k): the deque holds at most one window's worth, plus the newcomer for a moment before the expired front leaves.

This one needs a deque, not a stack, because items leave from both ends: hopeless ones from the back, expired ones from the front.

Why not a heap? The obvious alternative keeps a max-heap (the heaps chapter) of (value, index) pairs and, before reading the top, throws away tops whose index has left the window. That's correct and O(n log n): fine as a first answer. The deque is the O(n) answer interviewers are fishing for, and it uses only O(k) memory, while the lazy heap can hold up to n entries.

Sliding window max: keep a deque of indexes whose values decrease from front to back. Pop smaller values off the back when a new value arrives; pop the front when it leaves the window. The front is always the max. Each index enters and leaves once: O(n).

In the sliding window max, why must the candidates live in a deque rather than a stack?

Right. A stack only lets you touch one end. The window has two separate reasons to remove things, and they happen at opposite ends.

Think about who leaves and from where. A newcomer knocks out weaker candidates who arrived recently: they're at the back. Time knocks out the oldest candidate, who sits at the front. So you need to remove from both ends, and only a deque does both in O(1). A stack can keep sorted order just fine (that's section 9); what it can't do is let go of its oldest item.

11Queues in real systems: bounded or not?

Back to the video site. Say the deque fixed the speed problem, but uploads keep arriving faster than workers can process them. The queue grows, and grows. An unbounded queue doesn't fix overload; it hides it until the machine runs out of memory, and meanwhile every job waits longer and longer.

Picture a sink with the tap running faster than the drain. A bigger sink only delays the flood. Real systems put a limit on the queue and decide what happens when it's full:

  • Block the producer (backpressure): the uploader waits until there's room. The "turn down the tap" option. queue.Queue(maxsize=…) does this.
  • Reject new work: return "busy, try later" (HTTP 503 or 429). The client can retry elsewhere.
  • Drop the oldest: keep the newest data, as deque(maxlen=…) does. Right for metrics and logs, where fresh data matters more than old.

A ring buffer is the natural shape for a bounded queue: fixed memory, no allocation while running, and "full" is just size == capacity. A senior answer to "why a queue here?" includes "and what happens when it fills up".

Go deeper: Little's law, and why queues make latency explode

Little's law: the average number of items in a system = arrival rate × average time each spends in it. If 3,000 jobs arrive per second and each spends 2 s in the system, about 6,000 are in it at any moment. It holds for any stable queue, whatever the distribution.

The painful part is what happens near full use. For a simple single-server queue with random arrivals, the average time a job spends in the system (waiting plus being served) grows like 1 / (1 − utilization). At 50% busy, it's about 2× the service time; at 90%, 10×; at 99%, 100×. That's why systems aim to run well below 100% and why a queue that's "usually short" can suddenly get very long.

A service keeps the last 10,000 request latencies to compute a p99 every minute. Old values beyond 10,000 don't matter. Which structure?

Right. A bounded deque (a ring buffer, in effect) drops the oldest value in O(1) on each append and never grows past 10,000.

The list works but pays the front-of-array price: every pop(0) shifts 9,999 references, on every request. The unbounded queue can grow without limit between trims under a traffic spike, which is exactly when you're measuring. "Keep the newest k, drop the oldest" is what a bounded deque does: deque(maxlen=10000), O(1) per append, fixed memory.

12What to say in the interview

For a problem like "for each day, the next warmer day", a strong answer has this shape:

"The brute force scans right from every day: O(n²) in the worst case, for example when temperatures only go down. But once a warmer day arrives, every cooler day still waiting has its answer, and the days still waiting are always in decreasing order. So I keep them on a stack. Each new day pops and answers every cooler day on top, then pushes itself. Each index is pushed once and popped at most once, so it's O(n) time and O(n) space for the stack in the worst case. If it were a sliding window, I'd use a deque instead, because items also expire from the front."

Habits that make you sound senior:

  • Name the order the problem needs (most recent, oldest, both ends, smallest) before naming the structure.
  • Never write list.pop(0) in a loop. Say "deque" and why.
  • For monotonic stacks, prove the O(n) by counting pushes and pops per item.
  • For linked lists, draw the pointers and say which one you save before you overwrite it.
  • For queues in a design, say how big they can get and what happens when they're full.

✓What to remember

  1. Arrays are cheap at the end and O(n) at the front, because every item behind has to shift.
  2. A linked list stores order in pointers, so the front is O(1), but reaching item i is O(i), and scattered nodes are slow in practice.
  3. Doubly linked lists delete a node you hold in O(1); sentinels remove the edge cases.
  4. Reverse: save nxt, flip cur.next, advance. Fast/slow pointers find the middle and cycles in O(1) memory.
  5. Stack = most recent first: list. Queue = oldest first: deque.popleft. Never pop(0).
  6. A ring buffer moves the front marker, not the items: next free slot = (head + size) % capacity.
  7. Monotonic stack: keep waiting items sorted, pop what the newcomer beats. Each item in once and out once, so O(n).
  8. Sliding window max: a decreasing deque; pop hopeless items at the back, expired ones at the front.
  9. Real queues need a bound and a plan for "full": block, reject, or drop the oldest.

1. Run the monotonic stack by hand

Find the next greater value (not the distance) for each item of [2, 7, 3, 5, 4, 6, 8], using a stack of indexes. Write the stack after each item, and count the total pushes and pops.

Answer

Stack after each item (as values): [2] → [7] (7 pops 2: answer 7) → [7, 3] → [7, 5] (5 pops 3: answer 5) → [7, 5, 4] → [7, 6] (6 pops 4 then 5: both answer 6) → [8] (8 pops 6 then 7: both answer 8). Answers: [7, 8, 5, 6, 6, 8, −1]. 7 pushes and 6 pops: never more pops than pushes, which is the O(n).

Warm-up · pen and paper

2. Ring buffer bookkeeping

A ring buffer has capacity 5, head = 0, size 0. Do: enqueue A, B, C, D; dequeue twice; enqueue E, F, G. Give the array, head and size at the end. Is it full? Where would a front-insert (deque appendleft) of Z go?

Answer

After A–D: [A, B, C, D, _], head 0, size 4. Two dequeues: head 2, size 2. Slots 0 and 1 are free. Set them to None as you dequeue: they're not part of the line any more, but in Python or Java a leftover reference would keep the old object from being freed. E goes to (2 + 2) % 5 = 4, F to (2 + 3) % 5 = 0, G to (2 + 4) % 5 = 1. Array: [F, G, C, D, E], head 2, size 5: full. A front-insert of Z must grow first: copy C, D, E, F, G into slots 0–4 of a 10-slot array, head 0. Then Z goes to (0 − 1) % 10 = slot 9, and head becomes 9. The line reads Z, C, D, E, F, G.
