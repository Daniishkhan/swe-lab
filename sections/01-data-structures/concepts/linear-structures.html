Lines, chains, and waiting lists

1Why do plain lists hurt when the front moves?

Your worker service keeps 500,000 pending jobs in a Python list and pulls the oldest job off the front with jobs.pop(0). On 100 test jobs it finishes instantly.

Under real traffic, draining 500,000 jobs slides 499,999 slots left on the first pop, 499,998 on the second, and so on — roughly 125 billion slot copies. Your worker burns 30+ seconds shuffling pointers before running any real work.

Picture a row of numbered theater seats (0, 1, 2, …). Tight packing makes jumping straight to seat #42 instant arithmetic, yet it leaves zero gaps: whenever someone leaves seat 0, every remaining person stands up and scoots one seat left.

Tight packing makes indexing fast and front removals expensive. To drop the front in O(1), move where "front" starts instead of shifting every item.

Solving this shifting problem unlocks four staples of coding rounds:

  • Pointer surgery: reversing, splitting, or checking cycles in linked chains with zero extra memory.
  • Fast caches & queues: O(1) LRU cache eviction and O(1) double-ended queues.
  • Nested matching: validating brackets, undo stacks, and tracking a running minimum.
  • One-pass waiting lines: next warmer day, sliding-window maximum, and largest histogram rectangle.
A Python list is fast at the back (append, pop) and fast by index (a[i]). Inserting or deleting at the front or middle costs O(n) shifts.

You have 100,000 items in a Python list. Which loop finishes in O(n) total time instead of O(n²)?

Right! Removing from the back leaves all other seats still: n steps at O(1) each gives O(n) total.

Count total moves on a 4-seat row [A, B, C, D]: removing seat 0 shifts 3, then 2, then 1 items (n(n−1)/2 = O(n²)). Removing seat 3, then 2, then 1 shifts zero items at every step.

2What if items didn't have to sit side by side?

To escape theater-seat shifting, let people stand anywhere in the room and hold hands in a chain. Each person (a node) holds two fields: a value (val) and a link to the next person (next, or None at the tail). Splicing a newcomer behind a node you already hold takes two pointer writes and zero shifts:

Splicing 25 after 20 takes two writes: new.next = cur.next first, then cur.next = new so node 30 is never dropped.

Where the hand-holding picture breaks: walking past 100,000 items in a flat array vs. scattered nodes are both O(n) on paper, yet real CPUs load contiguous 64-byte cache lines in bursts. Scanning a Python list beats walking a linked list by a huge constant factor, so production code only reaches for linked nodes when it needs O(1) middle unlinks.

3How do you stop losing the head or walking backward?

Linked-list code breaks in two predictable places: editing the very first node (which has no predecessor) and removing a middle node when you only hold a forward link. Two lightweight upgrades fix both:

  • Dummy head (sentinel): whenever an edit might change which node is first (delete, merge, partition), prepend one throwaway node: dummy = Node(0, head). Now every real node has a predecessor, removing special-case head branches; return dummy.next at the end.
  • Doubly linked list (prev + next): give every node a backward link (plus dummy head and tail sentinels), and unlinking any known node x becomes two pointer writes: x.prev.next = x.next; x.next.prev = x.prev.
Go deeper: how an LRU cache pairs a hash map with a doubly linked list

An LRU (Least Recently Used) cache needs O(1) get(key), O(1) put(key, val), and O(1) eviction of the stalest key. A hash map from Chapter 1.1 stores key → Node for O(1) lookup; a doubly linked list tracks recency (newest right after dummy head, oldest right before dummy tail). On every hit, unlink node in O(1) via prev/next and move it to the front. On overflow, evict tail.prev and delete its key from the map.

Go deeper: deleting node x in a singly linked list without head

A classic trick question hands you only x (not head) and asks to delete it. You can copy x.val = x.next.val and skip x.next = x.next.next — provided x isn't the tail and nothing outside holds a reference to x.next. In real systems (like an LRU cache), external pointers to nodes exist, which is why you use a doubly linked list instead of mutating values.

A hash map hands you a direct pointer to node x in the middle of a 100,000-node list, and you must remove x in O(1). Which layout makes that work?

Spot on! Unlinking x rewires the node before x to point past it; only x.prev reaches that predecessor in one jump.

Trace removing B from A → B → C when your finger is only on B. To make A point to C, you must reach A. A singly linked chain has no arrow from B back to A, and a flat array still shifts everything after B left in O(n).

4How do stacks and queues keep lines disciplined?

A stack and a queue are rules about which end of a line you touch:

  • Stack (LIFO — Last In, First Out): push and pop only at the back. In Python, a plain list is already an O(1) amortized stack via append() and pop(). Use it whenever the newest open task must close first (nested brackets, undo history, explicit DFS).
  • Queue (FIFO — First In, First Out): join at the back (append), leave from the front (popleft). Always use collections.deque so both ends stay O(1).

Classic interview twist — Min Stack: support push, pop, top, and get_min all in O(1). A single min_so_far integer breaks when you pop the minimum. Instead, store (val, min_at_or_below) at every level (or push onto a parallel mins stack whenever val <= mins[-1] — using <=, NOT strict <, so duplicate minimums aren't erased early):

class MinStack:
    def __init__(self): self.st = []            # stores (val, min_so_far)
    def push(self, x):
        lo = x if not self.st else min(x, self.st[-1][1])
        self.st.append((x, lo))
    def pop(self): return self.st.pop()[0]
    def top(self): return self.st[-1][0]
    def get_min(self): return self.st[-1][1]    # O(1), survives any pop
Go deeper: building an amortized O(1) queue from two stacks

Keep two stacks: inbox (for enqueue) and outbox (for dequeue). Push arrivals onto inbox in O(1). On dequeue, if outbox is empty, pop every item from inbox and push it onto outbox — reversing the order into FIFO! Each item is moved from inbox to outbox at most once, so amortized cost per operation is O(1).

You implement a Min Stack with a parallel mins stack, pushing only when x < mins[-1] (strict). You push 5, 2, 7, 2 then pop 2. What happens next?

Sharp catch! Tracking duplicates with <= (or storing (val, cur_min) pairs) guarantees popping the top 2 still leaves 2 as the active minimum.

Trace the two stacks step by step: after pushing 5, 2, 7, 2 with strict <, vals = [5, 2, 7, 2] while mins = [5, 2] (the second 2 was skipped). Popping the top 2 sees 2 == mins[-1] and pops 2 off mins, leaving mins = [5] even though [5, 2, 7] still holds a 2!

5How do you rewire or inspect a chain in O(1) memory?

Singly linked list questions test whether you can track pointers cleanly in O(n) time and O(1) extra memory — with zero recursion (a 200,000-node list blows Python's ~1,000-frame recursion limit). Three moves cover almost all of them:

Move 1: Reverse in place

Walk three pointers — prev (reversed prefix), cur (node being flipped), and nxt (saved bookmark to the untouched suffix). Always save nxt = cur.next before overwriting cur.next = prev:

prev, cur = None, head
while cur is not None:
    nxt = cur.next      # 1. save the rest of the chain first
    cur.next = prev     # 2. flip cur's arrow backward
    prev, cur = cur, nxt
return prev             # old tail is now the new head
Step through reversing 1 → 2 → 3 → 4 → None. At every pause, prev heads the reversed prefix and cur heads the remaining suffix.

Moves 2 & 3: Middle and cycle detection (fast & slow runners)

Start slow = fast = head and move slow by 1 step and fast by 2 steps while fast and fast.next:

  • Middle in one pass: when fast reaches the end, slow lands on the middle (for even length 1→2→3→4, the second middle 3).
  • Cycle detection (Floyd's tortoise & hare): advance first, then check if slow is fast: return True (always use object identity is, never slow.val == fast.val, so duplicate values don't trigger false positives!).
slow = fast = head
while fast is not None and fast.next is not None:
    slow = slow.next
    fast = fast.next.next
    if slow is fast:    # check AFTER moving, using identity (`is`)
        return True
return False

Why must fast catch slow inside a loop? Once both runners enter the ring, measure the forward distance d from fast to slow. Each turn changes the gap by −2 + 1 = −1. A positive integer dropping by 1 every turn (d, d−1, …, 1, 0) cannot jump over 0.

Starting slow = fast = 1, after two turns slow enters at 3 while fast is at 5; two turns later they meet at 5.
Go deeper: first middle for splitting, and finding the cycle entry (Floyd phase 2)

Splitting a list (merge sort / palindrome): starting slow = fast = head lands on the second middle of an even list, which doesn't let you sever the left half. Start fast = head.next instead so slow stops at the first middle, then cut with right = slow.next; slow.next = None.

Finding the exact loop entry: if the tail has length a, the cycle has length c, and they meet at offset b past entry, then 2(a + b) = a + b + k·c, so a = k·c − b. Reset one pointer to head, walk both at speed 1, and they collide right on the loop entrance.

Inside a 2-node loop (A → B → A), slow starts at A (+1 step/turn) and fast starts at B (+3 steps/turn). What happens?

Exact! Relative speed 3 − 1 = 2 preserves parity: starting at gap 1 on an even-length ring keeps the gap odd forever! Relative speed 2 − 1 = 1 guarantees meeting from any starting offset.

Trace turn 1 by hand: slow moves 1 step A → B; fast moves 3 steps B → A → B → A. Now slow = B, fast = A — the exact mirror image! On turn 2 they swap right back, looping forever.

6Can we keep array speed without shifting the front?

Linked lists give O(1) ends at the cost of pointer overhead, scattered RAM, and O(n) indexing. To get both contiguous array indexing d[i] and O(1) push/pop at both ends, bend our theater row into a circle of numbered chairs (a ring buffer).

Store three fields: backing array buf of length cap, front chair index head, and count size. Modulo % cap wraps past chair cap − 1 back to chair 0:

  • Index d[i]: map negative i += size, check 0 <= i < size (else IndexError), return buf[(head + i) % cap].
  • Back append(x) / front appendleft(x): if size == cap, double first (below). Back writes buf[(head + size) % cap] = x; front steps head = (head - 1) % cap and writes buf[head] = x (in Python, (0 - 1) % 4 == 3). Increment size.
  • pop() / popleft(): if size == 0, raise IndexError! Clear vacated slots to None so old objects can be garbage-collected, move head = (head + 1) % cap on popleft, decrement size.
After appending A, B, C, popping A and B, and appending D, E, F, the line wraps from slot 3 back to slot 0 with zero shifts.

Growing when full: never copy raw slots 0..cap-1 straight into a bigger array — that tears a wrapped line down the middle! Unwind in logical order starting at head, then reset head = 0:

new_buf = [None] * (cap * 2)
for i in range(size):
    new_buf[i] = buf[(head + i) % cap]
buf, head = new_buf, 0

Doubling keeps total copies under 2n across n appends — amortized O(1) (Chapter 2.1). A steady queue holding at most 1,000 items across 300,000 enqueues and dequeues grows through powers of two up to 1,024 slots (~1,020 total copies) and then never copies again.

Go deeper: shrinking without thrashing, power-of-2 bitmasks, and CPython deque

Shrinking safely: halving capacity at size == cap // 2 causes O(n) thrashing on alternating push/pop right at the boundary. Shrinking only when size <= cap // 4 leaves a quarter-buffer of hysteresis and preserves amortized O(1).

Fast bitmasks: when cap is a power of two, low-level ring buffers replace % cap with bitwise & (cap - 1) (avoiding integer division and negative-modulo bugs in C++/Java).

CPython's collections.deque: uses a doubly linked list of 64-slot blocks — O(1) ends with zero resize pauses and good cache locality, trading away O(1) random middle indexing (d[i] is O(n/64) = O(n)).

A ring buffer has cap = 8, head = 0, and size = 3 (items at slots 0, 1, 2). You call appendleft("z"). What changes?

Exact! (0 - 1) % 8 == 7. Only one slot is written, and logical item 1 now reads from (7 + 1) % 8 == 0.

Picture chairs 0..7 in a circle: chair 7 sits right in front of chair 0. Putting "z" at the front without moving anyone steps head one chair backward to (0 - 1) % 8 = 7 and writes slot 7.

7Why re-scan people you already know can't win?

Now extend our line-of-people picture to one of the highest-leverage patterns in coding rounds. Given heights nums = [2, 1, 2, 4, 3], find for every position the first strictly taller value to its right (or -1). Scanning right from each item takes O(n²) on a falling list.

Monotonic stack (next greater / next smaller)

Walk left to right keeping a waiting stack of indexes whose answer hasn't arrived yet. When newcomer val arrives, ask: "Is val taller than the person on top of the waiting stack?" While yes, pop that person — val is their exact answer! Then push the newcomer's index.

Watch next_greater([2, 1, 2, 4, 3]). Because anyone shorter than a newcomer is popped before the newcomer enters, remaining stack heights stay non-increasing.

Why the nested while is still O(n): every index is pushed once and popped at most once — at most 2n stack operations across the entire run! Note where the line picture needs care: equal heights do not answer a "strictly taller" query, so the waiting stack stays non-increasing (weakly decreasing — equal values stay stacked).

ans = [-1] * len(nums)
waiting = []                    # indexes; nums[waiting] is non-increasing
for i, val in enumerate(nums):
    while waiting and nums[waiting[-1]] < val:
        ans[waiting.pop()] = val
    waiting.append(i)
return ans
The query picks the stack order: next greater evicts smaller waiters (stack stays decreasing); next smaller evicts taller waiters (stack stays increasing).

Monotonic deque (sliding window maximum)

Given nums and window width k, return the max of every length-k window. Taking max() per window costs (n − k + 1)·k (~5.6 billion reads for n = 300,000, k = 20,000). Apply the same eviction insight: an older value 3 sitting left of a newer 5 can never win this or any future window (it's smaller and expires sooner) — pop it from the back! Meanwhile, winners at the front eventually fall past the window's left edge (dq[0] <= i - k) — pop them from the front.

Front door drops winners that fell behind the window; back door drops dominated losers. Four short steps keep total work O(n) for any k.

Trace the four steps at each index i (guarding empty nums up front):

from collections import deque

def sliding_window_max(nums, k):
    if not nums: return []
    dq, out = deque(), []
    for i, val in enumerate(nums):
        while dq and nums[dq[-1]] <= val:   # 1. evict dominated back items
            dq.pop()
        dq.append(i)                        # 2. add newcomer index
        if dq[0] <= i - k:                  # 3. expire front if out of window
            dq.popleft()
        if i >= k - 1:                      # 4. record window max
            out.append(nums[dq[0]])
    return out

Why store indexes? Storing indexes makes expiration exact (dq[0] <= i - k) while letting you evict equal older values with <=. (You can store raw values on a random-access array if you switch back-eviction to strict < and expire via dq[0] == nums[i - k], but indexes generalize cleanly to streams.)

Go deeper: streaming time-based windows without a backing array

What if events arrive as a live stream (timestamp, val) and you need the maximum over the last 60 seconds (variable count per window, no array nums)? Store (timestamp, val) pairs directly in the deque: evict back entries with dq[-1][1] <= val, push (ts, val), and expire front entries while dq[0][0] < ts - 60. Same amortized O(1) per event.

You want the next strictly smaller bar to the right of every bar in a histogram. Which pop condition keeps the right invariant in the waiting stack?

Exact! Only a strictly shorter bar answers "next strictly smaller" (so >, not >= — equal bars stay waiting), leaving the stack non-decreasing from bottom to top.

Test on [3, 3, 1]: index 0 (height 3) needs the next strictly smaller bar, which is 1 (not the equal 3 at index 1). So 3 must NOT pop 3 (rules out >=), while 1 MUST pop both 3s (nums[top] > val).

8How can this break — and when is it the wrong tool?

Four classic bare-editor bugs sink candidates on these exact structures:

  1. has_cycle traps: checking slow is fast before moving them (always returns True immediately!), or writing slow.val == fast.val instead of slow is fast (fails on acyclic lists with duplicate values like [5, 5]).
  2. Forgetting to detach the old tail: reversing a sublist without setting the old head's .next to the next segment leaves a silent cycle.
  3. Negative modulo outside Python: Python's (0 - 1) % 8 == 7 wraps cleanly, while C++, Java, and JavaScript return -1 — always write (head - 1 + cap) % cap in those languages.
  4. < vs <= on duplicates: in next_greater, changing < to <= wrongly marks an equal neighbor as "strictly greater".

When these structures are the wrong tool:

  • Need fast key lookup? Use a hash map (Chapter 1.1), not a linked list scan.
  • Need a sliding-window median or arbitrary k-th smallest? A monotonic deque only tracks the extreme (min or max), because smaller items get discarded forever — use two heaps (Chapter 1.4) or a balanced tree instead.

Why can a monotonic deque solve sliding-window maximum in O(n), yet fail for sliding-window median?

Spot on! A smaller older value can never beat a newer larger value for the maximum, yet it can still become the median once bigger numbers slide out. Monotonic eviction only works when dominance is permanent.

Trace window size k = 3 on [4, 9, 1, 2]: when 9 arrives, a max-deque throws away 4 forever — safe for max, fatal for median, because the median of [4, 9, 1] IS 4!

9How you use this in interviews (and what to say)

Three flagship interview drills reuse the exact machinery from Sections 4 and 7:

  • Valid Parentheses (stack): map each closing bracket to its opener ({')':'(', ']':'[', '}':'{'}). Push openers; on a closer, reject if the stack is empty or stack.pop() != match[ch]; at the end return not stack.
  • Daily Temperatures (monotonic stack): identical to next_greater, except record the wait distance ans[idx] = i - idx instead of val.
  • Largest Rectangle in Histogram (monotonic stack): maintain an increasing stack of bar indexes, and append a trailing sentinel height 0 so every remaining bar flushes out cleanly at the end:
def largest_rectangle(heights):
    st, best = [], 0                    # increasing stack of indexes
    for i, h in enumerate(heights + [0]):
        while st and heights[st[-1]] > h:
            bar = heights[st.pop()]
            left = st[-1] if st else -1 # left boundary (<= bar)
            best = max(best, bar * (i - left - 1))
        st.append(i)
    return best

What to say in the interview (4 beats, ~90 seconds):

  1. Arrays vs. linked lists: "Contiguous arrays give O(1) indexing and strong CPU cache locality, but front/middle edits shift O(n) items. Linked lists give O(1) splices at a known pointer — and doubly linked lists add O(1) arbitrary unlink (the core of an LRU cache) — while sacrificing indexing and cache locality."
  2. In-place pointer moves: "Reversing tracks prev/cur/nxt (saving nxt before flipping); fast/slow runners find the middle or detect a cycle in O(1) space because relative speed 1 closes any cycle gap by 1 per step."
  3. Ring buffers: "Wrapping an array with (head + i) % cap gives O(1) push/pop at both ends and O(1) indexing; unwinding from head when doubling preserves amortized O(1)."
  4. Monotonic stack/deque: "Evicting dominated candidates keeps a waiting stack or deque sorted; since every index is pushed once and popped at most once, the nested while stays O(n) total."
