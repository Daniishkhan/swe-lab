Chapter 1 · Part 10

Totals over any range

P2 the follow-up when a range question also has updatesabout 55 minutes10 quick checks · 8 exercises

"Sum of the items from i to j" is easy once: add them up. It gets hard when the questions keep coming and the items keep changing. Keep only the raw items and every question re-adds thousands of them. Keep running totals and every change rewrites thousands of them. This chapter builds the two structures that get both down to about log₂ n steps: the segment tree, which works for sums, minimums, maximums and more, and the Fenwick tree, a lean version for sums in a single array of n slots, with loops five lines long.

By the end you'll be able to

  1. Explain, with numbers, why a plain array and a running-totals array each fail once updates and range questions are mixed.
  2. Build a segment tree, and explain why any range is covered by at most two stored blocks per level, so a query is O(log n).
  3. Use one segment tree for any associative combine (sum, min, max, gcd, joining strings) and say what the identity is for.
  4. Explain a Fenwick tree as "a segment tree with the right children removed", and walk its two loops using i & -i.
  5. Add to a whole range at once with a difference array, and describe lazy propagation.
  6. Solve rank, k-th item and "count smaller after self" questions, and pick the right structure for a problem.

How to read this: go top to bottom. Answer each quick check before reading on; a wrong answer gets the idea explained a different way. Grey "Go deeper" boxes are optional on a first read. 1The problem: a million counters that won't sit still

You run an analytics service. For one website it keeps a count of page views for every second of the last 12 days: 12 × 86,400 = 1,036,800 counters, about a million. Dashboards ask questions like "how many views between Tuesday 09:00 and Friday 17:30?", any start, any end, 20,000 times a second.

At the same time, phones that were offline upload their saved events late. Each one adds 1 to the counter of some second in the past, also about 20,000 times a second.

Try the two obvious designs. Keep only the counters: a late event is one write, but a question about the last week adds up 604,800 counters, and 20,000 of those a second is about 12 billion additions per second. Keep running totals instead (total views from the start up to each second): a question becomes one subtraction, but a late event at a random second changes the running total of every second after it, about half a million writes on average. 20,000 of those a second is about 10 billion writes per second.

The structures in this chapter do both jobs in about 20 to 40 steps, because log₂ of a million is about 20. That's roughly 20,000 × 40 + 20,000 × 20 = 1.2 million steps per second for the whole service, one core, barely busy.

The dashboards stop changing: no more late events, ever. 20,000 range questions a second keep coming. What's the best design now?

Right. Running totals are only expensive to change. If nothing changes, you pay O(n) once and every question after that is O(1). The trees in this chapter are for the mixed case: changes and questions arriving together.

Look at what each design pays for. Raw counters pay at question time: a week is 604,800 additions, every time, updates or not. Running totals pay at change time, and with no changes that bill is zero after one O(n) pass to build them. Then "views from a to b" is total(b) minus total(a), one subtraction, which beats the tree's 20 to 40 steps. Reach for a tree only when both kinds of operation keep arriving.

2Two ways that almost work

Shrink the problem to 8 jars of coins, so you can see every number. The jars hold 3, 1, 4, 1, 5, 9, 2 and 6 coins, numbered 0 to 7. Two kinds of request come in: "add a coin to jar 2" and "how many coins in jars 1 to 6?".

Design A: write nothing down. To answer a range question, open every jar in the range and count. Adding a coin is one action, but a range of 6 jars is 6 counts, and a range of a million jars is a million.

Design B: running totals. Tape a note to each jar with the number of coins in it and every jar to its left. That's a prefix sum: the sum of a prefix (a starting piece) of the list. With one extra 0 in front, so that "the first 0 jars" has a total too:

 jar          0   1   2   3   4   5   6   7
 coins        3   1   4   1   5   9   2   6
 prefix   0   3   4   8   9  14  23  25  31     prefix[k] = coins in jars 0..k-1

 coins in jars 1..6  =  prefix[7] − prefix[1]  =  25 − 3  =  22
 check:                 1 + 4 + 1 + 5 + 9 + 2  =  22

Any range is now one subtraction: everything up to the end, minus everything before the start. Writing ranges half-open, as [lo, hi) meaning "from lo up to but not including hi", like a Python slice, the rule is sum(lo, hi) = prefix[hi] − prefix[lo].

Now add a coin to jar 2. The notes on jars 2, 3, 4, 5, 6 and 7 are all wrong: each of them counted jar 2. Six notes to rewrite, and for a jar near the start of a million-jar row, nearly a million.

Here's the tension, stated in general. Each stored number is either a small fact (one jar), which is cheap to update but you need many of them per question, or a big total, which answers a question in one read but depends on many jars, so many of them change on every update. Design A stores only small facts; design B stores only big totals. What we want is a set of stored totals where:

  1. every jar is counted in only a few stored totals (so an update rewrites few), and
  2. every range can be built from only a few stored totals (so a question reads few).

Raw items make questions slow; running totals make updates slow. The goal is a middle ground: store partial totals so that each item sits in few of them and each range is made of few of them.

A prefix-sum array covers 1,000,000 items. You add 5 to item 999,990. How many prefix entries change?

Right. prefix[k] counts items 0..k−1, so it includes item 999,990 only when k ≥ 999,991. That's prefix[999,991] up to prefix[1,000,000]: 10 entries. Updates near the end are cheap; updates near the start cost almost n. On average, half of n.

Ask of each stored total: "did it count this item?". prefix[k] is the sum of items 0 to k − 1. Item 999,990 is in that sum only if k − 1 ≥ 999,990, so k runs from 999,991 to 1,000,000: 10 totals. An update at item 0 would hit all 1,000,000 of them. "O(n) per update" is the worst case, and the average is n/2: still far too many for the analytics service, whose late events land all over the window.

3Write down a few subtotals: blocks

A bank teller doesn't count a pile of coins one by one. The coins come in rolls of 50, with the count printed on the paper. She counts the rolls, then the few loose coins. Do the same with the million counters: cut them into blocks of 1,000, and next to each block write its total.

 counters  [ c0 … c999 ] [ c1000 … c1999 ] [ c2000 … c2999 ]  …  [ c999000 … c999999 ]
 blocks         B0              B1                B2                    B999
                                    ←────────── a range ──────────→
                     loose ends ↑       whole blocks in the middle       ↑ loose ends

An update changes one counter and one block total: 2 writes. A range question adds the loose counters at its two ends (at most 999 at each end) and the whole blocks in between (at most about 1,000 block totals). That's at most about 3,000 additions instead of a million. For the analytics service, 20,000 questions × 3,000 is 60 million additions a second, down from 12 billion.

Why 1,000? The block size b is a knob. Bigger blocks mean fewer block totals to add, but longer loose ends. A range costs up to about 2b + n/b additions. The two parts balance when 2b = n/b, at b = √(n/2), about 707 for a million, and any b within a small factor of √n (1,000 here) is nearly as good. That's why this idea is called square-root decomposition, and why it costs O(√n) per question.

Here's the flaw. The best block size still leaves about 3,000 additions per question, and look at where most of them go: adding up a run of up to 1,000 block totals. But "add up a run of block totals" is the very same problem we started with, on a list 1,000 times shorter. So use the same trick on it: group the blocks into bigger blocks. Then group those. That's the next section.

Blocks of size b make an update cost 2 writes and a question about 2b + n/b additions, best near b = √n. The leftover cost is a range sum over the block totals, which is the original problem again, only smaller. Repeat the trick and you get a tree.

Same million counters, but blocks of 100 instead of 1,000. What does the worst range question cost now?

Right. Loose ends cost at most 2 × 99 = 198, but a long range crosses up to 10,000 blocks, so the total is about 10,200. Smaller blocks moved the cost from the ends into the middle. 2b + n/b is 3,000 at b = 1,000 and 10,200 at b = 100.

A range question has two parts, and shrinking the blocks helps one and hurts the other. The loose ends shrink: at most 99 counters at each end. But a range covering almost everything now crosses a million ÷ 100 = 10,000 blocks, and each one is an addition. Total: about 10,200, more than 3 times worse than blocks of 1,000. Put numbers into 2b + n/b: b = 100 gives 200 + 10,000. The figure above shows the same thing as a bar.

4Blocks of blocks: the segment tree

Take the grouping all the way. Pair up the items into blocks of 2 and write each block's total. Pair those into blocks of 4, then 8, and so on, until one block holds everything. Picture a brick wall: the bottom row is the items, and every brick sits on exactly two bricks of the row below and holds their total.

 [0,8)                          31
 [0,4) [4,8)            9                  22
 2-wide blocks      4       5         14        8
 items            3   1   4   1     5   9     2   6
 index            0   1   2   3     4   5     6   7

That's a segment tree: a binary tree where every node stands for one block of items, written [lo, hi), and stores the total of that block. The root covers everything, each node's two children cover its left half and right half, and the leaves are the single items. Think of a company where every manager knows the total sales of their own team: the CEO knows everything, each director knows their half, and so on down to one person.

Answering a question

To get the total of items 1 to 6, the range [1, 7), start at the root and look at each node's block. There are only three cases:

  • Fully inside the range: use the node's stored total, and don't look below it.
  • Fully outside: it contributes nothing; ignore it.
  • Partly inside: the total is no use as it is, so ask both children the same question and add their answers.

The total of [1, 7) on 8 items, then an update. Watch which bricks get used whole: [1,2), [2,4), [4,6) and [6,7). Four stored totals answer a six-item question. Then item 5 changes from 9 to 4, and only the bricks above it are fixed.

Changing an item

An update changes one leaf, and the only totals that counted that leaf are the bricks directly above it: one per row. Walk down from the root to the leaf, set the new value, and on the way back up recompute each brick on the path from its two children. With about log₂ n rows, an update is O(log n). Building the whole tree is O(n): each of the n − 1 inner bricks is computed once, from its two children.

Storing it

Like a heap, a segment tree fits in a plain array with no pointers. Number the root 1 (not 0), and the children of node i are 2i and 2i + 1, its parent i // 2. Starting at 1 makes the arithmetic one step shorter than the heap chapter's 2i + 1 and 2i + 2. When n is a power of two, 2n slots are enough. For any other n, the halves are uneven and the tree gets ragged; an array of 4n slots is always enough for this numbering.

def query(node, lo, hi, qlo, qhi):
    # node covers items lo..hi-1; we want the total of qlo..qhi-1
    if qhi <= lo or hi <= qlo:        # fully outside: adds nothing
        return 0
    if qlo <= lo and hi <= qhi:       # fully inside: use the stored total
        return tree[node]
    mid = (lo + hi) // 2              # partly inside: ask both halves
    return (query(2 * node, lo, mid, qlo, qhi) +
            query(2 * node + 1, mid, hi, qlo, qhi))

# the total of items 1..6:  query(1, 0, n, 1, 7)

A segment tree stores the total of every block in a halving hierarchy: the whole list, its two halves, their halves, down to single items. A question uses whole blocks where it can and splits only the blocks it partly overlaps. An update fixes the one block per level above the changed item. Both are O(log n); building is O(n).

Same tree as the diagram (8 items). Which stored totals does the question [0, 6) use, and what's the answer?

Right. The root is partly inside, so split. [0,4) is fully inside: take 9 and stop. [4,8) is partly inside: split it. [4,6) is fully inside: 14. [6,8) is fully outside. Two totals: 9 + 14 = 23. Check: 3 + 1 + 4 + 1 + 5 + 9 = 23.

Two rules decide it. A block can be used only if it's fully inside [0, 6), so [4,8), which includes items 6 and 7, can't be used whole: it must be split. And once a block is fully inside, you take its total and never go below it, so [0,4) is one read of 9, not a visit to [0,2) and [2,4). The sum would come out the same, but the work wouldn't: on a million items, refusing to stop at whole blocks turns about 40 reads into one read per item in the range, up to a million. Answer: [0,4) and [4,6), 9 + 14 = 23.

5Why a question touches only O(log n) blocks

The update cost is easy to believe: one brick per row. The question cost is the part people take on faith, and interviewers like to ask "why is it log n and not more?". After all, a range can be huge. Why doesn't a big range need many blocks?

Picture the range as two knife cuts through the brick wall, one at its left end and one at its right end. A brick needs to be split (it's "partly inside") only if a knife passes through it. In each row of bricks, a knife at one spot passes through at most one brick, and there are only two knives. So each row has at most two split bricks.

Now count. The only bricks the search ever looks at are the root and the children of split bricks. With at most 2 split bricks per row, at most 4 bricks are looked at in the row below. A million items is 20 rows, so a question looks at no more than about 4 × 20 = 80 bricks, and uses at most about 2 per row whole, about 40 totals. A billion items: 30 rows, about 120 bricks looked at. The range's length doesn't appear anywhere in that count; only the number of rows does.

Explain it another way: making change with coins

The blocks in a segment tree come in sizes 1, 2, 4, 8, … like coins. Covering a range with blocks is like paying an amount with those coins, with one rule: a block of size 2k can only start at a multiple of 2k. Walk from the left end of the range toward the middle: you use small blocks first to reach a "round" position, then bigger ones, each at most once per size. From the middle toward the right end, the sizes shrink again, each at most once. So the cover is at most two blocks of each size, and there are only log₂ n sizes. [1, 7) is paid as 1 + 2 + 2 + 1: rising, then falling.

Go deeper: the bottom-up segment tree in 2n slots

There's an iterative version with no recursion: put the n leaves at array positions n to 2n − 1, and fill node i (for i from n − 1 down to 1) with the combination of nodes 2i and 2i + 1. A query starts with two pointers at the leaves for lo and hi and climbs: whenever the left pointer is a right child, its node is used whole and the pointer steps right; whenever the right pointer's neighbor is a left child, it's used whole too. Both pointers move up a level each round, so it's O(log n), and it uses exactly 2n slots for any n, not 4n. It's usually faster in practice than the recursive version.

The catch: when n isn't a power of two, some inner nodes combine items that aren't next to each other. The query never uses those nodes, so answers stay right, but if the combine isn't commutative (section 6), you must keep the left pointer's answer and the right pointer's answer separately and join them at the end in the right order.

A segment tree holds 1,048,576 items (220). A question asks for the total of items 3 through 1,048,570. About how many blocks does the search look at, at most?

Right. Two cuts, so at most 2 split bricks per row and at most 4 bricks looked at per row. 20 rows × 4 = 80. Most of the range is covered by a few huge bricks near the top.

A long range doesn't mean many blocks: its middle is covered by a few giant blocks near the top of the tree, such as [4, 8), [8, 16), … [262,144, 524,288) on the left half and their mirror images on the right. Only the bricks a "cut" passes through get split, and the range has just two cuts: one at item 3 and one after item 1,048,570. Each row has at most 2 split bricks, so at most 4 bricks are looked at per row, and there are 20 rows: about 80. Blocks of fixed size b give √n because they have only two levels; the tree has 20.

6Any combine, not just sums

Nothing in the segment tree cares that the bricks hold sums. Each manager in the company picture only has to report something that can be worked out from their two reports' answers: the total, the smallest number on the team, the largest, the number of failed orders. Swap "+" for min and the same tree answers "what's the smallest item in [lo, hi)?", a range minimum query. On our 8 items, [1, 7) uses the same four bricks as before, now holding minimums: min(1, 1, 5, 2) = 1.

Three conditions make a combine work:

  1. Associative: grouping doesn't change the answer, so (a ⊕ b) ⊕ c = a ⊕ (b ⊕ c), where ⊕ stands for the combine. The tree groups the items its own way, along brick boundaries: [1, 7) was computed as (1 ⊕ 5) ⊕ (14 ⊕ 2), not one item at a time from the left. Sum, min, max, gcd and "join two strings" are associative. Subtraction isn't: (8 − 3) − 2 = 3 but 8 − (3 − 2) = 7.
  2. An identity: a value that changes nothing, returned for "no items", such as a brick fully outside the range or an empty range. It's 0 for sum, +∞ for min, −∞ for max, 0 for gcd, "" for joining strings. Pick it wrong and it silently poisons answers: with 0 as the identity for min, every range of positive numbers that touches an outside brick comes out 0.
  3. Left before right: associative doesn't mean commutative (a ⊕ b = b ⊕ a). Sum and min don't mind the order, but joining strings does: "ab" isn't "ba". Combining "applies these edits in order" or "this transformation, then that one" is the same. Always combine the left part's answer with the right part's, in that order.

Some questions can't be answered from the two halves' answers alone. Take the median (the middle value). The halves [1, 2, 3] and [4, 5, 100] have medians 2 and 5; the whole list's median is 3.5. Now take the halves [1, 2, 9] and [4, 5, 6]: medians 2 and 5 again, but the whole median is 4.5. Same two answers in, different answer out, so no combine can exist. Counting distinct values fails the same way: {1, 2} and {2, 3} have 2 each and 3 together, while {1, 2} and {1, 2} have 2 each and 2 together.

And here's a difference from sums that matters in the next section. A sum can be undone: the total of [lo, hi) is the total up to hi minus the total up to lo. A minimum can't. Say the coldest day from January to December was −10°, and the coldest day from January to March was also −10°. What was the coldest day from April to December? Anything from −10° up: those two numbers can't tell you. (They help only in the lucky case where the year's minimum is lower than the first three months', so it must fall after March.) So for min and max, the prefix-subtraction trick from section 2 doesn't work; you need blocks that sit exactly inside the range, which is what the segment tree gives you.

A segment tree works for any combine that is associative and has an identity, such as sum, min, max, gcd or joining strings; combine left before right in case it isn't commutative. It can't answer questions like median or "how many distinct values", where the halves' answers don't determine the whole answer.

Go deeper: storing more per node (maximum subarray, and more)

When the halves' answers aren't enough, sometimes a few more numbers per node are. "Largest sum of any run of adjacent items in [lo, hi)" can't be combined from two "largest run" values, because the best run might cross the middle. Store four numbers per node instead: the total, the best run starting at the left edge, the best run ending at the right edge, and the best run anywhere. Then combine(L, R) = (L.total + R.total, max(L.prefix, L.total + R.prefix), max(R.suffix, R.total + L.suffix), max(L.best, R.best, L.suffix + R.prefix)). That's associative, O(1) per combine, and the whole tree works unchanged. Interviewers like this one because it tests whether you understand what a node has to remember.

Other variations worth knowing by name: a persistent segment tree copies only the O(log n) nodes on an update's path, so every old version stays queryable; a merge sort tree stores each block's items sorted, for "how many items in [lo, hi) are below x" in O(log² n); and a sparse table answers range min or max with no updates in O(1), after O(n log n) preprocessing, by covering any range with two overlapping power-of-two blocks (overlap is fine for min, not for sum).

Which of these can a plain segment tree answer, storing one value per node?

Right. gcd(a, b, c) = gcd(gcd(a, b), c) = gcd(a, gcd(b, c)), so it's associative, and 0 is its identity because gcd(0, x) = x. Median and distinct counts can't be built from the two halves' answers.

Test each one the same way: can two different pairs of halves give the same two answers but a different whole answer? Median: [1, 2, 3] + [4, 5, 100] and [1, 2, 9] + [4, 5, 6] both give medians 2 and 5, but whole medians 3.5 and 4.5. Distinct count: {1, 2} + {2, 3} and {1, 2} + {1, 2} both give 2 and 2, but 3 and 2 together. So neither can be combined. gcd passes: the gcd of the whole is the gcd of the two halves' gcds, whichever way you group it.

7Sums only? Throw away half the tree

When all you need is sums, there's a structure that's half the size and fits in a few lines: the Fenwick tree, also called a binary indexed tree (BIT). Peter Fenwick described it in 1994 for data compression, where a coder needs running totals of symbol counts that change as it reads. You can derive it from the segment tree in three steps.

Step 1: only prefixes. For sums, section 2 already showed that sum(lo, hi) = prefix(hi) − prefix(lo). So we only need fast answers to prefix questions, the total of the first k items. A prefix [0, k) has just one cut, at its right end.

Step 2: notice what prefix questions never use. In a prefix question, a right child is never used whole. If a right child were fully inside [0, k), then its left sibling, which sits further left, would be inside too, so their parent would be fully inside and the search would have used the parent and never gone down. So every right child in the tree is dead weight for prefix questions. Delete them all.

Now a prefix question. The first 13 items: 13 is 8 + 4 + 1 (1101 in binary), so split them into a block of 1, a block of 4 and a block of 8, from the right: item 13 is slot 13, items 9–12 are slot 12, items 1–8 are slot 8. Three reads. In binary, each step removes the lowest 1 bit: 1101 → 1100 → 1000 → 0. A number below n has at most about log₂ n one-bits, so a prefix question is O(log n).

A Fenwick tree is a segment tree with every right child deleted, which leaves exactly one block per item. Slot j holds the total of the lowbit(j) items ending at item j. The first k items split into blocks matching k's 1 bits, so a prefix sum reads one slot per 1 bit: O(log n).

In a Fenwick tree (items numbered from 1), which items does slot 12 cover?

Right. 12 is 1100 in binary; its lowest 1 bit is 4, so slot 12 holds the 4 items ending at 12: 9, 10, 11, 12. A prefix of 12 items then takes slot 12 (9–12) plus slot 8 (1–8): 12 = 8 + 4.

Use the ruler picture: a slot's block is as long as its lowest 1 bit. Odd slots (lowest bit 1) cover one item each. Slot 12 is 1100 in binary, so its lowest bit is 4 and its block is 4 items long, ending at 12: items 9–12. If slot 12 covered 1–12, that's 12 items, but 12 isn't a power of two; Fenwick blocks always are. And items 1–8 are already held by slot 8, so slot 12 only needs the rest.

8Walking the bits: i & -i

Everything in a Fenwick tree turns on one number, lowbit(j), and computers get it in one step with j & -j. Here's why that works, using 5-bit numbers. A negative number is stored as "flip every bit, then add 1" (that's two's complement, how almost every CPU stores negatives, and how Python's & treats negative ints too):

  12        =  0 1 1 0 0
  flip      =  1 0 0 1 1
  + 1       =  1 0 1 0 0   this is -12
  12 & -12  =  0 0 1 0 0   = 4
  • Flip: the trailing 0s become 1s, and the lowest 1 becomes 0.
  • Add 1: the carry runs through those 1s, turning them back into 0s, and stops at the lowest 1's spot, which becomes 1 again.
  • AND: below that spot both numbers have 0s; above it, every bit of −12 is the flip of 12's, so the AND is 0 there too.

Only the lowest 1 bit survives the AND. With that, both Fenwick operations are short loops.

Prefix sum: strip the lowest bit

def prefix(tree, k):           # total of items 1..k (tree[0] is unused)
    total = 0
    while k > 0:
        total += tree[k]       # slot k holds the lowbit(k) items ending at k
        k -= k & -k           # jump left past that block: 1101 -> 1100 -> 1000 -> 0
    return total

Add to one item: add the lowest bit

To add 2 to item 5, find every slot whose block contains item 5. Slot 5 does (it ends at 5). The next one is the nearest slot to the right whose block reaches back past 5, a taller tick on the ruler. You get it by adding the lowest bit instead of removing it: 5 + 1 = 6 (covers 5–6), 6 + 2 = 8 (covers 1–8), 8 + 8 = 16 (covers 1–16). Each addition carries into a higher bit, so the lowest bit at least doubles every step, and the walk ends after at most about log₂ n slots. The slots it skips, like 7, have blocks that start after item 5.

A Fenwick tree over 16 items. Each bar is one slot: it ends above its own item number and is lowbit(j) long. Pick "prefix sum" and a k to watch k lose its lowest bit at each step, or "add 2 to item p" to watch p gain it. Try k = 15 (four 1 bits, four reads) and k = 16 (one read).

The trap at 0. lowbit(0) is 0 & −0 = 0, so the add loop j += j & -j adds nothing and spins forever, and the prefix loop never runs. That's why slots start at 1. If your interface counts items from 0, like a Python list, shift once at the door: item i lives in slot i + 1. Forgetting that shift is the most common Fenwick bug, and it hangs instead of crashing.

Building. n adds cost O(n log n). There's an O(n) way: each slot's whole total belongs inside exactly one bigger slot, the next one that includes all of its items. Exercise 4 asks you to find which one.

Explain it another way: paying with powers of two

Say k = 13. In binary that's 8 + 4 + 1. A Fenwick prefix sum pays for "the first 13 items" with one bill of each of those sizes, laid out from the right: the last 1 item (slot 13), the 4 before it (slot 12), the 8 before those (slot 8). Every number has exactly one such binary breakdown, so every prefix has exactly one set of slots, and the number of slots is the number of 1 bits. An add is the reverse question: "which of these bills contain item 5?" The bills that end at 5, 6, 8 and 16 do, and each is at least twice as long as the one before, so there are only about log₂ n of them.

Go deeper: Fenwick or segment tree in practice
  • Size and speed: a Fenwick tree is n + 1 numbers and two tight loops, with no recursion. A segment tree is 2n to 4n slots. Both are O(log n); the Fenwick tree is usually faster in practice and much quicker to write correctly in an interview.
  • What it can't do: range questions need the combine to be undoable (sum, count, xor), because a range is prefix(hi) "minus" prefix(lo). For min or max over arbitrary ranges, use a segment tree. A Fenwick tree can keep a prefix maximum if values only ever go up.
  • Two dimensions: a Fenwick tree of Fenwick trees answers "sum over a rectangle of a grid" with point updates in O(log² n), with the same two loops nested.

A Fenwick tree has 16 slots. Which slots does prefix(11), the total of the first 11 items, read?

Right. 11 = 1011. Strip the lowest bit: 1010 = 10. Strip again: 1000 = 8. Again: 0, stop. Slot 11 covers item 11, slot 10 covers 9–10, slot 8 covers 1–8: 1 + 2 + 8 = 11 items, each counted once.

A prefix goes left: it needs blocks that end at or before item 11 and fit together with no gaps. Removing the lowest 1 bit does that: 11 (1011) covers item 11, then 10 (1010) covers 9–10, then 8 (1000) covers 1–8. 11, 12, 16 is the add walk (adding the lowest bit), which goes right to every slot that contains item 11. Halving (11, 5, 2, 1) is a heap's parent rule, not a Fenwick's: slot 5 covers only item 5, which would leave a gap.

9Changing a whole range at once

A hotel tracks how many rooms are booked on each night of the year. A booking from night 40 to night 70 adds 1 to 30 nights. With the trees so far that's 30 separate point updates, each O(log n), so the cost grows with the length of the booking: a range of a million items would be a million updates. The question is "add x to every item in [lo, hi)" in one O(log n) step.

Range add, single-item read: mark where changes start and stop

Instead of writing on every night, put a +1 marker on the night the booking starts and a −1 marker on the night it ends (the check-out night isn't booked). To get the count for night d, add up every marker from night 0 to night d. Each booking that started on or before d and hasn't ended yet contributes +1 with no matching −1 so far. Three bookings over 8 nights, [1, 4), [2, 6) and [3, 5):

 night         0   1   2   3   4   5   6   7
 markers       0  +1  +1  +1  −1  −1  −1   0      +1 at each start, −1 at each end
 running sum   0   1   2   3   2   1   0   0      = rooms booked that night

 night 3: inside all three bookings → 3.   night 5: only inside [2, 6) → 1.

The markers form a difference array: each entry is the difference between one night and the night before. A range add changes just 2 markers, and reading one night is a prefix sum of the markers. Prefix sums with point updates are exactly what a Fenwick tree does: put the markers in one, and range add and single-item read are both O(log n). It's the same +1 / −1 trick as the sweep line in Intervals; the Fenwick tree lets the markers keep changing while you read.

Range add and range question: sticky notes

If you need both "add 5 to every item in [lo, hi)" and "total (or minimum) of [lo, hi)", use a segment tree with lazy propagation. Picture a manager receiving the memo "everyone on your team gets +5". A lazy manager doesn't walk the floor telling each person. She updates her own team total (+5 × team size, or +5 for a minimum), sticks a note on her door saying "+5 for everyone below me, not passed on yet", and stops. The range add uses the same O(log n) whole bricks a question would.

Later, if some question or update has to look inside her team, she first passes the note down: each of her two direct reports applies +5 to their own total and gets their own note, and her note comes off. Notes only travel along paths the search was walking anyway, so every operation stays O(log n), however wide the ranges. The same trick handles "set every item in [lo, hi) to x".

Go deeper: range add and range sum with two Fenwick trees

There's a Fenwick-only way to get range add and range sum. With markers d (the difference array, items from 1), the sum of the first k items is d₁·k + d₂·(k − 1) + … + dk·1, because marker j is counted in items j through k. That rearranges to (k + 1)·(d₁ + … + dk) − (1·d₁ + 2·d₂ + … + k·dk). So keep two Fenwick trees, one over dj and one over j·dj: a range add changes 2 entries in each, and prefix(k) = (k + 1)·S₁(k) − S₂(k). It's shorter than lazy propagation, but it only works for sums.

You need "add x to every item in [lo, hi)" and "what is item i right now?", both fast, on a million items. What's the simplest structure that does it?

Right. A range add is +x at lo and −x at hi, and item i is the sum of markers 0..i: a prefix sum. Both O(log n). Lazy propagation also works, but it's much more code, and you only need it when you also ask range questions about min, max or (without the two-tree trick) sums.

Think about what a single item's value is in terms of the markers. If every change to a range is written as "+x where it starts, −x where it stops", then item i's value is the sum of all markers at or before i: a prefix sum. So a plain Fenwick tree over the markers does everything: range add = 2 point adds, read = 1 prefix sum. Adding x item by item is O(length × log n), a million times worse for a full-width range. Lazy propagation works too, but it's the heavy tool for when you also need range questions.

10Patterns: rank, k-th, and "how many smaller"

Most interview uses of these trees count things. The trick is to index the tree by value instead of by position: slot v holds "how many items have value v".

"What's my rank?"

A game has scores from 0 to 1,000,000 and millions of players. Keep a Fenwick tree of 1,000,001 counts, one per possible score. A player going from 300 to 950 is two point adds: −1 at 300, +1 at 950. A player's rank is 1 + the number of players with a higher score, which is "all players minus the players with score ≤ mine": one prefix sum. Both are about 20 steps, because log₂ of a million is about 20.

"Who's at rank k?" Walk down by powers of two

The reverse question: the k-th lowest score is the first score where the running count reaches k. Binary search over prefix sums works, but costs O(log n) prefix sums of O(log n) each: O(log² n). The Fenwick layout allows better: decide the answer one bit at a time, from the top. Use the 16 counts from section 8's figure (3, 1, 4, 1, 5, 9, 2, 6, 5, 3, 5, 8, 9, 7, 9, 3) and look for where the running count first reaches 40:

0400 + 8 = 8 (items 1–8)3131 < 40: jump to 8, still need 9
898 + 4 = 12 (items 9–12)2121 ≥ 9: too far
898 + 2 = 10 (items 9–10)88 < 9: jump to 10, still need 1
10110 + 1 = 11 (item 11)55 ≥ 1: too far

The walk ends at 10, so the answer is the next item, 11. Check: the running count is 39 through item 10 and 44 through item 11.

Each try adds the next smaller power of two to where you are, and the slot you land on always covers exactly the items you'd be skipping over. One slot read per bit: O(log n). This only works when every count is ≥ 0, so the running count never goes down.

Values too big to index: coordinate compression

If values go up to 1018, you can't have a slot per value. But you only care about their order. If you know all the values up front, sort the distinct ones and replace each value with its position in that sorted list: 1018, −5, 42 become 3, 1, 2. The tree now needs one slot per distinct value. This is coordinate compression, and it only works offline (all values known in advance). If values arrive one at a time and can be anything, use a balanced BST that stores subtree sizes (an "order-statistic tree") or a skip list that stores link spans, which is how Redis answers ZRANK on a sorted set (topic 01.11). A third option is a segment tree over the whole value range, 0 to 1018, that creates a node only when an update first reaches it. The range has about 60 levels (log₂ 1018 ≈ 60), so each update creates at most about 60 nodes, and memory grows with the number of updates, not with the size of the range.

"How many smaller numbers are to my right?"

For each item, count the items to its right that are smaller. Comparing every pair is O(n²). Instead, walk from the right, and keep a Fenwick tree of counts of the values you've already passed. Each value you pass is to the left of everything you've seen, so "how many seen values are smaller than mine?" is exactly the answer: a prefix sum up to my rank minus one. Then add my own value. For [5, 2, 6, 1] the ranks are 5 → 3, 2 → 2, 6 → 4, 1 → 1:

Read back left to right, the answer is [2, 1, 1, 0]: O(n log n) instead of O(n²).

Add the answers up and you get the number of inversions (pairs that are out of order), a measure of how unsorted a list is. Merge sort can count them too, while it merges.

Walking [3, 3, 1] from the right, you've passed 1 and the second 3, and now you're at the first 3. Which query counts the smaller items to its right?

Right. Ranks: 1 → 1, 3 → 2. prefix(1) counts only the 1, giving 1. The other 3 is equal, not smaller, so it must not count. The full answer is [1, 1, 0].

Plug in the numbers. Ranks are 1 → 1 and 3 → 2; you've seen ranks {1, 2}. prefix(2) counts both, giving 2, but one of them is the other 3, which isn't smaller. total − prefix(2) = 0 counts the seen values that are bigger. prefix(2 − 1) = prefix(1) counts just the 1: the right answer, 1. "Strictly smaller" means stopping one rank short; with "smaller or equal" you'd use the full rank.

Go deeper: the same ideas in real systems
  • Rollups: monitoring tools such as RRDtool and Graphite's Whisper store one series at several resolutions (per-minute and per-hour totals, for example), so a month-long chart reads hundreds of stored totals instead of millions of raw points. That's section 3's blocks with a few fixed levels.
  • Rank in a database: PostgreSQL's B-tree indexes don't keep a count per subtree, so COUNT(*) over a range of keys reads every matching entry. Keeping counts would make every insert and delete update a count on every level up to the root, and every writer would contend for the same few pages. That's the price of the "big total" a counted tree keeps.
  • Redis sorted sets do keep counts: their skip list stores, on each link, how many items it jumps over, so ZRANK is O(log n). That's topic 01.11.
  • Data compression: Fenwick's original use. An adaptive arithmetic coder needs, for every symbol it encodes, the total count of all symbols that come before it in the alphabet, and the counts change after every symbol: prefix sums with point updates.

In words: if nothing changes, precompute (prefix sums, or a sparse table for min and max). If items change and you need sums or counts, use a Fenwick tree: shortest code, smallest memory. If you need min, max or a custom combine, or range changes together with range questions, use a segment tree. If the set of items changes, with inserts in the middle and not just updates to fixed positions, and the values aren't known in advance, use an ordered tree with sizes instead. Square-root blocks are the fallback when the combine is awkward and n is moderate: easy to write, and √(106) = 1,000 is often fast enough.

Fixed positions with changing values: Fenwick for sums, segment tree for everything else. No changes: precompute. Items inserted anywhere: an ordered tree that keeps subtree sizes.

12What to say in the interview

For "an array gets point updates and range-sum queries, both frequent", a strong answer:

"With only queries I'd precompute prefix sums, O(1) each. With only updates, the plain array. Mixed, each of those is O(n) on one side. I'll use a Fenwick tree: slot j stores the sum of the lowbit(j) items ending at j, so a prefix sum strips the lowest bit and an update adds it, both O(log n), and a range sum is two prefix sums. That's n + 1 ints of memory and about 20 steps per operation for a million items. It's 1-indexed inside, because lowbit(0) is 0 and the update loop would never move. If they ask for range minimum instead, sums' subtraction trick doesn't work, so I'd switch to a segment tree, which handles any associative combine with an identity. If they add range updates, a Fenwick over the difference array gives range add with point reads; range add with range queries needs lazy propagation."

Habits that make you sound senior:

  • Name the trade-off first: raw values make queries O(n), prefix sums make updates O(n).
  • Say why it's log n: one block per level for updates, at most two split blocks per level for queries.
  • Say what the combine needs: associative, an identity, left before right.
  • Mention the off-by-one traps: half-open ranges and the 1-based Fenwick.
  • Know when it's the wrong tool: static data (precompute), or inserts in the middle (an ordered tree with sizes).

✓What to remember

  1. Raw items: O(1) update, O(n) range sum. Prefix sums: O(n) update, O(1) range sum. Mixed workloads need a middle ground.
  2. Blocks of size √n give O(√n). Blocks of blocks give a segment tree: O(log n) for both.
  3. Segment tree: each node holds its block's total; a query uses whole blocks and splits only the at most two per level that a range end cuts through. Update: one node per level. Build: O(n). Array of 2n to 4n.
  4. Any associative combine with an identity works (sum, min, max, gcd, strings); combine left then right. Median and distinct counts don't.
  5. Fenwick tree: a segment tree with the right children removed. Slot j covers the lowbit(j) items ending at j, with lowbit(j) = j & -j.
  6. Prefix: k -= k & -k. Add: j += j & -j. Slots start at 1, or the add loop never ends. Range = prefix(hi) − prefix(lo), so sums only.
  7. Range add: +x and −x in a difference array, read with a prefix sum. Range add plus range question: lazy propagation.
  8. Index by value for rank, k-th (walk down by powers of two) and "count smaller after"; compress big values to ranks first.

3. Pick the structure

Name the structure and the cost per operation: (a) 10 million prices that never change, then a million "total from day i to day j" questions; (b) a million temperatures, with updates, and "coldest reading between i and j" questions; (c) a ticketing site's seat map: "book seats lo to hi" and "is seat s taken?"; (d) "how many earlier orders were cheaper than this one?" for each of 5 million orders, all known in advance.

Answer

(a) Prefix sums: O(n) once, then O(1) per question. (b) Segment tree with min, O(log n) for both; a Fenwick tree can't, because a min can't be subtracted away. (A sparse table would give O(1) questions, but only if there were no updates.) (c) A Fenwick tree over the difference array: booking is two point adds, "is seat s taken?" is a prefix sum, both O(log n). (d) Compress prices to ranks, walk from the left with a Fenwick tree of counts, and ask prefix(rank − 1) before adding each order: O(n log n) in total.
