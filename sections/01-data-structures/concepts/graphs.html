Graphs and how to store them

Roads, friendships, package dependencies, network links: anything made of things and connections between them is a graph. Before you can run any graph algorithm, you have to decide how the graph sits in memory.

CoreThe one-sentence idea

A graph is a set of nodes and edges. An adjacency list stores, for each node, who it connects to, in O(V + E) space. An adjacency matrix stores every possible pair in O(V²). Most real graphs are sparse, so the list is the default.

Build itFrom first principles

1. The vocabulary, minimal version

  • Directed vs undirected: follows on social media (directed) vs friendship (undirected = an edge in both directions).
  • Weighted: edges carry a cost: distance, latency, price.
  • Sparse vs dense: E close to V (road networks, dependency graphs) vs E close to V² (rare: small complete graphs).
  • Cycle, DAG, tree: a tree is a connected graph with no cycles and exactly V−1 edges. A DAG is a directed graph with no cycles, which means you can order it (topological sort, chapter 2).
  • Implicit graphs: often nobody hands you the edges. A grid, a word ladder, or the states of a puzzle are graphs whose neighbors you compute on the fly.

2. Representation decides cost

Adjacency list

graph[u] = [v1, v2, …], a dict or list of lists. Space O(V + E). Iterating a node's neighbors costs O(degree). "Is u–v an edge?" costs O(degree), or O(1) if you use sets.

Adjacency matrix

M[u][v] = 1 or a weight. Space O(V²). Edge check O(1). Iterating neighbors O(V), even for a node with one edge. Good for small dense graphs and some DP problems (Floyd–Warshall).

Edge list

[(u, v, w), …]. The simplest form. It's what problems hand you, and it's exactly what Kruskal's MST and Bellman-Ford iterate over.

3. The first five lines of almost every graph solution

from collections import defaultdict
graph = defaultdict(list)
for u, v in edges:
    graph[u].append(v)
    graph[v].append(u)      # only if undirected
IntuitionAnalogy: a contacts list vs a seating chart

An adjacency list is everyone's phone contacts: each person lists only the people they actually know. It's cheap even with a billion people. An adjacency matrix is a giant seating chart with one cell for every possible pair. With a billion people that's 10¹⁸ cells, almost all of them "no".

Back-of-envelope: a social graph with 10⁹ users and 200 friends each has 2×10¹¹ edges. As lists, that's a few TB, which is big but shardable. As a bit matrix, it's about 125 PB.

    InterviewWhat a senior answer adds
    

      
    
        
  • Recognize hidden graphs. Many "non-graph" problems are graphs: course prerequisites (DAG, topological sort), word ladder (implicit edges between words one letter apart), islands in a grid (connected components), currency exchange (weighted, maybe negative cycles).
    • 
        
  • State your representation and why before coding: "sparse, so an adjacency list; sets because I'll check membership."
    • 
        
  • At system scale, graphs get partitioned across machines and the edge cut becomes the problem: friend-of-friend queries cross shards. Real systems use specialized stores (Facebook's TAO), precomputed fan-out, or graph databases. Know that this exists for design rounds.
    • 
      

    

  


  

    TrapsCommon mistakes
    

      
    
        
  • Forgetting the reverse edge for undirected graphs, or adding it for directed ones.
    • 
        
  • Missing isolated nodes: they never appear in the edge list. Iterate range(n), not just the keys of your dict.
    • 
        
  • Duplicate edges and self-loops in the input. Ask whether they can happen.
    • 
        
  • Allocating a V×V matrix "because it's easier" when V = 10⁵. That's 10¹⁰ cells.
    • 
      

    

  


  

    RecallCheck yourself
    

      
A tree with V nodes has how many edges? And a complete undirected graph?
A tree has V − 1. A complete graph has V(V − 1)/2.

      
How would you represent a 2D grid maze as a graph without building edges?
Keep it implicit: node = (row, col); neighbors = the 4 (or 8) adjacent cells that are in bounds and not walls, computed when you need them. That saves memory and code.

      
When is the matrix the right choice?
Small V (a few thousand at most), dense graphs, frequent O(1) edge checks, or algorithms naturally written over all pairs, like Floyd–Warshall or transitive closure.
