Chapter 1 · Part 4

Always grab the smallest next

P0 core Google & Anthropic roundabout 18 minutes6 quick checks · 6 exercises

Many programs never need every item kept in full sorted order — they only ever ask for the next most urgent item while new work keeps arriving. Giving up full sorting lets us pack a branching priority board flat inside a plain list with zero pointer objects, peek at the winner instantly, and update fast even at a million entries.

By the end you'll be able to

  1. Pack a priority tree into a flat list with no node objects, using simple slot arithmetic.
  2. Add new arrivals, remove the top winner, and organize an unsorted list from the bottom up in linear time.
  3. Avoid the classic Python priority-queue traps — reversed ordering, tied priorities, and in-place mutation.
  4. Spot and code the four flagship interview moves: top-k streams, merging sorted streams, worker scheduling, and live medians.
  5. Choose cleanly between a heap, full sorting, and a balanced search tree when an interviewer shifts constraints.

1Why is full sorting overkill for "who is next?"

Your scheduler manages 500,000 workers and assigns 1,000,000 incoming jobs. Each job goes to whichever worker becomes free soonest, updating that worker's next free time right away.

Scanning an unsorted list of 500,000 workers on every job performs 500 billion comparisons. Keeping a descending sorted list shifts up to 500,000 entries per job (hundreds of billions of shifts) when workers rotate to the back. Yet you never asked who is the 213,419th-soonest worker — you only ever asked who is #1.

A binary heap does just enough ordering to pin the smallest item at slot 0, turning 500 billion comparisons into ~19 million tree levels (~38 million comparisons).

That "only keep #1 on top" primitive unlocks four interview staples:

  • Top-k from a stream: keep only the k biggest values out of millions in O(k) RAM.
  • K-way merge: combine k sorted log shards or linked lists lazily in O(N log k).
  • Worker / event scheduling: always dispatch to the next available worker or earliest deadline.
  • Live running median: pair two heaps back-to-back so the middle sits exposed in O(1).

2What rule puts the most urgent item on top?

Picture an ER triage board arranged like a two-report org chart. Each patient card appears once in its own slot, labeled with an urgency score (smaller number = more urgent). The board enforces one vertical rule: every slot's score must be <= both slots directly beneath it (a min-heap; flip the inequality for a max-heap).

That vertical rule pins the most urgent patient straight to the top slot, while relaxing horizontal order completely — unlike a Binary Search Tree from Chapter 1.3, siblings have zero order between them! The right child can be smaller than the left child, and a grandchild on the left can be larger than a child on the right.

Where the triage-board picture breaks: because siblings aren't ordered left-to-right, you cannot search for patient #42 or list everyone with urgency between 3 and 7 without scanning the whole board in O(n). Need arbitrary lookup, deletion by key, or range queries? Use a hash map or balanced BST instead.

A binary heap keeps two invariants: (1) Shape — a complete binary tree (every level packed full top-to-bottom, left-to-right, zero gaps); (2) Order — every parent is <= both of its children.

3Why can we throw away all node pointers?

Because our triage board is complete (zero gaps anywhere), number its slots 0, 1, 2, … level by level from left to right and drop the values straight into a plain Python list a[0..n-1] — no Node objects, no left/right references, and packed side by side in RAM so the CPU cache prefetches nearby slots fast:

Notice a[4] = 4 < a[2] = 5 — completely legal in a min-heap! Every parent-child edge is instant integer math inside one flat list.
A complete tree of n items is always balanced with zero rotation code: its height is strictly ⌊log₂ n⌋ edges (⌊log₂ n⌋ + 1 levels — at most 20 levels for a million items), and every index i >= n // 2 is a leaf (its left child 2i + 1 >= n does not exist).

In a 0-indexed binary heap of n = 10 items, why is index 5 guaranteed to be a leaf?

Exact! For any index i >= n // 2, 2*i + 1 >= n — so indices 5..9 (half the array!) have zero children, while index 4 is the last non-leaf (left child 9).

Plug each index into left(i) = 2*i + 1 for valid slots 0..9: index 4 has left child 9 (inside the array!), whereas index 5 would need left child 11 (outside 0..9). Therefore n // 2 marks the very first leaf.

4How do push and pop keep the board packed tight?

Both updates keep the triage board packed with zero holes first, then repair the vertical urgency rule along one root-to-leaf path:

  • push(x) + sift-up: seat the new patient in the next open slot at the end (a.append(x)). While i > 0 and a[i] < a[parent], trade places upward with the less-urgent boss above you. On a heap of n items (after appending), climbing one level per swap performs at most ⌊log₂ n⌋ comparisons — O(log n) worst case (and ~1–2 swaps on random data).
  • pop() + sift-down: save the top patient a[0] to send to the OR. Never pull a child straight up into slot 0 (that opens a hole in the middle of the board!). Instead, pop the very last slot (last = a.pop()), place it at a[0], and step it downward — always swapping with the more urgent (smaller) of its two direct reports so the promoted patient beats its old sibling too!
def _sift_up(a, i):
    while i > 0:
        p = (i - 1) // 2
        if a[i] < a[p]: a[i], a[p] = a[p], a[i]; i = p
        else: break

def _sift_down(a, i):
    n = len(a)
    while 2 * i + 1 < n:
        l, r = 2 * i + 1, 2 * i + 2
        sm = r if (r < n and a[r] < a[l]) else l    # pick the smaller child!
        if a[sm] < a[i]: a[i], a[sm] = a[sm], a[i]; i = sm
        else: break
Watch the triage tree and its flat backing list stay in lockstep during push(2) (sift-up, 3 comparisons on 8 items) and pop() (last item to slot 0, then sift-down with the smaller child).

During pop(), node 9 sits at the root with left child 5 and right child 3. What happens if you swap 9 with 5 instead of 3?

Exact! Sift-down descends only into the left branch and never revisits 3, leaving peek() falsely returning 5 instead of 3.

Draw the top three slots after swapping 9 with 5: root is 5, left child is 9, right child is 3. Now sift-down keeps walking down 9's side — nobody ever compares 5 against 3, leaving the true minimum 3 buried under 5.

5Can we build a heap faster than n pushes?

Suppose a waiting room of n unsorted patients arrives at once (MinHeap.from_list(items) or heapq.heapify(items)). Pushing them one by one calls sift_up n times — on a falling list [n, n−1, …, 1], every bottom-row patient climbs all the way to the root, costing O(n log n).

Floyd's bottom-up heapify organizes the room from the bottom rows up in strict O(n) time (under 2n comparisons even in the worst case!). Copy items into a (never mutating the caller's list). All indices n // 2 .. n − 1 are already leaves (valid 1-node heaps!). Loop i backward from the last non-leaf (n // 2) - 1 down to 0, calling _sift_down(a, i).

With sift_up, the huge bottom half travels farthest (log₂ n). With bottom-up sift_down, the bottom half moves 0 steps and the next row moves at most 1.
Bottom-up heapify is O(n) worst case (not just average) because the series 0/2 + 1/4 + 2/8 + 3/16 + … sums to 1 — almost all nodes sit near the bottom where sift-down barely travels.

You call bottom-up MinHeap.from_list(items) on 32,768 values in worst-case reverse-sorted order. What bounds the work?

Spot on! Even when every single node sifts all the way down to a leaf, 16,384 leaves move 0 steps, 8,192 nodes move ≤ 1 step, and only 1 root moves 15 steps — always under 2n comparisons!

Count the worst case on a 15-node reverse-sorted tree: 8 leaves do 0 swaps, 4 nodes at height 1 do ≤ 1 swap (4), 2 nodes at height 2 do ≤ 2 swaps (4), and 1 root does ≤ 3 swaps (3). Total = 11 swaps (< 15) even in the worst possible order!

6How can heaps break — and when is a heap the wrong tool?

In interviews, use Python's C-accelerated heapq on a plain list: heappush, heappop, heapify, heapreplace(h, x) (pop then push in one sift), and heappushpop(h, x) (checks h[0] < x first — returning x in 1 comparison if it loses to the root, else replacing in one sift!). Watch four classic traps:

  1. heapq.heapify(lst) mutates in place and returns None: writing h = heapq.heapify(nums) silently sets h = None!
  2. Max-heap (numbers vs. objects): heapq is min-only. Negate numbers (-x). For strings or custom objects (like Top K Frequent Words), use a mixed tuple (-freq, word) or a tiny wrapper class reversing __lt__.
  3. Tuple tie-breaker crash: pushing (priority, payload) compares payload whenever two priorities tie! If payload is an iterator, dict, or custom object without <, Python raises TypeError. Always place a unique integer tie-breaker between them: (priority, idx, payload).
  4. Mutating priorities in place: changing a queued object's priority field does not re-sift it, silently corrupting the heap! Push a new entry and use lazy deletion (Section 9) instead.

When a heap is the wrong tool — decision guide:

What the problem asksBest toolWhy
Repeatedly grab min/max while items arriveBinary heapO(1) peek, O(log n) push/pop, flat RAM
One-shot full sort (or k ≈ n)Timsort (sort())O(n log n) with far better cache constants
Lookup by key, arbitrary delete, or range(lo, hi)Balanced BST / hash mapHeaps scan O(n) for arbitrary items/ranges
Static one-shot k-th largest (small k)heapify + k popsO(n + k log n) (Chapter 2.2's quickselect even hits O(n) avg!)

Merging sorted iterators with heapq, you push (val, it) and hit TypeError: '<' not supported between instances of 'list_iterator'. Which tuple prevents the crash?

Spot on! Python compares tuples left-to-right: equal vals compare slot 1 (unique integer list_idx) and stop before ever touching it in slot 2.

Check slot order left-to-right on two tied values (5, …) and (5, …): putting list_idx first sorts by list number instead of value; putting list_idx last still compares it1 < it2 at slot 1 and crashes! Only (val, list_idx, it) orders by val and breaks ties on list_idx.

7Pattern 1: Top-k largest from a stream

Given a single-pass stream of n items (say 10 million from a generator) and small k, return the k largest items sorted largest-first in O(n log k) time and O(k) memory (returning [] if k <= 0).

The key twist: to keep the k largest, keep a min-heap of size k! It pins the weakest current winner right at h[0], acting as a threshold gate:

Testing h[0] < x first bounces non-contenders in 1 comparison (and uses only <, never <=).
def top_k(stream, k):
    if k <= 0: return []
    h = []
    for x in stream:
        if len(h) < k:      heapq.heappush(h, x)
        elif h[0] < x:      heapq.heapreplace(h, x)   # or heapq.heappushpop(h, x)!
    h.sort(reverse=True)    # popping a min-heap yields smallest-first; sort/reverse for largest-first!
    return h
Use a min-heap of size k for the k largest (and a max-heap for the k smallest). Testing h[0] < x (or calling heapq.heappushpop) rejects weak arrivals in 1 comparison instead of two sifts.
Go deeper: distributed top-k across 100 machines

If 10 billion events are sharded across 100 servers, each server runs the exact top_k size-k min-heap locally and sends only its k winners (not 100M raw records!) to a coordinator, which runs a final size-k merge over the 100·k candidates.

On 100,000 random items with k = 100, why is if h[0] < x: heapreplace(h, x) (or heappushpop) far faster than calling heappush(h, x) followed by heappop(h)?

Exact! Both keep O(k) memory and O(n log k) worst-case time (e.g. a rising stream), yet on random streams >99% of arrivals lose to h[0] — dropping average work from ~13 comparisons/item down to ~1!

Trace a tiny arrival x = -5 when the 100th-largest winner at h[0] is 99,000: heappush sifts -5 all the way up to slot 0 (~7 cmps) and heappop immediately pops -5 and sifts back down (~6 cmps). Testing h[0] < x skips both sifts in 1 check.

8Patterns 2 & 3: K-way merge and worker scheduling

K-way merge of sorted streams

Given k sorted iterators holding N items total, keep a size-k min-heap holding one front item per non-empty stream: (val, idx, iterator). Watch on [[1, 4], [2, 3], [5]]:

  • Seed heap with one item from each stream: [(1, 0, it0), (2, 1, it1), (5, 2, it2)].
  • Pop/yield 1 from stream 0 → pull next item 4 from it0 → heap becomes [(2, 1, it1), (4, 0, it0), (5, 2, it2)].
  • Pop/yield 2 from stream 1 → pull 3 from it1 → heap becomes [(3, 1, it1), (4, 0, it0), (5, 2, it2)].
def merge_sorted(iterables):
    _END = object()
    h = []
    for idx, it in enumerate(iterables):
        it = iter(it)
        if (v := next(it, _END)) is not _END: h.append((v, idx, it))
    heapq.heapify(h)                        # O(k) bulk seed
    while h:
        v, idx, it = h[0]
        yield v                             # pull AFTER yielding so streams stay lazy!
        if (nxt := next(it, _END)) is not _END: heapq.heapreplace(h, (nxt, idx, it))
        else: heapq.heappop(h)

Total time is O(N log k), memory is O(k), and before yielding the m-th item you have pulled at most k + m − 1 items (or k + m if refilling right before yielding) — working even on infinite streams!

Go deeper: external merge sort and database SSTable compaction

When a 500 GB file won't fit in 16 GB of RAM, sort 10 GB chunks in memory and write 50 sorted runs to disk. Then run this exact 50-way merge with buffered file iterators! LSM-tree storage engines (RocksDB, LevelDB, Bigtable) use the same k-way merge to compact sorted SSTable files.

Worker scheduling (assign_jobs)

Back to Section 1: seed a min-heap with h = [(0, w) for w in range(workers)] (already a valid heap!). Tuple order (free_time, worker) breaks ties automatically by lowest worker ID. On durations = [1, 2, 3], workers = 2: job 0 → worker 0 at t=0 (push (1, 0)); job 1 → worker 1 at t=0 (push (2, 1)); job 2 → worker 0 at t=1 (push (4, 0)). Total time: O(w + n log w), heap space O(w):

def assign_jobs(durations, workers):
    h, out = [(0, w) for w in range(workers)], []
    for d in durations:
        t, w = h[0]
        out.append((w, t))
        heapq.heapreplace(h, (t + d, w))    # one combined sift!
    return out

9Pattern 4: Two-heap running median (and what to say)

To answer find_median() in O(1) as numbers stream in, split the stream into two halves sitting back-to-back at the middle: a max-heap lo (negated values) holding the smaller half, and a min-heap hi holding the larger half.

Routing every arrival across the boundary (lo → hi, then rebalance if hi is bigger) keeps both invariants tight in 3 clean lines.

Trace adding 5, then 2, then 10: after 5 → lo={5}, hi={} (median 5); after 2 → lo={2}, hi={5} (median 3.5); after 10 → lo={2,5}, hi={10} (median 5):

class MedianFinder:
    def __init__(self): self.lo, self.hi = [], []       # max-heap (negated), min-heap

    def add_num(self, x):
        heapq.heappush(self.lo, -x)                     # 1. push to lower half
        heapq.heappush(self.hi, -heapq.heappop(self.lo))# 2. bounce lo's max to hi
        if len(self.hi) > len(self.lo):                 # 3. keep len(lo) >= len(hi)
            heapq.heappush(self.lo, -heapq.heappop(self.hi))

    def find_median(self):
        if len(self.lo) > len(self.hi): return -self.lo[0]
        return (-self.lo[0] + self.hi[0]) / 2
Go deeper: lazy deletion for sliding-window median and indexed heaps

Lazy deletion (e.g. Sliding Window Median): record removed values in a collections.Counter and prune dead elements whenever they float to the top of a heap. Critical two-heap trap: len(lo) and len(hi) still include dead entries! You must maintain separate live_lo and live_hi counters, rebalance strictly using those live counts, and prune dead elements from both roots before reading the median.

Indexed heap vs. lazy deletion: an indexed heap keeps a companion key → array_index dict so arbitrary decrease_key/delete runs in true O(log n). In Python interviews (e.g. Dijkstra), pushing a duplicate (new_dist, node) and lazily skipping stale entries is shorter and faster unless unbounded updates on the same key could bloat RAM.

lo (max-heap) holds values {2, 5, 8} and hi (min-heap) holds {10, 14}. Why shouldn't add_num(x) push straight into the shorter heap hi?

Spot on! Bouncing lo's max into hi guarantees every value in lo is <= every value in hi for any arrival, with zero messy if/else branches.

Check what find_median() would return if 3 went straight into hi: lo root is 8, hi root is 3, giving (8 + 3) / 2 = 5.5 — completely wrong for [2, 3, 5, 8, 10, 14] whose true median is (5 + 8) / 2 = 6.5!

What to say in the interview (4 beats, ~90 seconds):

  1. Flat complete tree: "A binary heap packs a complete binary tree into a plain array with zero pointers: parent is (i − 1) // 2, children are 2i + 1 and 2i + 2, and every parent is <= its children."
  2. Core costs: "peek is O(1); push (append + sift-up) and pop (last element to root + sift-down with the smaller child) are O(log n); bottom-up heapify from the last non-leaf is O(n) worst case because most nodes live near the bottom."
  3. Python pitfalls: "heapq is min-only (negate numbers or wrap objects), heapify mutates in place returning None, and tuples use an integer tie-breaker (priority, idx, payload)."
  4. Patterns & trade-offs: "Min-heap of size k for top-k largest (gate on h[0] < x), size-k heap for O(N log k) k-way merge, (free_time, worker) for scheduling, and two back-to-back heaps for O(1) running median. For arbitrary lookup or ranges, switch to a hash map or balanced BST."
