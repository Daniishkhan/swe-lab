Trees, BSTs and traversals

A tree is a linked list that branches. Put an ordering rule on the branches and every comparison throws away half the remaining data. That only holds while the tree stays bushy, which is why balancing exists.

CoreThe one-sentence idea

In a binary search tree, everything left of a node is smaller and everything right is larger, so search is a walk down one path. Its cost is the tree's height: log n if it's balanced, n if it degenerates into a stick.

Build itFrom first principles

1. Start from the sorted array

A sorted array gives O(log n) search with binary search, but O(n) insert. What if the "middle element" weren't an array position but a node with pointers to the middle of each half? Then you could insert by adding a leaf instead of shifting. That is a binary search tree: a binary search frozen into pointers.

2. The BST invariant

For every node: all keys in the left subtree < node < all keys in the right subtree. Search, insert and delete each walk one root-to-leaf path, so they cost O(h), where h is the height.

3. The catch: height depends on insertion order

Insert 1, 2, 3, 4, 5 in order and every node goes right. The "tree" is a linked list, h = n, and you've lost the whole benefit. Try it in the playground below.

4. Balanced trees fix the height

They do a bit of extra work on insert and delete, called rotations, to guarantee h = O(log n). Know these at a conceptual level:

AVL

Left and right subtree heights differ by at most 1 at every node. Strictly balanced, so lookups are fast, but it rotates more often on writes.

Red-black

A looser coloring rule keeps the height under 2·log n. Fewer rotations per write. It backs Java's TreeMap, C++'s std::map and the Linux CFS scheduler.

B-tree (preview)

Hundreds of keys per node, so the tree is very shallow. It's built for disks, where each node read is expensive. Every relational database index uses one (chapter 6).

5. Traversal orders: when you visit the node

  • Pre-order (node, left, right): copy or serialize a tree; the root comes first.
  • In-order (left, node, right): on a BST, yields keys in sorted order. That's the BST's superpower.
  • Post-order (left, right, node): children before parent: delete a tree, compute sizes or heights, evaluate an expression tree.
  • Level-order (BFS with a queue): layer by layer. Use it for "minimum depth" or "right side view".
IntuitionAnalogy: twenty questions

A BST is a game of twenty questions where every question is "is it smaller than X?". A good questioner (balanced tree) halves the possibilities each time: 20 questions cover a million items. A bad questioner who asks "is it 1? is it 2? is it 3?" (degenerate tree) needs a million questions.

Physical picture for rotations: hold a mobile by a different string. The parts hang in the same left-to-right order (the sorted order is preserved), but the mobile hangs shorter.

InterviewWhat a senior answer adds
  • Hash map vs ordered tree is a real design decision. Choose the tree when you need ordering, range scans, floor/ceiling ("the next scheduled job after now"), or predictable worst-case latency without resize spikes.
  • Most tree problems are recursion on a contract. Say what your function returns for a subtree ("height", "is valid BST within (lo, hi)", "max path through this node"), trust it for the children, then combine. Saying that contract out loud is what interviewers listen for.
  • Validate-BST trap: checking only left < node < right locally is wrong. Pass down (low, high) bounds.
  • Real systems: databases use B+ trees (chapter 6), and in-memory sorted sets often use skip lists instead of trees because they're simpler to make concurrent (Redis sorted sets).
TrapsCommon mistakes
  • Assuming a BST is balanced. Plain BSTs fed sorted data degrade to O(n).
  • Recursion depth: a 10,000-node stick blows Python's default recursion limit. Iterative traversal uses an explicit stack.
  • Deleting a node with two children: replace it with its in-order successor (the smallest key in the right subtree), then delete that successor.
  • Mixing up "depth" (counted from the root) and "height" (counted from the leaves), and off-by-one on whether an empty tree has height 0 or -1. Pick one convention and say it.
RecallCheck yourself
Which traversal gives sorted output on a BST, and why?

In-order. It visits everything smaller (left subtree) before the node, and everything larger (right subtree) after it, recursively. That is the definition of sorted.

Can you rebuild a tree from its pre-order alone?

For a general binary tree, no. You need pre-order plus in-order (or explicit null markers). For a BST, yes: the in-order is just the sorted pre-order.

Roughly how tall is a balanced tree with a billion keys? A B-tree with 500 keys per node?

Binary: log₂(10⁹) ≈ 30. B-tree: log₅₀₀(10⁹) ≈ 3.3, so about 4 levels. That's why databases can find any row in a few disk reads.
