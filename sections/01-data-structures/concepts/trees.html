Split the search in half at every branch

Hash maps jump straight to an exact match, and flat lists preserve arrival order. Neither answers "give me every event between 2:00 and 2:05, sorted" while new events keep arriving every millisecond. A branching tree turns a straight line into a chain of forks so each yes-or-no choice cuts the remaining search space in half.

1Why isn't a hash map or sorted list enough?

You are building a live leaderboard for 1,000,000 players. Scores change every second, and every page load asks: "Who sits right above player X?" and "List all players between 4,200 and 4,500."

A hash map scatters keys across buckets, so finding who sits above 4,200 scans all million players. A sorted list answers ranges fast, yet every score update shifts ~500,000 entries.

To keep sorted order while data keeps changing, arrange keys as a branching signpost directory: every signpost splits all remaining keys into "smaller goes left" and "larger goes right".

Balanced trees bridge hash maps and flat arrays whenever sorted order must survive continuous inserts and deletes.

That branching shape shows up across four everyday engineering problems:

  • Ordered indexes & ranges: database B-trees, time-window queries, and live leaderboards.
  • Hierarchies: file systems, HTML DOM trees, and JSON/syntax trees.
  • Shared ancestry: git merge bases and Lowest Common Ancestor (LCA) routing.
  • Fast ordered statistics: k-th smallest item, predecessor, and successor under churn.

2How does a branching tree think recursively?

In a binary tree, one root signpost sits at the top, and every node links to at most two children: left and right. A node with zero children is a leaf. A node's depth is its distance from the root; the tree's height in this chapter is the number of levels (empty tree = 0, single root = 1). Interview tip: some textbooks count edges instead (empty = −1, single = 0), so always clarify height convention aloud.

Because every child heads a smaller binary tree, recursive solutions handle any tree by solving left and right subtrees first.
Ask left, ask right, combine. To solve a question for node (height, size, LCA), assume the recursive call already gives the right answer for node.left and node.right, handle None, and combine at node.

For example, tree height is two lines: return 0 if node is None, else 1 + max(height(node.left), height(node.right)). Each recursive call pauses its local variables on the call stack (a stack of active parent calls waiting for children to return), so visiting all n nodes takes O(n) time and O(height) stack memory.

Where the signpost directory picture breaks: a well-designed highway directory stays shallow (3–4 forks for a whole country). A plain binary tree has no built-in balance rule — insert sorted keys and every signpost points right, collapsing the directory into a million-sign straight road.

A perfect binary tree holds 1,048,575 nodes (2²⁰ − 1). How many levels tall is it, and how deep does a recursive walk's call stack grow?

Exact! Visiting all n nodes takes O(n) time, yet peak stack depth equals the height — only ancestors along the current root-to-leaf path wait simultaneously.

Trace a tiny 7-node perfect tree (height 3): you dive root → left → leaf (3 frames), pop back to left before diving right, and pop back to root before touching the right half. Peak frames = height = 20 (O(log n)), never n.

3What filing rule turns a tree into a fast search?

A Binary Search Tree (BST) adds one global signpost rule at every node:

  • Every key in node.left's entire subtree is strictly < node.val.
  • Every key in node.right's entire subtree is strictly > node.val.

Checking only direct children (node.left.val < node.val < node.right.val) is the #1 interview bug on Validate Binary Search Tree. Below, every parent-child pair passes locally while the tree is broken:

45 > 20 passes locally, yet searching for 45 from root 40 turns right toward 60 and misses it. Carrying (lo, hi) bounds catches every violation in one O(n) pass.

Using an explicit stack avoids Python's recursion limit on 100,000-node chains, and checking is not None avoids confusing a real value 0 with "no bound":

def is_valid_bst(root):
    if root is None: return True
    st = [(root, None, None)]           # (node, strict lo, strict hi)
    while st:
        n, lo, hi = st.pop()
        if (lo is not None and n.val <= lo) or (hi is not None and n.val >= hi):
            return False
        if n.right is not None: st.append((n.right, n.val, hi))
        if n.left is not None:  st.append((n.left, lo, n.val))
    return True
Go deeper: what if an interviewer allows duplicate keys in a BST?

The cleanest design stores a count field on each node — every search, successor, and delete rule stays strictly unique. Putting duplicates on the left (<=) or right (>=) works for basic search, yet subtly breaks Case 3 delete (promoting a duplicate to the wrong side) and complicates successor.

You write if lo and n.val <= lo: return False using lo = None for unbounded. Which input silently fails?

Classic Python bare-editor bug! bool(0) is False, so if lo: skips the lower-bound check when lo == 0. Always write lo is not None.

Step into the right child -1 of root 0: we push (-1, lo=0, hi=None). Now evaluate if lo and -1 <= 0: in Python — because 0 is falsy, the and short-circuits to False, accepting an invalid BST!

4How do search, insert, min, and max stay on one path?

Because every signpost eliminates the entire opposite branch, four operations walk one root-to-leaf path in O(height) time with zero backtracking:

  • Search (contains): at cur, stop if key == cur.val; step cur.left if smaller, cur.right if larger. Reaching None proves absence.
  • Insert: follow the exact search path to an empty child slot and attach the new leaf (returning False if an equal key is already present).
  • Min / Max: walk cur = cur.left until cur.left is None for min() (zero key comparisons!); walk right for max().

5How do you find the next higher key or a range fast?

Successor (smallest key strictly greater than key): walk down from the root remembering one candidate best = None — no parent pointers needed, and key doesn't have to be in the tree:

  • If key < cur.val: cur.val beats key → update best = cur.val and step left to search for a tighter candidate.
  • If key >= cur.val: discard cur and its left subtree → step right without changing best.

When cur reaches None, best is the exact successor in O(height) (~1 comparison per level).

Range query range(lo, hi) (sorted keys with lo <= k < hi): walk in-order, pruning dead subtrees before entering them (and returning [] right away if not (lo < hi)):

  • Descend into node.left only if lo < node.val (otherwise everything left is < lo).
  • Append node.val if lo <= node.val < hi.
  • Descend into node.right only if node.val < hi (if node.val >= hi, every key on the right is strictly > hi and outside [lo, hi)).

Total work visits only the two boundary paths plus the k reported keys: O(height + k).

In the BST built by inserting [50, 30, 70, 20, 40, 60, 80], you call successor(40). Which path runs?

Spot on! Turning left at 50 bookmarked best = 50; turning right at 30 and 40 never overwrote it, so hitting None returns 50 in 3 steps.

Check why remembering the last left turn matters: 40 has no right child, so its successor lives above it — specifically the deepest ancestor where you turned left (50). Only saving best = cur.val on every left turn captures it in one downward pass.

6How do you delete a node that has two children?

Walk down in O(height) tracking (parent, cur) to locate the target node x. Then handle one of three cases:

  1. Leaf (0 children): point parent's child link to None (or update self.root if parent is None).
  2. One child: splice x out by connecting parent straight to x's single child.
  3. Two children: find x's in-order successor s — the leftmost node of x.right (walking s.left uses zero comparisons!). Copy s.val into x.val, then splice out s. Because s is leftmost, s.left is guaranteed to be None, so removing s always reduces to Case 1 or Case 2!

Watch two classic bare-editor bugs in the code below: deleting the root (parent is None), and Case 3 when s is x.right itself (so sp is x, and splicing updates sp.right, NOT sp.left!):

if cur.left is not None and cur.right is not None:   # Case 3: two children
    sp, s = cur, cur.right
    while s.left is not None:
        sp, s = s, s.left
    cur.val = s.val                  # promote successor's key
    parent, cur = sp, s              # now unlink s (has at most 1 child!)
child = cur.left if cur.left is not None else cur.right
if parent is None:       self.root = child           # deleted root!
elif parent.left is cur: parent.left = child
else:                    parent.right = child        # handles s is x.right!
60 is greater than everything left of 50 and smaller than everything remaining on the right.

In the tree above, suppose node 60 also has a right child 65. After delete(50) promotes 60 to the root, where does 65 attach?

Exact! Unlinking 60 from 70.left is Case 2 (one child): parent.left = cur.right connects 70.left straight to 65, keeping 60 < 65 < 70 intact!

Check the inequality: 65 is larger than 60 and smaller than 70, so it must stay in 70's left subtree! Splicing 60 out of 70.left hands 60's only child (65) straight up to 70.left in one pointer write.

7How do you walk every node without crashing Python's stack?

Four orders visit every node: three Depth-First Search (DFS) orders and one Breadth-First Search (BFS) level order. Read all three DFS orders straight off any drawing with the finger-pass trick: trace your finger snugly around the outline of the tree — it passes each node three times:

Trace counterclockwise around the dashed outline: hit the left dot for pre-order, bottom dot for in-order, and right dot for post-order.
Step through all four traversal orders on the BST from tree_traversals.py (inserted as [8, 3, 10, 1, 6]).

Iterative templates (safe on 100,000-node chains): recursion crashes around depth 1,000 in Python. Keeping your own Python list stack in normal program memory — and a collections.deque for BFS (never list.pop(0): a 524,287-node tree has 262,144 nodes on its bottom level alone!) — keeps every traversal O(n):

def preorder(root):                     # push right first so LIFO pops left first
    if root is None: return []
    out, st = [], [root]
    while st:
        n = st.pop(); out.append(n.val)
        if n.right is not None: st.append(n.right)
        if n.left is not None:  st.append(n.left)
    return out                          # postorder: push left then right, then out.reverse()

def inorder(root):                      # dive left, pop & emit, step right
    out, st, cur = [], [], root
    while cur is not None or st:
        while cur is not None:
            st.append(cur); cur = cur.left
        n = st.pop(); out.append(n.val)
        cur = n.right
    return out

from collections import deque
def level_order(root):                  # freeze len(q) once per floor
    if root is None: return []
    out, q = [], deque([root])
    while q:
        lvl = []
        for _ in range(len(q)):
            n = q.popleft(); lvl.append(n.val)
            if n.left is not None:  q.append(n.left)
            if n.right is not None: q.append(n.right)
        out.append(lvl)
    return out
Go deeper: when the post-order reverse trick isn't enough

Running node, right, left and reversing produces the exact post-order values in O(n). However, if you need to compute bottom-up results iteratively (like subtree heights or freeing child nodes before parents), children must genuinely finish before you process the parent — track (node, visited) pairs on the stack (or a prev pointer) so you only evaluate node on its second pop.

In iterative preorder(root) above, what happens if you accidentally push n.left before n.right?

Exact! Because a stack is LIFO, whichever child you push last gets popped first — which is also why reversing that exact output gives post-order (left, right, node)!

Trace on root 8 with left 3 and right 10: pop 8, push 3 then push 10 → stack is [3, 10]. Next pop grabs the top (10, the right child!) before ever touching 3.

8How can trees break — and how do they stay balanced?

Insert sorted numbers 1, 2, 3, …, 500 into a plain BST and every key hangs on the right: height hits 500 instead of 9, turning every search into O(n).

Same sorted keys, completely different height. Picking the middle element at every split packs n keys into n.bit_length() levels.

Building a minimum-height BST from sorted data in O(n): pass index bounds (lo, hi) — never slice vals[:m]! Across all calls at each recursion level, slicing copies O(n) items, and across log₂ n levels that explodes to O(n log n) extra copies:

def build_balanced(vals):
    def build(lo, hi):
        if lo > hi: return None
        m = (lo + hi) // 2              # middle splits remaining keys evenly
        return TreeNode(vals[m], build(lo, m - 1), build(m + 1, hi))
    return build(0, len(vals) - 1)      # depth is ~log2 n, so recursion is safe

When a BST is the wrong tool (and Python's stdlib gap):

  • Need only exact lookups? A hash map beats a BST at O(1) average with smaller constants.
  • Static sorted data with zero updates? A sorted list + binary search is smaller and faster in CPU cache.
  • Only need the minimum or maximum? Use a binary heap (Chapter 1.4).
  • Python note: Python's standard library has no built-in balanced BST (unlike Java's TreeMap or C++'s std::map). In Python interviews, mention SortedList or SortedDict (from sortedcontainers) for production, bisect for small/read-heavy lists, or heapq + lazy deletion when only extremes matter.
Go deeper: AVL trees, Red-Black trees, and database B-trees

AVL trees keep left/right subtree heights within 1 using local pointer swaps (rotations) — shortest trees (fastest reads), slightly more rotations on writes. Red-Black trees bound the longest root-to-leaf path to ≤ 2× the shortest using at most 2–3 rotations per write — powering C++ std::map, Java TreeMap, and Linux's CFS scheduler. B+ trees widen each node to hundreds of sorted keys per 4–16 KB disk page so billions of rows fit in 3–4 levels.

You implement build_balanced(vals) by slicing build_balanced(vals[:m]) and build_balanced(vals[m+1:]) on 100,000 items. What is the total work?

Spot on! Level 1 slices ~n items, level 2 slices two halves totaling ~n items, and so on across log₂ n levels → O(n log n) copies. Passing integer bounds (lo, hi) reads each item once in O(n).

Count copies on 8 items: level 1 creates slices of size 3 and 4 (~7 copies), level 2 creates slices totaling ~4 copies, level 3 ~2 copies. Every level sums to O(n), and a balanced tree has log₂ n levels → O(n log n) total instead of O(n).

9How you use this in interviews (LCA, patterns & what to say)

Four high-frequency interview patterns build directly on Sections 2–8:

  • 1. Lowest Common Ancestor (LCA): given nodes p and q (assuming both exist in the tree), find the deepest node containing both in its subtree (a node counts as its own ancestor). In a BST, walk down from the root in O(height) time and O(1) space: go left if both are smaller, right if both are larger, and stop at the first split. In a general binary tree, ask left and right bottom-up in O(n):
def lca(node, p, q):
    if node is None or node is p or node is q:
        return node
    left = lca(node.left, p, q)
    right = lca(node.right, p, q)
    return node if (left and right) else (left or right)
  • 2. Kth Smallest in a BST: run Section 7's iterative inorder and stop immediately on the k-th pop — O(height + k) time, never scanning the rest of the tree!
  • 3. Serialize & Deserialize Binary Tree: emit pre-order values with a null marker "#" for every None child (e.g., 8,3,1,#,#,6,#,#,10,#,#); decoding consumes tokens from an iterator in the exact same pre-order in O(n).
  • 4. Binary Tree Maximum Path Sum: the classic twist on "ask left, ask right, combine" — a path bending through node can use both branches (node.val + max(0, L) + max(0, R), updating a global best initialized to float("-inf") so all-negative trees work, with 0 returned on None), while the value returned to node's parent can only continue down one branch (node.val + max(0, L, R))!
Go deeper: augmented order-statistics BST for dynamic k-th smallest

If an interviewer follows up Kth Smallest in a BST with "Now keys are inserted and deleted constantly, and kth(k) is called a million times!", augment every node with its subtree size (updated along the root-to-leaf path on every insert/delete). At any node, compare k against size(node.left) to step straight left, stop, or step right with k - size(node.left) - 1 in O(log n)!

In lca(node, p, q) above (assuming both exist in the tree), suppose p is an ancestor of q. Why does returning node immediately on node is p still work?

Sharp! Since q lives underneath p, nothing outside p's subtree can match q, so p bubbles all the way up. (Follow-up: if p or q might be missing from the tree, you must traverse both subtrees completely and verify both were found!)

Trace a tiny tree root=1 → left=p → left=q and right=4: calling lca(1, p, q) gets left = p (returned immediately) and right = None (4 matches neither). Then left or right returns p — the exact LCA!

What to say in the interview (4 beats, ~90 seconds):

  1. Why BSTs exist: "When data mutates dynamically and we need ordered operations — successor, k-th smallest, or range(lo, hi) — hash maps lose order and sorted arrays pay O(n) shifts. A balanced BST keeps search, insert, delete, and successor in O(log n) and ranges in O(log n + k)."
  2. Global invariant: "Every key in the left subtree is strictly smaller than the node, and every key in the right subtree is strictly larger — so validating a BST passes (lo, hi) bounds downward rather than checking direct children."
  3. Traversals & safety: "In-order emits a BST sorted; pre-order serializes with null markers; post-order combines child results; BFS uses a deque for level-order. Explicit stacks avoid Python's recursion limit on skewed trees."
  4. Balance & LCA: "Plain BSTs degrade to O(n) on sorted input, so self-balancing trees (AVL / Red-Black) use rotations to lock height at O(log n). General binary tree LCA bubbles matches bottom-up in O(n); BST LCA walks down to the first split in O(height)."
