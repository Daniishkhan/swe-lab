Chapter 1 · Part 3

Sorted and fast

P0 trees show up in most loopsabout 60 minutes8 quick checks · 8 exercises

A hash map finds any key in one step, but it has no idea which key comes next. A sorted list knows the order, but every insert shifts half of it. Trees are how you get both: order questions and fast changes, in O(log n). They're also the shape behind file systems, databases, compilers and half of all interview questions. This chapter builds the binary search tree from binary search itself, shows exactly how it breaks, and how balanced trees fix it.

By the end you'll be able to

  1. Explain a binary search tree as "binary search, frozen into pointers", and state its rule precisely.
  2. Search, insert and delete in a BST, including the two-children delete.
  3. Say why every BST operation costs O(height), and what makes the height n instead of log n.
  4. Explain what balanced trees (AVL, red-black) promise and how a rotation keeps that promise, without memorizing their code.
  5. Pick the right traversal order (pre, in, post, level) for a job, and write each without recursion.
  6. Choose between a tree, a hash map and a sorted array, and say what Python offers for each.

How to read this: go top to bottom. Answer each quick check before reading on; a wrong answer gets the idea explained a different way. Grey "Go deeper" boxes are optional on a first read. 1The problem: a leaderboard that keeps changing

You run the leaderboard for an online game with 10 million players. Scores change 50,000 times a second. Each player's screen shows the players ranked just above and just below them.

Try a hash map from player to score: updates are O(1), but "who's just above me?" means scanning all 10 million scores, because a hash map scatters keys on purpose. Try a sorted list of scores: "just above me" is binary search plus one step, about 24 comparisons. But every score change removes one entry and inserts another in sorted order, and each of those shifts about 5 million items on average. 50,000 changes a second × 2 × 5 million is 500 billion item moves per second.

Neither works. We need a structure that keeps keys in order (so "next one up" is cheap) but where inserting doesn't shift anything (so changes are cheap). A balanced binary search tree does both: about 24 steps for a lookup, an insert, a delete, or a "next one up", among 10 million keys. That's about 2.4 million steps a second for the whole leaderboard, which one core handles easily.

2Binary search, frozen into pointers

Start from what already works: binary search on a sorted array. Search for 60 in [10, 20, 30, 40, 50, 60, 70]. You look at the middle (40), go right, look at the middle of what's left (60), found. Every search, whatever the target, starts by looking at 40. Then it looks at either 20 or 60. Then at one of 10, 30, 50, 70.

Draw those decisions as a picture and you get this:

                 40              ← every search looks here first
              /      \
           20          60        ← then one of these
          /  \        /  \
        10    30    50    70     ← then one of these

 Smaller than the node? Go left. Bigger? Go right.

That picture is a binary search tree. Now here's the important part: if each number lives in its own little box with two pointers (like the linked list nodes from the previous chapter), we can store that picture itself instead of the array. Then inserting 55 doesn't shift anything. You walk down as if searching for it (40 → right to 60 → left to 50 → right: empty), and hang a new box there. One pointer changes (50's right). Nothing moves.

The words

Trees come with a lot of vocabulary. Here it is all at once, using the picture above (a family tree drawn upside down):

  • Node: one box (40, 20, 10…). Each has at most two children, called left and right. A tree with at most two children per node is a binary tree.
  • Root: the top node, 40. The only node with no parent.
  • Leaf: a node with no children (10, 30, 50, 70).
  • Subtree: a node plus everything below it. The left subtree of 40 is 20, 10 and 30.
  • Depth of a node: how many levels down it is; the root is at level 1. Height of a tree: its number of levels, so this one has height 3. (Many books count edges instead of levels, so the root has depth 0 and this tree has height 2. Either is fine; say which.)

A tree is a graph with no loops: from the root there's exactly one path down to each node. That's why "walk down from the root" always makes sense.

A binary search tree stores the decisions of binary search as nodes with left and right pointers. Searching walks down one level per comparison, and inserting hangs a new leaf where the search fell off, so nothing ever shifts.

3The BST rule, and search and insert

For walking down to work, every node must obey one rule:

The BST rule: every key in a node's left subtree is smaller than the node's key, and every key in its right subtree is bigger. Not just its children: the whole subtree.

That "whole subtree" part matters. Below, every parent and child pair looks fine: 30 < 50, and 60 > 30. But 60 sits in 50's left subtree while being bigger than 50. A search for 60 would go right at 50 and never find it. It's not a BST.

        50
       /  \
     30    70
       \
        60       ← bigger than 50, but in 50's left subtree: broken

Search and insert

Search: start at the root. Equal? Found. Smaller? Go left. Bigger? Go right. If you step off the tree (reach an empty spot), the key isn't there. Insert is the same walk, and at the empty spot where the search failed, you hang the new node. Duplicates are a choice: ignore them, count them in the node, or always send equals right. Say which.

Insert 50, 30, 70, 20, 40, 60, 80, 65 into an empty tree, then search for 65 (found) and 45 (not found). Highlighted nodes are the ones being compared; the found node turns green. Count them: each search compares with one node per level.

Each step goes down one level, so the cost of search and insert is the number of levels you pass: O(height). Keep that in mind; the whole next section is about it.

Is this a valid BST? Root 40; its left child 20; 20's right child 45; 40's right child 60.

Right. 45 > 20 is fine locally, but everything left of 40 must be smaller than 40. A search for 45 goes right at 40 and misses it. Checking only parent and child is the classic bug in "validate a BST".

Search for 45 and see what happens. At 40, 45 is bigger, so you go right to 60. 45 is smaller, so you go left: empty. Not found, even though 45 is in the tree. The rule is about the whole subtree, so each node must sit inside a range set by all its ancestors: below 40 on the left side, and above 20 under 20's right. 45 breaks the first limit. (Missing children are fine; a node can have zero, one or two.)

4Height is everything

Every operation walks from the root down, so the cost is the height. How tall does a tree get? That depends entirely on the order you insert the keys.

Insert 1, 2, 3, 4, 5, in that order. 1 becomes the root. 2 is bigger, so it goes right. 3 is bigger than 1 and 2, so it goes right of 2. Every new key goes to the far right. You've built a linked list leaning right, with height n. Searching for 5 visits all five nodes.

inserted 4, 2, 6, 1, 3, 5, 7          inserted 1, 2, 3, 4, 5, 6, 7

          4                            1
        /   \                           \
       2     6                           2
      / \   / \                           \
     1   3 5   7                           3
                                            \
 height 3: any search ≤ 3 steps              4 → 5 → 6 → 7    height 7

Same keys, same rule, and one tree is a perfect halving machine while the other is a linked list. A perfectly balanced tree with n nodes has height about log₂ n: 20 for a million keys, 30 for a billion, because each level doubles the number of nodes it can hold (1, 2, 4, 8…). A degenerate tree has height n: a million comparisons.

The same 15 keys, inserted in different orders. The height is the worst-case number of comparisons for a search. Sorted and zigzag orders both build a path, not a bushy tree. Shuffle a few times: random orders land in between, much closer to balanced.

The bad case isn't rare in real life. Data often arrives sorted or nearly sorted: timestamps, auto-increment ids, a file that was already in order. Insert user ids 1 to 1,000,000 into a plain BST and every lookup walks a million-node chain.

Random insertion order is kinder. With keys in random order, an average search compares with a little under 1.39 log₂ n nodes: about 25 for a million keys, against 20 for a perfect tree, and the deepest path is around 50. Not perfect, but logarithmic. You can't count on random input though, which is why section 8 exists.

Every BST operation is O(height). A balanced tree has height about log₂ n; a tree built from sorted input has height n and is really a linked list. The plain BST's worst case is O(n), and sorted input triggers it.

You insert the ids 1, 2, 3, …, 100,000 in order into a plain BST, then search for 100,000. About how many comparisons?

Right. Each new id is bigger than everything so far, so it hangs off the right end of a growing chain. The tree has 100,000 levels, and 100,000 is at the bottom.

log₂ n is the height of a balanced tree, and nothing here balances it; "twice the balanced height" would need some balancing too, just a looser kind. Watch the first few inserts: 1 is the root, 2 goes right of 1, 3 goes right of 2 (it's bigger than both), 4 right of 3… Every node has only a right child. That's a linked list with extra steps, so finding the last id walks all 100,000 nodes. Try the "sorted" option in the figure above.

5What the order buys you: min, next, range

Now the payoff: the questions a hash map can't answer.

  • Minimum: keep going left until there's no left child. The leftmost node is the smallest. Maximum: keep going right. O(height).
  • Successor (the next key up, "the player just above me"): if the node has a right subtree, it's the leftmost node of that subtree. If not, it's the nearest ancestor you reach by going up from a left child. Searching from the root for "smallest key bigger than x" does the same thing in one downward walk: every time you go left, remember the node as the best answer so far.
  • Floor and ceiling: the biggest key ≤ x, and the smallest key ≥ x. Same walk, same remembering.
  • Range query (all keys between a and b): do an in-order walk, but skip any subtree that can't hold keys in range: if a node is below a, its whole left subtree is too, so don't go left; if it's above b, don't go right. You walk down two boundary paths plus the k keys you report: O(height + k), instead of scanning all n. (Calling a from-the-root successor search k times would cost O(k · height).)
  • All keys in sorted order: visit the left subtree, then the node, then the right subtree. This is the in-order traversal, and it's O(n). It's sorted precisely because of the BST rule: everything smaller is visited before the node, everything bigger after.

Let's find the successor of 50 in the tree from the figure in section 3 (50 at the root; 70 on the right with children 60 and 80; 60 has a right child 65). 50 has a right subtree, so go right to 70, then left as far as possible: 60. 60 has no left child, so the successor of 50 is 60. Two hops down, in a tree that could hold millions.

Go deeper: "what's my rank?" (order-statistic trees)

The leaderboard also wants "you're ranked #48,213". A plain BST can't answer that without counting. The fix is to augment it: store in each node the size of its subtree. Then rank(x) walks down once: each time you go right, add the size of the left subtree plus one. "Who's ranked #k?" walks down the same way. Both are O(height). Inserts and deletes update sizes along their path at no extra Big-O cost. This is called an order-statistic tree. Redis does the same job for its sorted sets with a skip list that stores span counts (topic 01.11).

In a BST, a node has a right subtree. Where is its successor (the next key up)?

Right. Everything in the right subtree is bigger than the node, and the smallest of those is the leftmost one. The right child itself is only the answer when it has no left child.

Use numbers. Node 50 has right child 70, and 70 has a left child 60. All of 70's subtree is bigger than 50 (that's the BST rule), and we want the smallest of those. 70 isn't it: 60 is smaller and still bigger than 50. Keep going left from 70 until you can't: that's the smallest key bigger than 50. The parent can't be the answer here, because if the node is a left child its parent is bigger than its whole right subtree.

6Deleting: the two-children case

Deleting is where interviewers check whether you really understand the rule. Removing a node must leave a valid BST. There are three cases, by how many children the node has:

  1. No children (a leaf): just remove it. Its parent's pointer becomes empty.
  2. One child: the child takes the node's place. Picture a manager leaving a team of one: the one report now reports to the manager's boss. Everything in that child's subtree was already on the correct side of the boss, so the rule holds.
  3. Two children: the hard one. You can't attach two subtrees to one parent pointer.

For two children, don't remove the node's box at all. Replace its key with a key that can sit there without breaking the rule, then delete that key from where it came from. Which key fits? It must be bigger than everything on the left and smaller than everything on the right. The successor fits exactly: it's the smallest key in the right subtree, so it's bigger than the whole left side and no bigger than anything left on the right.

And here's why it's not recursive trouble: the successor is the leftmost node of the right subtree, so it has no left child. Deleting it is case 1 or case 2. The hard case always turns into an easy one. (The predecessor, the biggest key on the left, works just as well.)

Delete the root, 50, which has two children. Watch where the successor comes from, and that the in-order sequence underneath stays sorted at every step.

Delete a leaf: remove it. One child: splice the child up. Two children: copy in the successor (leftmost of the right subtree), then delete the successor, which has at most one child. All O(height).

You delete a node with two children by copying its successor's key into it. Why is deleting the successor's old node always easy?

Right. It's the leftmost node of a subtree, so by definition there's nothing to its left. It may still have a right child, which is why it's "at most one child", not "a leaf".

Look at how the successor is found: go right once, then left until you can't. "Until you can't" means the node you stop at has no left child. But it can have a right child: in the figure, 60 has a right child 65, which moves up when 60 is removed. So it's never the hard case, but it's not always a leaf either. And it's the right child only if the right child has no left child.

7Traversal orders: when do you visit the node?

Many tree problems need to visit every node once. There are four standard orders, and choosing the right one often is the solution.

Picture tracing around the outside of the tree with your finger, starting left of the root, going down the left side, hugging every node, and coming back up the right side. Your finger passes each node three times: on its left side (on the way down), underneath it (between its two subtrees), and on its right side (on the way back up). Each traversal order just picks which of those three passes is the moment you "visit" the node:

OrderVisit the node…Recursive shapeUsed for
Pre-orderbefore its childrennode, left, rightcopying or saving a tree (the parent must exist before its children)
In-orderbetween its childrenleft, node, righta BST's keys in sorted order; checking a BST is valid
Post-orderafter its childrenleft, right, nodeanything where a parent needs its children's answers first: folder sizes, tree height, deleting a tree
Level-orderlevel by level, top downa queue, not recursion"print each level", shortest path from the root, the nearest node with some property
The tree from section 3. Pick an order and step through it. Green nodes are visited; the output row shows the order. In-order comes out sorted. In post-order, notice that every node comes after its children.

Post-order in real life: folder sizes

How big is a folder? It's the size of its own files plus the size of every subfolder, and you can't add a subfolder's size until you've computed it. So you must finish the children before the parent: post-order. That's exactly what du does on Linux.

Level-order needs a queue

Level-order visits all of level 1, then all of level 2, and so on. Nodes on the same level aren't connected to each other; they're found through their parents. So as you visit a node, put its children at the back of a line, and always take the next node from the front: first discovered, first visited. That's a FIFO queue (collections.deque from the previous chapter). This is breadth-first search, which chapter 2 extends to any graph.

Recursion depth is the height

The three depth-first orders are three lines of recursion each. But each recursive call waits on the call stack until its subtree is done, so recursion uses O(height) memory, and Python stops at about 1,000 levels. A balanced tree with a billion nodes has height 30, no problem. The degenerate 100,000-node chain from section 4 crashes with RecursionError. The fix is to keep your own stack (a list) instead of the call stack. For in-order, the stack holds the path of nodes you've gone left from and still owe a visit:

  1. From the current node, go left as far as you can, pushing each node on the way down. Each one is waiting for its left subtree to finish.
  2. Pop one. Its left subtree is done, so visit it.
  3. Move to its right child and repeat from step 1. If it has none, the next pop is the nearest ancestor still waiting.

That's the call stack, made visible: the list holds exactly what the paused recursive calls would hold. Its size is O(height), but it lives in ordinary memory, which can hold millions of entries. You'll write all four orders this way in exercise 5.

Pre-order visits a node before its children (copying), in-order between them (sorted BST output), post-order after them (parents need children's answers), level-order by depth with a queue. Recursion costs O(height) stack space; on deep trees, use an explicit stack.

You need the total size of every folder on a disk, where a folder's size is its files plus all its subfolders. Which traversal?

Right. A folder can only add up its subfolders once they're all finished, so every child comes before its parent. That's post-order.

Ask: what does a folder need before it can finish? Its subfolders' totals. Pre-order visits the top folder first, before any subfolder is measured, so it can't know the answer yet. Level-order also visits parents before children. Only post-order guarantees that when you're at a folder, all of its subfolders are already done.

Which traversal is easiest to write with a queue rather than a stack or recursion?

Right. Level-order visits nodes in the order they were discovered, level by level, and "first discovered, first out" is a queue.

In-order and post-order go deep first and come back up: the most recent unfinished node is the one to return to, which is a stack (or recursion, which is the call stack). Level-order is different: after visiting 50 you want 30 and 70 before any of their children. The children of 30 were discovered before the children of 70, so they go first. Discovered first, visited first: a queue.

8Balanced trees: keeping the height at log n

The plain BST's flaw is that the input order decides the shape. Balanced trees fix it by repairing the shape as they go, so the height stays O(log n) for any insert order. To repair a shape, they need a move that changes the shape without breaking the BST rule.

The rotation

Picture a hanging mobile. You can pick it up by a different node and let it hang again: the pieces are still in the same left-to-right order, but a different piece is at the top. A rotation does that to two neighboring nodes, a parent and its child. (Where the picture breaks: a real mobile rehangs everything at once. A rotation is local: only one subtree, B below, changes parent, and three pointers change.)

      x                                  y
     / \       rotate left at x         / \
    A   y      ───────────────►        x   C
       / \     ◄───────────────       / \
      B   C     rotate right at y    A   B

 Left to right, both pictures read: A, x, B, y, C. Same order, so still a valid BST.
 Three pointers change, so it's O(1). C moves up one level, A moves down one level,
 and B stays at the same depth. So a right-heavy spot gets more even.

The trick to remembering it: B changes parent. B is everything between x and y. In the left picture it's y's left subtree, in the right picture it's x's right subtree. Both places mean "bigger than x, smaller than y", so the rule holds.

Insert 10, 20, 30 into a tree that rebalances. After 30, the root's right side is two levels taller than its left: too lopsided. One left rotation at 10 fixes it.

AVL trees and red-black trees

The two classic balanced BSTs differ in how lopsided they allow a node to get before they rotate:

  • AVL trees (1962): at every node, the heights of the left and right subtrees differ by at most 1. After an insert or delete, walk back up and rotate wherever that breaks; one or two rotations fix each spot. The guarantee: height ≤ about 1.44 log₂ n.
  • Red-black trees (1972–78): each node is colored red or black, with two rules: a red node never has a red child, and every path from a node down to an empty spot passes the same number of black nodes. So the longest path (alternating red and black) is at most twice the shortest (all black). The guarantee: height ≤ 2 log₂(n + 1). Looser than AVL, but inserts and deletes need fewer rotations: at most 2 for an insert, 3 for a delete.

Both give O(log n) worst case for search, insert, delete, min, successor and range queries. For a million keys, AVL's height is at most about 29 and red-black's at most about 40. Interviewers almost never ask you to code either one. They ask what they guarantee, how (rotations), and the trade-off:

Go deeper: B-trees, when nodes live on disk

A binary tree with a billion keys has 30 levels. In memory, 30 steps is nothing. On disk, each step can be a separate read, and a random read on an SSD is around 100 µs, about 1,000 times slower than RAM. So databases use fat nodes: a B-tree node holds hundreds of sorted keys and has hundreds of children, sized to fill one disk page (4–16 KB). With 500 children per node, a billion keys fit in about 4 levels (500⁴ = 6.25 × 10¹⁰), and the top levels stay cached in memory. Same BST rule and the same in-order sorted output, but a different way to stay balanced: when a node overflows, it splits in two and pushes its middle key up to the parent, so the tree grows at the root and every leaf stays at the same depth. (A red-black tree is secretly a B-tree with up to 4 children per node, drawn as a binary tree.) The default index in every major relational database (PostgreSQL, MySQL's InnoDB, SQLite) is a B-tree variant. Topic 01.13 covers them.

What does a rotation guarantee to stay the same?

Right. A rotation changes the shape (and the height, which is the point), but reading the keys left to right gives the same sequence, so the tree is still a valid BST.

Read the two pictures in the diagram left to right: both give A, x, B, y, C. That's the one thing that must not change, because that's what makes it a BST. Everything else is allowed to change, and does: a different node ends up on top (so the root can change if you rotate at the root), and one side gets shorter while the other gets taller. Changing heights is the whole reason to rotate.

Go deeper: tree questions interviewers follow up with
  • BST iterator: next() in O(1) amortized and O(height) memory: it's the explicit-stack in-order walk from section 7, paused between visits.
  • k-th smallest: in-order walk and stop at k (O(height + k)), or subtree sizes (section 5's aside) for O(height).
  • Lowest common ancestor: in a BST, walk down from the root until the two keys split to different sides. In a plain binary tree, use post-order: a node is the answer if its subtrees each report one of the two, or if it is one of the two and either subtree reports the other (one key is an ancestor of the other).
  • Serialize a tree: pre-order with markers for empty spots rebuilds it exactly. In-order alone can't: many shapes share one in-order sequence. Pre-order plus in-order (no duplicates) can.
  • Duplicates: decide up front (counts in the node, or "equal goes right") and say how search, delete and range treat them.
  • Other balanced trees: treaps (random priorities, balanced in expectation), splay trees (recently used keys move to the root), skip lists (topic 01.11; easier to make concurrent, which is why Java has ConcurrentSkipListMap but no concurrent TreeMap).

9Trees vs hash maps vs sorted arrays

When should you reach for a tree? Ask which questions you'll ask of your data:

  • Only "is it there?" and "what's its value?" Hash map. O(1) beats O(log n), and it's simpler.
  • Order questions (next up, min, range, sorted output) and frequent changes: balanced BST, O(log n) for everything.
  • Order questions, data rarely changes: a sorted array with binary search. It's O(log n) too, but with no pointers it uses less memory and is much faster in practice (cache-friendly, as in the previous chapter).
  • Only "the smallest" (or largest), over and over: a heap, the next chapter. Cheaper than a full tree for that one question.

What Python gives you

Python has no balanced BST in the standard library. Your options in an interview:

  • Say it plainly: "I'd use a balanced BST here, like Java's TreeMap or C++'s std::map." Interviewers accept that, and may ask how it stays balanced.
  • bisect on a sorted list: O(log n) search, O(n) insert. Fine for a few thousand items or few changes.
  • sortedcontainers.SortedList (third-party, widely used): about O(log n) per operation in practice. It's not a tree; it's a list of sorted sublists of about 1,000 items each, which is faster in Python than any pointer-based tree.
Go deeper: why not always use a tree instead of a hash map?

Beyond O(1) vs O(log n): for a million keys, log₂ n ≈ 20 comparisons, each possibly a cache miss (about 100 ns), so a tree lookup can cost a couple of microseconds while a hash lookup is one or two misses. Trees also need keys that can be ordered, while hash maps need keys that can be hashed. In exchange, trees give a worst case of O(log n) with no hash-flooding risk (Java 8's HashMap turns a bucket into a red-black tree once it holds 8 entries and the table has at least 64 slots, for exactly that reason; it works best when the keys are Comparable), and ordered iteration for free.

A service stores 50 million user sessions by session id. It looks sessions up and deletes them. It never needs them in order. Which structure?

Right. With no order questions, a tree's ordering is a cost you pay for nothing. O(1) average beats O(log n), and log₂ of 50 million is about 26 pointer hops.

Ask what the tree's extra power is for: order (next, min, range, sorted output). This service never asks an order question. So you'd pay about 26 comparisons per lookup, plus pointer-chasing, for a feature you don't use. A sorted array is worse still: every new session would shift millions of entries. Only "lookup and delete by key" means hash map.

10What to say in the interview

For the leaderboard, a strong answer sounds like this:

"I need two kinds of questions: point updates when a score changes, and order questions like 'who's just above this player'. A hash map handles updates in O(1) but has no order, so neighbors would be O(n). A sorted array has order, but each update shifts O(n) items. A balanced BST keyed by (score, player id) gives O(log n) for updates and for successor and predecessor: about 24 steps for 10 million players. I'd keep a hash map from player to current score too, so I can find and delete their old entry. If they want 'what's my rank', I'd store subtree sizes in each node. In Python I'd use SortedList; in Java, a TreeMap. At larger scale this is what Redis sorted sets do, with a skip list."

Habits that make you sound senior:

  • Say "O(height)" first, then what the height is: "O(log n) if balanced, O(n) for a plain BST on sorted input".
  • When validating a BST, pass down a (low, high) range; never just compare a node with its children.
  • Name the traversal order and why it fits (children before parent → post-order).
  • Mention recursion depth on deep or unbalanced trees, and how you'd avoid it.
  • Know the AVL vs red-black trade-off in one sentence, and where each is used.

✓What to remember

  1. A BST is binary search frozen into pointers: left subtree smaller, right subtree bigger, for the whole subtree.
  2. Search, insert, delete, min, successor and range queries all cost O(height).
  3. Balanced height ≈ log₂ n (20 for a million). Sorted inserts into a plain BST give height n.
  4. Delete with two children: copy in the successor, then delete the successor, which has no left child.
  5. Pre-order = parent first (copy), in-order = sorted, post-order = children first (sizes, delete), level-order = queue.
  6. Recursion uses O(height) stack; use an explicit stack on deep trees.
  7. Rotations change the shape but keep the in-order sequence. AVL is stricter (shorter, more rotations); red-black is looser (fewer rotations) and is in most standard libraries.
  8. No order questions? Use a hash map. Order plus changes? Balanced tree. Order, rarely changes? Sorted array.

Do them in order. Warm-ups are pen and paper: commit to an answer before you open it. Core exercises are code in exercises/, and their tests measure how much work your code does (key comparisons, reads, recursion depth, a time cap), so a correct but slow answer fails.

Warm-up · pen and paper

1. Build it, walk it

Insert 8, 3, 10, 1, 6, 14, 4, 7, 13 into an empty BST. Draw it and give its height. Then write the pre-order, in-order, post-order and level-order sequences.

Answer 
          8
        /   \
       3     10
      / \      \
     1   6      14
        / \    /
       4   7  13

Height 4. Pre-order: 8, 3, 1, 6, 4, 7, 10, 14, 13. In-order: 1, 3, 4, 6, 7, 8, 10, 13, 14 (sorted, as it must be). Post-order: 1, 4, 7, 6, 3, 13, 14, 10, 8. Level-order: 8 | 3, 10 | 1, 6, 14 | 4, 7, 13.

Warm-up · pen and paper

2. Delete, three ways

In the tree from warm-up 1, delete 14, then 3, then 8, one after another. Draw the tree after each delete, using the successor for the two-children case.

Answer

Delete 14 (one child, 13): 13 takes its place as 10's right child. Delete 3 (two children): its successor is the leftmost node of its right subtree, 6 → 4. Copy 4 into 3's node, then remove the old 4 (a leaf). Now 4 has children 1 and 6, and 6 has only 7. Delete 8 (two children): successor = leftmost of the right subtree, 10 (10 has no left child). Copy 10 into the root and splice the old 10 out: its only child, 13, takes its place. Final: root 10; left 4 (children 1 and 6; 6 → right 7); right 13. In-order: 1, 4, 6, 7, 10, 13, still sorted.

Warm-up · pen and paper

3. How tall?

For one billion keys, about how many levels in: (a) a perfectly balanced binary tree; (b) the worst AVL tree; (c) the worst red-black tree; (d) a plain BST built from sorted input; (e) a B-tree with 1,000 children per node?

Answer

(a) log₂ 10⁹ ≈ 30. (b) about 1.44 × 30 ≈ 43. (c) at most 2 log₂(10⁹ + 1) ≈ 60. (d) a billion. (e) log₁₀₀₀ 10⁹ = 3, so 3 to 4 levels (nodes are rarely completely full). This is why "O(log n)" hides a big practical range: 3 disk reads versus 30 versus 60.

Core · code

4. BST with delete, successor and range

In exercises/bst.py, build a plain (unbalanced) BST: insert, contains, delete (all three cases), min, max, successor, range queries and in-order iteration, plus height(). The tests hand you keys that count every comparison: a search must compare with about one key per level, a successor or range query must not scan the whole tree, and inserting 1 to 500 in order must give height 500, so you see the degenerate case with your own code.

Core · code

5. Traversals and tree checks without recursion trouble

In exercises/tree_traversals.py: pre-order, in-order, post-order and level-order traversals, is_valid_bst (section 3's trap is in the tests), and build_balanced, which turns a sorted list into a tree of minimum height. The tests use a 100,000-node chain, so recursion fails; they count reads of the input list, so slicing it at every level fails; and a time cap catches a level-order that shifts a list.

Stretch · build

6. Make it balance itself

Copy your BST into a scratch file and turn it into an AVL tree: store a height in each node, and after each insert walk back up, doing a single or double rotation wherever the two child heights differ by 2. Insert 1 to 100,000 in order and check that the height stays at most the AVL bound of about 1.44 log₂ n ≈ 24 (sorted inserts actually give about 17, close to perfect). Compare with your plain BST's 100,000.

7. Rank queries

Add a subtree size to each node of your BST (the "Go deeper" in section 5) and write rank(key) (how many keys are smaller) and kth(k) (the k-th smallest), both in O(height). Keep the sizes right through inserts and all three delete cases. Test against sorted() on random operations.
