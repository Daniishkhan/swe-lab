Chapter 1 · Part 6

Words that share a path

P1 autocomplete, routing tables, prefix questionsabout 60 minutes10 quick checks · 9 exercises

A hash map answers "is this exact key here?" in one step. It can't answer "which keys start with car?", or "which of my keys is the longest one that this address starts with?". A search box asks the first question on every keystroke. Every router on the internet asks the second for every packet. The structure built for both is the trie: a tree where words that start the same way share the same path. This chapter builds it from that one idea, prices its big weakness (memory), squeezes it into a radix tree, and then uses it for autocomplete, IP routing and a few interview favorites.

By the end you'll be able to

  1. Explain why a hash set can't answer prefix questions, and when a sorted array can.
  2. Insert and look up words in a trie, explain the end-of-word mark, and say why both cost O(L) however many words are stored.
  3. List, count and rank the words under a prefix, and explain why a number or a short list stored at each node makes those fast.
  4. Estimate a trie's memory, choose how to store each node's children, and compress the trie into a radix tree.
  5. Route an IP address by longest prefix match with a binary trie, and reuse the same bit trie for maximum XOR.
  6. Say when a trie is the wrong tool, and what to use instead.

How to read this: go top to bottom. Answer each quick check before reading on; a wrong answer gets the idea explained a different way. Grey "Go deeper" boxes are optional on a first read. 1The problem: a question on every keystroke

You build the search box for an online store with 1 million products. As the user types, a list of suggestions appears under the box: type "car" and you see "car seat", "car charger", "cardigan". About a tenth of a second is the usual limit for a response to feel instant. At peak, your users type 5,000 keystrokes per second in total, and every keystroke is a new question: which product names start with what's in the box so far?

First version: keep the names in a list and test each one with startswith. That's 1 million checks per keystroke, and 5,000 × 1,000,000 = 5 billion checks per second, every second, just for the search box.

Look at what the scan wastes. "car seat", "car charger" and "cardigan" all begin with c-a-r, and the scan reads those same three letters again for each of them. It also visits the hundreds of thousands of names that don't even start with c. By the end of this chapter, a keystroke will cost about as many steps as the letters typed so far, plus the handful of suggestions shown: a few dozen steps instead of a million.

Two words used all chapter: n is how many words are stored, and L is the length of the word or prefix you're asking about. A prefix is a starting piece of a word: "c", "ca" and "car" are prefixes of "card", and so is "card" itself, and so is the empty string "".

2What we already have, and where it breaks

Before building anything new, try the tools from earlier chapters on the question "which stored words start with p?".

A hash set turns the whole string into a slot number. Picture a coat check: you hand in a coat and get a ticket number, and two coats from the same family get completely unrelated numbers. "car" and "card" land in unrelated slots. So a set answers "is car stored?" fast, but "which words start with car?" means checking every word. You could patch it by storing every prefix of every word in a hash map, prefix → list of words. With 1 million names of 20 letters, that's up to 20 million prefix keys, and each name sits in the lists of all 20 of its prefixes: 20 million list entries. Heavy, but not crazy. Real typeahead systems do a version of it, keeping only the best few words per prefix; section 7 gets there from the trie side.

A sorted array with binary search is much better. Alphabetical order puts every word that starts with "car" in one unbroken block, the way a paper dictionary keeps all the car- words on the same few pages. Binary search finds the first word ≥ "car" in about log₂ 1,000,000 ≈ 20 comparisons; then walk forward until a word stops starting with "car". For a list that never changes, that's a strong answer. It breaks in three places:

  • Adding a word shifts everything after it: 500,000 moves on average for a million names.
  • Ranking by popularity means reading the whole block. In an English dictionary, about 17,000 words start with "a".
  • It answers one direction only: "which stored words start with my text?". A router asks the other direction: "which stored prefix is the longest one that my text starts with?" (section 10).

A hash set scatters similar words on purpose, so it can't answer prefix questions. A sorted array keeps them together and answers in O(L log n), but pays O(n) per insert and only answers "who starts with my text?". The trie keeps similar words together and stays cheap to change.

You keep 1 million product names in a Python set. The user types "car". Using only the set, how do you find the names that start with it?

Right. A hash set has no idea which names are "near" "car". Its only fast question is "is this exact string here?". For prefixes you need order (a sorted array) or shared paths (a trie).

A hash function is built to scatter: change one letter and the slot changes completely. In CPython, hash("car") and hash("card") are unrelated numbers, so the slot after "car" holds some random other name. And a set keeps no order at all; iterating it gives slot order, which is hash order, which is meaningless. Nothing about where "car" lives tells you where "card" lives, so the only way left is to look at every item.

3Share the starts: one letter per step

The scan's waste was reading c-a-r once per word. What if the words that start with c-a-r physically shared those three letters, so they're stored once and walked once?

Picture a road network that grows out of one roundabout. At every junction, each exit has a sign with one letter. To reach "cat", you take exit c, then a, then t. To reach "car" you drive the same road for c and a and turn off at the last junction. Words that start the same travel together, and split up exactly where they first differ.

 car, card, care, cart, cat, do, dog:

That's a trie, from retrieval. (Most people say "try", so it doesn't sound like "tree".) Each node is a junction. Each edge, the line from a node down to one of its children, carries one letter. The root is the node at the top, and it stands for the empty string.

Here's the fact everything else rests on: a node is a prefix. The letters on the path from the root down to a node spell one string, so the node for "ca" stands for "ca". Every word that starts with "ca" lives somewhere below that node, and no other word does. "Which words start with ca?" becomes "walk to the ca node and look underneath".

The sharing is real savings. The seven words above have 23 letters but need only 10 nodes, because car, card, care and cart all reuse c-a-r. The more words share starts, the bigger the saving.

Where the road picture breaks: real roads merge back together. A trie's roads never merge: every node has exactly one road coming into it, which is what makes it a tree. So "cat" and "bat" share nothing, even though they end the same way. (Structures that share endings too exist; see section 12.)

A trie stores strings as paths from the root, one letter per edge. Strings that share a prefix share the path for it. Each node stands for exactly one prefix, and everything below it starts with that prefix.

You insert "tea", "ten" and "to" into an empty trie. How many nodes does it have, counting the root?

Right: the root, t, te, tea, ten and to. One node per distinct prefix: "t" is shared by all three words and "te" by two, so they're stored once.

Count distinct prefixes, because each node is one prefix. The prefixes of tea are t, te, tea. Of ten: t, te, ten. Of to: t, to. The distinct ones are t, te, tea, ten, to: five, plus the root for "" makes 6. Counting every letter (9) forgets the sharing. Stopping at t, e and o forgets that "tea" and "ten" still need their own last letters, a and n, below e.

4Where does a word end?

Insert only "card" into an empty trie. The path c-a-r-d now exists. Now ask: is "car" stored? Walking c, a, r works fine: every node is there. But nobody inserted "car". Its path exists only because "card" drives through it.

Picture a bus route. The bus drives through many streets but only stops at some. In a trie, the path from the root is the route, and each word needs a stop sign where it ends. "card" has a stop at d. "car" is a street the bus passes without stopping, until someone inserts "car" and puts a sign up at r.

So every node carries one more piece of information: an end-of-word mark (also called terminal), the ● in the diagram above. A lookup walks the letters and then checks the mark. In the diagram, "car" has a mark at r even though r has children: a word can end at a node that still has roads going on. "do" and "dog" are the same.

The mark can carry more than yes or no. Store a value there and the trie becomes a map from strings to values, like a phone book (name → number), where "is a word" means "has a value". Store a count and it holds a bag of words where repeats matter.

A path existing only means some word starts with those letters. A word is stored only if the node where it ends carries an end-of-word mark (or a value). Words can end at nodes that still have children.

A trie holds exactly two words: "card" and "dog". What do contains("car") and starts_with("do") return?

Right. The path c-a-r exists, but the node r has no end mark, so "car" isn't a word. The path d-o exists and leads on to the word "dog", so some word starts with "do".

Separate the two questions. contains asks "did a bus stop here?": walk c-a-r, then look for the mark at r. Only "card" was inserted, so the only marks are at d (of card) and g (of dog): "car" is False. starts_with asks "does the road go on from here?": walk d-o; you made it, and "dog" continues below, so True. Mixing them up is the most common trie bug: a contains that forgets the mark says True for every prefix of every word.

5Insert and look up, one letter at a time

Both operations are a walk from the root, one letter per step.

  • Insert: for each letter, follow its edge if it exists, or build a new node if this is the first word to need it. At the last letter, put up the end mark.
  • Look up: for each letter, follow its edge. If the edge is missing, you fall off the trie: no stored word starts with these letters. If you get through every letter, check the end mark.
Insert car, cat, card, care, dog and do, then run four lookups. Blue: the node you're standing on. Green ring: a word ends here. Red: fell off. Watch "do": it builds nothing, it only puts up a sign on a node "dog" already built.

In Python, a node is a small object with a dict from letter to child, and a flag for the mark. Insert builds the roads it needs:

class Node:
    def __init__(self):
        self.kids = {}          # letter -> child Node
        self.end = False        # does a word end here?

def insert(root, word):
    node = root
    for ch in word:
        if ch not in node.kids:             # first word to need this road
            node.kids[ch] = Node()
        node = node.kids[ch]
    node.end = True                         # put up the stop sign

Finding the node for a string is the same walk, except that a missing edge means "stop":

def find(root, s):
    """The node that spells s, or None if no stored word starts with s."""
    node = root
    for ch in s:
        node = node.kids.get(ch)
        if node is None:                    # fell off the trie
            return None
    return node

Then contains(w) is "find(w) exists and its end mark is set", and starts_with(p) is "find(p) exists". That second one has a hidden assumption, which section 6 comes back to: every node must lead to at least one word. (The root is the exception: it exists even when the trie is empty.)

What does it cost?

Each step reads one letter and follows one edge. A word of L letters costs L steps, whether the trie holds 10 words or 10 million. The number of words, n, doesn't appear at all: insert and lookup are O(L). A binary search over a sorted array, by contrast, costs about log₂ n comparisons of up to L letters each.

Careful, though: a hash set lookup is O(L) too. Computing the hash reads every letter, and confirming a match compares the letters again. So for "is this exact word stored?", the trie is not faster in big-O, and in practice it's usually slower. The hash set makes one quick pass over letters that sit side by side in memory, then one jump to a slot. The trie makes L jumps, one per node, and each jump can be a cache miss: a read from main memory (around 100 ns) instead of from the CPU's cache (around 1 ns). The trie earns its place with the questions a hash set can't answer, which are the next three sections. (One smaller advantage: with array children, a trie has no collisions and never resizes, so its O(L) is a worst case. A hash set's O(L) is an average, and an insert that triggers a resize copies the whole table.)

Insert and lookup walk one letter per step: O(L), independent of how many words are stored. For exact lookups alone that's no better than a hash set (hashing is O(L) too) and usually slower in practice; the trie's value is prefix questions.

A trie holds 10 million words. About how many steps does it take to look up a 9-letter word?

Right. One step per letter: at each node you jump straight to the child for the next letter. 10 words or 10 million, a 9-letter word is 9 steps.

Picture the roads again. You don't search among the junctions; at each junction you read the sign for your next letter and take that exit. There's no halving (that's binary search, where log₂ n comes from), and you don't try every exit (a dict, or an array indexed by letter, finds the right child in one step). So the number of steps is the number of letters: 9. What grows with n is the number of nodes, which is memory, not lookup time.

6Everything under a prefix

Now the question the hash set couldn't answer. To find every word that starts with "car", walk c-a-r to its node: 3 steps. Every word below that node starts with "car", and no other word does. Then visit the node's subtree (the node and everything below it) with a depth-first walk: go down as far as you can, back up one level, try the next child. Every time you reach a node with an end mark, output the letters on the path to it.

Visit each node's children in letter order and the words come out in alphabetical order, with no sorting at all. Two reasons. A word is output when you reach its node, before you go deeper, so "car" comes out before "card": a prefix sorts before its longer versions. And everything under "card" comes out before everything under "care", because d comes before e. Those two rules are exactly how alphabetical order is defined.

Type a prefix. Blue: the walk down to the prefix's node. Yellow: the nodes the listing visits below it. Green ring: a word ends here. Try "c", then switch to "first 3" and watch how few nodes the walk touches. Try "ca" and "cab".

The cost is O(L + size of the subtree), and that subtree can be huge: in a 234,456-word English word list, 16,983 words start with "a". Two fixes cover almost every real use:

  • Stop early. The search box shows 10 suggestions, not 16,983. Stop the walk the moment you have k words. Each word costs at most its length in steps, so that's about k × (word length) steps instead of the whole subtree.
  • Store a count at each node. "How many words start with car?" Keep, at each node, how many words end in its subtree. Inserting a new word adds 1 at every node on its path, deleting subtracts 1. Then counting is a walk plus one read: O(L).

Deleting a word

Walk to the word and take down its end mark. That alone isn't enough. If "cart" was the only word under its last t, that node now leads to no word at all. Leave it there and two things go wrong: memory never comes back, and starts_with("cart") still says yes, because the path exists. So after taking the mark down, cut off every node that no longer leads to a word. With counts it's easy: subtract 1 along the path, and the first node whose count reaches 0 can be cut off from its parent, along with everything below it. Without counts, walk back up from the end and remove nodes while they have no children and no mark.

Prefix listing: walk L steps to the prefix's node, then depth-first through its subtree, children in letter order, which gives sorted output for free. Stop after k words to keep it cheap. A count per node turns "how many start with p?" into O(L). Deleting must also remove nodes that lead nowhere.

A trie holds "b", "ab" and "abc". A depth-first walk from the root, visiting children in letter order and outputting a word when it reaches the word's end mark, lists them as…

Right, and that's alphabetical order. The walk takes the a-branch first and finishes it completely (ab, then abc below it) before it moves to the b-branch.

Trace it. From the root, the children are a and b; a comes first, so go down a. The a node isn't a word. Its child b spells "ab": a word, output it, then go deeper: "abc", output it. Nothing more below, so back up all the way and take the root's b child: "b". Result: ab, abc, b. Shortest-first (b, ab, abc) is what a level-by-level walk (breadth-first) gives. Deepest-first (abc, ab, b) is what you get if you output a word after visiting its children instead of before.

7The best k, not the first k

Alphabetical isn't what users want. They want the most popular completions: "car seat", searched 90,000 times, should beat "carabiner", searched 12 times. Give every word a count of how often it's been searched. Now "the 5 most popular words under car" can't stop early, because the best word could be anywhere in the subtree. You'd have to look at every word below the node. For one-letter prefixes in a million-product catalog that's tens of thousands of words, and one-letter prefixes are the most common question of all: every search starts with one.

Picture each junction with a small noticeboard: "the 5 most popular destinations past this point". Standing at a junction, you read its board; you never drive down the roads. That's the fix: store the top k at every node. A suggestion is then a walk of L steps plus reading k entries: O(L + k), however big the subtree.

Building the boards

Build them bottom-up. A node's board is the best k among its own word (if a word ends there) and the entries on its children's boards. Why is that enough? Take a word that belongs on the node's board, and the child subtree it lives in. If it weren't on that child's board, the child alone would have k better words, so it couldn't be in the top k of the bigger subtree either. So every winner is on some child's board already, and merging the children's boards finds them all.

 counts: car 50, card 30, care 70, cart 20, cat 90      k = 2

 node "car": its own word car 50, plus its children's boards
             d: [card 30]   e: [care 70]   t: [cart 20]
             best 2  →  [care 70, car 50]
 node "ca":  no word of its own; its children's boards
             r: [care 70, car 50]   t: [cat 90]
             best 2  →  [cat 90, care 70]
 node "c":   one child, a: [cat 90, care 70]  →  the same board

Keeping them fresh

When "cart" is searched once more, which boards can change? Only boards of nodes whose subtree contains "cart", and those are exactly its prefixes: the root, c, ca, car and cart. That's L + 1 nodes. At each one: if cart is on the board, re-sort it; if not, add it if the board has fewer than k entries, or else compare cart with the board's last entry and swap it in if it now wins. O(k) per node, O(L · k) per update.

That simple update works because counts only go up: a word can only climb. If counts can go down (popularity that fades, a product that's removed), a word can drop off a board, and the board then needs its (k+1)-th best, which it never stored. Then you rebuild that path's boards from the children's boards (O(L) nodes, each merging a few boards), or keep a few spare entries per board as a buffer.

The memory price: k entries at every node. A trie the size of an English dictionary has about 760,000 nodes; with k = 10 that's 7.6 million entries, about 61 MB as 8-byte pointers. Large typeahead services usually don't update the boards on every search. They count searches from logs, rebuild the prefix → top-k table offline every so often, and serve it read-only from memory, split across machines by prefix. The shortest prefixes are few (26 one-letter and 676 two-letter ones for a to z) and the busiest, so they're cached everywhere, even in the browser. Topic 07.06 designs the whole service.

For "top k by popularity", store each node's best k. Suggest costs O(L + k). A node's board is the best k of its own word plus its children's boards. When a word's count rises, only the boards on its path change: O(L · k). Falling counts are harder, because the board never kept the (k+1)-th.

Every node stores its top-5 board. The count of "cart" goes up by one. Which boards might change?

Right. A board summarizes one subtree, and "cart" sits inside exactly the subtrees of its own prefixes. Five boards, five small checks.

Ask, for each board: "is cart one of the words this board summarizes?". The board at "ca" covers every word that starts with "ca", and cart is one of them, so cart may now belong on it. The board at "do" covers words starting with "do"; cart isn't one of them, so nothing there can change. The nodes whose subtree holds cart are exactly the nodes on its path from the root: "", c, ca, car, cart. Just the cart node is too few (the root's board can change too); every board is far too many.

8The memory bill

Here's the catch, measured. Take the word list that ships with macOS (/usr/share/dict/words), lowercased with duplicates removed: 234,456 words, 2,248,668 letters. Load it into CPython 3.13 three ways, measuring with tracemalloc:

Stored asMemory (measured)
The letters alone, one byte each2.2 MB

A trie: one small object and one dict per node, 758,897 nodesabout 184 MB, about 240 bytes per node

Sharing prefixes did its job: 2.25 million letters became 758,896 edges, a third as many. And still the trie is 13 times bigger than the plain list. (Other Python versions give different totals: 3.9 measures about 260 MB, 16 times its list.) Each node carries one letter of information but pays for an object, a dict (64 bytes when empty, more with keys), and the pointers between them.

Now look at the shape of that trie:

  • 25% of the nodes are leaves: no children at all.
  • 62% have exactly one child: they're links in a chain, like f and u in a trie that holds only "care" and "careful".
  • Only 13% branch into two or more children.

So most nodes are tiny, and how you store a node's children matters more than anything else. There are three usual choices:

How empty is the array? This word list uses 27 symbols (a to z and the hyphen), so each node gets 27 slots: 758,897 × 27 ≈ 20.5 million slots. How many are used? Every node except the root hangs from exactly one slot in its parent, so 758,896 slots hold something: 3.7%. Notice that the answer barely depends on the words: it's always about 1 in 27, one used slot per node. With 8-byte pointers, that's 216 bytes per node just for slots. And for Unicode an array per node is out of the question (there are 1,114,112 code points): use a dict, or store the UTF-8 bytes of each string so the alphabet is at most 256.

A trie's cost is memory: one node per distinct prefix, and per-node overhead dwarfs the one letter it holds. In CPython, a dict-per-node trie of an English word list is more than 10 times the size of the word list. Most nodes are leaves or single-child links, so the child representation (array, hash map, sorted pairs) decides the bill.

Go deeper: adaptive nodes

The Adaptive Radix Tree (ART, Leis, Kemper and Neumann, 2013) picks each node's layout by how many children it has: up to 4 children are kept in a tiny array of (byte, pointer) pairs, up to 16 in a bigger one, up to 48 in a 256-entry index pointing into 48 slots, and beyond that a full 256-slot array. Combined with the chain squeezing of the next section, it keeps memory low while keeping sorted order and prefix search. DuckDB uses ART for its indexes. The same trade appears in every serious trie: a full array where nodes are dense, something compact where they're sparse.

You store a trie of 1 million lowercase words (26 letters) with an array of 26 child slots in every node. The trie has 3 million nodes. About what fraction of all the slots hold a child?

Right. 3 million nodes × 26 = 78 million slots, and each node except the root fills exactly one slot in its parent: 2,999,999 used, about 3.8%. Most of the array memory stores nothing.

Count from the children's side instead of the parents'. Every node except the root has exactly one parent, and it occupies exactly one slot there. So the number of used slots is (number of nodes − 1), whatever the words are. The total is (number of nodes × 26). Divide: just under 1/26. That's why the answer doesn't depend on the words, and why the half-full guess is so far off: the many leaves and single-child nodes each waste 25 or 26 slots.

9Squeeze the chains: radix trees

59% of the word list's nodes are links in chains: one way in, one way out, no word ending there. (That's the 62% with one child, minus the few where a word also ends.) In a small trie of car, card, care, careful and cat, walking "careful" past "care" visits f, then u, then l, and there's never a choice to make. Picture a highway between two exits. Nobody puts up a signpost every hundred meters; signs go only where you can turn off. So collapse every chain into one edge labelled with a whole string: "care" → "ful" in one jump.

 trie (one letter per edge)           radix tree (chains squeezed)

   c - a - r ● - e ● - f - u - l ●       ca ─┬─ r ● ─┬─ e ● ── ful ●
       |      \                              │       └─ d ●
       t ●     d ●                           └─ t ●

 car, card, care, careful, cat: 9 nodes below the root → 6

That's a radix tree, also called a compressed trie or Patricia tree. Its rule: every node is the root, a word end, or a fork (two or more children). Nothing else survives. On the word list from section 8, the trie's 758,897 nodes become 314,479: 41% as many.

There's also a hard limit on the size. With n words, at most n nodes are word ends. Every other node except the root is a fork, and a tree always has fewer forks than leaves (every fork adds at least one extra branch, and each branch ends in a leaf). Every leaf is a word end, so there are fewer than n forks. In total: at most 2n nodes plus the root, however long the words are. A plain trie's node count grows with the total number of letters; a radix tree's grows only with the number of words.

Inserting means splitting

The price is that an edge now holds a string, and a new word may part ways with it halfway along. Insert "team" next to an edge labelled "test": they agree on "te", then differ (s vs a). So split the edge at that point: a new node for "te" (not a word), with two edges below it, "st" for the old word and "am" for the new one. Inserting "tea" next to "am" splits again, and this time the new middle node is a word.

Insert test, team, tea, toast, to and ten into a radix tree, then delete "to". Yellow: the edge being compared. Blue: the node just created or changed. Green ring: a word ends here. Watch the counter: the plain trie of the same words would need more nodes, and the gap grows with longer words.

Delete runs the split backwards. Take down the mark; if the node is now a leaf, remove it; if a node that isn't a word is left with exactly one child, it has become a chain link again, so merge it with that child ("o" + "ast" back into "oast"). Only the deleted node and its parent can need fixing, so delete stays O(L).

Copying strings at every split would be wasteful, so low-level implementations usually store an edge label as a position and length inside a key that's already stored, or as a few bytes kept inline in the node. Lookups compare a label's letters at each edge instead of one letter, so the total is still O(L) letter comparisons, but with fewer jumps between nodes.

A radix tree squeezes every single-child chain into one edge labelled with a string. Every node is a word end or a fork, so n words need at most 2n + 1 nodes. Insert may split an edge where a new word parts ways; delete may merge a node back into its only child. Lookups stay O(L) with far fewer node jumps.

Go deeper: where radix trees run
  • The Linux page cache finds the cached page for a given position in a file with a radix tree, keyed by the page number's bits. Since Linux 4.20 it's wrapped in the XArray API, which is still a radix tree inside.
  • Redis has its own radix tree, rax, which stores Redis Streams: entry IDs are timestamps, and neighboring IDs share long prefixes.
  • HTTP routers such as Go's httprouter (which the Gin framework builds on) match URL paths like /users/:id/orders with a radix tree: /users/ is one shared edge for every user route.
  • Ethereum keeps all account state in a Merkle Patricia trie: a radix tree where every node is also identified by its hash, so the single root hash commits to the entire state.
  • PATRICIA itself (Morrison, 1968) is a binary radix tree that stores at each fork only which bit to test next, skipping the bits in between, and compares the full key once at the end to confirm the match.

A radix tree holds only "test": one edge "test" from the root. You insert "team". What does the tree look like afterwards?

Right. "test" and "team" agree on "te" and differ at the next letter, so that's where the fork goes. The new node "te" isn't a word, but it's a fork, so it's allowed.

Two rules decide it. First, no two edges out of one node may start with the same letter; otherwise a lookup wouldn't know which edge to take. "test" and "team" both start with t, so they can't both leave the root. Second, a word lives below exactly the edges that spell it. "team" doesn't start with "test", so it can't hang below the test node. The only shape that obeys both: share the part they agree on, "te", then fork into "st" and "am".

10Routing tables: the longest prefix wins

A router receives a packet for 10.1.2.3. It holds a table of routes, and the full internet routing table holds about a million IPv4 prefixes. At 100 Gbit/s with the smallest packets, a port receives about 148.8 million packets per second: one decision every 6.7 nanoseconds.

First, what the routes look like. An IPv4 address is 32 bits, written as four numbers from 0 to 255: 10.1.2.3 is 00001010 00000001 00000010 00000011. A route such as 10.0.0.0/8 means "every address whose first 8 bits match 10.0.0.0's". The /8 is the prefix length, and that route covers 2²⁴ = 16,777,216 addresses. 10.1.0.0/16 covers 65,536 of those. 0.0.0.0/0 fixes no bits, so it matches everything: the default route, used when nothing better fits.

So 10.1.2.3 matches all three. Which one wins? Picture a mail sorting room with three instructions on the wall: "anything for France → truck A", "anything for Paris → truck B", "anything else → the international desk". A letter for Paris matches the first two, and the more specific one wins. Routers do the same: longest prefix match. Of all the routes that match, use the one with the longest prefix.

This is the "other direction" from section 2. Autocomplete asks "which stored words start with my text?". Routing asks "which stored prefixes does my text start with, and which is longest?". A trie answers both with the same walk. Use a binary trie: the alphabet is just 0 and 1, and each route sits at the node its prefix bits spell (the default route sits at the root). To look up an address, walk its bits from the left and remember the last route you passed. Stop when you fall off, or after 32 bits. The last route you remembered is the answer. That's at most 32 steps, however many routes there are.

A toy internet with 8-bit addresses and five routes. Each edge is labelled with its bit. Blue: where the walk is. Yellow: a route passed on the way, the best so far. Notice you can't stop at the first route you meet: a longer one may be further down.

Getting the bits in Python is shifting and masking:

def ip_to_int(ip):              # "10.1.2.3" -> 167838211
    a, b, c, d = map(int, ip.split("."))
    return (a << 24) | (b << 16) | (c << 8) | d

def bit(x, i):                  # i-th bit from the left, i = 0..31
    return (x >> (31 - i)) & 1

Routers pick the longest matching prefix. Put every route in a binary trie at the node its prefix bits spell, then walk the address's bits, remembering the last route passed. At most 32 steps for IPv4, independent of the table size. A trie answers "which stored keys are prefixes of my key?", which sorted arrays and hash sets handle badly.

Go deeper: how real routers do it fast enough
  • 32 steps is too many at 6.7 ns per packet if each step is a read from main memory. Multibit tries consume several bits per step: with a stride of 8, an IPv4 lookup is 4 steps, but every node becomes a 256-slot array. Choosing the strides is a memory-versus-steps trade-off.
  • Linux stores IPv4 routes in an LC-trie (level-compressed trie): it squeezes chains like a radix tree, and where the trie is dense it replaces several levels with one wide node.
  • Hardware routers often use TCAM (ternary content-addressable memory): special memory that compares an address against every stored prefix at once, in one cycle, and reports the first entry that matches. Routes are stored longest prefix first, so the first match is the longest. It's very fast, and expensive and power-hungry, so its size is limited.
  • Another software trick: keep one hash table per prefix length (33 for IPv4) and binary search over the lengths, so a lookup is about 5 hash probes. It needs extra "marker" entries to steer the search, which is the subtle part.
  • IPv6 addresses are 128 bits, which makes compression and multibit strides matter even more.

A router has three routes: 0.0.0.0/0 → C, 10.0.0.0/8 → A, 10.1.0.0/16 → B. Where does a packet for 10.2.3.4 go?

Right. The first 8 bits are 10, so 10.0.0.0/8 matches. The first 16 bits are 10.2, not 10.1, so 10.1.0.0/16 doesn't. Of the matching routes (C and A), A has the longer prefix.

"Longest" is chosen among the routes that match, and matching means the address agrees with the route on its first n bits. 10.1.0.0/16 needs the first two numbers to be 10 and 1; the address has 10 and 2, so it's out, however specific it is. 10.0.0.0/8 needs only the first number to be 10: it matches. The default route always matches but has length 0. In the trie walk: you pass the default at the root, pass A after 8 bits, then fall off where 10.1 and 10.2 part ways. The last route passed is A.

11Bits as letters: maximum XOR and word grids

Binary tries show up in interviews too. A classic: given 50,000 numbers, find the largest a ^ b over any pair. (XOR, written ^, gives a 1 in each bit where a and b differ.) Trying every pair is 50,000² / 2 = 1.25 billion XORs.

The key fact is about place value: a 1 in a high bit beats all the lower bits together. In binary, 10000 is 16 and 01111 is only 15. So, for a number x, the best partner is decided from the top bit down, greedily: at each bit, try to take the opposite of x's bit (that makes a 1 in the XOR). Only if no stored number continues that way, take the same bit. A choice made at a higher bit can never be beaten by anything lower, so you never need to look back.

The question at each step is "does any stored number start with these bits and then continue with this bit?", which is exactly a binary trie walk. Insert each number's bits (31 levels for numbers below 2³¹), and for each number walk the trie choosing opposite bits when they exist: O(31 n) instead of n²/2. Here it is on [3, 10, 5, 25, 2, 8] with 5 bits, finding the best partner for 5:

 stored: 3 = 00011   10 = 01010   5 = 00101
        25 = 11001    2 = 00010   8 = 01000

 x = 5 = 00101. At each bit, try the opposite of x's bit.

 bit 4: x has 0, try 1: 25 starts with 1     XOR so far 1
 bit 3: x has 0, try 1: 25 has 1 next        XOR so far 11
 bit 2: x has 1, try 0: 25 has 0 next        XOR so far 111
 bit 1: x has 0, try 1: none starts 1101     XOR so far 1110
 bit 0: x has 1, try 0: none starts 11000    XOR so far 11100

 partner 25 = 11001: 5 ^ 25 = 11100 = 28, the answer for this list

Three more trie patterns worth recognizing:

  • Find every dictionary word in a letter grid (Boggle-style). Searching for each word separately repeats the same paths again and again. Instead, put all the words in a trie and do one depth-first search from each cell (the backtracking from Recursion and backtracking), walking the trie as the path grows. The moment the path's letters aren't a prefix of any word, stop: that's pruning. One walk checks every word at once.
  • Wildcard search, like "c.t" where the dot matches any letter: walk normally on letters, and at a dot try every child. The cost depends on how many branches the dots open.
  • Typo tolerance ("did you mean"), the follow-up to autocomplete: walk the trie depth-first and carry one row of the edit distance table from Dynamic programming per node, so words that share a prefix share those rows. When every number in a node's row is over the allowed number of typos, nothing below it can come back under, so skip that branch.

Treat bits as letters and a binary trie answers questions about numbers: walk the high bit first, prefer the opposite bit, and you get the maximum XOR partner in 31 steps. A trie also prunes searches over many words at once: stop as soon as the path isn't a prefix of anything.

When looking for x's best XOR partner, the walk prefers the opposite bit at bit 30 even if that forces a 0 in every lower bit of the XOR. Why is that safe?

Right. Two candidate partners whose XORs with x first differ at bit 30: the one with the 1 there wins, however the lower bits turn out. So the greedy choice at each bit is final.

It's place value, the same reason 100 is more than 099 in decimal. Add up every lower bit: 2²⁹ + 2²⁸ + … + 1 = 2³⁰ − 1, which is one less than 2³⁰. So any XOR with a 1 at bit 30 beats any XOR with a 0 there. Storing high bits first is the consequence of this, not the reason: we build the trie top-down because the top bit decides first. And it holds for any numbers, not just random ones.

So a trie is the wrong tool when:

  • You only ever ask exact questions ("is this session id valid?"). A hash set is smaller and faster.
  • The word list rarely changes and memory is tight. A sorted array with binary search answers prefix queries with almost no overhead.
  • The keys share almost no prefixes (random ids, hashes). A trie then spends a node on nearly every letter, and a radix tree is little more than one long edge per key.
Go deeper: sharing endings, and other relatives
  • Sharing suffixes too. A trie shares starts but not endings: "walking", "talking" and "parking" all store -ing separately. A DAWG (directed acyclic word graph) merges identical subtrees, so shared endings are stored once; it's no longer a tree, because a node can have several parents. An FST (finite state transducer) does the same and also attaches outputs, such as a number, to the paths. Lucene, the search library under Elasticsearch, keeps its term dictionary index in an FST, and Elasticsearch's completion suggester is built on one.
  • Ternary search tree. Each node holds one letter and three children: less, equal, greater. At every level it's a little BST over the letters that occur there, so no node wastes slots on missing letters, and you still get prefix walks, at the price of a few extra comparisons per letter.
  • Suffix tree. Insert every suffix of one long text into a radix tree, and "does this pattern occur anywhere in the text?" becomes a walk of the pattern's length. Built cleverly it takes O(text length) time and space; string algorithms (topic 02.12) cover the simpler tools.

13What to say in the interview

For "design the suggestions under a search box" (or "implement a trie and tell me what it costs"), a strong answer:

"The question on every keystroke is 'which stored strings start with what's typed?'. A hash set can't help, because it scatters similar strings. A sorted array works for a static list, O(L log n) to find the block, but inserts cost O(n). I'd use a trie: each node is a prefix, and everything that starts with that prefix is below it. Insert and lookup are O(L), independent of n, and a node needs an end-of-word mark because a path existing doesn't mean a word ends there. For suggestions ranked by popularity I'd store the top k at each node, so a keystroke costs O(L + k), and an increase in a word's count only touches the L + 1 nodes on its path. The cost is memory: a node per distinct prefix, which in a language like Python is more than 10 times the size of a plain list of the same strings. So I'd compress chains into a radix tree, at most 2n nodes, and I'd build the table offline from search logs, serve it read-only, split by prefix, and cache the one- and two-letter prefixes, which get the most traffic."

Habits that make you sound senior:

  • Give costs in L, the key length, and point out that n doesn't appear.
  • Say what a hash set does better (exact lookups, memory) before choosing the trie.
  • Bring up the end-of-word mark and pruning on delete without being asked.
  • Price the memory, and name the fixes: child representation and radix compression.
  • Know the other direction: longest prefix match for routing.

✓What to remember

  1. A trie stores strings as paths, one letter per edge; each node is a prefix, and everything below it starts with that prefix.
  2. A path existing isn't a word: a word needs an end-of-word mark (or a value) on its last node.
  3. Insert and lookup are O(L), independent of n. A hash set is O(L) too and better for exact lookups; the trie wins on prefix questions.
  4. Prefix listing: walk to the node, then depth-first with children in letter order gives sorted output. Stop after k. A count per node makes counting O(L). Delete must prune nodes that lead nowhere.
  5. Ranked suggestions: store the top k at each node, O(L + k) per query; a count increase updates the L + 1 boards on the word's path.
  6. Memory is the cost: a node per distinct prefix, mostly leaves and single-child links. Array children are fast but nearly empty: about one used slot per node.
  7. A radix tree squeezes chains into string-labelled edges: every node is a word end or a fork, at most 2n + 1 nodes; insert splits, delete merges.
  8. Routers use longest prefix match: walk the address bits through a binary trie, remembering the last route passed. The same bit trie finds the maximum XOR partner greedily, high bit first.

Warm-up · pen and paper

1. Build it by hand

Insert "to", "tea", "ted", "ten", "i", "in" and "inn" into an empty trie. Draw it, mark the word ends, and count the nodes (with the root). Then draw the radix tree of the same words and count again. Which plain-trie nodes disappeared, and why those?

Answer

Trie: the root; t, to, te, tea, ted, ten; i, in, inn. That's 10 nodes. Marks on to, tea, ted, ten, i, in, inn. Radix tree: the root, then an edge "t" to a fork with edges "o" (word) and "e"; the "e" node is a fork with edges "a", "d", "n" (all words); and an edge "i" (word) → "n" (word) → "n" (word). Every node is either a word end or a fork, so nothing can be squeezed: still 10 nodes. With these short words there are no chains. Add "inner" and the plain trie gains e and r (two nodes), while the radix tree gains one edge "er".

Warm-up · pen and paper

2. Route four packets

Routes: 0.0.0.0/0 → D, 172.16.0.0/12 → A, 172.16.5.0/24 → B, 172.31.255.0/24 → C. Where do these go: (a) 172.16.5.9, (b) 172.20.1.1, (c) 172.32.0.1, (d) 172.31.255.255? For (b), say at which bit the trie walk falls off or stops.

Answer

/12 means the first 12 bits: 172 is 10101100, and the second number's top 4 bits must be 0001, which is 16 to 31. (a) B: matches /12 and /24, and /24 is longer. (b) A: 20 is in 16 to 31, but 172.20.1 isn't 172.16.5 or 172.31.255. The walk passes D at the root and A after 12 bits. Next come the low 4 bits of the second number: 20 is 0001 0100, 16 is 0001 0000, 31 is 0001 1111. The walk takes the first 0 (toward 172.16.5), then needs a 1 where only the 0 toward 16 exists, and falls off at bit 13 (counting from 0). The last route passed is A. (c) D: 32 is 00100000, its top 4 bits are 0010, not 0001, so the /12 doesn't match. (d) C: matches /12 and the /24 for 172.31.255.

3. Pick the tool

Trie, radix tree, hash set or sorted array? (a) Check whether 50 million session tokens are valid. (b) Suggestions for a box over 2 million place names, ranked by popularity, updated nightly. (c) Match URL paths like /api/users/:id to handlers. (d) Group words that are anagrams of each other. (e) A spell checker's "did you mean" list of words that start with the same 4 letters, on a phone with little memory and a word list that never changes.

Answer

(a) Hash set: exact questions only, random tokens share no prefixes. (b) A trie (or radix tree) with a top-k board per node, built offline each night and served read-only. (d) Hash map from the sorted letters of a word to a list of words: no prefix question here at all. (e) Sorted array with binary search: a static list, tight memory, and a prefix range is one block.
