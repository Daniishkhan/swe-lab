Many threads, one structure

P2 Concurrent structures: lock-free queue, ring buffer, concurrent hash mapabout 65 minutes10 quick checks · 9 exercises

Every structure in this chapter's earlier parts assumed one worker at a time. Real servers run dozens of threads that touch the same queue, the same map, the same counter. Done naively, updates quietly vanish. Done with one big lock, the dozens of threads take turns and you've paid for cores you can't use. This chapter starts from a counter that can't count and rebuilds, one fix at a time, the three shared structures interviewers ask about: the lock-free ring buffer, the lock-free queue and the concurrent hash map.

1The problem: a counter that can't count

You run the click counter for an ad network. Advertisers pay per click, so the count is money. Eight worker threads handle clicks, and every click runs one line on one shared number: clicks += 1. In a load test, each of the 8 threads counts 1,000,000 clicks. The total should be 8,000,000.

Written in Java or C, the program prints a different total almost every run, often millions short. Nothing crashed. No error was logged. Clicks just vanished.

So you put a lock around the line. Now the total is right every time. But the 8 threads together are now often slower than one thread counting all 8 million clicks alone. You bought 8 cores and they spend their time waiting for each other.

Both halves of that story are this chapter. First, why do updates vanish? Then, how do we stay correct without making every thread wait in one line? The answer is not one trick. It's a short list of ideas (a lock, one writer per variable, compare-and-swap, splitting one lock into many) and the three structures built from them.

Each of the 8 threads runs clicks += 1 exactly 1,000,000 times, and the program waits for all of them before printing. Why can the total come out short?

Right. clicks += 1 is really three steps: read, add, write. If two threads both read 41 before either writes, both write 42. Two clicks happened; the number went up by one. Section 2 takes this apart.

CPUs don't skip instructions, and the program waits for every thread (it "joins" them) before printing. Picture an office whiteboard with a tally on it. Two clerks each make a sale at the same moment. Each walks to the board, reads 41, walks back to their desk to work out 41 + 1, then returns and writes 42. Two sales, and the board says 42, not 43. Each clerk did their job right. The problem is the gap between reading and writing, where someone else can read the same old number.

2Read, change, write: where updates vanish

A thread is one sequence of instructions running inside a program. All threads of a program share the same memory, so they can all see clicks. The operating system runs threads on different cores at the same time, and it can also pause any thread between any two machine instructions and run another one.

To the CPU, clicks += 1 isn't one step. The number lives in memory, and arithmetic happens in a register, a tiny scratch slot inside one core. So the line becomes three steps:

 1. r = read clicks    (into my own register)
 2. r = r + 1          (change my private copy)
 3. write r to clicks  (copy it back to memory)

With two threads, A and B, each doing those three steps, the six steps can mix in many orders. Each possible mix is an interleaving. The result is right only if one thread writes before the other reads. Try it: you are the scheduler.

Both threads add 1 to x, which starts at 41, so the right answer is 43. Press "Step A" and "Step B" in any order. Try A, B, A, B, A, B: one update is lost. Then switch the mode to "With a lock" and try to break it again, and finally "Atomic add".

Count them. Six steps, three from A and three from B, can be ordered in 20 ways (choose which 3 of the 6 positions are A's: 6 × 5 × 4 / (3 × 2 × 1) = 20). Only 2 of the 20 give 43: all of A before all of B, or all of B before all of A. The other 18 lose an update. With 8 threads doing a million each, there are millions of chances for a bad mix, so some always happen.

The names for this: a race condition is a bug where the result depends on how the threads happened to interleave. An operation is atomic if no other thread can ever see it half done: it happened entirely or not at all. clicks += 1 is not atomic. Each of its three steps is atomic on its own, but nothing stops another thread from slipping between them.

A shared update is "read, change, write". If another thread can read between your read and your write, both of you start from the same old value and one change is lost. Every fix in this chapter either makes the three steps one atomic step, or makes sure only one thread ever writes the variable.

Go deeper: what about Python and the GIL?

CPython (the standard Python) has a global interpreter lock, the GIL: only one thread runs Python bytecode at a time. That doesn't make clicks += 1 atomic. The line compiles to several bytecodes (load, add, store), and the interpreter is allowed to switch threads between them. Recent CPython versions switch threads at fewer points, so this exact demo often prints the right total: in our runs with 8 threads on CPython 3.13 it printed 8,000,000 every time. That's luck about where switches happen, not a promise. When we put a function call between the read and the write (c.v = inc(c.v)), every run on CPython 3.13, 3.14 and 3.15 lost most of the 8 million updates, ending between 2 and 5 million. A thread paused while holding its stale value sleeps for a few milliseconds while the others add thousands; when it wakes, its one write wipes all of theirs out.

Since Python 3.13 there's also an optional free-threaded build with no GIL (PEP 703), officially supported since 3.14: threads really run in parallel on different cores. Built-in operations like a single dict or list update still lock internally and stay safe, but d[k] += 1 is still read, change, write. The rule is the same in every language: protect read-change-write on shared data.

One more Python fact interviewers like: with the GIL, threads don't make pure-Python number crunching faster, since only one runs at a time. Threads still help when they spend their time waiting on the network or disk (the GIL is released while waiting). For CPU work, Python uses processes (multiprocessing) or the free-threaded build.

Two threads each run x += 1 once, as read, add, write. x starts at 5. Which final values are possible?

Right. 7 if one thread writes before the other reads (2 of the 20 interleavings); 6 if both read 5 first. 5 is impossible: the last write to x is always someone's "value I read, plus 1", and every value read is at least 5.

List what each thread can write. A thread reads some value r and writes r + 1. The smallest r anyone can read is 5, so every write is at least 6, and the final value is whatever was written last: never 5. Can it be 6? Yes: A reads 5, B reads 5, A writes 6, B writes 6. Can it be 7? Yes: A does all three steps, then B reads 6 and writes 7. So the answer is "6 or 7", and which one you get depends on the interleaving. That dependence is exactly what "race condition" means.

3Fix 1: one lock

The cleanest fix stops the steps from mixing at all. Picture a gas station bathroom with one key on a hook. To go in, you take the key. Anyone else who wants in waits until the key is back on the hook. Only one person is ever inside.

That key is a lock, also called a mutex (short for "mutual exclusion"). A thread acquires it before touching the shared data and releases it after. The code between is the critical section. Only one thread can be inside, so the three steps of x += 1 now run as one unit: no other thread holding the same lock can slip in between.

import threading

clicks = 0
lock = threading.Lock()

def count_clicks(n):
    global clicks
    for _ in range(n):
        with lock:          # take the key; other threads wait here
            clicks += 1     # read, change, write: nobody else is inside
        # leaving the with-block hangs the key back up, even after an exception

A lock protects more than one variable. A queue has an array and a size that must change together; hold the lock while you change both, and no other thread ever sees the array updated but the size not. The rule that keeps it correct: every access to the shared data, reads included, holds the lock.

What does a thread do while it waits? Either it spins (keeps checking in a loop: fast if the wait is short, but it burns a core) or it sleeps (the operating system parks it and wakes it when the lock is free, which costs a few microseconds). Many locks spin briefly, then sleep; on Linux the sleeping part is built on a kernel feature called a futex.

What a lock costs:

  • Waiting. Only one thread at a time does the work inside. Section 4 puts numbers on it.
  • Stalls. If the operating system pauses the thread holding the lock (to run something else for a few milliseconds), every thread that needs the lock stops too.
  • Deadlock. Take two locks in the wrong order and two threads can wait for each other forever. Section 9 shows the fix.

A lock makes a group of steps atomic by letting only one thread into the critical section at a time. It's correct and simple, which is why it's the right first answer. The cost: every thread that needs it waits in one line.

Thread A does with lock: clicks += 1. Thread B, in another file, does clicks += 1 without taking the lock. Are updates safe?

Right. A lock isn't a force field around a variable. It's an agreement: everyone who touches clicks takes the key first. B never asks for the key, so it can read between A's read and write.

Back to the bathroom. The key on the hook only works because everyone agrees to take it before going in. Someone who climbs in through the window never checks the hook, and the key can't stop them. A lock works the same way: the computer doesn't link the lock to clicks at all. B reads clicks, A runs its whole critical section, B writes its stale value + 1, and A's update is gone. One thread skipping the lock is enough.

4Why one lock doesn't scale

Say each request in a server spends 100 ns holding the one lock around a shared map. Only one thread holds it at a time, so at most 1 / 100 ns = 10 million requests per second get through, whether you have 4 cores or 64. The lock is a one-lane bridge: adding cars doesn't add lanes.

10 µs (a slow critical section)100,000

The general version is Amdahl's law. If a fraction s of the work must run one thread at a time, then n cores give a speedup of at most 1 / (s + (1 − s) / n). With s = 0.25 (a quarter of each request holds the lock), 16 cores give 1 / (0.25 + 0.75/16) ≈ 3.4×, and infinitely many cores give 4×. The serial part sets the ceiling.

The hidden cost: a cache line moving between cores

The table assumed handing the lock over is free. It isn't, and the reason is how cores share memory. Picture each core with its own notebook (its cache), holding copies of pages from a shared library (main memory). Reading a page you already have takes about a nanosecond. The pages are called cache lines, 64 bytes each on most x86 and Arm server chips (Apple's M-series uses 128).

Copies must agree. So when one core writes to a line, every other core's copy of that line is torn out of its notebook. The next core that touches the line must fetch the fresh copy from the writer's cache, which takes tens of nanoseconds, more between chips in a two-socket server. This agreement protocol is called cache coherence.

A lock is a few bytes of memory, so it lives in one cache line. Every acquire writes to it. With 8 threads taking turns, that line moves core to core on every hand-off, and each move costs far more than the + 1 it protects. That's how 8 threads end up slower than 1: the single thread keeps the line in its own cache the whole time.

The same thing happens with no sharing at all. Two threads each increment their own counter, but the two counters sit next to each other in memory, on the same 64-byte line:

          one 64-byte cache line
 ┌───────────┬───────────┬────────────────┐
 │ counter_a │ counter_b │ (rest of line) │
 └───────────┴───────────┴────────────────┘
 core 1 writes a: core 2's copy of the
   whole line is torn out.
 core 2 writes b: core 1's copy is torn out.
 Every write is a cache miss.

 fix: padding, so a and b sit on different lines

That's false sharing: the threads share a cache line but no data. Java has an @Contended annotation that pads a field onto its own line (the JDK uses it internally; your own code needs a JVM flag to enable it), C++17 has std::hardware_destructive_interference_size for the right padding, and high-performance queues pad their counters by hand. In Python you don't control memory layout, but interviewers ask about it anyway.

A single lock caps throughput at 1 / (time inside the lock), and a write to shared memory makes its cache line travel between cores. So the way to scale is to share less: give each variable one writer, split one lock into many, or don't share at all. The rest of the chapter does each of these.

In C, two threads each increment their own counter: counts[0] and counts[1], in an array of 8-byte integers. Nothing is shared, yet it's far slower than one thread doing both. Why?

Right: false sharing. Bytes 0–7 and 8–15 share a 64-byte line, and cores move whole lines, not single variables. Pad each counter onto its own line and the slowdown goes away.

Nothing in C adds locks for you, and addition costs the same on any core. Think of what the cores pass around: not variables, but whole 64-byte lines. counts[0] is bytes 0 to 7 and counts[1] is bytes 8 to 15 of the same line. When core 1 writes its counter, core 2's copy of the whole line is thrown away, even though core 2 only cares about bytes 8 to 15. Then core 2 writes and throws away core 1's copy. The line ping-pongs on every write. Put 56 bytes of padding between the two counters and each one gets its own line.

5One producer, one consumer: a ring with no lock

A music app has two threads. A decoder thread unpacks the MP3 and produces sound samples. The audio thread must hand 128 samples to the sound card every 128 / 48,000 s ≈ 2.7 ms, every time, or you hear a click. If the audio thread ever waits for a lock, and the decoder holding it has just been paused by the operating system, the deadline is missed. Audio programmers have a rule: never take a lock in the audio thread.

So we need a queue between exactly one producer (the thread that adds items) and exactly one consumer (the thread that takes them out) with no lock at all. This is the SPSC case: single producer, single consumer.

Start from the ring buffer of Who goes next?: a fixed array of slots used in a circle. That version kept head and size. Both sides change size (push adds 1, pop subtracts 1), so size is a shared read-change-write: section 2's lost update again. The fix is to stop sharing any variable that both sides write.

Each counter has one writer

Picture a revolving sushi belt with 4 places. One cook puts plates on; one diner takes them off. The cook keeps a card, "plates placed so far". The diner keeps a card, "plates taken so far". Each writes only on their own card, and only glances at the other's. Plates on the belt = placed − taken.

In the ring those cards are two counters that only ever grow:

  • tail: how many items were ever pushed. Only the producer writes it.
  • head: how many items were ever popped. Only the consumer writes it.

Item number s lives in slot s % capacity. Items in the ring = tail − head. Empty when they're equal; full when tail − head == capacity. No variable has two writers, so there's no read-change-write race on any of them. And because the counters never wrap around, "full" and "empty" never look alike.

 producer: try_push(item)
  1. t = tail                  (my own counter)
  2. if t − head == capacity:  full, give up
  3. slots[t % capacity] = item
  4. tail = t + 1              ← publish, last

 consumer: try_pop()
  1. h = head                  (my own counter)
  2. if tail == h:             empty, give up
  3. item = slots[h % capacity]
  4. clear slots[h % capacity]
  5. head = h + 1              ← free the slot, last
A ring of 4 slots. Green slots hold items the consumer may take: slot numbers from head up to tail. Watch each push write its slot first and move tail second, and each pop read and clear first and move head second. Then press "Show the bug" to see what happens when the producer moves tail first.

Why reading a stale counter is safe

This is the part people find hard to believe. The producer reads head while the consumer may be changing it. So the producer can act on an old value. Is that a race?

No, because head only grows. An old head is smaller than or equal to the real one, so the producer computes tail − old head ≥ the real number of items. It thinks the ring is fuller than it is. The worst case: it says "full" a moment too early, and tries again later. It can never decide a slot is free when the consumer still needs it. The same holds the other way: a consumer with an old tail sees fewer items than there are, and says "empty" a moment too early. Stale means cautious, never wrong.

That gives a speed trick. Reading the other side's counter means reading a cache line the other core keeps writing: a cache miss (section 4). So each side keeps a cached copy of the other side's counter and re-reads the real one only when the copy says "full" (producer) or "empty" (consumer). Fill an empty ring of 1,024 slots and the producer reads head at most once. High-performance rings also put head and tail on separate cache lines, so the two cores don't false-share.

Two details that make real rings fast. Capacity is a power of two, so s % capacity becomes s & (capacity − 1): one AND instead of a division. And the counters are 64-bit unsigned integers. At a billion items per second, a 64-bit counter takes about 584 years to wrap around; and even if it did, unsigned subtraction tail − head still gives the right count across the wrap.

Explain it another way: why the classic ring wastes a slot

Many textbook rings keep wrapped indexes, both between 0 and capacity − 1. Then head == tail means "empty"… but a completely full ring also has head == tail, because the tail has gone all the way around. To tell them apart, either keep a shared size (two writers: not allowed here) or declare the ring full one slot early, at capacity − 1 items. Counters that never wrap carry the extra information for free: full is tail − head == capacity, a different number from empty's 0.

An SPSC ring needs no lock because every shared variable has exactly one writer: the producer owns tail, the consumer owns head. Counters only grow, so a stale read makes the reader cautious, never wrong.

The producer reads head = 10. A moment later the consumer advances it to 12, but the producer keeps working with 10. What can go wrong?

Right. With head 10 it believes 2 more items are in the ring than really are. It may give up on a push that would have fit, then succeed after re-reading. It never writes a slot the consumer still needs.

Plug in numbers. Capacity 4, tail = 14. Real items: 14 − 12 = 2, so 2 free slots. The producer's view: 14 − 10 = 4, "full". It refuses to push. It can't overwrite anything, because it only writes slot tail % 4 when it believes there's room, and its belief is always more pessimistic than the truth. head only grows, so an old head can only make the ring look fuller. The cost of staleness is a wasted retry, never a lost item.

6Publish last: the order of writes

Look again at the producer's last two steps: write the item into its slot, then move tail. The order is the whole point. Moving tail is the announcement "slot 5 is ready". If the announcement came first, the consumer could see tail = 6, read slot 5 before the item arrived, and return garbage: an old item, or in C half-written bytes. The figure's "Show the bug" button plays exactly that.

Picture a restaurant pass. The cook puts the plate on the counter, then rings the bell. Ring the bell first and the waiter grabs an empty counter. The consumer has the same rule on its side: read and clear the slot, then move head. Move head first and the producer may start writing a new item into a slot the consumer is still reading.

The machine may reorder your writes

Here is the uncomfortable part. You can write the two lines in the right order and still get the bug, because neither the compiler nor the CPU promises to keep that order for other cores to see:

  • The compiler may swap two writes to different variables, since a single thread can't tell the difference.
  • The CPU parks writes in a small per-core store buffer before they reach the cache. On Arm chips (phones, Apple's M-series, AWS Graviton), writes to different addresses can become visible to other cores in a different order than they were made. x86 keeps one core's writes in order relative to each other (its rules are called TSO, total store order), which is why code like this can pass every test on an x86 laptop and then lose items on an Arm server.

The fix is to tell both the compiler and the CPU which order matters, with a pair of special operations:

  • A release store to tail: every read and write before it in the program is complete, and visible to other cores, no later than the store itself.
  • An acquire load of tail in the consumer: no read or write after it can happen before it.

Together: if the consumer sees tail = 6, it also sees everything the producer wrote before setting tail to 6, including the item. The same pair, on head, covers the consumer's side: its release store of head makes sure it has finished reading the slot before the producer can see the slot is free. That's why a release orders reads too, not just writes. This costs almost nothing: on x86 the release store is an ordinary store that the compiler must not reorder; on Arm it's a special store instruction.

The name for what goes wrong without them: a data race is two threads touching the same memory at the same time, at least one of them writing, with nothing (a lock, or atomic operations) ordering the two. In C and C++ a data race is undefined behavior: the compiler may assume it never happens, and anything can result.

Write the data, then publish it by moving the counter. Make the publishing store a release and the other side's load an acquire, or the compiler and CPU may let the other thread see the counter before the data.

A developer's SPSC ring passes every test on an x86 laptop but sometimes hands out garbage on an Arm server. The producer writes the slot, then tail, both as plain variables. Most likely cause?

Right. x86 keeps one core's stores in order; Arm doesn't, and the compiler is free to reorder plain writes anyway. A release store on tail and an acquire load in the consumer fix it, with no lock.

Cache size doesn't change what's in the ring. A lock only in the consumer doesn't help either: the producer never takes it, so it can't order the producer's writes (section 3: a lock only stops threads that also take it), and locking both sides throws away the reason for the design. The order in the source code is a wish, not a promise. On Arm, the write of tail may reach the consumer's core before the write of the slot (both sat in the producer's store buffer, and Arm lets them drain in either order, for example when tail's cache line is already at hand and the slot's isn't). The consumer sees "6 items", reads slot 5, and finds the old contents. It's the bell ringing before the plate is down. Marking the tail store "release" says "everything before me must be visible first"; marking the consumer's load "acquire" says "don't read ahead of me".

7Many writers: compare-and-swap

Now let two producers share the ring. Both read tail = 5. Both write their item into slot 5. Both set tail = 6. One item overwrote the other and is gone. It's section 2's lost update again: tail now has two writers. The one-writer trick can't help. We need the read-change-write itself to be atomic, without a lock. That has to come from the hardware.

Picture the whiteboard again, with a new rule: "change 41 to 42, but only if it still says 41; if it doesn't, change nothing and tell me what it says now". Checking and writing happen as one indivisible step, so nobody can sneak in between. That's compare-and-swap, or CAS: cas(location, expected, new) writes new only if the location still holds expected, and reports whether it did.

Every CPU has it. On x86 it's the LOCK CMPXCHG instruction: the core takes the cache line in exclusive mode, compares, writes and lets go, with no other core able to touch the line in between. Arm has a load-exclusive / store-exclusive pair that achieves the same, and a single CAS instruction since Armv8.1. On top of CAS, every lock-free algorithm repeats one shape:

# Pseudocode: Python has no CAS instruction. Read cas(ref, expected, new)
# as the hardware's compare-and-swap: one indivisible step.
def increment(counter):
    while True:
        old = counter.load()           # 1. read the shared value
        new = old + 1                  # 2. compute privately
        if cas(counter, old, new):     # 3. write only if nobody changed it
            return new
        # someone changed it between 1 and 3: retry with the fresh value

A failed CAS is never a disaster. It changed nothing, and it failed only because another thread's CAS succeeded in between. So whenever someone retries, someone else made progress. That's the definition of lock-free: whatever the scheduling, some thread always completes its operation within a bounded number of steps of the whole system, even if other threads are paused forever in the middle of theirs. A lock can't promise that: pause the lock holder and nobody finishes.

For a plain counter there's an even simpler instruction, fetch-and-add (x86 LOCK XADD, Java's AtomicLong.getAndIncrement, C++ fetch_add): add and return the old value in one atomic step, no loop. But "atomic" doesn't mean "free". Sixty-four cores incrementing one atomic counter still pass one cache line around and take turns. Java's LongAdder fixes that by keeping several counter cells (more appear when threads collide), spreading the threads over them, and summing the cells only when someone asks for the total. Spread the writes out; pay on the rare read.

Compare-and-swap writes only if the value is still what you read, as one hardware step. Wrap it in a read-compute-CAS-retry loop and lost updates can't happen. A failed CAS means someone else succeeded, so the system always moves forward: lock-free.

Thread A reads counter = 10 and computes 11. Before A's CAS runs, thread B's CAS changes counter to 11. What does A's cas(counter, 10, 11) do?

Right. The counter holds 11, not the expected 10, so the CAS fails. A's loop reads the fresh 11, computes 12, and its next CAS succeeds unless someone beats it again. Both increments count: final value 12.

If A's write of 11 went through, B's increment would be lost: two increments, and the counter went from 10 to 11. That's the bug CAS exists to prevent. CAS compares first: "is it still 10?" It's 11, so nothing is written. And CAS never waits: it answers yes or no at once, which is why no thread can block another. A then loops: reads 11, computes 12, CAS(11 → 12) succeeds. Final value 12: both increments counted.

8A lock-free queue: Michael and Scott

Java's ConcurrentLinkedQueue lets any number of threads add and remove at once, with no lock. It's based on an algorithm Maged Michael and Michael Scott published in 1996. It's the standard interview example of a lock-free structure, and it's built from just the CAS loop above.

Start from the linked-list queue of Who goes next?, with a dummy node at the front: the list always starts with one node that holds no item, so even an empty queue has a node, and neither adding nor removing needs a special case for "the queue is empty". Two shared pointers: head points at the dummy, tail at the last node. Items are in the nodes after the dummy.

Picture a conga line. To join, you put your hand on the shoulder of the last dancer, but only if nobody's hand is already there. That's one CAS on the last node's next pointer, from empty to your node. A sign saying "END" points at the last dancer; moving it is a separate step that can fall one dancer behind. The rule that makes it lock-free: anyone who sees the sign is behind moves it forward before doing anything else, instead of waiting for whoever is responsible. (Where the picture breaks: a dancer can see the end of the line. A thread can only read one pointer at a time, so "the sign is behind" shows up as "the node the tail points at already has a next".)

Enqueue, in words:

  1. Make the new node. Read tail (call it last), then read last.next.
  2. If last.next is empty: CAS it from empty to the new node. If that succeeds, the item is in the queue: this one CAS is the moment the enqueue takes effect. Then try once to CAS tail from last to the new node. If that fails, someone already moved it for you: fine.
  3. If last.next is not empty, the tail is lagging. Help: CAS tail from last to last.next. Then start again from step 1.

Dequeue is one CAS on head: move it from the dummy to the first real node, which becomes the new dummy, and return its item. If the dummy has no next, the queue is empty. And if tail still points at the dummy even though there is a next node, the tail is lagging, and dequeue helps move it first (the exercise asks you why that matters).

Threads A and B enqueue at the same moment into a queue holding 1. Each cell's next is the cell to its right. Watch B's first CAS fail because A got there first, then watch B find the tail lagging and fix it instead of waiting for A. Yellow: a pointer being read. Blue: a successful CAS. Red: a failed one.

Every operation has one CAS where it "happens": the link for an enqueue, the head move for a dequeue. (A dequeue that finds the queue empty happens at its read of the dummy's empty next.) Before that instant the operation hasn't happened; after it, it has, for every thread. An object whose operations each take effect at one instant between their start and their end is called linearizable, and it's the standard meaning of "this concurrent queue behaves like a queue".

Lock-free is a promise about pauses and progress, not about speed. Under heavy contention, CAS loops retry and the same cache lines bounce between cores; a good lock, which puts waiters to sleep, can beat them. You reach for lock-free when a thread must never wait for another one that might be paused: audio and trading hot paths, interrupt handlers, code that runs while the scheduler itself is busy.

Go deeper: the ABA problem and freeing nodes

CAS asks "is it still A?". It can't tell "still A" from "changed to B, then back to A". Usually that doesn't matter. With pointers and reused memory, it does. A lock-free stack shows it: the top is node A, and A.next is B. Thread 1 reads top = A and next = B, and is about to CAS(top, A → B). It pauses. Thread 2 pops A, pops B, frees B, and pushes A back (the same memory, reused). The top is A again, but now A.next is C. Thread 1 wakes, its CAS sees A and succeeds, and the top is now B: a node that was freed. The structure is corrupt.

Fixes, from simplest to most used:

  • A version tag next to the pointer, bumped on every change, and a CAS over both at once (x86-64 has a 16-byte CAS, CMPXCHG16B). The original Michael-Scott paper used counted pointers like this.
  • Hazard pointers: each thread announces "I'm looking at node X", and no one frees X while it's announced.
  • Epoch-based reclamation: retired nodes are freed only after every thread has passed a checkpoint. Rust's crossbeam library works this way.
  • A garbage collector. In Java (and in Python), a node can't be freed and reused while any thread still holds a reference to it, so this form of ABA can't happen, and Java's ConcurrentLinkedQueue needs none of the other fixes.
Go deeper: bounded many-producer queues

The Michael-Scott queue is unbounded and allocates a node per item. A bounded alternative used in practice (Dmitry Vyukov's bounded MPMC queue) is a ring where each slot carries its own sequence number. A producer claims a position by CAS on a shared enqueue counter, writes the item, then sets the slot's sequence number to tell consumers "ready". No allocation, fixed memory, and each slot's sequence plays the role that tail played in the SPSC ring. (Strictly, it isn't lock-free: a producer paused between claiming a slot and marking it ready holds up the consumer that reaches that slot. In practice it's very fast.) The LMAX Disruptor, built for a trading exchange, is a ring in the same family: pre-allocated entries, sequence counters, and counters padded onto their own cache lines.

In the Michael-Scott queue, thread A's link CAS succeeds, and then the operating system pauses A for 10 ms before it moves tail. What do other enqueuers do meanwhile?

Right: helping. Moving tail is a CAS anyone may do, and A's own CAS will fail harmlessly when it wakes. No thread ever waits for another, which is what makes the queue lock-free.

Waiting would make the queue blocking: one paused thread would stall everyone, the very thing we're avoiding. Replacing A's node can't happen either: linking is a CAS from empty, and the lagging node's next isn't empty anymore (it's A's node), so that CAS fails. What the others do is read last.next, find A's node there, and conclude "the tail is one behind". Any thread can fix that with CAS(tail, last → last.next), then retry its own enqueue from the real end. The conga line keeps moving even with the sign-holder asleep.

9A concurrent hash map: many locks, not one

A login service keeps sessions in a hash map. 32 threads look up and update sessions, 200,000 times a second in total. Put one lock around a dict and section 4's ceiling applies: every thread waits in one line, though two threads touching two different users have nothing to do with each other.

Picture a supermarket with one checkout lane versus 16. Better still, lanes assigned by the first letter of your last name: two shoppers only wait for each other if they share a lane. That's lock striping. Keep S locks, the stripes. Key k belongs to stripe hash(k) % S, and that stripe's lock guards every key in it. An operation on one key takes only its stripe's lock. Threads working on different stripes never wait for each other. Each stripe can even keep its own small hash table and grow it on its own.

The numbers, for 16 threads all inside the map at once with keys spread evenly: one lock, 100% (someone is always in my way); 16 stripes, 62%; 64 stripes, 21%; 256 stripes, 5.7%. Real threads spend most of their time outside the map, so real collisions are rarer still, but the trend is what matters: more stripes, fewer collisions, and each stripe costs only one more small lock.

Now send 50% of all traffic to one celebrity's key. With 256 stripes the chance stays above 50%, and more stripes barely help, because every one of those operations needs the same stripe. Striping fixes contention spread across many keys. It can't fix one hot key. For that you split the key itself, as LongAdder does for a counter (several cells, summed on read), or batch updates on each thread and apply them together.

Two keys at once: deadlock

A bank transfer touches two accounts and must hold both stripes' locks, so no one sees the money in flight. The obvious code:

def transfer(m, src, dst, amount):     # deadlock-prone: don't copy this
    with m.lock_for(src):              # thread 1: transfer(x, y) takes x's stripe
        with m.lock_for(dst):          # thread 2: transfer(y, x) takes y's stripe
            ...                        # each now waits for the other's lock: forever

Two threads, each holding one lock and waiting for the other's, is a deadlock. Picture two cars meeting head-on on a one-lane bridge, each waiting for the other to back up. A deadlock needs a cycle of waiting: 1 waits for 2, 2 waits for 1.

The fix is to agree on one global order: always take the lower-numbered stripe first. Now both threads reach for the same lock first. Whoever gets it also takes the second and finishes; the other waits while holding nothing. A thread holding stripe 9 is never waiting for stripe 3, so no cycle can form. One more trap: if both keys are in the same stripe, take that lock once. Python's threading.Lock isn't re-entrant (the thread holding it can't take it again), so a second acquire waits for itself forever.

Whole-map questions: size and snapshots

"How many keys?" and "what's the total of all balances?" touch every stripe. Add up the stripes one at a time while transfers run and you can count money twice or not at all: a transfer can move money from a stripe you haven't read yet into one you already have. A consistent snapshot needs every stripe lock at once, taken in order: a stop-the-world moment you want to be rare. For the size, real maps keep a count per stripe and add the counts without any lock, accepting that the answer may be a moment out of date. Java's ConcurrentHashMap documents its size() exactly that way.

Lock striping splits one lock into S, chosen by hash(key) % S, so operations on different stripes run in parallel. Take two stripes in increasing order to rule out deadlock. Striping can't help a single hot key, and whole-map snapshots still need every lock.

Go deeper: Java's ConcurrentHashMap, then and now
  • Java 5 to 7: segments. The map was split into segments (16 by default, set by concurrencyLevel), each a small hash table with its own lock: lock striping exactly as above. Reads mostly took no lock. size() first tried to add up the segments without locking (twice, checking nothing changed) and only locked every segment if the map kept changing.
  • Java 8 onwards: a lock per bucket. The rewrite dropped segments. Putting a key into an empty bucket is one CAS, no lock. A non-empty bucket is locked by synchronizing on its first node, so the number of "stripes" grows with the table. Reads take no lock at all: writers publish fully built nodes, and readers use volatile reads (the acquire side from section 6). A bucket that collects 8 or more entries turns into a small balanced tree (once the table has at least 64 buckets). When the table grows, threads that run into a bucket being moved help move buckets instead of waiting. The size is kept in a LongAdder-style set of counter cells.
  • Other languages. Go's built-in map isn't safe for concurrent writes; the runtime detects it and crashes with "concurrent map writes". Go's sync.Map is documented for two cases: keys written once and read many times, and goroutines working on disjoint keys. In Python, one dict operation is safe (the GIL, or internal locks in the free-threaded build), but read-change-write needs your own lock.

A rate limiter keeps per-user request counters in a map with 256 stripes. One celebrity account sends 40% of all requests, and the map is a bottleneck. What would 4,096 stripes do?

Right. 40% of operations need the same stripe no matter how many stripes exist. Give the hot key several counter cells (each thread adds to one, reads sum them), or count locally and flush in batches.

More stripes lower the chance that two different keys share a lock. The celebrity's requests all use the same key, so they all hash to the same stripe, whether there are 256 stripes or 4,096. The slider in the figure shows it: at 50% on one key, adding stripes stops helping. The memory cost of 4,096 small locks is real but tiny, and it isn't what limits you. The fix is to stop funneling 40% of writes through one variable: split that counter into cells and add them up when someone reads it.

Thread 1 runs transfer(x, y) while thread 2 runs transfer(y, x). Key x is in stripe 3, y in stripe 9. Both follow "lower stripe first". What happens?

Right. The direction of the transfer no longer matters: both take 3, then 9. A thread holding 9 never waits for 3, so no cycle of waiting can form.

The rule ignores which key is the source. Both threads compute the same order, 3 then 9. Only one can hold stripe 3; the other blocks on stripe 3 while holding no lock. The winner takes 9 (nobody else holds it), finishes, and releases both. Then the other one goes. Starting at the same instant changes who wins, not whether someone does. A deadlock needs two threads each holding a lock the other wants, and a global order makes that impossible.

The order to reach for them: first a lock, because it's simple and correct. Measure. If the lock is hot, make the critical section shorter, then share less (stripes, one writer per variable, per-thread data). Go lock-free only when a thread truly must never wait for another one, and prefer a well-tested library structure to your own: lock-free code is famously easy to get almost right.

Go deeper: how people test concurrent code

Bugs that need one unlucky interleaving out of a billion don't show up in ordinary tests. Tools that help: race detectors watch memory accesses at run time and report unsynchronized ones (ThreadSanitizer for C, C++ and Rust; go test -race, which is built on it). Interleaving explorers run a test under a scheduler that tries many orders deliberately: Rust's loom. Stress harnesses such as Java's jcstress run tiny concurrent tests millions of times on real cores and report every outcome they saw, including the "impossible" ones. Model checkers such as TLA+ check a design before any code exists. The mpmc_queue exercise below uses the explorer idea: its tests own the scheduler and choose every interleaving.

11What to say in the interview

For "design a thread-safe counter / queue / cache", a strong answer goes in this order:

  1. Name what's shared and who writes it. "Eight request threads write the counter; one reporter reads it once a minute."
  2. Start correct: one lock around the shared state, and say why the naive version breaks ("+= 1 is read, change, write; two threads can read the same value").
  3. Say where it stops scaling: "every operation queues on one lock, and its cache line bounces between cores; with a quarter of the time under the lock, 16 cores give about 3.4×."
  4. Share less: per-thread cells summed on read for the counter; lock striping for a map; one writer per variable for a one-to-one hand-off (SPSC ring). Mention padding against false sharing.
  5. Lock-free only if it's earned: "if a thread must never wait on a paused one, I'd use a CAS-based queue like Michael-Scott, which is what ConcurrentLinkedQueue does. In C++ I'd also need to deal with ABA and memory reclamation, with hazard pointers or epochs."

"For the click counter: the bug is the lost update, since += 1 is three steps. A lock fixes it but serializes every click on one cache line. Since we read the total once a minute and write it millions of times, I'd give each thread its own counter, padded onto its own cache line, and have the reporter add them up; the sum can be a moment stale, which is fine for a dashboard. If the counts had to be exact at every instant, I'd say so and pay for the lock or an atomic add."

Habits that sound senior:

  • Name the guarantee you need: atomic, linearizable, lock-free, or just "eventually adds up".
  • Say what a stale read costs in your design ("it says full a moment early").
  • Keep the hardware in the picture: cache lines, false sharing, and that x86 hides reordering bugs Arm shows.
  • Know Python's limits: the GIL doesn't make += atomic, and there's a free-threaded build now.

✓What to remember

  1. x += 1 is read, change, write. Two threads can read the same value and lose an update: 18 of the 20 interleavings of two increments do.
  2. A lock makes a critical section atomic. It caps throughput at 1 / (time inside), and Amdahl's law caps speedup at 1 / (serial fraction).
  3. Cores share memory in 64-byte cache lines. Writing a shared line makes it travel between cores; two variables on one line false-share.
  4. SPSC ring: the producer owns tail, the consumer owns head, counters only grow, so no lock. Stale reads are cautious, never wrong.
  5. Write the item, then publish the counter, with a release store and an acquire load. x86 keeps store order; Arm doesn't.
  6. CAS writes only if the value is unchanged; wrap it in a retry loop. Lock-free: someone always finishes, even if others pause forever.
  7. Michael-Scott queue: link with a CAS on last.next, then swing tail; anyone who finds the tail lagging helps. ABA needs tags, hazard pointers, epochs or a GC.
  8. Concurrent map: stripe the locks by hash(key) % S, take two in increasing order, and split hot keys; whole-map snapshots need every lock.

✎Exercises

Do them in order. Warm-ups are pen and paper: commit to an answer before you open it. Core exercises are code in exercises/. Their tests measure what your code does: which locks it takes and in what order, how often it reads the other thread's counter, how many CAS it spends, and whether other threads can still finish while one is paused.

Warm-up · pen and paper

1. Count the interleavings

Two threads each run x += 1 as three steps (read, add, write), starting from x = 0. (a) How many interleavings are there, and in how many does x end at 2? (b) Same question if a thread's steps are only "read" and "write x = value read + 1". (c) Now each thread wraps its steps in a lock (take, read, add, write, release). Which interleavings are still possible, and what is x at the end?

Answer

(a) Choose which 3 of 6 positions are thread A's: 6!/(3!·3!) = 20 interleavings. x = 2 only when one thread's write comes before the other's read, which with read as each thread's first step means all of A then all of B, or the reverse: 2 of 20. (b) 4!/(2!·2!) = 6 interleavings, again 2 correct (AABB and BBAA). (c) Once A has taken the lock, B's "take" can't complete until A releases, so B's read, add and write can't fall between A's. Only two orders of the critical sections exist, A's then B's or B's then A's, and both end at x = 2.

Warm-up · pen and paper

2. Run an SPSC ring by hand

A ring of capacity 4 starts with head = tail = 0. Run: push a, push b, push c, pop, push d, push e, push f, pop, push f. For each step give head, tail, which slot was touched, and whether a push was refused. Then: with 64-bit counters and 2 billion items a second, how long until tail wraps?

Answer

push a: slot 0, tail 1. push b: slot 1, tail 2. push c: slot 2, tail 3. pop: takes a from slot 0, head 1. push d: slot 3, tail 4. push e: slot 4 & 3 = 0, tail 5. push f: tail − head = 5 − 1 = 4 = capacity, so refused. pop: takes b from slot 1, head 2. push f: slot 5 & 3 = 1, tail 6. The ring now holds c, d, e, f in slots 2, 3, 0, 1. Wrapping: 2⁶⁴ / (2 × 10⁹ per second) ≈ 9.2 × 10⁹ s ≈ 292 years.

Warm-up · pen and paper

3. Pick the tool

Name the structure and the one-line reason: (a) a video decoder thread feeding frames to the one render thread, which must never stall; (b) 32 request threads sending log lines to one disk-writer thread, where a short wait is acceptable; (c) per-endpoint request counts updated by 64 threads and read once a minute; (d) a feature-flag table read a million times a second and changed twice a day; (e) a session map with 100,000 users and 32 threads.

Answer

(a) SPSC ring: one producer and one consumer, no lock, so the render thread never waits on a paused decoder. (b) A bounded blocking queue (a lock and condition variables, like queue.Queue(maxsize=…)): many producers, waiting is allowed, and the bound gives backpressure if the disk falls behind. (c) Per-thread (or striped) counters, padded, summed by the reader: writes never contend, and a minute-old sum is fine. (d) An immutable snapshot behind one reference: readers just read, a writer builds a new table and swaps the reference. (e) A striped (or per-bucket-locked) concurrent map: 100,000 users spread over many stripes rarely collide.

4. SPSCRingBuffer: one producer, one consumer, no lock

In exercises/spsc_ring_buffer.py: try_push, try_pop and len on a power-of-two ring with counters that never wrap (sections 5 and 6). The tests swap in a recording slot list and check, at the moment of every access, that the item is written before tail moves and read and cleared before head moves; that push never writes head and pop never writes tail; and that each side reads the other's counter at most twice per 64 operations (re-reading every call costs 64). Then a real producer thread and consumer thread pass 30,000 items through a ring of 8.

5. StripedHashMap: many locks, in order

The tests hand you locks that record every acquire: single-key operations must take exactly their stripe's lock, keys must spread over all stripes (one global lock fails), transfer must take its two stripes in increasing order (or one, if they're the same), and total() must hold all of them at once. Core · code

6. MSQueue: a lock-free queue on simulated threads

In exercises/mpmc_queue.py: the Michael-Scott queue (section 8), written as generators where every shared access is a yield from on an AtomicRef. The tests own the scheduler: they run seeded random interleavings of up to 6 threads and check that every value comes out once, in each producer's order, and that EMPTY is returned only when the queue could have been empty. They pause an operation forever at every possible step and require every other thread to finish within 60 steps (a spin lock, or waiting for the lagging tail, fails). With an enqueue paused just after its link, a dequeue must still return that item and must not move head past the lagging tail. Alone, an enqueue must cost exactly 2 CAS and a dequeue 1, whatever the length.
