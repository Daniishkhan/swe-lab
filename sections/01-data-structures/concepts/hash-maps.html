Chapter 1 · Part 1

Hash maps: why a lookup is O(1)

P0 in almost every coding roundabout 35 minutes7 quick checks · 8 exercises

A hash map stores keys with their values and finds any key in about one step, however many keys it holds. Python's dict is a hash map, and set is the same structure without the values. Almost every coding interview uses one, and interviewers give credit for explaining why a lookup is O(1), when it stops being O(1), and what it costs in memory. This chapter builds a hash map from a plain array, one fix at a time, so that each part of the design has a reason you can say out loud.

By the end you'll be able to

  1. Build a hash map from an array: hash function, buckets, collisions, load factor and resizing.
  2. Compare separate chaining with open addressing, and explain why emptying a deleted key's slot breaks lookups.
  3. State what makes a valid key, and what breaks when a key is not one.
  4. Explain when O(1) becomes O(n), including when an attacker forces it.
  5. Recognize the problems a hash map solves, and the ones where it is the wrong structure.

How to read this: top to bottom. Some sections end with a quick check, and a wrong answer gets the idea explained a second way. "Go deeper" boxes are optional on a first read. This chapter builds on Big-O and complexity analysis, in particular amortized cost.

1The problem: a membership check on a list is O(n)

A list cannot answer "is this value already here?" without comparing the value against every item, and at ten million items that is too slow to do on every request.

Take a sign-up service with 10 million users. Each time someone picks a username, the server must check whether the name is taken. If the names are in a Python list, name in names compares the new name with each stored name in turn. A name that is free, which is the common case, gets compared with all 10 million. On a laptop that takes about 70 milliseconds.

one check of a free name     about 70 ms
1,000 sign-ups a second      1,000 × 70 ms = 70 s of work

The server is handed 70 seconds of work for every second that passes, so it can never catch up.

With the same names in a Python set, the check takes well under a microsecond, which is hundreds of thousands of times faster. It also does the same small amount of work at ten names and at ten million.

2Arrays: reading slot i takes one step

An array can read any of its slots in one step, because the slot's position in memory is computed and not searched for.

An array is a run of equal-sized slots stored side by side in memory. Every byte of memory has a number, called its address, and the hardware can read any address in about the same time. Because the slots are all the same size, the address of slot i follows from one multiplication and one addition.

slot          0      1      2      3      4
value        17     42      8     99      3
address    1000   1008   1016   1024   1032

8-byte slots, starting at address 1000
address of slot i  =  start + i × slot size
address of slot 3  =  1000 + 3 × 8  =  1024

Reading slot 3 costs the same as reading slot 3 million, which is why nums[i] is O(1) for a list of any length. A Python list is this kind of array, and its slots hold references to the items.

The limit of this trick is that the slot number must already be known. The sign-up check starts from a name and not from a slot number, and with a plain array that leaves two options.

ApproachCheck one nameAdd one nameWith 10 million names
Unsorted list, scannedO(n)O(1), append at the end10 million comparisons per check
Sorted list, binary searchO(log n)O(n), shift the items after it24 comparisons per check, about 5 million items shifted per insert

Sorting fixes the check and breaks the insert. An array has no gaps, so putting a new name in its sorted position means shifting every name after it, which is half the array on average. A sign-up does both a check and an insert, so both have to be fast.

The rest of the chapter turns a key such as a name into a slot number, so that any key gets the one-step read.

3Direct addressing: the key as the array index

When the keys are small whole numbers, the key itself can serve as the slot number, and a lookup is a single array read. This is called direct addressing.

Counting the letters of a text is the standard example. There are 26 lowercase letters, so an array of 26 counters has one slot for every possible key, and a letter's position in the alphabet is its index.

counts = [0] * 26
for c in "banana":
    counts[ord(c) - ord("a")] += 1    # its position is its slot
# counts[0] is 3 ("a"), counts[1] is 1 ("b"), counts[13] is 2 ("n")

Each letter costs one array read and one addition. Nothing is searched, and two different letters can never share a slot.

Direct addressing fits whenever the possible keys are few and packed close together: letters, ages from 0 to 150, days of the year, or user ids that run from 0 to 10 million. A bytearray with one flag for each of those ids takes about 10 MB.

It fails for usernames, because the array needs a slot for every key that could exist and not only for the keys in use. Suppose a username is 20 characters drawn from 37 symbols: the letters, the digits and the underscore.

possible usernames       37²⁰, about 2 × 10³¹
usernames in use         10,000,000
share of slots in use    about 4 × 10⁻²⁵

No computer has memory for that many slots, and nearly every one of them would stay empty. A 64-bit numeric id has the same problem, with about 18 billion billion possible values.

4Hash functions: from any key to a bucket

A hash function turns a key of any type into a number, and the remainder of that number after division by the array's length picks the slot.

The number is called the key's hash. A hash map built this way is also called a hash table, each slot of its array is a bucket, and m is the number of buckets.

bucket = hash(key) % m

The % operator gives the remainder after division, so the result is always a valid index into an array of m buckets, however large the hash is.

Java's hash function for strings is short enough to run by hand: start at zero, and for each character multiply the running value by 31 and add the character's code.

def toy_hash(s):
    h = 0
    for ch in s:
        h = h * 31 + ord(ch)    # earlier characters weigh more
    return h

Here it is on "cat".

character    code    h
c              99    0 × 31 + 99 = 99
a              97    99 × 31 + 97 = 3,166
t             116    3,166 × 31 + 116 = 98,262

toy_hash("cat") = 98,262      98,262 % 8 = 6
toy_hash("dog") = 99,644      99,644 % 8 = 4
toy_hash("act") = 96,402      96,402 % 8 = 2

In a table of 8 buckets "cat" goes to bucket 6, on every run and on every machine.

The multiplication makes the order of the characters count. A hash that only added the character codes would give "cat", "act" and "tac" the same value, 312, and all three keys would land in one bucket.

A hash function is usable when it has three properties.

  1. Deterministic. The same key gives the same hash for as long as the table exists. A key stored in bucket 6 and later looked up in bucket 3 would be reported missing.
  2. Uniform. Different keys spread evenly over the buckets, so that no bucket gets crowded. The hash that only adds character codes fails this test.
  3. Fast. Hashing a string of length k reads all k characters, so it costs O(k), and comparing two strings for equality costs up to O(k) as well. The O(1) usually quoted for hash maps assumes that keys are short.
Go deeper: what Python does with string hashes

Python computes a string's hash once and stores it in the string object, so hashing the same long string again costs O(1).

Python's hash of a string also changes from one run of the program to the next, for a reason section 10 explains. A value from hash() should therefore never be written to disk or sent to another process. A stable function from hashlib is the right tool for that.

5Collisions and separate chaining

Two different keys can land in the same bucket. This is called a collision, and no hash function can prevent it.

There are far more possible keys than buckets, so some keys have to share. The toy hash already produces a collision among three-letter words.

toy_hash("cat") =  98,262       98,262 % 8 = 6
toy_hash("tac") = 114,582      114,582 % 8 = 6

Both keys belong in bucket 6.

Collisions also begin long before a table is full. A collision only needs some pair of keys to match, and the number of pairs grows much faster than the number of keys. With 365 buckets, 23 keys already form 253 pairs, and each pair shares a bucket with a chance of 1 in 365.

A collision becomes more likely than not after roughly the square root of m keys. The row for 365 buckets is known as the birthday paradox, because it says that two people in a group of 23 probably share a birthday. Collisions are the normal case, and a hash table has to handle them from the first few inserts.

The most direct way to handle them is separate chaining. Each bucket holds a short list of key and value pairs, called a chain, and keys that collide share a chain.

  • Insert: hash the key, go to its bucket and walk the chain. If the key is already there, replace its value. If not, add the pair to the chain.
  • Lookup: hash the key, go to its bucket and compare the key with each stored key in turn, until one is equal or the chain ends.

This is why a hash table stores each key next to its value. The keys "cat" and "tac" share bucket 6, and comparing the stored keys is the only way to tell the two entries apart. A lookup also never leaves its own bucket, so the cost of a lookup is the length of one chain.

Six inserts and three lookups in a chained table of 8 buckets, using toy_hash. Each lookup compares keys in one bucket only.

Five keys go into an empty table of 8 buckets, with a good hash function. How likely is it that at least two of them share a bucket?

Each new key has to miss every bucket already in use.

That leaves a 79% chance that two of the keys share a bucket.

Count pairs of keys instead of keys. Five keys form 10 pairs, and each pair shares a bucket with a chance of 1 in 8. That many chances make a collision far more likely than not, and the exact figure is 79%.

6Load factor: what keeps lookups O(1)

The cost of a lookup in a chained hash table depends on how full the table is, and not on how many keys it holds.

Fullness is measured by the load factor, which is the number of keys divided by the number of buckets. It is written α, the Greek letter alpha, and it is also the average length of a chain.

α = n / m                      n keys in m buckets

lookup of an absent key        about α comparisons
lookup of a present key        about 1 + α/2 comparisons

An absent key costs one step to reach its bucket and then a comparison with every key in the chain, which holds α keys on average. A present key shares its chain with about α other keys, and on average it is found after half of them. The number of keys enters both costs only through the ratio.

Two table sizes show what this means for 10 million names.

BucketsLoad factorComparisons to check a new name
1,00010,000about 10,000
20,000,0000.50.5 on average

With 1,000 buckets each chain holds about 10,000 names, and the table is little more than a list cut into 1,000 pieces. With 20 million buckets most chains hold one name or none. A table that keeps its load factor under a fixed limit therefore answers a lookup in O(1) on average, which is why the set in section 1 did the same work at ten names and at ten million.

A hash map is fast because its load factor is bounded, not because hashing is fast. A lookup costs about one step plus the average chain length, so it stays O(1) only while the table keeps that average small.

A chained table holds 1,000,000 keys in 1,000 buckets, with a good hash function. About how many key comparisons does a lookup of an absent key take?

The load factor is 1,000, so the average chain holds 1,000 keys, and an absent key is compared with its whole chain.

Follow the lookup. The hash picks one bucket, so the other buckets are never touched and the answer cannot be a million. About 1,000 keys sit in that bucket, and the lookup must compare with all of them before it can report the key absent. O(1) holds only while the table keeps its chains short.

7Resizing and rehashing: amortized O(1) inserts

A hash table keeps its load factor bounded by growing. When an insert would push the load factor past a limit, the table allocates a larger array, usually twice the size, and moves every key into it.

The limit is a design choice and not a law. Java's HashMap uses 0.75. A lower limit gives shorter chains and uses more memory.

Every key has to be placed again, because a key's bucket depends on m and m has just changed. Working out each key's bucket in the new array is called rehashing.

KeyHashBucket in a table of 8Bucket in a table of 16
"dog"99,64499,644 % 8 = 499,644 % 16 = 12
"cat"98,26298,262 % 8 = 698,262 % 16 = 6

After the table doubles, a lookup for "dog" searches bucket 12. Had the old buckets been copied across unchanged, "dog" would still be in bucket 4 and no lookup would find it. Some keys, such as "cat", happen to keep their bucket.

A resize moves all n keys, so the one insert that triggers it costs O(n). Inserts stay cheap on average because doubling makes resizes rare, which is the amortized analysis from the complexity chapter. Here are 1,000 inserts into a table that starts with 8 buckets and grows at a load factor of 0.75.

Each resize moves about as many keys as all the earlier resizes combined, so the total stays below twice the number of inserts however long the run is. The extra cost per insert is O(1) on average, and that is what "amortized O(1)" means.

A fixed step resizes every few inserts and moves every key each time, which is O(n²) in total.

Go deeper: the latency spike of a single resize

Amortized O(1) is a statement about the total. The single insert that triggers a resize of a 10-million-key table still moves 10 million keys, and the request that issued it waits for about half a second. In a web service that shows up as a spike in tail latency.

Redis avoids the spike with incremental rehashing. It keeps the old and new tables side by side and moves one bucket on every operation, and lookups check both tables until the move is finished. Where the number of keys is known in advance, the simpler answer is to create the table at its final size, which Java, Go, Rust and C++ allow and Python does not.

Java and CPython store each key's hash, so a resize places every key again without calling the hash function.

Most tables never shrink. A table that has lost most of its keys keeps all its buckets, and iterating over it still visits every one of them, which costs O(n + m).

When a table doubles from 8 to 16 buckets, why can it not copy bucket 0 to bucket 0, bucket 1 to bucket 1, and so on?

Lookups in the new table take the hash modulo 16. A key left where modulo 8 put it may sit in a bucket that no lookup for it will ever visit.

Trace one key. In a table of 8 buckets "dog" is in bucket 4, and in a table of 16 its hash points to bucket 12. Copied straight across, "dog" would sit in bucket 4 while every later lookup searched bucket 12, and the key would be lost without any error. Changing m means working out every key's bucket again, although each key's hash stays the same.

8Open addressing: linear probing and tombstones

Open addressing handles collisions without chains. Every key is stored in the array itself, one key to a slot, so a lookup never walks a chain. A key whose slot is occupied goes to a different slot.

Python's dict and set use open addressing. The simplest form, and the one this section builds, is linear probing. The slot that the hash picks is the key's home slot. If the home slot is occupied, the insert tries the next slot and then the one after it, wrapping around from the end of the array to the start, and it stores the key in the first empty slot it finds. Each slot examined is called a probe.

A lookup follows the same path. It starts at the home slot and walks forward until it finds the key or reaches an empty slot. An empty slot proves that the key is absent, because an insert of that key would have stopped there. In a table of 8 slots the keys "cat", "tac" and "pig" all have home slot 6.

OperationWhat the probes findResult
Insert "cat"slot 6 is emptystored in slot 6
Insert "tac"slot 6 holds "cat"stored in slot 7
Look up "tac"slot 6 holds "cat", slot 7 holds "tac"found after 2 probes
Look up "pig"slots 6 and 7 hold other keys, slot 0 is emptyabsent after 3 probes

The lookup of "pig" wraps around to slot 0, finds it empty and stops.

Clustering

Linear probing needs a lower load factor than chaining, because runs of occupied slots feed on themselves. Such a run is called a cluster. A new key whose home slot lies anywhere inside a cluster walks to the end of it and makes the cluster one slot longer, and a longer cluster catches more new keys. The number of probes therefore climbs much faster than the load factor does.

Load factorProbes to find a present keyProbes to report a key absent
0.501.52.5
0.672.05.0
0.752.58.5

A table that is nine tenths full needs about 50 probes to report a key absent, twenty times as many as a table that is half full. Open-addressing tables therefore grow well before they are full, and Python's dict grows when it is about two thirds full.

Deletion and tombstones

Deletion is the hard part of open addressing, because emptying a slot can cut the path to keys stored beyond it.

How "cat" is deleted from slot 6The next lookup of "tac", stored in slot 7Result
The slot is emptiedslot 6 is empty, so the search stopsreported absent, which is wrong
The slot gets a tombstoneslot 6 is a tombstone, so the search goes on to slot 7found after 2 probes

In the first case the lookup stops at the gap in slot 6, although "tac" is still in the table. The second case is the fix. A tombstone is a marker left in the slot of a deleted key, and it tells a search to keep walking. Only a truly empty slot ends a search.

Tombstones add two rules. An insert may reuse a tombstone's slot, but only after walking on to an empty slot to confirm that the key is not stored further along, or the table could end up holding the same key twice. Tombstones also lengthen every search without holding a key, so they count toward the load factor, and when the limit is reached the table is rebuilt from its live keys.

Chaining tolerates a high load factor and makes deletion easy. Open addressing is usually faster, because the slots next to a probe come into the CPU's cache together with it, while list nodes are scattered across the heap.

Go deeper: Python's dict, other designs, and the cache

CPython's dict does not probe the next slot. It visits slots in a scrambled order that comes to depend on every bit of the hash, so keys with the same home slot soon take different paths.

# perturb starts as the full hash
perturb = perturb >> 5
i = (5 * i + 1 + perturb) % m

Since Python 3.6 a dict is two arrays: a sparse array of indexes, which is the part that gets probed, and a dense array of entries in insertion order. That layout is why a dict preserves insertion order, which the language has guaranteed since 3.7.

Quadratic probing and double hashing are the textbook ways to reduce clustering. Swiss tables, used by Abseil, Rust and Go, store one summary byte per slot and test a group of 8 or 16 slots at once.

Linear probing can also delete without tombstones. Backward-shift deletion moves later keys of the cluster back into the emptied slot, as long as no key moves before its home slot, so no gap is left on any key's path.

The cache also explains why a big table is slower than a small one although each lookup does the same work. With a different name on each check, a lookup in the set of 10 million names took about 150 nanoseconds, against about 20 in a set of ten names, because most of the big table is not in the cache.

With linear probing, "tac" is in slot 7 because "cat" held slot 6. Then "cat" is deleted by setting slot 6 back to empty. What does the next lookup of "tac" return?

An empty slot is what ends a search, and the delete created one in the middle of the path. A tombstone in slot 6 would have told the lookup to keep walking.

Follow the lookup one probe at a time. The home slot of "tac" is slot 6, so the search starts there and finds the slot empty. An empty slot means the key was never stored on this path, so the search stops without looking at slot 7. Nothing moves "tac" back on its own, which is why a delete leaves a tombstone instead.

9Hashable keys: the hash and equality contract

A hash map only works if a key reaches the same bucket when it is looked up as when it was stored. That requirement puts two rules on keys, and breaking either one loses entries without raising any error.

Equal keys must have equal hashes

A lookup hashes the key to choose a bucket and only then compares keys for equality. If two keys are equal but hash differently, a lookup with the second searches a different bucket from the one that holds the first, and the equality test never runs. The opposite case is harmless, since two unequal keys with the same hash are an ordinary collision.

Python enforces part of this rule. A class that defines __eq__ without __hash__ has its __hash__ set to None, so its objects cannot be used as keys at all. Java does not check. Overriding equals without hashCode compiles, and lookups then fail quietly.

A key must not change while it is stored

The table computes a key's bucket once, when the key is inserted. If the key's hash changes afterward, every lookup goes to a different bucket from the one that holds the entry.

class Point:
    def __init__(self, x, y): self.x, self.y = x, y
    def __eq__(self, o): return (self.x, self.y) == (o.x, o.y)
    def __hash__(self): return hash((self.x, self.y))

p = Point(1, 2)
seen = {p}
p.x = 99                      # the key changes inside the set
print(p in seen)              # False
print(Point(1, 2) in seen)    # False

The first lookup hashes (99, 2) and searches a different bucket. The second reaches the right bucket, where the stored key now equals (99, 2). The entry is still in the set, but neither value can reach it. This is why Python refuses to hash lists, sets and dicts, which can change, and hashes strings, numbers, tuples and frozensets, which cannot. A key made of several fields is written as a tuple, such as (x, y).

Go deeper: four consequences in Python

The values 1, 1.0 and True are equal, so they must hash alike, and they are one key. The dict {1: "a", True: "b", 1.0: "c"} ends up holding a single entry.

A NaN is not equal to itself. Python's dict checks whether two keys are the same object before it calls ==, so the same NaN object can be found again, but a newly created NaN never matches.

Changing the number of keys while looping over a dict raises RuntimeError. The loop checks the size on every step, because an insert could resize the table under it. Looping over list(d) avoids it.

An object whose class defines neither __eq__ nor __hash__ hashes by identity, so changing its fields does not move it, and only that same object finds it again.

In Java a list hashes by its contents. A list is used as a HashMap key, and an item is appended to it afterward. What happens?

Nothing tells the table that the key changed, so the entry stays in its old bucket while every lookup hashes the new contents. This is the reason Python makes lists unhashable.

The table computed the bucket once, at insert time, and it is never told about the append, so it cannot move anything. A later lookup hashes the list as it is now and searches a different bucket. Being the same object does not help, because the lookup goes to the wrong bucket before any keys are compared.

10Worst case O(n): weak hash functions and hash flooding

Every O(1) in this chapter assumed that the hash function spreads keys evenly. When it does not, a hash map degrades into a list.

In the worst case every key lands in the same bucket. The table is then a single chain, or a single cluster under open addressing. Each lookup is O(n), and inserting n keys costs O(n²) in total, because each insert first walks past the keys already stored.

A weak hash function can cause this by accident. The hash that only adds character codes puts every anagram of a word into one bucket.

Hash flooding

An attacker can also force the worst case on purpose, which is called hash flooding. Web servers commonly parse the fields of a request into a hash map. If the hash function is fixed and public, an attacker can compute thousands of field names that all collide and send them in a single request.

100,000 colliding field names
about 100,000² / 2 = 5 billion key comparisons
at about 10 ns each, about 50 seconds of CPU

One request of a few megabytes can keep a CPU core busy for close to a minute. The attack was described in 2003, and in 2011 researchers showed that it worked against PHP, Java, Python, Ruby and ASP.NET.

Three defenses followed. Python made its hash unpredictable. It picks a random secret when the process starts and mixes the secret into every string hash, using a function called SipHash, so an attacker cannot compute collisions in advance. Java kept its hash function and limited the damage: a bucket that grows past 8 entries is converted into a balanced tree, which makes the worst lookup O(log n). Web frameworks also cap the number of fields in one request.

Go deeper: patterned keys, integer keys and Java's tree bins

A table whose size is a power of two takes the remainder from the low bits of the hash alone, so keys that are all multiples of 16 share bucket 0 of a 16-bucket table. Libraries defend against such patterns by mixing the high bits of the hash into the choice of slot.

Python randomizes the hashes of strings and bytes, but not of numbers. An integer hashes to itself, reduced modulo 2⁶¹ − 1, so every number of the form below has hash 1.

k × (2⁶¹ − 1) + 1        for k = 0, 1, 2, …

Building a dict from n such keys takes O(n²) time. If untrusted input becomes integer keys, cap its size or convert the keys to strings.

Java's String.hashCode is the toy hash from section 4 and is not randomized, so colliding keys are cheap to make. The strings "Aa" and "BB" both hash to 2,112, so every string made of 17 such two-letter blocks shares one hash: 131,072 field names of 34 characters, about 4.5 MB. That is why Java added tree bins. A bucket becomes a tree only in a table of at least 64 buckets, and the O(log n) bound holds only when the keys are Comparable.

Python gives the same string a different hash each time the program starts. What problem does that solve?

Within one run the hash is fixed, so the table works as usual. Across runs it depends on a secret, so nobody outside the process can prepare a set of colliding keys.

Ask who the secret is kept from. Inside one run a string hashes the same way every time, as the table requires, and a secret spreads keys no better than a good fixed hash does. A set of strings does print in a different order on each run, but only as a side effect. The point is that someone outside the process can no longer compute 100,000 field names that share a bucket.

11Hash map patterns, and when to use another structure

In an interview a hash map is most often the step that turns an O(n²) solution into an O(n) one. It does so by remembering what has already been seen, so that nothing has to be searched for twice.

The signal in a problem is a brute-force solution with two nested loops, where the inner loop only searches for one thing. A lookup replaces that search. Four patterns cover most of these problems.

PatternWhat the map remembersClassic problem
Seen beforeeach item already passedTwo Sum: for each x, look up target − x
Group by keythe items that share each labelGroup Anagrams: the label is the word's letters in sorted order
Counthow many times each item has appearedTop-k frequent words, with collections.Counter
Prefix sumshow many earlier positions had each prefix sum, the total of the items up to that positionCount the subarrays that sum to k: a subarray sums to k when the prefix sums at its two ends differ by k

Each pattern spends O(n) extra memory to remove the inner loop.

A hash map is the wrong structure in four situations.

  • The order of the keys matters. Finding the smallest key, the next key after a given one, or every key in a range costs O(n), because hashing scatters neighboring keys on purpose. A balanced tree or a sorted array keeps keys in order.
  • The keys are small and dense. Letters, ages and ids from 0 to n fit an array with direct addressing, which is faster and smaller.
  • Memory is tight. A hash table keeps empty slots on purpose. If the 10 million names rarely change, a sorted list of them needs 80 MB against the 268 MB table of a Python set, and still answers a check in 24 comparisons.
  • A worst-case bound is required. A hard real-time system cannot accept an occasional O(n) resize, while a balanced tree takes O(log n) on every operation.
Go deeper: hash maps across machines

The natural way to spread keys over N servers is to take the hash modulo N. It has the same flaw as resizing: changing N from 10 to 11 changes the server of almost every key, so almost all the data has to move. Consistent hashing moves only about one key in N.

A service must support two operations: add an event with a timestamp, and list all events between 9:00 and 9:05. Which structure fits best?

A sorted structure finds 9:00 in O(log n) steps and then walks forward to 9:05, touching only the events in the range.

A hash map can say in O(1) whether an event exists at exactly 9:03:17. A range needs the keys in order, and hashing deliberately scatters 9:00:01 and 9:00:02 into unrelated buckets. Scanning every key does work, but it costs O(n) per query, which is the cost the structure was meant to avoid.

12What to say in the interview

When asked why a dict lookup is O(1), or how to build a hash map, answer in this order.

  1. Array indexing. "An array reads any slot in one step, because the slot's address is computed. A hash function turns any key into a number, and that number modulo the table size picks the slot."
  2. Collisions. "Different keys can share a slot, and that starts early. I would chain, so each bucket holds a short list of key and value pairs and I compare keys for equality. The alternative is open addressing, which needs tombstones for deletes."
  3. Load factor and resizing. "A lookup costs about one step plus the load factor, which is keys divided by buckets. I keep it under a limit such as 0.75 by doubling the table and rehashing. An occasional insert costs O(n), and the amortized cost is O(1)."
  4. Worst case. "That is O(1) on average. The worst case is O(n) if the keys pile into one bucket, which an attacker can force unless the hash is randomized."
  5. Trade-off. "A hash map spends extra memory and gives up order. For range queries or a guaranteed worst case I would use a balanced tree."

✓What to remember

  1. An array reads slot i in one step because the address is computed. A hash map gives that one-step read to keys of any type.
  2. Direct addressing needs a slot for every possible key, so it only suits small, dense keys.
  3. A hash function must be deterministic and uniform. The hash modulo the table size picks the bucket.
  4. Collisions start after about the square root of m keys. Separate chaining keeps the colliding entries in a list and compares keys for equality.
  5. A lookup costs about one step plus the load factor, so a bounded load factor is what makes lookups O(1).
  6. Resizing doubles the table and rehashes every key. Doubling keeps the total under two moves per insert, so inserts are amortized O(1) although one insert costs O(n).
  7. Open addressing probes forward on a collision. An empty slot ends a search, so deletes leave tombstones.
  8. Equal keys must hash alike, and a key must not change while it is stored.
  9. The worst case is O(n), when keys pile into one bucket. Randomized hashing stops an attacker from forcing it.
  10. A hash map is the wrong structure for ordered or range queries, small dense keys, tight memory or a hard worst-case bound.

1. Trace linear probing by hand

A table has 8 slots and uses linear probing. The keys have these hashes: A is 3, B is 11, C is 4, D is 19 and E is 5. Insert A, B, C, D and E in that order, then delete B and look up D. Write down the table after each step and every slot the lookup visits.

Answer 
insert A    3 % 8 = 3     slot 3
insert B   11 % 8 = 3     3 is taken, so slot 4
insert C    4 % 8 = 4     4 is taken, so slot 5
insert D   19 % 8 = 3     3, 4 and 5 are taken, so slot 6
insert E    5 % 8 = 5     5 and 6 are taken, so slot 7

table       [ _  _  _  A  B  C  D  E ]

delete B    slot 4 becomes a tombstone
look up D   slot 3 holds A, slot 4 is a tombstone,
            slot 5 holds C, slot 6 holds D
            found after 4 probes

Had slot 4 been emptied, the lookup would have stopped there and reported D absent. Key C also shows clustering: its home slot was taken by B, a key that did not belong in that slot either.

3. Find the bug

class User:
    def __init__(self, email): self.email = email
    def __eq__(self, other):
        return self.email.lower() == other.email.lower()
    def __hash__(self): return hash(self.email)

Which rule of the key contract does this class break? Give two User objects that show the bug, and fix it.

Answer

Equal keys must have equal hashes. The objects User("A@x.com") and User("a@x.com") compare equal, but their hashes come from different strings, so they almost always land in different buckets. Put one in a set and the other is not found. The fix is to hash the value that equality compares, which is self.email.lower(). Better still, normalize the email once in __init__ and use a frozen dataclass, so the email cannot change after the user goes into a set.
