Chapter 1 · Part 1

Find anything in one step

P0 in almost every coding roundabout 18 minutes8 quick checks · 8 exercises

A hash map — Python's dict (and set, which is the same structure without values) — shows up in almost every coding round. Nobody gets credit just for using one. Interviewers want to know why it finds one item out of ten million in a single jump, how it can break, and when to reach for it instead of a loop.

By the end you'll be able to

  1. Explain why a hash map finds one item out of 10 million without scanning the rest.
  2. Rebuild a hash map from scratch using one physical picture: a coat-check room.
  3. Predict what happens on collisions, when the room fills up, or when a stored key mutates.
  4. Apply the four interview patterns that turn nested loops into a single pass — and spot when a hash map is the wrong tool.
  5. Deliver a crisp 2-minute interview explanation without notes.

1Why do we even need a hash map?

You run sign-ups for an app with 10 million users. Every time someone picks a username, your server asks: "Is this name taken?"

In a plain Python list, name in names checks every stored name one by one. A free name (the usual case) checks all 10 million — about 70 ms on a laptop. At 1,000 sign-ups a second, that's 70 seconds of work every second. Your server falls behind and melts.

Move those same 10 million names into a Python set and the check takes under a microsecond — roughly the same tiny effort at 10 users or 10 million.

A list searches. A hash map computes where the answer must live and checks only that spot.

That single "stop searching, jump straight there" trick unlocks four huge interview moves:

  • Seen before? Taken usernames, duplicates, or finding a pair that sums to a target in one pass.
  • Group by fingerprint. Bucketing anagrams or log lines that share a trait.
  • Count frequencies. Most common words, votes, or characters.
  • Remember running totals & results. Counting subarrays summing to k, or caching expensive calls.

How can a computer find one name out of 10 million without glancing at the other 9,999,999? Let's invent it from scratch, one fix at a time.

2What's the only thing a computer finds in one step?

Picture a coat-check room with a wall of identical numbered hooks: 0, 1, 2, 3, …. Hand the attendant ticket #42, and they go straight to hook #42 without inspecting hooks 0 through 41.

Computer memory (RAM) works the same way. Every byte has a numeric address, and an array parks equal-sized slots side by side in RAM. Finding slot i is just one multiply and one add:

slot:        0      1      2      3      4
          ┌──────┬──────┬──────┬──────┬──────┐
value:    │  17  │  42  │   8  │  99  │   3  │
          └──────┴──────┴──────┴──────┴──────┘
address:  1000   1008   1016   1024   1032    (8-byte slots)

address(i) = start + i × slot_size
address(3) = 1000  + 3 × 8 = 1024  → 1 jump at any size
nums[3] is arithmetic, not a search. (A Python list is an array of 8-byte memory addresses/pointers, so names[i] is also one jump.)

Where the coat-check analogy breaks: a human attendant still walks further down a hallway to hook #4,000 than hook #4. RAM jumps electrically to any address in about the same time (modulo CPU caches favoring nearby memory).

The catch: you need the hook number up front. Our sign-up server only has a username, which leaves plain arrays stuck between two bad options:

Plain-array optionCheck one nameAdd one nameAt 10M names
Unsorted list (scan)O(n)O(1) amortized append at end10M checks per sign-up
Sorted list (binary search)O(log n)O(n) shift items after it24 checks, ~5M shifts per insert

Sorting fixes lookups and breaks inserts: arrays have no gaps, so inserting under "M" slides half the array over. Sign-ups do both a check and an insert, so both must be fast.

Go deeper: strings are arrays too (and why immutability matters)

A string is an array of characters: s[5] is O(1), while comparing two length-k strings checks up to k characters: O(k). In Python, Java, Go, and JavaScript, strings are immutable — so repeated s += ch in a loop conceptually copies the growing string each step (O(k²) in general; collect pieces in a list and "".join() instead). Immutability is also what makes strings safe keys in section 7.

An array jumps to slot i in one step via arithmetic. A hash map turns any key (like a username) into a hook number so every key gets that one-step jump.

Binary search on a sorted list of 10 million usernames checks any name in 24 steps. Why isn't that enough for sign-ups?

Exactly. 24 alphabetical comparisons is microseconds; it's the insert that kills it (~5 million shifts per sign-up).

Sign-ups do two things: check the name, then insert it if free. Binary search handles sorted strings easily in log₂(10M) ≈ 24 steps. The bottleneck is inserting into the middle of an array, which has no gaps and must slide every item after it down by one.

3Why not just give every key its own hook?

Simplest idea: use the key itself as the hook number. Counting lowercase letters in "banana" needs only 26 hooks ('a' → 0 through 'z' → 25):

counts = [0] * 26
for ch in "banana":
    hook = ord(ch) - ord("a")   # ord() turns a char into its numeric code
    counts[hook] += 1           # direct jump, zero collisions

That's direct addressing. Whenever possible keys are small and tightly packed (26 letters, 256 byte values, ages 0–150, dense IDs 0..n), direct addressing beats a hash map on speed and memory.

Now try usernames. Even 10-letter lowercase usernames have 26¹⁰ — over 140 trillion — possible names. Direct addressing builds a hook for every key that could exist, not just the 10 million you store. Almost every hook would sit empty forever.

Direct addressing sizes the array to the possible key range. It's unbeatable for small, dense keys and impossible when the key space is huge.

You only have 500 customers, each with a random 64-bit account ID. Why can't you store them in an array indexed directly by account ID?

Right. Direct addressing needs a slot for every possible ID up to ~18 quintillion — even when only 500 slots are used.

Think about our coat-check wall: if customer #1 has ID 9,482,103,847,120, hook #9,482,103,847,120 only exists if you build all 9 trillion hooks before it. Direct addressing scales with the range of possible keys, not the count of stored keys.

4How do we squeeze infinite names into 8 hooks?

Suppose our coat room has m = 8 hooks (numbered 0 to 7), and guests walk in with any name. The attendant needs a repeatable rule that turns any name into an integer, then wraps it into 0..7 using remainder (% m).

Try the simplest head-math rule: give each letter its alphabet number (a=1, b=2, …) and add them up:

"cat" → 3 + 1 + 20 = 24  → 24 % 8 = 0
"act" → 1 + 3 + 20 = 24  → 24 % 8 = 0   ← same hook!
"tac" → 20 + 1 + 3 = 24  → 24 % 8 = 0   ← same hook again!

Addition ignores letter order, so every anagram piles onto the same hook. Fix: multiply the running total before adding each letter so earlier letters weigh more:

def simple_hash(word):
    h = 0
    for ch in word:
        h = h * 31 + ord(ch)    # 31 is a tunable odd multiplier, not a magic law
    return h
# simple_hash("cat") = 98,262 -> 98,262 % 8 = 6
# simple_hash("act") = 96,402 -> 96,402 % 8 = 2
# simple_hash("dog") = 99,644 -> 99,644 % 8 = 4

Why an odd multiplier like 31 instead of 8? Multiply by 8 and every earlier character becomes a multiple of 8 — so % 8 would ignore everything except the last letter!

In CS terms, this rule is a hash function, each hook is a bucket, and m is the bucket count:

Every insert and lookup runs the exact same pipeline: bucket = hash(key) % m.

A usable hash function needs three traits: deterministic (same key → same hash every time during the table's life), uniform (spreads keys evenly across hooks), and fast (O(k) to read a length-k key, so "O(1) lookup" assumes short keys).

Go deeper: production hashes, power-of-two masking, and Python bignums

simple_hash is Java's String.hashCode() in fixed 32-bit math. Note a subtle Python trap: Python integers grow arbitrarily large, so without a 32-bit mask (& 0xFFFFFFFF), multiplying a k-character string produces a k-digit bignum and costs O(k²) instead of O(k)!

Python caches each string's hash inside the string object (so repeat lookups are O(1)) and mixes a random startup secret (SipHash) into string hashes — never save hash() to disk or send it over the network; use hashlib for stable hashes.

Real tables keep m a power of two so h & (m - 1) replaces slow division with one AND. The catch: masking reads only the lowest bits of h, so patterned keys (like multiples of 16) pile up unless you mix high bits down (e.g., Java's h ^ (h >>> 16)) or choose a prime m.

A hash function turns any key into an integer, and hash(key) % m maps it onto one of m buckets — deterministically, uniformly, and fast.

Why is "add up the alphabet numbers of each letter" a bad hash function for English words?

Right. It's deterministic and fast (O(k) in word length, like any string hash), but it fails uniformity: anagrams collide and sums cluster tightly.

Check the output range: every 5-letter word sums to at most 5 × 26 = 130. In a table of 1,000 hooks, hooks 131 through 999 sit completely empty while thousands of words cram into hooks 5–130! Good hashes spread outputs across the whole table.

5What if two names land on the same hook?

Now hit the catch: millions of names, only 8 hooks. Two different names are guaranteed to share a hook — even simple_hash collides immediately:

simple_hash("cat") % 8 = 6
simple_hash("tac") % 8 = 6   ← collision!

That's a collision. No hash function can prevent them, so a hash map plans for them. In our coat room, the cleanest fix is simple: hang both coats on hook #6, and clip a name tag onto each coat.

That's separate chaining. Each bucket stores a short list (a chain) of (key, value) pairs. Insert hashes the key and appends (or overwrites if already in that chain); lookup hashes the key and checks only that one chain with ==. Storing the key next to the value is the name tag — without it, you couldn't tell "cat" from "tac" on hook #6.

Six inserts and three lookups in an 8-bucket chained table. Press ▶ Play or step with ▶|. Looking up eel checks only hook 4 and ignores every other hook.
Go deeper: why collisions start surprisingly early (the birthday paradox)

A collision only needs any pair of keys to match, and pairs grow quadratically. With 365 hooks, 23 keys already form 253 pairs — enough for a >50% collision chance. In general, collisions become likely around 1.2 × √m keys (4 keys in 8 buckets; 1,178 keys in 1,000,000 buckets).

Go deeper: how Python dicts handle collisions without chains (open addressing & tombstones)

Python's dict and set (plus Rust's and Go's maps) use open addressing: no lists per bucket — every key sits directly in one flat array, at most one coat per hook. (Since Python 3.6, a dict actually keeps a sparse array of slot indexes alongside a dense insertion-ordered array of entries, which is why Python dict preserves insertion order!)

In linear probing, if your home hook (#6) is taken, you try #7, then wrap to #0 until you find an empty hook. (CPython scrambles the probe sequence using higher hash bits to reduce clustering.) Lookups follow the same path until they match the key or hit an empty hook.

The deletion trap (tombstones): Suppose "cat" sits in slot 6 and "tac" spilled into slot 7. Emptying slot 6 on delete breaks lookups for "tac" — the search stops at empty slot 6 and wrongly says absent! The fix is a tombstone (✝): a "someone was here" marker that tells lookups to keep walking, while allowing inserts to reuse that slot only after walking on to an empty slot to confirm the key isn't already further along. Tombstones still lengthen walks, so they count toward fullness and get cleared on rebuild.

Because occupied runs snowball (clustering), open addressing grows earlier (Python grows near 2/3 full). Its payoff is CPU cache locality: flat array probes sit side by side in RAM.

Try: insert cat, insert tac (slides to slot 7), delete cat (leaves ✝ in 6), look up tac, then re-insert cat to watch tombstone reuse. Needed for Exercise 5.
Collisions are normal. Separate chaining hangs colliding (key, value) pairs on a short per-bucket list and compares keys with == so lookups never touch other buckets.

Both "cat" and "tac" land in bucket 6. Why must bucket 6 store the keys alongside their values, rather than just the values?

Spot on — that's the coat's name tag! Hash functions aren't reversible, and hook #6 holds two coats, so storing keys lets lookups verify a match (and lets resizes rehash entries).

Imagine bucket 6 only stored [10, 20]. When you ask for get("tac"), you jump to bucket 6 and see two numbers with no way to know which belongs to "tac" — or whether "tac" is stored at all. Storing each key next to its value resolves the collision.

6What happens as the coat room fills up?

What if 10 million guests pile coats onto our 8 hooks? Each hook holds over a million coats — we're back to linear scanning! A hash map stays fast only while hooks stay uncrowded.

Measure crowdedness by dividing coats by hooks: n / m. Computer scientists call this the load factor and write it α (alpha). A lookup does 1 jump to the bucket plus about α comparisons on a miss (1 + α/2 on a hit):

crowdedness (load factor)  α = n / m   (keys ÷ buckets)

10M keys /      1,000 hooks → α = 10,000  (slow: ~10k checks)
10M keys / 20,000,000 hooks → α = 0.5     (fast: ~1 step!)
Slide n up at m = 16 and watch chains grow; then bump m to 64 to flatten them. Try "multiples of 16" to see a bad hash wreck the spread.

The fix: double the room and rehang every coat

When an insert would push α past a chosen limit — say 0.75 (a tunable trade-off between speed and empty-slot memory, not a law) — the table allocates an array twice as big (8 → 16 → 32 → …) and moves every key over.

You can't just copy bucket i into bucket i: lookups now take % 16 instead of % 8, so every key must be re-placed (rehashed) into its new bucket:

After doubling from 8 to 16, lookups for "dog" check bucket 12. Copied into bucket 4, "dog" would vanish.

Moving all n keys makes that one resize insert O(n) — yet inserts stay O(1) amortized because doubling makes resizes exponentially rarer (1,000 inserts from 8 buckets):

Growth ruleResizesKeys movedInsert cost
Double buckets (8 → 16 → 32 …)81,530 (~1.5 / insert)O(1) amortized
Add 8 each time (+8, +8 …)16683,166O(n) → O(n²) total
Go deeper: resize latency spikes, pre-sizing, and shrinking

Amortized O(1) averages over time — the single request that resizes a 10M-key table still pauses for hundreds of milliseconds. Redis avoids tail-latency spikes with incremental rehashing (migrating one bucket per operation while lookups check both old and new tables). Java, Go, Rust, and C++ let you pre-size capacity upfront (Python does not). Most tables also never shrink on delete, so iterating a shrunken map still visits all m buckets: O(n + m).

Bounded load factor (α = n / m) is what makes lookups O(1). Doubling and rehashing makes one insert O(n) and all inserts O(1) amortized.

When a table doubles from 8 buckets to 16, why can't it copy bucket i directly into bucket i of the new array?

Exactly. Each key's hash stays unchanged, but m changed from 8 to 16, moving keys like "dog" from bucket 4 to bucket 12.

Check "dog" (hash 99,644): 99,644 % 8 = 4, but 99,644 % 16 = 12. Left in bucket 4, future lookups check empty bucket 12 and report "dog" missing.

7How can a hash map break?

1. Mutating a stored key (the key contract)

Suppose your coat's name tag is a synced digital badge showing "Sam" on hook #2. While you're inside, you change your name to "Max" (hook #5), and the badge on hook #2 flips to "Max" too. Now asking for "Max" checks empty hook #5, and asking for "Sam" checks hook #2 and sees "Max" != "Sam". Your coat is stranded silently.

Assuming Point defines custom value-based __hash__/__eq__ on (x, y) (Python's default classes hash by object identity). Mutating a stored key strands it silently.

Two laws keep keys reachable: keys must not mutate while stored (why Python bans list/dict/set keys and uses immutable str/int/tuple), and equal keys must have equal hashes (otherwise lookup jumps to the wrong bucket and == never runs; Python disables __hash__ when you override __eq__, while Java lets broken classes fail silently).

Go deeper: Python key quirks (1 == True, NaN, and mutating while looping)

Equal values collapse: Because 1 == 1.0 == True, all three share one hash, so {1: "a", True: "b", 1.0: "c"} holds a single entry ({1: "c"}).

The NaN trap: float('nan') != float('nan'), yet Python checks object identity (is) before ==. So for x = float('nan'); d = {x: 1}, looking up x succeeds by identity, while looking up a fresh float('nan') misses — allowing multiple NaN keys in one dict!

Looping: Never add or delete keys while iterating a dict (raises RuntimeError because a resize could shuffle slots); loop over list(d) instead.

2. Everyone piled onto one hook: worst-case O(n)

If every key collides into one bucket — from a weak hash or a deliberate hash flooding attack — a hash map degrades into a plain list scan: O(n) per lookup and O(n²) to build. Python prevents crafted string collisions by mixing a random secret at startup; Java turns crowded buckets into balanced trees.

Go deeper: hash flooding math, defenses, and Python's unrandomized ints (Exercise 7)

Sending 100,000 colliding HTTP form fields in one few-MB request triggers 100,000² / 2 ≈ 5 billion comparisons — pinning a CPU core for ~50 seconds. Python defends strings/bytes with randomized SipHash; Java keeps String.hashCode and converts buckets past 8 collisions (in a large table of ≥64 buckets) into balanced trees for O(log n) worst-case lookup.

Python does not randomize integers: an int hashes to itself modulo 2⁶¹ − 1. Every integer of the form k × (2⁶¹ − 1) + 1 (k = 0, 1, 2, …) has hash 1 — triggering O(n²) dict construction, which you'll measure in Exercise 7.

3. When a hash map is the wrong tool

A hash map trades extra memory (empty hooks) and sorted order for O(1) average lookup. (Python's dict remembers insertion order, not sorted order.) Pick another structure when you need: sorted/range queries (use a balanced tree or sorted array), small dense keys (plain array), tight memory (a 10M-name Python set uses ~3× a sorted list of references), or a strict worst-case guarantee with no resize pauses (balanced tree: O(log n) every call).

OperationBestAverageWorstWhy worst happens
Look up, deleteO(1)O(1)O(n)All keys pile into one bucket
InsertO(1)O(1) amortizedO(n)Resize moves all keys, or one-bucket pile-up
Iterate all keysO(n + m)O(n + m)O(n + m)Visits all m buckets, empty or not
Min/max, range, find valueO(n)O(n)O(n)Not sorted by key; values aren't hashed
SpaceO(n)O(n)O(m)Empty slots; peak m if never shrunk

Assumes O(1) hash and equality; for length-k strings, multiply lookup/insert/delete by O(k).

Go deeper: at scale — 100 machines, streams, and concurrency

100 machines (sharding): Splitting keys with hash(key) % N has the exact same problem as resizing: adding one server (N → N+1) remaps almost every key across the network. Consistent hashing moves only ~1/N of keys.

Too big for RAM / streams: Partition keys into k files on disk by hash so identical keys land in the same file, or trade exactness for tiny memory with a Bloom filter (membership) or Count-Min Sketch (counts). For bounded memory, pair a hash map with a doubly linked list (LRU cache).

Concurrency: Concurrent writes and resizes corrupt a plain map. Lock the whole map (simple, serializes traffic), shard locks by bucket stripe (Java's ConcurrentHashMap — see concurrent structures), or run single-threaded (Redis).

In Java, a List hashes by its contents. You use a List as a HashMap key, then append a new item to it. What happens on lookup?

Right. Nothing notifies the map, so the entry stays stranded in its old bucket while lookups hash the new contents and check elsewhere.

Back in the coat room: mutating the list flips its synced name tag from "Sam" to "Max" without moving the coat off hook #2. Lookups for the mutated list check hook #5 (empty). That's why Python bans mutable keys.

An event logger must support two operations: add an event with a millisecond timestamp, and list every event between 9:00 and 9:05. Which structure fits best?

Spot on. A balanced tree finds 9:00 in O(log n) and walks straight to 9:05. Direct addressing by Unix millisecond (~1.7 trillion) would blow up RAM.

A hash map answers exact lookups (9:03:17.042) in O(1), but hashing scrambles timestamps across hooks so range queries need an O(n) scan. Direct addressing by millisecond timestamp needs trillions of slots. A sorted tree keeps timestamps adjacent in order.

8How you use hash maps in interviews

Whenever a brute-force solution has two nested loops where the inner loop just searches for something, a hash map replaces that inner loop with one O(1) lookup — collapsing O(n²) into O(n) at the cost of O(n) memory.

Pattern 1: Seen before (Two Sum)

Before: nested loop — O(n²)

def two_sum_slow(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return (i, j)

After: single pass + map — O(n)

def two_sum(nums, target):
    seen = {}                 # value -> index
    for j, x in enumerate(nums):
        if target - x in seen:
            return (seen[target - x], j)
        seen[x] = j           # store AFTER checking

Pattern 2: Group by a shared fingerprint (Group Anagrams)

Comparing every pair of words costs O(n² · k). Instead, turn each word into an immutable fingerprint that is identical for matching words — tuple(sorted(word)) (O(k log k) per word) or a 26-count tuple from section 3 (O(k)!) — and append to groups[fingerprint]:

groups = {}
for word in words:
    key = tuple(sorted(word))         # "eat" and "tea" both -> ('a','e','t')
    groups.setdefault(key, []).append(word)

Pattern 3: Running totals (Subarray Sum = k)

Checking every slice nums[i:j] costs O(n²). Let total be the sum from index 0 up to now. A slice ending here sums to k whenever an earlier prefix had sum total - k:

Instead of looping over all start points i, look up counts.get(total - k, 0) in O(1) — works even with negative numbers!
counts = {0: 1}                 # empty prefix has sum 0
total = ans = 0
for x in nums:
    total += x
    ans += counts.get(total - k, 0)   # check BEFORE recording total
    counts[total] = counts.get(total, 0) + 1

Pattern 4: Frequency counting. Need "how many times did each item appear?" (Top-k frequent words, valid anagram)? Use collections.Counter(items) — a dict mapping item → count in one O(n) pass.

In two_sum([5, 1], 10), what breaks if you write seen[x] = j before checking if target - x in seen?

Exactly! Checking first guarantees you only pair x with an earlier index (i < j) — same reason subarray_sum_count checks total - k before incrementing counts[total] when k = 0.

Trace j = 0, x = 5 with target = 10: if you store seen[5] = 0 first, then 10 - 5 = 5 immediately finds index 0 — pairing the single 5 with itself! Checking before storing ensures i < j.

9What to say in the interview

If an interviewer asks "Why is a dict lookup O(1), and when isn't it?", hit these five beats in under two minutes:

  1. Array jump + hash: "An array reads any slot in one step via address arithmetic. A hash function turns any key into a number, and hash % m picks its bucket."
  2. Collisions: "Keys inevitably collide. Separate chaining keeps colliding (key, value) pairs in a short per-bucket list and checks keys with ==. (Bonus if probed: Python's dict uses open addressing in a flat array with tombstones for deletes.)"
  3. Load factor & resizing: "A lookup takes about 1 + α steps on a miss where α = n / m. Doubling and rehashing when α passes a limit like 0.75 keeps chains short: one resize is O(n), so inserts are O(1) amortized."
  4. Average vs. worst case: "That's O(1) on average. If keys pile into one bucket, lookups degrade to O(n) — prevented against attackers by randomized hashing (Python's SipHash) or tree bins (Java)."
  5. Trade-off: "You spend extra memory on empty slots and give up sorted order. For range queries, min/max, or strict worst-case bounds, I'd use a balanced tree."

✓What to remember

  1. An array jumps to slot i in one step by arithmetic; a hash map gives that jump to keys of any type.
  2. Direct addressing beats hashing for small, dense keys, but blows up when possible keys are huge.
  3. A hash function must be deterministic, uniform, and fast; hash(key) % m picks the bucket.
  4. Collisions are normal: separate chaining hangs (key, value) pairs on short lists and compares keys with ==.
  5. Bounded load factor (α = n / m) keeps lookups O(1); doubling and rehashing makes inserts O(1) amortized.
  6. Keys must stay immutable while stored, and equal keys must produce equal hashes.
  7. Worst case is O(n) on a one-bucket pile-up (defended by randomized hashing or tree bins).
  8. No sorted order, extra memory, and occasional resize pauses — use a sorted structure for ranges or hard worst-case bounds.

A chained table starts with m = 4 buckets and doubles when α > 0.75. Keys have hashes: A = 2, B = 6, C = 5, D = 10. Insert A, B, C, D in order. Write down the buckets after each insert — and note which keys move when the table doubles to 8.

Answer

Inserting D would give 4/4 = 1.0 > 0.75, so double to m = 8 and rehash: A → 2 % 8 = 2 (stays), B → 6 % 8 = 6 (moves!), C → 5 % 8 = 5 (moves!), then D → 10 % 8 = 2 (shares bucket 2 with A).

3. Find the bug

class User:
    def __init__(self, email): self.email = email
    def __eq__(self, other):
        return isinstance(other, User) and self.email.lower() == other.email.lower()
    def __hash__(self): return hash(self.email)

Which law of the key contract does this break? Give two objects that show it, and fix it.

Answer

4. Trace linear probing & tombstones by hand

An 8-slot linear-probing table receives hashes A = 3, B = 11, C = 4, D = 19, E = 5 in order (hash % 8). Delete B, then look up D. Write the table and every slot the lookup probes.
