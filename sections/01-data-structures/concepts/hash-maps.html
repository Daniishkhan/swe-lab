Hash maps, arrays and strings

Arrays are fast because memory is a numbered street. Hash maps borrow that speed for keys that aren't numbers. Everything else on this page is about what it costs to pretend.

CoreThe one-sentence idea

A hash map turns a key into an array index, so finding a value costs one jump instead of a search. Collisions and resizing are the price, and both are paid in a way that averages out to O(1).

FoundationArrays and strings: the memory underneath

Memory is one long row of numbered bytes. An array is a contiguous run of equal-sized slots, so the address of slot i is pure arithmetic:

address(i) = base + i × slot_size        # one multiply, one add: O(1)

That arithmetic is the whole reason arrays are fast. It is also why inserting in the middle is slow: to keep the slots contiguous, everything after the insertion point shifts one place, which is O(n).

Dynamic arrays (Python list)

When full, allocate a bigger block (roughly 1.125× to 2×), copy everything over, free the old one. A single append can be O(n), but the copies get rarer as the array grows, so append is O(1) amortized.

Strings

In Python, Java, Go and JS, strings are immutable arrays of characters. s += c in a loop builds a new string every time, so the loop is O(n²). Collect the parts in a list and "".join(parts) once.

Cache friendliness

The CPU fetches memory in 64-byte cache lines. Walking an array uses every byte of each line; chasing pointers (linked lists, chained buckets) wastes most of each fetch. Same big-O, very different constant.

WhyThe problem a hash map solves

You have a million users and you want to look one up by email. Your options without hashing:

  • Unsorted list: scan everything. O(n) per lookup.
  • Sorted list + binary search: O(log n) lookups, but every insert shifts elements. O(n) per insert.
  • Balanced tree: O(log n) for both. Good, and it keeps keys ordered, but ~20 pointer hops for a million keys.

Arrays already give O(1) access, but only by integer position. The question a hash map answers is: can we turn an email into a position?

Build itFrom first principles, in five steps

1. Direct addressing

If keys are small integers, use them as indexes. Counting letters in a word? An array of 26 counters, indexed by ord(c) - ord('a'). Perfect O(1), no collisions. It falls apart when the key space is huge (all possible emails), because you can't allocate an array that big.

2. Squash the key space with a hash function

A hash function maps any key to a big integer, deterministically. Then index = hash(key) % m squashes it into an array of m buckets. Good hash functions spread keys evenly, so every bucket is equally likely.

3. Accept that collisions will happen

More possible keys than buckets means two keys must share a bucket sometimes (pigeonhole principle). It happens sooner than intuition says: with 365 buckets, 23 random keys give a 50% chance of at least one collision. That is the birthday paradox, and it means collision handling is not an edge case, it is the main case.

Separate chaining

Each bucket holds a small list. Colliding keys go in the same list. Simple; deletion is easy. Java's HashMap does this and even turns long chains into small trees.

Open addressing

One key per slot. On collision, probe other slots (next one over, or a pseudo-random sequence) until you find a free one. Better cache behavior, but deletion needs "tombstones". Python's dict does this.

4. Keep buckets short: load factor and resizing

The load factor α = n / m is the average number of keys per bucket. Expected lookup cost is about 1 + α. So when α passes a threshold (0.75 in Java, about 2/3 in Python), allocate an array twice as big and rehash every key, because hash % m changes when m changes.

5. Why doubling makes resizing "free"

A resize costs O(n), but if you double each time, the total copying across all resizes up to n items is n/2 + n/4 + n/8 + … < n. Spread over n inserts, that is O(1) extra per insert. Grow by a constant (say +10 slots) instead and you resize every 10 inserts: O(n²) total. Geometric growth is the trick behind every amortized O(1) container.

IntuitionAnalogy: the coat check

A coat check has numbered hooks. The attendant doesn't search for your coat; your ticket number is the hook number. That's the hash.

  • Collision: two tickets map to the same hook. Either hang both coats on that hook (chaining) or walk to the next free hook (open addressing).
  • Load factor: when the room is 75% full, the attendant spends more time walking past occupied hooks.
  • Resize: move to a room with twice the hooks. Every coat must be re-hung, because hook numbers depend on the room size. It's a painful afternoon, but it happens rarely.

Where it breaks down: a real attendant can see the whole room. A hash map only "sees" the one bucket the hash points to, which is exactly why lookups stay O(1).

InterviewWhat a senior answer adds

Almost every coding round uses a hash map somewhere. Nobody gets credit for using one. The credit goes to saying precisely what it costs. When someone asks "why is a dict lookup O(1)?", a senior answer covers:

  • "Average, not worst case." Name the assumption: the hash spreads keys evenly.
  • Amortized resizing and its operational cost: a resize stalls one request. Redis avoids that with incremental rehashing: it keeps two tables and moves a few buckets on each operation.
  • Hash flooding: if attackers can choose keys and your hash is predictable, they can force O(n²) behavior and take down a server. That is why Python randomizes string hashes per process (SipHash, PYTHONHASHSEED).
  • The key contract: keys must be immutable, and equal objects must have equal hashes. Break it and entries become unfindable.
  • When not to use one: you need ordering or range scans, memory is tight (each entry carries real overhead), or the key space is tiny and dense (use an array).
  • Concurrency: a shared map needs a lock. Java's ConcurrentHashMap splits it into independently locked segments, so writers rarely contend.
TrapsCommon mistakes
  • Using a mutable object (a list) as a key, or mutating a key object after inserting it.
  • Overriding __eq__ without __hash__. Python then makes the class unhashable; in Java you silently get broken lookups.
  • x in some_list inside a loop. That's O(n) per check. Build a set first.
  • String concatenation in a loop (O(n²)). Use join.
  • Relying on iteration order. Python dicts keep insertion order (since 3.7); Java's HashMap and Go maps don't (Go deliberately randomizes it).
  • Forgetting that float('nan') != float('nan'), so NaN keys behave strangely.
RecallCheck yourself
Why double the table instead of adding a fixed number of buckets?

Doubling makes total resize work a geometric series bounded by about 2n, so it's O(1) amortized per insert. Adding a constant k resizes every k inserts, and each resize copies everything, so the total is O(n²/k).

In linear probing, why can't you just empty the slot on delete?

A later key may have probed past that slot to find its home. Emptying the slot breaks its probe chain, so lookups would stop early and miss it. A tombstone says "keep probing, but this slot can be reused on insert".

Why does the hash map have to rehash every key when it grows?

The bucket is hash(key) % m. Change m and almost every key's bucket changes. (Consistent hashing in chapter 2 is the trick for when moving keys is expensive, like across servers.)

You need "top 10 keys by value, updated live" and "lookup by key". Is a hash map enough?

No. Lookup by key is the hash map; ordering by value needs a second structure (a heap or a sorted structure) kept in sync. Combining structures like this is the core move behind LRU caches (hash map + linked list).
