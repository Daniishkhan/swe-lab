Almost every coding interview uses a hash map somewhere: a Python dict or set. Nobody gets credit for using one. The credit goes to knowing why it's fast, when it stops being fast, and what it costs. This chapter builds a hash map from nothing, one fix at a time, so every part of it has a reason you can say out loud.

By the end you'll be able to

  1. Explain why reading slot i of an array is one step, and why that's the whole trick.
  2. Build a hash map from first principles: hash function, buckets, collisions, load factor, resizing.
  3. Compare chaining and open addressing, including why deleting needs "tombstones".
  4. Say what makes a valid key, and what breaks when you get it wrong.
  5. Explain when "O(1)" turns into O(n), including on purpose, by an attacker.
  6. Spot hash map problems in interviews, and know when a hash map is the wrong tool.

How to read this: go top to bottom. Answer each quick check before reading on; a wrong answer gets the idea explained a different way. Grey "Go deeper" boxes are optional on a first read. This chapter leans on How fast is your code?: Big-O, the doubling test, and amortized cost.

1The problem: is this name taken?

You run sign-ups for a service with 10 million users. Every time someone picks a username, the server must answer one question: is this name already taken?

The names sit in a Python list. name in names checks them one by one. When the name is new (the common case), it has to look at all 10 million. Measured on a laptop, that takes about 70 milliseconds.

That sounds quick, until 1,000 people sign up in the same second. Now the server needs 1,000 × 70 ms = 70 seconds of work every second. It falls further behind with every sign-up.

Put the same 10 million names in a Python set and the same check takes about 30 nanoseconds. That's more than two million times faster. And it stays about 30 nanoseconds whether the set holds ten names or ten million.

How can a check not depend on how many names there are? It sounds like magic. It isn't. It's one fact about computer memory, plus about five clever fixes, each one patching the hole left by the one before. By the end of this chapter you'll have built all of them.

2Memory is a numbered street

Start with the one fact everything else rests on.

Picture a very long street of identical mailboxes, numbered 0, 1, 2, 3 and so on, all the same width and all in a row. If someone says "go to box 4,512", you don't walk past the first 4,511 boxes checking numbers. You know each box is, say, 30 cm wide, so box 4,512 is 4,512 × 30 cm from the start. You go straight there.

Computer memory (RAM) is that street. Every byte has a number, called its address. The hardware can read any address in about the same time, near or far. (That's a simplification: the CPU keeps recently used memory, and its neighbors, in a small fast cache, so nearby reads can be about 100× cheaper. Section 8 uses this.) An array is a run of equal-sized slots side by side on that street. To find slot i, the computer does one multiply and one add:

address of slot i  =  start  +  i × slot size

 slot:     0      1      2      3      4
        ┌──────┬──────┬──────┬──────┬──────┐
        │  17  │  42  │   8  │  99  │   3  │
        └──────┴──────┴──────┴──────┴──────┘
 address: 1000   1008   1016   1024   1032      (8-byte slots, start = 1000)

 slot 3 → 1000 + 3 × 8 = 1024. One step, whatever the array's length.

That's why nums[3] is O(1): it's arithmetic, not a search. (A Python list stores 8-byte references to its items in such a block, so the rule holds for lists too.)

The catch: arithmetic only helps if you already know the slot number. Our sign-up check knows a name, not a slot. With only an array, here are the two options:

ApproachCheck one nameAdd one nameWith 10 million names
Unsorted list, scan itO(n)O(1), append at the end10 million comparisons per check
Sorted list, binary searchO(log n)O(n), shift everything after it24 comparisons per check, but about 5 million items moved per insert

The sorted list is like an alphabetized bookshelf. Finding a book is fast: open to the middle and keep halving. But slotting a new book in under "M" means sliding every book after it one place over. On average that's half the shelf. Arrays have no gaps, so inserting in the middle always shifts.

Strings are arrays too

A string is an array of characters. That's why s[5] is O(1), but comparing two strings of length k takes up to k steps, one character at a time. In Python (and Java, Go, JavaScript) strings are also immutable: they can't change after they're made. s += "x" builds a brand-new string and copies everything over, so doing it in a loop is O(n²); collect the pieces in a list and "".join them once (the complexity chapter has the details). Both facts come back when strings become keys: hashing one costs k steps, and immutability is exactly what makes a string a safe key (section 9).

An array reads slot i in one step because the slot's address is arithmetic. The whole game of this chapter is turning a key (like a name) into a slot number, so we get that one-step jump for keys that aren't numbers.

You keep the 10 million names in a sorted list and use binary search. Lookups take 24 comparisons. Why isn't that good enough for sign-ups?

Right. Lookups are fine; the inserts kill it. Sign-ups are a mix of "check" and "add", so we need both to be fast.

Think about what a sign-up does: it checks the name, and if it's free, adds it. Checking takes about log₂(10,000,000) ≈ 24 comparisons, which is quick, and alphabetical order works fine for binary search on strings. Adding is the problem. The new name has to go in its sorted place, and an array has no gaps, so every name after that spot slides over by one. That's about 5 million moves per sign-up.

3Use the key as the address

Here's a bold idea. What if the key itself were the slot number?

Say you want to count the letters in a book. There are only 26 lowercase letters. Make an array of 26 counters. For the letter c, use slot ord(c) - ord('a'): 'a' is slot 0, 'b' is slot 1, … 'z' is slot 25. Seeing a letter means one jump and one add. No searching at all, and no two letters ever share a slot.

counts = [0] * 26
for c in "banana":
    counts[ord(c) - ord("a")] += 1   # the letter IS the address
# counts[0] == 3 ('a'), counts[1] == 1 ('b'), counts[13] == 2 ('n')

This is called direct addressing: the key is used directly as the array index. It's perfect when the keys are small whole numbers packed close together: letters, ages (0 to 150), days of the year, or user ids that run from 0 to 10 million (a bytearray of 10 million true/false flags is about 10 MB, which is fine).

Where it breaks

Now try it for usernames. Turn a name into a number by treating its letters like digits: with 37 possible characters (a–z, 0–9, underscore), a 20-character name is a 20-digit number in base 37. The biggest such number is about 37²⁰ ≈ 2 × 10³¹. That's how many slots you'd need.

Picture a hotel with a room for every name anyone could ever pick. It has 2 × 10³¹ rooms. Your 10 million guests fill a fraction of them so tiny it has 24 zeros after the decimal point (about 4 × 10⁻²⁵). Even at one bit per room, the hotel needs more memory than every computer on Earth combined. 64-bit ids have the same problem: 2⁶⁴ ≈ 1.8 × 10¹⁹ slots.

So direct addressing fails for one reason: the number of possible keys is astronomically bigger than the number of keys you actually have.

Direct addressing (key = index) gives perfect one-step lookups, but needs one slot per possible key. That only works when the possible keys are few and dense. For names, emails or big ids we need to squash a huge key space into a small array.

Which of these would you sensibly store with plain direct addressing (an array indexed by the key)?

Yes. There are only 366 possible days, so an array of 366 counters covers every possible key, with no waste worth mentioning.

Ask "how many possible keys are there?", not "how many keys do I have?". There are 10 billion possible 10-digit phone numbers, so an array for 2,000 employees would be 99.99998% empty: with an 8-byte record per slot, that's 80 GB to hold 16 KB of data. Emails are even worse: unlimited length, so the possible keys are endless. Days of the year: only 366 possible keys. That's the one an array can index directly.

4Squash any key into a slot: hashing

Picture a coat check at a theater. It has 100 hooks. You hand over your coat and get a ticket with a number from 0 to 99. When you come back, the attendant doesn't search the room. Your ticket number is the hook. Millions of different people could visit; the room still has just 100 hooks, because tickets are about hooks, not about people.

Where the analogy breaks: a real attendant hands out a fresh ticket for a free hook, and you must keep it. A hash is a ticket printed from the coat itself: show the same coat again and you get the same number, so you never need to keep the ticket. The price is that two different coats can print the same number. That's section 5.

A hash function is the ticket machine. It takes any key (a name, an email, a tuple) and turns it into a number. Then we squash that number into the array's range with the remainder: slot = hash(key) % m, where m is the number of slots. Each slot is called a bucket, and the whole array is the hash table.

A hash function you can run by hand

Here is a real one (it's what Java uses for strings). Start at 0. For each character, multiply what you have by 31 and add the character's code (ord):

def toy_hash(s):
    h = 0
    for ch in s:
        h = h * 31 + ord(ch)   # mix in each character, in order
    return h
stepcharacterordh = h × 31 + ord
1c990 × 31 + 99 = 99
2a9799 × 31 + 97 = 3,166
3t1163,166 × 31 + 116 = 98,262

With 8 buckets, "cat" goes to bucket 98,262 % 8 = 6. Every time, on every run. "dog" hashes to 99,644, so bucket 4. "act" hashes to 96,402, so bucket 2.

Why multiply by 31 at all? Try the lazy version: just add up the character codes. "cat", "act" and "tac" all add up to 312, so all three land in the same bucket. Adding ignores order. Multiplying before each add makes earlier characters count differently from later ones, so rearranged letters give different numbers.

What a good hash function needs

  1. Same key, same number, for as long as the table exists. If "cat" gave 6 when you stored it and 3 when you looked it up, you'd look on the wrong hook. This is the one rule that can never bend. (Python's string hashes change between runs, as section 10 explains, so never save hash() values to disk or send them to another process. Use a stable hash like hashlib for that.)
  2. Spread keys evenly. Different keys should look random across the buckets, so no bucket gets crowded. The "add the letters" hash fails this.
  3. Fast. Hashing a string of length k touches all k characters, so it costs O(k). For short keys that's tiny. For a 1 MB string it's a million steps, which is why Python remembers (caches) a string's hash inside the string after the first time.

One trap in other languages: Java's and C's % keeps the sign, so a negative hash gives a negative slot. Even Math.abs(hash) % m fails for one value (Math.abs(Integer.MIN_VALUE) is still negative), which is why Java masks the sign bit off instead. Python's % always returns 0 to m − 1, so this never shows up there.

Notice the "O(1)" of a hash map quietly assumes hashing the key takes constant time. With long keys, a lookup is really O(k). Saying that in an interview is a small senior signal.

A hash function turns any key into a number, the same number every time, spread evenly. hash(key) % m squashes it into one of m buckets. It's a coat-check ticket: it tells you which hook to go to without searching.

A teammate writes a "hash" that returns a random number each time it's called, because "random numbers spread perfectly evenly". What goes wrong?

Exactly. Insert "cat" and it lands in bucket 6. Look it up and the "hash" now says bucket 3, which is empty: "cat" seems to be missing. Same key, same number is the rule that can't bend. Even spread only matters once that holds.

Speed isn't the issue (random numbers are cheap). Act it out at the coat check: you hand over your coat and get ticket 6. When you come back, the machine prints you a new random ticket, 3. The attendant goes to hook 3, finds nothing, and says your coat isn't here. A hash is only useful if the same key gives the same number every time. Spreading evenly is the second rule, not the first.

5Collisions happen early: chaining

We squashed a huge number of possible keys into m buckets. So some different keys must share a bucket. That's the pigeonhole principle: put 9 pigeons into 8 holes and at least one hole has two. When two different keys land in the same bucket, it's called a collision.

Look back at our toy hash: "tac" hashes to 114,582, and 114,582 % 8 = 6. That's the same bucket as "cat". Our very first handful of keys already collided.

Sooner than you'd think

You might hope collisions are rare while the table is mostly empty. They're not. Think of birthdays: in a room of just 23 people, there's a better than 50% chance two share a birthday, even though there are 365 days. That's the birthday paradox. It's not about your birthday matching someone; it's about any pair matching, and 23 people make 253 pairs.

The pattern: collisions start after about √m keys (the square root of the number of buckets), long before the table is full. So collisions aren't an edge case to handle someday. They're the normal case, and the design has to plan for them from the start.

The fix: each bucket holds a short list

Back to the coat check: when two tickets say hook 6, hang both coats on hook 6. To find yours, go to hook 6 and read the name tag on each coat until it's yours.

In a hash table, each bucket holds a small list of (key, value) pairs. This is called separate chaining, and each list is a chain.

  • Insert: hash the key, go to its bucket, and walk the chain. If the key is there, replace its value. If not, add the pair to the chain.
  • Look up: hash the key, go to its bucket, and walk the chain comparing each stored key with ==.

That's why the table must store the key, not just the value. "cat" and "tac" share bucket 6; the only way to tell them apart is to compare the keys themselves.

Explain it another way: count the handshakes

A collision isn't one key against the table; it's any pair of keys landing together. Picture every key shaking hands with every other key. 10 keys make 45 handshakes, 40 keys make 780, 100 keys make 4,950. Each handshake is a small, independent chance (1 in m) of a shared bucket.

With 1,000 buckets, 38 keys already make 703 handshakes, each with a 1-in-1,000 chance. That's like rolling a 1,000-sided die 703 times and hoping for no 1s. The keys grow slowly, but the pairs grow like the square of the keys, which is why collisions arrive near √m.

Six inserts and three lookups in a table of 8 buckets, using the toy hash from section 4. Step through it and count the == comparisons each lookup does. Notice that a lookup only ever looks inside one bucket.

Collisions are guaranteed and start early (after about √m keys). Chaining handles them: each bucket keeps a short list of (key, value) pairs, and a lookup walks only its own bucket's list, comparing keys with ==.

You put 5 keys into an empty table with 8 buckets, using a good hash. What's the chance at least two land in the same bucket?

Yes, 79%. The first key can go anywhere. The second avoids it with chance 7/8, the third 6/8, the fourth 5/8, the fifth 4/8. Multiply: 7/8 × 6/8 × 5/8 × 4/8 ≈ 0.21 chance of no collision, so 79% chance of at least one.

Work it out one key at a time, asking "does it miss all the buckets already used?". Key 2 misses key 1's bucket with chance 7/8. Key 3 must miss two used buckets: 6/8. Key 4: 5/8. Key 5: 4/8. All of that has to happen: 7/8 × 6/8 × 5/8 × 4/8 ≈ 0.21. So there's a 79% chance of at least one collision. Many keys means many pairs, and any pair can collide.

Go deeper: why √m, and why chains stay short

With k keys there are k(k−1)/2 pairs, and each pair collides with chance 1/m. Expect about one collision when k²/2 ≈ m, so k ≈ √(2m). The exact 50% point is about 1.18√m.

If you put n keys into n buckets at random, about 37% of buckets end up empty (that's 1/e) and the longest chain is surprisingly short. It grows like log n / log log n. In a quick simulation with a million keys in a million buckets, the longest chain was 8. So "average chain length 1" really does mean almost every lookup touches one or two keys.

6Load factor: how full is too full

Chaining keeps working however many keys you add. But it doesn't stay fast.

Picture a supermarket with 10 checkout lanes. If 10 shoppers arrive, most lanes have one person and you walk right up. If 1,000 shoppers arrive, every lane has about 100 people, and you wait behind all of them. The number of lanes didn't change. The ratio of shoppers to lanes did.

Now with real numbers. Put our 10 million names into a table with only 1,000 buckets. Each chain holds about 10,000 names. Checking a new name means walking its whole chain: 10,000 comparisons. That's 1,000 times better than the plain list, but nowhere near one step. We've built a list cut into 1,000 pieces.

The ratio that decides everything is called the load factor, written α (the Greek letter alpha):

α = n / m = keys ÷ buckets

It's the average chain length. With a good hash:

  • looking up a key that isn't there walks a whole chain: about 1 + α steps (1 to find the bucket, α keys to compare);
  • looking up a key that is there stops halfway on average: about 1 + α/2 steps.

So the speed of a hash table depends only on α, not on n. Keep α below some small constant like 1, and every lookup is O(1) on average, whether there are ten keys or ten million. That's the answer to section 1's puzzle.

One more thing the figure below shows. When m is a power of two, like 16, hash % 16 keeps only the last 4 binary digits of the hash, just as 123,456 % 100 keeps only the last two decimal digits, 56. Tables like power-of-two sizes because that remainder is one fast bit-mask. The catch: the bucket then depends on the last few bits alone, so keys whose last bits are all the same (like multiples of 16) all land together. Some tables use prime sizes instead, which mixes in every digit but costs a slower division.

The load factor α = n/m is the average chain length. Lookup cost is about 1 + α, so it depends on how full the table is, not how big. Keep α bounded and lookups stay O(1) on average.

A chained table has 1,000,000 keys in 1,000 buckets, with a good hash. About how many key comparisons does looking up a missing key take?

Right. α = 1,000,000 / 1,000 = 1,000 keys per chain, and a missing key has to be compared against its whole chain. O(1) only holds while α stays small. The next section is how real tables make sure it does.

Picture the checkout lanes: 1,000,000 shoppers, 1,000 lanes, so about 1,000 per lane. A missing key goes to one bucket (not all of them, so not a million), but it must compare against every key in that bucket to be sure it's absent. That's about 1,000. "Hash maps are O(1)" is only true when the table keeps the keys-per-bucket ratio small.

7Resizing: growing without losing O(1)

We don't know in advance how many keys are coming. So the table starts small and grows. The rule is: when adding a key would push α past a limit (Java uses 0.75), make a bigger table, about twice the size, and move everything over.

Why every key has to move

You can't just copy the buckets across in order. A key's bucket is hash(key) % m, and m just changed. "dog" was in bucket 99,644 % 8 = 4. In a table of 16, it belongs in 99,644 % 16 = 12. Copy the old buckets over unchanged and a later lookup for "dog" would go to bucket 12 and find nothing.

Not every key moves. "cat" (98,262) and "tac" (114,582) both stay in bucket 6, because both numbers leave remainder 6 when divided by 16 as well. When a power-of-two table doubles, each key either stays at slot i or moves to exactly i + m (the old size). Which one depends on a single binary digit of its hash: the one that the new, bigger mask lets through. On average half the keys move. Java's HashMap uses this to split each bucket into a "stay" list and a "move" list without recomputing any remainders.

So a resize rehashes every key: work out its new bucket and put it there. It's the coat check moving to a room with twice the hooks: every ticket number changes, so every coat gets re-hung.

Doesn't that make inserts slow?

One resize touches every key, so that one insert is O(n). But resizes are rare, and they get rarer as the table grows. This is exactly the amortized argument from the complexity chapter. Here are the real numbers for 1,000 inserts, starting with 8 buckets and growing at α = 0.75:

If you grew by a fixed amount instead (say, 8 more buckets each time), you'd resize every few inserts and move everything each time: O(n²) total. Growing by a multiple is what keeps it constant.

Explain it another way: count backwards from the last resize

Look at the table right after its last resize, holding about n keys. That resize moved every key: about n. The one before moved n/2, the one before that n/4, and so on. Add them up: n + n/2 + n/4 + … never reaches 2n. Each resize moves about as many keys as all the earlier ones combined, so the whole history costs less than two trips through the keys. Spread over n inserts, that's under two moves each.

When α passes a limit, the table grows by a multiple (usually 2×) and rehashes every key, because each key's bucket depends on m. One insert pays O(n), but the total over n inserts stays under about 2n moves: amortized O(1).

When the table doubles from 8 to 16 buckets, why can't it copy bucket 0 to bucket 0, bucket 1 to bucket 1, and so on?

Right. Lookups in the new table compute hash % 16. A key sitting where hash % 8 put it may be in the wrong place for that, and would never be found.

Try one key: "dog" hashes to 99,644. In 8 buckets: 99,644 % 8 = 4. In 16 buckets: 99,644 % 16 = 12. If we copied bucket 4 to bucket 4, "dog" would sit in 4, but every future lookup would compute 12 and look there. The key would be lost. The bucket number depends on m, so changing m means recomputing every key's bucket.

Go deeper: the latency spike, and how real systems avoid it

Amortized O(1) is a promise about the total. The one unlucky insert that triggers a resize of a 10-million-key table still pays for 10 million moves, maybe a second of work, while that request waits. For a web service, that's a p99 latency spike.

Redis avoids it with incremental rehashing: it keeps the old and new tables side by side and moves a few buckets on every operation (and some more in the background). Lookups check both tables until the move is done. No single request pays for the whole move.

Other common answers: pre-size the table when you know roughly how many keys are coming (Java's new HashMap<>(expected)), and remember that most tables never shrink. Delete 9 million of 10 million keys and the table stays big, which wastes memory and makes iterating slow, since iteration walks every bucket: O(n + m), not O(n).

8Open addressing and the tombstone problem

Chaining needs a separate little list per bucket, and each list item lives somewhere else in memory. There's another way that keeps everything in the one array: open addressing. Each slot holds at most one key. Python's dict and set work this way.

Picture a parking lot where your ticket says "spot 6". If spot 6 is taken, you try spot 7, then 8, and park in the first free one. To find your car later, start at spot 6 and walk forward until you see it. If you reach an empty spot first, your car isn't in the lot: if it were, you'd have parked it there or earlier.

That's linear probing. Each slot you look at is a probe. "Next slot" wraps around from the end of the array to the start.

Why it needs a lower load factor

Parked cars clump together. A car that finds its spot taken parks just past the clump, so the clump grows, and a bigger clump catches even more cars. This is called clustering. It means the cost grows much faster than α, and explodes near full. The expected number of probes for linear probing:

Explain it another way: a traffic jam

A short jam on a highway is easy to pass. But each car that arrives at the back of the jam stops and makes it longer, and a longer jam catches more arriving cars. Two jams that grow into each other become one huge jam. A cluster in linear probing works the same way: any key whose home slot is anywhere in the cluster joins the end of it. So big clusters grow faster than small ones, and the cost rises much faster than the table fills.

The textbook fixes spread out the walk: quadratic probing tries slots 1, 4, 9, 16 … away from home, and double hashing uses a second hash to pick the step size, so two keys with the same home take different paths. Python's scrambled probe order (see "Go deeper" below) is in the same spirit.

That's why open-addressing tables resize earlier than chaining ones. Python's dict grows at about 2/3 full. (With chaining, α can go past 1 and things just get gradually slower; with open addressing, α can never pass 1, since each slot holds one key.)

Deleting: the hard part

Say "cat" wants slot 6 and gets it. Then "tac" also wants slot 6, finds it taken, and parks in slot 7. Now delete "cat" by emptying slot 6. Look up "tac": start at slot 6, find it empty, and stop. "Empty means not here," so "tac" looks missing, even though it's sitting in slot 7.

The fix: deleting leaves a marker, called a tombstone, that says "something used to be here, keep walking". Lookups walk past tombstones. A real empty slot is still the only thing that ends a search.

Inserts may reuse a tombstone's slot, but carefully. Say "cat" is deleted (slot 6 is a tombstone) and you insert "tac" again to change its value. If you drop "tac" into the first tombstone you meet, you now have two copies: the new one in slot 6, the old one still in slot 7. An insert must keep walking until it finds the key or an empty slot, and only then use the first tombstone it passed.

Tombstones have a cost too: they don't hold keys, but they still make searches walk further. A table that sees lots of inserts and deletes can fill up with them. So tables count tombstones toward the "how full" limit. When that limit is hit, the table is rebuilt: only live keys are re-inserted, and the new size is chosen from the live keys. A table that's mostly tombstones is rebuilt at the same size, clean, rather than doubled for no reason.

Open addressing keeps one key per slot and walks to the next slot on a collision. An empty slot ends a search, so deleting must leave a tombstone instead of an empty slot, or keys further along the walk get lost.

With linear probing, "tac" sits in slot 7 because "cat" had slot 6. You delete "cat" by setting slot 6 back to empty. What happens on the next lookup of "tac"?

Right. The search rule "empty means it isn't here" is what makes misses fast, and it's exactly what deleting breaks. A tombstone in slot 6 would say "keep walking".

Follow the lookup step by step, the way the computer does. "tac" hashes to slot 6. The search looks at slot 6: empty. The rule says that if "tac" were in the table, it would have parked here or at a later slot before any gap, so an empty slot means "not here", and the search stops. It never gets to slot 7. Nothing moves keys around on its own. That's why a delete must leave a tombstone, which tells the search to keep going.

Go deeper: what Python's dict actually does

CPython's dict uses open addressing, but not plain "next slot". It probes in a scrambled order, roughly i = (5·i + 1 + perturb) % m, where perturb starts as the full hash and shifts right by 5 bits each step. (Python's set first checks a few neighboring slots, for the cache, then scrambles.) Every bit of the hash eventually affects where it looks, so keys that only differ in their high bits still spread out.

Since Python 3.6, a dict is two arrays: a small sparse array of slot indexes, and a dense array of entries in insertion order. That's why dicts remember insertion order (guaranteed since 3.7) and why they use less memory than before. The table grows when it's about 2/3 full, to roughly 3× the number of live keys rounded up to a power of two.

Newer designs push open addressing further. Robin Hood hashing lets a key that's far from home take a slot from one that's close to home, which keeps all walks short. Swiss tables (Google's Abseil, Rust's HashMap, Go 1.24 maps) keep a tiny summary byte per slot and check a group of 8 or 16 slots at once, often with a single CPU instruction.

9The key contract

The whole design so far rests on one promise: a key gets the same bucket on the way in and on the way out. Two habits break that promise, and both are classic interview questions.

Rule 1: keys that are equal must hash the same

A lookup goes to bucket hash(key) % m, then compares with ==. Say two keys are equal (a == b) but have different hashes. Store under a, look up with b: you go to a different bucket, and never even get to the == check. The reverse is fine: two unequal keys may share a hash. That's just a collision, and == sorts it out.

Python enforces part of this. If your class defines __eq__ but not __hash__, Python sets __hash__ to None and the class can't be a key at all. Java doesn't: override equals without hashCode and lookups quietly fail.

Rule 2: a key must not change while it's in the table

Back to the coat check. You hand in your coat, get ticket 6, and then scribble the ticket into a 9. The coat is on hook 6, but you'll ask for hook 9. The coat is still in the room, but nobody can find it.

Here's that in code. The key is an object whose hash depends on a field that can change:

class Point:
    def __init__(self, x, y): self.x, self.y = x, y
    def __eq__(self, o): return (self.x, self.y) == (o.x, o.y)
    def __hash__(self): return hash((self.x, self.y))

p = Point(1, 2)
seen = {p}
p.x = 99                  # the key changes while it's inside the set
print(p in seen)          # False: we look in the bucket for (99, 2)
print(Point(1, 2) in seen)  # False: right bucket, but the stored key is now (99, 2)

The entry isn't deleted. It's in the set, but neither the old value nor the new one can reach it. That's why Python refuses to hash lists, sets and dicts (they can change) but hashes tuples, strings, numbers and frozensets (they can't). Use a tuple, like (x, y), when you want a composite key.

A Python gotcha that follows from rule 1: 1 == 1.0 == True, so they must hash the same, and they're the same key. {1: "a", True: "b", 1.0: "c"} is {1: "c"}. Related: adding or removing keys while looping over a dict raises RuntimeError, because a resize could reshuffle what you're walking over. Loop over list(d) instead.

One odd case to know: float("nan") != float("nan"), so NaN is never equal to itself. Python's dict checks "is it the very same object?" before ==, so the same NaN object can be found, but a freshly made NaN never can.

A key must keep one promise: equal keys have equal hashes, and the key never changes while stored. Break either and entries become unfindable, without any error. That's why dict keys must be immutable: strings, numbers, tuples, frozensets.

You use a list as a key in a language that allows it, and later append to the list. What's the most likely result?

Right. Nobody tells the table the key changed, so the entry stays in its old bucket while every lookup computes the new hash. This is exactly why Python makes lists unhashable.

The table only computed the bucket once, when you inserted. It has no idea you appended later, so it can't move anything. Now a lookup hashes the list's current contents and lands in a different bucket. Being the "same object" doesn't help, because the table never gets far enough to compare objects: it looks in the wrong place first. It's the scribbled coat-check ticket: the coat is in the room, on a hook nobody will visit.

10When O(1) becomes O(n)

Every "O(1)" in this chapter came with a quiet condition: with a good hash, keys spread evenly. What if they don't?

Worst case, every key lands in the same bucket. Then the table is one long chain (or, with open addressing, one long cluster). Each lookup is O(n), and inserting n keys is 1 + 2 + … + n = O(n²). The table is a list again, with extra steps.

By accident

Bad hashes happen. The "add up the letters" hash puts every anagram together. A table of 16 buckets keeps only the last 4 bits of the hash, so keys that are all multiples of 16 (try it in the section 6 figure) all land in bucket 0. Real libraries defend against this by scrambling the hash before using it: Java mixes the high bits into the low bits, and Python's probe order uses every bit.

On purpose: hash flooding

Now imagine an attacker who knows your hash function. Web servers often parse a request's form fields into a hash map. The idea was published in 2003 (Crosby and Wallach). In 2011, researchers showed that for most popular web languages (PHP, Java, Python, Ruby, ASP.NET and more), you could compute thousands of field names that all collide. A request with about 100,000 such fields makes the server do around 100,000²/2 = 5 billion key comparisons. One few-megabyte request could tie up a CPU core for close to a minute. That attack is called hash flooding.

The fix was to make the hash unpredictable. Python picks a random secret at startup and mixes it into every string hash (using a function called SipHash), so hash("cat") changes from one run of Python to the next, and an attacker can't precompute collisions. Java took a different route: when a bucket's chain gets long (8 entries), it turns that chain into a balanced tree, so the worst case per lookup becomes O(log n) instead of O(n). A third, blunt fix ships everywhere too: cap the input, such as limiting how many form fields one request may have (PHP's max_input_vars, Tomcat's maxParameterCount).

OperationAverageWorstWhy the worst case happens

Python changes hash("cat") every time the program starts. What problem does that solve?

Right. Within one run, the hash is still fixed (same key, same number), so the table works normally. Across runs it's a secret, so nobody can precompute a pile of colliding keys and flood your server.

Think about who it's hiding from. Inside one run, "cat" hashes the same every time, as it must, and a random secret doesn't make the spread any more even than a good fixed hash would. Equal strings always hash the same; that's the key contract. What changes is that the hash is different on every run, so someone outside can't compute in advance 100,000 field names that land in one bucket. It's a defence against hash flooding.

Go deeper: integers are still predictable

Python only randomizes the hashes of strings and bytes. Integers hash to themselves, reduced modulo 2⁶¹ − 1, so hash(2**61) == hash(1). Every number of the form k·(2⁶¹ − 1) + 1 has hash 1. Building a dict from a few thousand such keys is hundreds of times slower than from the same number of ordinary ints, and the gap doubles every time n doubles: O(n²) against O(n). If untrusted input becomes integer keys, cap the input size or convert the keys to strings.

Java's version of the story: String.hashCode (our toy hash) is not randomized at all, which is why Java added tree bins. A bucket only becomes a tree once it holds 8 entries and the table has at least 64 buckets (below that, Java just resizes), and the O(log n) guarantee only holds if the keys are Comparable.

Also: hash(-1) == hash(-2) == -2, because CPython uses −1 internally to mean "error".

11Hash maps as a tool, and when not to use one

In interviews, the hash map is usually the trick that turns O(n²) into O(n). The move is always the same: spend memory to remember something, so you never have to search for it again. It shows up in four shapes:

PatternThe question you ask the mapClassic problem
Seen it?"Have I met the partner of this item before?"Two Sum: for each x, look for target − x among the items already passed
Group by a label"Which group does this item belong to?" The label is a key that's equal for things that belong together.Group Anagrams: the label is the word's letters, sorted ("eat" → "aet")
Count"How many times so far?"First unique character, top-k frequent words (collections.Counter)
Running total"How many earlier prefixes had exactly this sum?"Count subarrays that sum to k, even with negative numbers

The tell in a problem statement: a brute force that loops over pairs, where the inner loop is really just searching for something specific. Replace that search with a lookup.

When it's the wrong tool

  • You need order. "Smallest key", "next key after x", "all keys between a and f": hashing scrambles order on purpose, so these are O(n). Use a sorted structure (a balanced tree, a sorted list with binary search, a skip list).
  • The keys are small and dense. Letters, ages, ids from 0 to n: a plain array (direct addressing from section 3) is faster and smaller.
  • Memory is tight. Hash tables keep empty slots on purpose. A Python set of our 10 million names has a 268 MB table, three times the list's 89 MB array of pointers. The strings themselves (about 530 MB) are shared, so the whole set costs about 30% more memory than the list. At a billion keys, consider a sorted file, a database index, or a Bloom filter (an approximate set, coming later in chapter 1).
  • You need a guaranteed worst case. A hard real-time system can't accept a rare O(n) resize. A balanced tree is O(log n) every time.

Reach for a hash map when a brute force keeps searching for something: remember it instead. Skip it when you need order or ranges, when keys are small dense integers, or when memory or worst-case time is what matters.

You need to support "add an event with a timestamp" and "list all events between 9:00 and 9:05". Which structure fits best?

Right. A sorted structure finds 9:00 in O(log n) and walks forward until 9:05, touching only the events in the range. That's what hash maps can't do.

A hash map can answer "is there an event at exactly 9:03:17?" in O(1). But "between 9:00 and 9:05" needs the keys in order, and a hash map scatters 9:00:01 and 9:00:02 into unrelated buckets on purpose. Scanning all keys works but is O(n) per query, the thing we're trying to avoid. A sorted structure keeps neighbors together, so a range is "find the start, walk forward".

Go deeper: when the map doesn't fit on one machine

A natural way to spread keys over N servers is server = hash(key) % N. It's the same squash as a bucket. And it has the same problem as resizing: change N from 10 to 11 and almost every key's server changes, so almost all the data has to move. Consistent hashing (topic 02.15) fixes that, so adding a server moves only about 1/N of the keys.

Shared maps inside one program need care too: two threads inserting at once can corrupt a chain or lose a resize. Java's ConcurrentHashMap locks per bucket and lets reads skip locks. That's in the concurrent structures chapter.

12What to say in the interview

When an interviewer asks "why is a dict lookup O(1)?" or "how would you build a hash map?", walk through it in this order. Each step is one or two sentences:

  1. The trick: "An array reads any slot in one step, because the address is arithmetic. A hash function turns any key into a slot number: hash(key) % m."
  2. Collisions: "Many keys share a slot, and it starts early, after about √m keys. I'd chain: each bucket holds a short list of key-value pairs, and I compare keys with equality. Or use open addressing, with tombstones for deletes."
  3. Load factor: "Cost is about 1 + α, where α = n/m. So I keep α below a limit, like 0.75, by doubling the table and rehashing. That's O(n) for one insert but amortized O(1)."
  4. The fine print: "That's O(1) average, O(n) worst case if keys pile up, which an attacker can force without randomized hashing. And hashing a key of length k costs O(k)."
  5. The trade-off: "It costs extra memory and throws away order. If I need ranges or a guaranteed worst case, I'd use a balanced tree."

"For the sign-up check, I'd keep the names in a hash set. Each check is O(1) on average, about 30 nanoseconds in Python, versus scanning 10 million names. The cost is memory: the table is about three times the list's array of pointers, roughly 30% more overall once you count the names themselves. Python randomizes string hashes, so users can't pick names that collide on purpose. If we outgrow one machine, I'd shard by hash of the name, using consistent hashing so adding a shard doesn't move everything."

✓What to remember

  1. Arrays read slot i in one step: the address is start + i × size. Hash maps exist to get that jump for any key.
  2. Direct addressing (key = index) needs a slot per possible key, so it only works for small, dense keys.
  3. A hash function turns a key into a number: same key, same number, spread evenly. hash % m picks the bucket.
  4. Collisions start after about √m keys (the birthday paradox). Chaining keeps a list per bucket and compares keys with ==.
  5. Load factor α = n/m is the average chain length; lookup costs about 1 + α. Bounded α means O(1).
  6. Resize by doubling and rehash every key (the bucket depends on m). One insert is O(n); n inserts total under 2n moves: amortized O(1).
  7. Open addressing walks to the next free slot. An empty slot ends a search, so deletes leave tombstones.
  8. Keys: equal keys must hash equal, and keys must not change while stored. Hence immutable keys.
  9. O(1) is average; worst case is O(n) when keys pile up. Randomized hashing stops attackers forcing it.
  10. Use one when a brute force keeps searching. Not for order or ranges, small dense keys, tight memory, or hard worst-case limits.

Warm-up · pen and paper

1. Run a probing table by hand

A table has 8 slots and uses linear probing. The keys' hashes are: A = 3, B = 11, C = 4, D = 19, E = 5. Insert A, B, C, D, E in that order (slot = hash % 8). Then delete B and look up D. Write down the table after each step and every slot the lookup visits.

Answer

A → 3. B: 11 % 8 = 3, taken, so 4. C: 4 is taken, so 5. D: 19 % 8 = 3, then 4, 5 taken, so 6. E: 5 and 6 taken, so 7. Table: [_, _, _, A, B, C, D, E]. Delete B: slot 4 becomes a tombstone. Look up D: slot 3 (A, no), slot 4 (tombstone, keep going), slot 5 (C, no), slot 6 (D, found). Four probes. If B's slot had been emptied instead, the lookup would stop at slot 4 and wrongly report D missing. Notice C: its home slot 4 was taken by B, a key that didn't even belong there. Keys spill into each other's homes and the run grows: that's clustering.

(a) An array of 256 counters: the keys are small and dense, so direct addressing beats hashing. (b) A hash set: pure membership, no order needed. 3. Find the bug

class User:
    def __init__(self, email): self.email = email
    def __eq__(self, other): return self.email.lower() == other.email.lower()
    def __hash__(self): return hash(self.email)

Which part of the key contract does this break? Give two User objects that show it, and fix it.

Answer

Equal keys must have equal hashes. User("A@x.com") == User("a@x.com") is true, but their hashes are computed from different strings, so they (almost always) land in different buckets: put one in a set and the other isn't found. Fix: hash the same thing equality compares, hash(self.email.lower()). Even better, normalize once in __init__ and use a frozen dataclass so the email can't change after the user goes into a set.
