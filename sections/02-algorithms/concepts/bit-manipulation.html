Chapter 2 · Part 11

Bit manipulation

P1 asked often, and used everywhere in systemsabout 50 minutes10 quick checks · 11 exercises

Every number in a computer is already a row of on/off switches. Bit manipulation means working on those switches directly instead of on the number they spell. That sounds like a low-level party trick, but it's how permissions, feature flags, IP address ranges, Bloom filters, hash tables and database indexes squeeze a whole set into one machine word and answer questions about it in one instruction. Interviewers ask bit questions to see whether you can reason about representation, not just about algorithms.

By the end you'll be able to

  1. Read and write binary and hex, and explain two's complement with an odometer.
  2. Picture what AND, OR, XOR, NOT and the shifts do to each switch, and test, set, clear or flip one bit from memory.
  3. Use an int as a set of up to 64 things: union, intersection, subset test and size, each in a step or two.
  4. Explain why x & (x - 1) clears the lowest 1, why x & -x isolates it, and why XOR finds the number without a partner.
  5. Enumerate every subset, every submask and every k-subset with masks, and say what each costs.
  6. Handle Python's unlimited ints: negatives, 32-bit masks, bit_count(), and what a big-int operation really costs.

How to read this: top to bottom. It builds on How fast is your code? (2n growth) and Recursion and backtracking (subsets as a decision tree). Answer each quick check before reading on; a wrong answer gets you a second explanation. "Go deeper" boxes are optional on a first read.

1The problem: a million users, forty switches

Your company's admin console has 40 permissions: read, write, deploy, billing and so on. Each of its 1,000,000 users holds about 10 of them. The first version stores each user's permissions as a Python set of strings.

A set of 10 strings takes 728 bytes in CPython, before counting the strings. A million of them is about 730 MB of RAM, just to remember who may do what. And every page load asks "does she have read, write and deploy?", which is three hash lookups, each one probing a table and comparing strings.

Now look at the problem differently. Each permission is a yes/no question. 40 yes/no answers are 40 switches, and a 64-bit number is 64 switches. Give each permission one switch: read is switch 0, write is switch 1, and so on. Then a user's permissions are one number: 8 bytes in a database column or a C array, 8 MB for a million users instead of 730 MB. "Does she have all three?" becomes one AND and one comparison, both single CPU instructions.

That's the whole chapter in one story: a number is a row of switches, so one number can hold a whole set of yes/no facts, and the CPU can flip, test or combine all of them at once. To use it, we need to see the switches clearly, then learn the handful of operators that work on them.

Why can one 64-bit number replace a set of up to 64 permission names?

Right. A permission set never needs the names themselves, only "has it / doesn't have it" for each of a fixed list. That's one switch per permission. The names live once, in the code (WRITE = 1 << 1), not once per user.

Nothing is hashed or compressed. Think of a light panel with 64 labelled switches on a wall: the labels are painted on once, and each user just gets a photo of which switches are up. The photo is 64 yes/no answers, which is exactly what one 64-bit number holds. That only works because the list of possible permissions is fixed and small.

2Binary: a row of light switches

Start with something you already trust: decimal. In 407, the 4 is worth 4 hundreds, the 0 is worth no tens, the 7 is worth 7 ones. Each place is worth 10 times the place to its right, because there are 10 digits.

Binary is the same idea with only two digits, 0 and 1. So each place is worth 2 times the place to its right: 1, 2, 4, 8, 16, 32, 64, 128. Picture a row of light switches, each with a price tag. A switch that's on adds its price; a switch that's off adds nothing. The number is the total.

price:   128  64  32  16   8   4   2   1
switch:    0   0   0   0   1   1   0   1      →  8 + 4 + 1 = 13
position:  7   6   5   4   3   2   1   0

Each switch is a bit (binary digit). We number positions from the right, starting at 0, so bit i is worth 2i. The rightmost bit is the lowest bit (worth 1) and the leftmost is the highest. In Python you write binary with a 0b prefix: 0b1101 == 13.

Eight switches. Click a switch to flip it; its price is above it and its position below. Press All off, then + 1 until it reads 7 (0111). Press + 1 once more and watch the carry ripple left, just like 999 + 1 in decimal. Press × 2 and see every switch slide one place left.

Three facts fall straight out of the picture:

  • n switches give 2n patterns. Each switch doubles the count: 8 bits give 256 values (0 to 255), 32 bits about 4.3 billion, 64 bits about 1.8 × 1019.
  • All switches on is one less than the next price. 1111 = 15 = 16 − 1, just as 999 = 1000 − 1. So (1 << n) - 1 is "n ones", the mask you'll use constantly. (1 << n is 1 slid n places left, which is 2n; section 4 covers the shift operators.)
  • Sliding everything one place left doubles the number, like writing a 0 after a decimal number multiplies it by 10.

Long rows of 0s and 1s are hard to read, so programmers group them in fours. Four bits have 16 patterns, so each group is one hex (base-16) digit: 0–9, then a–f for 10–15. 1111 1111 is 0xff = 255, and 32 ones are 0xffffffff. Hex is just binary with a shorter spelling.

A number is a row of switches; bit i is worth 2i. n bits hold 2n values, n ones in a row is 2n − 1, and each hex digit is exactly 4 bits.

A packet header has a 12-bit field for the packet's length. What's the largest length it can hold?

Right. 12 bits have 212 = 4,096 patterns, but one of them is 0, so they cover 0 to 4,095. The largest is all twelve switches on: 4,096 − 1, written 0xfff.

Count with a smaller case first. 3 switches: 000 up to 111, which is 4 + 2 + 1 = 7. That's 8 patterns (23), from 0 to 7. So n bits have 2n patterns and the biggest is 2n − 1. For 12 bits: 4,096 patterns, largest 4,095. (2,048 is just the price of the top switch alone, bit 11.)

3Negative numbers: the odometer that rolls back

Switches can only be on or off. There's no switch for a minus sign. So how does a computer store −3?

Picture a car's odometer with three wheels, reading 000. Roll it back one mile and it shows 999. Roll it back three miles: 997. The odometer has no minus sign either, but 999 behaves exactly like −1: add 1 to it and you get 000, because the carry falls off the left end. And 997 + 3 is 000, so 997 acts like −3.

Computers do the same with a fixed number of bits. In 8 bits, 0 − 1 rolls back to 11111111, so that pattern means −1. This scheme is called two's complement. Here it is on a 4-bit wheel, small enough to see every pattern at once:

The 16 patterns of 4 bits on a wheel; the number inside each circle is what the pattern means. Press − 1 from 0000 and you land on 1111 = −1. Keep pressing + 1 past 0111: the wheel goes on to 1000, which means −8. That jump is overflow. Switch to "unsigned" and the same patterns read 0 to 15, with the jump between 15 and 0 instead.

Read the wheel and the rules appear:

  • The top bit says the sign. Patterns starting with 0 are 0 to 7; patterns starting with 1 are −8 to −1. With n bits the range is −2n−1 to 2n−1 − 1. For 32 bits that's −2,147,483,648 to 2,147,483,647.
  • To negate: flip every bit, then add 1. 3 is 0011; flipped it's 1100; plus 1 is 1101, which the wheel shows as −3. Why it works: x plus "x flipped" is all ones (each place has exactly one 1), and all ones is −1. So "x flipped" = −1 − x, and adding 1 gives −x.
  • Adding needs no special case. In 8 bits, 5 + (−3) is 00000101 + 11111101 = 1 00000010. The ninth bit falls off the end, like the odometer's carry, leaving 00000010 = 2. One adder circuit handles positive and negative numbers alike. That's why every modern CPU uses this scheme.

Two follow-ups interviewers like. First, one number has no positive partner. In 4 bits, −(−8) is flip 1000 → 0111, plus 1 → 1000: −8 again, because +8 doesn't fit. That's why abs(INT_MIN) is still negative in C and Java. Second, what overflow does is a language rule, not a law. Java and Go wrap around the wheel as shown. In C and C++, overflow of a signed int is undefined behaviour: the compiler may assume it never happens, so code that "relies on wrapping" can be optimized into something else (unsigned types do wrap). Rust panics on overflow in debug builds, and Python never overflows at all (section 9).

Two's complement is an odometer: going below 0 rolls over to all ones. The top bit means negative, −x = (flip every bit of x) + 1, and the same adder works for both signs. Go past the largest value and you wrap to the most negative one: overflow.
Explain it another way: the top switch has a negative price

Keep the price tags from section 2, but make the top one negative. In 8 bits the prices are −128, 64, 32, 16, 8, 4, 2, 1. Then 11111111 is −128 + 127 = −1, 10000000 is −128 on its own, and 11111101 is −128 + 125 = −3. Every pattern still means "add up the prices of the switches that are on". Only the top price changed sign.

An 8-bit signed value holds 11111110. What number is it?

Right. It's two steps back from 00000000 on the odometer, so −2. Check with flip-and-add-one: flipped it's 00000001, plus 1 is 00000010 = 2, so the original was −2.

254 is what the pattern means unsigned, but the question says signed, and the top bit is on, so it's negative. −126 comes from reading the top bit as a plain minus sign in front of the other seven (1111110 = 126). That's not how two's complement works. Use the odometer: one step back from 0 is 11111111 (−1), two steps back is 11111110, so it's −2. Or with prices: −128 + 64 + 32 + 16 + 8 + 4 + 2 = −2.

4Five operators, five pictures

Bitwise operators work on every switch position separately, all at the same time. Bit 0 of the answer depends only on bit 0 of the inputs, bit 1 only on bit 1, and so on. So each operator is fully described by what it does to one pair of switches. Here they are as pictures you can hold in your head:

One switch at a time

Combine a shift with an operator and you can touch exactly one bit. 1 << i is a row with only switch i on: a mask that points at bit i. Then:

One trap with precedence. In Python, << and >> bind looser than + and -, so 1 << n - 1 means 1 << (n - 1). And &, |, ^ bind tighter than ==, so x & 1 == 0 means (x & 1) == 0. In C, C++ and Java it's the other way round for that last one: x & 1 == 0 there means x & (1 == 0). Write the parentheses in any language and nobody has to remember.

Bitwise operators work column by column. AND keeps where both are on, OR where either is, XOR where they differ (so XOR with 1 flips), NOT flips all, shifts slide. With the mask 1 << i you test, set, clear or flip one bit.

A bug report says "turning off bit 3 sometimes turns it on". The code is flags = flags ^ (1 << 3). What's wrong?

Right. XOR is the hallway switch: it changes the light whatever state it's in. "Turn off" must force the bit to 0 no matter what: AND with a mask that has a 0 at bit 3 and 1s everywhere else, which is ~(1 << 3). Exercise 8's discard tests exactly this.

Bit 3 is the one worth 8, and 1 << 3 is 8, so the position is right. And in Python, power is **; ^ really is XOR. The problem is what XOR means: "flip". Run it twice on a flag that's already off: off → on → off. A "turn off" needs to be idempotent (doing it twice is the same as once), and only AND with 0 is: flags & ~(1 << 3).

5A mask is a set

Back to the permissions from section 1. Number the 40 permissions 0 to 39. A user's permissions are a number whose bit i is on when they hold permission i. That number is a set: a bitmask, or just a mask. Every set operation turns into one operator:

READ, WRITE, DELETE, ADMIN = 1, 2, 4, 8   # one bit each: 1 << 0, 1 << 1, ...
perms = READ | WRITE                       # {read, write}            0011
perms |= DELETE                            # add delete               0111
perms &= ~WRITE                            # remove write             0101
NEED = READ | DELETE
has_all = (perms & NEED) == NEED           # holds every one in NEED? True
has_any = (perms & (WRITE | ADMIN)) != 0   # holds at least one?      False

Compare that with a Python set of strings: a union walks both sets and hashes every element. With masks, the CPU combines 64 memberships in one step because it handles all 64 switches of a word in parallel. That's the real win: not cleverness, but 64 questions answered per instruction.

The catch is the fixed universe. A mask only works when the items can be numbered 0, 1, 2, … and there aren't too many. 64 fit in a machine word; a few thousand fit in a short array of words (a bitset, section 10); a million fit in 125 KB. Arbitrary strings or a universe of 264 possible ids don't fit; that's what hash sets and Bloom filters are for.

A mask is a set over a small, numbered universe: bit i on means item i is in. Union is |, intersection &, difference & ~, and "A ⊆ B" is (a & ~b) == 0. Each costs about one instruction per 64 items.

A deploy needs permissions need. A user holds have. Which test says the user may deploy?

Right. need & ~have is "the permissions needed but not held". If that set is empty, every needed bit is held. In Python & binds tighter than ==, so this reads as intended; add parentheses anyway for other readers.

Try it with numbers. Say need = 0110 (write and delete) and have = 0010 (only write). have & need is 0010, not 0, so the first test lets her deploy without delete: that test means "has any of them". have >= need compares the numbers' sizes, not their switches: have = 1000 (8, admin only) is bigger than need = 6 but holds neither. The right question is "is anything needed missing?": needed bits AND not-held bits, need & ~have, must be 0.

6The lowest 1: x & (x - 1) and x & -x

How many permissions does a user hold? That's counting the 1 bits of a number, called the population count or popcount. The obvious way checks every position:

def popcount_slow(x):          # x >= 0
    count = 0
    while x:
        count += x & 1         # is the lowest bit on?
        x >>= 1                # slide the next bit down
    return count               # one loop per POSITION, up to the highest 1

For a 64-bit number that's up to 64 loops, even when only 2 bits are on. Can we jump straight from one 1 to the next and skip the zeros?

What subtracting 1 does

Think about the odometer again. In decimal, 4,000 − 1 = 3,999: the lowest nonzero digit goes down by one, and every 0 below it becomes the largest digit, 9. Binary does the same thing with only two digits: the lowest 1 becomes 0, and every 0 below it becomes 1. Everything above the lowest 1 stays the same.

x         = 1011 0100      (180)
x - 1     = 1011 0011      (179)   lowest 1 → 0, the zeros below it → 1s
x & (x-1) = 1011 0000      (176)   the changed bits disagree, so AND drops them all

So x & (x - 1) is x with its lowest 1 turned off. Each round deletes exactly one 1, wherever it sits. Replace the slow loop's body with x &= x - 1, count the rounds until x is 0, and you've looped once per 1 bit, not once per position: 2**63 + 1 takes 2 rounds instead of 64. This is known as Kernighan's popcount (exercise 4 has you write it).

Counting the 1s of a 12-bit number two ways. Yellow cells are the bits that subtracting 1 changed; red is the 1 that gets deleted. Step through both methods on "two 1s": 2 steps against 12. Then pick "all 1s", where the two methods tie.

Two more tricks use the same picture.

  • Is x a power of two? A power of two has exactly one 1 (1, 10, 100, 1000…). Deleting it leaves 0. So x > 0 and x & (x - 1) == 0. The x > 0 matters: 0 has no 1 bits, and 0 & -1 is 0 too.
  • Keep only the lowest 1: x & -x. Remember −x = (flip x) + 1. Flipping turns the lowest 1 into 0 and the zeros below it into 1s. Adding 1 ripples through those 1s and stops at exactly the lowest 1's position. Above that, −x is still the flip of x, so AND clears it:
x         = 1011 0100
~x        = 0100 1011
-x = ~x+1 = 0100 1100      the +1 ripples up to the lowest 1 of x, and stops
x & -x    = 0000 0100      only the lowest 1 survives: 4

x & -x is called the lowbit of x. It's the engine of the Fenwick tree (chapter 1, section 8 of Segment and Fenwick trees), and with bit_length() it gives the position of the lowest 1. (x.bit_length() is how many bits x needs: 1 for 1, 3 for 100, 0 for 0. For a power of two 2i that is i + 1.) So the lowest 1 sits at (x & -x).bit_length() - 1: for x = 180 that's 100.bit_length() − 1 = 2.

x - 1 turns the lowest 1 into 0 and the zeros below it into 1s. So x & (x - 1) deletes the lowest 1 (popcount in one loop per 1 bit; power of two when it leaves 0), and x & -x keeps only the lowest 1.
Go deeper: popcount in hardware, and in parallel

x86 CPUs have had a single POPCNT instruction since about 2008, and ARM has an equivalent. C compilers turn __builtin_popcount into it when the target CPU has it. CPython's int.bit_count() (3.10+) calls that builtin once per 30-bit digit of the int (section 9); whether it becomes a real POPCNT depends on the flags Python was compiled with, since generic x86-64 builds can't assume the instruction exists.

Before that, the fastest software trick counted in parallel ("SWAR", SIMD within a register): add neighbouring bits in pairs, then neighbouring pairs in groups of 4, then 8, using masks like 0x5555… (0101…) and 0x3333… (0011…). That's log₂ 64 = 6 rounds whatever the input. Interviewers sometimes ask for it after Kernighan's version, to see if you can think of bits as 32 tiny 2-bit counters side by side.

How many times does the x &= x - 1 loop run for x = 2**40 + 2**3?

Right. x has two 1 bits, at positions 3 and 40. The first round deletes bit 3 (the lowest), the second deletes bit 40, and x is 0. The 36 zeros in between (bits 4 to 39) are never visited.

Write it out: x is a 1 at bit 40, then 36 zeros, then a 1 at bit 3, then 000. Subtracting 1 only disturbs the bits from the lowest 1 down: bit 3 becomes 0, bits 0–2 become 1, and AND wipes all four. Bit 40 is untouched. Now x = 240, and the second round deletes that. Two rounds: one per 1 bit, never one per position.

7XOR: pairs that cancel

An interview classic: a list of 1,000,001 numbers where every number appears exactly twice except one. Find the loner. A set or a counter works, but costs memory for 500,000 entries. Can you do it with one variable?

Go back to the hallway light. Each number is a set of switches to flip. Flip the same switches twice and the light is back where it started. So if you start with all lights off and flip by every number in the list, every pair undoes itself, whatever order they come in, and only the loner's switches are left on. In XOR terms, three facts:

  • a ^ a == 0: flipping twice cancels.
  • a ^ 0 == a: flipping nothing changes nothing.
  • Order and grouping don't matter: a ^ b == b ^ a and (a ^ b) ^ c == a ^ (b ^ c), because each column is just "is the number of 1s odd?".
[4, 1, 2, 1, 2]
0 ^ 4 ^ 1 ^ 2 ^ 1 ^ 2
  = 4 ^ (1 ^ 1) ^ (2 ^ 2)      regroup: allowed, order doesn't matter
  = 4 ^ 0 ^ 0
  = 4

So one pass with one running value is enough: O(n) time, O(1) extra memory. It works on negative numbers too, since XOR is column by column. Exercise 5 measures the memory, so a set fails it.

The same "pairs cancel" idea solves cousins:

  • Missing number: a list holds 0 to n with one missing. XOR all the values and all of 0..n. Every present number appears twice and cancels; the missing one appears once.
  • Two loners: every number appears twice except a and b. XOR-ing everything gives a ^ b, which isn't 0 because a ≠ b. Its lowest 1 (x & -x!) is a column where a and b differ. Split the list by that bit and XOR each half: each half has exactly one loner.
  • RAID 5 storage: store a parity block P = D1 ^ D2 ^ D3 next to three data blocks. If the disk with D2 dies, D2 = P ^ D1 ^ D3. One extra disk protects against any single failure.
XOR is "flip": a ^ a = 0, a ^ 0 = a, and order doesn't matter. So XOR-ing a whole list cancels every pair and leaves what appears an odd number of times, in O(1) memory. That's how RAID parity rebuilds a lost disk.
Explain it another way: one column at a time

Look at only the lowest bit of every number. XOR-ing a column gives 1 exactly when the column has an odd number of 1s. Each pair puts in two equal bits, which adds 0 or 2 ones: no effect on odd-or-even. Only the loner can change it. So each column of the result is the loner's bit, in every column at once.

Go deeper: the XOR swap, and why not to use it

a ^= b; b ^= a; a ^= b swaps two variables without a temporary. It's a cute puzzle and a bad idea: in Python a, b = b, a is clearer and just as fast, and in C, if a and b are the same memory location (swap(&x[i], &x[j]) with i == j), the first line sets it to 0 and the value is lost. Compilers already swap through registers for free. Say this if an interviewer brings it up.

Now every number appears exactly three times except one, which appears once. What does XOR-ing the whole list give?

Right. x ^ x ^ x = (x ^ x) ^ x = 0 ^ x = x, so each triple leaves one copy behind. The trick only cancels pairs. For triples you count each column's 1s and take the count mod 3: the columns where the loner has a 1 are the ones whose count isn't a multiple of 3.

Flip a switch three times: off → on → off → on. It ends on. Three copies of x leave x, not 0. So in [5, 5, 5, 9] the result is 5 ^ 9 = 12, not 9. XOR only erases things that appear an even number of times. For triples, count the 1s in each column across the whole list; a column whose count isn't a multiple of 3 is a column where the loner has a 1.

8Every subset is a number

Three pizza toppings, ham, cheese and olive. List every combination you could order. In the backtracking chapter you drew this as a decision tree: for each topping, take it or leave it, 2 × 2 × 2 = 8 leaves.

Masks give the same 8 without any recursion. Give ham bit 0, cheese bit 1, olive bit 2. Then every order is a 3-bit number, and every 3-bit number is an order. Counting from 0 to 7 is turning a binary odometer, and an odometer visits every reading exactly once:

mask  olive cheese ham    subset
000     .     .     .     {}
001     .     .     ham   {ham}
010     .   cheese  .     {cheese}
011     .   cheese ham    {ham, cheese}
100   olive   .     .     {olive}
...
111   olive cheese ham    {ham, cheese, olive}

Here's the loop at work on a small search: n tasks with durations, and the busiest set of them that fits in a time budget.

def busiest_fit(durations, budget):     # n <= ~20 tasks
    n, best = len(durations), 0
    for mask in range(1 << n):          # 0 .. 2**n - 1: every subset once
        total = sum(durations[i] for i in range(n) if (mask >> i) & 1)
        if total <= budget:             # bit i on means "task i is in"
            best = max(best, total)
    return best                         # 2**n masks × n bit tests: O(n · 2**n)

That's the whole technique. It's handy when n is small, about 20 or less (220 ≈ 1 million subsets). It's also why backtracking code uses a mask for its "used" set: the mask is one small hashable number you can use as a cache key.

The subsets of a subset

Harder question: you already have a set, say mask 10110 = {B, C, E}, and you want every subset of it. Counting from 0 to 22 and skipping the numbers with a bit outside the mask works, but wastes time: for a mask with 3 bits spread over 50 positions you'd count to 250 to find 8 answers.

The fix uses section 6's picture of subtracting 1. Count down, but only on the wheels that exist. s - 1 turns s's lowest 1 into 0 and fills everything below with 1s; & mask then throws away the 1s that landed outside the mask. What's left is the next smaller submask, with nothing skipped and nothing visited twice:

mask = 10110            s = (s - 1) & mask

s      s - 1    & mask = next s
10110  10101    10100
10100  10011    10010
10010  10001    10000
10000  01111    00110     the borrow fills bits 0-3; the mask keeps bits 1 and 2
00110  00101    00100
00100  00011    00010
00010  00001    00000     8 submasks: 10110 10100 10010 10000 00110 00100 00010 00000
Green cells are the items in the current subset; dim cells are bits outside the mask, which (s − 1) & mask never lets in. Step through the submask mode: 8 subsets of a 3-element set, found in 8 steps, while the numbers from 22 down to 0 are 23.

A mask with k bits has 2k submasks, so this loop costs O(2k) however wide the mask is. When you run it for every mask of n items, the total is 3n, not the 2n × 2n = 4n you'd pay testing every s against every mask: each item has only three legal states, outside the mask, in the mask but not in s, or in both. For n = 15 that's 14 million steps against a billion. That 3n is the cost of any bitmask DP that, for every set, tries every way to split it in two.

Bitmask DP, briefly

Some problems need "which items have I used?" as part of a dynamic programming state. Traveling salesman is the famous one: 20 cities have 19! ≈ 1.2 × 1017 routes. But the best way to finish a route only depends on which cities you've visited and where you are now, not on the order you visited them. As a mask, that's 220 × 20 ≈ 21 million states, each trying up to 20 next cities: about 4 × 108 steps (the Held–Karp algorithm). Still exponential, so n stays around 20, but feasible where 19! never is. The DP chapter's "Go deeper" box has more; exercise 9 has you design one.

Counting 0 to 2n − 1 visits every subset of n items once. s = (s - 1) & mask walks the 2k submasks of a k-bit mask with no waste. A mask in a DP state turns n! orders into 2n sets.
Go deeper: Gosper's hack, the next number with the same number of 1s

To visit only the subsets of size k, in increasing order, jump from one mask to the next with the same popcount:

c = x & -x                 # lowest 1
r = x + c                  # carry ripples through the lowest block of 1s
x = (((r ^ x) >> 2) // c) | r   # put the leftover 1s back at the bottom

From 0011 it goes 0101, 0110, 1001, 1010, 1100: all C(4, 2) = 6 masks, one step each. A recursion that chooses k positions works just as well and is easier to explain in an interview; exercise 7c accepts either.

You run the submask loop for mask = (1 << 60) | (1 << 30) | 1. How many times does the loop body run?

Right. The mask has 3 bits, so 23 = 8 submasks, and (s - 1) & mask jumps from each straight to the next. The 58 positions outside the mask (of the 61 from bit 0 to bit 60) are never visited, and neither are the numbers in between.

Think of three wheels on an odometer that only has those three wheels. It shows 2 × 2 × 2 = 8 readings. s - 1 may set lots of bits below the lowest 1, but & mask keeps only the ones on real wheels, so every step lands on a real submask, the next smaller one. 8 steps. Counting every number below 260 would be about 1018 steps, which never finishes.

9Bits in Python: no odometer

Everything so far assumed a fixed number of switches, like a C int32_t. Python's int has no fixed width. It grows as needed: 2**100 is an exact integer, and nothing ever overflows. That's convenient for arithmetic and surprising for bits.

Negative numbers have infinitely many 1s

Python pretends a negative number is two's complement with an infinite row of 1s to the left. −1 is …1111 forever; −4 is …11100. Every operator follows from that picture:

~5             # -6: flipping 0...0101 gives 1...1010, which is -6 (~x == -x - 1)
-1 >> 100      # -1: sliding right brings in more 1s from the infinite left
-5 >> 1        # -3: right shift rounds DOWN (floor), so it's -5 // 2, not -2
bin(-5)        # '-0b101': bin shows a minus sign and the size, NOT the bit pattern
-5 & 0xFF      # 251 = 0b11111011: AND with a mask cuts the infinite row to 8 bits

So to see or simulate a fixed width, mask: x & 0xFFFFFFFF keeps 32 bits, and the answer is always a non-negative number with the same low 32 switches. To read such a pattern back as signed, look at bit 31:

MASK = 0xFFFFFFFF                         # 32 ones
def to_signed32(u):                       # u is a 32-bit pattern, 0 .. 2**32 - 1
    return u - (1 << 32) if u >> 31 else u # top bit on: it's negative, roll back 2**32

This is the bug in the classic "add two numbers without +" puzzle (exercise 6). The loop is: XOR adds without carrying, AND then shift left is the carry, repeat until there's no carry. On a 32-bit CPU the carry falls off the end after 32 rounds. In Python there's no end to fall off: for −1 + 1 the carry walks left forever through the infinite 1s. You must mask every round to 32 bits, then convert back with to_signed32.

Useful built-ins

  • x.bit_count(): popcount (Python 3.10+). x.bit_length(): how many bits x needs; for x > 0 that's the position of the highest 1 plus one.
  • int.from_bytes(b, "little") and x.to_bytes(n, "little"): convert between bytes and an int, in C speed.
  • There's no >>> (Java's "shift right, fill with 0s"). Mask first, then shift: (x & MASK) >> k. Python's >> always copies the sign bit in from the left (an arithmetic shift); Java's >> does too, and C++20 guarantees it, while older C left right-shifting a negative number up to the compiler.
  • Shift distances: in Python 1 << 100 is just a big number. In Java, an int shift uses only the low 5 bits of the distance, so 1 << 32 is 1; in C, shifting by the width or more is undefined. Another reason to mask on purpose.
  • enum.Flag and enum.IntFlag: named bit flags that combine with |, for readable permission code.

What a big int really costs

A Python int is stored as an array of 30-bit "digits". On ints that fit in a machine word, & or | is effectively O(1). On a million-bit int, it's O(1,000,000 / 30): it walks the digit array, in C, which takes microseconds. That's still about 30 bits per step instead of 1, which is why one big int makes a fine bitset (exercise 8). But ints are immutable: bits |= 1 << i builds a brand-new int and copies all of it. On a million-bit set, each single add copies about 125 KB. If you add bits one at a time far more often than you combine whole sets, a list of 64-bit words (or array("Q"), or a bytearray) changes one word in place instead.

Python ints never overflow, and negatives act as if they had infinitely many 1s on the left. To get fixed-width behaviour, AND with a mask like 0xFFFFFFFF and convert back by checking the top bit. Big-int operations cost O(bits / 30), and every change copies the int.

You port Java's String.hashCode to Python. It computes h = 31 * h + c for each character code in a Java int, which wraps on overflow. In Python the hashes come out different and enormous. What's the fix?

Right. Java's 32-bit int is an odometer that rolls over at 232; Python's ints never roll over. Keeping the low 32 bits after each step is exactly what the hardware does. Java's int is signed, so the final step is to_signed32: patterns with bit 31 on mean value − 232. (Porting the same loop from C? There it must use an unsigned type, because signed overflow in C is undefined, not a wrap.)

Python ints don't overflow at 64 bits or anywhere else: they grow until memory runs out. And % 31 keeps a remainder by 31, a completely different number. What Java does on overflow is drop every bit above bit 31, like an odometer losing its carry. In Python you drop them yourself with & 0xFFFFFFFF (which equals % 2**32 for this), and, since Java's int is signed, convert the top bit back into a minus sign at the end.

The CIDR row is worth doing by hand once. An IPv4 address is 32 bits, written as four bytes. A /p network keeps the top p bits fixed and lets the other 32 − p vary, so it holds 232−p addresses and its mask is p ones followed by zeros: (0xFFFFFFFF << (32 - p)) & 0xFFFFFFFF. For /12 that's 255.240.0.0: 8 ones, then 11110000, then 16 zeros.

In systems, bits are a representation choice: a fixed list of yes/no facts per thing (permissions, flags), a set over numbered ids (bitmaps, Bloom filters), a prefix (CIDR, power-of-two tables), or several small fields packed in one word (Snowflake ids). Each buys memory and one-instruction checks, and costs readability.

A firewall allows 10.16.0.0/12. Is 10.20.30.40 allowed?

Right. The /12 mask is 255.240.0.0. Only the second byte needs work: 20 is 00010100, and AND with 240 = 11110000 keeps 00010000 = 16. So the masked address is 10.16.0.0, the network itself. The /12 covers 10.16.0.0 to 10.31.255.255.

A /12 doesn't compare whole bytes; it compares the first 12 bits. That's all 8 bits of the first byte and the top 4 of the second. 16 is 0001 0000 and 20 is 0001 0100: their top four bits, 0001, match. So yes. Any second byte from 16 (0001 0000) to 31 (0001 1111) is inside. Being inside 10.0.0.0/8 is true too, but the firewall doesn't ask about that.

11What to say in the interview

When a problem smells of bits (small sets, "every number appears twice", powers of two, flags, "without using +"), a strong answer sounds like this:

  1. Name the representation: "n is at most 20, so I'll keep the chosen items as a bitmask: bit i means item i is in. That's one int, and it's hashable, so I can memoize on it."
  2. Say the trick and why it works, with one tiny example: "x & (x − 1) clears the lowest 1, because subtracting 1 turns that 1 into 0 and the zeros below it into 1s: 1100 becomes 1011, and AND gives 1000."
  3. Give the cost in the right unit: "This loops once per set bit, not once per position. Over all masks, the submask loop is 3n, so n = 15 is about 14 million steps."
  4. Cover the edges: 0 (no set bits, and 0 & −1 is 0 so check x > 0 for powers of two), negative numbers, and fixed width. "In Python I'll mask with 0xFFFFFFFF because ints don't overflow."
  5. Offer the readable version: "In production I'd wrap this in an IntFlag or a small Bitset class with named methods, so nobody has to decode & ~ in a code review."
Go deeper: follow-up questions interviewers like
  • "Reverse the bits of a 32-bit int." Loop 32 times: shift the answer left, OR in x & 1, shift x right. The O(log w) version swaps halves, then quarters, then pairs, with masks like 0x0000FFFF, 0x00FF00FF, …, 0x55555555.
  • "Count the bits of every number from 0 to n." bits[i] = bits[i >> 1] + (i & 1), or bits[i] = bits[i & (i - 1)] + 1: a tiny DP, O(n) total.
  • "Gray code." i ^ (i >> 1) lists all n-bit numbers so neighbours differ in one bit. Rotary encoders use it so a sensor between two positions can't misread wildly.
  • "Is it little- or big-endian?" Endianness is the order of bytes in memory, not bits within a byte. Network protocols send big-endian ("network byte order"); x86 and most ARM systems store little-endian. int.from_bytes(b, "big") handles it in Python.
  • "Why is a power-of-two table size risky?" h & (cap - 1) keeps only the low bits, so keys that differ only in their high bits all collide. Mix the hash first (the HashMap and Murmur rows above).

✓What to remember

  1. A number is a row of switches; bit i is worth 2i. n bits hold 2n values; n ones is 2n − 1; a hex digit is 4 bits.
  2. Two's complement is an odometer: −1 is all ones, the top bit means negative, −x = ~x + 1, and passing the top wraps around (overflow).
  3. AND = both, OR = either, XOR = differ (flip), NOT = flip all, shifts slide (×2 and ÷2 rounding down). Test (x >> i) & 1, set | (1 << i), clear & ~(1 << i), flip ^ (1 << i).
  4. A mask is a set over numbered items: | union, & intersection, & ~ difference, (a & ~b) == 0 subset. 64 memberships per instruction.
  5. x & (x - 1) deletes the lowest 1 (popcount in one step per 1 bit; power of two if x > 0 and it gives 0). x & -x keeps only the lowest 1.
  6. XOR cancels pairs: XOR of a list leaves what appears an odd number of times, in O(1) memory.
  7. range(1 << n) is every subset; s = (s - 1) & mask walks a mask's 2k submasks; 3n over all masks. Masks in DP states turn n! into 2n.
  8. Python ints never overflow and negatives have infinite 1s on the left: mask with 0xFFFFFFFF for fixed width, check bit 31 to read it signed. Big-int ops are O(bits / 30) and copy.

Warm-up · pen and paper

1. Work the switches by hand

In 8 bits, write: 13, −13, 13 & −13, 13 & 12, 13 ^ 6, 13 << 2, and −13 >> 1 (as Python computes it). For each, say which section's picture predicts the answer before you work it out.

Answers

13 = 00001101. −13 = flip + 1 = 11110010 + 1 = 11110011. 13 & −13 = 00000001 = 1 (lowbit). 13 & 12 = 00001100 = 12 (lowest 1 deleted, since 12 = 13 − 1). 13 ^ 6 = 00001011 = 11. 13 << 2 = 00110100 = 52. −13 >> 1 = −7 (floor of −6.5), pattern 11111001.

2. Break the naive version

(a) Someone writes is_power_of_two = lambda x: x & (x - 1) == 0. Find the input where it's wrong in Python, and one more where the same test is wrong on a 32-bit Java int. (b) Someone uses XOR-all to find the number without a partner, but the list is [2, 2, 2, 7]. What do they get? (c) In Java, if (flags & MASK == 0) doesn't compile or misbehaves. Why, and why does the same line work in Python?

Answers

(a) 0: 0 & -1 is 0, so it says True. In Python every negative x gives a negative answer (both sides have infinite 1s on the left), so 0 is the only wrong one. On a 32-bit int, −231 is 1000…0 and −231 − 1 wraps to 0111…1, so their AND is 0 and it says True. The fix is x > 0 and …. (b) 2 ^ 2 ^ 2 ^ 7 = 2 ^ 7 = 5: the triple leaves one 2 behind. (c) Java's == binds tighter than &, so it's flags & (MASK == 0), an int AND a boolean. Python's & binds tighter than ==.

3. Permissions and networks

(a) A file has mode 0o640. Write it as rwx letters. Which single expression tells you whether the group may write? (b) How many addresses does 192.168.4.0/22 hold, and what are the first and last? Is 192.168.7.200 inside?

Answers

(a) 110 100 000 = rw- r-- ---. Group write is mode & 0o020, which is 0 here: no. (b) 232−22 = 1,024 addresses. The mask's third byte is 11111100 = 252; 4 & 252 = 4, so the range is 192.168.4.0 to 192.168.7.255. 7 & 252 = 4, so 192.168.7.200 is inside.
