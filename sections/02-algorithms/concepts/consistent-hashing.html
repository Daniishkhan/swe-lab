Chapter 2 · Part 15

Which server holds this key?

P1 the "how do you add a server?" follow-up in every cache and storage designabout 45 minutes10 quick checks · 9 exercises

Every system that spreads data over several machines has to answer one question millions of times a second: which machine holds this key? The obvious answer, hash(key) % N, works perfectly until N changes. Then it moves almost every key at once. This chapter builds the two standard fixes, the hash ring and rendezvous hashing, from scratch, and shows where real systems (Dynamo, Cassandra, Memcached clients, Google's load balancers) use each one.

By the end you'll be able to

  1. Work out exactly how many keys hash % N moves when N changes, and why it's almost all of them.
  2. Explain the hash ring, why adding a server moves only about 1/N of the keys, and why it needs virtual nodes.
  3. Explain rendezvous hashing, and pick between it and the ring for a given system.
  4. Place replicas on a ring or with rendezvous, and say why the hash must be the same in every process.
  5. Name the alternatives interviewers bring up: fixed hash slots, jump hash, Maglev, bounded loads.

How to read this: top to bottom. You should know what a hash function and % m do (Hash maps, section 3) and how binary search finds a spot in a sorted list (Binary search). 1The problem: adding one cache server takes down the database

A shop keeps product pages in a cache in front of its database. The cache is 4 Memcached servers (Memcached is a popular in-memory key-value cache). Each request picks its server with hash(key) % 4. At peak there are 50,000 reads a second, and 95% of them are found in the cache (a hit). Only the other 5%, 2,500 a second, reach the database, which can handle about 5,000.

Black Friday is coming, so an engineer adds a 5th cache server and changes the code to hash(key) % 5. Within seconds the database is at 40,000 reads a second, eight times what it can take. It falls over, and the site goes down with it.

Nothing was broken. The data was all still in the cache. But % 5 sends most keys to a different server than % 4 did, and the new server has nothing in it. So almost every request asks the wrong server, misses, and goes to the database. The cache is full of data nobody can find.

This is a cache stampede: a crowd of misses all hitting the slow layer behind the cache at once. The numbers: 80% of keys moved (the next section counts this exactly). Only the 20% that stayed can still hit, so the hit rate falls from 95% to 0.95 × 0.2 = 19%. 81% of 50,000 is 40,500 misses a second.

The same thing happens anywhere keys are spread over machines: a sharded database moving rows, a storage cluster copying files, a load balancer sending a user's requests to a server that doesn't have their session. So the question for this chapter is: how do we spread keys over N machines so that changing N moves as few keys as possible?

Going from hash(key) % 4 to hash(key) % 5, what fraction of keys end up on a different server?

Right. A key stays only if its remainder happens to be the same for 4 and 5, and that's true for just 1 key in 5. The new server should take only a fifth, but % 5 also shuffles keys between the four old servers. Section 2 counts it on 20 keys.

Try a few keys. Hash 7: 7 % 4 = 3, 7 % 5 = 2, so it moves from server 3 to server 2, between two old servers. Hash 13: 1 then 3, moved. Hash 2: 2 and 2, stays. Out of every 20 hashes in a row, only 4 (0, 1, 2 and 3) give the same remainder both times. So 16 in 20, 80%, move. 20% is what should move (the new server's fair share); 100% is too many, since a few keys get lucky.

2Why % N moves almost everything

Picture dealing a deck of cards around a table, one card to each player in turn. Card 0 goes to player 0, card 1 to player 1, and so on, back to player 0 after the last seat. That's exactly what hash % N does: hash h goes to seat h % N.

Now a fifth player sits down and you deal the same deck again. Cards 0 to 3 go to the same players as before. But card 4, which used to go back to player 0, now goes to the new player 4. From then on every card is one seat "behind" where it was, then two seats, then three. The two deals drift apart, and only line up again every 20 cards.

Count it. With 4 servers going to 5, look at hashes 0 to 19 (after 20, the pattern repeats, because 20 is the first number both 4 and 5 divide). A hash stays only if h % 4 == h % 5. Every pair of remainders shows up exactly once in those 20 hashes, and the pairs that match are (0, 0), (1, 1), (2, 2) and (3, 3). That's 4 hashes out of 20. One in five stays; four in five move.

The same count works for any N. In N × (N + 1) hashes in a row, exactly N keep their server. So the fraction that stays is N / (N × (N + 1)) = 1 / (N + 1), and the fraction that moves is N / (N + 1):

It gets worse as the cluster grows: the bigger your cache, the bigger the stampede. Removing a server (a crash, say) is just as bad: 5 → 4 moves the same 80%.

The right column is the floor. When a fifth server joins, it has to take a fifth of the keys, or it sits idle. So 20% must move. A scheme that moves exactly that, and moves it only onto the new server, with no shuffling between the old ones, is the best possible. That's the goal, and it has a name: minimal disruption.

With hash % N, a key keeps its server only when its remainder happens to match for both N and N + 1: 1 key in N + 1. So N / (N + 1) of all keys move, 80% for 4 → 5. The minimum is 1 / (N + 1), all of it onto the new server.

Instead of adding one server, you double: % 10 becomes % 20. What fraction of keys move?

Right. h % 20 is either h % 10 (stay) or h % 10 + 10 (move to a new server), half and half. And half is the minimum here, since the 10 new servers must take half the keys. Doubling with % is actually optimal. The catch is you can only grow by doubling and shrink by halving, which is a big constraint when you need one more server, or one crashes.

N / (N + 1) is the rule for adding one server. Count again for 10 → 20: take hash 23. 23 % 10 = 3, 23 % 20 = 3, stays. Hash 13: 3, then 13, moves to new server 13. In any 20 hashes in a row, 0–9 stay and 10–19 move to servers 10–19. That's 50%, and it's the minimum: 10 new servers must take half the keys. So doubling works well; you just can't add one server at a time.

3The ring: let keys find the next server

Why does % N shuffle? Because every key's server depends on N. Change N and you change every answer. So the fix must make a key's server depend on something that doesn't change when an unrelated server is added: the key itself and the servers near it.

Here's an idea. Hash the servers too, onto the same range of numbers as the keys. Now a key and the servers all have positions on one long line. Give each key to the first server at or after its position. A new server lands somewhere on the line, and only the keys just before it, between it and the previous server, change hands. Everyone else's "next server" is the same as before.

One problem: a key past the last server has no "next" server. Fix it by bending the line into a circle, like a clock face. Past the top of the range, you come back around to 0. This is the hash ring, and the scheme is consistent hashing (Karger and others, 1997, the paper Akamai's CDN was built on).

A ring with positions 0 to 99 (a real ring uses 0 to 2⁶⁴ − 1). Servers are big circles, keys are small dots. Step through: each key walks clockwise to the first server it meets. Then server E joins, and then server B crashes. Watch which keys change color, and how many.

Trace it. Servers A, B, C and D hash to 12, 37, 61 and 88. The key bob hashes to 20. Walk clockwise from 20: 21, 22, … the first server is B at 37. So B owns bob. The key hal hashes to 95; walking clockwise passes 99, wraps to 0, and meets A at 12. Each server owns the arc of the ring just behind it, back to the previous server: B owns 13 to 37.

In code, the servers' positions sit in a sorted list. "The first position at or after the key" is a binary search, so a lookup is O(log N). Here it is on the toy clock:

import bisect

positions = [12, 37, 61, 88]          # sorted server positions on the ring
names     = ["A", "B", "C", "D"]      # names[i] sits at positions[i]

def owner(key_position):
    i = bisect.bisect_left(positions, key_position)  # first position >= key
    return names[i % len(positions)]                 # past the last? wrap to 0

owner(20)   # "B"
owner(95)   # "A": bisect returns 4, and 4 % 4 = 0 wraps around

A real ring does the same with 64-bit positions from a hash like MD5 or Murmur. (Section 9 is about which hash, and the one you must not use.)

Hash servers and keys onto the same circle. Each key belongs to the first server clockwise from it. A sorted list of server positions plus binary search finds it in O(log N). Wrap around past the end.

Servers sit at positions 10, 40 and 75 on a 0–99 ring. A key hashes to 90. Who owns it?

Right. Walk clockwise from 90: 91, …, 99, then wrap to 0, and the first server you meet is at 10. "Closest" doesn't matter; direction does. In the code, bisect_left returns 3 (past the end), and 3 % 3 = 0.

The rule is "first server clockwise", not "nearest". 75 is behind the key, so walking forward from 90 never reaches it. And the ring has no end: after 99 comes 0. So the walk goes 91, 92, …, 99, 0, 1, …, 10 and stops at the server at 10. Picture the hand of a clock: from 11 o'clock, the next stop at 1 o'clock is reached by passing 12, not by going back to 10 o'clock.

4Adding and removing a server

Go back to the figure and look at the last few steps.

Adding: server E hashes to 50, inside C's arc (38 to 61). The keys between 38 and 50 used to walk on to C; now they stop at E. That's it. Keys in every other arc walk to exactly the same server as before, because nothing changed in front of them. In the figure only dan moves, 1 key out of 8, not the 6 or 7 that % 5 would move.

How much moves on average? With N + 1 servers dropped at random spots on a circle, no spot is special, so on average each one ends up with 1 / (N + 1) of the circle. The new server is one of them. So on average it takes 1 / (N + 1) of the keys, and every one of them comes from the server just after it. That's the minimum from section 2.

Removing: when B crashes, its keys keep walking clockwise past where B was, to the next server. Only B's keys move. Everyone else is untouched.

Back to the Black Friday story: with a ring, adding the 5th server moves about 20% of keys instead of 80%. The hit rate drops from 95% to about 0.95 × 0.8 = 76% while the new server fills up: 12,000 misses a second instead of 40,500. That's still more than the database's 5,000, which is why teams add cache servers before the peak, not during it, or warm the new one first (for a while, a miss on the new server is retried on the key's old owner, and copied over if found). You can't move less than 20%; the ring makes sure you don't move more.

But the figure shows a problem too. When B died, all of its keys went to one server, E. E went from 1 key to 3, and its arc from 13 positions to 38, while A, C and D got nothing. In a real cluster, the dead server's whole load lands on its single neighbor, which might then fall over too, sending double the load to its neighbor. One crash can walk around the ring. We'll fix that in section 6.

Adding a server on the ring moves only the keys in the arc it lands in, about 1 / (N + 1) of them, all onto the new server. Removing one moves only its keys. The flaw: they all move to one neighbor.

A ring has 10 servers, one position each. You add an 11th. Which keys move?

Right. The new server lands inside one existing arc and splits it. Only keys in the first part of that arc change hands, from the server that used to own the whole arc. Everyone else keeps walking to the same server. "Evenly from everyone" would be nicer, and it's exactly what virtual nodes (section 6) give you.

Draw it: 10 dots on a circle, then an 11th dropped between, say, the dots at 3 and 4 o'clock. Keys between 3 o'clock and the new dot used to walk on to 4 o'clock; now they stop early. Keys anywhere else walk to the same dot as before, since nothing changed in front of them. So the movers all come from one server (the 4 o'clock one), not from everyone, and it's a small slice, not 10/11. Taking evenly from everyone needs one more trick: section 6.

5Random spots make uneven arcs

"On average 1/N each" hides a nasty spread. Throw 10 darts at a circle blindfolded. They don't land evenly spaced. Some land close together (one tiny arc), and somewhere there's a big gap (one huge arc). The server at the end of the big gap owns all of it.

How uneven? For N random points on a circle, the expected biggest arc is about (ln N + 0.58) / N of the circle (ln is the natural logarithm: ln 10 ≈ 2.3), and the expected smallest is 1 / N². The last column below is the standard deviation: roughly, how far a typical server's load is from the average, here as a fraction of the fair share. Plugging in:

So with 10 servers, one position each, the busiest server typically has about 3 times its fair share and the quietest about a tenth. The busiest one runs out of memory or CPU while others sit idle. You'd have to buy 3× the servers to survive the worst one. A spread of 90% means a typical server is off by about as much as its whole fair share, which is terrible.

In the ring figure, A, B, C and D own 24, 25, 24 and 27 of the 100 positions: nearly even, but only because those positions were picked by hand for the picture. The next figure uses real hashes, and the first thing it shows is how uneven they are.

10 servers, one position each, placed by hashing their names. Roughly what share of keys does the busiest server usually get?

Right. A uniform hash makes every position equally likely, but 10 random positions still clump and leave gaps. The biggest gap averages about (ln 10 + 0.58) / 10 ≈ 29% of the circle. Uniform per point is not the same as even arcs.

"Uniform" means each server's position is equally likely to be anywhere. It doesn't mean the 10 positions spread out evenly; they're independent, so they clump. Think of 10 people choosing seats at random around a round table with 100 seats: you'll see neighbors and big empty stretches, not one person every 10 seats. The biggest empty stretch with 10 random points averages about 29% of the circle, and the server at its end owns all of it.

6Virtual nodes: many small arcs instead of one big one

One die roll is very random: anything from 1 to 6. The average of 100 rolls is almost always close to 3.5. Averaging many random things cancels out their luck.

Use that. Instead of one position per server, give each server many: hash "A#0", "A#1", …, "A#99" and put A at all 100 spots. Each spot is a virtual node (vnode, or "token" in Cassandra). A server's load is now the sum of its 100 small arcs. Some are big, some small, and the luck averages out.

Each 100× more vnodes buys 10× less spread. 100 to 200 per server is a common choice: Memcached's ketama clients use 160 per server.

Virtual nodes fix three things at once:

  1. Balance. The table above.
  2. Removal spreads out. A crashed server's 100 arcs each pass to whichever server comes next after that arc, and those are different servers. So its load is shared by everyone instead of doubling one neighbor. Adding a server, likewise, takes a little from everyone. In a database, where the new server must first copy its keys from their old owners, that also means it copies small pieces from many servers in parallel instead of one big piece from one.
  3. Different-sized servers. A server with twice the memory gets twice the vnodes, and so about twice the keys.

The price is memory and a slightly deeper search. 100 servers × 160 vnodes is 16,000 positions, a few hundred kilobytes, and binary search over 16,000 is about 14 steps instead of 7. Every client that routes keys keeps this table, which is usually fine. (Rendezvous hashing, next, needs none of it.)

In a replicated database there is a subtler price. With 256 vnodes per node and 3 copies of each key, every node ends up sharing some key range with almost every other node. So any two nodes down at once leave some keys with only one live copy, and every repair or rebuild has to talk to the whole cluster. With one or a few points per node, two failures only hurt if the two nodes sit close together on the ring. That is why Cassandra cut its default from 256 to 16 in version 4.0, and placed those 16 carefully instead of at random so balance stays good. More vnodes is not free; pick the smallest number that gives the balance you need.

Give each server v positions on the ring. Its load becomes the sum of v small random arcs, so the spread shrinks like 1 / √v: about 10% at v = 100. Removing a server then spreads its keys over everyone, and bigger servers can get more vnodes. Cost: N × v positions in memory.

With 100 vnodes per server the spread is about 10% of a fair share. You go to 400 vnodes per server. About how big is the spread now?

Right. Spread ∝ 1 / √v, and √4 = 2, so 4× the vnodes halves it. To get 10× less spread you need 100× the vnodes. That's why nobody uses a million: the memory grows linearly and the balance only by the square root.

Think of averaging dice again. The average of 4 rolls isn't 4× steadier than one roll; it's 2× steadier. Random ups and downs partly cancel, and the leftover shrinks with the square root of how many you add. More vnodes do help (they're the whole fix), but by √4 = 2: from 10% to 5%. The table shows the same pattern: 10 → 1,000 vnodes (100×) took the spread from 30% to 3% (10×).

7Rendezvous hashing: every server bids on every key

The ring needed a circle, sorted positions, binary search and hundreds of vnodes to work well. There's a second answer, from 1996, that needs none of that (Thaler and Ravishankar called it highest random weight, HRW; most people now say rendezvous hashing).

Picture a raffle for every key. Each server draws a ticket for the key, and the highest ticket wins the key. The ticket isn't really random: it's a hash of the server's name and the key together, like stable_hash(f"{server}|{key}"), so the same server always draws the same ticket for the same key, in every process, forever. To find a key's owner, compute all N tickets and take the biggest:

def owner(key, servers):
    # one hash of (server, key) together per server; the highest wins
    return max(servers, key=lambda s: stable_hash(f"{s}|{key}"))

Now check the two properties we want.

Adding a server. The new server draws a ticket for every key. Where its ticket is the highest, it wins the key. Everywhere else, the old winner still holds the highest of the old tickets, and those didn't change. So keys only move to the new server, never between old ones. How many? With N + 1 servers drawing fair tickets, each is equally likely to have the highest: 1 / (N + 1). Minimal disruption, with no ring.

Removing a server. Its keys go to whoever had the second-highest ticket for that key. That's a different server for different keys, effectively random, so the dead server's load spreads evenly over all the others. Virtual nodes had to be added to the ring to get this; here it comes for free.

Balance is free too. Each key picks a winner at random from N servers, so with 20,000 keys over 10 servers each gets about 2,000, give or take 2%. No vnodes needed.

The cost is the lookup: N hashes for every key. With 10 cache servers that's 10 hashes, well under a microsecond each in C, so it doesn't matter. With 5,000 storage nodes on a hot path it does, and the ring wins: one hash and a binary search of about 19 steps, even with 100 vnodes per node.

One trap: the ticket must hash the server and key together. hash(server) ^ hash(key) looks similar, but XOR flips the same bits of every server's hash, so the comparison is decided by the first bit where the servers' hashes differ, and the key's bit there. The key's first few bits pick the winner, and the shares come out as halves, quarters and eighths: with 10 servers, one can get about 25% while another gets 3%, as lopsided as a ring with one point per server. (The rendezvous exercise's tests catch this.)

Rendezvous hashing: score every server with hash(server, key) and give the key to the highest score. Adding a server only takes keys it now wins (1 / (N + 1)); removing one hands each key to its runner-up, spread evenly. No ring, no vnodes, but O(N) per lookup.

With rendezvous hashing over 10 servers, server 7 dies. Where do its keys go?

Right. Every other key's winner is still alive and still holds the highest ticket, so it stays. Server 7's keys each go to whichever server had the second-highest ticket for that key, and that's a different server for different keys. The ring needs vnodes to do this; rendezvous does it with none.

There's no "next to" in rendezvous: no ring, no order of servers. Each key just has a list of tickets, one per server. If the winner leaves, the next-highest ticket wins. All the other keys still have their living winner, and nothing about their tickets changed, so they don't move at all. And server 7's runner-ups are independent random picks per key, so its keys land evenly on the other 9.

Go deeper: weights, and rendezvous with thousands of servers

Weights. To give server s a weight w (twice the memory, w = 2), turn its hash into a number u strictly between 0 and 1 and score it as -w / ln(u). Server s then wins a key with probability w / (sum of all weights), and adding or removing a server still only moves the keys it wins or loses. (This is the "logarithmic method" from Schindelhauer and Schomaker, 2005.) A naive w × hash looks right but gives the wrong shares.

Thousands of servers. N hashes per lookup gets slow. The fix is a hierarchy: group servers into, say, 70 racks of 70; pick the rack by rendezvous over 70 racks, then the server by rendezvous inside it. 140 hashes instead of 4,900. Groups also make "replicas in different racks" easy.

8Replicas: the next k different servers

A cache can lose a key and refetch it. A database can't. Storage systems keep each key on k servers (k = 3 is common), so one crash loses nothing. Where should the copies go? They need to be easy to find (every client must compute the same k servers) and they should move as little as the owner does.

On the ring the answer is: keep walking. The first server clockwise is the owner; the next ones are the replicas. With vnodes there's a catch. The next few positions may belong to the same server: positions A#17, A#52 and B#3 could be neighbors. Three copies on two machines is a lie. So you skip positions whose server you already picked, and keep going until you have k different servers. Amazon's Dynamo calls this list the preference list.

With rendezvous it's even simpler: the replicas are the servers with the k highest tickets. When one dies, the server with the (k + 1)-th ticket joins the list.

Real systems also skip servers in the same rack or zone, since one power failure or one network switch can take out a whole rack. Cassandra's NetworkTopologyStrategy does that walk: next distinct server, but also spread across racks and data centers.

k replicas on the ring = keep walking clockwise and take the first k distinct servers, skipping extra vnodes of servers you already have. With rendezvous, take the k highest scores.

You want 3 copies of a key. Walking clockwise from it, the next positions belong to B, B, C, B, A, D. Which servers hold the copies?

Right. Take B, skip the second B, take C, skip the third B, take A. Three copies on three different machines. If you'd taken B, B, C, losing B would lose two of your three copies at once.

The point of 3 copies is that 3 different machines must fail before you lose the key. Positions are not machines: with vnodes, one server has many positions, and they can sit next to each other. So walk the list and keep only servers you haven't picked yet: B (new), B (skip), C (new), B (skip), A (new). Stop: B, C, A.

9Every process must get the same answer

Consistent hashing only works if every client computes the same owner for the same key. In the Black Friday shop, 200 web servers each run their own copy of the routing code. If two of them disagree about where user:42 lives, one writes it to server A and the other looks for it on server C, and the cache is useless again.

Python's built-in hash() breaks this for strings. Since Python 3.3, every process picks a random secret seed at startup and mixes it into the hash of every str and bytes. It's a defense against hash flooding (attackers crafting keys that all collide, see Hash maps). The result: the same string hashes differently in every process.

$ python3 -c 'print(hash("user:42"))'
5058836470753863480
$ python3 -c 'print(hash("user:42"))'
6002988770975417973

Two runs, two answers. Within one process it's consistent, so tests on one machine pass and the bug only shows up in production. (Setting PYTHONHASHSEED everywhere would make it repeatable, but it switches off that defense, and other languages hash differently anyway.)

So use a hash defined by a published algorithm, which gives the same bits everywhere: MD5 or SHA-1 from hashlib (fine here: we need spread, not security), or faster non-cryptographic ones like MurmurHash3 (Cassandra) or xxHash. Take 8 bytes of the digest as a 64-bit number.

Integers have the opposite problem: hash(42) is 42 in every process, but that's no spread at all. User ids 1 to 1,000,000 would all land in a sliver at the very start of a 2⁶⁴ ring, less than a millionth of a millionth of it, and the one server just after that sliver would own every key. The hash must be deterministic and scattering.

The hash isn't the only thing that must match. Every client also needs the same vnode labels ("A#17"), the same vnode count and, hardest of all, the same list of servers. If half the clients have heard that server E joined and half haven't, they route differently until the news spreads. Real systems keep the server list in one coordination service (ZooKeeper, etcd) or spread it by gossip (Dynamo, Cassandra), and accept a short window of disagreement.

Every client must compute the same owner, so the hash must give the same bits in every process and on every machine. Python's hash() on a str is randomly seeded per process: never use it for routing. Use hashlib (or Murmur, xxHash) and agree on the server list.

A team builds a perfect ring with vnodes, using Python's hash(f"{name}#{i}") and hash(key). It runs on 50 web servers. What happens?

Right. Each process gets its own random seed, so each web server places the vnodes and the keys at different spots. A key written through one web server is looked up somewhere else through another. It passes every test on a laptop, because inside one process the hash is stable.

Within one process, hash("user:42") is the same every time, which is why this bug survives testing. But each new process picks a fresh random seed for string hashes (try running python3 -c 'print(hash("a"))' twice). 50 web servers are 50 processes with 50 different rings. That's not an upgrade problem; it happens on every restart.

10Other designs and real systems

Fixed slots: many more pieces than servers

The most common alternative avoids the problem instead of solving it. Cut the key space into a fixed number of slots, far more than you'll ever have servers, and never change that number. Redis Cluster uses 16,384 slots: slot = CRC16(key) % 16384, where CRC16 is a simple 16-bit hash. A separate, small table says which server owns each slot. Adding a server means moving whole slots to it: with 5 servers going to 6, move about 2,730 of the 16,384 slots, about 1/6 of the data. The % never changes, so nothing else moves.

This is the same trick as vnodes, with a twist: the slots are equal-sized and you choose who owns each one, instead of letting a hash decide. Elasticsearch (a fixed number of primary shards per index), Riak (64 partitions by default) and Dynamo's later design work the same way. The price: you must pick the slot count up front. (Why not a table entry per key? With billions of keys the table would be as big as the data; a table of 16,384 slots fits in every client.)

Kafka is the cautionary tale: a record goes to partition murmur2(key) % partitions. Add partitions to a topic and most keys map to a new partition, while their older messages still sit in the old one.

A Kafka topic has 12 partitions, and messages are keyed by user id so that each user's events stay in order. You raise it to 16 partitions. What happens?

Right. Partition = hash % 12 before and hash % 16 after, the exact problem from section 2. Only keys with the same remainder for both stay put. A user whose old events are still waiting in partition 3 now writes to partition 11, and a consumer can process the new events first. That's why teams pick a generous partition count up front.

Kafka's default partitioner is plain hash(key) % partitions, with no ring and no slots. So changing 12 to 16 changes the partition for most keys, old users included (a key stays only if its hash gives the same remainder for 12 and 16, which is just 1 key in 4). Kafka doesn't move existing messages either. A user's old events sit in the old partition and new ones go to another, so they can be consumed out of order.

Go deeper: jump consistent hash (no memory at all)

Google's jump consistent hash (Lamping and Veach, 2014) maps a key to one of n buckets numbered 0 to n − 1 using no table at all, just a loop of a few lines. Imagine growing from 1 bucket to n, one at a time. When the count goes from b to b + 1, a key should jump to the new bucket with probability 1 / (b + 1): exactly the share the new bucket deserves, and keys never move between old buckets. The algorithm uses the key as a random seed to skip straight from one jump to the next. Jumps get rarer as b grows, so it takes about ln n steps: 21 for a billion buckets.

Every bucket's expected share is exactly 1/n, the spread is as even as a fair random pick, and it needs zero memory. The catch: buckets are numbers, and you can only add or remove the last one. If bucket 3 of 10 dies, you can't remove just it. So it fits storage shards that only grow (with each shard replicated, so a "bucket" never dies), not caches whose servers come and go. Exercise 7 has you write it.

Go deeper: Maglev, the load balancer's version

Google's Maglev network load balancer (2016) spreads packets over backends and must keep each connection on the same backend. It needs O(1) lookups at line rate, so it builds a lookup table with a prime number of entries (65,537 in the paper). Each backend gets its own random order of the table's slots, from two hashes of its name. The backends take turns, each claiming its next preferred empty slot, until the table is full. A packet's backend is table[hash(connection) % 65537].

Every backend gets almost exactly the same number of slots, so balance is near perfect. Removing a backend moves its slots and a few others: slightly more than minimal disruption, traded for balance and speed. Maglev also remembers recent connections, so a table change doesn't break them. Envoy offers both a ring hash and a Maglev load-balancing policy.

Go deeper: bounded loads, for hot keys

Even with a perfect spread of keys, the requests may not be spread: one viral video gets a million requests and they all go to its one server. Consistent hashing with bounded loads (Mirrokni, Thorup and Zadimoghaddam, 2016) gives every server a cap of about (1 + ε) × the average load, for example 1.25×. A request walks clockwise as usual, but if its server is full it keeps walking to the next server with room. Loads can never pass the cap, and keys still move very little when servers change. Vimeo added it to HAProxy (the hash-balance-factor setting) for its video caches.

11What to say in the interview

In a system design round this comes up as "and what happens when you add a cache node?" or "how do you shard this?". A strong answer sounds like this:

  1. Name the problem with numbers: "With hash % N, going from N to N + 1 moves N / (N + 1) of the keys, 80% at 4 → 5. For a cache that's a stampede on the database."
  2. Give the fix: "Consistent hashing: servers and keys on a ring, each key goes to the next server clockwise, a sorted list and binary search, O(log N). Adding a server moves only about 1/N of keys, onto it."
  3. Pre-empt the follow-up: "With one point per server the arcs are very uneven, about 3× for the busiest with 10 servers, so I'd use 100 to 200 virtual nodes. That also spreads a dead server's load over everyone and lets bigger machines take more."
  4. Show you know the alternatives: "With a few dozen servers, rendezvous hashing is simpler: score every server, take the highest, no vnodes. Or, like Redis Cluster, fixed slots with an ownership table, which makes rebalancing an explicit operation."
  5. Close the details: "Replicas go on the next k distinct servers, ideally in different racks. The hash must be deterministic across processes, so MD5 or Murmur, never a seeded language hash. And if one key is hot, hashing can't help: replicate it or use bounded loads."

✓What to remember

  1. hash % N moves N / (N + 1) of keys when N grows by one: 80% for 4 → 5. The minimum is 1 / (N + 1), all onto the new server.
  2. The ring: hash servers and keys onto a circle; a key belongs to the first server clockwise. Sorted positions plus binary search: O(log N).
  3. Adding a server moves only the keys in its arc, about 1 / (N + 1). Removing one moves only its keys, but without vnodes they all go to one neighbor.
  4. One random point per server gives very uneven arcs (busiest about 3× fair with 10 servers). v virtual nodes per server shrink the spread like 1 / √v: about 10% at v = 100.
  5. Rendezvous: every server scores the key with hash(server, key); the highest wins. Minimal disruption, even load and even failover with no vnodes, but O(N) per lookup.
  6. Replicas: the next k distinct servers clockwise (skip extra vnodes), or the k highest rendezvous scores.
  7. The hash must give the same answer in every process: hashlib or Murmur, never Python's seeded hash() on strings.
  8. Alternatives: fixed slots with an ownership table (Redis Cluster), jump hash (no memory, numbered buckets), Maglev (O(1) table for load balancers), bounded loads (caps for hot spots).

✎Exercises

Do the warm-ups on paper first. The coding exercises are in exercises/consistent_hash.py, exercises/rendezvous_hash.py and exercises/jump_hash.py. Their tests count your hash calls, check how many keys move, and time lookups on a ring of 100,000 points, so a linear scan fails. Run them with python3 -m pytest -k "consistent_hash or rendezvous or jump_hash".

Warm-up · pen and paper

1. Count the movers

(a) For hashes 0 to 41, write h % 6 and h % 7. How many keys keep their server? Does it match 1 / (N + 1)? (b) Do 6 → 12 the same way. Which keys move, and where to? (c) Without writing them all out: how many of the hashes 0 to 59 keep their server going from 4 to 6 servers? (Hint: list the pairs of remainders that can match.)

Answers

(a) Only hashes 0 to 5 keep their server (both remainders are h itself): 6 of 42 = 1/7 = 1 / (N + 1). Yes. (b) Hashes with h % 12 from 0 to 5 stay; those with h % 12 from 6 to 11 move from server h % 6 to the new server h % 12 (hash 7: server 1 → server 7). Half move, all onto the 6 new servers, the minimum. (c) The pattern repeats every 12 hashes (the smallest number both 4 and 6 divide). A remainder by 4 is 0 to 3, so the only matches are h % 12 = 0, 1, 2, 3: 4 in every 12, so 20 of the 60 stay and 40 move. That's two thirds, while the minimum is one third (the 2 new servers' share).

Warm-up · pen and paper

2. Trace a ring with vnodes and replicas

On a 0–99 ring: A at 5, 50; B at 20, 70; C at 35, 90. (a) Who owns keys at 0, 21, 49, 95? (b) What are the 2 replicas (2 distinct servers) for keys at 15 and 85? (c) B dies. Who gets each of B's two arcs? Compare with what would happen if each server had one position. (d) What share of the ring does each server own? How far is that from a third?

Answers

(a) 0 → A (5), 21 → C (35), 49 → A (50), 95 → A (wraps to 5). (b) 15: B at 20, then C at 35 → [B, C]. 85: C at 90, then A at 5 → [C, A]. (c) B's arc 6–20 goes on to C at 35; B's arc 51–70 goes on to C at 90. Both to C, just by bad luck in this small example: with 2 vnodes each, C happens to follow both of B's points. With many vnodes, B's arcs would go to many different servers. (d) A: 91–5 (15) + 36–50 (15) = 30%; B: 6–20 (15) + 51–70 (20) = 35%; C: 21–35 (15) + 71–90 (20) = 35%. Fairly close to a third; two points each is still too few to count on it.

Warm-up · pen and paper

3. Pick the scheme

Which would you use, and why? (a) 8 Memcached servers, routed by the web app's client library. (b) A storage system with 3,000 nodes, 3 replicas per key, nodes failing every day. (c) A network load balancer sending millions of packets a second to 50 backends. (d) An event pipeline keyed by user id that may need more partitions next year. (e) A cluster where half the machines have twice the memory.

Answers

(a) Either works; rendezvous is the least code and needs no vnodes for balance, and 8 hashes per lookup is nothing. A ketama ring is the classic answer. (b) A ring with vnodes or fixed slots: O(log) or O(1) lookups at 3,000 nodes, replicas as the next 3 distinct nodes in different racks (rendezvous would need 3,000 hashes per lookup, or a hierarchy). (c) Maglev-style table: O(1) per packet, near-perfect balance, plus connection tracking so existing connections survive changes. (d) Fixed slots: create far more partitions than you need now (say 256) and move whole partitions later, since hash % partitions would remap everyone. (e) Weights: twice the vnodes on the ring, or weighted rendezvous.

Core · code

4. stable_hash and ConsistentHashRing: owners, add, remove

In consistent_hash.py: a 64-bit hash from hashlib, then a ring with vnodes points per node, labelled f"{name}#{i}", and get_node by binary search with wraparound. The tests check exact owners on a toy clock and against a brute force, that adding an 11th node to 10 moves about 9% of keys and only onto the new node, and that vnodes balance the load. They wrap your hash function in a counter (one call per lookup, exactly vnodes per add), time 50,000 lookups on a ring of 100,000 points, and run your code in two processes with different PYTHONHASHSEEDs to catch hash().

Core · code

5. get_nodes(key, k): replicas on the ring

Same file. Keep walking from the owner and return the first k distinct nodes, wrapping around. The tests check the order against a brute-force walk, that extra vnodes of a node you already have are skipped, and that you return all nodes when there are fewer than k. 150,000 calls on the 100,000-point ring run under a time cap, so walking the whole ring every time fails, and so does copying or slicing the point list per call: stop as soon as you have k.

Core · code

6. RendezvousHash: highest score wins

In rendezvous_hash.py: score = hash_fn(f"{node}|{key}"), highest wins, ties to the larger name. get_nodes(key, k) returns the top k. The tests check that adding a node only takes keys it wins, that a removed node's keys each go to their old second choice, and that 10 nodes balance within 15% with no vnodes. Your hash calls are counted: at most N per lookup, even for get_nodes(key, 25), so rescoring every node for each of the k picks fails.

Stretch · code

7. jump_hash(key, num_buckets)

In jump_hash.py: the Lamping–Veach algorithm from the Go deeper box in section 10, with its exact 64-bit generator, so your numbers match the paper's C++ code (the tests hard-code 14 of them). They also check that growing from n to n + 1 buckets moves keys only into bucket n, and run 2,000 keys with 2³¹ − 1 buckets under a time cap: checking every bucket count from 1 to n takes billions of steps. Before coding, explain why the jump probability must be 1 / (b + 1).

Stretch · measure

8. Measure the spread

With your ring, place 10 nodes and 100,000 keys for v = 1, 4, 16, 64, 256 and 1,024 vnodes. For each, record the busiest node's share divided by 10% and the standard deviation of the shares. Plot std dev against v on log-log axes: is the slope −½, as 1 / √v predicts? Then count the keys that move when you add an 11th node with % N, your ring, and your rendezvous hash. Which ones match 1/11?

Stretch · explain

9. Say it out loud

Set a 4-minute timer. An interviewer asks: "Your cache has 20 nodes behind a ring. One node gets 5× the traffic of the others. Why, and what do you do?" Cover: too few vnodes (uneven arcs) versus one hot key (no hash fixes that), how to tell the two apart, and the fixes for each (more vnodes or weights; replicate the hot key, a small local cache in front, or bounded loads).
