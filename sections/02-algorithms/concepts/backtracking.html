Chapter 2 · Part 6

Recursion and backtracking

P0 asked almost everywhereabout 55 minutes10 quick checks · 9 exercises

Some questions want every answer: every subset of a list, every ordering, every way to fill a board without breaking a rule. You can't write those with a fixed number of loops, because the number of choices is only known when the code runs. Recursion solves that, and backtracking is the search built on top of it. Interviewers like these problems because the template is short but the bugs are subtle, and the running time grows faster than people guess.

By the end you'll be able to

  1. Write a recursive function by naming its base case and its smaller problem, and trace its call stack.
  2. Draw the decision tree for subsets, permutations and combinations, and count its leaves: 2n, n! and C(n, k).
  3. Write choose → explore → un-choose from memory, and explain why you save a copy of the path.
  4. Prune branches that break a rule, can't reach the goal, or repeat a branch you've already explored.
  5. Estimate the cost as nodes × work per node, and say when to switch to dynamic programming.

How to read this: top to bottom. It builds on How fast is your code? (2n and n! growth) and Exploring graphs (depth-first search). Answer each quick check before reading on; a wrong answer gets you a second explanation. "Go deeper" boxes are optional on a first read.

1The problem: loops you can't write

Your app has 3 feature flags, each on or off. Before every release, QA tests each combination: 2 × 2 × 2 = 8 configurations. You write three nested loops, and it works.

Next sprint a fourth flag ships, so you add a fourth loop. Then a fifth. Then product adds a rule: dark_mode and legacy_ui can never both be on. And the release manager wants every order in which to turn on 6 flags, one per day: 720 orders, which as loops means 6 nested loops, each checking that its flag isn't already taken.

configs = []
for a in (False, True):
    for b in (False, True):
        for c in (False, True):          # one loop per flag...
            configs.append((a, b, c))    # ...so 6 flags need 6 loops

The trouble isn't speed. It's shape. The number of loops is fixed when you write the code, but the number of flags is only known when it runs. What we want to say is "decide flag 1, then do the same thing for the rest". A function that calls itself can say exactly that.

The numbers also warn us. 10 flags give 1,024 configurations, 20 give 1,048,576, 30 give over a billion. So we need two things: a way to walk through every choice, and a way to skip choices that can't work, like any configuration with both dark_mode and legacy_ui on.

The list of flags comes from a config file. What stops you from writing "every on/off combination" with for-loops?

Right. Each flag needs its own level of looping, and code has a fixed number of levels. Recursion gives you one more level on demand: each call handles one flag and calls itself for the rest.

Count the loops, not the steps. Three flags need three nested loops; seven flags need seven. The loops aren't slow (any method has to produce all 2n combinations), and a loop can skip things with continue. The problem is that you'd need a different program for every number of flags. A function that handles one flag and calls itself for the remaining ones works for any count.

2Recursion: a smaller copy of the same problem

You're in a long line at a cinema and want to know your position. You can't see the front, so you ask the person ahead of you. They don't know either, so they ask the person ahead of them, and so on, until the question reaches the first person, who knows without asking: "1". Each person then adds 1 and passes the answer back.

That's recursion: a function that solves a problem by calling itself on a smaller version of the same problem. It has two parts:

  • A base case: an input small enough to answer directly. (The first person in line.)
  • A recursive case: shrink the problem, call yourself on the smaller one, and build your answer from its answer. (Ask the person ahead, add 1.)
def total(nums):
    if not nums:                      # base case: an empty list adds up to 0
        return 0
    return nums[0] + total(nums[1:])  # first number + the total of the rest

Trust the recursive call. Don't trace total(nums[1:]) all the way down in your head; that's how people get lost. Assume it returns the right total for the shorter list, and check only two things: the base case is right (an empty list sums to 0), and every call moves toward it (nums[1:] is one shorter). If both hold, it works for every length: it works for 0, and whenever it works for one length it works for the next. That argument is induction, and it's why recursion is safe to trust. (One cost note: nums[1:] copies the rest of the list each time, about 500,000 item copies for 1,000 numbers. Passing an index avoids it.)

A recursive function needs a base case it can answer directly, and a step that shrinks the problem and trusts the call to solve the smaller version. Check those two things; don't trace the whole chain in your head.
Explain it another way: handing off to an assistant

You're asked to add up 100 receipts. You keep the top one, hand the other 99 to an assistant ("add these up and tell me"), and add your receipt to whatever they say. You don't care how they do it. They do the same with 98, and so on, until someone is handed an empty stack and says "0" without asking anyone. The trust is only safe because the stack really gets smaller each time, and someone really does get the empty stack.

This counts how many times you can halve n before reaching 1. halvings(8) returns 3. What does halvings(0) do?

def halvings(n):
    if n == 1:
        return 0
    return 1 + halvings(n // 2)

Right. 0 // 2 is 0, so halvings(0) calls halvings(0) forever. The input never shrinks, so the base case is never reached, and Python stops it after about 1,000 calls. The fix is a base case every input can reach: if n <= 1.

Apply the two checks. Does the input shrink? From 0, the next call is halvings(0 // 2), which is halvings(0) again. Nothing ever returns, so nothing can come back as 0 or 1. Python gives up with a RecursionError after about 1,000 nested calls. "Every call moves toward the base case" has to hold for every input, not just the ones you tried.

3The call stack: where paused calls wait

When total([3, 1, 4]) calls total([1, 4]), the first call isn't finished. It's paused halfway through 3 + total(...), waiting. Every call gets a frame: a small record of its own local variables (its own nums) and where to continue. Frames pile up on the call stack like plates. Only the top one runs. When it returns, its frame is thrown away and the one below wakes up with the answer.

The call stack for total([3, 1, 4]), newest frame on top. Blue is the call that's running; the ones below are paused, each with its own nums. Step with ▶| and watch it grow to 4 frames, then shrink as the answers come back.
  • Memory is set by depth, not by the number of calls. A list of n numbers needs n + 1 frames at the deepest point.
  • Depth has a hard limit. Python allows about 1,000 frames (sys.getrecursionlimit() returns 1000); go deeper and you get a RecursionError. Backtracking trees are usually shallow (their depth is the number of choices, like 20 flags), so this rarely bites them. It does bite recursion over long lists, or a recursive DFS down a graph path of 5,000 nodes.
Every call that hasn't returned has a frame on the stack with its own local variables. Memory is set by the deepest chain of waiting calls, and Python caps that chain at about 1,000.

You call the recursive total on a list of 10,000 numbers. What happens?

Right. Every number adds a paused call, and none can finish until the empty list is reached, so all 10,001 frames exist at the same moment: ten times the limit. For plain list processing, use a loop. Recursion earns its keep when the depth is small and the branching is the hard part.

Picture the plates. total of 10,000 numbers can't finish until total of 9,999 does, which can't finish until… so all 10,001 calls are on the stack at once. The base case would be reached (the list does shrink), but Python stops at about 1,000 plates and raises RecursionError long before that.

Go deeper: raising the limit, or using your own stack

sys.setrecursionlimit raises Python's counter, but frames also use the real thread stack, and set too high the interpreter can crash outright. Python has no tail-call optimization either. The robust fix is a loop with a list you manage as the stack, each entry holding what a frame would hold. Here is the take-or-skip search from the next section that way:

def subsets_iterative(items):
    result, stack = [], [(0, [])]           # (next index, path so far)
    while stack:
        i, path = stack.pop()
        if i == len(items):
            result.append(path)
            continue
        stack.append((i + 1, path))               # skip items[i]
        stack.append((i + 1, path + [items[i]]))  # take items[i] (popped first)
    return result

No list is ever changed after it's made (taking an item builds a new one), so nothing needs undoing, at the price of a copy per take. Section 4 explains that trade-off.

4The decision tree, and choose → explore → un-choose

This is the most important section of the chapter. Everything after it is the same idea with a different kind of choice.

Every answer is a path

Call the flags items 1, 2 and 3. Building one configuration is a series of decisions: take item 1 or skip it, then item 2, then item 3. Draw every possible series and you get a tree:

                                   []
                         +1/                  \−1
                 [1]                                 []
            +2/         \−2                     +2/         \−2
       [1,2]              [1]               [2]               []
     +3/    \−3        +3/    \−3        +3/    \−3        +3/    \−3
 [1,2,3]   [1,2]    [1,3]     [1]     [2,3]     [2]      [3]      []

+2 means "take item 2", −2 means "skip item 2". Each node shows the path so far.

Each level is one decision. Each node is a partial answer. Each leaf (a node with nothing left to decide) is one complete answer, spelled out by the path from the root down to it. Every level doubles the node count, so n decisions give 2n leaves and 2n+1 − 1 nodes: 8 subsets from 15 nodes for 3 items, 1,048,576 from 2,097,151 for 20.

Backtracking is a depth-first walk of this tree. It's the DFS from the last chapter with one twist: the tree is never stored. Each node exists only while you stand on it, as the current contents of one list.

Walking the tree with one shared list

We keep one list, path, holding the choices from the root to where we stand. Three moves at every node:

  1. Choose: change path to make one choice.
  2. Explore: recurse to make the remaining choices.
  3. Un-choose: undo exactly that change, so path is back to what it was before you chose.
def subsets(items):
    result, path = [], []
    def explore(i):                  # decide items[i]
        if i == len(items):          # nothing left to decide: a leaf
            result.append(path[:])   # save a COPY of the path
            return
        path.append(items[i])        # choose: take items[i]
        explore(i + 1)               # explore everything that includes it
        path.pop()                   # un-choose: path is as it was
        explore(i + 1)               # explore everything that skips it
    explore(0)
    return result
The code above on [1, 2, 3]. Blue is the node you're on, blue edges are the current path, green nodes are finished. Watch path grow on the way down and shrink on the way back. Then switch the menu to save path (the bug) and play it again: every saved entry changes at once.
Backtracking is a depth-first walk of the decision tree with one shared path. Choose (change the path), explore (recurse), un-choose (undo that exact change). At a leaf, save a copy.

Why un-choose?

Because there's only one path for the whole search. After the leaf [1, 2, 3], the code must visit [1, 2]: the same path without the 3. Delete the pop() and every branch inherits whatever earlier branches added. On [1, 2, 3] you get:

[[1,2,3], [1,2,3], [1,2,3,3], [1,2,3,3], [1,2,3,3,2,3], [1,2,3,3,2,3], [1,2,3,3,2,3,3], [1,2,3,3,2,3,3]]

Un-choose is what makes "standing on a node" mean something: when you come back to a node, the shared state is exactly what it was when you left.

The classic bug: saving the path instead of a copy

Write result.append(path) instead of result.append(path[:]). A Python variable holds a reference to a list (an arrow pointing at it), not the items. So result ends up with 8 arrows to the same single list. That list keeps changing, and when the search ends every append has been popped, so you get [[], [], [], [], [], [], [], []]. path[:] (or list(path)) makes a snapshot that later changes can't touch. Copying up to n items at each leaf is part of the real cost (section 10).

Explain it another way: a maze and a chalk line

You explore a maze drawing a chalk line behind you. At a fork you pick a corridor (choose) and walk it (explore). At a dead end you walk back to the fork, erasing the chalk as you go (un-choose), and try the next corridor. The chalk always shows the route from the entrance to where you stand. At an exit, a photo of the chalk line records the route; a note saying "the route is the chalk line" doesn't, because the chalk will be erased. path[:] is the photo.

A friend's code collects the subsets of ["a", "b"] but prints [[], [], [], []]. Which line is the bug?

def explore(i):
    if i == len(items):
        result.append(path)        # line A
        return
    path.append(items[i])          # line B
    explore(i + 1)
    path.pop()                     # line C
    explore(i + 1)

Right. All four entries are the same list object, and by the end every append has been undone by a pop, so you see one empty list four times. Line C is correct and needed: without it the second branch would still hold the first branch's items.

Count the objects, not the lines. How many lists does this program make? One: path. Line A puts a reference to it into result four times. Line C does remove items, but from the shared list, and that's needed so the next branch starts clean; it only damages the results because they are the shared list. Line B is the choose step; it has to change path, or there'd be nothing to save. Save a snapshot at line A, result.append(path[:]), and later pops can't reach it.

Go deeper: copying instead of undoing

You can skip un-choose by passing a new list down: explore(i + 1, path + [items[i]]). No undo, no aliasing bug, but a copy of up to n items at every node instead of only at the leaves. For subsets that's still O(n · 2n), since the tree has about twice as many nodes as leaves, so it's fine in an interview if you name the trade-off. Undoing wins when the state is big: copying a sudoku grid is 81 writes, undoing one placement is 1.

5Permutations: when order matters

Back to the release manager: turn on 6 flags, one per day, in every possible order. Now a choice isn't "take or skip" but "which flag goes next?". Day 1 has 6 options, day 2 the 5 left, and so on: 6! = 720 orders. An ordering of all the items is a permutation, and n items have n! of them.

                          []
                 a/        |b       \c
        [a]               [b]               [c]
      b/   \c           a/   \c           a/   \b
  [a,b]    [a,c]    [b,a]    [b,c]    [c,a]    [c,b]
    |c       |b       |c       |a       |b       |a
 [a,b,c]  [a,c,b]  [b,a,c]  [b,c,a]  [c,a,b]  [c,b,a]

The new question at every node is "which items are still free?". We keep a used list of booleans, one per input position, as part of the shared state:

def permutations(items):
    result, path = [], []
    used = [False] * len(items)          # used[i]: is items[i] already in path?
    def explore():
        if len(path) == len(items):      # every item placed: a leaf
            result.append(path[:])
            return
        for i in range(len(items)):      # try each free item in the next spot
            if used[i]:
                continue
            used[i] = True               # choose (two changes...)
            path.append(items[i])
            explore()                    # explore
            path.pop()                   # un-choose (...so undo both)
            used[i] = False
    explore()
    return result
  • Un-choose undoes every change the choose made, here two. Forget used[i] = False and that item is gone for the rest of the search.
  • Track positions, not values. if items[i] in path seems to work, but it's O(n) per check, and with two equal values the second one looks "already used". used[i] is O(1) and doesn't care about values.

Size: 3 items give 6 leaves and 16 nodes; 4 give 24 and 65; 10 give 3,628,800 leaves and 9,864,101 nodes. The total is always about 2.718 × n! (e × n!). The last two levels have n! nodes each (once n − 1 items are placed, the last one is forced), so they hold about three quarters of the tree, and listing all permutations costs O(n · n!) with the copies.

Permutations: each level picks the next item from the ones not used yet: n, then n − 1, then n − 2 choices, n! leaves. used is part of the state, so un-choose resets it along with path.

You delete the if used[i]: continue check and run the code on [1, 2, 3]. What comes out?

Right. Every one of the 3 levels can now pick any of the 3 items: 3 × 3 × 3 = 27 sequences, repeats included. It still stops, because the base case is about the path's length, which still grows by one per level.

Ask what's still true. The base case still fires at 3 items and each level still adds one, so the search ends. What's gone is "each item only once": level 1 has 3 choices, level 2 has 3 again, level 3 has 3 again. That's 27 leaves instead of 3 × 2 × 1 = 6, and some are [1, 1, 1]. The branching shrinks by one per level only because of used.

Go deeper: a bitmask as the used set

The whole used list can be one integer (the bit manipulation chapter builds this up): bit i is 1 when item i is used. Test with mask & (1 << i), pass explore(mask | (1 << i)), and there's nothing to un-choose, because each call gets its own integer. The bigger payoff: the mask is a small hashable summary of "which items are placed", so it can be a cache key. Visiting 15 cities in the best order has 15! = 1,307,674,368,000 orders, but only 215 × 15 = 491,520 pairs of (cities visited, current city). Caching by those pairs is dynamic programming, the next chapter.

6Combinations: the start index

New request: pick 3 of your 10 engineers for an on-call rotation. Order doesn't matter now: {Ana, Bo, Cy} is one team however you list it. That's a combination. The permutation code stopped at 3 items gives 10 × 9 × 8 = 720 ordered triples, with every team appearing 3! = 6 times. There are only 720 / 6 = 120 teams.

The fix is one rule: only pick items that come after the last item you picked. Then each team can be built only one way, in increasing order: {1, 4, 7} comes out as 1 → 4 → 7, never 4 → 1 → 7, because after 4 you may only look at 5 and up. In code, each call gets a start: the first item it may use.

                       []
                1/        \2   \3
         [1]               [2]       [3]
      2/  |3  \4         3/   \4      |4
 [1,2]  [1,3]  [1,4]  [2,3]  [2,4]  [3,4]

Choosing 2 of 1..4. After picking x, the next level starts at x + 1. Nothing starts with 4: no bigger number would be left to pair it with.

def combinations(n, k):                   # all k-sized subsets of 1..n
    result, path = [], []
    def explore(start):
        if len(path) == k:
            result.append(path[:])
            return
        need = k - len(path)               # how many more we must pick
        for x in range(start, n - need + 2):   # leave room for the rest
            path.append(x)                 # choose x
            explore(x + 1)                 # only numbers bigger than x after it
            path.pop()                     # un-choose
    explore(1)
    return result

The loop's upper end is a first taste of pruning. If we still need 2 numbers, starting at n is pointless: nothing would be left after it. For choosing 10 of 20, that bound cuts the tree from 616,666 nodes to 352,716, with the same 184,756 answers.

Every node of this tree is a set in increasing order. Drop k, save path[:] at every node, and let the loop run to n, and you get every subset exactly once. That "loop form" of subsets is what section 8 builds on.

Combinations: give each call a start index and only pick items after the last one picked. Each set comes out exactly once, in increasing order: C(n, k) leaves instead of k! copies of each.

To choose 2 of [a, b, c, d], someone uses the permutation code (loop from index 0 every time, skip used items) and stops at 2 items. How many lists come out?

Right. 4 choices, then 3: 4 × 3 = 12 ordered pairs, and each of the C(4, 2) = 6 pairs appears in 2 orders. A start index removes the second order, because after picking b you can't go back to a.

Count the branches. Level 1 loops over 4 items; level 2 loops from index 0 again, skipping only the one already used: 3 options, so 4 × 3 = 12 leaves. (16 would need an item paired with itself, which used prevents.) Those 12 include both [a, b] and [b, a]. Picture a roster you may only read downward: you'd tick a before b every time, so each pair could be written only one way. That's what the start index enforces.

7Pruning: cut dead branches early

The trees grow brutally, but in real problems most branches are hopeless long before they reach a leaf. Pruning means asking, before you walk down a branch, "can anything below here be an answer?". If not, you skip the branch and its whole subtree, which might be millions of nodes. Almost every pruning trick is one of three cuts:

  1. The path already breaks a rule. With dark_mode and legacy_ui both on, no choice for the other flags can fix it.
  2. The path can't reach the goal anymore. You need a sum of 10 and you're at 12; or you need 2 more items and 1 is left (section 6's bound). When the question asks for the best answer, the same cut is called branch and bound: drop a branch when even its best possible outcome can't beat the best answer found so far.
  3. The branch repeats one already explored. Two equal values at the same spot (section 8), or the mirror image of a board you've searched.

The N-Queens puzzle

Place n queens on an n × n chessboard so no two attack each other (a queen attacks along its row, its column and both diagonals). Each row gets exactly one queen, so level r of the tree decides the column of the queen in row r. Without pruning that's nn complete boards: for 8 × 8, 16,777,216 boards to build and check.

With cut 1, we check each square before placing a queen, and skip it if an earlier queen attacks it. Three sets make the check O(1): cols for used columns, diag for used "\" diagonals (every square on one has the same row − col), and anti for used "/" diagonals (same row + col).

def count_queens(n):
    cols, diag, anti = set(), set(), set()
    def place(row):
        if row == n:
            return 1                       # a queen in every row: one solution
        found = 0
        for c in range(n):
            if c in cols or row - c in diag or row + c in anti:
                continue                   # attacked: prune this whole branch
            cols.add(c); diag.add(row - c); anti.add(row + c)          # choose
            found += place(row + 1)                                    # explore
            cols.remove(c); diag.remove(row - c); anti.remove(row + c) # un-choose
        return found
    return place(0)
The code above on a 4 × 4 board, rows and columns counted from 0. The square with the thick outline is the one being checked; red squares are attacked by queens already placed. Every attacked square the search skips is a subtree it never builds. Step to the end for the counts.

On 4 × 4 the pruned search places 16 queens (checking 60 squares) to find both solutions, against 256 complete boards. On 8 × 8 it places 2,056 queens and checks 15,720 squares to find all 92 solutions. Counting the empty board, that's 2,057 nodes instead of the unpruned tree's 19,173,961: over 9,000 times fewer.

Look at the growth column: from n = 6 on, each extra row multiplies the work by a factor that itself keeps rising. A polynomial doesn't do that (n3 grows by about × 1.25 from n = 13 to 14). With one queen per row and per column the tree can't have more than n! leaves, and nobody knows a polynomial-time way to count all the solutions. (Finding just one solution is a different question: for every n ≥ 4 there are known formulas that place the queens directly, no search needed.) So the sentence for the interview is: pruning can cut the work by thousands of times, but a search that grows exponentially usually still does, just more slowly. It's still worth doing: 19 million nodes versus 2 thousand is "too slow" versus "instant".

Cut 2 gets stronger with sorted input. Picking numbers to reach a target, with 4 left to go: if the numbers are sorted and the current one is 5, every later one is at least 5 too. So you don't skip one branch, you break out of the loop and skip them all with one comparison.

Prune a branch as soon as it breaks a rule, can't reach the goal, or repeats one you've explored. Make each check O(1) (sets, running sums), and sort when it lets one check rule out everything after it. Pruning can cut the work by thousands of times; the worst-case bound stays exponential.

Pruning took 8-queens from 19 million nodes to about 2,000. Is the pruned search that counts all solutions now a polynomial-time algorithm?

Right. One data point fits any curve; the growth rate shows the shape. For n4 the factor shrinks toward 1 as n grows: (9/8)4 ≈ 1.6, (15/14)4 ≈ 1.3. Here it keeps growing, from about 3 to about 6. Pruning cut the work enormously; the growth is still exponential.

Test the guess against the table. If the work were n4, going from 13 to 14 rows would multiply it by (14/13)4 ≈ 1.35. The real factor is about 5.9, and it rises every row: that's exponential growth, whatever the count at n = 8 happens to be. And pruning helps whether or not solutions exist: it removes attacked squares in every branch, including the ones that lead to the 92 solutions.

Go deeper: mirror images, and failing fast

Cut 3 on a board. Flip an N-Queens solution left to right and you get another one. So try the first-row queen only in the left half of the columns and double the count. For odd n, also try the middle column but don't double those: their mirror images also start in the middle column, so the search finds them anyway. The same idea applies when splitting numbers into k groups of equal sum: empty groups are interchangeable, so if a number fails in one empty group, trying it in another explores a mirror copy. Exercise 7 tests exactly that.

Fail first. When you can choose the order, try what's most likely to fail early. A dead end found at depth 2 removes a big subtree; found at depth 12, almost nothing. That's why exercise 7 places big numbers first, and why the sudoku solver in the next section fills the most constrained cell first.

8Duplicates in the input

So far the items were all different. Take the subsets of [1, 2, 2]: the take-or-skip tree treats the two 2s as different items, so it makes 8 subsets, with [1, 2] and [2] each appearing twice. There are only 6 different ones: [], [1], [1, 2], [1, 2, 2], [2], [2, 2].

Generating everything and throwing repeats into a set still builds every branch, and with many duplicates almost all are wasted: [2] * 20 builds 1,048,576 subsets to find 21 different ones. We want cut 3 instead: never build a branch that copies one already explored.

Use the loop form from section 6 (each iteration picks "the next item in the subset") and sort first, so equal values sit side by side. If one loop tries a 2 as the next item and then tries the other 2 as the next item, both branches start from the same path plus a 2, with the same items left. Same subtree. So: at each depth, skip a value equal to the one just tried at that same depth.

                   []
              1/     \2   \2
        [1]          [2]    (skip)
      2/   \2         |2
  [1,2]   (skip)    [2,2]
    |2
 [1,2,2]

Subsets of [1, 2, 2], loop form. In each loop, the second 2 is skipped because the first 2 was just tried there. The second 2 is still reachable one level down, which is how [2, 2] and [1, 2, 2] get built.

def subsets_unique(nums):
    nums = sorted(nums)                     # equal values side by side
    result, path = [], []
    def explore(start):
        result.append(path[:])              # every node is a subset
        for i in range(start, len(nums)):
            if i > start and nums[i] == nums[i - 1]:
                continue                    # same value already tried at this depth
            path.append(nums[i])
            explore(i + 1)
            path.pop()
    explore(0)
    return result

The condition is i > start, not i > 0, and that's the whole trick. i == start is the first item this loop looks at, so it can't repeat anything this loop tried, even if it equals the item before it: that earlier item was chosen one level up, as part of the path. With the rule, [2] * 20 visits exactly 21 nodes, one per answer.

Permutations need their own version of this rule (exercise 4). A permutation's loop starts at index 0 at every depth, so "the one just tried at this depth" has to be worked out differently. Draw the tree for [1, 1, 2] before you code it.

With duplicates: sort, then at each depth try each distinct value once, skipping nums[i] when i > start and it equals nums[i − 1]. Equal choices at the same depth would grow identical subtrees.

Someone writes the skip as if i > 0 and nums[i] == nums[i - 1]. What does subsets_unique([2, 2]) return now?

Right. At the root, index 0 is taken and index 1 is skipped, which is correct. One level down the loop starts at index 1, and i > 0 is true there too, so the second 2 is skipped even though it's the first thing that loop tries. [2, 2] can never be built.

Walk it by hand. Root: path [], i = 0 takes the first 2 and recurses with start = 1. There, path is [2] and the loop starts at i = 1. Is 1 > 0 and nums[1] == nums[0]? Yes: skipped, so that call adds nothing more. Back at the root, i = 1 is skipped too (correctly). Result: [[], [2]]. The rule must compare with "the value this loop tried just before", and a loop's first value has none, which is what i > start says.

9Constraint search: sudoku and grids

N-Queens belongs to a bigger family, constraint search: some variables to fill (empty sudoku cells), each with a domain of values (digits 1 to 9), and constraints on which combinations are allowed (no digit twice in a row, column or 3 × 3 box). The same template handles all of them:

def solve(state):
    if state.is_complete():
        return True
    var = state.pick_empty()                 # which variable to fill next?
    for value in state.legal_values(var):    # only values that break no rule
        state.assign(var, value)             # choose
        if solve(state):                     # explore
            return True                      # one answer is enough: stop
        state.unassign(var, value)           # un-choose
    return False                             # every value failed: back up

Two differences from the subset searches. We stop at the first answer: return True unwinds every call without undoing, so the solved state stays in place. And legal_values must be cheap: keep a set of used digits per row, column and box (27 sets), so "can 5 go here?" is 3 lookups instead of re-reading 27 cells, the same trick as cols and diag in N-Queens.

Which cell first?

The natural order is reading order. A much better one is the most constrained variable: the cell with the fewest legal digits. A cell with one legal digit costs no guessing. A cell with zero means this branch is dead, and you learn it now instead of 30 levels later. Real numbers from one simple solver with the 27 sets: the sudoku printed on Wikipedia has 51 empty cells, and blind guessing would face 951 ≈ 4.6 × 1048 fillings. Reading order places 4,208 digits; most-constrained-first places 51, with no wrong guess at all. A puzzle built to be hard (Arto Inkala's 2012 puzzle, 21 givens) takes 49,558 placements in reading order and 10,101 most-constrained-first.

Grids: the board is the state

A walk on a grid (a word in a letter grid, a path through a maze) must remember which cells it has used. The cheap way is the grid itself: overwrite the cell with a marker like "#" when you step on it, explore the neighbors, and write the original back when you step off. Writing it back is the un-choose. Forget it and later walks find cells blocked that should be free, and the caller gets back a damaged grid.

Constraint search fills one variable per level with a value that breaks no rule. Keep the rules in sets so each check is O(1), fill the most constrained variable first, and stop at the first answer if one is all you need.

Your sudoku solver is picking its next cell. Cell A has exactly 1 legal digit. Cell B has 6. Which should it fill first?

Right. Filling A is a branch of size 1: no guess, nothing to undo. And once its digit is placed, the cells in its row, column and box lose that option, so B might drop to 5 options or even 1. That's how most-constrained-first placed 51 digits on the Wikipedia puzzle instead of 4,208.

Count the tree. Branching on B first makes 6 subtrees, and each still has to fill A somewhere deep inside. Branching on A first makes 1 subtree, which then branches on B. Same answers, but the order decides how many dead ends you walk into before noticing them, so the work is not the same. On the Wikipedia puzzle: 4,208 placements in reading order, 51 with fewest-options-first.

Go deeper: how real solvers search

Constraint propagation: after each placement, remove that digit from the options of every cell in its row, column and box; a cell left with one option is filled at once, a cell with none means back up now. SAT solvers are backtracking plus that forced-move propagation (the DPLL algorithm); modern ones (CDCL) also learn a new rule from every dead end and jump back several levels to the decision that caused it. They solve industrial problems with millions of variables, such as chip verification, and some package managers use them to resolve dependencies. Exact cover (Knuth's Algorithm X with "dancing links") is a backtracking search for a family of puzzles that includes sudoku, tiling and, with a small extension, N-Queens. Nobody expects you to write these in an interview; saying "most constrained first, and propagate forced moves" shows you know where the speed comes from.

10What it costs, and when it's the wrong tool

The cost of a backtracking search is (number of nodes) × (work per node). Most nodes sit near the bottom, so the leaves usually decide it, and at each leaf we copy a path of up to n items. Python does roughly 10 million simple steps per second (from the complexity chapter):

  • You can't beat the size of the output. To list every subset, any algorithm must write 2n lists, so O(n · 2n) is the best possible. Say so: the search isn't slow, the question is big.

When backtracking is the wrong tool

Backtracking visits answers one at a time. That's right when you must list them. It's wasteful when you only need to count them or find the best one, and the tree keeps asking the same smaller question. How many ways can you climb 30 stairs taking 1 or 2 steps at a time? The tree ("1 step or 2?") has 1,346,269 leaves, one per way, and walking it makes 2,692,537 calls. But each call only asks "how many ways from stair k to the top?", and there are just 31 different k.

def ways(n):                      # walks the whole tree
    if n <= 1:
        return 1
    return ways(n - 1) + ways(n - 2)   # 2,692,537 calls for n = 30

from functools import cache

@cache                            # remember each answer the first time
def ways_memo(n):
    if n <= 1:
        return 1
    return ways_memo(n - 1) + ways_memo(n - 2)   # computes only 31 answers for n = 30

Remembering answers by their arguments is memoization, the door into dynamic programming. It works because the answer from stair k doesn't depend on how you reached stair k. If you had to list every way, no cache could help: the output alone has 1,346,269 entries.

The question asks for…Reach for
every subset, ordering, combination or valid boardbacktracking (the output is the cost)
one valid answer under strong rules (sudoku, N-Queens, a word on a grid)backtracking with pruning, stopping at the first answer
a count, minimum or maximum, where the same smaller question repeatsdynamic programming
Cost = nodes × work per node: O(n · 2n) for subsets, O(n · n!) for permutations. Memory is the depth plus the output. If you only need a count or a best value and the same subproblem keeps coming back, memoize: that's dynamic programming.

Which of these is a bad fit for plain backtracking?

Right. There are about 2.5 trillion ways up 60 stairs, so a tree walk with one leaf per way would take days, yet there are only 61 different subproblems. Memoize and it's instant. Listing 720 seatings is optimal (you have to write them), and sudoku wants one answer under strong rules, pruning's best case.

Ask two questions: is the output itself big, and does the tree repeat itself? Seatings: you must print 720 rows anyway. Sudoku: one answer, and the rules prune almost every branch. Stairs: the answer is one number, about 2.5 trillion, but the tree has that many leaves, and every call is one of only 61 questions ("ways from stair k"). A few repeating questions behind a huge tree is the signal for dynamic programming.

Go deeper: generators, and the bridge to dynamic programming

Don't store what you don't need. A generator (a function using yield) hands out one answer at a time and pauses in between. Memory drops from "all answers" to "one path", and the caller can stop early: next(subsets_lazy(items)) runs only until the first answer.

def subsets_lazy(items, i=0, path=None):
    path = [] if path is None else path
    if i == len(items):
        yield path[:]                      # hand out one answer, then pause
        return
    path.append(items[i])
    yield from subsets_lazy(items, i + 1, path)
    path.pop()
    yield from subsets_lazy(items, i + 1, path)

From backtracking to DP: (1) make each call return its answer (a count, a best value) instead of appending to a shared list, so it depends only on its arguments; (2) cache by those arguments. Step 1 is the hard part. If the answer depends on state outside the arguments, like a shared used list, caching gives wrong answers. That's why the bitmask from section 5 matters: it moves the used set into the arguments.

11What to say in the interview

When a problem says "all", "every", "list the ways" or "find any arrangement that…", a strong answer sounds like this:

  1. Name the tree: "Each level decides one item, take or skip: n levels, 2n leaves." (Or "next unused item, n! leaves", or "only items after the last pick, C(n, k) leaves".)
  2. Give the cost before coding: "O(n · 2n) time, since I copy up to n at each leaf, and O(n) extra space for the recursion, not counting the output. That's optimal: the output has 2n lists."
  3. Write the template out loud: choose, explore, un-choose; "I save path[:], not path, because it's one shared list."
  4. Prune and dedupe: "I'll sort so I can break once a number is too big", "skip a value equal to the one just tried at this depth", "sets make each rule check O(1)".
  5. Test small, name the boundary: empty input, one item, duplicates. Then: "if we only needed the count, I'd memoize, because the subproblems repeat."
Go deeper: follow-up questions interviewers like
  • "What if n is 40?" 240 is about 1.1 trillion. For subset-sum questions, split the items into two halves of 20, list each half's 220 = 1,048,576 sums, sort one list and binary search it for each sum of the other. That's meet in the middle: about 2 × 220 × 20 ≈ 42 million steps.
  • "Just one answer": return True up the chain, like the sudoku template. "An iterator": a generator. "Deep recursion": an explicit stack (section 3). "In parallel": subtrees share nothing, so hand them to workers, each with its own path. Split a few levels down so there are many more tasks than workers, because subtrees can be very uneven.
  • "Many words on one board" (after word search): put all the words in a trie and run one search from each cell, following the trie as you walk, so a prefix shared by many words is walked once, not once per word.

✓What to remember

  1. Recursion: a base case you answer directly, plus a step that shrinks the problem and trusts the call. Every input must reach the base case.
  2. Each waiting call is a frame on the call stack. Memory is the deepest chain of frames; Python stops at about 1,000.
  3. "Generate all" problems are decision trees: one level per choice, one leaf per answer. Backtracking walks that tree depth-first without storing it.
  4. The template: choose (change the shared path), explore (recurse), un-choose (undo exactly that change). Save path[:], never path.
  5. Subsets: take or skip, 2n leaves. Permutations: next unused item, n! leaves. Combinations: only items after the last pick, C(n, k) leaves.
  6. Prune when a branch breaks a rule, can't reach the goal, or repeats one already explored. Sort so you can break; use sets for O(1) checks. Pruning cuts the real work; the worst case usually stays exponential.
  7. Duplicates: sort, then skip a value equal to the one just tried at the same depth (i > start).
  8. Constraint search: one variable per level, most constrained first, stop at the first answer if that's all you need.
  9. Cost = nodes × work per node. If you only need a count or a best value and subproblems repeat, memoize: dynamic programming.

3. Pick the tool

Backtracking, backtracking with pruning, or dynamic programming? One sentence each. (a) List every way to seat 6 guests in a row. (b) Count the ways to climb 50 stairs taking 1, 2 or 3 steps. (c) Find one way to place 10 queens on a 10 × 10 board. (d) List every way to split "aab" into pieces that are all palindromes. (e) The fewest coins that make 14 cents from coins worth 1, 7 and 10 cents.

Answers

(a) Backtracking: the 720 seatings are the output. (b) DP: one number, and "ways from stair k" repeats; only 51 different questions. (c) Backtracking with pruning, stopping at the first solution. Core · code

4. unique_permutations(nums), with repeats in the input

Every distinct ordering: [1, 1, 2] gives 3, not 6. The test uses 12 values with 2,970 distinct orderings and counts every comparison, hash and function call, so building all 479,001,600 orderings and removing repeats fails. Adapt section 8's skip rule to a loop that starts at index 0 at every depth.

Core · code

5. combination_sum(candidates, target)

All combinations of distinct positive candidates that add up to the target, each reusable any number of times; [2, 2, 3] and [3, 2, 2] count once. The tests count every +, − and comparison. One fails a search that builds every order (section 6). Another has 104 candidates: rejecting each one at every node costs over 1.5 million operations, while sorting and breaking at the first that's too big (section 7) costs about 200,000. The budget is 500,000.

Core · code

6. word_search(board, word)

Spell the word by walking up, down, left and right through a letter grid, each cell at most once. Leave the board unchanged (section 9's mark and restore). The test counts cell reads: stop a walk at the first wrong letter (building whole walks first reads over 12 million cells), and catch a hopeless word, like two Bs on a board with one, with a cheap pass before searching.

Core · code

7. can_partition_k(nums, k)

Can the numbers be split into k groups with equal sums? The hard tests have no answer, so every branch must fail; dealing each number into each group is kn deals, over 4 billion for 16 numbers in 4 groups. Use section 7's three cuts: skip a group the number would overflow, place big numbers first, and never retry a number in a second empty group. Missing either of the last two costs over 2.8 million operations; the budget is 1 million.
