Dynamic programming

DP has a reputation for being clever. It's really bookkeeping: name the subproblem, write how a big one is built from smaller ones, and never solve the same one twice.

CoreThe one-sentence idea

DP is recursion plus a cache. When a problem breaks into overlapping subproblems with optimal substructure, solve each distinct subproblem once and store it. Time becomes (number of states) × (work per state).

Build itFrom first principles: the four questions

Answer these in words before any code. In interviews, say them out loud.

  1. State: what does dp[i] (or dp[i][j]) mean, in one sentence? "dp[i][j] = the edit distance between the first i chars of a and the first j chars of b."
  2. Transition: how is a state built from smaller states? Think about the last decision: what happened to the last character, item, or step?
  3. Base cases: the smallest states you can answer directly (empty string, zero capacity).
  4. Order and answer: fill states so dependencies are computed first; say which cell holds the final answer.

Top-down vs bottom-up

Top-down (memoization)

Write the natural recursion and add @functools.cache. Only computes the states you actually reach. Easy to get right; recursion depth can be an issue.

Bottom-up (tabulation)

Fill a table in dependency order. No recursion, and you can often shrink space to one or two rows because each row only depends on the previous one.

IntuitionAnalogy: a filled-in crossword

Recursion without memoization is answering the same crossword clue every time it intersects another word. DP is writing the answer in the grid once, so every later clue just reads it.

Physical picture for a 2D table: water flowing from the top-left corner. Each cell's value depends only on cells water has already reached: up, left, and up-left. Fill in the direction of the flow.

# 0/1 knapsack (1D, iterate capacity DOWNWARD so each item is used once)
for w, v in items:
    for c in range(cap, w - 1, -1):
        dp[c] = max(dp[c], dp[c - w] + v)

InterviewWhat a senior answer adds
  • Start from brute-force recursion, point out the repeated subproblems, add memoization, then optionally convert to a table and compress space. That progression is exactly what interviewers want to hear.
  • Name the state space size to justify complexity: "n × capacity states, O(1) each."
  • Reconstruct the solution, not just the number: keep parent pointers or walk back through the table.
  • DP in real systems: diff tools and spell checkers (edit distance), sequence alignment in genomics, query optimizers choosing join orders, Viterbi decoding in speech and early NLP, and line breaking in text layout (TeX).
TrapsCommon mistakes
  • An off-by-one between "first i characters" (table size n + 1) and "index i" (size n). Pick one and write it down.
  • 0/1 knapsack in 1D iterating capacity upward, which silently turns it into unbounded knapsack.
  • A state that doesn't capture everything the future depends on (e.g. forgetting "holding a stock or not").
  • @cache on a function taking lists (unhashable). Pass indexes, or convert to tuples.
RecallCheck yourself
Greedy vs DP for coin change: when does greedy fail?

With coins {1, 3, 4} and amount 6, greedy takes 4 + 1 + 1 (3 coins), but 3 + 3 is 2. Greedy works for "canonical" systems like US coins; DP works for all.

Why does edit distance only need the previous row?

Each cell depends on (i−1, j), (i, j−1) and (i−1, j−1): the current and previous rows only. Keep two rows: O(min(m, n)) space.

How do you know a problem is DP rather than greedy or backtracking?

You're asked for an optimum or a count over many choices, the choices form overlapping subproblems (the same smaller state reached many ways), and the optimal answer is built from optimal answers to substates.
