Chapter 2 · Part 7

Dynamic programming

P0 a favorite in coding roundsabout 60 minutes10 quick checks · 10 exercises

Dynamic programming (DP) has a scary name and a simple core. If a recursive solution keeps asking the same smaller question, write the answer down the first time and look it up after that. That one change turns hours of work into milliseconds. The hard part is never the code. It's deciding what to write down, and this chapter gives you a recipe for that, plus the handful of problem shapes that cover most interview questions.

By the end you'll be able to

  1. Spot repeated subproblems in a recursion and count how much work they waste.
  2. Turn slow recursion into memoization, then into a bottom-up table, then shrink the table.
  3. Use the recipe: state in words, recurrence from the last choice, base cases, fill order, where the answer is, and the cost.
  4. Solve the classic shapes: 1D (coins, house robber), knapsack, longest increasing subsequence, two strings (edit distance), and ranges (interval DP).
  5. Rebuild the actual answer (which coins, which items), not just the number.
  6. Tell when a problem needs DP, greedy or backtracking, and say why out loud.

How to read this: top to bottom, like a book. It builds on How fast is your code? (exponential growth), Binary search (used in section 6) and Recursion and backtracking (decision trees). Answer each quick check before reading on; a wrong answer gets you a second explanation. "Go deeper" boxes are optional on a first read.

1The problem: the same question, millions of times

A staircase has 30 steps. You can climb 1 or 2 steps at a time. In how many different ways can you reach the top?

A friend writes the natural recursion. To stand on step 30, your last move came either from step 29 (a 1-step) or from step 28 (a 2-step). So the ways to reach 30 are the ways to reach 29 plus the ways to reach 28. Neat and correct.

calls = 0

def climb(n):
    global calls
    calls += 1
    if n <= 1:                          # step 0 or step 1: exactly one way
        return 1
    return climb(n - 1) + climb(n - 2)  # last move was 1 step, or 2 steps

climb(30)    # 1,346,269 ways, and calls is now 2,692,537

A real one: making change

A vending machine owes you 6 cents and has coins of 1, 3 and 4 cents. It should use as few coins as possible. A cashier's instinct is greedy: take the biggest coin that fits, repeat. That gives 4 + 1 + 1, three coins. But 3 + 3 is two coins. Greedy grabbed the 4 and could never take it back.

The safe way is to try every coin as the last coin and keep the best:

def fewest(amount, coins):
    if amount == 0:
        return 0                       # nothing left to pay: no coins
    best = float("inf")                # "impossible" until shown otherwise
    for c in coins:
        if c <= amount:                # try c as the last coin
            best = min(best, 1 + fewest(amount - c, coins))
    return best

Correct, and slow again: 2,550,408 calls for 30 cents, and 313,679,521 calls (about 20 seconds) for 40 cents. Yet there are only 41 different amounts, 0 to 40, it could ever ask about.

climb(30) makes 2,692,537 calls. How many different values of n does it call with?

Right. n starts at 30, drops by 1 or 2 each call, and stops at 1 or 0, so it's always one of 0 to 30. Every other call repeats one of those 31. That gap, 31 questions versus 2.7 million calls, is why DP exists.

Look at what the argument can be: it starts at 30, each call subtracts 1 or 2, and it stops at 1 or 0. So n is a whole number from 0 to 30, only 31 possibilities, asked over and over. (1,346,269 is the answer, not a count of questions.)

2Why it's slow: the same subproblems, over and over

Draw the calls as a tree, like the decision trees in the backtracking chapter. Each node is one call; its children are the calls it makes. A subproblem is a smaller version of the same question: climb(4) is a subproblem of climb(6).

In climb(6), the subproblem climb(3) is solved 3 times, climb(2) 5 times and climb(1) 8 times. The tree has 25 nodes, but only 7 different questions. This is the first ingredient of DP:

  • Overlapping subproblems. The same subproblem shows up in many branches of the recursion. If you remember its answer, every repeat becomes free.

Not every recursion has this. Merge sort (from the sorting chapter) splits a list into halves that never overlap, so each piece is sorted exactly once. Remembering answers would never help it. That's plain divide and conquer, not DP.

The second ingredient is about correctness, and the coin problem shows it best:

  • Optimal substructure. The best answer to the big problem is built from best answers to smaller ones. Suppose the best way to pay 6 cents ends with a 3-cent coin. Then the coins before it pay 3 cents, and they must be a best way to pay 3 cents. If there were a better way to pay those 3 cents, you could swap it in and get a better way to pay 6, which is impossible.

Not every problem has this. For the longest route between two cities that never repeats a city, the best route A to B and the best route B to C may share a city, so gluing them breaks the rule. When pieces interfere like that, a DP recurrence gives wrong answers.

Dynamic programming is recursion plus a notebook. It works when the recursion asks the same questions many times (overlapping subproblems) and the best answer is built from best answers to smaller questions (optimal substructure). The cost becomes: number of different questions × work per question.
Explain it another way: the tutor's notebook

A student asks a tutor "what's 17 × 23?" The tutor works it out: 391. Ten minutes later, in a different problem, the same question comes up. A tutor without a notebook works it out again. A tutor with a notebook glances at the page: 391.

The plain recursion is the tutor without the notebook: it redoes the whole climb(3) subtree every time. DP is the notebook. (The name means nothing deep; Richard Bellman picked "dynamic" in the 1950s partly because it sounded impressive.)

Which of these recursions gains the most from remembering answers?

Yes. The amount 26 is reached as 30 − 4, 30 − 1 − 3, 30 − 3 − 1 and more, and each path re-solves it. Merge sort's halves never overlap, and binary search never comes back to a range, so a notebook would sit empty.

Ask: "can two different paths reach the same subproblem?" Merge sort's two halves share no items; each piece is sorted once. Binary search throws half away and never revisits it. In the coin recursion, 30 − 4, 30 − 1 − 3 and 30 − 3 − 1 all arrive at 26, and each re-solves it from scratch. Only overlap makes a memo pay.

3Remember the answers: a memo, then a table

Top-down: memoization

Memoization means keeping a dictionary (the memo) from subproblem to answer. Before solving a subproblem, look it up; after solving it, store it. The recursion stays exactly the same.

memo = {}

def climb(n):
    if n <= 1:
        return 1
    if n in memo:                  # asked before? read the notebook
        return memo[n]
    memo[n] = climb(n - 1) + climb(n - 2)
    return memo[n]

Each n from 2 to 30 is now computed once and makes 2 calls: 29 × 2 + 1 = 59 calls instead of 2,692,537. The coin recursion with a memo makes 86 calls for 30 cents instead of 2,550,408. In Python, @functools.cache above the def keeps the memo for you.

The cost rule from now on: number of states × work per state. A state is one distinct subproblem, like "n = 17" or "amount = 26". Stairs: 31 states × O(1) = O(n). Coins: 31 amounts × 3 coins each = O(amount × coins).

The flaw: recursion depth

The memoized climb(5000) crashes with RecursionError. The memo saves work, not depth: the first call goes 5000 → 4999 → … all the way down before anything returns, and Python allows about 1,000 nested calls. (In a plain script on Python 3.13, climb(999) works and climb(1000) fails.)

Bottom-up: tabulation

Turn it around: start from the smallest subproblems and build up, writing each answer into a list. This is tabulation, and the list is the table.

def climb(n):
    ways = [1] * (n + 1)           # ways[0] = ways[1] = 1
    for i in range(2, n + 1):      # small to big: ways[i-1] and ways[i-2] are ready
        ways[i] = ways[i - 1] + ways[i - 2]
    return ways[n]

No recursion, so no depth limit; climb(5000) is instant. The one rule of tabulation: fill the table in an order where every cell you read is already filled. Here that's left to right, because cell i reads cells i − 1 and i − 2.

Shrinking the table

Look at what the loop reads: only the last two cells. Everything older is dead weight. So keep two variables instead of a list:

def climb(n):
    two_back, one_back = 1, 1      # ways[i-2] and ways[i-1]
    for _ in range(2, n + 1):
        two_back, one_back = one_back, one_back + two_back
    return one_back                # also right for n = 0 and n = 1

O(n) time, O(1) memory. This "rolling" trick works whenever each cell looks a fixed distance back; in a 2D table, it means keeping only the previous row.

Memoization is the recursion plus a dictionary: same code, each state solved once. Tabulation fills a table from the smallest states up, in an order where every cell it reads is already done; it has no depth limit and makes it easy to keep only the last row or two.

Your memoized climb works for n = 500 but raises RecursionError for n = 5,000. What's the best fix?

Right. The error is about how deep the calls nest, not how many there are, and a loop doesn't nest. (sys.setrecursionlimit can raise the limit, but that only moves the wall: see the box below.)

Picture the call stack: climb(5000) waits on climb(4999), which waits on climb(4998), 5,000 calls stacked up. Any memo, dict or functools.cache, only helps once answers exist; on the first trip down it's empty. A loop from 0 up to n never stacks calls.

Go deeper: functools.cache, its traps, and the recursion limit

@functools.cache (Python 3.9+) is @functools.lru_cache(maxsize=None), an unlimited memo keyed by the arguments. For climb(30), cache_info() reports 31 misses and 28 hits.

  • Arguments must be hashable: no lists. Pass a tuple, or better, indexes into a list the function closes over.
  • The cache outlives the call. A module-level cached function that reads coins from outside gives stale answers when called again with different coins. Define the cached helper inside the function.
  • The recursion limit is 1,000 by default. sys.setrecursionlimit raises it, but every waiting call still holds a frame in memory, a @functools.cache function still stops at the real C stack (on Python 3.13, 100,000 levels still fail with the limit set to 10 million), and older Pythons could crash outright instead of raising. In interviews: "this recursion is n deep, so for large n I'd go bottom-up".
  • Memory: a dict entry costs several times a list slot, and a memo keeps every state forever.

4The recipe, on coin change

Every DP solution answers the same six questions. Answer them in words first and the code nearly writes itself. Here they are for "fewest coins", with coins 1, 3 and 4.

  1. State, in words. best[a] = the fewest coins that pay exactly a cents. Say it as a full sentence; most DP bugs are a fuzzy state.
  2. Recurrence, from the last choice. The best way to pay a has some last coin c. Remove it and what's left pays a − c, which must also be paid the best way (optimal substructure). We don't know which coin is last, so try them all: best[a] = 1 + min(best[a − c]) over every coin c ≤ a.
  3. Base cases. best[0] = 0: paying nothing takes no coins. An amount you can't pay at all gets ∞ (infinity), so it never wins a min.
  4. Fill order. best[a] only reads smaller amounts, so fill a = 1, 2, 3, … upward.
  5. Where the answer is. best[amount]. If it's still ∞, the amount can't be paid.
  6. Cost. States × work per state = (amount + 1) × (number of coins). For 10,000 cents and 5 coins, about 50,000 steps.
Filling best for coins 1, 3, 4 up to 6 cents. The blue cell is being decided; the yellow cell is the amount left after trying one coin as the last coin. The second row remembers which coin won, which section 9 uses to list the coins. Step through, and watch best[6] pick 3 + 3 over greedy's 4 + 1 + 1.
def fewest_coins(coins, amount):
    INF = float("inf")
    best = [0] + [INF] * amount            # best[0] = 0; the rest unknown
    for a in range(1, amount + 1):         # small amounts first
        for c in coins:                    # try each coin as the last coin
            if c <= a and best[a - c] + 1 < best[a]:
                best[a] = best[a - c] + 1
    return best[amount] if best[amount] < INF else -1

Trace the edges before trusting it. Amount 0: the loop never runs and it returns 0. No coins at all: every best[a] stays ∞, so it returns −1. Coins larger than the amount: skipped by c <= a.

The recipe: (1) the state in one sentence, (2) a recurrence that tries every possible last choice, (3) base cases, (4) a fill order where every read is already filled, (5) where the answer sits, (6) cost = states × work per state.
Explain it another way: think about the last step

Stop thinking about the whole solution and think about its last step. You don't know the best way to pay 6 cents, but you know it ends by dropping one coin into the tray: a 1, a 3 or a 4. If it's a 3, the rest is "the best way to pay 3", a smaller question already answered. Three possible last steps, three lookups, take the best.

Greedy also thinks about one step, but it picks the first step by a rule and commits. DP checks every possible last step against stored answers, which it can afford because each lookup is O(1).

Run it again: house robber

A thief walks down a street of houses holding 2, 7, 9, 3 and 1 thousand dollars. Robbing two houses side by side sets off an alarm. What's the most cash he can take?

State: best[i] = the most cash from houses 0 to i. Last choice, about house i: rob it and add best[i − 2] (house i − 1 is off limits), or skip it and keep best[i − 1]. Base: before the street, 0. Order: left to right; answer: the last cell; cost: O(n), and two rolling variables are enough, as with the stairs.

Coins are 1, 7 and 10 cents, and you owe 14 cents. How many coins does greedy (biggest coin first) use, and how many does the DP use?

Right. Greedy takes the 10, and then only 1s fit the remaining 4 cents. The DP checks every last coin: best[14] = 1 + min(best[13] = 4, best[7] = 1, best[4] = 4) = 2.

Run greedy by hand: 10 fits, leaving 4, and only the 1 fits that, four times: 5 coins. Greedy never asks "what if I hadn't taken the 10?" The DP asks it for every coin: with 7 as the last coin, the rest is 7 cents, one coin, so 2 in total. A choice that looks best now can force bad choices later.

5Knapsack: take it or leave it

You're packing a backpack that holds 7 kg. There are four items, and you can take each one at most once:

itemABCD
weight (kg)1345
value1457

Greedy by value per kg takes D (1.4 per kg) first, then nothing fits but A: value 8. The best is B + C: 7 kg, value 9. This is the 0/1 knapsack: each item is either in (1) or out (0).

Why one number isn't enough state

In coin change, "amount left" was the whole story, because coins can be reused. Here "4 kg of room left" doesn't say which items are still available. Fix: decide the items in order, A, then B, then C. Then "which items have I decided?" is always "the first i", one more number.

  1. State: best[i][c] = the best value using only the first i items, with capacity c.
  2. Last choice: what happens to item i − 1 (the newest one)? Leave it: best[i − 1][c]. Take it (if its weight w fits): its value v plus the best from the earlier items in the room that's left, best[i − 1][c − w] + v. Take the larger.
  3. Base: with no items, every capacity is worth 0: row 0 is all zeros.
  4. Order: row by row, since each row reads only the row above. Answer: best[n][W], bottom right. Cost: (n + 1)(W + 1) cells × O(1) = O(n·W).

The answer is the bottom-right cell: 9.
def knapsack(weights, values, W):
    n = len(weights)
    best = [[0] * (W + 1) for _ in range(n + 1)]   # row 0: no items, value 0
    for i in range(1, n + 1):
        w, v = weights[i - 1], values[i - 1]       # the newest item
        for c in range(W + 1):
            best[i][c] = best[i - 1][c]             # leave it
            if w <= c:                              # or take it, if it fits
                best[i][c] = max(best[i][c], best[i - 1][c - w] + v)
    return best[n][W]

One row is enough, if you go backwards

Each row reads only the row above, so you can keep one row and overwrite it in place. But now the direction of the inner loop matters. This is the most-asked knapsack follow-up, so take it slowly.

def knapsack(weights, values, W):
    best = [0] * (W + 1)                   # the "row above", reused
    for w, v in zip(weights, values):
        for c in range(W, w - 1, -1):      # BACKWARDS: big capacities first
            best[c] = max(best[c], best[c - w] + v)
    return best[W]

When you compute best[c], the "take it" option reads best[c − w], and it must be the old value, from before this item was considered. Going backwards, you write big capacities first, so the smaller cell c − w hasn't been touched yet in this pass: it's still the old row. Going forwards, c − w was already rewritten a moment ago, and it may already include this item. Then "take it" takes it a second time.

One pass of the 1D knapsack: adding item B (3 kg, value 4) to the row that already has A. Blue is the cell being written, green cells were already rewritten in this pass, yellow is an old value being read, red is a new value being read by mistake. Run Backwards, then switch to Forwards and watch capacity 6 pack B twice.

Here's the twist: sometimes using an item many times is exactly what you want. In the unbounded knapsack, each item can be taken any number of times, and the forwards loop is the correct one, because reading a cell that already includes the item is how you take it again. Coin change is an unbounded knapsack: coins are the items, and you minimize the count instead of maximizing value. One loop direction is the whole difference between the two problems.

0/1 knapsack: state (items considered, capacity), choice "leave it or take it", O(n·W). With one row, loop capacity backwards so every read sees the old row and each item is used at most once. Loop forwards and an item can be reused, which is right for the unbounded knapsack and coin change.

In the 1D 0/1 knapsack, someone changes the inner loop to go forwards: for c in range(w, W + 1). What happens?

Right. Forwards, best[c − w] was already updated for this item, so "take it" can stack the item again. That's the unbounded knapsack. At capacity 6, B (3 kg) gets packed twice for 8.

Think of the row as two rows on one sheet: the old row (without the item) being overwritten by the new one (with it). "Take it" must read the old row. Backwards, you only overwrite cells nobody reads again in this pass. Forwards, you overwrite best[3] with "B in the bag", then best[6] reads it and adds B again. Nothing crashes (the loop starts at w); the answer is just quietly wrong for 0/1.

"O(n·W)" is not as fast as it looks

O(n·W) looks polynomial, but W is a number, not a count of things. A capacity of 2,000,000,000 is written with 10 digits, and it means 2 billion columns. Each extra digit multiplies the work by 10. An algorithm that's polynomial in the numeric value but exponential in the number of digits is called pseudo-polynomial. Great for capacity 10,000; useless for 2 billion.

You have 50 files and a 2,000,000,000-byte disk, and you want the most valuable set that fits. Is the O(n·W) knapsack DP a good plan?

Right. 50 × 2 × 10⁹ = 10¹¹ steps is about 3 hours at 10 million a second, and even one row has 2 billion entries (16 GB as a Python list). Better: measure sizes in megabytes, DP over values if they're small, or meet in the middle (2²⁵ subsets per half).

Count the table: a column for every capacity from 0 to 2,000,000,000, so 50 × 2 billion = 10¹¹ cells. The 1D version saves rows, not columns: one list of 2 billion entries (16 GB) and still 10¹¹ updates. O(n·W) is only fast when W itself is small.

Go deeper: knapsack is NP-hard, and what people do about it

The 0/1 knapsack is NP-hard: no one knows an algorithm polynomial in the input's size (items plus digits of the weights), and finding one would settle P vs NP. The DP doesn't contradict this: its time grows with the value of W, which is exponential in W's digit count.

  • DP over value: state = (items considered, total value), storing the lightest weight that reaches it. O(n · total value): good when values are small and weights huge.
  • Meet in the middle: for n up to about 40, list the 2²⁰ ≈ 1 million subsets of each half. Sort one side by weight and keep a running best value (so each weight maps to the best value at that weight or less), then, for each subset of the other side, binary search for the room it leaves. Any W.
  • Approximation: round values to a coarser scale, then DP over value: within any chosen percentage of the best, in polynomial time.
  • Branch and bound (backtracking that cuts branches that can't beat the best so far), often mixed with DP, is how practical solvers handle big instances.

6Longest increasing subsequence: choosing the state

Given [10, 9, 2, 5, 3, 7, 101, 18], find the longest strictly increasing subsequence (LIS). A subsequence keeps the original order but may skip items; it doesn't have to be one unbroken block. Here the answer is 4, for example 2, 3, 7, 18 or 2, 5, 7, 101.

The obvious state doesn't work

Try the stairs pattern: "best[i] = the LIS among the first i + 1 numbers". To decide whether nums[i] can extend that subsequence, you need to know its last value, and the state doesn't record it. Two subsequences of length 3, one ending in 7 and one ending in 101, are very different futures.

The fix is a move you'll use again and again: pin down the end. Make the last element part of the state.

  1. State: ends[i] = the length of the longest increasing subsequence that ends exactly at index i.
  2. Last choice: what came just before nums[i]? Some earlier j with nums[j] < nums[i]. So ends[i] = 1 + max(ends[j]) over those j, or 1 if there are none.
  3. Answer: the largest ends[i], not the last one, because the best subsequence can end anywhere.
  4. Cost: n states × O(n) each = O(n²).

def lis_length(nums):
    ends = [1] * len(nums)            # ends[i]: longest run ending AT i
    for i in range(len(nums)):
        for j in range(i):            # every earlier number
            if nums[j] < nums[i]:     # nums[i] can extend that run
                ends[i] = max(ends[i], ends[j] + 1)
    return max(ends, default=0)       # the best run can end anywhere

Faster: keep only the best tails

For 100,000 numbers, O(n²) is 5 × 10⁹ comparisons, a few minutes of pure Python. The faster idea keeps a different table. For each length k, remember the smallest possible last value of any increasing subsequence of length k seen so far. Call that list tails. A smaller tail is always at least as good: anything that can extend a run ending in 7 can also extend a run ending in 3.

Two facts make it fast. First, tails is always sorted (strictly increasing). Second, a new number x only ever changes one entry: find the first tail that is ≥ x and replace it with x (x makes a run of that length end lower), or, if x is bigger than every tail, append it (x extends the longest run). Finding that spot in a sorted list is a binary search: O(log n). So the whole thing is O(n log n), about 1.7 million steps for 100,000 numbers.

x = 10    tails = [10]
x = 9     tails = [9]               9 replaces 10: a length-1 run can end lower
x = 2     tails = [2]
x = 5     tails = [2, 5]            5 is bigger than every tail: append
x = 3     tails = [2, 3]            3 replaces 5: same length, lower tail
x = 7     tails = [2, 3, 7]
x = 101   tails = [2, 3, 7, 101]
x = 18    tails = [2, 3, 7, 18]     length 4

One warning that catches people: tails is not itself a subsequence. For [2, 5, 3, 7, 1] it ends as [1, 3, 7], but the 1 comes after the 7 in the input. The length, 3, is right. The list is a record of the best tail for each length, mixed from different runs. To get a real subsequence you need extra bookkeeping, which is exercise 6.

When "best so far" doesn't carry enough information to continue, put the missing piece into the state: "the LIS that ends at i". That gives O(n²). The O(n log n) version keeps the smallest tail for each length; the list stays sorted, so each number costs one binary search. Its length is the answer; its contents are not.

For [2, 5, 3, 7, 1], the tails method ends with tails = [1, 3, 7]. What does that tell you?

Right. 1 replaced 2 because 1 is now the smallest possible end of a length-1 run: true and useful later, but it mixes runs, since the 1 comes after the 7. The real answers are 2, 3, 7 and 2, 5, 7.

Read tails as separate facts: "the best length-1 run ends in 1", "the best length-2 run ends in 3", "the best length-3 run ends in 7". Each is about a different run, and each is true, so replacing 2 with 1 is no bug. But stringing them together ignores the input order: 1 comes last. Only the length, 3, is the answer.

Go deeper: why tails stays sorted, and where LIS hides

Why sorted: take a run of length k + 1 ending in tails[k]. Its first k items are a length-k run whose last value is smaller than tails[k]. tails[k − 1], the smallest length-k tail, is at most that value, so it's smaller than tails[k] too.

Variants: for "non-decreasing", search for the first tail greater than x (bisect_right) instead of ≥ x (bisect_left). The method is also called patience sorting, after a card game that deals cards onto piles the same way.

Where it hides: "Russian doll envelopes" is LIS on heights after sorting by width (equal widths by height descending).

7Two sequences: edit distance and friends

A spell checker sees "kitten" and wonders whether you meant "sitting". How far apart are they? The edit distance (also called Levenshtein distance) is the fewest single-letter edits that turn one word into the other, where an edit is inserting a letter, deleting a letter or replacing one letter with another. kitten → sitten (replace k with s) → sittin (replace e with i) → sitting (insert g): 3.

With two inputs, the state needs a position in each. Think about prefixes: the first i letters of a and the first j letters of b.

  1. State: d[i][j] = the fewest edits to turn the first i letters of a into the first j letters of b.
  2. Last choice: look at the last letters, a[i − 1] and b[j − 1]. If they're the same, keep them, no edit: d[i − 1][j − 1]. If they differ, the last edit was one of three, each costing 1:
    • delete a's last letter, then solve the rest: d[i − 1][j] (the cell above),
    • insert b's last letter at the end: d[i][j − 1] (the cell to the left),
    • replace a's last letter with b's: d[i − 1][j − 1] (the cell up and to the left).
  3. Base cases: d[i][0] = i (delete all i letters) and d[0][j] = j (insert all j letters).
  4. Order: row by row, left to right, since every cell reads up, left and up-left. Answer: bottom right. Cost: (n + 1)(m + 1) cells × O(1) = O(n·m).

The edit-distance table, one cell per step. Rows are prefixes of the first word, columns prefixes of the second; ε means the empty prefix. The blue cell is being filled and the yellow cells are what it reads. The last frame walks back from the corner (green) and lists the edits. Try your own words, up to 9 letters each.
def edit_distance(a, b):
    d = [[0] * (len(b) + 1) for _ in range(len(a) + 1)]
    for i in range(len(a) + 1): d[i][0] = i         # delete everything
    for j in range(len(b) + 1): d[0][j] = j         # insert everything
    for i in range(1, len(a) + 1):
        for j in range(1, len(b) + 1):
            if a[i - 1] == b[j - 1]:
                d[i][j] = d[i - 1][j - 1]           # same last letter: free
            else:
                d[i][j] = 1 + min(d[i - 1][j],      # delete
                                  d[i][j - 1],      # insert
                                  d[i - 1][j - 1])  # replace
    return d[len(a)][len(b)]

Each row reads only itself and the row above, so two rows are enough: O(min(n, m)) memory if you make the shorter word the columns. The plain recursion, by comparison, makes 3,032 calls for kitten and sitting, against 56 cells, and that gap explodes for longer words.

The same table answers other questions

Longest common subsequence (LCS): the longest sequence that appears, in order, in both inputs. Same state and same table shape; only the rule changes. If the last letters match, it's 1 + the up-left cell; otherwise, the larger of the cell above and the cell to the left. For "ABCBDAB" and "BDCABA" it's 4 (for example BCBA). Run it on lines instead of letters and you have the core of diff: lines in the LCS are unchanged, and every other line is a deletion or an addition. That's exercise 7.

Grid paths: a robot in a 3 × 7 grid moves only right or down. How many routes go from the top-left to the bottom-right? paths[r][c] = paths[r − 1][c] + paths[r][c − 1], with 1s along the top row and the left column: 28. Same "read up and left" shape, with no strings at all.

Two sequences, so two indexes: d[i][j] is about the first i items of one and the first j of the other. The recurrence looks at the last items: match, or one of a few edits. Fill row by row; the answer is in the bottom-right corner; the cost is n·m.

In the table for a = "kitten" and b = "sitting", what does the cell d[2][3] mean?

Right: rows go with a, columns with b. Its value is 2 (replace k with s, insert t). Every cell is a complete smaller edit-distance question, which is what lets later cells reuse it.

Go back to the state sentence: "d[i][j] = fewest edits to turn the first i letters of a into the first j letters of b". i = 2, j = 3 gives "ki" into "sit". A cell is never a count of matches; it's the full answer to a smaller question (here 2).

Go deeper: edit distance in real systems
  • Spell checkers and fuzzy search use Levenshtein distance, often adding a fourth edit, swapping neighbors (Damerau–Levenshtein), because "teh" for "the" is so common. Search engines use automata or trees that only explore words within distance 1 or 2, instead of comparing against the whole dictionary.
  • diff and git output an edit script: the kept, deleted and inserted lines that LCS describes. A full table for two 10,000-line files is 10⁸ cells, so real tools use Myers' algorithm, O((n + m)·D) where D is the number of differences: fast when files are similar. git also offers "patience" and "histogram" diffs, which first anchor on lines that are unique (or rare) in both files.
  • Bioinformatics aligns DNA and proteins with the same table, scoring matches, mismatches and gaps: Needleman–Wunsch (whole sequences) and Smith–Waterman (best-matching parts).
  • Hirschberg's trick recovers the full alignment, not just the distance, in O(n + m) memory: find the middle of the best path with two half passes, then recurse on each half.

8Ranges: interval DP

So far every subproblem was a prefix: the first i stairs, items or letters. Some problems shrink from both ends, and then the natural subproblem is a range, from index i to index j.

Example: the longest palindromic subsequence of "bbbab". A palindrome reads the same backwards. The answer is 4 ("bbbb").

  1. State: best[i][j] = the longest palindromic subsequence inside s[i..j].
  2. Choice, at the two ends: if s[i] == s[j], both ends can wrap whatever is best inside: best[i + 1][j − 1] + 2. Otherwise at least one end isn't used: max(best[i + 1][j], best[i][j − 1]).
  3. Base: a single letter is a palindrome of length 1; an empty range is 0.
  4. Order: every cell reads shorter ranges inside it, so fill by increasing length: all ranges of length 1, then 2, and so on. Answer: best[0][n − 1], the whole string. Cost: about n²/2 ranges × O(1) = O(n²).
def longest_palindrome_subseq(s):
    n = len(s)
    best = [[0] * n for _ in range(n)]
    for i in range(n):
        best[i][i] = 1                          # one letter: a palindrome
    for length in range(2, n + 1):              # short ranges before long ones
        for i in range(n - length + 1):
            j = i + length - 1
            if s[i] == s[j]:
                best[i][j] = best[i + 1][j - 1] + 2   # both ends join in
            else:
                best[i][j] = max(best[i + 1][j], best[i][j - 1])
    return best[0][n - 1] if n else 0

Only the triangle with i ≤ j is used; each diagonal is one range length, and the answer, 4, is the top-right corner, filled last. For "bb" the code reads best[i + 1][i], an empty range below the diagonal, still 0, so "bb" gets 2, as it should.

When the choice is a split point: O(n³)

In a second family of interval problems, solving a range means choosing a point k inside it to split at, or to act on: in what order to multiply a chain of matrices, where to cut a stick first (exercise 8), which balloon to burst. Each range tries every k, and each try adds the two smaller ranges on either side. That's n² ranges × O(n) splits = O(n³), fine for n in the low hundreds.

The art is choosing what k stands for. In "burst balloons" (popping a balloon earns its number times its two current neighbors', and a missing neighbor counts as 1), "which balloon is popped first?" doesn't split cleanly: afterwards the two sides become neighbors, so they aren't independent. "Which is popped last in this range?" does: until its turn it stands as a wall between the sides, and when it pops, its neighbors are the range's two edges. For [3, 1, 5, 8] the best total is 167.

Interval DP: the state is a range (i, j). Each range reads only shorter ranges inside it, so fill by increasing length, and the answer is the whole range, (0, n − 1). If each range tries every split point, the cost is O(n³).

Why does interval DP fill the table in order of increasing range length?

Right. It's section 3's rule: fill so that every cell you read is done. Range (i, j) reads (i + 1, j), (i, j − 1) and (i + 1, j − 1), all shorter. (Filling i from n − 1 down to 0, j upward, also works, for the same reason.)

The fill order is never about cost; every cell costs about the same. It's about reading only finished cells. Range (i, j) reads (i + 1, j − 1), or (i + 1, j) and (i, j − 1): ranges one or two letters shorter, which read shorter ranges still. And the answer, the whole range (0, n − 1), sits in the top-right corner, not the last row.

9Getting the answer, not just the number

You've told the interviewer "2 coins". The next question is always: which coins? The table only holds numbers. There are two ways to get the choices back, and both rely on the same fact: every cell was won by one specific choice.

  1. Parent pointers. When you write a cell, also write down which choice won (the last coin, the item taken, the edit made). At the end, start at the answer cell and follow the pointers back to a base case.
  2. Walk back through the table. Keep the full table and, at the answer cell, ask again: "which choice produces exactly this number?" Move to the cell that choice came from, and repeat. The edit-distance figure in section 7 does this in its last frame.

For coins, add a list last to fewest_coins from section 4, and next to best[a] = best[a - c] + 1 also write last[a] = c. Then, if best[amount] isn't ∞:

def coins_used(last, amount):
    out = []
    while amount > 0:                 # follow the pointers back to 0
        out.append(last[amount])      # the coin that won for this amount
        amount -= last[amount]        # ...and the amount it came from
    return out                        # coins 1, 3, 4 and amount 6: [3, 3]

For coins 1, 3, 4 and 6 cents: last[6] = 3, so pay a 3 and go to amount 3; last[3] = 3, pay another 3 and reach 0. Answer: [3, 3]. Amount 0 returns an empty list, which is right: no coins.

Walking back needs the history, which is exactly what the space tricks throw away. The 1D knapsack row only knows the final values, not which items made them. So it's a real trade-off: if you need the choice, keep the full table (or a table of pointers), and say so when you choose the space-saving version. In the 2D knapsack table, each row answers "did this item matter here?": compare a cell with the one above it.

Every cell was won by one choice. Record it (parent pointers), or re-derive it from the full table, then walk from the answer back to a base case. Shrinking the table to one row loses that history, so reconstruction needs the full table or a pointer table.

10Is it DP? DP vs greedy vs backtracking

The hardest part in an interview is noticing that a problem is DP. These signals are worth checking:

  • The question asks for a count ("how many ways"), a best value ("fewest", "most", "longest") or whether something is possible, not for a list of every solution.
  • The solution is a sequence of choices: take or skip, which coin, which letter edit, where to split.
  • The brute force is exponential, but you can describe "where you are" with a few small numbers: an index, an amount left, a range (i, j). Ask: "if I know these numbers, does the rest of the problem care how I got here?" If not, those numbers are your state.
  • The sizes fit: n up to a few thousand suggests O(n²), a few hundred O(n³), an amount up to about 10⁵ a table over it.
ToolWhat it doesUse it whenExample
Greedytakes the best-looking choice and never looks backyou can prove the local choice is always safemost meetings in one room (earliest end first); change with 1, 5, 10, 25 cents
DPtries every choice, but solves each state oncechoices interact, and the state is a few small numbersfewest coins with any coins, knapsack, edit distance
Backtrackingwalks every path of the decision tree, cutting dead endsyou need every solution, or the state is the whole path so farlist all combinations, N-queens, sudoku

They're closer than they look. Backtracking plus a memo is top-down DP, which is where the backtracking chapter ended. And greedy is DP where you've proved that only one choice ever needs checking. If you can't prove that, the coins 1, 3, 4 story says: don't trust it.

Which of these is a job for backtracking rather than DP?

Right. A count or a minimum is one number per state, which DP stores and reuses. A list must contain every solution, so you walk every path anyway. (50 cents from 1, 5, 10 has 36 ways; for bigger amounts it's millions.)

Compare what each question returns. "How many" and "fewest" return one number per state ("ways to make 37 cents"), which you store and reuse. "List every way" must write out every solution, and no table shortcuts that. Huge output means walking the whole tree: backtracking. A number means look for DP.

Go deeper: bitmasks, DAGs, Viterbi and other DP in the wild
  • Bitmask DP: when the state must include a set of things used, store it as the bits of an integer. Traveling salesman becomes state (cities visited, current city): n² · 2ⁿ work (Held–Karp). For 20 cities that's about 4 × 10⁸ steps, against 19! ≈ 1.2 × 10¹⁷ routes. Still exponential, so n stays around 20.
  • DP is a path problem on a DAG: states are nodes, choices are edges, and the fill order is a topological order. A cycle would mean a state depending on itself. Graphs with cycles need shortest-path tools (Dijkstra, Bellman-Ford), the next topic in this chapter.
  • DP on trees: each node's answer is built from its children's ("invite the most people, but never someone together with their direct boss"). Post-order is the fill order.
  • Viterbi: the most likely hidden states behind noisy observations, with state (time step, hidden state). It decodes error-correcting codes in phones and modems, and powered classic speech recognition.
  • TeX line breaking (Knuth–Plass) picks every line end in a paragraph by DP over "best layout up to word i".

11What to say in the interview

A strong DP answer follows the recipe out loud, before any code:

  1. Start with the brute force, and name the repeat. "Try every coin as the last coin. That's exponential, but the only thing that matters is the amount left, and there are only amount + 1 of those, so the same subproblems repeat."
  2. Say the state in one sentence. "best[a] is the fewest coins that make exactly a."
  3. Give the recurrence and the base cases. "best[a] = 1 + min(best[a − c]) over coins up to a; best[0] = 0; impossible amounts are infinity."
  4. Say the cost as states × work. "amount + 1 states, one step per coin: O(amount × coins) time, O(amount) space."
  5. Pick top-down or bottom-up, and mention the follow-ups. "I'll go bottom-up to avoid recursion depth. If you need the coins themselves, I'll store the winning coin per amount and walk back."

Then code it, and trace it on the smallest inputs: amount 0, no coins, a coin bigger than the amount.

Go deeper: follow-up questions interviewers like
  • "Can you use less memory?" If each row reads only the previous row, keep one or two rows. Say what you lose: the ability to walk back for the actual choice.
  • "Does order matter?" When counting ways to make change, combinations (1 + 2 and 2 + 1 are the same) and sequences (they're different) give different counts: 4 versus 9 for coins 1, 2, 5 and 5 cents. Know which one your loops compute, and why.
  • "Each coin only once?" Then it's a 0/1 knapsack: loop the amount backwards.
  • "The amount is up to 10⁹." The table is pseudo-polynomial; say so, then look for structure (small values, few items, meet in the middle) or a greedy that you can prove.
  • "Return every optimal solution." Keep every winning choice per cell and walk back through all branches: backtracking guided by the table.
  • "Why not greedy?" Have a counterexample ready: coins 1, 3, 4 and amount 6.
  • "The count is huge." Python ints never overflow; in Java or C++ the problem will ask for the count modulo a prime such as 10⁹ + 7, so take the remainder after every addition.

✓What to remember

  1. DP = recursion + a notebook. It needs overlapping subproblems and optimal substructure. Cost = states × work per state (stairs: 2.7 million calls became 59).
  2. Memoization keeps the recursion and adds a dict, but can hit Python's ~1,000 depth limit. Tabulation fills a table so every read is ready, and can keep just the last row or two.
  3. The recipe: state in a sentence, recurrence from the last choice, base cases, fill order, answer location, cost.
  4. Greedy can be wrong (coins 1, 3, 4 for 6 cents). DP tries every last choice.
  5. 0/1 knapsack: O(n·W); with one row, loop capacity backwards. Forwards reuses items: unbounded knapsack, coin change. O(n·W) is pseudo-polynomial.
  6. Missing information? Put it in the state: "LIS ending at i", O(n²). Smallest tails + binary search: O(n log n), but tails isn't the subsequence.
  7. Two sequences: d[i][j] over prefixes, answer bottom right. Ranges: best[i][j], filled by increasing length; O(n³) with a split point.
  8. To return the choice, keep parent pointers or the full table and walk back.

Answers

2. The recipe on a grid with a rock

A robot starts in the top-left of a grid with 3 rows and 4 columns and must reach the bottom-right, moving only right or down. The cell in row 1, column 1 (counting from 0) holds a rock it can't enter. Write the six recipe answers (state, recurrence, base cases, fill order, answer, cost), then fill the table. How many routes are there? How many without the rock?

Answers

State: paths[r][c] = routes from the start to cell (r, c). Recurrence: paths[r − 1][c] + paths[r][c − 1] (it arrived from above or from the left), and 0 for the rock. Base: paths[0][0] = 1; anything outside the grid counts 0. Order: row by row, left to right. Answer: bottom-right cell. Cost: rows × columns.

Rows: 1 1 1 1 / 1 0 1 2 / 1 1 2 4. So 4 routes. Without the rock, 10.

Warm-up · pen and paper

3. DP, greedy or backtracking?

For each, pick the tool and give a one-line reason. (a) Fewest coins with coins 1, 5, 10, 25. (b) Fewest coins with coins 1, 3, 4. (c) List every subset of 15 numbers that adds up to 30. (d) Attend as many meetings as possible in one room, no overlaps. (e) Can the string "applepenapple" be split into words from a given dictionary?

Answers

(a) Greedy works: for these coins you can prove the biggest coin is always safe (DP also works). (b) DP: greedy gives 4 + 1 + 1 for 6. (c) Backtracking: you must output every subset, so you walk the tree; if you only had to count them, DP over (index, sum left) would do. (d) Greedy: always take the meeting that ends earliest. (e) DP over prefixes: "the first i letters can be split" is true if some dictionary word ends at i and the prefix before that word can be split.
