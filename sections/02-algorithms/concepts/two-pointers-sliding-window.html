Chapter 2 · Part 4

Two pointers, sliding window, prefix sums

P0 one of the most common interview patternsabout 55 minutes10 quick checks · 11 exercises

A huge share of interview questions about arrays and strings have the same shape. "Find the busiest stretch." "Find two numbers that add up to 100." "How many stretches add up to exactly k?" The obvious answer looks at every pair or every stretch, and that's n². This chapter is about three tools that get the same answers in about n steps. They all rest on one idea: neighbouring candidates share most of their work, so don't redo it. The code for each tool is short. The part interviewers probe is the reasoning: why is it safe to skip all those candidates?

By the end you'll be able to

  1. Look at a brute force and say exactly which work it repeats.
  2. Explain why, on sorted input, moving one pointer safely throws away a whole row of pairs.
  3. Write fixed and variable sliding windows, and prove they're O(n) even though they have a loop inside a loop.
  4. Say why a sliding window breaks when numbers can be negative, and what to use instead.
  5. Use prefix sums for O(1) range sums, and prefix sums plus a hash map for "how many stretches sum to k".

How to read this: top to bottom. It builds on How fast is your code? (especially "a loop inside a loop is not always n²"), Putting things in order and Binary search. Answer each quick check before reading on. "Go deeper" boxes are optional on a first read.

1The problem: a year of traffic

You run a website. For every minute of last year you have one number: how many requests arrived in that minute. A year has 525,600 minutes, so that's 525,600 numbers in a list.

Your boss has three questions. Which 60-minute stretch was the busiest? What's the shortest stretch of minutes that, added together, got at least 1,000,000 requests (how fast can a flood build up)? And a new dashboard will ask, 100,000 times a day, "how many requests came in between minute a and minute b?"

Each question is about a range: a run of neighbouring items, from index i to index j, with nothing skipped. (A range of a list is also called a subarray; a range of a string is a substring.) The direct way to answer each one adds up ranges from scratch. Here's what that costs, at the 10 million simple steps per second that Python manages:

QuestionDirect wayStepsTime
Busiest hourAdd up each of the 525,541 windows of 60 minutesabout 31 million additions3 s
Shortest stretch with 1,000,000 requestsTry every start and every end, with a running sumabout 138 billionabout 3.8 hours
Dashboard, 100,000 questionsAdd up the range for each questionup to 52.6 billionabout 1.5 hours

By the end of this chapter, each of these takes about a million steps or fewer: a tenth of a second. Not by buying a faster computer, but by noticing that almost all of that work is the same work, done again and again.

How many different ranges (start ≤ end) does a list of 1,000 items have?

Right: 1,000 + 999 + … + 1 = 1,000 × 1,001 / 2 = 500,500. Start 0 has 1,000 possible ends, start 1 has 999, and so on. That's the n²/2 "triangle" every brute force in this chapter walks through.

Count by starting point. A range that starts at index 0 can end at any of the 1,000 indexes. One that starts at index 1 can end at 999 of them (the end can't come before the start). Start 999 has only one: itself. Add them up: 1,000 + 999 + … + 1 = 500,500, which is about n²/2. Not n (each start has many ends), and not n² (half the start/end combinations have the end before the start).

2Where the work goes

Look at two neighbouring windows from the first question: minutes 100 to 159, and minutes 101 to 160. They share 59 of their 60 numbers. The direct way throws away the first total and adds those 59 numbers again. Every window repeats almost all the work of the one before it.

minute:     100  101  102  …  159  160
window A:  [ 60 numbers ............. ]
window B:       [ the same 59 ....... + 1 new ]

total(B) = total(A) − minute 100 + minute 160      2 steps, not 59

The other questions have the same problem in a different form. Every brute force in this chapter walks through a triangle of about n²/2 candidates: all pairs (i, j), or all ranges from i to j. Each tool skips almost all of the triangle, for a reason you can say out loud:

  • Two pointers: one comparison proves that a whole row of candidates can't win, so you never look at them.
  • Sliding window: the next candidate is the last one plus one small change, so you update instead of starting over.
  • Prefix sums: compute running totals once, and every range becomes one subtraction.
Neighbouring candidates overlap. Reuse the overlap, or prove that a whole group of candidates can't win, and n² work becomes about n.

3Opposite ends: pairs in a sorted list

Start with the simplest triangle: pairs. You have a sorted list and a target, and you want two numbers that add up to the target. You wrote a version of this in the complexity chapter (exercise 6, count_pairs_with_sum). This time, the focus is why it works, because that's what an interviewer asks next.

The brute force checks every pair: for 7 numbers that's 7 × 6 / 2 = 21 pairs. The two-pointer way puts one pointer, lo, on the smallest number and another, hi, on the largest. Then it looks at a[lo] + a[hi]:

  • Equal to the target: found it.
  • Too small: move lo one step right (to a bigger number).
  • Too big: move hi one step left (to a smaller number).

Why is it safe to throw a number away?

Take the list [1, 3, 4, 6, 8, 11, 13] and target 10. The first check is 1 + 13 = 14. Too big. Now think about 13. Its smallest possible partner is 1, the smallest number in the list. If 13 plus its smallest partner is already too big, then 13 plus any other partner is bigger still. So 13 can't be in any answer. One comparison ruled out every pair that uses 13, and we drop it by moving hi left.

It works the same way in reverse. If a[lo] + a[hi] is too small, then a[hi] is the biggest partner a[lo] has left. Even that isn't enough, so nothing can rescue a[lo]. Drop it.

The picture that makes this click: draw every pair as a grid. Each row is the smaller number of the pair, each column the larger one, and each cell holds their sum. Because the list is sorted, sums grow as you go right along a row and as you go down a column. The two pointers always sit at the top-right corner of the part of the grid that's still possible. Each check crosses out a whole row or a whole column.

target
Opposite-ends two pointers on a sorted list. Yellow cells are the two numbers being added; in the grid, the current pair is solid blue and the row or column about to be crossed out is yellow. Step through and count: each check removes a whole row or column, never just one cell. Then try target 30, where no pair exists.

Each check moves lo up by one or hi down by one. They start n − 1 apart and stop when they meet, so there are at most n − 1 checks. That's O(n) instead of n²/2. On a million sorted numbers: under a million checks instead of 500 billion.

On sorted input, compare the two ends. If one end is hopeless even with its best possible partner, it can't be in any answer, so drop it. Each check throws away a whole row or column of pairs, so there are at most n − 1 checks.
Explain it another way: two gifts, one gift card

You have a gift card for exactly $10 and a shelf of items sorted by price. Hold the cheapest item in your left hand and the most expensive in your right. Total over $10? The right-hand item is too expensive even with the cheapest companion on the shelf, so it goes back, and you never pick it up again. Under $10? The left-hand item is too cheap even with the most expensive companion, so it goes back. Every item you put back is gone for good, and each check puts one item back. That's why you finish in one pass along the shelf.

Sorted list [2, 5, 9, 14, 20], target 16. The first check is 2 + 20 = 22. What do you know now?

Right. 2 is the smallest partner 20 could have, and 2 + 20 is already 6 over. Every other pair with 20 is bigger. So the whole "20" column of the grid is crossed out with one check: 4 pairs gone. Next check: 2 + 14 = 16, found.

Plug in the numbers. Every pair that uses 20 is 20 + (something from 2, 5, 9, 14). The smallest of those is 2 + 20 = 22, already over 16. So 5 + 20, 9 + 20 and 14 + 20 are all over too, without checking them: drop 20. Moving lo would be the wrong direction: it makes the sum bigger, and we're already too big. The rule: too big, shrink the big end; too small, grow the small end.

The same move in other problems

  • Three numbers that sum to zero: sort, fix the first number, then run opposite-ends pointers on the rest. O(n²) instead of O(n³).
  • Merging two sorted lists (the merge step from the sorting chapter) is two pointers, one per list, each only moving forward.
  • Container with the most water: two walls, one at each end; always move the shorter wall inward. The shorter wall limits every narrower container that uses it, so it's hopeless for the rest of the search.
  • Counting pairs at or under a limit (exercise 4): when a pair is small enough, ask how many other pairs you just learned are small enough too.
Go deeper: the proof, and when to use a hash set instead

The invariant. An invariant is a statement that's true before the loop starts and stays true after every step. Here it is: "if a pair that hits the target exists, both of its numbers lie between lo and hi". At the start, lo and hi are the two ends, so it's true. Each step drops an end that we just proved can't be in any answer, so it stays true. When lo meets hi with nothing found, no pair lies between them, so no pair exists. This is the sentence that turns "it seems to work" into "it's correct".

Unsorted input. If the list isn't sorted, you have two options. Sort it first and use two pointers: O(n log n) time, and O(1) extra memory with an in-place sort like heapsort (Python's Timsort can use up to n/2 extra slots). Or walk the list once with a hash set of the numbers seen so far, asking "is target − x in the set?": O(n) expected time but O(n) memory. For "is there a pair with exactly this sum", the hash set wins on time. But a hash set only answers exact questions. "The pair closest to the target", "how many pairs are under a limit" or "all triples summing to zero" need the order, and that's when sorting earns its cost.

4Same direction: a reader and a writer

The two pointers don't have to start at opposite ends. In the second shape, both move left to right, one fast and one slow. The classic job is cleaning a list in place, which means without building a second list: O(1) extra memory.

Say you want to remove every 0 from a list, keep the order of the rest, and not use a second list. The tempting way is to delete each 0 when you see it. But deleting from the middle of a Python list shifts everything after it one slot left, so each delete is O(n). On a million items where half are zeros, that's about 250 billion shifts.

Instead, use two pointers. read visits every item once. write marks where the cleaned part ends. When read finds an item to keep, copy it down to write and move write forward.

def remove_all(nums, bad):
    write = 0                          # nums[:write] is the cleaned part
    for read in range(len(nums)):      # read looks at every item exactly once
        if nums[read] != bad:
            nums[write] = nums[read]   # keep it: copy it down to the write spot
            write += 1
    return write                       # new length; nums[write:] is leftover junk
[ kept, final  |  already read, now junk  |  not read yet ]
 0              write                       read          n

write never gets ahead of read, so you never overwrite an item you haven't read yet. That's n reads, at most n writes, and no extra list. Notice that the function returns a length. The slots after it still hold old values. C arrays can't shrink, so "remove in place" in C, and in many interview prompts, works exactly this way.

Same-direction pointers: a fast reader looks at every item once, and a slow writer marks the end of the finished part. O(n) time, O(1) extra memory, and the writer can never overtake the reader.

You run remove_all on [0, 3, 0, 0, 5, 7] with bad = 0. It returns 3. What does the list look like afterwards?

Right. The function only ever overwrites slots 0, 1 and 2 (with 3, 5 and 7). Slots 3, 4 and 5 keep whatever was there: the original 0, 5, 7. The list never changes length; the returned 3 tells you how much of it is meaningful.

Trace the writes. write starts at 0. The 3 at index 1 is copied to slot 0. The 5 at index 4 goes to slot 1. The 7 at index 5 goes to slot 2. That's every write the function does. It never deletes anything, and it never writes zeros, so slots 3 to 5 keep their old values: 0, 5, 7. In-place functions like this return the new length and leave junk after it.

Go deeper: fast and slow pointers on a linked list (Floyd's cycle detection)

Same direction, different speeds. On a linked list (each node points to the next), move slow one node per step and fast two.

  • Middle of the list: when fast reaches the end, slow is halfway. One pass, no counting.
  • Does the list loop back on itself? If there's no loop, fast reaches the end. If there is one, fast enters the loop first and keeps lapping. Once both are inside a loop of length c, fast gains exactly one node on slow per step, so the gap closes within c steps and they land on the same node. O(n) time and O(1) memory. A set of visited nodes also works, but costs O(n) memory.
  • Where does the loop start? Let a be the number of steps from the head to the loop's first node, and b the steps from there to the meeting point. Slow walked a + b; fast walked twice that. The extra a + b steps fast took were whole laps, so a + b is a multiple of c. Now put one pointer back at the head and move both one step at a time. After a steps, the one from the head is at the loop's start, and the other has gone a + b in total from the loop's start, a whole number of laps, so it's there too. They meet exactly at the loop's start.
  • The same trick finds the duplicate in a list of n + 1 numbers from 1 to n without changing the list or using extra memory: treat each value as a "next" pointer, and the duplicate is where the loop starts.

5Fixed window: every stretch of exactly k

Back to the busiest hour. A window is the range you're currently looking at. A fixed-size window always holds exactly k items. When it slides one step right, exactly one number joins on the right and exactly one leaves on the left. So keep a running total and update it with two steps, instead of adding k numbers again.

A window of k = 5 sliding over 10 minutes of traffic. Green is the window; blue just joined; red just left. Watch the work counter: sliding costs 2 per step whatever k is, while re-adding each window costs k − 1 = 4.
def max_sum_of_k(nums, k):             # assumes 1 <= k <= len(nums)
    window = sum(nums[:k])             # the first window: k numbers, added once
    best = window
    for right in range(k, len(nums)):
        window += nums[right]          # the new number joins on the right
        window -= nums[right - k]      # the oldest number leaves on the left
        best = max(best, window)
    return best

For the year of traffic, that's about 1.05 million steps instead of 31 million. For the busiest day (k = 1,440) it's still about 1.05 million, while re-adding each window costs 754 million. The sliding cost doesn't depend on k at all.

A fixed window of size k: when it slides, one item joins and one leaves. Update the running answer with those two, and the whole scan is O(n), whatever k is.

n = 1,000,000 numbers, k = 1,000. About how many additions does re-adding every window take, compared with sliding?

Right. There are 999,001 windows, and re-adding each takes 999 additions: about 998 million. Sliding takes 999 for the first window, then 2 per step: about 2 million. A 500× difference, and it grows with k.

Count windows and the cost per window. A window can start at index 0 up to index n − k, so there are n − k + 1 = 999,001 windows. Re-adding one costs k − 1 = 999 additions, so the total is about 999,001 × 999 ≈ 1 billion: not one pass. And never a trillion: even the worst k, about n/2, gives n²/4 = 250 billion. Sliding pays 2 per step, one in and one out: about 2 million.

Go deeper: the maximum of every window (monotonic deque)

A sum is easy to update: subtract what leaves. A maximum isn't. When the biggest number leaves the window, which one is the new biggest? Rescanning the window costs O(k) per step, O(n·k) total.

The fix is a deque (a list you can add to and remove from at both ends in O(1)) of indexes whose values decrease from front to back. When a new number arrives, pop from the back every item that's ≤ it. Those can never be the maximum again: the new number is at least as big and will stay in the window longer. Then push the new index. If the front index has slid out of the window, pop it from the front. The front is always the current maximum.

Each index is pushed once and popped at most once, so the total work is O(n), the same "count the total moves" argument as everywhere in this chapter. For [1, 3, −1, −3, 5, 3, 6, 7] with k = 3, the maximums are 3, 3, 5, 5, 6, 7. The data structures chapter calls this a monotonic queue.

Go deeper: windows over a stream, and rate limiters

A fixed window only needs the last k items, never the whole history. That's why it fits streams, data that never ends: "requests in the last 5 minutes" on a monitoring dashboard is a sliding window kept in a ring buffer (a fixed-size array whose end wraps around to the start) or a deque, with old items dropped from the front as time moves on.

Rate limiters ("at most 100 requests per user per rolling minute") use the same idea in two versions. A sliding window log keeps the timestamp of every request in the last 60 seconds and drops the old ones from the front: exact, but it stores up to 100 timestamps per user. A sliding window counter keeps only two counts, this minute's and last minute's, and estimates. 15 seconds into this minute, with 30 requests so far and 80 last minute, it assumes the last 45 seconds of last minute held 80 × 45/60 = 60 of them: estimate 30 + 60 = 90. Constant memory, slightly approximate. The rate-limiting chapter (02.14) goes further.

6Variable window: the caterpillar

The second question, "the shortest stretch with at least 1,000,000 requests", has no fixed size. The window has to grow and shrink. To keep things small enough to trace by hand, take a cousin of that question: the longest run of days whose total spending stays within a budget of 8, with daily spends [2, 1, 3, 4, 1, 1, 2, 5, 1]. Every number is positive, and that matters a lot (section 7).

The brute force tries every start and every end: 9 × 10 / 2 = 45 ranges. A variable-size window moves like a caterpillar instead. Each step, the right end eats the next number. If the window now breaks the rule (the sum is over 8), the left end lets go of numbers, one at a time, until the window is valid again. Then record its length.

inputbudget 8
The caterpillar: L and R are the two ends; green is the window. Blue just got eaten on the right, red was just let go on the left. Watch the move counters: R moves once per number; L moves several times at some steps and not at all at others, but never more than n times in total. Leave the "One negative" input for section 7.
def longest_within_budget(spend, budget):   # spends and budget are >= 0
    left = total = best = 0
    for right in range(len(spend)):
        total += spend[right]                # the right end eats one number
        while total > budget:                # over budget: let go from the left
            total -= spend[left]
            left += 1
        best = max(best, right - left + 1)   # spend[left..right] is valid now
    return best

Check it on the edges. An empty list: the loop never runs, and the answer is 0. A single number bigger than the budget: the while lets go of it, left ends up at right + 1, and the length is 0. All numbers equal: the window just settles at the right size and slides.

Why it's O(n), even with a loop inside a loop

The inner while can run several times in one step. In the figure, when the 5 arrives at index 7, the left end lets go of two numbers in a row (4, then 1). So one step can cost a lot. But left only ever moves forward, and it never passes right + 1. Across the whole run, it moves at most n times in total. right moves exactly n times. That's at most 2n pointer moves, each O(1): O(n). In the figure, R moves 9 times and L moves 6 times: 15 moves, under 2n = 18.

This is rule 6 from the complexity chapter: don't multiply the worst inner loop by the number of outer steps; count the total work across the whole run. The cost is called amortized O(1) per step, because the occasional expensive step is paid for by many cheap ones.

What's the time complexity of this loop over n numbers?

left = total = 0
for right in range(n):
    total += nums[right]
    while total > budget:
        total -= nums[left]
        left += 1

Right. Count the line left += 1 over the whole run: left starts at 0, only goes up, and never passes n. So that line runs at most n times in total, however the runs are spread across the steps. n steps of the for loop plus at most n steps of the while loop: 2n.

"Up to n times for each right" is true for one step but not for all of them at once. Think of a bucket of n tokens. Every time left += 1 runs, it spends a token, because left moves forward and can never come back. There are only n tokens for the whole run. So if one step spends 5 tokens, other steps must spend none. Total: n for the outer loop + at most n for the inner one = O(n). Nothing here halves anything, so there's no log n either.

Why it's safe to let go (the part interviewers probe)

Being fast is no use if it's wrong. When the window [left .. right] goes over budget, we let go of left and never look at it as a start again. How do we know the best answer doesn't start at left?

Every range that starts at left and that we haven't checked yet is longer: [left .. right′] with right′ > right. It holds everything in [left .. right] plus more numbers, and all the numbers are positive, so its sum is even bigger. Over budget now means over budget for every later end. That start is hopeless forever. This is the pair grid from section 3 again: one check crosses out a whole row, here the row of every range that starts at left.

And after the while stops, the window is the longest valid range that ends at right, because any longer one would start before left, and those starts were all proven hopeless. Checking the longest valid range for every end means checking the answer.

A variable window works when the rule has one direction: once a window breaks the rule, growing it can't fix it. Then each time the left end lets go, it retires a start for good. Each pointer moves at most n times, so the whole scan is O(n).
Explain it another way: a caterpillar on a ruler

A caterpillar crawls along a ruler. It stretches its head forward one mark at a time, and if its body gets too long (the rule breaks), it pulls its tail forward until it's comfortable again. Its tail never goes backwards, and neither does its head. By the time it reaches the end of the ruler, its head has visited every mark once and its tail at most once. However wiggly the trip, that's at most two visits per mark.

Where the picture breaks: a real caterpillar pulls its tail forward because it wants to. Ours only lets go when it's proven that the tail position can't start the best answer. That proof is the part you must say in an interview.

Two shapes: longest and shortest

Variable-window problems come in two shapes, and the difference is which direction is "good":

  • Longest valid stretch (within a budget, no repeated letter, at most k different letters): growing can break the rule. Eat on the right every step, let go on the left while the window is invalid, then record. That's the code above.
  • Shortest valid stretch (sum at least a target, contains every letter of a word): growing can only help. Eat on the right until the window becomes valid; then, while it's still valid, record it and let go on the left to see if a shorter one works.

Exercises 7 and 8 are one of each. For longest-without-repeats, the rule is "no letter twice": keep a set of the letters inside the window, and when the new letter is already in the set, let go from the left until it isn't.

Longest substring without a repeated letter, on "abcbd". The window is "abc" (left = 0) and the right end eats the second "b" at index 3. Where does left end up?

Right. The rule broke because of the first "b", so the left end has to let go until that "b" is gone: first "a", then "b". The window "cb" is valid again. Starting over at index 3 would throw away "c", which is still part of a valid window.

Ask what broke the rule: two b's in the window. Letting go of "a" alone leaves "bcb", still two b's, so the while keeps going and lets go of the first "b" too. Now "cb" is valid, left = 2, and we stop: letting go of anything more would only make the window shorter for no reason. Restarting at index 3 throws away the "c", which never caused a problem.

7When the window breaks: negative numbers

Everything in section 6 rested on one sentence: "all the numbers are positive, so its sum is even bigger". Allow a negative number and that sentence is false, so the whole argument falls apart.

Go back to the figure in section 6 and pick One negative: [3, 1, 1, 3, 6, −8, 6], budget 8. When the 6 arrives at index 4, the window [3, 1, 1, 3, 6] sums to 14, so the left end lets go of 3, 1, 1 and 3. But [3, 1, 1, 3, 6, −8] sums to 6, within budget, and has length 6. The window answers 4. It retired start 0, betting that every longer range from there would be bigger. The −8 made it smaller, and the bet was lost.

The property the window needs is called monotonicity: as a window grows, "valid" can turn into "invalid" (or the other way round, for the shortest shape) but never flip back and forth. Some rules have it and some don't:

RuleOne direction?Sliding window?
sum ≤ budget, every number ≥ 0yes: growing only addsyes
sum ≥ target, every number ≥ 0yesyes
no letter repeated; at most k different lettersyes: growing never removes a letteryes
sum ≤ budget, negatives allowedno: a later negative can bring it backno, use prefix sums plus a binary search over their running maximum, O(n log n)
sum exactly k, negatives allowednono, use prefix sums + a hash map (section 9)
exactly k different lettersno: too few, then right, then too manyto count them: (at most k) − (at most k − 1); see section 11
A sliding window is only correct when growing the window pushes the rule in one direction. Negative numbers break that for sums. Before you write the loop, say out loud why letting go of the left end is safe.

Which of these can a sliding window solve correctly?

Right. With only positive numbers, a window that reaches 10 stays at 10 or more as it grows, and a window that's below 10 stays below as it shrinks. So letting go from the left while the sum is still ≥ 10 never throws away an answer. The two others allow negatives, so a longer window can have a smaller sum, and no start can be safely retired.

Test each one with a single negative number. Longest with sum ≤ 10 on [6, 6, −5]: the window lets go of the first 6 when [6, 6] hits 12, yet [6, 6, −5] = 7 was fine and longer. Exactly 10 with negatives: in [10, −3, 3], both [10] and the whole list sum to 10. Once the window holds [10], it can't know whether eating more numbers will bring the sum back to 10, so it can't decide what to let go. Only the all-positive option has the one-direction property: once the sum reaches 10, more numbers keep it there.

8Prefix sums: every range in one subtraction

Now the dashboard: 100,000 questions of the form "total from minute a to minute b". A window doesn't help, because the questions jump around. Instead, do one pass of work up front and make every question cheap.

A prefix sum is a running total. Define P[0] = 0, and P[i] = the sum of the first i numbers. Then the sum of nums[i:j] (from index i up to, but not including, j) is

sum(nums[i:j]) = P[j] − P[i]       everything before j, minus everything before i

With nums = [3, 4, −2, 5, −6, 1, 4, 2, −3, 3], the prefix sums are P = [0, 3, 7, 5, 10, 4, 5, 9, 11, 8, 11]. The sum of nums[2:6] is −2 + 5 − 6 + 1 = −2, and P[6] − P[2] = 5 − 7 = −2. Same answer, one subtraction.

def build_prefix(nums):
    P = [0] * (len(nums) + 1)          # one more slot than nums: P[0] = 0
    for i, x in enumerate(nums):
        P[i + 1] = P[i] + x            # P[i + 1] = sum of the first i + 1 numbers
    return P

def range_sum(P, i, j):                # sum of nums[i:j], i.e. nums[i] .. nums[j - 1]
    return P[j] - P[i]

The extra slot P[0] = 0 is what makes ranges that start at index 0 work without a special case: sum(nums[0:j]) = P[j] − P[0] = P[j]. For the dashboard, that's 525,600 additions once, then one subtraction per question: about 625,600 steps, 0.06 seconds instead of up to 1.5 hours.

It helps to see the prefix sums as a line, like the height of a hiking trail. Each number is a step up or down. The sum of a range is how much higher the trail is at the end of the range than at its start.

Prefix sums: P[0] = 0 and P[i + 1] = P[i] + nums[i]. Then sum(nums[i:j]) = P[j] − P[i]. O(n) once, then O(1) per range, and negative numbers don't matter.

With P[0] = 0 and P[i] = the sum of the first i numbers, which expression is the sum of nums[2] through nums[5], both included?

Right. nums[2] through nums[5] is nums[2:6] in Python terms: start at 2, stop before 6. P[6] holds nums[0..5]; P[2] holds nums[0..1]; the difference is exactly nums[2..5].

Plug in numbers: nums = [5, 1, 2, 7, 3, 4], so P = [0, 5, 6, 8, 15, 18, 22]. The answer should be 2 + 7 + 3 + 4 = 16. P[6] − P[2] = 22 − 6 = 16. P[5] − P[2] = 18 − 6 = 12: it misses the 4, because P[5] stops before nums[5]. P[6] − P[1] = 22 − 5 = 17: it includes nums[1] = 1. Read P[i] as "the total of everything before index i".

Go deeper: 2D prefix sums, difference arrays, changing data, floats

2D prefix sums. For a grid, let P[r][c] be the sum of every cell in rows 0 to r − 1 and columns 0 to c − 1. The sum of a rectangle covering rows r1 to r2 − 1 and columns c1 to c2 − 1 is P[r2][c2] − P[r1][c2] − P[r2][c1] + P[r1][c1]: take the big rectangle, subtract the strip above and the strip to the left, then add back the corner you subtracted twice. Graphics calls this a summed-area table (fast box blurs), and the classic Viola–Jones face detector calls it an integral image.

Difference arrays: prefix sums backwards. You get q updates of the form "add v to every item from index a up to, but not including, b", then need the final list once. Doing each update item by item is O(n·q). Instead, keep D (n + 1 slots, all 0) with D[a] += v and D[b] −= v for each update, then take the prefix sums of D at the end: O(n + q). Example: hotel bookings, each one adds 1 room for nights a to b − 1; the prefix sums of D give the rooms occupied every night.

When the data changes. Changing one number changes every prefix sum after it: O(n) per update. If updates and range sums are mixed, use a Fenwick tree (binary indexed tree) or a segment tree: O(log n) for both. They're in the data structures section (topic 01.10).

Floats. Running totals of floating-point numbers pile up rounding error, and subtracting two huge totals that are almost equal loses digits. Store money as integer cents where you can. In Java or C++, a running total of ints can overflow; use a 64-bit type. Python's ints don't overflow.

9Prefix sums plus a hash map: an exact total

Section 7 left a hole: "how many stretches sum to exactly k", with negatives allowed. The window can't do it, and the brute force checks n²/2 ranges. Prefix sums turn it into a lookup.

A range nums[i:j] sums to k exactly when P[j] − P[i] = k, that is, when P[i] = P[j] − k. So, standing at position j, the good starts are the earlier positions whose prefix sum is exactly P[j] − k. "Have I seen this value before, and what do I know about it?" is a hash map question: O(1) on average. One pass does it all. At each j, look up first, then record P[j]. O(n) time and O(n) memory. Negative numbers don't matter, because nothing assumed the trail only climbs.

Here's the idea on a different question: the longest stretch of games where wins and losses break even. Write +1 for a win and −1 for a loss. A break-even stretch sums to 0, so it runs between two positions with the same prefix sum. For the longest one, remember the first time each prefix value appeared.

def longest_break_even(results):       # +1 for a win, -1 for a loss
    first_seen = {0: -1}               # prefix sum 0 "happens" just before index 0
    run = best = 0
    for i, r in enumerate(results):
        run += r                       # run = sum of results[0..i]
        if run in first_seen:          # same height as before: the stretch between sums to 0
            best = max(best, i - first_seen[run])
        else:
            first_seen[run] = i        # keep only the first time: it gives the longest stretch
    return best

Exercise 9 asks a different question about the same picture: not "how long", but "how many". Think about what the map has to remember for that, and what the starting entry should be.

The sum of a range is the difference of two prefix sums. So "a range ending here with sum k" means "an earlier prefix sum equal to P[j] − k", which is a hash map lookup. n² ranges become n lookups, and negatives are fine.
Explain it another way: a hiking altimeter

You're hiking a trail that goes up and down, writing your altitude in a notebook at every marker. You want stretches where you climbed exactly 100 m in total. At each marker you don't re-walk the trail. You look in your notebook: "was I ever exactly 100 m lower than I am right now?" Each earlier marker at that altitude is the start of one such stretch. Going downhill (negative steps) doesn't confuse the notebook at all. That's exactly what confuses a sliding window.

Why does longest_break_even start with first_seen = {0: -1} instead of an empty dict?

Right. A stretch from index 0 to i sums to P[i + 1] − P[0], and P[0] = 0 sits "before index 0". Without the entry, [+1, −1] would return 0 instead of 2: the code would never see height 0 before index 1. Storing −1 makes the length come out as i − (−1) = i + 1.

Try [+1, −1] without the entry. At i = 0, run = 1: not seen, store {1: 0}. At i = 1, run = 0: not seen, so store {0: 1}, and best stays 0. But the whole list breaks even! The missing piece is the height before any game: 0, at position −1. There's no KeyError risk either way (the code checks in first), and empty stretches never count: the length i − (−1) is always at least 1.

A list of daily account balance changes, some up, some down. You need the number of stretches of days whose changes add up to exactly 0. Which tool?

Right. A stretch sums to 0 exactly when two prefix sums are equal, so for each day you look up how many earlier days had the same running balance. Negatives are fine. O(n).

Two signals decide it. "Some down" means negative numbers, so a sliding window can't safely let go of a start: a later drop can bring a too-big sum back to 0. And "stretches of days" means the order matters, so sorting destroys the very thing you're asked about: after sorting, neighbours are no longer consecutive days. A stretch sums to 0 when the running balance is the same at its two ends: that's an equal-prefix-sum lookup in a hash map.

11What to say in the interview

When one of these problems comes up, a strong answer sounds like this:

  1. Name the brute force and its cost: "Checking every start and end is n²/2 ranges, so O(n²)."
  2. Name the waste, and why skipping it is safe: "All numbers are positive, so once a window is over budget, every longer window from that start is too. I can retire the start."
  3. State the invariant (the fact that stays true after every step): "After the inner loop, nums[left..right] is the longest valid window ending at right."
  4. Give the complexity with the reason: "There's a loop inside a loop, but left only moves forward, at most n times in total. So it's O(n) time and O(1) extra memory."
  5. Test the edges out loud: empty input, one item, no valid window (return 0), all items equal, k bigger than n, and the question that catches most people: "can the numbers be negative?"
Go deeper: follow-up questions interviewers like
  • "What if the numbers can be negative?" Exact sums: prefix sums + hash map. Shortest stretch with sum ≥ target: prefix sums plus a monotonic deque of increasing prefix values, still O(n). Or prefix sums plus binary search when the prefix sums happen to be sorted (all positive), O(n log n).
  • "How many stretches have exactly k different letters?" That rule has no single direction, but "at most k" does, and a window can count: after the inner loop, every start from left to right gives a valid range ending at right, so add right − left + 1. Then exactly k = (at most k) − (at most k − 1). For the longest one, the at-most-k window already finds it, as long as the string has at least k different letters.
  • "Sum divisible by k?" Same map, keyed by P[j] mod k: two prefix sums with the same remainder bound a range whose sum is a multiple of k.
  • "Can three-sum beat n²?" Not by much. No known algorithm does three-sum in O(n^(2−ε)) for any fixed ε > 0, and that belief (the "3SUM conjecture") is used to argue other problems are hard too.
  • "The data is a stream." A fixed window needs O(k) memory, a variable window needs the items between its two ends, and prefix-sum-plus-map needs one entry per distinct prefix value. Say which one you're paying for.
  • "The data doesn't fit on one machine." Prefix sums split well: each machine sums its chunk, a short pass adds up the chunk totals, then each machine adds its offset. That's a parallel prefix sum (a "scan"), a basic building block on GPUs.

✓What to remember

  1. Every brute force here walks a triangle of n²/2 pairs or ranges. Neighbouring candidates overlap; reuse the overlap or prove a whole row can't win.
  2. Opposite ends on sorted input: if one end is hopeless with its best partner, drop it. At most n − 1 checks. Unsorted, exact sum: a hash set is O(n).
  3. Same direction: a reader visits each item once, a writer marks the finished part. In place, O(1) memory. Fast and slow pointers find loops in linked lists.
  4. Fixed window: one in, one out, 2 steps per slide whatever k is.
  5. Variable window: grow on the right, let go on the left. O(n) because each pointer moves at most n times in total.
  6. It's only correct when the rule has one direction as the window grows. Negative numbers break it for sums. Say why letting go is safe.
  7. Prefix sums: P[0] = 0, sum(nums[i:j]) = P[j] − P[i]. O(n) once, O(1) per range, negatives fine.
  8. Exact sums with negatives: for each j, look up earlier prefix sums equal to P[j] − k in a hash map. O(n).

Warm-up · pen and paper

1. Cross out the grid

Draw the pair grid for the sorted list [1, 2, 4, 7, 11, 15]. Run opposite-ends pointers for target 15, then for target 20. For each check, write the sum, which pointer moves, and how many pairs that check crossed out. How many checks did each target take, out of 15 pairs?

Answers

Target 15: 1 + 15 = 16 > 15: hi moves, column 15 crossed out (5 pairs); 1 + 11 = 12 < 15: lo moves, row 1 crossed out (4 pairs); 2 + 11 = 13 < 15: lo moves, row 2 crossed out (3 pairs); 4 + 11 = 15: found. 4 checks. Target 20: 1 + 15 = 16 < 20: lo moves, row 1 crossed out (5 pairs); 2 + 15 = 17 < 20: lo moves, row 2 crossed out (4 pairs); 4 + 15 = 19 < 20: lo moves, row 4 crossed out (3 pairs); 7 + 15 = 22 > 20: hi moves, column 15 crossed out (2 pairs); 7 + 11 = 18 < 20: lo moves, row 7 crossed out (1 pair). Now lo = hi, so there's no pair: 5 checks, and the crossed-out counts 5 + 4 + 3 + 2 + 1 add up to all 15 pairs.

Warm-up · pen and paper

2. Pick the tool

Which tool, and why? (a) The average temperature of every 7-day stretch. (b) The longest run of days with total rainfall at most 50 mm. (c) One million questions "total sales from day a to day b" on last year's data. (d) The number of stretches of a bank account's daily changes that add up to exactly −100. (e) Two numbers in a sorted list whose sum is closest to 1,000. (f) Whether a linked list loops back on itself, using O(1) memory. (g) Any two numbers in an unsorted list that add up to 50.

Answers

(a) Fixed window, k = 7. (b) Variable window: rainfall is never negative, so the rule has one direction. (c) Prefix sums: O(n) once, then O(1) per question. (d) Prefix sums + hash map: changes can be negative, so no window. (e) Opposite-ends pointers, keeping the closest sum seen; a hash set can't answer "closest". (f) Fast and slow pointers (Floyd). (g) A hash set of the numbers seen so far, O(n); or sort and use two pointers, O(n log n) but less memory.

Warm-up · pen and paper

3. Break the window

The "shortest stretch with sum ≥ target" window (section 6, second shape) is correct when every number is positive. Find a list of three numbers, one of them negative, and a target, where it gives the wrong answer. Then say which step threw the right answer away.

One answer

[3, −2, 4] with target 4. The window grows to [3, −2, 4] (sum 5, valid, length 3), then lets go of 3: the sum drops to 2, no longer valid, so it stops letting go and finishes with 3. But [4] alone has sum 4: length 1. Letting go of the −2 would have raised the sum. With only positive numbers, a shorter window always has a smaller sum, so stopping is safe; with a negative inside, it isn't.

Core · code

4. count_pairs_at_most(nums, limit) in O(n log n)

Count pairs i < j with nums[i] + nums[j] ≤ limit, in an unsorted list with duplicates and negatives. Sort a copy, then use opposite-ends pointers. The twist: when a pair passes, a whole row of pairs passes with it; count them all at once. The test's numbers count every addition and subtraction, and allow 3n of them. Checking every pair is about 2,000,000 for n = 2,000.

Core · code

5. dedupe_sorted(nums, keep), in place

In a sorted list, keep each value at most keep times, in order, in the front of the list, and return the new length. A reader and a writer, as in section 4, but the keep-or-skip question is different: which already-written slot tells you whether one more copy is allowed? The test hands you a fixed-size array that counts reads and writes and measures your extra memory, so deleting and shifting (O(n²) writes) or building a second list both fail.

Core · code

6. anagram_starts(text, pattern), a fixed window of letter counts

Find every index where a rearrangement of pattern starts in text. The window is the size of the pattern; what slides in and out are letter counts. The test's text counts every character you read and allows about 5 reads per character. Re-counting each window from scratch reads n × m: 2,000,000 for n = 20,000 and m = 100.

Core · code

7. longest_k_distinct(s, k), a variable window (longest shape)

The longest substring with at most k different letters. A set isn't enough any more: when the left end lets go of a letter, you need to know whether another copy of it is still inside. The test allows about 6 reads per character; trying every start reads about 18 million for n = 6,000.

Core · code

8. shortest_reaching(nums, target), a variable window (shortest shape)

The second question from section 1, on positive numbers: the length of the shortest stretch with sum ≥ target, or 0 if there's none. The test's numbers count additions and subtractions and allow 3n; restarting the sum at every start costs millions for n = 5,000. It also tests a target bigger than the whole list's sum.

Core · code

9. count_sum_k(nums, k), prefix sums plus a hash map

How many stretches sum to exactly k, with negatives and zeros allowed. A sliding window gives wrong answers here (the tests include cases where it does). The numbers count additions and subtractions, and allow 3n. Zeros are the trap: [0, 0, 0] with k = 0 has 6 answers.

Stretch · design

10. A rate limiter for 10 million users

"At most 100 requests per user in any rolling 60 seconds." Design it twice: once as a sliding window log (a deque of timestamps per user) and once as a sliding window counter (two counts per user). For each, how many bytes per active user, and how much memory for 10 million active users? What does the counter get wrong, and when would that matter? What happens when one user sends 1,000 requests in one second?
