Chapter 2 · Part 9

Connect everything, cheaply

P1 Minimum spanning tree (Kruskal, Prim)about 55 minutes10 quick checks · 10 exercises

You have some places and a price list for joining pairs of them. You want every place joined to every other, directly or through others, for the least money. That's the minimum spanning tree problem. It looks like it needs a search over a huge number of options, but two short greedy algorithms solve it exactly: Kruskal's and Prim's. This chapter shows why greedy is safe here, which is the part interviewers probe. It also shows when each algorithm wins, and how to spot an MST hiding inside clustering, bandwidth and route-planning questions.

By the end you'll be able to

  2. State and prove the cut property and the cycle property, with a picture.
  3. Run Kruskal (sort + union-find) and Prim (grow one tree with a heap) by hand, and give their costs.
  4. Pick between Kruskal, heap Prim and array Prim from the graph's shape (sparse or dense).
  5. Explain why an MST is not a shortest-path tree, and when the MST is unique.
  6. Use the MST for clustering, widest paths and a 2× approximation for the traveling salesman.

1The problem: fiber for seven towns

An internet provider wants to bring fiber to seven towns, A to G. Engineers have priced the 12 trenches that are possible (rivers and hills rule out the rest). Each price is in units of $100,000: the A–B trench costs 9, so $900,000.

Digging all 12 costs 90 units: $9 million. But the provider only needs every town to reach every other town, possibly through a third town. Which trenches should it dig?

The obvious approach is to try every combination. Here's how fast that grows:

  • For our 7 towns, the answer will turn out to use 6 trenches. There are 924 ways to choose 6 of the 12. Checking all 924 is fine.
  • For 30 towns where any pair can be joined, there are 3028 ≈ 2.3 × 1041 possible networks without loops (that count is called Cayley's formula). At a billion checks per second, that takes about 7 × 1024 years.

Real problems have thousands of towns, or millions of points. So we need an idea, not a faster computer. The idea will be greedy: always grab the cheapest trench that's safe. The whole chapter is about what "safe" means and why it works.

2What the answer looks like

Before looking for the cheapest network, let's work out what shape it must have.

It has no loops. Suppose the network has a loop: A–B, B–E, E–D, D–A, say. Cut out the most expensive trench on that loop. Is everyone still connected? Yes. Any trip that used the removed trench can go the long way round the rest of the loop. So a loop always contains a trench you paid for and didn't need. The cheapest network has no loops. (One exception: if some prices are negative, someone pays you to dig, and extra trenches can save money. The Go deeper box in section 9 covers it. Here, all prices are positive.)

It has exactly n − 1 trenches. Picture the towns as islands. At the start there are 7 separate islands. Each trench that doesn't close a loop joins two separate islands into one, so the count of islands drops by exactly 1. To get from 7 islands down to 1 takes exactly 6 trenches. For n towns, n − 1.

A set of links that connects all n points and has no loops is called a spanning tree: "spanning" because it reaches every point, "tree" because it has no loops. Give every link a cost, called its weight. A spanning tree whose weights add up to the smallest possible total is a minimum spanning tree, or MST. In graph words: the towns are vertices (V of them) and the possible trenches are edges (E of them).

The cheapest way to connect n points is always a tree: no loops (a loop has a link you can drop), exactly n − 1 links (each link merges two groups, and you start with n groups).

A company connects its 50 offices with leased lines, as cheaply as possible. How many lines does it lease?

Right. Start with 50 separate offices. Each useful line merges two groups, so the number of groups drops by one per line. From 50 groups to 1 takes 49 lines. A 50th line would join two offices that are already connected, closing a loop.

Count groups instead of lines. At the start each office is alone: 50 groups. A line between two different groups merges them: 49 groups. Every line that isn't wasted lowers the count by exactly 1, so reaching 1 group takes 49 lines, however many lines were on offer. A 50th line would connect two offices that already reach each other: a loop, and money spent on nothing.

3The cut property: which link is safe to take

Greedy algorithms are risky. Grabbing the cheapest thing now can force you into an expensive choice later. So before we go greedy, we need a rule that says "this link is definitely part of a cheapest network". Here is that rule. It starts with a picture.

Draw a line across the map that splits the towns into two camps. Say West = {A, D, F} and East = {B, C, E, G}. In graph words, a split of the vertices into two non-empty groups is a cut, and an edge with one end in each group crosses the cut. Some trench has to cross the line, or West could never talk to East. Now look at the trenches that cross: A–B 9, B–D 10, D–E 11, E–F 12, F–G 13. The cheapest is A–B, at 9.

The cut property: for any cut, the cheapest edge crossing it belongs to a minimum spanning tree. Try it below before reading the proof.

Dashed yellow lines cross the cut; the thick green line is the cheapest one crossing. Press Show the MST to draw the MST's other edges dotted purple. Whatever cut you make, the green edge is always an MST edge.

Why it's true: the swap argument

Call the cheapest crossing edge e. Suppose someone hands you a cheapest network T that doesn't use e. We'll show we can swap e in without paying more.

  1. Add e to T. T already connects e's two ends, so adding e closes a loop.
  2. The loop crosses the line twice. Walk around the loop: e takes you from West to East. To get back to where you started, the loop must cross back to West somewhere. That's a second crossing edge, f, which is part of T.
  3. f costs at least as much as e, because e is the cheapest crossing edge.
  4. Remove f. You removed an edge from a loop, so everything is still connected, and you're back to n − 1 edges: a spanning tree again. Its cost is cost(T) + cost(e) − cost(f), which is no more than cost(T).

So there's a cheapest network that uses e. If e is strictly cheaper than every other crossing edge, the swap makes T strictly cheaper, which is impossible because T was already the cheapest. So in that case every MST uses e. This trick, "swap one piece of the optimal answer for the greedy choice and show it doesn't get worse", is called an exchange argument. The greedy chapter uses it again and again.

Explain it another way: two villages and a river

Two villages sit on opposite banks of a river. They must be joined by at least one bridge, and there are five places a bridge could go, with five prices. Whatever else you build on each bank, you need at least one bridge. Why would you ever build anything but the cheapest bridge? If your plan uses a pricier bridge, swap it for the cheapest one: the two banks are still joined, and you saved money. The cut is the river. The "swap" in the proof is exactly this, done carefully so you don't accidentally disconnect someone on the same bank.

Cut property: draw any line splitting the points into two camps. The cheapest link across the line is safe to take. Proof: if a cheapest network skips it, adding it makes a loop that crosses the line a second time; drop that other crossing link and the cost doesn't go up.

In the seven-town map, the cheapest trench touching town F is D–F (cost 3). Is D–F certainly in the MST?

Right. Put F alone in one camp. The edges crossing that cut are exactly F's own edges: D–F 3, E–F 12, F–G 13. D–F is the cheapest, so the cut property says it's in an MST (in every MST, since nothing else costs 3). The same works for every town: each town's cheapest link is in the MST.

The cut property works for any cut you like, so choose a convenient one: draw a small circle around F alone. Every trench crossing that circle touches F: D–F 3, E–F 12, F–G 13. The cheapest crossing is D–F, so it's in the MST. Nothing needs to be the cheapest on the whole map; it only has to be the cheapest across the line you drew. (On this map the cheapest overall is E–G at 2, and D–F still makes it in.)

In the swap proof, why does removing f leave everything connected?

Right. Any trip that used f can go around the rest of the loop instead (which now includes e). That's why the proof picks f from the loop, and not just any crossing edge of T: removing a crossing edge that's not on the loop could cut T in two.

Think about the loop as a ring road. Closing one stretch of a ring road doesn't strand anyone: you drive the other way around. f was chosen to be on the loop formed by adding e, so removing it is closing one stretch of the ring. f doesn't have to be T's most expensive edge, and crossing edges are often needed: e itself is one. If you removed some crossing edge of T that's not on the loop, you could cut the tree in two.

4The cycle property: which link is safe to throw away

The cut property tells you what to take. Its mirror image tells you what to throw away.

Look at the triangle C, E, G on the map. Its three edges cost C–E 4, E–G 2 and C–G 7. If a network uses all three, it has a loop, and the most expensive one, C–G, is the one to drop: C still reaches G through E. In fact, C–G is never needed at all:

      C
     / \      loop C–E–G:
  4 /   \ 7   C–G (7) is the
   /     \    most expensive,
  E ----- G   so no MST uses it
      2

The cycle property: if an edge is strictly the most expensive edge on some loop (a cycle), no MST contains it.

Why: suppose a spanning tree T uses C–G. Remove it. T falls into two pieces, one containing C and one containing G. Those two pieces are a cut. The rest of the loop (C–E–G) still runs from C's piece to G's piece, so some edge on it crosses the cut. Every other edge on the loop is cheaper than C–G, so add that crossing edge back: you have a spanning tree again, and it's cheaper. So T wasn't a minimum.

The two properties are two views of the same swap. The cut property says: the cheapest edge across any cut is in. The cycle property says: the most expensive edge on any cycle is out. Every MST algorithm is a way of applying these two rules in some order until n − 1 edges are in.

Cycle property: the strictly most expensive edge on any loop is in no MST, because removing it from a tree and adding a cheaper edge of the same loop gives a cheaper tree. Cut property says what to take; cycle property says what to skip.

The most expensive trench on the whole map, F–G at 13, is on the loop D–F–G–E–D. Someone says "the most expensive edge in the graph is never in the MST". Are they right?

Right. F–G is the most expensive on the loop D–F–G–E–D, so it's out. But picture an island town joined to the mainland by exactly one possible trench costing 1,000. That trench is on no loop, and without it the island is cut off, so every spanning tree, cheapest included, must use it. The cycle property needs a loop.

The cycle property is about loops, not about the whole graph. F–G is out because the loop D–F–G–E–D offers a cheaper way around it. Now imagine an island reachable by just one possible trench, at cost 1,000. There's no loop through it and no other way to reach the island, so every spanning tree must include it. Expensive is fine; "most expensive on a loop" is what rules an edge out.

Go deeper: the exact statements, with ties
  • Cut property. If e is a cheapest edge across some cut (ties allowed), then some MST contains e. If e is strictly cheaper than every other crossing edge, then every MST contains e.
  • Cycle property. If e is strictly the most expensive edge on some cycle, then no MST contains e. If it only ties for most expensive, then some MST avoids it, but another MST might use it.
  • Generic MST algorithm. Keep a set of edges known to be in some MST (start empty). Find a cut that none of them cross, and add a cheapest edge across it. Repeat n − 1 times. Kruskal, Prim and Borůvka are three ways of choosing the cut.
  • Borůvka (1926), the oldest of the three, was designed for an electricity network in Moravia. Every group, at the same time, takes its own cheapest outgoing edge (cut: that group versus everything else). Each round at least halves the number of groups, so there are log V rounds and O(E log V) total. Since all groups work at once, it's the natural choice for parallel and distributed MST. With ties you must break them the same way everywhere (for example by edge id), or two groups can pick two different equal-cost edges between them and make a loop.

5Kruskal: cheapest first, skip the loops

We have two safety rules. The simplest way to use both: look at the edges from cheapest to most expensive, and decide each one on the spot. The union-find chapter sketched this. Here's why it's correct.

When edge (u, v) comes up, everything cheaper has already been decided. Two cases:

  • u and v are already connected by edges we took. Those edges are all cheaper or the same price (we go cheapest first), so this edge would be the most expensive one on the loop it closes (or tied for most expensive, and then it adds nothing the loop doesn't already give). Cycle property: skip it.
  • u and v are in different groups. Use the cut "u's group | everything else". Could a cheaper edge cross it? Every cheaper edge has been decided already. The ones we took are inside groups. The ones we skipped joined two towns of one group. So no cheaper edge crosses this cut, which makes (u, v) a cheapest one that does (an equal-cost edge still waiting in the list may tie with it; the cut property allows ties). Cut property: take it.

One gap an interviewer may poke at: the cut property promises (u, v) is in some MST, but is it the same MST that holds the edges we already took? Yes, and the cut is why. None of the taken edges cross "u's group | everything else" (they're all inside groups). So in the swap proof, the edge f that gets swapped out crosses the cut and can't be one of ours. Start from an MST that holds all our earlier edges, swap (u, v) in, and you get an MST that holds all of them plus (u, v). Repeat for every edge taken. Prim's cut "tree | rest" has the same feature: no tree edge crosses it.

That's Kruskal's algorithm (Joseph Kruskal, 1956):

  1. Sort the edges by weight. Sort a copy, or a list of indexes, so you don't scramble the caller's list.
  2. Put every vertex in its own group.
  3. For each edge (u, v), cheapest first: if u and v are in different groups, take the edge and merge their groups; otherwise skip it.
  4. Stop once n − 1 edges are taken. If the edges run out first, the graph wasn't connected.

Step 3 asks "same group?" while groups keep merging. That's exactly what union-find does: find(u) == find(v) answers it, and union(u, v) merges. With union by size and path compression, each call costs about O(1) in practice.

Kruskal on the seven towns. Top: edges sorted by cost (yellow = being decided, green = taken, red = skipped). When an edge is taken, the blue towns are the group on one end of it: the cut that proves it safe. The dashed yellow lines also cross that cut, and they all come later in the sorted list. When an edge is skipped, the yellow towns show the loop it would close.

Cost. Sorting E edges costs O(E log E). The loop does at most 2E finds and V − 1 unions, almost O(1) each, so O(E · α(V)), where α is the "practically at most 4" function from the union-find chapter. The sort dominates, so Kruskal is O(E log E). That's the same as O(E log V): a graph without parallel edges has fewer than V² edges, so log E < 2 log V. (Parallel edges? Keep only the cheapest one per pair first.) Memory: the edge list, O(E).

Kruskal: sort edges, take each one whose ends are in different groups (cut property, using "u's group" as the cut), skip the rest (cycle property). Union-find answers "same group?". O(E log E), dominated by the sort.

You run Kruskal with a "same group?" check that does a BFS over the edges taken so far, instead of union-find. The graph has 100,000 towns and 300,000 edges. What happens?

Right. The answer is still correct, since BFS finds out whether u reaches v. But once the groups get big, each BFS walks a big group: up to 100,000 steps for each of 300,000 edges. Union-find answers the same question in a few steps. Sorting is only about 300,000 × 18 ≈ 5.5 million steps, so with BFS the checks, not the sort, dominate. Exercise 4's test has exactly this size.

BFS does answer "is v reachable from u?", so the answer is right. The problem is cost. Late in the run, most edges join two towns that are already in one big group, and a BFS has to walk through that group to find out: up to 100,000 steps, for each of 300,000 edges. Compare the sort: 300,000 × log₂ 300,000 ≈ 5.5 million steps. Union-find's find is a few steps per edge. That's why Kruskal and union-find always come as a pair.

6Prim: grow one tree outward

Kruskal builds many small trees all over the map and lets them merge. Prim's algorithm (Vojtěch Jarník in 1930, Robert Prim in 1957) picks one cut and keeps using it: "the tree so far | everything else".

Picture a town that only ever builds roads out of its own built-up area. Start at A. Look at every road leaving the built-up area, build the cheapest one, and the town on the other end joins. Look again at every road leaving the (now bigger) area, build the cheapest one, and so on, until every town has joined. By the cut property, every road built is safe, because it's the cheapest one crossing "inside | outside".

Finding the cheapest road out, fast

The plain way is to look at every edge at every step: V steps × E edges. For 10,000 towns and 50,000 edges, that's 500 million edge checks.

The fix: keep the edges leaving the tree in a min-heap, keyed by weight. When town v joins the tree, push each of v's edges whose far end is still outside. To grow, pop the cheapest edge. One catch: an edge that was pushed earlier may no longer leave the tree, because its far end joined in the meantime by a cheaper route. That's a stale entry. When you pop one, throw it away and pop again. This is called lazy deletion: you never search the heap to remove old entries, you just skip them when they surface.

Prim from A. Green towns are in the tree. Dashed yellow lines cross the cut "tree | rest". The heap row lists every entry still waiting, cheapest first (each one reads "from→to cost"). Once all seven towns are in, the remaining pops are red: stale entries whose far end has already joined.

Cost. Each edge is pushed at most once: when the first of its two ends joins, and only if the other end is still outside. So the heap sees at most E pushes and E pops, each O(log E). That's O(E log E) = O(E log V), with up to O(E) entries in the heap. Every vertex's adjacency list is read exactly once: when that vertex joins.

Prim and Dijkstra are one line apart

If you've read the shortest-paths chapter, this loop looks familiar. Same heap, same "pop the smallest, skip if already done, push the neighbors". The only difference is what goes into the heap:

# Dijkstra: distance from start
heappush(heap, (dist[u] + w, v))
# Prim: just this one edge
heappush(heap, (w, v))

Dijkstra asks "which town is closest to the start?". Prim asks "which town is closest to the tree, by a single edge?". Section 8 shows how differently the two answers can turn out.

Prim: grow one tree; the cut is always "tree | rest". A min-heap holds the edges leaving the tree; skip stale entries when popped. O(E log V). It's Dijkstra's loop with the key changed from dist[u] + w to w.

Prim pops the heap entry F→E, cost 12. It was pushed when F joined the tree, but E has joined since then (by B–E, cost 6). What should Prim do?

Right. The entry was pushed while E was outside. E has since joined by a cheaper edge, so F–E now joins two towns that are both in the tree; taking it would close a loop. Lazy deletion just skips it. Each skip costs one pop, O(log E), and there are fewer than E of them in total. Step the figure to the end to watch this exact pop.

A heap entry is a note written in the past: "F–E crosses the cut". When E joined (by B–E, cost 6), that note went out of date, but nobody went into the heap to erase it, because finding it would be slow. So when it surfaces, check: is the far end still outside? E isn't, so F–E connects two towns that are both in the tree, and taking it closes a loop. Changing E's parent would swap a 6 for a 12. Pop again.

Go deeper: eager Prim, decrease-key and Fibonacci heaps

The lazy heap can hold O(E) entries. The eager version keeps one entry per outside vertex: best[v] = the cheapest known edge from the tree to v. When a new tree vertex u offers v a cheaper edge, it lowers v's key in the heap (a decrease-key), which needs an indexed heap that knows where each vertex sits. The heap then holds at most V entries; time is still O(E log V). Python's heapq has no decrease-key, which is why the lazy version is the usual one in Python interviews.

With a Fibonacci heap (Fredman and Tarjan, 1987), decrease-key is O(1) amortized and Prim becomes O(E + V log V). That's better on paper for dense graphs, but the constant factors are large, so real code rarely uses it. For dense graphs there's a simpler win, in the next section.

7Dense graphs: drop the heap

Now a different problem. A drone company has 5,000 charging pads scattered over a city. Any two pads can be linked by a direct radio relay, and the cost is the distance between them. Find the cheapest way to link all the pads.

Every pair is a possible edge: 5,000 × 4,999 / 2 ≈ 12.5 million edges. A graph where E is close to V² is called dense; one where E is a small multiple of V (road maps, social networks) is sparse. Look at what the two algorithms so far would do here:

  • Kruskal must build and sort all 12.5 million edges. In Python each edge is a tuple of about 100 bytes, so that's over a gigabyte just to hold them, then about 12.5M × 24 ≈ 300 million steps to sort.
  • Heap Prim pushes up to 12.5 million entries: E log V ≈ 12.5M × 12 ≈ 150 million heap steps, and a heap just as big as Kruskal's list.

The fix is to notice what the heap is for. It finds the cheapest of many candidates. But in eager Prim there are only V candidates at any time, one best[v] per outside vertex. With only 5,000 of them, you can just scan a plain array:

  1. Keep best[v] (cheapest known edge from the tree to v) and parent[v] for every vertex. Start with best[start] = 0 and the rest at infinity.
  2. V times: scan the outside vertices for the smallest best[v]. That's V steps. Add that vertex u to the tree.
  3. For every outside vertex v, compute dist(u, v) and lower best[v] if it's smaller. That's another V steps.

That's V rounds of about 2V steps: O(V²) time and O(V) memory, with no heap and no edge list. Distances are computed when needed, never stored. For 5,000 pads, that's about 25 million simple steps, and a few arrays of 5,000 numbers.

10,000 points on a plane, and any two can be linked at a cost equal to their distance. Which approach do you pick?

Right. There are about 50 million pairs. Kruskal would store and sort all of them (several GB in Python). Heap Prim would push up to 50 million entries, about 50M × 13 ≈ 650 million heap steps. 8An MST is not a shortest-path tree

This is the most common mix-up, in interviews and at work. Both produce a tree. They answer different questions:

  • MST: "What's the cheapest set of links that connects everyone?" It minimizes the total cost of the network. It has no starting point.
  • Shortest-path tree (what Dijkstra builds from a start s): "What's the fastest route from s to each place?" It minimizes each place's distance from s. Change s and you get a different tree.

The hub-and-ring graph below makes the difference big. A warehouse H sits in the middle of six shops. Direct roads from H cost 10 to 15; the roads between neighboring shops on the ring cost 3 to 8. The MST uses the cheap ring roads plus a single spoke, for a total of 35. But the drive from H to shop R6 along the MST goes all the way round the ring: 35, against 15 on the direct road.

Blue lines: the MST. Dotted purple lines: the shortest-path tree from the start. The table compares each town's distance from the start inside each tree. Switch between them and compare the totals.

One more test that separates them: add 100 to every edge's cost. The MST doesn't change. Every spanning tree has exactly n − 1 edges, so every tree's total goes up by the same 100 × (n − 1), and the cheapest stays the cheapest. Shortest paths can change: a path with 5 edges gets 500 more expensive while a path with 1 edge gets only 100 more, so routes with fewer hops start winning.

MST: cheapest total network, no start point. Shortest-path tree: cheapest route from one start to each place. The path between two towns inside the MST can be far longer than the shortest path. Adding a constant to every edge leaves the MST alone but changes shortest paths.

You've built the MST of a road network. Your manager asks you to use it to answer "fastest route from depot X to customer Y". What do you say?

Right. In the hub-and-ring example, H to R6 is 15 directly but 35 through the MST, because the MST dropped the direct road to save on total length. Prim's start vertex doesn't help: every start gives the same MST (when weights are distinct). For routes, you want a shortest-path tree from X.

Look at the hub-and-ring numbers: the MST keeps only one of H's six roads, because the ring roads are cheaper in total. So the MST route from H to R6 goes all the way round: 35, against 15 direct. "Cheapest network" and "cheapest trip" are different goals. Starting Prim at X doesn't fix it either: Prim grows the same MST from any start (with distinct weights); it just builds it in a different order. Dijkstra from X is the right tool.

9Only the order of the weights matters

Look back at Kruskal. The weights are used for exactly one thing: sorting. The algorithm never adds them up or subtracts them. So any change to the weights that keeps their order keeps the same MST: add 100 to all of them, double them, square them or take their logarithm (both only if they're all positive). Three consequences interviewers like:

Negative weights are fine

Dijkstra breaks on negative edges, because it assumes a path can only get longer as it grows. Kruskal and Prim make no such assumption. An edge of cost −5 just sorts first. Kruskal and Prim work on any real weights.

Distinct weights mean exactly one MST

If no two edges cost the same, the MST is unique. Why: suppose there were two different MSTs, T1 and T2. Take the cheapest edge e that's in one of them but not the other; say it's in T1. Add e to T2: that makes a loop, and the loop has some edge f that isn't in T1 (otherwise T1 would contain the whole loop). f is in T2 but not T1, so it's one of the edges that differ, and e was the cheapest of those, so f costs more than e (no ties). Swap f for e in T2 and you get a cheaper tree, which is impossible. So T1 = T2.

With ties there can be several MSTs, all with the same total. A square with four sides of cost 1 has four MSTs: drop any one side. They also all have the same list of weights, sorted.

Flip the order: maximum spanning trees and widest paths

Sort from most expensive to cheapest (or negate every weight) and Kruskal builds a maximum spanning tree. That sounds pointless until you meet bandwidth. A path's bandwidth is set by its narrowest link, like a water pipe that's only as wide as its thinnest section. The widest path from s to t is the one whose narrowest link is as wide as possible. The path between s and t inside the maximum spanning tree is always a widest path. That's the cycle property with "narrowest" in place of "most expensive".

You can see why by running Kruskal from the widest link down and watching s and t. Say they first land in the same group when a link of width c is added. Every link taken so far is at least c wide, so the path between them in the tree has bandwidth at least c. Could some other path do better, with every link wider than c? All those links came earlier in the list, so they would already have joined s and t before c came up. They didn't, so no path beats c. With numbers: if s and t join at width 40, every link of width 41 or more together still left them apart, so no path made only of such links exists.

The same holds the other way round for an MST: the path between two towns inside the MST makes its most expensive edge as cheap as possible (a minimax path). Say each road's weight is its steepest hill, and a heavy truck wants the route whose steepest hill is as gentle as possible. The route through the MST is one. Exercise 8 has you find the widest path by running Kruskal from the widest edge down and stopping the moment s and t join.

MST algorithms only compare weights: any order-keeping change leaves the MST the same, and negative weights are fine. Distinct weights give exactly one MST. Reverse the order to get the maximum spanning tree; the paths in it are widest (bottleneck) paths.

A network's link costs are latencies in milliseconds. A teammate converts them all to seconds (divides by 1,000) and then adds a fixed 2 ms of switch delay to each. Does the MST change?

Right. Divide by a positive number, add the same constant: if link X was cheaper than link Y before, it still is. Kruskal would sort them identically and make the same choices. (If the costs were stored as rounded integers, rounding could create ties; with floats it doesn't matter.) Shortest paths, on the other hand, would change from the added constant.

Ask what Kruskal does with weights: it sorts them, and that's all. Dividing by 1,000 keeps every comparison the same: 3 < 7 and 0.003 < 0.007. Adding 2 to every link also keeps them: 3 + 2 < 7 + 2. Same sorted order, same decisions, same MST. Another way to see it: every spanning tree has n − 1 links, so adding 2 to each link adds 2(n − 1) to every tree, and the cheapest tree stays the cheapest.

Go deeper: negative weights, forests and the second-best tree
  • "Cheapest connected set of links" isn't always a tree. If some links have negative cost (someone pays you to dig them), the cheapest connected set takes the MST and then also every remaining negative link. The MST is the cheapest tree, which is what "spanning tree" asks for.
  • Disconnected graphs. Kruskal run to the end gives a minimum spanning forest: one MST per connected piece. Prim only covers the piece containing its start, so you'd restart it from each unvisited vertex.
  • Adding one edge to an existing MST. The new edge (u, v, w) closes one loop with the tree path from u to v. If w is less than the most expensive edge on that path, swap them; otherwise ignore it. O(V) per new edge, no full rebuild.
  • Second-best MST. Among the cheapest spanning trees that differ from the MST, there is always one that is just one swap away: add some non-tree edge, drop the most expensive edge on its loop. Try all non-tree edges, using the "most expensive edge on the tree path" for each.
  • Directed graphs are a different problem: the cheapest set of arrows from a root reaching every vertex is a minimum arborescence. Kruskal and Prim give wrong answers there; the Chu–Liu/Edmonds algorithm solves it in O(EV).

10Where MSTs show up

Network design, and its limits

Cables, pipes, power lines, the seven-town fiber problem. Two warnings that show senior judgment. First, an MST has no backup: cut any one link and the network splits in two. Real networks add extra links so that every point survives one failure; that's a harder problem, and the MST is the usual starting point. Second, if you're allowed to add new junction points (a splice box in a field), the cheapest network can be cheaper than the MST. That's the Steiner tree problem, which is NP-hard (no known fast exact algorithm); the MST is within 2× of it.

Clustering: cut the k − 1 most expensive links

You have 10,000 customers and the distance between similar ones, and you want 5 groups. Run Kruskal, but stop when 5 groups remain instead of 1. Equivalently: build the MST and delete its 4 most expensive edges. The result has the largest possible spacing: the closest two customers in different groups are as far apart as any 5-grouping allows. Why: call the next edge Kruskal would have taken e; it's the closest pair in different groups, so the spacing is cost(e). Any other 5-grouping has to split one of Kruskal's groups. Kruskal built that group from edges no more expensive than e, and at least one of those edges now joins two different groups. So the other grouping has a cross-group pair no farther apart than e: its spacing is no better. This is single-linkage clustering. Exercise 7 builds it.

The traveling salesman, within 2×

The traveling salesman problem (visit every city once and return, as cheaply as possible) is NP-hard. But when distances obey the triangle inequality (going straight is never longer than a detour through a third city, true for real distances) the MST gives a tour at most twice the best:

  1. MST ≤ best tour. Delete one road from the best tour and you have a path through every city: a spanning tree. The MST is no more expensive than that, so MST ≤ best tour.
  2. Walk around the MST. Go around the tree like tracing its outline, using every edge twice: that walk costs 2 × MST and visits every city.
  3. Take shortcuts. When the walk is about to revisit a city, skip straight to the next new one. By the triangle inequality, skipping never makes the trip longer.

So the tour costs ≤ 2 × MST ≤ 2 × best tour. With numbers: if the best tour is 100 km, the MST is at most 100 km, and the shortcut tour is at most 200 km. Christofides' algorithm (1976) improves this to 1.5× by adding a matching on the odd-degree vertices.

Smaller ones

  • Image segmentation: pixels are vertices, color difference is the weight; Kruskal-style merging with a stopping rule groups pixels into regions (the Felzenszwalb–Huttenlocher method).
  • Maze generation: randomized Kruskal on a grid of cells gives a maze with exactly one path between any two cells.
  • Libraries: NetworkX's minimum_spanning_tree (Kruskal by default; Prim and Borůvka on request) and SciPy's minimum_spanning_tree in scipy.sparse.csgraph.
MSTs show up in network design (but they have no redundancy), in clustering (cut the k − 1 heaviest MST edges for the best spacing), and as a 2× approximation for the metric traveling salesman (MST ≤ best tour, walk the tree twice, shortcut).

You've built an MST over 1,000 photos, with edge weights = how different two photos look. You want 3 groups of similar photos. What do you do?

Right. A tree splits into k pieces when you delete k − 1 of its edges, so 3 groups means 2 deletions. Deleting the most expensive ones cuts where photos are least alike, which is the same as stopping Kruskal when 3 groups remain. Deleting edges of the whole graph wouldn't split anything: there are other paths around them.

Two facts. One: deleting one edge from a tree splits it into two pieces; deleting k − 1 edges gives k pieces. So 3 groups means deleting 2 edges, not 3. Two: you want to cut between photos that look most different, so delete the most expensive MST edges, the "weakest links". Deleting the cheapest would split near-identical photos apart. And deleting edges of the full graph usually splits nothing, since other paths go around them; only tree edges are bridges.

11What to say in the interview

When a problem says "connect all", "minimum cost to link", "cheapest network", or "group into k clusters", a strong answer sounds like this:

  1. Name it: "This is a minimum spanning tree: n points, weighted links, connect everything at the lowest total. The answer is a tree with n − 1 edges."
  2. Say why greedy is safe: "By the cut property, the cheapest edge across any cut is in some MST. Kruskal uses the cut around one endpoint's group; Prim uses the cut around the tree it's growing."
  3. Pick by shape: "The edges come as a list and the graph is sparse, so Kruskal: sort, then union-find, O(E log E)." Or: "Every pair of points is an edge, so array Prim: O(V²) time, O(V) memory, no edge list."
  4. Cover the edges: "If the graph is disconnected, I get fewer than n − 1 edges and report it. Ties are fine; the total is the same. Negative weights are fine too."
  5. Check it's not shortest paths: if they say "from s" or "route", it's Dijkstra, not an MST.
Go deeper: follow-up questions interviewers like
  • "Prove Kruskal is correct." Give the swap argument from section 3 with the cut "u's group | rest" from section 5. Two minutes, and it's the question that separates people who've memorized Kruskal from people who understand it.
  • "Can you beat O(E log E)?" If weights are small integers, sort them with counting or radix sort and Kruskal becomes O(E · α(V)). In theory, a randomized algorithm (Karger, Klein and Tarjan, 1995) runs in expected O(E), and Chazelle's (2000) in O(E · α(E, V)) deterministically.
  • "Points on a plane, millions of them." Even O(V²) is too slow. The Euclidean MST only uses edges of the Delaunay triangulation, which has at most 3V edges and can be built in O(V log V). Run Kruskal on those: O(V log V) total.
  • "The graph doesn't fit on one machine." Borůvka's rounds parallelize: every group picks its cheapest outgoing edge independently, groups merge, repeat; about log V rounds. Many distributed graph systems implement MST this way.
  • "Edge weights change over time." Lowering a non-tree edge or raising a tree edge can change the tree; the loop and cut properties tell you which single swap to check. Fully dynamic MST structures exist but are rarely asked about.

✓What to remember

  1. The cheapest way to connect n points is a tree: no loops, exactly n − 1 edges. That's the minimum spanning tree.
  2. Cut property: the cheapest edge across any cut is in an MST (in every MST if it's strictly cheapest). Proof by swapping it in for the other crossing edge on the loop it makes.
  3. Cycle property: the strictly most expensive edge on any loop is in no MST.
  4. Kruskal: sort edges, take each one joining two different groups (union-find), skip the rest. O(E log E).
  5. Prim: grow one tree from a start; a min-heap of edges leaving the tree; skip stale entries. O(E log V). Same loop as Dijkstra with key w instead of dist[u] + w.
  6. Dense or all-pairs graphs: array Prim, O(V²) time and O(V) memory, no heap.
  7. An MST minimizes the total, not the route from any one point. Don't use it for shortest paths.
  8. Only the order of weights matters; negative weights are fine; distinct weights mean one MST. Reverse the order for a maximum spanning tree, which holds the widest paths.
  9. Uses: network design (no redundancy!), k-clustering by cutting the k − 1 heaviest MST edges, and a 2× tour for the metric traveling salesman.

Warm-up · pen and paper

1. Trace both by hand

Use the hub-and-ring graph from section 8: hub H; ring R1…R6; spokes H–R1 10, H–R2 11, H–R3 12, H–R4 13, H–R5 14, H–R6 15; ring edges R1–R2 3, R2–R3 4, R3–R4 5, R4–R5 6, R5–R6 7, R6–R1 8. (a) Run Kruskal: list each edge in sorted order and write "take" or "skip (loop through …)". Where do you stop? (b) Run lazy Prim from R4: write the heap after every step, and mark each stale pop. (c) Do both give the same tree? Why must they?

Answers

(a) Take R1–R2 3, R2–R3 4, R3–R4 5, R4–R5 6, R5–R6 7. Skip R6–R1 8 (loop R6–R1–R2–…–R6, it's the most expensive on it). Take H–R1 10. Six edges taken, so stop: the other five spokes are never looked at. Total 35. (b) From R4 the tree grows R4 → R3 (5) → R2 (4) → R1 (3) → R5 (6) → R6 (7), and then H by H–R1 (10). The entry R1→R6 8 is popped after R6 has joined: stale. All seven are in once H joins; if you keep popping, the five spokes left in the heap (11 to 15) are all stale too. (c) Same tree, total 35. All weights are distinct, so the MST is unique, and both algorithms build an MST.

Warm-up · pen and paper

2. True or false, with a reason

(a) The cheapest edge in the whole graph is always in some MST. (b) If every town takes its own cheapest edge, the result is a spanning tree. (c) Squaring every (positive) weight can change the MST. (d) If you multiply every weight by −1, Kruskal finds the maximum spanning tree. (e) Prim's result depends on the start vertex.

Answers

(a) True: use the cut around one of its endpoints; it's the cheapest edge crossing that cut (it's the cheapest edge of all). (b) False. Each of those edges is in the MST (cut around that town), but they can leave gaps: in a square A–B 1, C–D 2, B–C 5, D–A 6, A and B pick each other and C and D pick each other, giving two separate pieces. Borůvka repeats this step on the pieces until one is left. (c) False: squaring positive numbers keeps their order. (d) True: the most expensive edge becomes the cheapest. (e) The edges can't depend on it when weights are distinct (the MST is unique); with ties, different starts can return different MSTs with the same total. The order edges are added always depends on the start.

Warm-up · pen and paper

3. Break the shortcuts

Draw 4 towns and 5 edges where "take the 3 cheapest edges" fails. Then draw a graph where "run Dijkstra from A and take its tree" gives a tree more than twice as expensive as the MST. (Hint: section 8.) Finally, say in two sentences why Kruskal's skip rule fixes the first failure.

Core · code

4. kruskal_mst(n, edges)

Sort, then union-find (write a small one inside the file, with union by size and path compression). Return the chosen edge tuples; raise ValueError if the graph is disconnected. The tests include parallel edges, self-loops, negative weights, ties and a 100,000-town graph with about 300,000 edges, built so that its MST is known in advance. They also check that you didn't sort the caller's list in place, and they include a star-shaped graph that makes a union-find without either trick walk a chain of 50,000.

Core · code

5. prim_mst(n, adj) with a heap

Lazy Prim from town 0; return the total and a parent list. The adjacency list you get counts every entry you read, with a budget of about two reads per entry. Rescanning the tree's edges at every step blows it at once, and copying the lists first and then rescanning the copy runs into the time cap on a 60,000-town graph. So does array Prim from section 7: on a sparse graph its V² = 3.6 billion scan steps take minutes, against about a second for the heap.

Core · code

6. prim_dense(n, dist) with an array

A complete graph given only as a distance function. Keep best[] and parent[], scan for the minimum each round. The test allows n² calls to dist (you need about n²/2) and measures peak memory with tracemalloc: an edge list, a heap of all pairs or a distance matrix for 600 points is dozens of times over the limit.

Core · code

7. k_clusters(n, edges, k)

Stop Kruskal at k groups; return the spacing (the next edge Kruskal would have taken) and a label per point. Checked against a brute force over every grouping on small inputs, and on 100,000 points in 40 planted clusters under a time cap.

Core · code

8. widest_path(n, edges, s, t)

The largest bandwidth from s to t, where a path's bandwidth is its narrowest link. Run Kruskal from the widest link down and stop when s and t join (a max-min version of Dijkstra also works; say why). The big test is built so that "try each bandwidth from the top with a BFS" does about 180,000 BFS runs.

Stretch · design

9. Fiber with a backup

The provider from section 1 now has 200 towns and wants every town to stay connected if any one trench is cut. Why is the MST not enough? Sketch a plan: start from the MST, then add the cheapest extra trenches that put every tree edge on a loop. How would you find, for each tree edge, the cheapest non-tree edge whose loop covers it? What does your plan cost in time, and is it optimal? (It isn't, in general: say why.)

Stretch · explain

10. Say it out loud

Set a 3-minute timer. To an imaginary interviewer: state the cut property, prove it with the swap argument, and use it to explain why Kruskal's "take" and Prim's "take" are both safe. Then say, with numbers, when you'd use array Prim instead. Did you mention the second crossing edge on the loop, and why removing it keeps the tree connected?
