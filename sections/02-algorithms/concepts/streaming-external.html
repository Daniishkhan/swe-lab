Chapter 2 · Part 13

Data bigger than memory

P2 Streaming and external algorithms: reservoir sampling, external merge sortabout 50 minutes11 quick checks · 8 exercises

Every algorithm so far assumed the data sits in memory, where any item is one fast step away. Real data often doesn't fit. A day of logs is a terabyte; a laptop has 16 GB. This chapter is about what changes when the data is too big to hold: you get to look at it once, in order, or you read it from a disk that hates jumping around. Interviewers like these questions because they test whether you can reason from physical limits instead of from habits.

By the end you'll be able to

  1. Explain why a disk punishes random access, with the numbers, and why "count the passes" is the right cost model.
  2. Pick k random lines fairly from a stream of unknown length, and prove it's fair with small numbers.
  3. Sort a terabyte with 16 GB of RAM: make runs, merge them with a heap, and work out the passes and the hours.
  4. Compute a mean and variance in one pass without the floating-point trap.
  5. Find the heavy hitters of a stream with k counters, and say exactly what Misra-Gries guarantees.
  6. Know which one-pass tool answers which question, including the sketches from chapter 1.

How to read this: top to bottom. It builds on merge sort (section 3 there) and on the heap's k-way merge. Answer each quick check before reading on; a wrong answer gets you a second explanation. "Go deeper" boxes are optional on a first read.

1The problem: a terabyte and a laptop

Your service writes a log: one line per request, about 100 bytes a line. Yesterday's file is 1 TB, which is about 10 billion lines. You have a machine with 16 GB of RAM. Your lead asks for three things:

  1. "Pick 100 random lines, fairly, so we can eyeball them." And later: "Do the same on the live stream, which never ends."
  2. "Sort the file by user id, so we can join it with the users table."
  3. "Which IPs send more than 1% of the traffic? And what's the mean and spread of the latency?"

In memory, each of these is one line of Python: random.sample(lines, 100), sorted(lines), Counter(ips). Here, every one of them breaks. 16 GB is 1.6% of the file. You can't hold the lines, you can't hold an index of where they are, and for the live stream you don't even know how many lines there will be.

What you can do is read the data front to back, keeping a small notebook as you go. Some questions survive that. "How many lines?" needs one counter. "What's the biggest latency?" needs one number. Others, like "sort it", clearly need more. This chapter is about pushing the "one pass, small notebook" idea as far as it goes, and about the cleanest way to cheat when it doesn't go far enough.

You can read the 1 TB file once, front to back, and keep a few kilobytes of notes. Which question can you answer exactly?

Right. One counter, plus one each time you see "ERROR". The other two need to remember far more: the exact median depends on where every value sits relative to every other, and the exact top 10 IPs can change because of an IP you saw once at the start and then again at the very end. For those, this chapter (and chapter 1's sketches) give approximate answers with guarantees.

Ask, for each one: "what must my notebook hold so that the next line can't surprise me?" For a count of ERROR lines, one number: add one or don't. For the exact median, a line at the very end can shift the median, and to know where it lands you need every value seen so far. For the exact top IPs, an IP seen once early might show up a million times later, so you'd have to remember every IP. Only the count fits in a few kilobytes.

2The rules of the game: one pass, and long straight reads

Before any algorithm, get the physical facts straight. They decide everything else.

A hard disk is a record player. The data sits on a spinning platter, and a mechanical arm moves to the right track. Moving the arm and waiting for the platter to come around takes about 10 milliseconds. Once the arm is in place, data streams off at about 200 MB per second. So reading the next byte is nearly free, but jumping somewhere else costs 10 ms, which is long enough to have read 2 MB.

An SSD has no arm, but it still prefers straight lines. It reads in pages of about 4 KB or more, so fetching one 100-byte line costs a whole page, and each separate request has a fixed delay (tens of microseconds, up to about a hundred). Reading straight through lets it fetch big blocks ahead of time. The storage chapter has more on pages.

Put real numbers on our 1 TB file, reading one thing at a time:

RAMNVMe SSDSATA SSDHard disk
Read the whole 1 TB front to backunder 2 min (10+ GB/s)about 6 min (3 GB/s)about 33 min (500 MB/s)about 1.4 hours (200 MB/s)
One random read (wait time)about 100 nsabout 50 µsabout 100 µsabout 10 ms
Read all 10 billion lines in random orderabout 17 minabout 6 daysabout 12 daysabout 3 years

Same bytes, same disk: about an hour and a half in order, three years out of order. That gap is the whole chapter. It gives us two rules:

  1. Read in long straight lines. Sequential access is hundreds to tens of thousands of times cheaper than random access on anything but RAM: per line, about 500× on a SATA SSD and 20,000× on a hard disk.
  2. Count passes. When every pass is a straight read of the whole file, the cost of an algorithm is roughly "number of passes × time for one pass". On a hard disk, comparisons in memory are almost free next to that, so a 3-pass algorithm costs about three times a 1-pass one, no matter how clever its inner loop is. (On a fast SSD the CPU starts to catch up; section 7 puts a number on it.)
For data bigger than memory, the cost model changes. Stop counting comparisons and start counting passes over the data and random jumps (seeks). A good external algorithm makes few passes and reads each one in long straight lines.

A teammate's plan for sorting the file: sort only the small (user id, position in file) pairs, then build the output by jumping to each line's position in sorted order and copying it. On a hard disk, how long does that copying step take?

Right. In sorted order, consecutive lines sit at unrelated places in the file, so every one of the 10 billion copies starts with a seek: 10¹⁰ × 10 ms ≈ 10⁸ s ≈ 3 years. It reads the same bytes as one pass, but in the worst possible order. (The pairs aren't small either: 16 bytes × 10 billion is 160 GB.) The fix is to only ever read in long straight lines, which is what external merge sort does.

Count the bytes and the jumps separately. The bytes are 1 TB, which straight through would take 1.4 hours. But the plan visits lines in user-id order, and neighbors in that order live far apart in the file, so the disk arm moves before every line: 10 billion moves at about 10 ms each is 10⁸ seconds, about 3 years. The pairs don't save you either: 10 billion pairs of 16 bytes is 160 GB, ten times the RAM. Same bytes, different order, a different universe.

3One fair pick from a stream

Start with the smallest version of request 1: pick one line, so that every line has the same chance. "Fair" means exactly that: if there are n lines, each one ends up as the pick with probability 1/n.

Idea 1: count first, then pick

Read the file once to count the lines, n. Pick a random number r between 1 and n. Read again and stop at line r. It works for a file, at the price of two passes (over an hour on a SATA SSD). But for the live stream it's impossible: there is no "end" to count to, and your lead wants a sample at any moment.

Idea 2: flip a coin for each new line

Hold one line. For each new line, flip a coin: heads, the new line replaces the one you hold. Now look at the chances. The last line is held with probability 1/2. The one before it had to win its flip and then survive one more flip: 1/4. The first line has to survive every flip after it: (1/2)n−1. With a million lines, the first line's chance has 300,000 zeros after the decimal point. That isn't a fair sample; it's "one of the last few lines".

The flaw is clear: a fixed coin is far too eager late in the stream. Line 1,000,000 should replace the held line only rarely, because it has to compete with a million others.

Idea 3: the coin gets lazier as the stream grows

Picture one chair. The first person to arrive sits in it. Person number i, when they arrive, rolls a fair die with i sides. If it shows 1, they take the chair and the sitter leaves. So person 2 takes the chair with chance 1/2, person 3 with chance 1/3, person 100 with chance 1/100.

Is it fair? Check with 4 people, by following each one to the end:

Every row comes out to 1/4. Look at why: each fraction's top cancels the previous fraction's bottom. 1/2 × 2/3 × 3/4: the 2s cancel, the 3s cancel, and only 1/4 is left. In general, person j holds the chair at the end with chance (1/j) × (j/(j+1)) × ((j+1)/(j+2)) × … × ((n−1)/n) = 1/n, for every j. And because the rule never needed to know n, the pick is fair at every moment: stop the stream after 7 lines and each of the 7 has chance 1/7.

Keep line i with probability 1/i. Each survival chance cancels the one before it, so after n lines, every line is held with probability exactly 1/n, without ever knowing n in advance.

With the "keep line i with probability 1/i" rule, a stream has 5 lines. What's the chance that line 1 is the one you hold at the end?

Right. It survives line 2 with chance 1/2, line 3 with 2/3, line 4 with 3/4, line 5 with 4/5. Multiply: 1/2 × 2/3 × 3/4 × 4/5 = 1/5. The tops and bottoms cancel in a chain. That's the same as every other line, which is the whole point.

1/16 is what the coin-flip rule (idea 2) gives: survive four 50/50 flips. Here the later lines are lazier. Line 1 is knocked out by line 2 with chance 1/2, by line 3 with only 1/3, by line 4 with 1/4, by line 5 with 1/5. So it survives with 1/2 × 2/3 × 3/4 × 4/5. Cancel the matching numbers top and bottom: 1/5. Every line ends up with 1/5.

4Reservoir sampling: k fair picks

Now 100 lines, not one. Call the k slots you hold the reservoir. "Fair" now means every set of k lines is equally likely, which in particular means every line ends up in the reservoir with probability k/n.

The rule grows out of the one-chair version:

  1. The first k lines go straight into the reservoir.
  2. Line i (counting from 1, with i > k) is kept with probability k/i.
  3. If it's kept, it replaces one of the k reservoir lines, chosen uniformly at random.

This is reservoir sampling (in the literature, "Algorithm R"). It reads the stream once, holds only k lines, and does O(1) work per line.

Reservoir sampling with k = 3 slots on a stream of 12 lines. Yellow is the line arriving now; blue is the slot it just took. Watch the "chance each line is held" row: after every step, every line seen so far has the same chance, k/i. Press "New run" for different random draws.

Why it's fair: the numbers first

Take k = 2 and a stream A, B, C, D. After two lines the reservoir is {A, B} for sure. Follow A:

  • C arrives. C is kept with chance 2/3. If kept, it lands on A's slot with chance 1/2. So A is kicked out with chance 2/3 × 1/2 = 1/3, and survives with 2/3. C itself is in with 2/3. After 3 lines: every line, 2/3. That's k/i = 2/3.
  • D arrives. D is kept with chance 2/4. If kept, it hits A's slot with chance 1/2: A is kicked out with chance 1/4, so A survives with 3/4. A was in with 2/3, so now: 2/3 × 3/4 = 1/2. D is in with 2/4 = 1/2. After 4 lines: every line, 1/2. That's k/i = 2/4.

Then the general argument

Suppose that after i lines, each of them is in the reservoir with chance k/i (true at i = k, where all k are in). Line i + 1 arrives:

  • It goes in with chance k/(i+1). That's the rule.
  • An old line that's in the reservoir gets kicked out only if the newcomer is kept and picks its slot: k/(i+1) × 1/k = 1/(i+1). So it survives with i/(i+1), and its total chance becomes k/i × i/(i+1) = k/(i+1).

Everyone, old and new, is at k/(i+1). The step repeats forever, so the claim holds for every length. (This "if it's true at i, it's true at i + 1" argument is called induction.) The same bookkeeping shows the stronger fact: every set of k lines is equally likely, not just every single line.

There's no code here on purpose: the three-step rule above is the whole algorithm, and writing it is exercise 4. The traps are all in the details: counting i from 1, not 0; picking the slot at random, not always the same one.

Reservoir sampling: keep the first k; keep line i with probability k/i, replacing a random slot. An old line is kicked out with chance exactly 1/(i+1) per step, which keeps every line at k/i. One pass, O(k) memory, n unknown.

k = 100, and the stream ends after 10,000 lines. What's the chance that line number 1,000 is in the final sample?

Right: every line ends with k/n = 100/10,000 = 1%. Line 1,000 entered with 10%, and then had to survive 9,000 later lines, each one kicking it out with chance 1/(i+1). Those survival chances multiply to 1,000/10,000, and 10% × 1/10 = 1%.

10% is its chance of getting in when it arrives. But 9,000 more lines come after it, and each one may take its slot: line i + 1 kicks out any particular resident with chance 1/(i+1). Surviving all of them is 1,000/1,001 × 1,001/1,002 × … × 9,999/10,000 = 1,000/10,000. So 10% × 1/10 = 1%, the same k/n as every other line. And it doesn't depend on lines 1 to 999: whatever they did, each resident faces the same odds.

The off-by-one bug pushes the first four lines down to about 16%; "always replace slot 1" keeps lines 2 to 4 every single time. This is exactly what exercise 4's tests measure.
Go deeper: skipping ahead (Algorithm L), and samples you can merge

Fewer random numbers. Algorithm R draws one random number per line. When n is billions and k is 100, almost every draw says "skip". Algorithm L instead draws how many lines to skip before the next replacement, so it needs only about k·log(n/k) random numbers. The answer has the same distribution; it only matters when random numbers are expensive or you can skip lines without reading them.

Merging across machines. If 10 servers each keep a reservoir of 100, you can't just pool the 1,000 lines and take 100: a quiet server's lines would be over-represented. Either weight each server's sample by how many lines it saw, or use the random-tag trick in the next section, which merges trivially.

5Random tags: samples you can merge, and weights

Here's a second way to see the same thing. Give every line a random tag, a number drawn uniformly between 0 and 1, the moment it arrives. Keep the k lines with the smallest tags, using a heap of size k (the top-k pattern from the heaps chapter). Since the tags are random and independent of the lines, every set of k lines is equally likely to hold the k smallest. That's a fair sample too, at O(log k) per line instead of O(1).

Why bother? Because tags merge. Ten servers each keep their 100 smallest-tagged lines; the 100 smallest tags overall must be among those 1,000, so take the 100 smallest of them. Done, no weighting needed.

Weighted sampling

Sometimes lines aren't equal. You want to sample requests in proportion to their bytes, or customers in proportion to spend: an item with weight 3 should be picked three times as often as one with weight 1. "Weighted sampling without replacement" means: pick one item with probability weight / total weight, remove it, pick the next from what's left, k times.

The tag trick handles this with one change. Think of a race: every item runs toward a finish line, and an item with weight w runs w times as fast, with some random luck. The first k to finish are the sample. A fast runner usually wins but not always, and the chance of finishing first turns out to be exactly w divided by the total weight.

The formula for that race: draw u uniform in (0, 1) and use the tag u1/w, keeping the k largest tags. (This is the Efraimidis-Spirakis method, often called A-Res.) Check it with two items, weights 1 and 3, k = 1: the weight-3 item wins when u₂1/3 > u₁. Raising a number between 0 and 1 to the power 1/3 pushes it toward 1 (0.1251/3 = 0.5), so heavy items get big tags. For a fixed u₂, the weight-3 item wins when u₁ lands below u₂1/3, which happens with chance u₂1/3. Averaged over all u₂ between 0 and 1 (the average of up is 1/(p + 1), and here p = 1/3), that's 3/4, exactly 3/(1 + 3).

Give each item a random tag and keep the k best tags with a heap. Uniform tags give a fair sample that merges across machines. Tags u1/w (keep the largest) give weighted sampling without replacement, in one pass and O(k) memory.

A teammate writes the weighted tag as u × w instead of u1/w ("bigger weight, bigger tag, same thing"). With weights 1 and 3 and k = 1, how often does the weight-3 item win now?

Right. The weight-1 item wins only if u₁ > 3u₂, which needs u₂ < 1/3 and then u₁ above 3u₂. That region is a triangle with area 1/6. So the weight-3 item wins 5/6 ≈ 83% of the time instead of 75%. "Bigger weight, bigger tag" isn't enough; the tag's distribution has to be exactly right. Exercise 4's weighted test catches this.

The two items draw different u's, so 3u₂ isn't always bigger than u₁: if u₂ = 0.1 and u₁ = 0.5, then 0.3 < 0.5. Picture the unit square of (u₁, u₂). The weight-1 item wins where u₁ > 3u₂: a thin triangle along the bottom edge with corners (0, 0), (1, 0), (1, 1/3). Its area is 1/2 × 1 × 1/3 = 1/6. So the weight-3 item wins 5/6 of the time, more than the 3/4 it should. The tag u1/w gets exactly 3/4.

Go deeper: why u1/w is the race

Take logs: keeping the largest u1/w is the same as keeping the smallest −ln(u)/w. And −ln(u)/w is an exponential random variable with rate w: the waiting time for an event that happens at rate w. Among independent exponential clocks, the first to ring is clock i with probability wᵢ / Σw. Exponential clocks are also memoryless: once the first one rings, the others are as if they had just started. So the second to ring is a fresh weighted pick among the rest, and so on. That's exactly "pick by weight, remove, repeat".

6Sorting a terabyte: runs, then one big merge

Request 2: sort the 1 TB file by user id. No one-pass trick can do this: the line that sorts first might be the very last line in the file. So we'll make a few passes, and the rule from section 2 says to make each one a long straight read.

We already have the two pieces. Merge sort taught that merging sorted piles only ever looks at the front of each pile. And the heap chapter taught how to find the smallest of k fronts cheaply. External merge sort is those two ideas, sized for the disk.

Phase 1: make sorted runs

Say 10 GB of the 16 GB is free for sorting. Read the first 10 GB of the file into memory, sort it there with any fast in-memory sort, and write it back to disk as one sorted file. That file is called a run. Repeat for the next 10 GB, and so on. 1 TB / 10 GB = 100 runs. Every byte was read once and written once, all in long straight lines.

Phase 2: merge the runs

Now picture 100 checkout lines, each already in order. The next record of the whole sorted output is the smallest of the 100 front records. Keep those 100 fronts in a min-heap. Pop the smallest, write it to the output, and push the next record from the run it came from. That's the k-way merge. A heap of 100 is about 7 levels deep (log₂ 100 ≈ 6.6), and each pop-and-push walks those levels, so each record costs roughly 7 to 14 comparisons.

What does memory hold during the merge? Not 100 records: reading one record at a time from each run would be a seek per record. Each run gets a read buffer: a chunk of, say, 50 MB read from that run in one straight gulp. When a buffer runs dry, refill it with the next 50 MB of that run. 100 buffers × 50 MB = 5 GB, plus an output buffer. The disk sees 100 interleaved streams of big sequential reads, which it handles well.

External merge sort: phase 1 sorts memory-sized chunks into runs; phase 2 merges up to k runs at once with a heap of their fronts, each run read through its own big buffer. Every pass is sequential, and with 100 runs, one merge pass finishes the job.

During the 100-way merge, what has to be in memory?

Right. The heap only needs the current front of each run: 100 records of 100 bytes, about 10 KB. The buffers are what take the memory, and they're a speed choice, not a correctness one: they turn "one seek per record" into "one seek per 50 MB".

Think about what the merge actually looks at: only the front of each run, never anything deeper. So the heap holds 100 records, one per run. Holding all of run 1 would be 10 GB for nothing. But a heap on disk would mean a seek per comparison, years again. The memory goes to read buffers: each run is read in big sequential chunks, so the disk does a few long reads per run instead of one seek per record.

Go deeper: longer runs, stability, and where this runs in real systems
  • Replacement selection makes runs about twice the size of memory on random input. Keep a heap of M records; pop the smallest to the current run and read the next record in. If the new record is smaller than the one just written, it can't join this run, so mark it for the next run. On already-sorted input it makes one single run. Fewer runs can mean fewer passes.
  • Stability. Break heap ties by run number: run 1 holds earlier records than run 2, so equal keys come out in input order. heapq.merge does exactly this.
  • Loser trees replace the heap in serious implementations: about log₂ k comparisons per record instead of about 2·log₂ k (the heaps chapter has more).
  • Real systems. When a PostgreSQL ORDER BY doesn't fit in work_mem, EXPLAIN ANALYZE says "Sort Method: external merge". Hadoop's MapReduce sorts map output this way and merges at most mapreduce.task.io.sort.factor files at once (10 by default). GNU sort on a file bigger than its buffer writes temporary runs and merges them.

7Passes, buffers and the I/O bill

Why not always merge all the runs at once? Because memory is shared between the buffers. With M bytes of memory and buffers of B bytes, you can merge at most about M/B runs at once. That number is the fan-in, k.

If there are more runs than k, one merge pass can't finish. Merge them k at a time: R runs become R/k longer runs, then R/k², and so on until one is left. The number of merge passes is

P = ⌈logk R⌉, where R = ⌈N / M⌉

and every record is read and written once in phase 1 and once per merge pass: 1 + P times each. Here's the count, written out:

import math

def merge_passes(runs, fan_in):
    passes = 0
    while runs > 1:
        runs = math.ceil(runs / fan_in)   # merge fan_in runs into one, across the board
        passes += 1
    return passes

merge_passes(100, 10)     # 2: 100 runs -> 10 -> 1
merge_passes(100, 2)      # 7: two-way merging, the textbook merge sort shape
merge_passes(1000, 10)    # 3

Now the real bill for our 1 TB on a SATA SSD (500 MB/s). 100 runs, fan-in 100 or more, so P = 1. Phase 1 reads 1 TB and writes 1 TB; the merge pass does the same. 4 TB of traffic at 500 MB/s is about 8,000 seconds, a bit over 2 hours. On NVMe (about 3 GB/s) it's around 22 minutes. Two-way merging would need 7 merge passes, so 16 TB of traffic: four times longer.

At NVMe speed, the comparisons stop being free. Sorting 10 billion records takes about 10¹⁰ × log₂(10¹⁰) ≈ 3 × 10¹¹ comparisons in total (runs plus merge). At roughly 5 to 10 ns each, that's about 30 to 55 minutes on one core: as long as the disk time. So fast external sorts sort several runs in parallel on different cores, and read the next chunk while the CPU sorts the current one. On a hard disk, the I/O still dominates by far.

The trap: tiny buffers

Fewer passes is better, so why not set the fan-in huge, with tiny buffers, and always finish in one pass? Because every buffer refill is a seek. Take a small container with only 100 MB of memory sorting the same 1 TB on a hard disk. That's R = 10,000 runs.

  • One pass, fan-in 10,000: each buffer gets 10 KB. Merging reads 1 TB in 10 KB pieces: 10⁸ refills × 10 ms seek ≈ 10⁶ seconds, about 12 days.
  • Two passes, fan-in 100: each buffer gets 1 MB. Each pass is 10⁶ refills × (10 ms seek + 5 ms reading) ≈ 15,000 s, plus writing 1 TB in straight lines, about 5,000 s. Two passes ≈ 11 hours, plus about 3 hours for phase 1: about 14 hours.

More passes, 20 times faster. The disk wants big reads more than it wants few passes. The good fan-in is the one that keeps buffers big enough that seeking is a small part of each refill.

A rough I/O calculator for external merge sort. Fan-in is memory ÷ buffer (ignoring the one small output buffer). Time is the bytes moved at the disk's straight-line speed, plus one seek per buffer refill during the merges. Try: 1 TB, 100 MB, hard disk, then switch the buffer between 10 KB and 1 MB.

One more rule of thumb falls out of the formula. A single merge pass is enough when R ≤ k, that is N/M ≤ M/B, or N ≤ M²/B. With 10 GB of memory and 10 MB buffers, M²/B is 10 TB. That's why in practice almost every external sort is a two-pass sort: one pass to make runs, one pass to merge them.

Each record is read and written 1 + P times, with P = ⌈logk(N/M)⌉ merge passes and fan-in k ≈ M/B. Big memory makes few runs; big buffers keep reads sequential. With real numbers, P is almost always 1.

A sort makes 1,000 runs and can merge 10 at a time. How many times is each record read from disk, in total?

Right. Merging 10 at a time: 1,000 runs → 100 → 10 → 1, so 3 merge passes. Plus the read in phase 1 that made the runs: 4 reads per record, and 4 writes. If memory allowed a fan-in of 1,000, it would be 2.

Count the passes, and don't forget phase 1. Making the runs reads every record once. Then each merge pass reads everything once: 1,000 runs become 100, then 10, then 1. That's ⌈log₁₀ 1,000⌉ = 3 merge passes. 1 + 3 = 4 reads per record. 10 would be the fan-in, not the number of passes.

Why not set the fan-in to 10,000 so that any file sorts in one merge pass?

Right. A heap of 10,000 costs about 2 × 13 comparisons per record, which is nothing. The cost is the disk: with 100 MB of memory, 10,000 buffers are 10 KB each, and on a hard disk each 10 KB refill is a 10 ms seek. That turns a 14-hour sort into a 12-day one.

The heap is fine (log₂ 10,000 ≈ 13 levels) and the merge is correct for any fan-in. The problem is memory: 10,000 runs each need their own read buffer, and they all share the same memory. 100 MB ÷ 10,000 = 10 KB each. Every time a buffer runs dry the disk seeks to that run, so you pay a 10 ms seek per 10 KB read: about 1 MB/s instead of 200 MB/s. Two passes with 1 MB buffers are far faster.

Go deeper: the other external tool, hash partitioning

Many "too big" questions don't need order at all: "find duplicate lines", "count requests per user", "join two huge files on user id". For those, partition by hash: read the file once and append each line to one of 200 bucket files chosen by hash(key) mod 200. Equal keys always land in the same bucket, and each bucket is about 5 GB, so it fits in memory. Then handle each bucket with an ordinary hash map. Two passes, like the sort, with no merge and no comparisons. That's the grace hash join in databases and the shuffle in MapReduce and Spark.

The catch is skew. If one key is 10% of the data, its bucket is 100 GB and doesn't fit. Sorting handles skew gracefully, because a run is always exactly memory-sized. Partitioning needs a fix for the heavy keys, such as spotting them first with the heavy-hitters method of section 9.

8One-pass statistics: mean and variance

Request 3, second half: the mean and spread of latency over 10 billion lines, in one pass. The mean needs two numbers: a running sum and a count. The variance is the average squared distance from the mean, and its square root, the standard deviation, is the "spread".

The textbook shortcut is variance = (average of x²) − (average of x)². Keep three running numbers (count, sum, sum of squares) and you're done. Try it on four latencies in nanoseconds, all close to one second: 1,000,000,004, 1,000,000,007, 1,000,000,013 and 1,000,000,016. The mean is 1,000,000,010, the distances are −6, −3, 3, 6, so the true variance is (36 + 9 + 9 + 36)/4 = 22.5. Python's floats give:

xs = [1e9 + 4, 1e9 + 7, 1e9 + 13, 1e9 + 16]
n, s, sq = len(xs), sum(xs), sum(x * x for x in xs)
sq / n - (s / n) ** 2          # 0.0   (should be 22.5)

Each x² is about 10¹⁸, and a 64-bit float only keeps about 16 significant digits. Near 10¹⁸, neighboring floats are 128 apart, so the "+36" and "+9" parts are rounded away before the subtraction. Subtracting two huge, nearly equal numbers leaves only the rounding noise. This is called catastrophic cancellation, and it can even give a negative variance.

The fix is to never form the huge numbers. Track the mean itself, and the running sum of squared distances from it (call it M2), and nudge both as each value arrives. This is Welford's method:

n, mean, m2 = 0, 0.0, 0.0
for x in xs:
    n += 1
    d = x - mean            # how far the new value is from the old mean
    mean += d / n           # move the mean a 1/n share of the way toward x
    m2 += d * (x - mean)    # old distance × new distance: adds this value's share
variance = m2 / n           # 22.5  (use m2 / (n - 1) for the sample variance)

Every number it handles is a distance like 6 or 36, never 10¹⁸, so nothing important gets rounded away. It's still one pass and O(1) memory.

For a one-pass mean and variance, use Welford: keep n, the running mean and M2 (the sum of squared distances from the mean). "Sum of squares minus square of sum" cancels catastrophically on big values with small spread.

The sum-of-squares formula returns 0.0 for the four latencies above. What went wrong?

Right. A float holds 10⁹ exactly, so the inputs are fine. Their squares need about 19 digits and a float keeps about 16, so the low digits, where all the spread lives, are lost. The formula is correct math; it's only bad arithmetic in floating point. Welford avoids squaring anything big.

The formula is correct algebra, and 10⁹ fits in a float with room to spare. The trouble is what happens next: squaring makes numbers around 10¹⁸, where a float can only land on multiples of 128. The four squares sum to about 4 × 10¹⁸, and the spread adds just 90 to that. Rounding swallows the 90 and the subtraction gives 0. Work with distances from the mean instead, which is what Welford does.

Go deeper: merging statistics from many machines

Welford's state (n, mean, M2) merges. For two parts A and B with δ = mean_B − mean_A: n = n_A + n_B, mean = mean_A + δ·n_B/n, and M2 = M2_A + M2_B + δ²·n_A·n_B/n (Chan's formula). So each server summarizes its own logs, and a coordinator combines the summaries. Medians and percentiles do not merge exactly like this; for those, real systems use quantile sketches such as t-digest or KLL, which give approximate percentiles in small memory.

9Heavy hitters with k counters: Misra-Gries

Request 3, first half: which IPs send more than 1% of the requests? An exact count needs one counter per distinct IP, and a busy service sees hundreds of millions of them. But we don't need every count. We only need the few IPs that are heavy, and there can be at most 99 IPs with more than 1% each.

Picture an election hall with k tables. Each arriving voter is a supporter of some candidate (an IP).

  • If their candidate has a table, they stand at it. That table's count goes up by one.
  • If not, and a table is free, they claim it for their candidate.
  • If all k tables are taken by other candidates, the newcomer and one person from every table walk out together. Every table's count drops by one; tables that hit zero become free. The newcomer is not counted.

That's Misra-Gries. It keeps at most k (candidate, count) pairs. Here it is with k = 2 on the stream a b a c a b d a:

arrives   tables after                 what happened
  a       {a:1}                        free table
  b       {a:1, b:1}                   free table
  a       {a:2, b:1}                   a has a table
  c       {a:1}                        full: c, one a, one b walk out (b's table empties)
  a       {a:2}
  b       {a:2, b:1}                   free table
  d       {a:1}                        full: d, one a, one b walk out
  a       {a:2}                        end: n = 8. True counts: a 4, b 2, c 1, d 1

What it guarantees

Each walk-out removes k + 1 people from the hall: the newcomer plus one per table. Only n people ever arrive, so there can be at most n/(k+1) walk-outs. A candidate's counter only ever loses one per walk-out, so for every item x:

count(x) − n/(k+1) ≤ estimate(x) ≤ count(x)

Check it on the trace: n = 8, k = 2, so the counters can be at most 8/3 ≈ 2.7 too low. a's counter says 2, the truth is 4: off by 2, inside the bound. And the important consequence: any item with more than n/(k+1) occurrences still has a table at the end, since its counter can't have fallen to zero. For "more than 1%", k = 99 tables suffice.

The same counting argument settles the speed. A walk-out touches all k tables, so it costs O(k), but there are at most n/(k+1) of them, so all the walk-outs together cost at most about n steps. Every other arrival is one dictionary update. That's O(1) amortized per item (the complexity chapter explains "amortized"), even though a single unlucky item costs O(k).

The counters are low, and the list can include light items too: had the stream stopped after its 6th item, b would hold a table with 2 occurrences out of 6, not above 6/3. So the standard pattern is two passes: pass 1 runs Misra-Gries to get at most k candidates; pass 2 counts just those candidates exactly and keeps the ones really over the threshold. On a live stream with no second pass, you report the candidates with the error bound.

Misra-Gries keeps k counters; when a newcomer finds them all taken, every counter drops by one. Each drop cancels k + 1 occurrences, so there are at most n/(k+1) drops: every counter is at most n/(k+1) too low, and every item above n/(k+1) survives. A second pass gives exact counts.

Misra-Gries with k = 99 counters runs over 1 billion requests. One IP really sent 2% of them (20 million). What do you know at the end?

Right. n/(k+1) = 10⁹/100 = 10 million: the counter can be up to 10 million low, never high. 20 million − 10 million = 10 million > 0, so it can't have been dropped, whatever the order. A second pass would get the exact 20 million.

Use the walk-out argument. Every walk-out removes 100 people (the newcomer plus one from each of 99 tables), and only 10⁹ people arrive, so there are at most 10⁷ walk-outs. Each walk-out lowers this IP's counter by at most 1. So it ends at least 20M − 10M = 10M, which is above zero: it still has its table, no matter when its requests arrived. And the counter never goes up for anyone else's requests, so it's at most 20M. Exact only if no walk-outs touched it.

Explain it another way: k = 1 is the majority vote

With one counter, Misra-Gries is the Boyer-Moore majority vote: keep a candidate and a count; a match adds one, a mismatch subtracts one, and at zero the next item becomes the candidate. Think of it as pairing off opposing voters and sending each pair home. If one candidate has more than half the votes, they can't all be paired off, so that candidate is left standing. With k tables, groups of k + 1 different voters go home, and anyone with more than n/(k+1) votes is left standing.

Go deeper: merging summaries, and Space-Saving

Merging. Two Misra-Gries summaries from two servers combine: add the counters item by item, then, if more than k remain, subtract the (k+1)-th largest counter from all of them and drop the ones at zero or below. The merged summary keeps the same n/(k+1) guarantee for the combined stream, so 50 servers can each summarize their own traffic.

Space-Saving is the popular cousin. When the k counters are full, it evicts the smallest counter and gives the newcomer that count plus one. Its counts are never too low (the opposite of Misra-Gries) and in practice usually more accurate for the top items. The two are close relatives; know which direction each one errs in.

A dashboard must show, at any moment, how many different users visited today, across 50 web servers. Memory per server is tight. Which tool?

Right. "How many distinct" is exactly HyperLogLog's question: about 12 KB per server, about 1% error, and two HyperLogLogs merge by taking the larger value in each register, so the 50 servers combine into one count. A sample can't tell how many distinct users there are, and Misra-Gries only tracks the heavy ones.

Match the question to the tool. A reservoir sample tells you what a typical visit looks like, but scaling it up can't tell you how many different users exist: two visits by the same user and two by different users look alike in a sample. Misra-Gries finds the few users who visit a lot and ignores everyone else. Counting distinct items is HyperLogLog's job, and its sketches merge across servers.

11What to say in the interview

When the data doesn't fit, a strong answer sounds like this:

  1. Size it first: "1 TB of 100-byte lines is 10 billion lines; 16 GB is 1.6% of it. A sequential read is about 30 minutes on a SATA SSD; random access is hopeless. So I'll design for a small number of sequential passes."
  2. Ask whether one pass is enough: "Sampling, mean and variance, heavy hitters and distinct counts all fit in one pass with small memory. Sorting doesn't."
  3. Name the tool and its guarantee: "Reservoir sampling keeps line i with probability k/i, and every line ends at k/n." Or: "Misra-Gries with 99 counters keeps every IP over 1%, with counts at most 1% of n low; a second pass makes them exact."
  4. For sorting, do the arithmetic: "Runs of 10 GB give 100 runs. With 50 MB buffers I can merge all 100 at once with a heap, so it's two passes: each record read and written twice, about 4 TB of I/O."
  5. Mention the real-system detail: buffer size versus seeks, stable merges via run-number tie-breaks, or hash partitioning when order isn't needed.
Go deeper: follow-up questions interviewers like
  • "Sample from a stream across 10 machines." Random tags, keep the k smallest per machine, then the k smallest overall.
  • "Find duplicate lines in a 1 TB file." Hash-partition into buckets that fit in memory, then a set per bucket. Or external sort and compare neighbors. Say both, and say why partitioning can break on skew.
  • "Top 10 URLs by count, from a 1 TB log." Hash-partition by URL, count each bucket exactly, keep a size-10 heap across buckets. If approximate is fine: Misra-Gries or a Count-Min Sketch plus a heap, one pass.
  • "Merge sorted files on many machines." Range-partition: sample keys to choose split points, send each key range to one machine, sort locally, concatenate (the TeraSort shape).
  • "The stream is infinite; we only want the last hour." Reservoir sampling covers the whole stream so far. For a sliding window, keep per-minute summaries (counts, Welford states, sketches) and combine the last 60, or see the sliding-window counters in rate limiting.

✓What to remember

  1. When data is bigger than memory, count passes and seeks, not comparisons. Sequential reads are hundreds to tens of thousands of times cheaper than random ones.
  2. Reservoir sampling: keep the first k, then keep line i with probability k/i in a random slot. Every line ends with chance k/n. One pass, O(k) memory, n unknown.
  3. Random tags merge across machines; tags u1/w (keep the largest k) give weighted sampling without replacement.
  4. External merge sort: sort memory-sized runs, then k-way merge them with a heap of fronts and a big buffer per run. Stable if ties break by run number.
  5. Passes: P = ⌈logk(N/M)⌉ with fan-in k ≈ M/B. Each record is read and written 1 + P times. One merge pass works up to N ≈ M²/B, so most sorts are two-pass.
  6. Bigger buffers beat fewer passes when buffers get small enough that seeks dominate.
  7. Mean and variance in one pass: Welford, never "sum of squares minus square of sum".
  8. Misra-Gries with k counters: counts at most n/(k+1) low, never high; every item above n/(k+1) survives. A second pass gives exact counts.
  9. Distinct counts, frequencies and membership have sketches (chapter 1: HyperLogLog, Count-Min, Bloom). Say the error bound out loud.

Warm-up · pen and paper

1. Trace a reservoir

k = 2, stream A B C D E F. The random draws are: for C, slot-or-skip number 1 out of {0, 1, 2}; for D, 3 out of {0, 1, 2, 3}; for E, 0 out of {0, …, 4}; for F, 1 out of {0, …, 5}. A draw below k means "keep, and replace that slot". Write the reservoir after each line. Then compute the chance that A survives to the end, and check it equals 2/6.

Answer

Start [A, B]. C draws 1: keep, slot 1 → [A, C]. D draws 3: skip → [A, C]. E draws 0: keep, slot 0 → [E, C]. F draws 1: keep, slot 1 → [E, F]. A's chance to survive: C, D, E and F each knock it out with chance 1/3, 1/4, 1/5, 1/6, so it survives with 2/3 × 3/4 × 4/5 × 5/6 = 2/6.

Warm-up · pen and paper

2. The I/O bill

Sort 4 TB on a machine with 32 GB of RAM, of which you use 25 GB, and a SATA SSD (500 MB/s). How many runs? With 16 MB buffers, what's the fan-in, and how many merge passes? How much data moves in total, and about how long does it take? What if you only had 250 MB of memory and kept the 16 MB buffers?

Answer

4 TB / 25 GB = 160 runs. Fan-in ≈ 25 GB / 16 MB ≈ 1,560, so one merge pass. Each record is read twice and written twice: 16 TB at 500 MB/s ≈ 32,000 s ≈ 9 hours. With 250 MB: 16,000 runs. 250 MB ÷ 16 MB is about 15 buffers; keep one for the output and the fan-in is 14, so ⌈log₁₄ 16,000⌉ = 4 merge passes (14³ = 2,744 is too few, 14⁴ = 38,416 is enough). That's 1 + 4 = 5 reads and writes per record: 40 TB, about 22 hours.

Warm-up · pen and paper

3. Misra-Gries by hand

Run Misra-Gries with k = 2 on x y x z z x y z x w. Write the counters after each item. Which items does the guarantee say must still hold a counter at the end? Does holding a counter prove that an item is heavy? Check against the true counts.

Answer

x {x:1}; y {x:1, y:1}; x {x:2, y:1}; z full → {x:1}; z {x:1, z:1}; x {x:2, z:1}; y full → {x:1}; z {x:1, z:1}; x {x:2, z:1}; w full → {x:1}. n = 10, n/(k+1) ≈ 3.3. True counts: x 4, z 3, y 2, w 1. Only x is above 3.3, so only x must hold a counter: it does (1, which is 3 low, inside the 3.3 bound). And no, holding a counter proves nothing: with k = 2, the stream x x x x y ends with {x:4, y:1}, and y holds a counter with 1 occurrence out of 5, below 5/3. That's why the second pass exists.

Core · code

4. reservoir_sample(stream, k, rng) and the weighted version

Sections 3 to 5. The stream is an iterator you can read once. The tests run tens of thousands of seeded samples and compare how often every subset shows up with its exact probability, using a loose chi-square bound that the off-by-one and "always the same slot" bugs blow far past. They also measure peak memory with tracemalloc on a 200,000-item generator: keep it under 64 KB, so no list(stream). The weighted version must match "pick by weight, remove, repeat" exactly, which u * w tags don't.

Core · code

5. external_sort(disk, name, memory, fan_in)

Sections 6 and 7, on a pretend disk that counts every record read and written and raises the moment you break a rule: more than memory + 1 records alive, more than fan_in files open, or more than n × (1 + P) reads or writes. Use only the disk's public methods: a source check rejects reaching into its bookkeeping. Half-size runs or two-way merging run out of budget mid-sort. A test with fan_in = 256 counts key comparisons, so scanning all 256 fronts for the smallest (255 per record) fails where a heap (about 25) passes. The output must be stable.

Core · code

6. MisraGries(k) and heavy_hitters(make_stream, k)

Section 9. The tests check the guarantee, estimate ≤ true ≤ estimate + n/(k+1), after every single add, and never more than k counters. Peak memory is measured on 100,000 distinct values, so a full Counter fails. A k = 20,000 run catches an add that looks at every counter each time. heavy_hitters may read the stream twice and must return exactly the items above n/(k+1), with exact counts.
