Chapter 2 · Part 3

Binary search and "search on the answer"

P0 asked almost everywhereabout 55 minutes10 quick checks · 9 exercises

Binary search looks like the easiest algorithm there is: look in the middle, throw away half, repeat. It is also one of the easiest to get subtly wrong. Loops that never end, answers that are off by one, searches that find "a" copy when you needed the first one. Interviewers love it for exactly that reason.

This chapter teaches it as one idea instead of a pile of special cases: you are never really searching for a value; you are searching for the place where a yes/no answer flips. Once you see that, the off-by-one bugs have a clear cause, and you can binary search things that aren't arrays at all: the smallest ship that works, the slowest pace that finishes on time, a square root.

By the end you'll be able to

  1. Write a binary search that finds the first position where a yes/no question turns to yes, and say its invariant out loud.
  2. Explain why binary search loops hang or miss by one, and check any loop against three rules.
  3. Use lower bound and upper bound (bisect_left / bisect_right) to find the first and last copy, count copies, and answer range questions.
  4. Search a rotated sorted array in O(log n).
  5. Spot "search on the answer" problems, write the yes/no check, and give the O(n log range) cost.
  6. Say when binary search is the wrong tool, and what to use instead.

How to read this: top to bottom, like a book. It builds on How fast is your code? (where log₂ n comes from) and Putting things in order (sorting as a one-time cost that makes later questions cheap). Answer each quick check before reading on; a wrong answer gets you a second explanation. "Go deeper" boxes are optional on a first read.

1The problem: 10 million orders, 1,000 questions a second

A delivery app keeps every order from today in one list, in the order they arrived, so the list is sorted by time. By evening it holds 10,000,000 orders. A support dashboard keeps asking questions like "show me the orders placed between 18:00:00 and 18:00:59". Across all the support staff, it asks about 1,000 of these a second.

The first version scans: walk the list from the start until you reach 18:00:00, then collect orders until 18:01:00. On average that reads about half the list, 5 million orders, per question. 1,000 questions a second is 5 billion reads a second. Python does roughly 10 million simple steps a second, so the dashboard needs about 500 seconds of work every second. It falls behind within minutes.

The scan ignores the one thing that makes this list special: it's sorted. Look at the order in the middle of the list. If it was placed at 14:12, then every order before it is earlier than 14:12 too, so none of them can be at 18:00. One look, and half the list is ruled out. Look at the middle of what's left, and half of that goes. That's binary search.

With it, each question needs two searches (where 18:00:00 starts, and where 18:01:00 starts), and each search needs at most 24 looks into a list of 10 million. That's 48 reads per question instead of 5 million, or 48,000 reads a second for the whole dashboard: about 5 milliseconds of work per second instead of 500 seconds.

Notice what the dashboard actually needs. Not "is there an order at exactly 18:00:00.000?", but "where does 18:00 start?". Most of this chapter is about that difference.

A teammate suggests loading all 10 million timestamps into a hash set instead, because set lookups are O(1). What goes wrong?

Right. A hash set throws the order away: items are placed by their hash, not by time. To answer "between" with a set you'd have to try every possible timestamp in that minute (60,000 of them at millisecond precision) or scan everything. The sorted list keeps the order, and order is exactly what binary search uses.

Think of a coat check. Hand over your exact ticket and you get your coat back instantly; that's a hash set. Now ask the attendant "which coats came in between 6:00 and 6:01?". They have no idea: the coats are hung by ticket number, not by time. A sorted list is a rail of coats in arrival order: find where 6:00 starts and where 6:01 starts, and everything between is your answer. Timestamps hash fine; the problem is that "between" needs order, and hashing destroys it.

2Halving a sorted list

You've already met halving in the complexity chapter: guessing a secret number from 1 to 64 takes only 6 yes/no questions, because each answer cuts the possibilities in half. Binary search on a sorted list is the same game. The list plays the secret-keeper.

Keep two indexes, lo and hi, that fence in the part of the list where the target could still be. Look at the item in the middle, mid.

  • If it's the target, you're done.
  • If it's smaller than the target, the target can't be at mid or anywhere left of it (those are even smaller). Move lo to mid + 1.
  • If it's bigger, the target can't be at mid or to its right. Move hi to mid − 1.

When the fence is empty (lo > hi), the target isn't there.

def find(a, x):
    lo, hi = 0, len(a) - 1      # if x is anywhere, it's in a[lo..hi]
    while lo <= hi:             # the fenced part still has items
        mid = (lo + hi) // 2
        if a[mid] == x:
            return mid
        if a[mid] < x:
            lo = mid + 1        # x is bigger: it can only be right of mid
        else:
            hi = mid - 1        # x is smaller: it can only be left of mid
    return -1                   # fence is empty: x isn't in the list
The search above on 15 sorted numbers. Yellow is the probe (mid); faded cells are ruled out. Try a target that's missing, like 40, and notice where lo ends up: right where 40 would go. Section 3 is built on that.

Pass indexes, not slices. find(a[mid + 1:], x) looks the same but copies half the list on every step, which costs n/2 + n/4 + … ≈ n in total: O(n), not O(log n). It also returns an index into the copy, not into a. (The complexity chapter's section 5 has this trap.)

How many probes?

Each probe at least halves what's left. So the worst case is the number of times you can halve n before nothing is left, which is ⌊log₂ n⌋ + 1 (⌊ ⌋ means "round down").

Each probe rules out half of what's left, so n items need at most ⌊log₂ n⌋ + 1 probes: 20 for a million, 30 for a billion. It only works because the list is sorted: one comparison tells you which half can't hold the answer.

A sorted list of 1,000,000 user ids grows to 2,000,000. In the worst case, how many more probes does binary search need?

Right. The very first probe on 2,000,000 items cuts them to 1,000,000, and from there it's the old search. Doubling the data adds one probe. That's what log₂ means, and it's why binary search barely notices growth: a billion items is 30 probes.

Work backwards. Halve 2,000,000 once and you have 1,000,000 left, which is exactly the old problem: 20 more probes at most. So 21 in total. Twice the data means one more halving, not twice the halvings. "A million more" would be a scan's cost, which grows with n itself.

Go deeper: the bug that sat in Java for nine years

In C, C++, Java and Go, an int has a fixed size. A Java int is 32 bits and tops out at 2,147,483,647. If lo and hi are both above about 1.07 billion (2³⁰), then lo + hi goes past that limit, wraps around to a negative number, and mid becomes a negative index. In Java that throws an exception (in C it's undefined behavior), but only on arrays with more than a billion items, so tests never catch it.

That bug was in Java's own Arrays.binarySearch for about nine years before Joshua Bloch wrote it up in 2006; the same line is in the classic book Programming Pearls. The fix is mid = lo + (hi - lo) / 2, which never exceeds hi, or in Java (lo + hi) >>> 1, which treats the sum as unsigned. Python's ints never overflow, so (lo + hi) // 2 is safe in Python. (NumPy's fixed-size ints are not.) If you write binary search in a fixed-width language in an interview, use the safe form and say why.

3The real idea: find where the answer flips

find answers one question: "is x in the list, and where is a copy?". That's not what most real problems ask. Try it on [2, 4, 4, 4, 4, 7, 9]:

  • Searching for 4, the first probe is index 3, which holds a 4, so it returns 3. But the first 4 is at index 1. Which copy you get depends on where the probes happen to land.
  • Searching for 5, it returns −1. But the dashboard from section 1 needs "where would 5 go?" (index 5), because "orders from 18:00:00 on" starts there even if no order was placed at exactly 18:00:00.

Here's the reframe that fixes both. Instead of comparing with x three ways (smaller, equal, bigger), ask one yes/no question about each position. For "where would 5 go?", the question is "is a[i] ≥ 5?":

index:      0    1    2    3    4    5    6
a[i]:       2    4    4    4    4    7    9
a[i] ≥ 5?   no   no   no   no   no   yes  yes
                                     ↑ the first yes: index 5

Because the list is sorted, the answers can only go no, no, …, no, yes, …, yes. Once a yes appears, every later item is at least as big, so it's a yes too. A yes/no question whose answer changes at most once, and never goes back, is called monotone (all no or all yes counts too). What we want is the boundary: the first yes.

Searching for a boundary

Binary search finds that boundary by keeping two facts true at every step. This pair of facts is the loop's invariant (something the loop never breaks):

  • everything left of lo is a known no;
  • everything from hi on is a known yes.

Between them, from lo up to (but not including) hi, is the unknown zone, written [lo, hi).

[ known no  |  unknown ...  |  known yes ]
 0           lo              hi           n
  1. Start with lo = 0 and hi = n. Nothing is known. hi = n is one past the end: a pretend "yes" that stands for "maybe no item is a yes at all".
  2. Probe mid = (lo + hi) // 2. Since lo < hi, mid is always inside the unknown zone.
  3. If the answer at mid is yes, then mid and everything after it are yes: set hi = mid.
  4. If it's no, then mid and everything before it are no: set lo = mid + 1.
  5. Stop when the zone is empty, lo == hi. Now lo is the first yes, or n if there is none.
Top row: the values. Bottom row: what the search knows about each position (red = known no, green = known yes, ? = unknown). The faded cell at the end is the pretend "yes" at index n. Try "a[i] > x" with x = 8: the boundary moves past all the 8s.

The same loop works for any monotone question, not only "a[i] ≥ x". Here it is on something that isn't a list of numbers at all. Builds 1 to n of an app; at some point a bad change went in, and every build after it is broken too. Each test run takes 10 minutes. Which build broke it?

def first_broken(n, is_broken):
    lo, hi = 1, n + 1        # unknown zone is [lo, hi); n + 1 means "none broken"
    while lo < hi:           # stop when the unknown zone is empty
        mid = (lo + hi) // 2 # lo <= mid < hi: always an untested build
        if is_broken(mid):
            hi = mid         # mid and everything after: known broken
        else:
            lo = mid + 1     # mid and everything before: known fine
    return lo                # the first broken build, or n + 1 if none are

With 1,000 builds, testing them one by one could take 1,000 runs, almost 7 days. This takes at most 10 runs: 100 minutes.

Don't search for a value; search for the boundary where a monotone yes/no question flips. Keep "left of lo is no, from hi on is yes" true at every step, and stop when lo and hi meet: lo is the first yes.
Explain it another way: two flags

Stand a red flag on the last spot you know is a no, and a green flag on the first spot you know is a yes. At the start you know nothing, so the red flag stands just before the list (position −1) and the green flag just after it (position n). Each probe lands strictly between the flags and moves one of them there: a no moves the red flag, a yes moves the green flag. The flags only ever walk toward each other. When they're neighbors there's nothing left between them, and the green flag marks the first yes.

Some people write the loop exactly like this: lo, hi = -1, n, while hi - lo > 1, and both branches set lo = mid or hi = mid; return hi. It's the same invariant with different labels (here lo is the red flag itself, not the spot after it). Pick one style and keep to it.

In first_broken, when is_broken(mid) is true the code sets hi = mid. Why not hi = mid - 1, since we've already tested mid?

Right. hi means "from here on, everything is known broken". We know mid is broken, so mid can join that zone. We know nothing about mid − 1; it might be fine. Builds 1 to 4 with build 3 the first broken one: lo = 1, hi = 5, mid = 3 is broken, and hi = mid − 1 = 2 declares build 2 broken. The loop then returns 2, the wrong build.

Read hi as a promise: "every build from hi on is broken". Setting hi = mid − 1 makes that promise about build mid − 1 without testing it. It doesn't hang (the zone still shrinks), and it isn't a style choice: it gives wrong answers. Trace builds 1 to 4 where build 3 is the first broken one. lo = 1, hi = 5. mid = 3 is broken, so the buggy line sets hi = 2. mid = 1 is fine, so lo = 2. Now lo == hi == 2, and it reports build 2, which works fine. The correct line, hi = 3, keeps build 3 in play.

Go deeper: why the loop must be right, and git bisect

The invariant gives you a proof in three steps, the same three that prove any loop. It starts true: with lo = 0 and hi = n there's nothing left of lo and nothing from hi on except the pretend yes. Each step keeps it true: a yes at mid means everything after mid is yes (that's monotone), so hi = mid is safe; a no means everything before mid is no, so lo = mid + 1 is safe. The loop ends: hi − lo is a whole number, at least 1 inside the loop, and both branches make it smaller (mid < hi, and mid + 1 > lo). It reaches 0 after at most ⌈log₂(n + 1)⌉ steps (⌈ ⌉ means "round up"). When it does, lo == hi, there are no unknowns, so lo is the first yes.

first_broken is exactly what git bisect does. You mark one commit good and one bad; git checks out the commit in the middle; you test it and type git bisect good or bad; repeat. About log₂ of the number of commits rounds: 10 for 1,000 commits. git bisect run ./test.sh does the whole thing unattended. It relies on the same monotone assumption: if a bug was introduced, fixed, and introduced again, bisect finds a place where good turns to bad, not necessarily the first one.

4Why binary searches hang (and miss by one)

When Jon Bentley gave professional programmers a couple of hours to write binary search, only about one in ten got it bug-free. The bugs are almost always one of a few lines: < versus <=, mid versus mid + 1, n versus n − 1. Guessing between them until the tests pass is how people get stuck. The invariant turns the guessing into three rules you can check line by line:

  1. Start with the invariant true. If "no item is a yes" is a possible answer, hi must start at n, one past the end. Starting at n − 1 means the search can never answer "none".
  2. Every branch must keep it true. Only mid itself was tested. On a yes, hi = mid (not mid − 1: section 3's quick check). On a no, lo = mid + 1 (mid is a known no, so it leaves the zone).
  3. Every branch must shrink the zone. Otherwise the next pass computes the same mid, gets the same answer, and changes nothing again, forever.

Rule 3 is the one that causes hangs, and the reason is rounding. (lo + hi) // 2 rounds down. When the zone is down to one cell, say lo = 4 and hi = 5, mid = 9 // 2 = 4 = lo. If the code then says lo = mid, lo stays 4, hi stays 5, and the loop spins forever. hi = mid is safe because mid is always strictly less than hi; lo = mid + 1 is safe because it's always more than lo.

Three rules: hi starts where the invariant is true (n if "none" is possible); each branch moves only mid into a known zone (hi = mid on yes, lo = mid + 1 on no); and each branch must shrink [lo, hi). Since // rounds down, mid can equal lo but never hi, which is why lo = mid hangs and hi = mid doesn't.

This loop has a bug: the no branch says lo = mid. On a = [1, 3, 5, 7], which target finishes instead of looping forever?

lo, hi = 0, len(a)
while lo < hi:
    mid = (lo + hi) // 2
    if a[mid] >= x:
        hi = mid
    else:
        lo = mid          # bug: should be mid + 1

Right. With x = 1 every probe is a yes (everything is ≥ 1), so only hi moves and the buggy line never runs: hi goes 4, 2, 1, 0 and the loop returns 0. For x = 4 the zone shrinks to lo = 1, hi = 2; mid = 1, a[1] = 3 is a no, and lo = mid = 1 changes nothing. For x = 8 it gets stuck at lo = 3, hi = 4 the same way.

Look for the moment the zone is down to one cell: hi = lo + 1. Then mid = (lo + lo + 1) // 2 = lo, because // rounds down. If that cell is a no, lo = mid leaves lo where it was, and the next pass does the exact same thing. So the loop hangs whenever it takes the no branch with a one-cell zone, and for x = 4 and x = 8 it does (stuck at lo = 1, hi = 2 and at lo = 3, hi = 4). For x = 1, a[mid] ≥ 1 is true at every probe, so the no branch never runs and the bug never fires.

Go deeper: searching for the last yes, and the other loop style

The last yes. Some questions flip the other way: yes, yes, yes, no, no. If you want the last yes, the easiest correct move is to search for the first no with the same loop and subtract 1 (section 8 does this). The alternative keeps lo as a known yes and uses lo = mid, which only works if you round mid up: mid = (lo + hi + 1) // 2. Then mid is never equal to lo, and the zone always shrinks. It's correct but easy to forget, which is why "first no, minus 1" is the safer habit.

The closed style. find in section 2 uses hi = len(a) - 1, while lo <= hi and hi = mid - 1, all things the table calls bugs. It isn't buggy, because it has a different invariant: "if x is anywhere, it's in a[lo..hi], both ends included". For that invariant, an empty zone is lo > hi, and mid itself has already been ruled out when a[mid] ≠ x, so mid − 1 is right. Every bug in the table comes from taking a line from one style and dropping it into the other. Know which invariant your loop keeps, and every line follows from it.

5First, last, and how many: lower and upper bound

Two boundary questions cover almost every "sorted list" problem. They're common enough to have names:

  • lower bound of x: the first index with a[i] ≥ x. Python calls it bisect_left(a, x).
  • upper bound of x: the first index with a[i] > x. Python calls it bisect_right(a, x).

Both are the boundary loop from section 3; only the question changes. Between them sit exactly the copies of x:

index:     0    1    2    3    4    5
a[i]:      2    4    4    4    7    9
a[i] ≥ 4?  no   yes  yes  yes  yes  yes   → bisect_left(a, 4)  = 1
a[i] > 4?  no   no   no   no   yes  yes   → bisect_right(a, 4) = 4
the 4s live in [1, 4): indexes 1, 2, 3, and there are 4 − 1 = 3 of them
xbisect_left(a, x)bisect_right(a, x)what it tells you
100smaller than everything: it would go at the front
414three copies, at indexes 1 to 3
544both equal: no copies; 5 would go at index 4
956one copy, the last item
1066bigger than everything: index n, past the end

Everything else is a line of arithmetic on those two numbers. Call them L and R:

  • How many copies of x: R − L.
  • Is x there at all: L < n and a[L] == x. (Equivalently, R − L > 0.)
  • First copy: L, if x is there. Last copy: R − 1, if x is there.
  • Where to insert x and keep the list sorted: L (before equal items) or R (after them).
  • How many items in [lo, hi]: bisect_right(a, hi) − bisect_left(a, lo). Two searches, any size of range.

That last line is the whole dashboard from section 1:

from bisect import bisect_left, bisect_right

def orders_between(times, start, end):
    """times is sorted. How many orders have start <= t <= end?"""
    i = bisect_left(times, start)   # first order at or after start
    j = bisect_right(times, end)    # first order strictly after end
    return j - i                    # times[i:j] is exactly the range
bisect_left is the first a[i] ≥ x; bisect_right is the first a[i] > x. The copies of x are exactly a[left:right]. Counting, first copy, last copy, insert position and range queries all come from these two boundaries, each found in O(log n).

a = [2, 4, 4, 4, 7, 9]. What does bisect_left(a, 5) return?

Right. bisect_left answers "where is the first a[i] ≥ 5?". a[3] = 4 is a no; a[4] = 7 is the first yes. That's also where you'd insert 5 to keep the list sorted. A boundary search always returns a position from 0 to n; "not found" shows up as a[L] != x, never as −1.

Write the yes/no row for "a[i] ≥ 5": 2 no, 4 no, 4 no, 4 no, 7 yes, 9 yes. The first yes is at index 4. Index 3 is the last 4, which you'd get from bisect_right(a, 4) − 1, a different question. And a boundary search never says −1: it always lands on a position, even past the end (index 6 here, for any x above 9).

Go deeper: the same tool in other languages, and in databases
  • C++: std::lower_bound and std::upper_bound are exactly these two; std::equal_range returns both at once.
  • Java: Arrays.binarySearch returns the index if found, otherwise −(insertion point) − 1, so a "not found" result is always negative and still tells you where x would go. With duplicates, it doesn't promise which copy you get; if you need the first, write the boundary loop.
  • Python: bisect.insort(a, x) inserts into a sorted list, but the insert shifts every later item, so it's O(n) per insert even though the search is O(log n). Since 3.10, the bisect functions also take a key=.
  • Databases: WHERE t BETWEEN a AND b on an indexed column does the same thing: a tree search finds where a starts, then the database walks forward until it passes b. That walk is called a range scan.

6A sorted list that's been rotated

A server keeps the ids of its last 7 requests in a ring buffer: 7 slots, and when they're full, the newest id overwrites the oldest. Ids only go up. Read the slots from 0 to 6 and you see:

slot:   0    1    2    3    4    5    6
id:     25   28   31   12   15   18   21
        └── newer ─┘   └───── older ────┘

It's a sorted list that was cut in two and the pieces swapped. That's called a rotated sorted array. Try section 2's find on it. For 15 it gets lucky: the middle is 12, 12 < 15, it goes right and finds 15. For 28 it fails: the middle is still 12, 12 < 28, so it goes right again, and 28 is on the left. One comparison with the middle no longer tells you which side is safe to throw away.

Way 1: find the cut, then search one piece

The cut is where the smallest id sits. Find it with a boundary question. Compare every item with the last item, 21: "is a[i] ≤ 21?". The newer piece (25, 28, 31) is all bigger than 21; the older piece (12 to 21) is all ≤ 21. So the answers are no, no, no, yes, yes, yes, yes: monotone. The first yes, at index 3, is the smallest id. Then decide which piece the target lives in (≤ 21 means the right piece) and run an ordinary search there. Two binary searches, O(log n).

  31 |       *
  28 |    *
  25 | *
  21 |                   *
  18 |                *
  15 |             *
  12 |          *
     +------------------------
       0  1  2  3  4  5  6   index
≤ 21?  n  n  n  y  y  y  y   (n = no, y = yes)

Way 2: one pass

Cut a rotated array anywhere and at least one of the two halves is in plain sorted order. You can tell which by comparing its ends: if a[lo] ≤ a[mid], the left half a[lo..mid] has no cut in it. A sorted half lets you check "is the target between its ends?". If yes, search there; if no, the target can only be in the other half. Either way, half is gone.

Both ways are O(log n). Way 1 is easier to get right under pressure, because it reuses the boundary loop you already trust.

A rotated sorted array is two sorted runs. "Is a[i] ≤ the last item?" is monotone on it (no for the first run, yes for the second), so a boundary search finds the smallest item, and an ordinary search finishes the job. Total O(log n).

You want the index of the smallest item in a rotated sorted array (all values distinct), and the array might not be rotated at all. Which question can you binary search for its first yes?

Right. On [25, 28, 31, 12, 15, 18, 21] the answers to "≤ 21?" are no, no, no, yes, yes, yes, yes: first yes at index 3. On an unrotated [12, 15, 18, 21], every answer is yes, so the first yes is index 0, still the smallest. "< a[0]" works on a rotated array but is all no on an unrotated one, giving n: wrong without a special case. "< a[i − 1]" is yes at only one spot, so there's no boundary to find.

Test each question on two arrays: rotated [25, 28, 31, 12, 15, 18, 21] and unrotated [12, 15, 18, 21]. "a[i] < a[0]": rotated gives no, no, no, yes, yes, yes, yes (good), but unrotated gives no, no, no, no, and the search returns 4, past the end. "a[i] < a[i − 1]": rotated gives no, no, no, yes, no, no, no. A single yes in the middle isn't a boundary; a probe that lands on a no can't tell which side the yes is on. "a[i] ≤ a[n − 1]" gives the right first yes on both: index 3, then index 0.

Go deeper: duplicates make it O(n)

Allow repeated values and rotation gets truly harder. Compare [1, 1, 1, 1, 1, 0, 1] with [1, 0, 1, 1, 1, 1, 1]. In both, a[lo], a[mid] and a[hi] are all 1, so no probe can tell you which side the 0 is on. The best you can do is drop one end (hi −= 1) and try again, and an array of all 1s with a single 0 forces that n times. So with duplicates, the worst case is O(n), and an interviewer who asks the follow-up wants to hear exactly that, plus why.

A bonus from Way 1: the index of the smallest item is how far the array was rotated. In the ring buffer, it's the slot of the oldest request.

7Search on the answer

So far the yes/no question has been about positions in a list. Now for the move that turns binary search from a lookup trick into a problem-solving tool: asking the question about possible answers instead.

A teacher has 5 stacks of exams to grade: 30, 11, 23, 4 and 20 exams. Each hour she picks one stack and grades up to p exams from it; if fewer than p are left in that stack, she finishes it and takes the rest of the hour off (she never mixes stacks within an hour). She has 8 hours. What's the slowest pace p that still gets everything graded in time?

At pace p, a stack of s exams takes s / p hours, rounded up. Write that ⌈s / p⌉. The total is the sum over all stacks. The first idea: try p = 1, 2, 3, … and stop at the first pace that fits.

pace p151014152030
hours needed8819119875
within 8?nonononoyesyesyes

That works here: 15 tries. But scale it up and it falls apart. Make it a batch job with 100,000 queues of up to 1,000,000,000 items each, where the answer could be in the hundreds of millions. Trying paces one at a time is up to a billion tries, each adding up 100,000 queues: 10¹⁴ steps.

The answers form a sorted list

Look at the bottom row of the table: no, no, no, no, yes, yes, yes. A faster pace never needs more hours (each ⌈s / p⌉ can only stay the same or drop as p grows). So "can she finish at pace p?" is a monotone question over p, and the answer we want is its first yes. That's section 3's boundary search, except the "list" is the range of paces 1 to 30, and "reading an item" means running a check.

The range needs care. lo must be no bigger than the answer: pace 1 is the slowest that makes sense. hi must be a sure yes: at pace 30 (the biggest stack) every stack takes exactly one hour, 5 hours in all, the fastest possible. (If she had fewer hours than stacks, no pace would work; check that first.)

Binary search over paces 1 to 30. The bars show the true hours at every pace, but the search only computes the ones it probes (numbers on top). Red = known too slow, green = known fast enough, yellow = the check being run. Change the deadline and watch the answer move. Bars taller than 40 are cut off (↑).
def slowest_pace(stacks, hours):
    def can_finish(pace):                  # the yes/no question
        return sum((s + pace - 1) // pace for s in stacks) <= hours
    lo, hi = 1, max(stacks)                # at max(stacks), every stack takes 1 hour
    while lo < hi:
        mid = (lo + hi) // 2
        if can_finish(mid):
            hi = mid                       # fast enough: the answer is mid or slower
        else:
            lo = mid + 1                   # too slow: the answer is faster than mid
    return lo                              # assumes hours >= len(stacks)

(s + pace - 1) // pace is ⌈s / pace⌉ in whole numbers, with no floats. Notice hi starts at max(stacks), not one past it: here a yes is guaranteed, so hi can be a real known yes instead of a pretend one. The invariant is the same.

The recipe

Every "search on the answer" problem has the same five steps. Say them out loud in an interview:

  1. What is the answer a number of? A pace, a capacity, a number of days, a distance.
  2. Write the check: "if the answer were x, would it work?". It's usually a greedy pass over the input, O(n). The trick is that checking a given x is much easier than finding the best x.
  3. Argue it's monotone: "if x works, does x + 1 work too?". Give the reason in one sentence. No reason, no binary search.
  4. Pick bounds: lo at or below the answer, hi a sure yes. A hi that's too small gives a wrong answer silently; a hi that's too big costs only a few extra checks (doubling hi adds one), so err big.
  5. Binary search for the first yes (or the last yes; next section). Cost: one check per probe, so O(cost of check × log(hi − lo)).

How to spot one: the problem says "minimum X such that…" or "maximum X such that…", the possible answers span a huge range, and if someone told you an X, you could check it quickly.

When "does x work?" is monotone in x, the possible answers form a sorted list of no's then yes's. Binary search over the answer range, running the O(n) check at each probe: O(n log range) in total. For a billion possible answers that's 30 checks.
Explain it another way: the shower knob

Turn a shower knob to the right and the water gets hotter, never colder. You want the coldest setting that's at least 38°C. You don't try every notch from the left. You turn it halfway, feel the water, and go halfway again toward warmer or colder. Your hand is the check; the knob's range is the list of possible answers. Nobody wrote the temperatures down anywhere; you only ever need the answer at the spots you test. That's search on the answer: the "sorted list" is imaginary, and you compute an item only when you probe it.

Which of these can you solve with binary search on the answer?

Right. "Do s servers meet the 200 ms target?" is monotone: if s servers do, s + 1 do too. So the answers go no, …, no, yes, …, yes, and you want the first yes. "Exactly 8 hours" isn't monotone: paces 1 to 14 are no, 15 to 19 are yes, and from pace 20 on (7 hours or fewer) it's no again. Two flips. And a stock price wanders up and down, so "closest to $100" has no single flip point.

For each one, write the yes/no answers in order and see if they flip only once. Servers: more servers never hurt, so it's no, no, no, yes, yes, yes: one flip. "Exactly 8 hours": paces 1 to 14 are no (too slow), 15 to 19 are yes, and 20 to 30 are no again (too fast, only 7 or fewer hours). Two flips: a probe at pace 25 says "no", and you can't tell whether to go faster or slower. The stock price goes up and down all year, so "closest to $100" isn't even a yes/no that flips once. Binary search needs exactly one flip.

The batch-job version: 100,000 queues, the biggest holding 1,000,000,000 items. Roughly how much work is binary search on the pace?

Right. log₂(1,000,000,000) ≈ 30, so about 30 probes, and each probe runs the check, which reads all 100,000 queues: 30 × 100,000 = 3,000,000. O(n log range). 100 trillion (10¹⁴) is what trying every pace from 1 up could cost.

Count two things and multiply. How many probes? The range is 1 to a billion, and each probe halves it: about 30. What does one probe cost? Running can_finish, which adds up every queue: 100,000 steps. So 30 × 100,000 ≈ 3 million. "30 steps" forgets that a probe isn't free; here, unlike a sorted list, reading one "item" costs n. 100 trillion is a billion paces × 100,000 queues: the one-by-one approach.

Go deeper: when the check is the expensive part
  • Expensive checks. The check can be anything monotone: a 10-minute test run (git bisect), a one-minute load test for "how many requests per second can 4 servers take?", a simulation. Binary search keeps the number of checks at log₂ of the range, which is what makes these practical: 30 one-minute load tests instead of a billion.
  • No known upper bound. Start hi at 1 and double it until can(hi) is a yes: 1, 2, 4, 8, … That finds a sure yes in about log₂(answer) checks, and then the normal search runs below it. This is exponential search (section 10) applied to answers.
  • You need the plan, not just the number. Binary search gives you the best x. If the problem wants the actual schedule (which items on which day), run the check once more at the answer and record what it does.

8The other direction: the biggest value that still works

Some problems ask for a maximum. A hardware shop has cables of 7, 12 and 5 meters. A customer needs at least 4 pieces, all the same whole number of meters long (leftovers are thrown away). What's the longest piece length that still gives 4 pieces?

The check: at length x, cable c gives c // x pieces. Add them up and compare with 4. Now the monotone direction is flipped. Shorter pieces are always easier to get, so the answers go yes, yes, …, yes, no, no:

length x1234567
pieces (7//x + 12//x + 5//x)241175432
at least 4?yesyesyesyesyesnono

We want the last yes, 5. Rather than invent a second loop (and its own off-by-one traps, section 4's deeper box), use the loop you already trust to find the first no, then step back one:

def longest_piece(cables, k):
    # can(x) = "at least k pieces of length x?": yes ... yes, no ... no
    lo, hi = 1, max(cables) + 1      # length max+1 can't give any piece: a sure no
    while lo < hi:                   # search for the FIRST no
        mid = (lo + hi) // 2
        if sum(c // mid for c in cables) >= k:
            lo = mid + 1             # mid works: the first no is further right
        else:
            hi = mid                 # mid fails: it might be the first no
    return lo - 1                    # the last yes is just before the first no

Compare it with slowest_pace: the branches have swapped roles, because now "works" is on the left. If even length 1 fails (fewer than k meters of cable in total), the first no is 1 and the function returns 0, meaning "impossible". Decide up front what your function should return in that case.

Minimum that works: first yes. Maximum that works: the answers flip from yes to no, so find the first no with the same loop and subtract 1. One loop to trust, in both directions.

For the cables 7, 12 and 5 with k = 4, the loop above ends with lo = 6. A teammate's version returns lo instead of lo - 1. What goes wrong?

Right. The loop finds the first length that fails, and 6 fails: 1 + 2 + 0 = 3 pieces. The answer is the one before it, 5: 1 + 2 + 1 = 4 pieces. Returning lo is the classic "search for a maximum" off-by-one.

Remember what this loop's lo means at the end: the first no. Check 6 directly: 7 // 6 = 1, 12 // 6 = 2, 5 // 6 = 0, so 3 pieces, not enough. Length 5 gives 1 + 2 + 1 = 4 pieces, enough. So the last yes is 5, which is lo − 1. It's true that returning lo also breaks the impossible case (1 instead of 0), but that's a symptom: lo is the first no every single time, so returning it is wrong every single time.

9Searching real numbers

The answer doesn't have to be a whole number. Square root is the classic: √x is the boundary where "is m · m ≥ x?" flips from no to yes, and that question is monotone for m ≥ 0. With real numbers there's no "next" number, so the loop changes in two ways:

def sqrt(x):                      # x >= 0
    lo, hi = 0.0, max(1.0, x)     # the root is always in here
    for _ in range(100):          # a fixed count, not "while hi - lo > eps"
        mid = (lo + hi) / 2
        if mid * mid < x:
            lo = mid              # fine here: / doesn't round down onto lo
        else:
            hi = mid
    return hi
  • hi = max(1, x), not x. For x below 1 the root is bigger than x (√0.25 = 0.5), so [0, x] would miss it.
  • lo = mid is fine here. The hang in section 4 came from // rounding mid down onto lo. With real division mid lands strictly between lo and hi, until lo and hi are neighboring floats. Then mid rounds to one of them, a step changes nothing, and only the fixed count ends the loop.
  • Count iterations; don't wait for a gap. Each step halves the gap: starting from [0, 2], 21 steps get it under 0.000001 (2 / 2²¹ ≈ 0.00000095). You need about log₂(starting gap ÷ precision) steps, so 100 gives a float-exact root for any x up to about 10²⁸; for √(10¹⁰⁰) it isn't enough (that start gap needs about 220). But while hi - lo > 1e-9 can hang: computing √(10²⁰), lo and hi end up at two neighboring floats near 10¹⁰, and neighboring floats there are 0.0000019 apart. The gap can never drop below 10⁻⁹, so the loop never ends.

On sqrt(2) this returns 1.4142135623730951, the same as math.sqrt(2). For an exact integer square root of a huge number, use the integer boundary loop instead: the last m with m · m ≤ n (Python ships it as math.isqrt).

Binary search works on real numbers too: same invariant, real division, and a fixed number of iterations. Each one halves the gap, so pick about log₂(starting gap ÷ precision) of them; a fixed count can't hang.

10When binary search is the wrong tool

Binary search needs two things: a monotone question, and the ability to jump straight to any position (to "read item mid" in one step). Take either away, or make the setup cost more than the searching saves, and something else wins.

SituationWhy binary search losesUse instead
Unsorted data, one lookupSorting first costs n log n; one scan costs nScan
Many exact lookups, never rangeslog n per lookup, versus about 1Hash set or dict
Many inserts and deletes between lookupsInserting into a sorted array shifts up to n itemsBalanced tree, skip list, or a database index
A linked listReaching the middle means walking thereScan, or a skip list / tree
The question isn't monotoneThere's no single flip to findRethink the question, or scan
A dozen itemsSaves a handful of stepsScan; it's simpler and just as fast

The first two rows are a trade-off you should be able to price out loud. With n = 1,000,000 unsorted numbers and k lookups: k scans cost k × 1,000,000; sorting once and then binary searching costs about 20,000,000 + 20k. Sorting pays off after about 20 lookups. A hash set costs about 1,000,000 to build and about 1 per lookup, so it wins for exact lookups at any k above a few, and loses the moment you need "between", "first after", or "how many below".

You have a sorted linked list of 1,000,000 nodes and binary search it for one value, walking as little as possible (you keep a pointer to the first node of the part that's left). About how many node-to-node steps does it take?

Right. To read the middle node you walk from the head: 500,000 steps. The next middle is 250,000 steps from there, then 125,000, and so on: about 1,000,000 in total. O(n), no better than a plain scan, and the scan is simpler. (Restart every walk from the head and it's worse: up to about 20 million.) That's why systems that need sorted order plus fast search use trees or skip lists, not sorted linked lists.

Binary search's 20 probes assume you can jump to any index in one step, like an array. A linked list can only go node by node. Reaching the first middle costs 500,000 steps; the next middle is 250,000 further; then 125,000. That adds up to about 1,000,000, so it's O(n). 20 million is what you'd pay restarting every walk from the head; walking on from the start of the part that's left, each walk is half as long as the last, so the total is about one trip down the list.

Go deeper: B-trees, disks, and searching without an end

On disk, every probe is a trip. A billion sorted 100-byte records is 100 GB on disk. Binary search needs 30 probes, each a random read: on a spinning disk (about 10 ms per random read) that's 0.3 seconds per lookup; on an SSD (about 0.1 ms) about 3 ms. Databases do better with a B-tree: each node is one disk page (8 KB in PostgreSQL, 16 KB in MySQL's InnoDB) holding a few hundred sorted keys. You binary search inside the page, in memory, and follow one pointer down. With 500 keys per page, 4 levels hold 62.5 billion keys (500⁴), and the top levels stay cached in RAM, so a lookup costs one or two disk reads instead of 30. A B-tree is binary search reshaped so that every slow probe brings back a whole page of answers.

Exponential (galloping) search. If you don't know where the list ends (a stream, a paged API, a file with no index), probe positions 1, 2, 4, 8, … until you pass the target, then binary search inside the last gap. If the answer is at position p, that's about 2 log₂ p probes: about 40 for p = 1,000,000, without ever knowing n. It's also cheaper than plain binary search when the answer is near the front. Python's own sort (Timsort) gallops like this when merging, once one side keeps winning.

Interpolation search guesses the position by proportion instead of taking the middle, the way you open a phone book near the back for "W": about log log n probes on evenly spread values, but O(n) on skewed ones.

11What to say in the interview

When binary search fits, a strong answer sounds like this:

  1. Name the boundary. "I'll binary search for the first index where a[i] ≥ target." Or: "for the smallest capacity that ships everything in time."
  2. Say the invariant and the bounds. "Everything left of lo is a no, everything from hi on is a yes. hi starts at n, because the answer can be 'none'."
  3. For search on the answer, argue monotone. "If capacity c works, c + 1 works too: every day's load still fits. So the answers flip once."
  4. Give the cost. "O(log n) probes." Or: "about 30 checks over a range of a billion, each O(n), so O(n log range)."
  5. Test the edges out loud. Empty input, one item, all items equal, target below everything, target above everything, answer exactly at lo or at hi.

Write the loop from the invariant, not from memory. If you catch yourself changing < to <= to make a test pass, stop and re-state what lo and hi mean.

Go deeper: follow-up questions interviewers like
  • "Would this work in Java?" (lo + hi) / 2 overflows past about a billion; use lo + (hi - lo) / 2 (section 2).
  • "What if the rotated array has duplicates?" Worst case O(n), because a[lo] = a[mid] = a[hi] gives no information (section 6).
  • "What if you don't know the length?" Exponential search: 1, 2, 4, 8, … then binary search the last gap (section 10).
  • "Find a peak" in an unsorted array. Binary search still works: if a[mid] < a[mid + 1], some peak must lie to the right, so the left half can go. The real requirement is never "sorted"; it's "one probe tells me which half is safe to throw away".
  • "The sorted data is split across 100 machines." If each machine holds one key range, keep a small sorted list of each machine's first key: one binary search over it picks the machine, which then searches its own part. Range queries touch only the machines whose ranges overlap.
  • "k-th smallest in a sorted matrix" or "median of two sorted arrays". Both are boundary searches: the first on the value (count how many entries are ≤ x, monotone in x), the second on where to cut the shorter array, O(log(min(m, n))).

✓What to remember

  1. Binary search rules out half of what's left with every probe: at most ⌊log₂ n⌋ + 1 probes, 20 for a million. It needs sorted order and jumps to any position in one step.
  2. The real idea is a boundary: a monotone yes/no question goes no, …, no, yes, …, yes, and you want the first yes.
  3. Invariant: left of lo is no, from hi on is yes, [lo, hi) is unknown. Start lo = 0, hi = n; yes → hi = mid; no → lo = mid + 1; stop when lo == hi.
  4. Hangs come from a branch that doesn't shrink the zone (lo = mid, since // rounds down); misses come from moving a bound past an untested spot or starting hi at n − 1.
  5. bisect_left = first a[i] ≥ x, bisect_right = first a[i] > x. Count = right − left; last copy = right − 1; range count = two searches.
  6. A rotated sorted array is two runs: "a[i] ≤ last item?" is monotone, so find the smallest item, then search one run. Duplicates make it O(n) in the worst case.
  7. Search on the answer: if "does x work?" is monotone, binary search the range of answers, running the O(n) check at each probe: O(n log range). For a maximum, find the first no and subtract 1.
  8. Real numbers: real division and a fixed number of iterations. Wrong tool: unsorted single lookups, exact-only lookups (hash), heavy inserts, linked lists, questions that aren't monotone.

Warm-up · pen and paper

1. Trace it by hand

Take a = [3, 8, 8, 8, 12, 17, 21]. (a) Run find from section 2 for 12 and for 9; write lo, hi and mid at each step. (b) Run the boundary loop from section 3 for "a[i] ≥ 8" and for "a[i] > 8"; write lo, hi, mid and the yes/no answer at each step. How many copies of 8 are there, according to (b)?

Answers

(a) For 12: (lo 0, hi 6, mid 3: a = 8 < 12) → (4, 6, mid 5: 17 > 12) → (4, 4, mid 4: 12, found at index 4). For 9: the same first two probes, then (4, 4, mid 4: 12 > 9) → hi = 3, lo = 4 > hi: not found, returns −1, and lo = 4 is where 9 would go.

(b) "≥ 8": (0, 7, mid 3: yes) → (0, 3, mid 1: yes) → (0, 1, mid 0: 3, no) → lo = hi = 1. "> 8": (0, 7, mid 3: no) → (4, 7, mid 5: yes) → (4, 5, mid 4: 12, yes) → lo = hi = 4. Copies of 8: 4 − 1 = 3.

Warm-up · pen and paper

2. Break the loop

Each version of "first index with a[i] ≥ x" below has one line changed from section 3's loop. For each, find the smallest input that breaks it, and say whether it gives a wrong answer, hangs, or crashes. (a) hi = len(a) - 1 at the start. (b) while lo <= hi. (c) lo = mid in the no branch. Then say which of section 4's three rules each one breaks.

Answers

(a) a = [1], x = 2: the loop never runs and it returns 0, but the answer is 1 ("none"). Wrong answer; rule 1. (b) a = [], any x: lo = hi = 0, the loop runs, and a[0] crashes. With a = [1], x = 1 it hangs at lo = hi = 0 (yes, hi = mid = 0, no change). Rule 3. (c) a = [1], x = 2: lo = 0, hi = 1, mid = 0 is a no, lo = mid = 0, forever. Hangs; rule 3.

Warm-up · pen and paper

3. Binary search, or not?

For each one, say whether binary search applies. If it does, name the yes/no question and the range, and estimate the number of probes. (a) The first day a server's disk was over 90% full, from a year of daily usage numbers, if files are never deleted. (b) The same, but files do get deleted sometimes. (c) The integer square root of a 30-digit number. (d) Whether 42 appears in an unsorted list of 1,000 numbers, checked once. (e) The lowest floor of a 100-floor building from which a dropped phone breaks, if you have as many phones as you like.

Answers

(a) Yes: "is usage on day d over 90%?" is monotone because usage only grows. Range 365 days, 9 probes. (b) No: usage can go up and down, so there can be several crossings; binary search lands on a crossing, not necessarily the first. Scan. (c) Yes: the last m with m · m ≤ n, over 0 to n; log₂(10³⁰) ≈ 100 probes, exact in Python's big ints. (d) No: one scan is 1,000 steps; sorting first costs more than that. (e) Yes: "does it break from floor f?" is monotone. 7 drops, since 2⁷ = 128 ≥ 100. (With only two phones it becomes a different puzzle, a dynamic programming one.)

Core · code

4. search_range(nums, target): first and last copy

Return (first, last), or (−1, −1). The list comes as a read-only sequence that counts every item you read. The test allows 6 · ⌈log₂(n + 1)⌉ + 6 reads (108 for n = 100,000) and includes a list where every item equals the target, so finding one copy and walking outward (O(n)) fails. Write the boundary loop yourself; no bisect.

Core · code

5. search_rotated(nums, target)

Distinct values, sorted, then rotated (or not rotated at all). Return the index or −1. The test checks every rotation of every small list against brute force, then counts reads on 100,000 items, allowing 8 · ⌈log₂(n + 1)⌉ + 8. Finding the cut by scanning for the drop is O(n) and fails. Way 1 in section 6 is the safer route.

Core · code

6. min_ship_capacity(weights, days)

Packages ship in order; each day the ship loads the next packages that fit under its capacity. Find the smallest capacity that ships everything within days days. Use the recipe from section 7: what's the check, why is it monotone, and what are lo and hi? (Hint: the ship must carry the heaviest package on its own.) The weights count every comparison and addition made with them; trying capacities one at a time blows the budget of 4 · n · (⌈log₂(sum)⌉ + 2).

Core · code

7. max_min_gap(positions, k)

Put k sensors at k of the given positions on a road so that the closest two are as far apart as possible; return that distance. This is a maximum: section 8's direction. Sort once, then write a greedy check for "can k sensors be placed with every gap at least d?". The test counts comparisons, additions and subtractions: one sort plus about n per probe fits; sorting inside every check, or trying d = 1, 2, 3, …, doesn't.

Stretch · design

8. Bisect a flaky benchmark

A performance regression slipped into one of the last 2,000 commits. Each benchmark run takes 15 minutes, and about 1 run in 20 gives the wrong answer. How many runs would plain binary search need if the benchmark were perfect? What does one wrong answer do to it, and can it recover? Design something robust (repeat each probe? verify the final pair? run probes in parallel?) and estimate the total time.
