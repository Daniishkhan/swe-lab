Sorting and its trade-offs

You'll almost never hand-write a sort at work. You will constantly pick between sorting strategies, reason about stability, and use the ideas inside sorts (partitioning, merging, counting) to solve other problems.

CoreThe one-sentence idea

Comparison sorts can't beat O(n log n) in the worst case. Merge sort and heapsort guarantee it, quicksort usually beats both in practice, and counting/radix sort dodge the limit by not comparing at all.

Build itFrom first principles

Why n log n is the floor for comparison sorts

n items can be arranged in n! orders. Each comparison is a yes/no question, so it at best halves the possible orders. You need log₂(n!) ≈ n log n questions to narrow down to one. No clever trick gets around this. Only using more than comparisons does.

Insertion sort: O(n²), but O(n) on nearly sorted data

Like sorting a hand of cards: take the next card and slide it left into place. Tiny overhead and stable. It's the inner engine of Timsort for short runs.

Merge sort: O(n log n) always, stable, O(n) extra space

Split in half, sort each half, merge two sorted lists in one pass. Predictable. It's the basis of external sorting (data bigger than RAM) and of Python's Timsort.

Quicksort: O(n log n) average, O(n²) worst, in place

Pick a pivot and partition into smaller and larger, then recurse. Cache-friendly and usually the fastest. Random pivots make the worst case vanishingly unlikely, and introsort switches to heapsort if recursion goes too deep.

Heapsort: O(n log n) always, in place, not stable

Heapify, then pop max repeatedly. Great guarantees, but it jumps around memory, so it's slower in practice. Mostly used as a fallback.

Counting / radix: O(n + k), no comparisons

If keys are small integers (ages, bytes, digits), count occurrences and lay them out. Radix sort repeats a stable counting sort digit by digit. That beats n log n for the right data.

Stability, and why you should care

A stable sort keeps equal elements in their original order. That lets you sort by multiple keys in passes: sort by name, then stably by department, and each department stays alphabetized. Python's sorted is stable (Timsort). C++'s std::sort is not; use std::stable_sort.

IntuitionPhysical pictures
  • Merge sort is two sorted stacks of exam papers face up: always take the smaller top paper. Merging is easy; the recursion is just a way to get sorted stacks.
  • Quicksort is a bouncer with a height cutoff: everyone shorter goes left, everyone taller goes right. Then each side gets its own bouncer. A bad cutoff (the shortest person) means one side gets everybody.
  • Counting sort is mail sorting into pigeonholes by zip code: you never compare two letters with each other.

InterviewWhat a senior answer adds
  • "Should I sort first?" Sorting is often the O(n log n) step that turns an O(n²) problem into a two-pointer or greedy O(n) pass: intervals, two-sum on sorted input, meeting rooms, deduplication.
  • Quickselect: partition, but recurse into only one side. That finds the k-th smallest in O(n) average. Compare it with a heap's O(n log k) and with full sorting.
  • Data bigger than memory: external merge sort. Sort chunks that fit in RAM, write them out, then k-way merge with a heap. This is a classic follow-up, and it's how databases sort and how LSM compaction works.
  • Real libraries are hybrids: Timsort finds existing runs (great on real-world, partly sorted data); introsort is quicksort + heapsort + insertion sort. Knowing why they are hybrids is the senior bit.
  • Custom comparators: in Python, prefer key= over cmp_to_key. The key is computed once per element, not once per comparison.
TrapsCommon mistakes
  • Quicksort with a fixed first or last pivot on sorted input: O(n²), and possibly a recursion overflow.
  • Merge step using < instead of <= when taking from the left half breaks stability.
  • Sorting inside a loop: that's O(n² log n) hiding in one line.
  • list.sort() returns None. sorted() returns a new list.
RecallCheck yourself
You need to sort 1 billion 32-bit integers on one machine with 4 GB of RAM. Approach?

Four bytes × 10⁹ = 4 GB, which doesn't fit with overhead. Use external merge sort: sort chunks of a few hundred MB, write the sorted runs to disk, then k-way merge them with a heap. Alternatively, with a bounded key range, counting in buckets (radix-style) also works.

Why is quicksort usually faster than heapsort even though both are O(n log n)?

Quicksort scans memory sequentially during partitioning, which is cache-friendly with a tight inner loop. Heapsort jumps between i and 2i+1, causing cache misses at large n.

When would you choose merge sort over quicksort?

When you need stability, a guaranteed worst case, or you're sorting linked lists or external data (merging is sequential access, no random access needed).
