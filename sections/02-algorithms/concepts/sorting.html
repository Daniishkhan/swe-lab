Chapter 2 · Part 2

Putting things in order

P0 asked almost everywhereabout 50 minutes9 quick checks · 11 exercises

You will almost never write a sorting function at work. Python's sorted() is better than anything you'd write in an afternoon. So why a whole chapter? Because the ideas inside sorting come up again and again: splitting a problem in half, merging two sorted things, partitioning around a pivot, counting instead of comparing. Interviewers use sorting to see if you understand those ideas, and to see if you know when sorting is the right tool.

By the end you'll be able to

  1. Explain insertion sort, merge sort and quicksort in plain words, and write them from memory.
  2. Say why merge sort is n log n, and why quicksort is usually fast but sometimes terrible.
  3. Explain why no comparison sort can beat n log n, and how counting sort cheats.
  4. Know what "stable" means and when it matters.
  5. Spot problems where "sort first" is the key move, and problems where sorting is a waste.

How to read this: top to bottom, like a book. You should have read How fast is your code? first. Answer each quick check before reading on; a wrong answer gets you a second explanation. "Go deeper" boxes are optional on a first read.

1The problem: a messy pile

A teacher has 500 exam papers in a random pile. She wants them in order by score, so she can find the median, spot ties, and see who's in the top 10.

Before sorting, every one of those questions means digging through the whole pile. After sorting, each one is instant: the median is the paper in the middle, ties sit next to each other, and the top 10 are on top.

That's the real reason sorting matters. Sorting is a one-time cost that makes lots of later questions cheap. Once a list is sorted:

  • Duplicates are neighbors, so one pass finds them.
  • You can find anything with binary search in O(log n) instead of O(n).
  • Two pointers from the two ends can find pairs that add up to a target (you did this in the last chapter).
  • Overlapping intervals (meetings, bookings) line up so you can merge them in one pass.

So the question for this chapter is: what's the cheapest way to turn a messy pile into a sorted one? Let's start with the most natural idea, the one you'd use without thinking.

Which of these gets much easier once the list is sorted?

Yes. After sorting, the closest pair must be neighbors, so one pass over n − 1 neighboring pairs finds it. Without sorting you'd compare every pair: n². The sum doesn't care about order at all, and for a single lookup, one O(n) scan is cheaper than an O(n log n) sort.

Ask: "does order help this question?" A sum is the same in any order, so sorting can't help. A single lookup is O(n) by scanning, while sorting costs O(n log n), so sorting just to check once is a loss (it only pays off if you'll search many times). But the closest pair: after sorting, the two closest numbers must sit next to each other. So you check n − 1 neighbors instead of n² pairs.

2The natural way: insertion sort

Think about how you sort a hand of playing cards. You pick up cards one at a time. Each new card, you slide left past the bigger ones until it's in the right spot. The cards in your hand are always sorted; you're just inserting one more.

def insertion_sort(a):
    for i in range(1, len(a)):
        card = a[i]                 # the new card
        j = i - 1
        while j >= 0 and card < a[j]:
            a[j + 1] = a[j]         # shift the bigger card right
            j -= 1
        a[j + 1] = card             # drop the new card in the gap

How much work is it?

It depends on how messy the pile is.

  • Worst case: the pile is backwards. Every new card has to slide all the way to the left. Card 2 slides 1 place, card 3 slides 2 places, … card n slides n − 1 places. That adds up to about n²/2. O(n²).
  • Best case: the pile is already sorted. Every new card is already in place. One comparison each, n comparisons in total. O(n).
  • Nearly sorted: only a few cards are out of place, so only a few slide. Close to O(n).
Insertion sort is slow on a messy pile (n²) but very fast on an almost-sorted one (about n). It also has almost no overhead, so it beats fancier sorts on tiny lists. That's why Python's own sort uses (binary) insertion sort on pieces under about 64 items.

A log file has 1,000,000 lines, in time order, except that a handful of lines arrived a few milliseconds late and are slightly out of place. Roughly how many comparisons does insertion sort need?

Right. Each line is compared once with its left neighbor and stays put. The few late lines slide a short way. So the total is about n plus a little. Insertion sort's cost is really "n plus the number of out-of-order pairs". Those pairs are called inversions, and exercise 5 has you count them fast.

n²/2 is the worst case, when every card has to slide all the way left. Here, almost every line is already in place: it gets compared with its left neighbor once, and stops. Only a handful slide, and only a little. So it's about n comparisons. A useful way to say it: insertion sort costs n + (number of out-of-order pairs).

3Divide and conquer: merge sort

n² is too slow for a million items (about 500 billion steps). We need a cleverer idea. Here's one that sounds almost too simple.

Step 1: merging two sorted piles is easy

Imagine two piles of exam papers, each already sorted, face up, lowest score on top. To combine them into one sorted pile, just look at the two top papers, take the lower one, and repeat. You never have to look deeper than the top of each pile. Each paper is handled once, so merging two piles with n papers in total takes about n steps.

Merging two sorted piles. At every step, compare only the two front cards (yellow) and move the smaller one down. Press ▶ Play or step with ▶|.

Step 2: but where do sorted piles come from?

Here's the trick. Split the pile in half. Sort each half the same way (split it in half again, and again). Keep splitting until each pile has just one paper. A pile of one paper is already sorted! Then merge pairs of piles back together, level by level.

def merge_sort(a):
    if len(a) <= 1:
        return a[:]                 # one card: already sorted (return a copy)
    mid = len(a) // 2
    left = merge_sort(a[:mid])      # sort the left half
    right = merge_sort(a[mid:])     # sort the right half
    return merge(left, right)       # the easy part from step 1

Why it's n log n

Draw the splitting as levels:

level 0:  [ 8 papers                    ]     merging here: 8 steps
level 1:  [ 4          ] [ 4          ]     merging here: 4 + 4 = 8 steps
level 2:  [ 2  ] [ 2  ] [ 2  ] [ 2  ]     merging here: 8 steps
level 3:  [1][1] [1][1] [1][1] [1][1]     (nothing to merge)

Two facts make this work:

  1. Every level does about n work in total. The piles get smaller but there are more of them; together they always hold all n papers, and merging touches each paper once.
  2. There are only log₂ n levels of merging. You halve each time, and (from the last chapter) you can only halve n about log₂ n times before you reach 1. For 8 papers that's 3 levels of merging; the bottom row of single papers needs none.

n work per level × log n levels = n log n. For a million items, that's about 20 million steps instead of 500 billion. Same computer, 25,000 times less work.

Merge sort = split in half until trivial, then merge back up. log n levels, n work per level, so O(n log n). Always, no matter what the input looks like.
Explain it another way: merging teams

Picture 1,024 people who need to line up by height. Instead of one person organizing everyone, pair them up: each pair lines itself up (easy). Then pairs of pairs merge into lines of 4. Then 8, 16, and so on. After 10 rounds (because 2¹⁰ = 1,024) there's one line.

In every round, every person takes one step into a merged line, so every round costs about 1,024 steps. 10 rounds × 1,024 people ≈ 10,000 steps. That "rounds × people" is exactly log n × n.

You give merge sort a list that's already sorted. How much work does it do?

Right. Merge sort doesn't look at the data before splitting. It still makes log n levels and still merges n items per level. That's its strength (predictable: never worse than n log n) and its weakness (never better either, unlike insertion sort).

Merge sort splits blindly, in the middle, without looking at the values. So it always builds the same log n levels and always merges every item at every level. Sorted, reversed, random: all n log n. (Python's real sort, Timsort, adds a check for already-sorted runs to get O(n) on sorted data. Plain merge sort doesn't.)

Go deeper: the recurrence, and the memory cost

Write T(n) for the time to merge sort n items. Sorting n items means sorting two halves and merging: T(n) = 2·T(n/2) + n. Unroll it: T(n) = 4·T(n/4) + 2n = 8·T(n/8) + 3n = … = n·T(1) + n·log₂ n. That's the same n log n as the picture, in algebra form. This pattern ("split into 2 halves, do n extra work") is so common that it's worth recognizing on sight; the general tool is called the Master Theorem.

Memory: merging needs somewhere to put the merged result, so merge sort uses O(n) extra space. That's its main downside. It's also why merge sort is the go-to for data too big to fit in memory: you sort chunks that fit, write them to disk, then merge the sorted files by reading just the front of each one. That's external merge sort, and databases do it when an ORDER BY doesn't fit in memory and no index already gives them the order.

4Quicksort: the bouncer

Merge sort does its hard work on the way up (merging). Quicksort flips this around: it does the hard work on the way down, so there's nothing left to do on the way up.

Picture a bouncer at a club with a height cutoff. Pick one person as the pivot. Everyone shorter than the pivot goes to the left room. Everyone taller goes to the right room. The pivot stands in the doorway, and now the pivot is in exactly the right final spot. Then each room gets its own bouncer and does the same thing. When a room has 0 or 1 people, it's done.

The splitting step is called partitioning. It takes one pass over the items, so it's O(n), and it happens in place: no second list needed.

Partitioning around the pivot (purple, the last item). Green cells are known to be smaller than the pivot. The scanner (yellow, "scan") checks one item at a time; "edge" marks where the green zone ends, and the next small item is swapped there. At the end the pivot swaps into the doorway.
def quicksort(a, lo, hi):
    if lo >= hi:
        return
    p = partition(a, lo, hi)   # pivot lands at index p, in its final spot
    quicksort(a, lo, p - 1)    # the "shorter" room
    quicksort(a, p + 1, hi)    # the "taller" room

Good pivot, bad pivot

Everything depends on the pivot.

  • Good pivot (near the middle): the two rooms are about the same size. That's just like merge sort's halving: log n levels, n work per level, O(n log n).
  • Bad pivot (the smallest or largest): one room is empty and the other has everyone but the pivot. You've removed just one person per level. n levels × n work = O(n²).

Here's the trap. A simple quicksort uses the last item as the pivot. If the list is already sorted, the last item is always the largest. Worst case, every time, on the most innocent-looking input there is.

The fix: pick the pivot at random. Now no input is bad on purpose. To hit the worst case on 1,000 items you'd have to pick the smallest or largest item at nearly every step, which is far less likely than flipping 1,000 heads in a row. Half the time a random pivot lands in the middle half (a 25/75 split or better), and even a steady 25/75 split only costs about 2.4 × log₂ n levels instead of log₂ n. Still n log n.

Quicksort = partition around a pivot, then recurse on both sides. Average O(n log n), worst O(n²). A random pivot makes the worst case practically impossible for distinct items; with many equal items you also need a three-way partition (Go deeper below). It sorts in place and is usually the fastest in practice.

Quicksort always picks the first item as the pivot. Which input makes it slowest?

Right. In a sorted list the first item is the smallest, so the "smaller" room is always empty and you peel off one item per level: n levels, O(n²). A reversed list is just as bad. That's why real quicksorts pick a random pivot (or the median of three samples).

Quicksort is only n log n when the pivot splits the list into two decent-sized rooms. If the list is already sorted, the first item is the smallest. Everyone else goes to the "taller" room; the other room is empty. You've only removed one item, and you do that n times: n levels of about n work, so O(n²). Random pivots fix this because no fixed input can trick them.

Go deeper: when everybody is the same height

Random pivots don't save you from one case: lots of equal items. The partition in the animation above (it's called Lomuto's) sends everything "not smaller than the pivot" to the right. If all n items are equal, that's every item. One room of n − 1, again and again: O(n²) and, in Python, a RecursionError.

The fix is the three-way partition (sometimes called the Dutch national flag partition): split into smaller, equal, and larger. The equal group is finished immediately, and you only recurse on the other two. On an all-equal list, that's one pass and done. Your quicksort exercise tests exactly this. Keep four zones as you scan:

[ smaller | equal | not checked yet | larger ]
 lo        lt      i                 gt      hi

Look at the item at i: if it's smaller, swap it to the end of the "smaller" zone; if larger, swap it to the front of the "larger" zone (and look at whatever came back before moving on); if equal, just step past it. Stop when the unchecked zone is empty.

Hoare's partition, the other classic, scans from both ends and stops on items equal to the pivot too, so it also splits an all-equal list evenly. Interviewers sometimes ask about Lomuto vs Hoare: Lomuto is simpler to write; Hoare does about 3× fewer swaps and handles duplicates.

Why "average n log n" isn't hand-waving: with random pivots, the expected number of comparisons is about 2n·ln n ≈ 1.39·n·log₂ n. Only 39% more than a perfect split every time. The proof counts, for each pair of items, the chance they ever get compared; it's a classic, and worth looking up once.

Recursion depth: recursing into the smaller room first (and looping on the bigger one) keeps the call stack at O(log n) even in bad cases.

Yes. Merge sort splits in the middle without looking, so its work barely depends on the data. 6The speed limit: why nothing beats n log n

Merge sort is n log n. Quicksort is n log n on average. Heapsort (you met heaps in chapter 1) is n log n. Why does everyone get stuck at the same number? Is there a smarter idea nobody's found yet?

No, and you can prove it with a game of 20 questions.

I shuffle n cards and hide them. Your job is to figure out the exact order. You may only ask yes/no questions of the form "is card A smaller than card B?". How many questions do you need?

Count the possible answers first. There are n! possible orders (n × (n − 1) × … × 1). For 3 cards that's 6; for 10 cards, 3.6 million.

Each yes/no answer can at best cut the possibilities in half. To get from n! possibilities down to 1, you need at least log₂(n!) questions, because that's how many halvings it takes. And log₂(n!) is about n log₂ n.

A sort that only learns about the data by comparing two items is playing this game. So any comparison sort needs about n log n comparisons in the worst case. Merge sort and heapsort aren't just good; they're as good as it gets.

Every comparison is a yes/no question. There are n! possible orders, so you need log₂(n!) ≈ n log n questions. That's a hard floor for any sort that works by comparing.

Someone claims their new sort handles any list of numbers in O(n), using only comparisons. What's wrong?

Exactly. With at most c·n yes/no answers you can tell apart at most 2^(c·n) orders. But log₂(n!) ≈ n log₂ n outgrows c·n for any fixed c: even at 5 comparisons per item, n! passes 2^(5n) at n = 84, and the gap keeps growing. So for big enough n, two different orders get identical answers and the sort gets one of them wrong.

Use the 20-questions argument. O(n) comparisons means at most c·n yes/no questions for some fixed c, and those can tell apart at most 2^(c·n) situations. There are n! possible orders, and log₂(n!) ≈ n log₂ n eventually beats c·n whatever c is (for c = 5, from n = 84 on). Past that point some different orders get identical answers, and the sort has to treat them the same, which means getting one wrong. O(n) is possible, but only by doing something other than comparing; that's the next section.

Go deeper: why log₂(n!) ≈ n log₂ n

log(n!) = log 1 + log 2 + … + log n. That's at most n·log n (n terms, none bigger than log n). It's also at least the top half of the terms: (n/2) terms, each at least log(n/2), giving (n/2)·log(n/2). Both bounds are "some constant × n log n", so log(n!) = Θ(n log n). (Stirling's formula gives the exact form: log₂(n!) ≈ n log₂ n − 1.44n.)

This argument is called a decision tree lower bound. It's one of the few places in computer science where you can prove that no comparison-based algorithm, however clever, can beat a limit. The bound also holds on average and for randomized sorts. And if there are only d distinct values, the floor drops to about n log d, which is why three-way quicksort can finish an all-equal list in O(n) without breaking this rule.

7Breaking the limit: don't compare at all

The speed limit only applies to sorts that compare. If you know something extra about your data, you can skip comparing entirely.

Counting sort: pigeonholes

Think of a post office sorting letters by zip code into a wall of pigeonholes. The clerk never compares two letters. She reads the zip code and drops the letter straight into its hole. Then she collects the holes in order.

If your keys are small whole numbers (ages 0–120, exam scores 0–100, bytes 0–255), you can do the same:

  1. Count how many items have each key. One pass: O(n).
  2. Work out where each key's group starts in the output (a running total of the counts). O(k), where k is the number of possible keys.
  3. Place each item at its group's next free spot, going through the input in order. One pass: O(n).

Total: O(n + k). For a million people sorted by age, that's about a million steps, not 20 million.

Counting sort on exam grades 0–4. Each item drops into its pigeonhole without being compared to anything. Then the holes are emptied in order. The figure keeps a list per hole (the simplest code); steps 1–3 above do the same thing with only counts, where step 2's running totals say where each hole's group starts in the output.

Radix sort: one digit at a time

What if keys are big, like 9-digit numbers? A billion pigeonholes is too many. Instead, sort by the last digit (10 holes), then by the second-last, and so on. Each pass must be stable (next section) so that earlier passes aren't undone. Nine passes of O(n) each sorts 9-digit numbers. It's how old punch-card machines sorted, and it's still used for sorting integers and fixed-length strings.

When is counting sort a bad idea?

Right. Counting sort costs O(n + k). Here n = 100 but k = a billion pigeonholes, almost all empty. A normal O(n log n) sort does about 700 comparisons. Counting sort shines only when k is small compared to n.

Look at both parts of O(n + k). Birth years: n = 10 million, k ≈ 150 years; great. Bytes: k = 256; great. But 100 prices with k = a billion means building a billion pigeonholes to hold 100 items. A regular sort on 100 items takes about 700 comparisons. Counting sort only wins when the range of keys (k) isn't much bigger than the number of items (n).

8Stability: keeping ties in order

A sort is stable if items with equal keys stay in the same order they started in.

Why would you care? Imagine a spreadsheet of employees, already sorted by name. Now you sort by department. With a stable sort, everyone within the same department is still in name order, because equal departments kept their earlier (alphabetical) order. With an unstable sort, each department comes out scrambled.

Before (sorted by name)
Ana    Sales
Bo     Eng
Cy     Sales
Di     Eng
After a STABLE sort by department
Bo     Eng      ← Bo before Di, still
Di     Eng
Ana    Sales    ← Ana before Cy, still
Cy     Sales

This "sort by the less important key first, then stably by the more important key" trick is exactly how radix sort works, and it's how clicking column headers in a table behaves.

  • Stable: insertion sort, merge sort, counting sort, Python's sorted and list.sort (Timsort), Java's object sort.
  • Not stable: the usual quicksort and heapsort (they swap items over long distances, jumping over equal ones), C++'s std::sort.

You want a list of orders sorted by customer, and within each customer, by date. You have a stable sort. What do you do?

Right. The last sort wins as the main order; the stable sort keeps the earlier order (date) inside each group of ties (same customer). In Python you'd usually just write sorted(orders, key=lambda o: (o.customer, o.date)), which does it in one go.

Think about which sort decides the final order: the last one. So the last sort should be by customer. Stability then keeps ties (orders from the same customer) in whatever order they had before, so the sort before it should be by date. Least important key first, most important key last. (In Python, a tuple key (customer, date) does it in one sort.)

9What real languages actually use

Real-world sorts are hybrids that steal the best part of each idea:

  • Timsort (Python, Java for objects, Android): finds runs that are already sorted, uses insertion sort to stretch short runs, then merges runs like merge sort. Stable. O(n) on sorted data, O(n log n) worst case.
  • Introsort / pdqsort (C++ std::sort, Rust's unstable sort, Go): quicksort, but switches to heapsort if the recursion gets suspiciously deep (so the worst case is n log n) and to insertion sort for tiny pieces. Not stable, in place, very fast.
  • Java uses dual-pivot quicksort for primitives (int[]) but Timsort for objects. For plain numbers, stability is invisible (two equal 7s look the same), so it can pick the faster unstable sort.

Go deeper: why quicksort beats heapsort in practice

Both are n log n on paper. But quicksort's partition walks through memory in a straight line, which is what CPU caches are built for: when you read one item, the next few come along for free. Heapsort jumps from index i to 2i + 1, all over the array, missing the cache constantly. The Big-O is the same; the constant factor is not. This is a great example of "when Big-O lies" from the last chapter.

10Sorting as a tool in interviews

In interviews, you rarely implement a sort. You use one. Here are the patterns to recognize:

  1. Sort, then scan neighbors. Closest pair, duplicates, "minimum difference". A cousin: grouping anagrams sorts the letters of each word to make a hash key.
  2. Sort intervals by start. Merge overlapping meetings, count rooms needed, insert an interval. After sorting by start, anything that overlaps the current interval must come right after it.
  3. Sort, then two pointers or binary search. Pair sums, three-sum, "how many pairs are under a limit".
  4. Custom order. "Largest number formed from these numbers" ([3, 30, 34, 5, 9] → 9534330) sorts by a comparison rule, not by value: put a before b if a+b > b+a as strings. In Python, wrap the rule with functools.cmp_to_key.
  5. Don't sort everything when you only need part.
    • The k-th smallest item: quickselect partitions like quicksort but only recurses into the side that contains k. Average O(n) (n + n/2 + n/4 + … ≈ 2n); O(n²) worst case with terrible pivots.
    • The top k of a huge stream: keep a heap of size k. O(n log k), with only k items in memory.
  6. Don't sort when a hash set will do. "Any duplicates?" is O(n) expected with a set and O(n log n) with sorting. Mention both, and pick the set unless memory is tight.

A server sees 1 billion requests a day. You want the 10 slowest. What's the best approach?

Right. For each request, compare it with the fastest of your current top 10 (the heap's top). If it's slower, swap it in: O(log 10) work, which is basically constant. One pass, tiny memory, and it works on a stream that never ends. Quickselect is O(n) too, but it needs all billion items in memory at once.

Sorting a billion items to keep 10 does a huge amount of work you throw away, and needs the whole billion in memory. Quickselect avoids the sorting but still needs everything in memory. A min-heap of size 10 holds your current "top 10 slowest"; its top is the fastest of them. Each new request either beats that and replaces it (O(log 10)), or is ignored. One pass, 10 items of memory, works on a live stream.

11What to say in the interview

When sorting comes up, a strong answer sounds like this:

  1. Say why sorting helps: "If I sort by start time, overlapping meetings end up next to each other, so one pass merges them."
  2. Say the cost: "Sorting is O(n log n), and the scan is O(n), so overall O(n log n). Python's sort uses O(n) extra memory."
  3. Check if you can do better: "Do we need everything sorted, or just the top k? If just the top k, a heap gets O(n log k)." Or: "The keys are ages, so counting sort would make this O(n)."
  4. Mention stability if ties matter: "Python's sort is stable, so equal start times keep their input order."

If you're asked to implement a sort, merge sort is the safest to write correctly under pressure. If you choose quicksort, say "random pivot" and "three-way partition for duplicates" before anyone asks.

Go deeper: follow-up questions interviewers like
  • "How unsorted is this list?" Count inversions with merge sort: when you take an item from the right pile, it jumps ahead of everything left in the left pile. O(n log n). That's exercise 5.
  • "Can quickselect be O(n) worst case?" Yes: median of medians picks a pivot that's guaranteed decent. It's slow in practice, so libraries use introselect: quickselect that switches to median of medians if it's going badly.
  • "What does comparing cost?" Comparing two strings of length L can take L steps, so sorting n strings is O(L · n log n). Same for building anagram keys.
  • "What if the data is spread over many machines?" Sample the data to choose split points, send each range to one machine, sort locally, and concatenate (sample sort / range partitioning, which is what MapReduce's shuffle and the TeraSort benchmark do).
  • "Every item is at most k places from where it belongs." Slide a min-heap of size k + 1 across the list: O(n log k).
  • Python details. A key= function runs once per item, not once per comparison. For "descending by score, ascending by name", sort by name first, then stably by score with reverse=True (which keeps stability), or use a key like (-score, name) when the score is a number.

✓What to remember

  1. Sorting is a one-time O(n log n) cost that makes many later questions cheap: neighbors, binary search, two pointers, intervals.
  2. Insertion sort: O(n²) in general, about O(n) when nearly sorted. Stable, tiny overhead.
  3. Merge sort: split, sort halves, merge. log n levels × n per level = O(n log n) always. Stable. O(n) extra memory.
  4. Quicksort: partition around a pivot. O(n log n) average, O(n²) with bad pivots. Use a random pivot and three-way partitioning. In place, fastest in practice, not stable.
  5. No comparison sort beats n log n: n! orders, yes/no answers, log₂(n!) ≈ n log n.
  6. Counting and radix sort beat it by not comparing: O(n + k) for small integer keys.
  7. Stable means ties keep their order. Sort by the least important key first, or use a tuple key.
  8. Need only part of the order? Quickselect (k-th item, average O(n), O(n²) worst) or a size-k heap (top k, O(n log k)).

✎Exercises

Do the warm-ups on paper first. The coding exercises are in exercises/sorts.py. Their tests count every comparison you make, so a correct but slow sort fails. Run them with python3 -m pytest -k sorts.

Warm-up · pen and paper

1. Trace it by hand

Sort [5, 2, 8, 1, 9, 3] three times on paper: with insertion sort (write the list after each card is inserted), merge sort (draw the split levels and each merge), and quicksort with the last item as pivot (write the list after each partition). Count comparisons for each.

Warm-up · pen and paper

2. Pick the sort

Which sort, and why? (a) 50 items on a tiny embedded chip with almost no spare memory. (b) 2 TB of log lines on a machine with 16 GB of RAM. (c) A list that's sorted except for 20 new items appended at the end. (d) 100 million test scores from 0 to 100. (e) Customer records that are already sorted by signup date, and you need them by country with signup order kept inside each country.

Answers

(a) Insertion sort (tiny n, O(1) memory) or heapsort. (b) External merge sort: sort chunks that fit comfortably (say 8–10 GB), write out ~200–250 sorted runs, then merge them all at once with a heap holding the front line of each run. Every line is read and written twice. (c) Sort the 20 new items and merge them in: O(n + k log k). Timsort does roughly this on its own. Insertion sort works too, but each new item may slide nearly the whole list, so it's about 20·n: fine for 20, bad for 20,000. (d) Counting sort: k = 101, so O(n). (e) Any stable sort by country; Python's sorted(records, key=lambda r: r.country).

Warm-up · pen and paper

3. Break the quicksort

Write down an input of 8 numbers that makes "first item as pivot" quicksort do the most comparisons. How many does it do? Then write one that makes it do the fewest. Then explain in two sentences why a random pivot means no input is the worst every time.

Core · code

4. merge_sort(items), returns a new list

Split, sort the halves, and write the merge yourself. The test checks stability (when the two fronts are equal, take from the left pile!) and that you use at most n log₂ n comparisons. Avoid list.pop(0): it shifts every remaining item, a hidden O(n).

Core · code

5. count_inversions(items) in O(n log n)

Count pairs i < j with items[i] > items[j]: how unsorted the list is (it's the "out-of-order pairs" from section 2). Checking every pair is n². Instead, ride along with merge sort: whenever you take an item from the right pile, it jumps ahead of every item still waiting in the left pile. The test allows n log₂ n comparisons.

Core · code

6. quicksort(items), in place, random pivot

The test throws five kinds of input at it, including already sorted and all items equal. The simple (Lomuto) version passes the first and fails the second. Read the "Go deeper" box in section 4 when it does.

Core · code

7. counting_sort(items, key, max_key), O(n + k)

Sort people by age without ever comparing two people. The test's items raise an error if you compare them, and it counts calls to key(), so a loop over every possible key for every item (O(n · k)) fails. It must be stable, so place items by walking the input from left to right.

Core · code

8. merge_intervals(intervals)

The classic "sort then scan". Sort by start, then walk through: if the next interval starts before (or exactly when) the current one ends, stretch the current one's end to the larger of the two ends (the next one may sit entirely inside it); otherwise start a new one. The test counts comparisons, so merging pairs over and over (n²) fails.

Core · code

9. kth_smallest(items, k) with quickselect

Partition like quicksort, then only keep going on the side that contains position k. The test allows about 10n comparisons for n = 20,000 (best of 3 runs, since quickselect is random); sorting the whole thing needs about 13n, so it fails. Partition in one pass: three separate list comprehensions cost 3 comparisons per item and can blow the budget. It also tests lists full of equal items.
