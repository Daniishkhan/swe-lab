Chapter 2 · Part 12

Finding a needle fast

P1 comes up in coding and design roundsabout 55 minutes10 quick checks · 8 exercises

"Does this text contain that pattern?" is one of the most common questions a program asks. Python answers it with in, and you should use in at work. But the ideas behind fast string search show up far beyond in: rsync, backup deduplication, plagiarism checkers and "find the longest repeated block" all run on the same trick. Interviewers ask about it to see whether you can spot work that's being thrown away and get it back.

By the end you'll be able to

  1. Say why the obvious search costs n·m on bad input, with the input that does it.
  2. Explain a rolling hash as "a window of text is a number, and sliding the window updates the number in one step".
  3. Choose a modulus and base, say what a collision is, and say what Rabin-Karp costs on average and in the worst case.
  4. Explain KMP's failure table in one sentence ("how much of what I matched is still useful") and why the search never moves back.
  5. Pick the tool: in, Rabin-Karp, KMP, Aho-Corasick or a suffix array, and name real systems that use rolling hashes.

How to read this: top to bottom. You should know Big-O, hash maps and binary search. Answer each quick check before reading on; a wrong answer gets you a second explanation. "Go deeper" boxes are optional on a first read.

1The problem: one nasty request

A web firewall checks every request body for a known attack signature: 1,000 bytes long. Normal requests are a few kilobytes, and the check takes microseconds.

Then someone sends a 10 MB body that is nothing but the letter a, and the signature they know you check for happens to be 999 a's followed by a b. The firewall's CPU goes to 100% and stays there. Ten such requests a second and the site is down, without any attack code ever reaching the servers behind it.

Here's what happened. The firewall's search is the obvious one: line the signature up at position 0 and compare character by character; on a mismatch, move it one position right and start over. On normal text, the very first character usually mismatches, so each position costs about one comparison. On aaaa…a, each position matches 999 characters before the b fails. That's 10 million positions × 1,000 comparisons = 10 billion comparisons for one request. In C at about a billion a second, that's 10 seconds of CPU. In pure Python, several minutes.

This is called an algorithmic complexity attack: the attacker doesn't overwhelm you with traffic, they pick the input that hits your worst case. It's the reason "the average case is fine" isn't a good enough answer for code that reads untrusted input.

The text is n characters and the pattern is m characters. On ordinary English text, the obvious search does roughly how many comparisons?

Right. On real text the first character of the pattern mismatches at most positions, so most positions cost one comparison, a few cost two or three. That's why the obvious search is fine in practice and why the bad case is easy to miss in testing. n·m is the worst case, and an attacker can choose it.

Picture searching for "needle" in a novel. At most positions the text doesn't even start with "n", so you compare one character and move on. Only where it does start with "n" do you look at a second character, and almost never at a sixth. So it's about one comparison per position: about n. n·m only happens when nearly every position matches almost all of the pattern, like aaaa…a against aa…ab. And you can't get away with m: every text position might be the start, so you must at least look at each one.

2The obvious way, and where the work goes

Here's the obvious search as code. It's correct, and on most inputs it's fast.

def naive_find(text, pattern):
    n, m = len(text), len(pattern)
    hits = []
    for i in range(n - m + 1):            # every possible start
        j = 0
        while j < m and text[i + j] == pattern[j]:
            j += 1                         # the match grows by one
        if j == m:
            hits.append(i)
    return hits                            # worst case: (n-m+1)*m compares

Step through it on a small version of the attack: text aaaaaaaaab (10 characters), pattern aaab (4). Watch the little counters above the text: they say how many times each text character has been read.

The obvious search on a bad input. Green = matched, yellow = being compared, red = mismatch. The number above each text cell counts how often that character has been read. Step with ▶| and watch the middle characters get read 4 times each.

Look at what it throws away. At start 0 it learned that text[0..2] are aaa. Then it moves to start 1 and reads text[1] and text[2] again, as if it had never seen them. There are two separate wastes here, and this chapter fixes each one:

  1. Each start costs up to m comparisons. What if checking one start cost one step, whatever m is? That's the idea behind Rabin-Karp (sections 3 to 5): compare one number instead of m characters.
  2. It forgets what it just read. After a mismatch, you already know the last few characters of the text: they're the part of the pattern you matched. What if you used that and never read a text character twice? That's KMP (sections 6 and 7).
The obvious search costs (n − m + 1)·m comparisons in the worst case: about 10 billion for a 10 MB text and a 1,000-character pattern. The waste is re-reading characters it has already seen.

Text is 1,000,000 a's. Which pattern makes the obvious search do the most work?

Yes. The search compares from the left, so a pattern that matches 999 characters before it fails costs 1,000 comparisons at every one of about a million starts: a billion in total. Put the b first and every start fails on the first comparison: a million in total.

Ask: at one start, how far does the comparison get before it fails? The search compares from the left. With b first, it fails at once: 1 comparison per start, about a million in total. With 1,000 b's, same thing. With 999 a's then b, the first 999 comparisons all succeed and only the last one fails. That's 1,000 comparisons at every start, about a billion in total, 1,000× more. (A search that compares from the right end, like Boyer-Moore, would fail at once here; every fixed order has some bad input.)

3Fingerprints: compare one number, not m characters

Start with the simplest version of the problem: text made of digits. Say the text is 2314152673992 and you're looking for 31415.

Here's the thing to notice: a window of 5 digits is a number. The window starting at position 1 is the number 31,415. Checking "is this window the pattern?" is the same as checking "is this number 31,415?", and comparing two numbers is one step for a CPU, however many digits they have (as long as they fit in a machine word).

That's a fingerprint: a short value that stands in for a long thing. Like checking a person's fingerprint instead of comparing them feature by feature. If the fingerprints differ, the things differ, guaranteed. If they're equal, the things are very probably equal (we'll come back to "probably").

But there's a catch, and it's the whole problem. To get the number for a window, you have to read its 5 digits. Doing that for every window costs 5 per window again, the same m per start as before. Fingerprints only help if we can get each window's number without reading the whole window.

Turn each window into a number (a fingerprint) so that "is this window the pattern?" becomes one comparison. This only pays off if the next window's number can be computed from the previous one cheaply.

4Rolling the number along

Think of an odometer, or a ticker tape sliding past a 5-digit window. When the window moves one step right, one digit falls off the left and one appears on the right. Everything in between just shifts one place.

With numbers, that's three cheap operations. Going from window 23141 to window 31415:

  23141
- 20000      take the leftmost digit out (2 × 10⁴)
=  3141
×     10     shift everything one place left
= 31410
+     5      put the new digit in on the right
= 31415      the next window, without reading its other 4 digits

Each slide costs the same three steps, whether the window is 5 digits or 5,000. So computing all n − m + 1 window numbers costs about n steps in total, plus m to compute the first one.

From digits to any characters

Text isn't digits, but every character has a number: ord("a") is 97. Treat a string as a number written in some base B (instead of base 10), where each character is one "digit". For a window c₀c₁…c₍ₘ₋₁₎:

H = c₀·B^(m−1) + c₁·B^(m−2) + … + c₍ₘ₋₂₎·B + c₍ₘ₋₁₎

slide right by one:   H' = (H − c₀·B^(m−1)) · B + cₘ
                              ↑ take out     ↑ shift ↑ put in
def slide(h, out_ch, in_ch, B, top):   # top = B ** (m - 1), computed once
    h = h - ord(out_ch) * top          # take the first character out
    h = h * B                          # shift everything one place left
    return h + ord(in_ch)              # put the new last character in

This is a rolling hash: a hash of a sliding window that can be updated in O(1) when the window moves. (A hash is any function that squashes a big thing into a small number; you met them in the hash-maps chapter.) Using it to find a pattern, by comparing the pattern's hash with each window's hash, is the Rabin-Karp algorithm (Karp and Rabin, 1987).

A rolling hash treats the window as a number in base B. Sliding right is: subtract the leaving character's place value, multiply by B, add the new character. O(1) per step, so all windows cost O(n) together.

Base 10, window size 4. The window is 7182 and the next digit is 8. What do you compute?

Right. The 7 is worth 7 × 10³ = 7000 because of where it sits, so that's what you subtract. Then shift and add. In general you subtract c₀ · B^(m−1), and you compute B^(m−1) once, before the loop.

Read the window as an odometer: 7, 1, 8, 2. The 7 falls off the left, everything else moves one place left, and 8 comes in on the right: 1, 8, 2, 8 = 1828. Just multiplying by 10 keeps the 7 (now 5 digits). Subtracting 7 is wrong because the 7 isn't worth 7 here: it's in the thousands place, worth 7 × 10³ = 7000. The leaving character is always worth c₀ · B^(m−1).

5The numbers get huge: modulus, collisions, checking

There's a problem with the formula. A 1,000-character window in base 256 is a number with 1,000 "digits": about 8,000 bits. A CPU word holds 64. In C or Java the number overflows. In Python it doesn't (Python's integers grow as needed), but then every subtract and multiply touches all 8,000 bits, and each slide costs time proportional to m again. We're back where we started.

The fix: keep only the remainder after dividing by some number M, the modulus. Do every step "mod M" (in Python, % M), and the numbers never grow past M. Remainders work with + , − and × , so the slide formula still works, step by step, on the remainders.

The price: now different windows can have the same remainder. 31415 and 67399 are different numbers, but both leave remainder 7 when divided by 13. When two different strings get the same hash, that's a collision. So a matching hash no longer proves a match. It only says "worth a look". Rabin-Karp then checks the window character by character. A hash match that turns out to be false is called a spurious hit.

Watch it on the digits example with M = 13. The pattern 31415 has hash 31415 mod 13 = 7.

Choosing the modulus and the base

Thirteen is a terrible modulus: about 1 in 13 windows would be a spurious hit. Real code picks:

  • A big prime M. Common choices: 10⁹ + 7 (products of two remainders fit in 64 bits), or 2⁶¹ − 1 (a prime, and in Python big products are fine). Prime matters because it's what makes the guarantee below work.
  • A random base B, picked fresh each run, between 256 and M − 1. Then for any two different strings of length m, the chance they collide is at most (m − 1)/M. With M = 2⁶¹ − 1 and m = 1,000, that's about 4 × 10⁻¹⁶ per comparison: you'd need over a quadrillion windows before you expect even one spurious hit.

Why random? With a fixed, published base and modulus, an attacker can work out strings that collide and send them, just like the firewall attack. A random base means they'd have to guess your base. (The C habit of letting 64-bit arithmetic overflow, which means "mod 2⁶⁴", is especially bad: 2⁶⁴ isn't prime, and there are known strings, built from the Thue–Morse sequence, that collide for every base.)

Keep the hash mod a big prime M so the numbers stay small. Now different windows can collide, so every hash match must be checked character by character. A random base makes collisions about as likely as m/M, whatever the input.

A coworker's Rabin-Karp reports a match whenever the hashes are equal, without checking. It uses M = 10⁹ + 7. What's the problem?

Right. There are far more possible windows than there are remainders below 10⁹ + 7, so some different windows must share a hash. With a random base it's rare (about m/M per window), but a search over a billion windows will likely hit some, and with a fixed base an attacker can force them. It can never miss a real match: equal strings always have equal hashes. Checking costs m only when the hashes agree.

Count first. There are 26¹⁰ possible 10-letter windows (about 10¹⁴) and only about 10⁹ remainders, so on average 100,000 different windows share every hash value. Equal hashes can't mean equal strings. The other direction is safe: two equal strings always produce the same hash, so a real match is never skipped. Mistakes go one way only: false "found" reports. That's why Rabin-Karp checks the characters whenever the hashes agree.

Go deeper: why the collision chance is at most (m − 1)/M

Take two different strings x and y of length m. H(x) − H(y) = (x₀ − y₀)·B^(m−1) + … + (x₍ₘ₋₁₎ − y₍ₘ₋₁₎). Read that as a polynomial in B: it isn't all zeros (the strings differ somewhere) and its degree is at most m − 1. A collision means B is a root of it, mod M.

When M is prime, arithmetic mod M behaves like ordinary arithmetic with fractions, and a polynomial of degree d that isn't zero has at most d roots. So at most m − 1 of the M possible bases cause a collision. Pick B at random and the chance is at most (m − 1)/M. That's the whole proof, and it's why M must be prime: mod 2⁶⁴ a polynomial can have a huge number of roots.

Want even smaller odds without bigger numbers? Use two independent hashes (two moduli or two bases) and compare both; the collision chances multiply. A Rabin fingerprint, strictly, uses polynomials over bits (GF(2)) instead of numbers mod a prime; same idea, cheaper in hardware, and it's the version backup systems often use.

Expected versus worst case

Rabin-Karp's cost is: m to hash the pattern and the first window, 1 per slide, and m for every window whose hash matches. So:

  • Expected O(n + m) when there are few real matches, with a random base and a big prime: spurious hits are so rare that their checking costs nothing on average.
  • O(n + m + (number of matches) · m) in general, because every real match is checked. Text aaaa…a and pattern aaa…a match at almost every position, and Rabin-Karp checks them all: n·m again.
  • O(n·m) worst case with a bad hash (tiny M, fixed base under attack), because then spurious hits are everywhere.

Rabin-Karp with a good random hash searches for aaaa (m = 4) in a text of a million a's. How much work?

Right. Almost every window is a real match, every hash match gets checked, and each check costs m = 4. That's O(n + matches · m). With m = 1,000 it would be a billion. If you only need to know whether it occurs, stop at the first match; if you need all of them, KMP reports each in O(1).

Follow one window. Its hash matches the pattern's (it really is aaaa), so Rabin-Karp checks its 4 characters to be sure. That happens at nearly all of the million positions: 4 million comparisons, plus a million slides. The rolling part is O(n); the checking part is (number of matches) × m. It's not n² either: each check is only m long, not n.

6KMP: use what you already know

Now the second waste: forgetting. Go back to the moment a match breaks. Say the pattern is ababaca, you've matched ababa, and the next text character is b, not the c you needed.

The obvious search would move the pattern one step right and re-read the text. But stop and ask: what do you already know about the text? You know the last five characters you read: they're ababa, because they matched the pattern. You don't need to look at them again to know that. The question is just: where could the next match start?

text:     … a b a b a b …          the text you've read (the last 5 matched)
pattern:    a b a b a c a          broke here: text has b, pattern wants c

slide 1:      a b a b a …          needs "baba" = "abab": no
slide 2:        a b a b a c a      needs "aba" = "aba": yes, keep going from here
                    ↑
           compare pattern[3] with the SAME text character b

The match that's still alive must start with a piece of ababa that's also how the pattern starts. The longest such piece is aba: it's both the end of what you matched and the beginning of the pattern. So slide the pattern until its first three characters sit on top of those three text characters, and carry on comparing at the same text position. The text pointer never moves back.

Physical picture: the pattern is printed on a transparent strip you slide along the text. When a match breaks, you don't jump back to re-read the text; you slide the strip right to the first place where the part that's already under it still lines up, and you only ever look at the text through the slot at its current position.

The failure table

Notice that the answer, aba, came only from the pattern. The text added nothing we didn't know. So it can be worked out once, before the search, for every possible "matched k characters, then failed". That's the failure table (also called the prefix function, or π):

fail[i] = the length of the longest piece that is both a prefix (beginning) and a suffix (end) of pattern[0..i], not counting the whole thing. In words: "if I've matched the first i + 1 characters, how much of that is still useful as the start of a new match?"

The search then follows three rules, keeping k = how many pattern characters are matched right now:

  1. Read the next text character c (once).
  2. While k > 0 and pattern[k] ≠ c: fall back, k = fail[k − 1] (k characters matched means pattern[0..k − 1], so its entry is fail[k − 1]). You're sliding the strip; the text stays put.
  3. If pattern[k] = c, then k goes up by one. If k reaches m, you found a match ending here; report it and fall back to k = fail[m − 1] so overlapping matches are found too.
KMP searching for ababaca. The text pointer i only moves right. On a mismatch the pattern slides, using the failure table (bottom row; the purple entry is the one just used), and the same text character is compared again. Count the steps at the end: comparisons stay under 2 per text character.
After a mismatch, the matched part of the text is a copy of the start of the pattern, so you already know it. The failure table says, for each length matched, the longest part of it that can still start a match. The text is read once, left to right, and never again.
Explain it another way: the dance line

You're memorizing a dance: step, turn, step, turn, step, kick. You're following along with a video, and you've done step, turn, step, turn, step. The video does a turn instead of a kick. Do you start the whole dance over from the next move? No. You notice that your last three moves, step-turn-step, are also how the dance begins, and the video's turn fits after them as move four. You're already three moves in, and you continue from there.

The failure table is that "how many of my last moves also start the dance?" worked out ahead of time, for every point where you might get interrupted.

Pattern abcabd. You've matched abcab and the next text character isn't d. How many characters of the pattern are still matched after falling back once?

Right. The text you've seen ends in abcab. Its longest end that is also a start of the pattern is ab (fail[4] = 2). So the pattern slides so its ab lies under the text's ab, and you compare pattern[2] = c with the same text character. If that fails too, fall back again: fail[1] = 0.

Write out what you know: the text's last five characters are a b c a b. Now try each slide of the pattern and ask whether its start agrees with what's already under it. Slide 1: pattern starts abca, text there is bcab: no. Slide 2: abc vs cab: no. Slide 3: ab vs ab: yes. So 2 characters are still matched. Starting over at 0 throws away a real possibility (a match could start at that ab); sliding 1 step and claiming 4 matched assumes text you haven't checked.

What is the failure table of aaaa?

Right. For aa, the longest proper start that's also an end is a: 1. For aaa it's aa: 2. "Proper" means not the whole thing, so it's always one less here. This is the case that makes KMP linear on aaaa…a: after a full match it keeps 3 of 4 characters, so the next match costs just one comparison.

Take the definition one entry at a time. fail[i] looks at pattern[0..i] and asks for the longest piece that's both its start and its end, not counting the whole piece (otherwise every answer would be "all of it"). a: nothing shorter than itself: 0. aa: a is both start and end: 1. aaa: aa: 2. aaaa: aaa: 3. [0, 0, 0, 0] would mean no overlap at all, like in abcd; [1, 2, 3, 4] counts the whole string, which isn't allowed.

7Building the table, and why it's linear

The table is KMP run on the pattern itself

To fill fail[i], you need the longest start of the pattern that ends at position i. That's the same question the search asks about the text ("how much of the pattern ends here?"), with the pattern playing the role of the text. So you build the table by running the same three rules over the pattern, starting from position 1 (fail[0] is always 0), and using the entries you've already filled to fall back. Each entry needs only earlier ones, so the table builds itself left to right. That's exercise 5.

Why the fall-back loop can't blow up

Step 2 is a while loop. Inside a for loop. That smells like n·m. It isn't, and the argument is a nice one to have ready.

Think of k as the height of a stack of plates. Each text character adds at most one plate (step 3: k goes up by at most 1). Each fall-back removes at least one plate (fail[k − 1] is always less than k). You can't remove plates you never added. So over the whole search, the total number of fall-backs is at most n. Adding the one comparison per text character, KMP does at most 2n comparisons, plus at most 2m to build the table. O(n + m), worst case, for every input.

This kind of argument, "something goes up by at most 1 per step and every expensive step makes it go down, so the expensive steps are paid for in advance", is called an amortized or potential argument. You saw it with the monotonic stack and with dynamic arrays; here it is again.

text "aaaaaaab", pattern "aaab" (fail = [0, 1, 2, 0]):
text:     a  a  a  a  a  a  a  b
k after:  1  2  3  3  3  3  3  4   ← a match; then k falls back to fail[3] = 0
                   ↑  each 3 → 3 hides one fall-back (3 → 2) and one climb (2 → 3)
Building the failure table is KMP on the pattern against itself. The total number of fall-backs can't exceed the total number of climbs, which is at most one per character, so KMP is at most about 2n + 2m comparisons on every input.

In one step of KMP, the fall-back loop runs 500 times. What does that tell you?

Right. A long fall-back is possible in one step (for example, after matching 500 characters that all fail together). But each fall-back lowers k by at least one, and k only rose by one per text character. So 500 fall-backs now means 500 cheap steps before. Over the whole search, at most n fall-backs: the total is still linear.

Use the plates picture. k is a stack of plates. Each text character adds at most one plate. Each fall-back takes at least one away. If 500 came off in one step, at least 500 went on earlier, one per character. So yes, one step can be slow, but the slow steps are paid for by earlier cheap ones, and across the whole text there can be at most n fall-backs. Big-O of the total is what matters: O(n + m). Nothing is broken: long fall-backs happen with correct tables.

Go deeper: the Z-function, Boyer-Moore, and Aho-Corasick

Z-function. Another linear-time tool: Z[i] = length of the longest common prefix of s and s[i:]. Computing it reuses earlier answers through a "rightmost match box", the same "don't re-read what you know" idea. To search, compute Z on pattern + "\0" + text (a separator that appears in neither) and report every position where Z equals m. Many people find Z easier to get right under pressure than KMP.

Boyer-Moore compares from the right end of the pattern and, on a mismatch, can jump ahead by up to m. On ordinary text it can read as few as n/m characters: it's sublinear, which is why grep-style tools use variants of it for one fixed string. Its simpler cousin, Horspool, keeps only the "bad character" skip table.

Aho-Corasick is KMP for many patterns at once. Put all the patterns in a trie (chapter 1), and give every trie node a failure link: "the longest suffix of what I've matched that is also a path in the trie". Then one left-to-right pass finds every occurrence of every pattern in O(text + total pattern length + matches). Intrusion detection systems, antivirus scanners and grep -F with a file of patterns use this.

What Python's in does

pattern in text, text.find(pattern) and text.count(pattern) run in C, inside CPython's "fastsearch". Which loop it runs depends on the sizes:

  • Small inputs (text under 2,500 characters, or pattern under 100 and text under 30,000) and any pattern under 6 characters: a simple loop in the Boyer-Moore-Horspool style. It checks the last character of the window first, and keeps a 64-bit mask of the pattern's characters (a mini Bloom filter) so it can jump a whole pattern length when the next text character can't be in the pattern. Its worst case is n·m, but these limits keep that small: at most 5 comparisons per character for short patterns, a few million in total otherwise.
  • Everything bigger, since Python 3.11: the two-way algorithm (Crochemore and Perrin, 1991), linear in the worst case with O(1) extra memory. (If the pattern is more than about a third of the text, it starts with the simple loop and switches to two-way once it has wasted about m/4 comparisons.) Python 3.10 added two-way but used it only for patterns of 100 characters or more; 3.11 set the limits above.

glibc's strstr and memmem use two-way for long needles too. So the firewall attack from section 1 doesn't work on Python's in today. One exception worth knowing: str.rfind and str.rindex (search from the right) still use only the simple loop. On 10 MB of a's, searching for 500 a's, a b, then 499 a's takes about 0.05 seconds with in and about 2 seconds with rfind.

In an interview, that changes what you say. If the task is "does s contain t", write t in s and say why it's fine: "it's C, and since 3.11 CPython switches to a linear worst-case algorithm (two-way) on anything but small inputs." Write KMP or Rabin-Karp yourself only when they ask you to, or when the problem needs something in can't give you: matches in a stream you can't rewind, many substrings compared against each other, or a repeated block of unknown content.

An interviewer asks: "Given a list of a million log lines, return the lines that contain the string OutOfMemoryError." What's the best first answer?

Right. One fixed pattern, strings already in memory: the built-in is the right tool, it's faster than anything you'd write in Python, and you've shown you know why it's safe. Ask what the problem actually needs: one pattern, text already in Python strings. Python's in is written in C, so it's 10 to 100 times faster than KMP or Rabin-Karp written in Python, and since 3.11 it switches to a linear worst-case algorithm (two-way) on anything but small inputs. Writing your own here costs time and adds bugs for no gain. Senior answers use the library and can explain what's inside it. Bring out KMP or Rabin-Karp when the problem changes: a stream, many patterns, or comparing substrings with each other.

9Rolling hashes in the wild

KMP is about searching for a known pattern. Rolling hashes do more: they let you compare any window with any other window in O(1). That's where they really earn their keep.

The longest repeated piece of text

"Find the longest substring that occurs twice" (LeetCode 1044) has no pattern to search for. Two ideas crack it:

  1. Binary search on the length. If some piece of length L repeats, then a piece of length L − 1 repeats too (drop the last character of both copies). So the answers "is there a repeat of length L?" go yes, yes, …, yes, no, no: exactly the shape binary search on the answer needs (chapter 02.03).
  2. One length in O(n). Roll a window of length L across the text and put each hash in a hash set. A hash you've already seen is a repeat (after checking, or trusting a 61-bit hash).

About log₂ n lengths × O(n) each = O(n log n) expected. For n = 20,000, that's 15 passes instead of the 200 million pairs of start positions. That's exercise 6.

Comparing any two substrings in O(1)

Store the hash of every prefix: P[k] = H(text[0..k)). Then the hash of any piece text[i..j) is P[j] − P[i]·B^(j−i) (mod M): the prefix up to j, minus the prefix up to i shifted into place. After O(n) setup, "is text[i..i+L) equal to text[j..j+L)?" is two subtractions and a comparison. Combined with binary search on L, that gives the longest common prefix of any two suffixes in O(log n), which is enough for palindromes, sorting suffixes and many "compare pieces of one big string" problems. That's the third part of exercise 4.

rsync: send only what changed

You have a 1 GB file; the server has yesterday's version. rsync makes the server cut its copy into blocks (say 1 KB each) and send two hashes per block: a weak rolling checksum and a strong one (MD5, or xxHash in newer versions). Your side then slides a 1 KB window over your file one byte at a time, rolling the weak checksum in O(1) per byte. When it matches a block's weak checksum, it confirms with the strong one, and sends "you already have block 42" instead of the bytes. Without rolling, checking every byte offset would cost a full block hash per byte: 1,000× more work.

Content-defined chunking: deduplication that survives an insert

Backup systems store each chunk of data once, keyed by its hash. If you cut files into fixed 8 KB chunks, inserting one byte at the start shifts every boundary, and every chunk looks new:

fixed-size cuts, before:  [the quick b][rown fox ju][mps over th]
after inserting "X":      [Xthe quick ][brown fox j][umps over t]   every chunk changed

content-defined, before:  [the quick ][brown fox ][jumps over]
after inserting "X":      [Xthe quick ][brown fox ][jumps over]   only the first changed

The fix: roll a hash over a small window (LBFS used 48 bytes) and cut wherever the hash's low 13 bits are all zero. That happens about once every 2¹³ = 8,192 bytes, so chunks average 8 KB, but the cut points depend on the content near them, not on their position. An insert only moves the cuts right next to it. restic, Borg and many other backup tools use this (with Rabin fingerprints or buzhash as the rolling hash).

Plagiarism detection

MOSS, the Stanford code-plagiarism checker, hashes every k-gram (every run of k tokens) of each submission with a rolling hash, then keeps only the smallest hash in each window of w consecutive hashes. This is called winnowing. The kept hashes are the document's fingerprints; two submissions that share many fingerprints share text. Winnowing guarantees that any shared run of at least w + k − 1 tokens is caught, while storing only a small fraction of the hashes.

Rolling hashes make "compare this window with that window" O(1). That powers binary-search-plus-hashing for repeats, O(1) substring equality, rsync's delta transfer, content-defined chunking for deduplication, and plagiarism fingerprints.

A backup tool cuts files into fixed 8 KB chunks and stores each distinct chunk once. You add one line to the top of a 1 GB log file. Roughly how much new data does the next backup store?

Right. Fixed cuts are tied to byte positions, and the insert moved every byte. Every chunk now has different contents and a different hash. Content-defined chunking puts the cuts where the data says (where a rolling hash's low bits are zero), so the cuts move along with the data and only the chunk around the new line changes.

Picture the 8 KB cuts as marks every 8,192 bytes on the file. Insert a 100-byte line at the top: every byte after it moves 100 places, but the marks stay where they were. So every chunk now holds different bytes, gets a different hash, and has to be stored again: about 1 GB. (Hashes don't ignore small changes; a one-byte change gives a completely different hash.) Content-defined chunking fixes this by placing cuts based on the bytes nearby, so they move with the data.

10What to say in the interview

When string search comes up, a strong answer sounds like this:

  1. Name the brute force and its trap: "Check every start: O(n·m) worst case, for example aaa…a against aa…ab. On normal text it's about O(n), which is why it's easy to miss."
  2. Use the library when it fits: "For one pattern I'd use in; it's C, and since 3.11 CPython uses the two-way algorithm, linear in the worst case, on anything but small inputs."
  3. Pick the idea by the shape of the problem: "Comparing many windows with each other: rolling hash, O(n) for all windows. A worst-case guarantee or a one-pass stream: KMP. Many patterns: Aho-Corasick."
  4. Say the hashing details before they ask: "Mod a big prime like 2⁶¹ − 1, random base, and I check every hash match, so it's never wrong, only occasionally slower. Expected O(n + m), worst O(n·m) if there are many real matches."
  5. For KMP, one sentence: "After a mismatch, the matched part of the text is a copy of the pattern's start, so a precomputed table says how much of it is still useful, and I never move back in the text. Fall-backs are paid for by earlier matches, so it's at most 2n comparisons."
Go deeper: follow-up questions interviewers like
  • "Search for 10,000 patterns of the same length." Put the patterns' hashes in a set and roll once over the text: O(n + total pattern length) expected. Different lengths: one pass per distinct length, or Aho-Corasick.
  • "Find a 2-D pattern in an image." Roll a hash along each row for windows of the pattern's width, then roll a second hash down the columns of those row-hashes. O(rows × columns) for all positions.
  • "Search a 1 TB file on 100 machines." Split it into pieces that overlap by m − 1 characters, so a match that crosses a boundary is seen whole by one machine; each machine runs any linear search on its piece. The same overlap rule applies to a stream read in chunks.
  • "Is string B a rotation of string A?" Same length, and B occurs in A + A. One search.
  • "Shortest palindrome by adding characters in front." Find the longest palindromic prefix: run the failure table on s + "#" + reversed(s); its last entry is the length of the longest palindromic prefix, and you prepend the reverse of the rest. Or compare forward and backward rolling hashes.
  • "What's a suffix array?" All suffixes of the text, sorted, stored as their start positions. Neighbors in that order share the longest prefixes, so the longest repeated substring is the largest LCP (longest common prefix) between neighbors. Built in O(n log n) (or O(n) with SA-IS); suffix trees hold the same information as a radix tree of all suffixes (chapter 1's tries mentioned them).
  • "Is Java's indexOf safe?" It's a plain scan (well tuned, but O(n·m) worst case). Know that your language's built-in can differ from Python's.
  • Unicode. Python strings index by code point, so ord() of a character can be up to 1,114,111. That's fine for the hash (M is far bigger), but "base 256" doesn't mean "bytes" here. Search bytes and text consistently: "é" is one character but two UTF-8 bytes.

✓What to remember

  1. The obvious search is about n on normal text but (n − m + 1)·m on aaa…a vs aa…ab. The waste is re-reading characters already seen.
  2. A window of text is a number in base B. Sliding it is: subtract the leaving character × B^(m−1), multiply by B, add the new character. O(1) per step.
  3. Keep it mod a big prime (2⁶¹ − 1 or 10⁹ + 7) with a random base. Then two different strings collide with probability at most (m − 1)/M.
  4. Equal hashes mean "probably equal": check the characters. Rabin-Karp is O(n + m) expected, plus m per match; O(n·m) worst case.
  5. KMP's failure table: fail[i] = the longest proper prefix of pattern[0..i] that's also its suffix, "how much of what I matched is still useful". The text is read once, never backwards.
  6. KMP is at most about 2n + 2m comparisons on every input: each fall-back is paid for by an earlier climb. The table is KMP of the pattern on itself.
  7. In Python 3.11+, in / find / count are C and use a linear worst-case algorithm (two-way) on anything but small inputs; rfind doesn't. Say so, and use them.
  8. Rolling hashes compare any window with any other in O(1): longest repeat (binary search + hash set), substring equality via prefix hashes, rsync, content-defined chunking, plagiarism fingerprints.

Warm-up · pen and paper

1. Roll a hash by hand

Text 41592, window size 3, base 10, modulus 7. Compute the hash of the first window directly, then get the other two by rolling (B^(m−1) mod 7 = 100 mod 7 = 2). Check each against the window's number mod 7. Then: the pattern is 305. Which window is a spurious hit?

Answers

415 mod 7 = 2. Roll: (2 − 4·2)·10 + 9 = −51, and −51 mod 7 = 5 (159 mod 7 = 5 ✓). Roll: (5 − 1·2)·10 + 2 = 32, and 32 mod 7 = 4 (592 mod 7 = 4 ✓). The pattern 305 mod 7 = 4, the same as window 592: a spurious hit. Checking the three digits rules it out. (Python's % always gives a result between 0 and M − 1, even for −51; in C or Java you'd add M first.)

Warm-up · pen and paper

2. Fill a failure table

Write the failure tables of aabaaab and abcabcd. Then: searching for aabaaab, you've matched aabaa and the next text character is b, not a. What is k after falling back, and does the b then match?

Answers

aabaaab: [0, 1, 0, 1, 2, 2, 3]. abcabcd: [0, 0, 0, 1, 2, 3, 0]. Matched 5 characters, so fall back to fail[4] = 2 (the aa at the end of aabaa is the pattern's start). pattern[2] = b matches the text's b, so k becomes 3, all without re-reading any text.

Warm-up · pen and paper

3. Pick the tool

Which tool, and why? (a) In a Python interview, check whether one string contains another. (b) Block 20,000 banned phrases in chat messages. (c) Find any 100-character block that appears twice in a 1 GB log. (d) Count a pattern in a network stream you can't rewind or store, with a worst-case guarantee. (e) Answer a million "are these two pieces of this one big string equal?" questions. (f) Upload a new version of a large file when the server has the old one.

Answers

(a) in, and say it's C and linear in the worst case (two-way, since 3.11). (b) Aho-Corasick: one pass for all patterns. (c) Rolling hash of every 100-character window into a hash set, checking matches: O(n) expected (on disk, process it in parts or keep only the hashes). (d) KMP: O(m) state, reads each character once. (e) Prefix hashes: O(n) setup, O(1) per question. (f) rsync's rolling checksum plus a strong hash per block.

Core · code

4. window_hashes, find_all and SubstringHasher (rabin_karp.py)

Build the rolling hash, then Rabin-Karp on top of it, then O(1) substring equality from prefix hashes. The test checks your hashes against the exact formula, passes a tiny modulus like 7 to make sure you check every hash match, allows about 3 reads per text character for all windows (recomputing each window costs n·m), and checks that equal() reads zero characters. Each test also has a 3-second cap, so recomputing every window from a list of ord() values (which the read count can't see) fails too.

5. failure_table, kmp_find_all and count_in_stream (kmp_search.py)

The table in O(m), the search in O(n + m) worst case, and the same search over a stream of chunks. The test's text raises an error if you ever read an earlier position after a later one, budgets about 8 reads per pattern character for the table (trying every prefix costs m²), streams megabytes of aaa…a under a time cap, and measures your peak memory (keeping the whole stream fails). A 300,000-character pattern under a time cap catches a buffer of the last m characters that gets re-checked at every position.

6. longest_dup_substring(s) in O(n log n)

Binary search on the length plus a rolling hash set (section 9). The test plants a 300-character repeat in 20,000 random letters and allows about 60 reads per character. A set of slices reads every slice in full, and trying lengths 1, 2, 3, … needs 19,999 passes on aaa…a (each test has a 5-second cap), so both fail.

7. Design deduplicating backups
