Chapter 2 · Part 1

How fast is your code?

P0 asked almost everywhereabout 45 minutes9 quick checks · 9 exercises

Every coding interview has a moment where someone asks, "What's the complexity of that?" This chapter is about answering that question properly. That means knowing what to say, and also why it's true. Nothing here assumes you already know it. We start from zero and go deep.

By the end you'll be able to

  1. Explain why we count steps instead of timing code.
  2. Look at a piece of code and say its Big-O, including the tricky cases.
  3. Feel the difference between O(log n), O(n), O(n log n), O(n²) and O(2ⁿ).
  4. Talk about memory (space) as well as time.
  5. Explain "amortized" without hand-waving.
  6. Know when Big-O is lying to you, and how to check.

How to read this: go top to bottom, like a book chapter. Answer each quick check before reading on. If you get one wrong, you'll get the idea explained a different way. Grey "Go deeper" boxes are optional; skip them on a first read.

1The problem: will it finish?

You write a little function that checks a playlist for duplicate songs. You test it on your own 200-song playlist, and it answers instantly. It works.

Then your company wants to run it on the whole catalog: 100 million songs. Will it finish in a second? An hour? Next year?

You can't just try it and see. It might run for days before you find out, and in an interview there's no computer to try it on anyway. You need a way to predict how your code will behave on big inputs by looking at it.

Here are two correct ways to find a duplicate:

# Way A: compare every pair
def has_dup_a(songs):
    for i in range(len(songs)):
        for j in range(i + 1, len(songs)):
            if songs[i] == songs[j]:
                return True
    return False
# Way B: remember what you've seen
def has_dup_b(songs):
    seen = set()
    for s in songs:
        if s in seen:
            return True
        seen.add(s)
    return False

Both give the right answer. On 200 songs, both feel instant. So which one is "better"? That's the real question this chapter answers. The surprising answer: on 100 million songs, one of them finishes in seconds and the other takes about a month.

2Count steps, not seconds

The obvious idea is to time the code with a stopwatch. The trouble is that the time depends on things that have nothing to do with your code:

  • a fast laptop vs a slow one,
  • Python vs C,
  • whether Spotify is open in the background,
  • which exact songs are in the list.

We want a measure of the method, not the machine. So we count steps.

A step is any tiny action the computer does in roughly the same tiny amount of time: comparing two numbers, adding, reading one slot of a list, checking one item in a set. We don't care exactly how long a step takes. We only care how many steps there are.

Let's count. Here's the simplest possible loop:

def total(nums):
    t = 0               # 1 step
    for x in nums:      # the loop body runs n times
        t += x          #   1 step each time → n steps
    return t            # 1 step

If the list has n items, that's about n + 2 steps. Ten items, 12 steps. A million items, about a million steps.

Now Way A. The outer loop picks a song. The inner loop compares it with every song after it. For n songs, the number of comparisons is:

(n − 1) + (n − 2) + … + 1 = n(n − 1) / 2

That's the number of pairs you can make from n things. Way B looks at each song once, so about n steps (each "is it in the set?" check counts as one step; section 7 of the hash map page explains why that's fair).

A function loops through a list of n items and, for each item, prints it twice. Roughly how many steps?

Right. Two prints per item, n items: 2n. Hold that thought, because in the next section we'll see why we end up calling 2n just "n".

Count one item first: it gets printed twice, so 2 steps. Then multiply by how many items there are. Two steps × n items = 2n. It's not n², because there's no second loop going through the whole list again for each item.

3Only the growth matters

Let's put real numbers in. Imagine the computer does 10 million simple steps per second (roughly what Python manages).

On small inputs the difference doesn't matter. On big inputs it's everything. And notice what decided it: not the exact number of steps, but how fast the count grows as n grows.

The doubling test

Here's the single most useful way to feel growth. Ask: if I double the input, what happens to the work?

  • Way B: double the songs, double the steps. Work grows like n.
  • Way A: double the songs, and the pairs go up about four times (2n × 2n = 4n²). Work grows like n².

So we drop the details

Because only growth matters for big inputs, we throw away two things:

  1. Constant multipliers. 2n and n both double when n doubles. They grow the same way. So 2n is written O(n).
  2. Smaller terms. In n² + 100n, when n is a million, n² is a trillion and 100n is a hundred million: less than 0.01% of the total. It stops mattering, so n² + 100n is written O(n²).

Big-O describes how the number of steps grows as the input grows, ignoring constant multipliers and smaller terms. "This is O(n²)" means: double the input, and the work roughly quadruples.

Explain it another way

Think of two ways to travel: walking and driving. Walking gets a head start because you don't have to find your keys, back out of the garage, or park. For a trip to the corner shop, walking might even win.

But for a trip to another city, the head start is meaningless. What decides it is speed per mile. Big-O is about the long trip. The "head start" (constants, setup) only matters for short trips, meaning small inputs.

Which is bigger when n = 1,000,000: 5n + 1000 or n² / 100?

Yes. 5n + 1000 is about 5 million. n²/100 is 10¹² / 100 = 10 billion, which is 2,000 times bigger. The n² eats the small constant in front of it.

It's tempting to look at the numbers in front (5 vs 1/100). But plug in n = 1,000,000: 5n + 1000 ≈ 5,000,000, while n² / 100 = 1,000,000,000,000 / 100 = 10,000,000,000. The shape (n vs n²) wins over the constant once n is big. That's exactly why Big-O drops constants.

Go deeper: the formal definition, and Θ vs O

Formally, f(n) is O(g(n)) if there are constants c and n₀ such that f(n) ≤ c·g(n) for every n ≥ n₀. In words: past some point, f never grows faster than a constant times g.

Strictly, O is only an upper bound, so it's technically true that a linear function is also O(n²). The tight bound is written Θ (theta): f is Θ(g) if it's bounded above and below by constant multiples of g. Ω (omega) is the lower bound. In interviews and in industry, people say "O" and mean the tight bound. Use O, but give the tightest one you can justify.

4Meet the growth rates

Almost every algorithm you'll see falls into one of a handful of families. Learn each one with a picture from real life.

O(1): constant

The work doesn't depend on n at all. Reading nums[5] takes the same time whether the list has 10 items or 10 million, because the computer calculates exactly where slot 5 is in memory and jumps there. Like opening a book to page 200 when you know the page number.

O(log n): halving

Play "guess my number between 1 and 100". If you always guess the middle and I tell you "higher" or "lower", you throw away half the numbers each time. 100 → 50 → 25 → 13 → 7 → 4 → 2 → 1. Seven guesses.

log₂ n just means: how many times can you cut n in half before you reach 1? That's all a logarithm is here.

Halving a range of 64 numbers. Each step throws away half. 64 numbers need only 6 steps, because 2⁶ = 64.

The magic of log n is how slowly it grows: a million items takes about 20 halvings, and a billion takes about 30. Binary search and balanced trees live here.

O(n): linear

Look at every item once. Reading every page of a book. Summing a list, finding the max, Way B from our story.

O(n log n): "sort-like"

This is n multiplied by log n. It shows up when you do log n rounds of work and each round touches all n items. Good sorting algorithms work this way. It's only a little worse than linear: for a million items, log n ≈ 20, so it's about 20× the work of one pass.

O(n²): every pair

At a party of n people, everyone shakes hands with everyone else. That's n(n−1)/2 handshakes. Any time you see "compare each item with each other item", think n². Way A lives here.

O(2ⁿ): every subset

Ordering pizza with n possible toppings: each topping is either on or off, so there are 2 × 2 × … × 2 = 2ⁿ possible pizzas. Every new topping doubles the count. With 30 toppings that's over a billion pizzas. Trying every subset (backtracking without shortcuts) lives here.

O(n!): every ordering

The number of ways to seat n people in a row: n × (n−1) × … × 1. With 10 people, that's 3.6 million; with 20, it's more than the number of grains of sand on Earth. Trying every ordering lives here.

Problem statements tell you how big n can be. Since a second of Python is around 10⁷ steps, you can work backwards to what the interviewer expects:

A problem says n can be up to 100,000. Your first idea compares every pair. Is that OK?

Exactly. n²/2 = 5 × 10⁹ steps. Say the brute force out loud anyway (interviewers want to hear it), then say "that's too slow for 10⁵, so let's get to O(n log n) or O(n)."

Do the arithmetic, it's the whole trick: 100,000² is 10¹⁰, and half of that is 5 × 10⁹. At 10⁷ steps per second, that's 500 seconds. Even in C (around 10⁹ steps per second) it's several seconds. The size of n in the problem is a hint about which family of algorithm they expect.

About how many halvings does it take to get from 1,000,000 down to 1?

Right. 2¹⁰ ≈ 1,000, so 2²⁰ ≈ 1,000,000. Remember "2¹⁰ ≈ a thousand" and you can estimate any log in your head.

Halve it and count: 1,000,000 → 500,000 → 250,000 → 125,000 → … Each halving takes away a lot. A handy fact: 2¹⁰ = 1,024, about a thousand. So a million (a thousand × a thousand) is about 2¹⁰ × 2¹⁰ = 2²⁰. That's 20 halvings.

5Reading Big-O from code (the hard part)

Knowing the families is the easy part. The skill interviewers actually test is looking at code you've never seen and saying its complexity correctly. Here are the rules, from simplest to trickiest.

Rule 1: Steps one after another add, and the biggest wins

for x in nums: ...          # O(n)
for x in nums: ...          # O(n)
for x in nums:
    for y in nums: ...      # O(n²)

O(n) + O(n) + O(n²) = O(n²). Two separate loops are still O(n), not O(n²). They happen one after the other, not inside each other.

Rule 2: Loops inside loops multiply

If the inner loop runs m times for each of the outer loop's n runs, that's n × m. If both go over the same list, n × n = n².

Rule 3: Halving or doubling means log

i = n
while i > 1:
    i = i // 2       # halves every time → O(log n)

Any time the remaining work is cut by a fixed fraction each step, you get a log.

Rule 4: Recursion = (number of calls) × (work per call)

Draw the tree of calls. Count how many boxes there are and how much work each box does.

def fib(n):
    if n < 2: return n
    return fib(n - 1) + fib(n - 2)

Each call makes two more calls, so the tree roughly doubles at every level, about n levels deep. That's around 2ⁿ calls doing O(1) work each: O(2ⁿ). (It's actually about 1.6ⁿ, but that's still exponential.) It's slow because it solves the same small problems over and over. The dynamic programming chapter fixes exactly this.

Rule 5: Know what Python hides

One line of Python can secretly be a loop. These are the usual suspects:

Looks like one stepActually costsWhy
x in my_listO(n)checks items one by one
x in my_set / my_dict[k]O(1) on averagehashing jumps straight to the spot
my_list[a:b]O(b − a)slicing copies
my_list.pop(0), insert(0, x)O(n)every other item shifts over
s += "x" on a stringO(len(s))strings can't change, so a new one is built
sorted(my_list)O(n log n)it's a full sort
len(my_list), appendO(1)length is stored; append is amortized O(1) (section 7)

What's the complexity of this, for a list of n numbers?

result = []
for x in nums:
    if x not in result:
        result.append(x)

Right. x not in result walks the result list, which can grow to n items. One hidden loop inside a visible loop is n². Change result to a set (and keep order with a separate list) and it becomes O(n).

The trap is that in looks like a single step. On a list, Python checks each item until it finds a match, which is a loop you can't see. So for each of the n items, you might scan up to n items: n × n. Whenever you see in, ask "list or set?"

Rule 6 (the tricky one): a loop inside a loop is not always n²

This is where people lose points. Look carefully:

j = 0
for i in range(n):
    while j < n and nums[j] < nums[i] + 10:
        j += 1

It looks like n², but j never goes backwards. Over the whole run, j moves from 0 to n at most once. So the inner loop runs at most n times in total, not n times per outer step. Total: n + n = O(n).

The trick is to count the total work across the whole run, not the worst case for one iteration times the number of iterations. Sliding windows, two pointers and monotonic stacks all depend on this.

What's the complexity?

i = 0
while i < n:
    j = i
    while j < n and nums[j] == nums[i]:
        j += 1
    print(nums[i], "appears", j - i, "times")
    i = j

Yes. i jumps to j, so every index is visited by the inner loop exactly once in total. Two nested loops, O(n) total work. Spotting this is a senior-level signal.

Follow one index, say index 5. How many times does the inner loop touch it? Once, while j sweeps through the group containing it. After that, i = j jumps past the whole group, so index 5 is never visited again. Every index is touched once, so the total is O(n) even though the loops are nested. Don't count loops; count how many times each item gets touched.

Go deeper: the "levels × work per level" picture for recursion

Merge sort splits a list in half, sorts each half recursively, then merges them in one pass. Draw it: the top level has 1 problem of size n; the next has 2 of size n/2; the next has 4 of size n/4… Each level does a total of n work (merging), and there are log n levels (halving again). Total: n × log n.

The same picture explains binary search (log n levels, O(1) per level, so O(log n)) and the slow Fibonacci (n levels, but the number of calls doubles each level, so ~2ⁿ). This general method is called the recursion-tree method; the "Master Theorem" is a shortcut formula for it that you don't need to memorize for interviews.

6Space: memory counts too

Complexity isn't only about time. Space complexity asks how much extra memory your code needs as n grows. "Extra" means beyond the input you were given.

  • A few variables (a counter, a running total): O(1) space.
  • A set or dict that might hold every item (Way B's seen): O(n) space.
  • An n × n table: O(n²) space.

The hidden memory: recursion

Every function call that hasn't finished yet sits on the call stack, like a stack of plates. A recursion that goes n levels deep holds n plates at once, so it uses O(n) space even if it never creates a list. In Python the stack stops at about 1,000 levels by default, which is why deep recursion crashes with RecursionError.

The big trade: space for time

Way A uses O(1) extra space but O(n²) time. Way B uses O(n) space to get O(n) time. That's the most common trade in all of programming: remember things (use memory) so you don't have to redo work (save time). Caches, indexes and hash maps are all this trade.

A recursive function calls itself on n - 1 until it hits 0. It creates no lists. What's its space complexity?

Right. n calls are waiting on the stack at the deepest point. Interviewers love asking about this one.

Picture it: call(n) can't finish until call(n−1) finishes, which can't finish until call(n−2) does… At the bottom, all n calls are paused and waiting. Each paused call takes up a little memory (its plate on the stack). n plates is O(n) space.

7Amortized: the occasional expensive step

Here's a puzzle. A Python list stores its items in one solid block of memory. When the block is full and you append, Python has to:

  1. find a new, bigger block,
  2. copy every item over (that's n steps!),
  3. then add the new item.

So append is sometimes O(n). Yet everyone says append is O(1). Who's right?

The trick: grow by doubling

When Python grows the block, it doesn't add one slot; it makes it much bigger (we'll use doubling to keep the math simple). So the expensive copies happen at sizes 1, 2, 4, 8, 16, … and in between there are lots of cheap appends.

Add up all the copying to reach n items: 1 + 2 + 4 + … + n. That sum is less than 2n. (Each number is bigger than all the earlier ones put together: 8 > 1 + 2 + 4.) So n appends cost at most n (the appends themselves) + 2n (all the copying) = 3n. Spread over n appends, that's about 3 steps each, a constant.

Amortized O(1) means: a single operation can be slow, but averaged over any long sequence of operations, each one costs a constant. It's a guarantee about the total, not luck.

Each bar is the cost of one append. Tall bars are the copies. The blue line is the average cost so far. With doubling it flattens out; with "adding 4 slots" it keeps climbing.
Explain it another way: the piggy bank

Imagine every append costs you $3 instead of $1. You spend $1 on the append itself and drop $2 in a piggy bank. When the block is full and you need to move n items, the piggy bank has been filling up since the last move, and it holds enough to pay for every item's move. You never go into debt. Charging a small, fixed "tax" on cheap operations to pay for the rare expensive one is exactly what amortized means.

Why does doubling matter so much? If instead you grew by a fixed 4 slots, you'd copy everything every 4 appends: 4 + 8 + 12 + … + n ≈ n²/8 total. That's O(n) per append. Growing by a multiple is what makes it constant.

A list grows by doubling. You append 1,024 items, starting from capacity 1. Roughly how many item-copies happen in total?

Exactly: 1,023 copies for 1,024 appends, less than one copy per append on average.

Copies only happen when the block is full: at sizes 1, 2, 4, 8, …, 512. Add those up: 1 + 2 + 4 + 8 + 16 + 32 + 64 + 128 + 256 + 512 = 1,023. Doubling makes the copies rare enough that the total is about the same as the number of appends.

Go deeper: why real systems don't always double, and where amortized bites

CPython actually grows lists by about 1.125× plus a little, to waste less memory. Any growth factor bigger than 1 gives amortized O(1); a smaller factor means more frequent copies but less unused space. Some allocators prefer 1.5× because freed old blocks can eventually be reused for a later, bigger block.

The catch for real systems: amortized O(1) still means that one particular request sometimes pays O(n). If that request is a user waiting on a web page, they see a latency spike. This is why Redis resizes its hash tables incrementally (moving a few buckets per operation) instead of all at once. When people talk about "p99 latency", these occasional expensive operations are a common cause.

8Best case, average case, worst case

Looking for your keys: if they're in the first pocket you check, that's the best case. If they're in the last place you look, that's the worst case. Same search, very different luck.

  • Worst case: the most work for any input of size n. This is the guarantee.
  • Average case: the expected work over typical or random inputs.
  • Best case: rarely useful on its own ("it's fast if the answer is first").

Some famous examples where they differ:

AverageWorstWhat causes the worst case
Hash map lookupO(1)O(n)every key lands in the same bucket
QuicksortO(n log n)O(n²)always picking the smallest item as the pivot
Plain binary search treeO(log n)O(n)inserting already-sorted data

In an interview, always say which one you mean: "O(1) on average for the hash lookups, O(n) in the worst case." In production, the worst case is what wakes you up at 3am, because attackers and unlucky data find it.

You say "my solution is O(n) because hash lookups are O(1)". What's the most precise way to say it?

That's the senior version. You probably don't need to dwell on it, but saying it shows you know where the O(1) comes from.

Hash lookups are O(1) on average. In the worst case (many keys colliding into one bucket) one lookup can be O(n), and doing n of those would be O(n²). Stating "average" vs "worst" is a small phrase that signals you really understand the tool.

9When Big-O lies

Big-O throws away constants. Usually that's fine. Sometimes it's not:

  • Small inputs. An O(n²) algorithm with tiny steps can beat an O(n log n) one with heavy steps when n is 20. That's why Python's own sort switches to a simple O(n²) method (insertion sort) for small chunks.
  • Memory layout. Reading a list item by item is very fast because neighbors in memory get loaded together. Following pointers around (like a linked list) is often several times slower with the same Big-O.
  • Python vs C. sorted() and sum() run in fast C code. A hand-written Python loop doing "less" work can still be slower than a built-in doing "more".

How to check: the doubling experiment

You can measure growth without trusting your analysis. Time your code at n, then at 2n:

  • time roughly ×2 → linear
  • a bit more than ×2 → n log n
  • ×4 → n²
  • ×8 → n³

This is the same doubling test from section 3, done with a stopwatch. Exercise 8 has you do it for real.

Use Big-O to predict how code will scale. Use measurement to know how fast it actually is. A senior engineer does both and knows which question each one answers.

10Saying it out loud in an interview

Here's what a strong answer sounds like for the duplicate problem. Notice the structure: brute force, its cost, the improvement, its cost, and the trade-off.

"The simplest approach compares every pair: O(n²) time, O(1) extra space. With n up to 10⁵ that's around 5 billion comparisons, too slow. If I keep a set of what I've seen, each check is O(1) on average, so the whole thing is O(n) time, at the cost of O(n) extra space. If memory were tight, I could sort first instead: O(n log n) time and O(1) extra space, then compare neighbors."

Habits that make you sound senior:

  • Give both time and space, every time, without being asked.
  • Name your variables when there's more than one input: O(n + m), O(n · k), O(V + E). It's more precise than forcing everything into "n".
  • Say average vs worst when hashing or randomness is involved.
  • Mention the trade-off you made (usually space for time).

✓What to remember

  1. Count steps, not seconds. Big-O is how the step count grows with n.
  2. The doubling test: double n, and O(n) doubles the work, O(n²) quadruples it, O(log n) adds one step.
  3. Drop constants and smaller terms; keep the fastest-growing part.
  4. Reading code: sequences add, nested loops multiply, halving gives log, recursion is calls × work per call. Count how often each item is touched, not how many loops there are.
  5. Watch for hidden loops: in list, slicing, pop(0), string +=.
  6. Space counts, including the recursion stack. Trading memory for time is the most common optimization.
  7. Amortized O(1) = rare expensive steps paid for by many cheap ones. It needs growth by a multiple.
  8. Say average vs worst. Measure when it matters.

Warm-up · pen and paper

1. Name that complexity

Give the time complexity of each. Write your answers down before opening.

# (a)
for i in range(n):
    for j in range(5):
        print(i, j)

# (b)
i = 1
while i < n:
    i *= 3

# (c)
for i in range(n):
    for j in range(i):
        print(i, j)

# (d)
def f(n):
    if n <= 1: return 1
    return f(n // 2) + f(n // 2)
Answers

(a) O(n): the inner loop is a constant 5. (b) O(log n): multiplying by 3 is "halving in reverse"; it takes log₃ n steps, and the base of a log doesn't matter in Big-O. (c) O(n²): 0 + 1 + … + (n−1) = n(n−1)/2. (d) O(n), not O(log n)! There are log n levels, but the number of calls doubles each level: 1 + 2 + 4 + … + n ≈ 2n calls.

Warm-up · pen and paper

2. Spot the hidden cost

def reverse_words(text):
    out = ""
    for word in text.split():
        out = word + " " + out
    return out.strip()

What's the complexity in terms of the length L of the text, and how would you fix it?

Answer

O(L²). Each word + " " + out builds a brand-new string as long as everything so far. Fix: collect the words in a list, reverse it, and " ".join(...) once. That's O(L).
