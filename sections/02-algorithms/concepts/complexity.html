Complexity analysis

Big-O is a way to predict how code behaves when the input gets 1000× bigger, without running it. It's also the first thing you say out loud in every coding round.

CoreThe one-sentence idea

Big-O counts how the number of basic steps grows with input size and ignores constant factors. That's why it predicts scaling well, and why it can lie about speed at the sizes you actually run.

Build itFrom first principles

1. Count steps, not seconds

Seconds depend on the machine, the language and the cache. Steps depend only on the algorithm. So we count primitive operations (a comparison, an arithmetic op, an array read) as a function of input size n.

2. Keep only the dominant term

3n² + 50n + 7: at n = 1,000,000 the n² term is 99.998% of the work. Drop the lower terms and the constant, and you get O(n²). The constant matters for speed but not for shape.

3. Read the shape from the code

Code shapeComplexityExample
fixed number of stepsO(1)hash lookup, array index
halve the problem each stepO(log n)binary search, balanced tree walk
one passO(n)sum, max, sliding window
halve, solve both halves, merge in linear timeO(n log n)merge sort, heap of n pushes
loop inside a loop over the same dataO(n²)all pairs, naive dedupe
every subset / every orderingO(2ⁿ) / O(n!)backtracking without pruning

4. Space counts too

Extra memory as a function of n: the hash set you built, the recursion stack (depth × frame), the DP table. "O(1) extra space" means you only used a few variables beyond the input.

5. Amortized: averaging over a sequence

Some operations are usually cheap and occasionally expensive. A dynamic array append is O(1) until it fills, then O(n) to copy. Since capacity doubles, the expensive copies are exponentially rare, and the total over n appends is under 3n. Amortized O(1) is a guarantee about the sequence, not a probability.

6. Best, average, worst

Quicksort is O(n log n) on average but O(n²) worst case. A hash map is O(1) average, O(n) worst case. In interviews, say which one you mean. In production, the worst case is what pages you at 3am.

IntuitionPhysical picture: doubling the input

The fastest way to feel a complexity class is to ask: what happens when n doubles?

  • O(1): nothing. O(log n): one more step. O(n): twice the time.
  • O(n log n): a bit more than twice. O(n²): four times. O(2ⁿ): squared. Going from n = 30 to n = 60 takes you from a second to 30 years.

Rule of thumb for interview constraints. Python does about 10⁷ simple operations per second; compiled languages about 10⁸–10⁹. So the input size in a problem statement tells you which complexity they want:

InterviewWhat a senior answer adds: when constants matter
  • State complexity without being asked, for time and space, right after the brute force and again after each improvement. It's the backbone of "talk through it".
  • Name your variables. O(n·m) or O(V + E) or O(n log k) is more precise and more senior than forcing everything into "n".
  • Constants and memory layout matter at real sizes. An O(n) linked-list walk can lose to an O(n log n) sort of an array because of cache misses. Insertion sort beats merge sort below ~16 elements, which is why real sorts (Timsort, introsort) switch to it for small runs.
  • Python specifics: built-ins run in C. sorted() on 10⁶ items is fast; a Python-level O(n) loop doing the same work can be slower. Know the hidden costs: slicing copies (O(k)), in list is O(n), string += in a loop is O(n²).
  • Tail latency is a complexity question too: amortized O(1) still means the occasional O(n) request. At the p99.9 level, those spikes are what users notice.
TrapsCommon mistakes
  • Calling a nested loop O(n²) when the inner loop is amortized (two pointers, monotonic stack: each element is processed a constant number of times, so it's O(n)).
  • Forgetting the recursion stack in space complexity.
  • Forgetting that string or list building inside a loop can hide another factor of n.
  • Saying "O(n) where n is the number…" and then mixing up which n: string length vs number of strings.
  • Saying hash maps are O(1) without "average".
RecallCheck yourself
What is the complexity of for i in range(n): for j in range(i, n, i or 1)-style harmonic loops?

n/1 + n/2 + n/3 + … = n·Hₙ ≈ n ln n, so O(n log n). This is the sieve of Eratosthenes shape.

Recursive Fibonacci without memoization?

About O(φⁿ) ≈ O(1.618ⁿ) time, because each call branches twice and subproblems repeat. O(n) stack space. Memoization makes it O(n) time.

Is O(n log n) always slower than O(n)?

No. Big-O says nothing about constants. log₂(10⁶) ≈ 20, so a tight O(n log n) can beat a sloppy O(n) with a 50× constant (hashing, allocation, cache misses) at every size you'll ever run.
