Chapter 2 · Part 1

How fast is your code?

P0 asked in every coding roundabout 18 minutes7 quick checks · 8 exercises

Every coding interview asks the same follow-up the moment you finish writing a solution: "How does this scale?" Nobody wants a memorized chart of math symbols. They want to know whether you can look at ten lines of code, picture how the pile of work grows when the input gets 100× bigger, and catch a slowdown before it hits production.

By the end you'll be able to

  1. Predict how much slower your code gets when the input doubles, without running a stopwatch.
  2. Spot the six growth shapes on sight and read them straight off Python loops and built-ins.
  3. Count extra memory, including the invisible stack of paused recursive calls.
  4. Explain why a rare, expensive copy step (like growing a list) still averages out to cheap over time.
  5. Catch the four real-world cases where growth formulas mislead — and read input limits backward to pick an approach.

How to read this: top to bottom. This is the first chapter in the track — it assumes only basic Python loops and lists. Answer every quick check before moving on; a wrong answer explains the idea another way. Skip collapsed "Go deeper" boxes on your first pass.

1Why can't we just time our code with a stopwatch?

You write a feature that checks whether a playlist has duplicate songs by comparing every pair. On your laptop with 500 songs, it finishes in 2 milliseconds. Ship it.

Next week a power user imports 50,000 songs (100× bigger). You expect 0.2 seconds. Instead it freezes the server for 20 full seconds — 10,000× slower.

A stopwatch only measures one laptop on one input size. Run the same code on a faster server and the milliseconds shrink, yet the 10,000× cliff stays identical. Timing measures the hardware; we need a way to measure the method.

Both methods feel instant on 500 songs. Counting how work scales exposes the 20-second cliff before a user hits it.

Reading how work scales unlocks three immediate payoffs:

  • Spot timeouts before coding: glance at n = 100,000 in a prompt and rule out slow methods immediately.
  • Pinpoint the slow line: catch harmless-looking Python helpers (like x in list inside a loop) that silently multiply work.
  • Defend trade-offs: weigh extra memory against speed, rare copy pauses against long-run averages, and math against real CPUs.
A stopwatch measures one machine on one input. Complexity analysis counts how simple steps grow with input size n, isolating the method from the hardware.

Your pair-checking code takes 20 seconds on 50,000 songs. You buy a server that is 10× faster. What happens on 500,000 songs (10× bigger)?

Exactly! 10× more songs means 10 × 10 = 100× more pairs. A 10× faster CPU divides that by 10, still leaving 10× slower (~200 s). Growth shape always beats faster hardware at scale.

Contrast two methods on that 10× faster server when the playlist grows 10×: a single-pass scan does 10× more work, so the 10× CPU cancels it out (still 20 s). Pair-checking scales with the square (10 × 10 = 100× work), so a 10× CPU still leaves 10× more time (~200 s).

2What happens when the stack doubles?

Picture a stack of index cards on a desk — one card per song or item. Every comparison, copy, or flip is one card touch. Instead of timing milliseconds, ask: "When the stack doubles, what multiplies my card touches?" (In section 7 we'll see where this breaks on real CPUs and huge integers.)

Put n = 8 cards on the desk, then double to 16, then 32. Almost every algorithm falls into one of six growth shapes:

  • Stays flat: grab the top card — even a million cards takes 1 touch.
  • Adds +1 touch: halve a sorted stack and drop the wrong half (binary search). Doubling 8 → 16 adds just one split (3 → 4); 1,000,000 cards takes only ~20 splits! That halving count ("how many times you halve n to reach 1") is written log₂ n.
  • Doubles (×2): read every card once.
  • Doubles plus one extra pass: halve the stack down to single cards, then zip sorted halves back together — each of the log₂ n levels touches all n cards.
  • Quadruples (×4): compare every card with every other card (2 × 2 = 4× touches).
  • Explodes on +1 card: test every subset of cards (keep or skip each card). Adding just one card doubles total subsets!

Computer scientists label each growth shape with Big-O notation, written O(…). Slide n below — or click Double n — to watch the six curves pull apart:

Click Double n from 8 (8 → 16 → 32 → 64 → 128). Watch log₂ n creep up by +1 while n² quadruples and 2ⁿ blasts off the chart.

Go deeper: Big-O vs. Big-Omega (Ω), Big-Theta (Θ), and why log base disappears

Formally, O(g(n)) is an upper bound ("at most"), Ω(g(n)) is a lower bound ("at least"), and Θ(g(n)) is a tight bound (both). Saying a linear loop is O(n³) is technically true and completely unhelpful — in interviews, "Big-O" always means the tight worst-case bound unless you say otherwise.

Why omit the base in O(log n)? Halving (log₂ n) and cutting in thirds (log₃ n) always differ by the same constant factor (log₂ 3 ≈ 1.58), and section 3 drops constant factors.

Big-O names the growth shape as n scales: doubling n leaves O(1) flat, adds +1 to O(log n), doubles O(n), quadruples O(n²), while adding just +1 card doubles O(2ⁿ).

Two jobs run on a deck of cards: Job A is O(log n) (halving search) and Job B is O(2ⁿ) (testing every subset). You add 3 more cards to Job B, and you double Job A from 1,000,000 to 2,000,000 cards. What happens to their work?

Spot on! Halving 2,000,000 cards takes just one extra split to drop back down to 1,000,000 (20 → 21). Meanwhile each single card doubles the subsets, so 3 extra cards multiplies work by 2 × 2 × 2 = 8×.

Check both on small stacks: halving 16 cards takes 4 splits, and 32 cards takes 5 splits — doubling adds just +1 split (so 1M → 2M goes 20 → 21). For subsets, 1 card gives 2 subsets, 2 cards gives 4, 3 cards gives 8 — each +1 card doubles the pile, so +3 cards multiplies by 2³ = 8×.

3Why do we throw away constants and smaller terms?

Suppose Method A spends 20 setup touches opening and labeling the card box, then touches each card 3 times: 3n + 20 touches. Method B starts immediately and checks half of all pairs: 0.5 n² touches. On n = 4 cards, Method B wins (8 touches vs. 32)! Why does Big-O still call Method A O(n) and Method B O(n²)?

At n = 4, 0.5 n² (8) beats 3n + 20 (32). By n = 1,000, 3n + 20 is 3,020 while 0.5 n² is 500,000 — ~166× slower.

Two rules drop out directly:

  1. Drop constant multipliers: 3n and 0.5n both double when n doubles → O(n).
  2. Drop slower terms: in n² + 50n + 200, at n = 1,000 the n² term is 1,000,000 while 50n + 200 is only 50,200 (~5%) → O(n²).

What you NEVER drop: a second independent input. Scanning u users and p permissions sequentially is O(u + p) (not "O(n)" — what if u = 10 and p = 10,000,000?). Checking every user against every permission is O(u · p).

Drop constant multipliers and smaller terms of the same variable because the steepest curve dominates at scale. Keep separate inputs separate (O(u + p), O(u · p)).

A function loops over M words, each of length K, and checks every character in each word. What is its time complexity?

Exactly! Not every nested loop is O(n²). The outer loop runs M times and the inner loop runs K times per word, touching M · K characters total.

Plug in small numbers: 1,000 words of length 5 is 1,000 × 5 = 5,000 character touches — nowhere near 1,000² = 1,000,000, and bigger than 1,000 + 5 = 1,005. Nested loops over two independent sizes multiply: O(M · K).

4How do you read complexity straight off Python code?

Four patterns let you read Big-O straight off a screen of Python in seconds:

Pattern 1: Sequential adds, nested multiplies — unless the inner pointer never resets

One after another → ADD: O(a + b)

for x in list_a:      # a steps
    total += x
for y in list_b:      # + b steps
    total += y

Nested & restarting → MULTIPLY: O(a · b)

for x in list_a:      # a times ...
    for y in list_b:  #   ... full b scan
        pairs += (x == y)

Watch out: count total steps, not indentation! Below, j never resets to 0, so the inner while advances at most n times across the entire function — making the whole block O(n):

j = 0
for i in range(n):
    while j < n and arr[j] < arr[i] + 5:
        j += 1        # runs at most n times TOTAL, not n per i!

Pattern 2: The triangle loop is still O(n²)

When the inner loop starts at i + 1, it shrinks each round — yet on an n × n grid of pairs, skipping j ≤ i just cuts the square in half along the diagonal:

1 + 2 + … + (n−1) = n(n−1)/2 appears constantly in interviews. Half a square is always O(n²).

Pattern 3: Halving or doubling a counter gives O(log n)

while n > 1:
    n //= 2          # 16 -> 8 -> 4 -> 2 -> 1 (4 trips; doubling i *= 2 up to n is identical!)

Pattern 4: Hidden loops inside Python one-liners

A single for loop becomes O(n²) if one line inside it quietly walks the whole stack:

Go deeper: CPython's string-concatenation quirk

CPython has a narrow optimization that occasionally extends an unshared string in place, masking s += ch in tiny benchmarks. Never rely on it — interviews (and Java, JS, Go, PyPy) treat repeated immutable string concatenation as O(k²); always collect chunks in a list and "".join().

Inspect every helper inside a loop for hidden scans, shifts, copies, or string length k — and remember that a nested pointer that never resets still totals O(n).

What is the time complexity of this single-loop function on n distinct numbers?

def unique_items(items):
    seen = []
    for x in items:
        if x not in seen:
            seen.append(x)
    return seen

Sharp catch! On distinct items, seen grows 0, 1, 2, …, n−1, so x not in seen checks 0 + 1 + … + (n−1) = n(n−1)/2 cards — our exact triangle! Keeping a set alongside seen drops it to O(n).

Trace the 100th unique number: seen is an unsorted Python list, so x not in seen checks all 99 prior numbers one by one. Summing 0 + 1 + 2 + … + (n−1) checks gives n(n−1)/2 — O(n²) hiding inside one loop.

5What about memory — and the hidden pile of paused calls?

Checking songs in one pass had a price: storing seen songs takes space for up to n cards. That's the time–space trade-off: spend extra desk space to save card touches. Interviewers measure auxiliary (extra) space — extra memory you allocate beyond the input (name any returned output array separately).

The space people forget most is recursion. Each time a function calls itself before finishing, Python writes a sticky note holding its local variables and where to resume, and stacks it on the call stack:

Iterative — O(1) extra space

def sum_to(n):
    total = 0
    for i in range(1, n + 1):
        total += i
    return total

Recursive — O(n) call-stack space

def sum_to(n):
    if n <= 0: return 0
    if n == 1: return 1
    return n + sum_to(n - 1)  # pauses here!
Stack space equals the tallest pile of paused calls alive at one instant — finished calls pop off and free their slots.

Two crisp consequences follow: a halving recursion (like recursive binary search) stacks at most log₂ n notes (O(log n) space). And a branching recursion (exploring all 2ⁿ subsets of n cards) makes O(2ⁿ) total calls (2ⁿ⁺¹ − 1 calls across the whole tree), yet only stacks n notes at once because Python discards the left branch before starting the right!

Go deeper: recursion trees & auxiliary vs. output space

Recursion trees (time):

  • T(n) = T(n/2) + 1 (binary search): log₂ n levels × 1 → O(log n) time, O(log n) stack.
  • T(n) = 2T(n/2) + 1 (visiting every tree node) or T(n) = T(n/2) + n (work halves each level: n + n/2 + n/4 + …): both sum to O(n) — not every halving recursion is O(n log n)!
  • T(n) = 2T(n/2) + n (mergesort): log₂ n levels × n → O(n log n) time, O(n) space.
  • T(n) = 2T(n−1) + 1 (all subsets): 2ⁿ⁺¹ − 1 calls → Θ(2ⁿ) time, O(n) stack. (Naive Fibonacci is T(n) = T(n−1) + T(n−2) + 1: bounded by O(2ⁿ), tightly Θ(φⁿ) where φ ≈ 1.618, so O(1.62ⁿ).)

Output space: If you return all 2ⁿ subsets (each up to length n), the returned list takes O(n · 2ⁿ) space — state "O(n) auxiliary working space, O(n · 2ⁿ) output space."

Extra space counts both allocated data structures and peak recursion stack depth — not total function calls over time.

A recursive function explores every subset of n cards (branching "keep" and "skip" at each card) and only increments a counter total += 1 at each of the 2ⁿ leaves — making O(2ⁿ) total calls without storing the subsets. What is its peak space complexity?

Nailed it! Python walks one root-to-leaf path of length n, pops those sticky notes off the stack, and reuses the space for the next branch — so peak space is O(n) even though time is O(2ⁿ).

Check both traps: even with zero lists allocated, every paused recursive call still places a frame on the call stack (so it isn't O(1)). Yet those frames don't pile up to 2ⁿ either — as soon as the "keep" branch returns, its sticky notes come off the desk before the "skip" branch begins, capping height at n.

6Why can one slow step still average out to fast?

Python lists keep cards inside a fixed-size binder in memory. When the binder fills up and you call list.append(x), Python allocates a bigger binder and copies every existing card into it — an O(n) step! So why do engineers call append O(1)?

Watch what happens when you multiply capacity by a fixed factor — say doubling (1 → 2 → 4 → 8 → 16) — whenever the binder fills. (Any constant multiplier > 1 works; doubling is cleanest for head math, while Java uses ×1.5 and CPython ~×1.125 to trade empty slots against copies.)

Press ▶ Play or step with ▶|. Resizes hit at appends 2, 3, 5, and 9 — farther apart each time — keeping total copies strictly below 2n.

After 16 appends you copied 1 + 2 + 4 + 8 = 15 cards total — under 1 copy per append. Right after append 17 copies 16 cards, total copies are 31 < 2 × 17. Because resizes get exponentially rarer, n appends always do fewer than 2n copies: O(1) amortized.

Compare doubling against adding a fixed chunk (+10 slots) over 1,000 appends starting from capacity 1:

Growth rule (1,000 appends)ResizesTotal copiesCopies / appendAmortized cost
Multiply (×2)101,023~1.0O(1) amortized
Add constant (+10)10049,600~49.6 (grows with n!)O(n) amortized (O(n²) total)

Never blur three distinct ideas in interviews: amortized O(1) is a deterministic guarantee over every sequence of operations; average-case O(1) assumes typical/well-spread inputs; and worst-case single op is still O(n) on the one append that triggers a resize.

Explain it another way: the moving-coin jar (accounting method)

Charge each arriving card 3 coins: 1 coin pays to sit in an empty slot now, and 2 coins drop into a jar. When a size-8 binder fills, the 4 newest cards (slots 4–7) dropped 4 × 2 = 8 coins — paying the exact bill to copy all 8 cards into the new size-16 binder! The jar never goes negative, proving every append costs at most 3 coins: O(1) amortized.

Go deeper: growth-factor math, shrink thrashing, and amortized vs. expected

Tunable multiplier r: Growing by factor r > 1 bounds copies at r / (r − 1) per append amortized (dropping to 1 / (r − 1) right before a resize): ×2 → ≤2 copies (1 when full), up to 50% empty; ×1.5 → ≤3 copies (2 when full), up to 33% empty; CPython ~×1.125 → ≤9 copies (~8 when full), ~11% empty.

Shrinking trap (thrashing): Shrinking in half the instant size drops below 50% causes alternating append/pop at the boundary to resize on every single call! Fix: shrink in half only at 25% full (hysteresis).

Adversarial inputs: Both amortized (deterministic over any sequence) and randomized/expected (random pivots or randomized string hashing) hold even against hostile worst-case inputs — unlike input-dependent average-case bounds, which an attacker can deliberately trigger into O(n).

Multiplicative growth makes resizes exponentially rarer, guaranteeing fewer than 2n copies across any n appends: O(1) amortized — distinct from average case and single-op worst case.

You change a growable array (like Python's list) to add +100 slots whenever it fills instead of doubling (×2). What happens over n = 100,000 appends?

Right! Any fixed addition +c triggers n/c resizes copying c, 2c, 3c, … cards — a triangle sum of ~n² / (2c). Here that's ~50 million copies instead of ~131,000!

Count the resizes for 100,000 appends with +100: you resize 1,000 times, copying 50,000 cards on average → 1,000 × 50,000 = 50,000,000 copies (O(n²)). Only multiplying capacity by a factor > 1 keeps resizes rare enough for O(1) amortized.

7When does Big-O lie to you?

Senior engineers know the four places our card-desk model breaks down on real hardware:

1. Best, average, and worst case aren't the same

Always say which input shape your Big-O describes. Scanning an unsorted stack is best O(1) (top card), average O(n) (middle), and worst O(n) (last or absent). A Python set averages O(1) lookup, yet degrades to O(n) worst case if every key lands in the same slot (Chapter 1).

2. CPU cache locality beats equal Big-O by 10×–50×

Reading RAM takes ~100 nanoseconds, so CPUs fetch whole 64-byte chunks (cache lines) into fast L1 cache (~1 nanosecond). Walking cards parked side-by-side rides that prefetched chunk; chasing scattered memory addresses stalls on every hop:

Both loops are O(n), yet scanning contiguous primitives in C/Rust/Go/NumPy runs 10×–50× faster than chasing scattered pointers.

3. Small inputs & huge numbers

At tiny n, low overhead beats a better Big-O: C++'s std::sort switches to O(n²) insertion sort below ~16 items, and Python's built-in sort() builds initial runs of 32–64 items with insertion sort before merging. Meanwhile, O(1) math only holds for fixed 64-bit numbers — multiplying two 100,000-digit Python big integers takes millions of CPU ops (tens of milliseconds), so Exercise 7's fast_power(3, 100_000) uses O(log exp) multiplications, not O(log exp) wall-clock time.

4. Tail-latency pauses (slowest 1% of requests)

Amortized O(1) averages over time — the single request that resizes a 10-million-item array still pauses for tens of milliseconds (a tail-latency spike). When size is known upfront, pre-allocate capacity ([None] * n, C++ reserve(), Go make) to eliminate resize pauses altogether.

Go deeper: Python lists vs. C arrays, incremental resizing, I/O, streams, and 100 machines

Python lists: A Python list holds contiguous 8-byte pointers to heap objects — better than a linked list, but still one hop per element compared to packed C int[] or NumPy arrays.

Avoiding resize spikes when n is unknown: Low-latency stores like Redis use incremental resizing — copying one small slice per operation while reads check both old and new buffers.

I/O dwarfs CPU: One network hop (~10–50 ms) or SSD random read (~100 µs) outweighs millions of RAM ops. Out-of-RAM data optimizes disk passes instead of CPU comparisons.

100 machines (Amdahl's Law): If even 5% of a job must run sequentially (coordination/merging), 100 servers cap out under 1 / 0.05 = 20× speedup.

Big-O predicts large-n scaling, not L1 cache wins, small-n crossovers, big-integer math, or resize spikes. Always name the case (best, average, worst, amortized).

In C++, two functions both sum 10 million integers in O(n) time with zero extra allocations: Function A walks a contiguous array (std::vector), while Function B follows pointers through a linked list scattered in RAM. Function A finishes 20× faster. Why?

Exactly! Same Big-O, 20× different constant factor — hardware prefetching and L1 cache locality explain why flat arrays crush pointer-heavy structures on real CPUs.

Both loops visit every single integer once on one CPU core, and dereferencing a pointer is still O(1) — so both are strictly O(n). The 20× gap is hardware physics: reading arr[0] pulls arr[1..15] into fast L1 cache for free, while every linked-list pointer jumps blind in RAM.

8How you use complexity in interviews

Habit 1: Read the input limit backward

Ask for max n in minute 1. At ~10⁸ simple ops/sec (~10⁶–10⁷ loop steps in Python), n tells you the slowest Big-O that finishes well under a second (the technique column previews later track chapters; n! = factorial n × (n−1) × … × 1, so 10! ≈ 3.6M):

Max nTarget Big-OTypical technique
n ≤ 10O(n!)Permutations, brute-force orderings
n ≤ 20O(2ⁿ)Subsets, backtracking
n ≤ 2,000O(n²)Nested loops, 2D tables
n ≤ 100,000O(n log n) or O(n)Sorting, heaps, hash maps, two pointers
n ≤ 10⁸O(n)Single pass, counting array, streaming
n > 10⁸O(log n) or O(1)Binary search, math, square-and-multiply

Habit 2: Kill the bottleneck line (three core shifts)

Shift 1 — Trade space for speed (O(n²) → O(n) time, O(n) space, Exercise 4):

Before: check every pair — O(n²)

def has_dup_slow(nums):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] == nums[j]:
                return True
    return False

After: seen set — O(n) avg

def has_dup_fast(nums):
    seen = set()          # requires hashable items
    for x in nums:
        if x in seen:     # O(1) avg lookup
            return True
        seen.add(x)
    return False

Shift 2 — Exploit sorted order (O(n²) → O(n) time, O(1) space, Exercise 6): On a sorted distinct list, place two fingers at the left and right ends. Sum too big → move R left; sum too small → move L right; exact match → count it and move both inward (since values are distinct, neither end can pair again!):

Sorted order replaces an O(n) inner scan with two converging pointers in O(1) extra space.

Shift 3 — Halve the exponent (O(exp) → O(log exp) multiplications, Exercise 7): Naive 3¹³ multiplies 3 × 3 × … 12 times. Instead, square the base whenever exp is even (b²ᵏ = (b²)ᵏ), and peel off one factor of b whenever exp is odd (b²ᵏ⁺¹ = b · (b²)ᵏ):

3¹³  (13 odd  → peel 3, square base)   = 3 · 9⁶
     ( 6 even → square base)           = 3 · 81³
     ( 3 odd  → peel 81, square base)  = 3 · 81 · 6561¹
     ( 1 odd  → peel 6561, done!)      = 1,594,323   (only 5–6 mults!)

For exp = 100,000 → just 22–23 mults (≤ 33 worst case), instead of 99,999!

9What to say in the interview

Every time you analyze a solution aloud, hit these four crisp beats:

  1. Name the variables first: "Let n be the number of songs, and k the max title length." (Never drop an unnamed independent variable.)
  2. Brute force → bottleneck → improved cost: "Checking every pair is O(n²) comparisons and O(1) space. A hash set removes the inner scan: O(n) average for bounded titles (or O(n · k) for length-k strings), trading O(n) extra space."
  3. Keep cases and stack space separate: "list.append is O(1) amortized (doubling keeps total copies under 2n) with occasional O(n) resize spikes; recursion depth h adds O(h) call-stack space."
  4. Ground in reality if asked: "At n = 10⁵, O(n) or O(n log n) is well inside budget; on tiny slices or tight loops, contiguous arrays can win on CPU cache locality and constants."

✓What to remember

  1. Count how operations scale as n doubles instead of trusting one stopwatch run.
  2. Know the six growth shapes on sight: O(1), O(log n), O(n), O(n log n), O(n²), O(2ⁿ).
  3. Drop constants and slower terms of the same variable, but never collapse independent inputs (O(u + p), O(u · p)).
  4. Half a square (1 + 2 + … + n−1) is O(n²); check one-liners for hidden O(n) scans/shifts and length-k string work.
  5. Space complexity equals allocated structures plus peak call-stack depth (not total calls).
  6. Amortized O(1) (multiplicative growth) guarantees cheap cost over every sequence — distinct from average case and single-op worst case.
  7. Big-O hides cache locality, small-n constants, big-integer math, and resize pauses; read max n backward to pick your target shape.

Warm-up · pen and paper

1. Rank the growth shapes & predict doubling

Order these six functions from slowest-growing to fastest-growing at large n, and note what happens when n doubles: 500n + 10,000, 0.01 n², 2ⁿ, 12 log₂ n, 4n log₂ n, 999,999.

Answer

999,999 (O(1), ×1) → 12 log₂ n (O(log n), +12 steps) → 500n + 10,000 (O(n), ~×2) → 4n log₂ n (O(n log n), ×2 + 8n) → 0.01 n² (O(n²), ×4) → 2ⁿ (O(2ⁿ), squares!).

Warm-up · pen and paper

2. Spot the hidden loop

Give the tight time and auxiliary space complexity for each snippet on a list of length n (assume process() is O(1) time and space, and strings are immutable with no in-place optimization):

# (1)
while queue:
    process(queue.pop(0))

# (2)
out = ""
for ch in chars:
    out += ch

# (3)
def sum_list(a):
    return 0 if not a else a[0] + sum_list(a[1:])

# (4) len(a) == n, len(b) == 10
for x in a:
    for y in b:
        process(x, y)
Answer

(1) O(n²) time, O(1) space (pop(0) shifts every remaining item). (2) O(n²) time, O(n) space (copies 1 + 2 + … + n chars). (3) O(n²) time AND O(n²) space (every slice a[1:] allocates a new copy of size n−1, n−2, … sitting live on the call stack at once!). (4) O(n) time, O(1) space (10 is constant; if len(b) = m varies, it's O(n · m)).

Warm-up · pen and paper

3. Trace doubling vs. +4 growth

Start with capacity 1 and append 16 items. Count total copies under (a) doubling (1 → 2 → 4 → 8 → 16) and (b) adding 4 slots each resize (1 → 5 → 9 → 13 → 17). Which stays below 2n at n = 10,000?

Answer

(a) Doubling: 1 + 2 + 4 + 8 = 15 copies (< 1/append). (b) Adding 4: 1 + 5 + 9 + 13 = 28 copies — and by n = 10,000 it does ~12.5 million copies (O(n²)), whereas doubling does only 16,383 (< 2n).
