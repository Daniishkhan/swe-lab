Chapter 2 · Part 5

Exploring graphs

P0 asked almost everywhereabout 55 minutes10 quick checks · 10 exercises

A maze, a grid of islands, course prerequisites, friends of friends, a build that has to compile packages in the right order. These look like different problems, and in interviews they are some of the most common ones. Underneath, they are all the same thing: things, and connections between things. That's a graph. Almost every graph question is answered by one short loop, with one choice inside it: take the next item from a queue, or from a stack.

By the end you'll be able to

  1. Turn a problem into nodes and edges, and store it as an adjacency list.
  2. Write breadth-first search (BFS) and depth-first search (DFS) from memory, and say why both cost O(V + E).
  3. Explain why BFS finds shortest paths when every step costs the same, and rebuild the path itself.
  4. Treat a grid as a graph, and count its separate pieces.
  5. Detect cycles, and explain why "already visited" is the wrong test in a directed graph.
  6. Put tasks in dependency order (topological sort), and recognize when no order exists.

How to read this: top to bottom, like a book. It builds on How fast is your code? (O(V + E) is a sum of two sizes) and uses Python sets and dicts, whose lookups are O(1) on average. 1The problem: how far apart are two people?

You work on a social network with 1,000,000 users. Each one has about 100 friends. Product wants a small badge on every profile: "2nd connection", "3rd connection", and so on up to "6th", meaning how many friend-hops separate you from the person you're looking at.

The first idea: start from you and follow every chain of friends. You have 100 friends. Each of them has 100, so there are 10,000 chains of length 2, a million of length 3, and 100⁶ = 10¹² chains of length 6. At about 10 million simple Python steps a second, 10¹² steps take about 28 hours. For one badge.

Something is badly wrong here, because there are only 1,000,000 people. A trillion chains means that the same people turn up over and over. Your friend Cy is the end of the chain you → Cy, but also you → Bo → Cy, and you → Bo → Dee → Cy, and every one of those chains then explores everything behind Cy again. Worse, some chains never end at all: you → Bo → you → Bo → … is a perfectly good chain of friendships.

This chapter fixes that one flaw: visit each person once. Then the whole network costs about 1,000,000 people plus the 100,000,000 entries in their friend lists: about 10⁸ steps, roughly 10 seconds of Python for your distance to everyone at once. With small changes, the same fix also answers "are these connected?", "is there a loop?" and "in what order do I do these?".

There are only 1,000,000 people, but the naive search follows 10¹² chains. Where does the extra work come from?

Right. The chains overlap. Every person can be reached along many different routes, and the naive search re-explores everything behind them once per route (and loops forever on chains like you → Bo → you). Remembering who you've already reached removes the overlap.

Count the friendships: 1,000,000 × 100 / 2 (each friendship has two people) is 50 million, nowhere near 10¹². A faster language runs the same 10¹² steps faster, not fewer: at 50 to 100 times quicker, still 15 to 35 minutes per badge. The real problem is repetition: Cy is reached as you → Cy, you → Bo → Cy, you → Bo → Dee → Cy, …, and each route explores everything behind Cy again.

2What a graph is, and how to store one

A graph is a set of nodes (also called vertices: the things) and edges (the connections between pairs of things). Two nodes joined by an edge are neighbours. We write V for the number of nodes and E for the number of edges.

  • Undirected: an edge goes both ways. Friendship: if Ana is Bo's friend, Bo is Ana's friend.
  • Directed: an edge has a direction, drawn as an arrow. Following someone on a social app, a web page linking to another, "package A needs package B".
  • Weighted: each edge carries a number, like a road's length in minutes. This chapter is about graphs where every edge counts the same. Weights need a different tool (section 9).

Graphs often hide. In a maze, cells are nodes and steps between them are edges. In a build, packages are nodes and each "needs" is an arrow. Spotting the hidden graph is half of most interview questions.

Two ways to store it

Take four people: Ana is friends with Bo and Cy, and Bo is friends with Dee.

The adjacency matrix answers "are Ana and Dee friends?" in one lookup. But for our network it has 10¹² cells, about 100 ones per row of a million. Even at one bit per cell that's 125 GB of almost all zeros, and listing someone's friends means reading a million cells.

The adjacency list keeps only the actual neighbours: 100,000,000 entries (each of the 50 million friendships sits in two lists), 10,000 times less. Listing a person's friends costs as many steps as they have friends.

def build_graph(people, friendships):
    graph = {p: [] for p in people}   # every person is a key, even with no friends
    for a, b in friendships:
        graph[a].append(b)            # undirected: store the edge
        graph[b].append(a)            # in BOTH lists
    return graph

For a directed graph, drop the second append: the arrow a → b goes only in a's list.

Store graphs as adjacency lists: a dict from each node to the list of its neighbours. Most real graphs are sparse (E is far smaller than V²), so the list uses V + E memory where a matrix uses V².

A road map has 50,000 intersections, each joined to about 4 roads. How should you store it?

Right. 50,000² is 2.5 billion cells with about 4 ones per row. The list stores about 4 entries per intersection: 200,000. And searching the matrix is O(V²), because finding a node's roads means reading its whole row.

Plug in the numbers. A matrix has a cell for every pair of intersections: 50,000 × 50,000 = 2.5 billion, almost all zero. Searching it isn't O(V + E) either: to find one intersection's 4 roads you read its whole row of 50,000 cells, so O(V²). The list keeps only roads that exist, about 200,000 entries. The O(1) edge check rarely matters for a search.

3Don't walk in circles: the visited set

Here's the most natural way to explore a graph: visit a person, then visit each of their friends the same way.

def walk(graph, person):
    print(person)
    for friend in graph[person]:
        walk(graph, friend)      # Ana -> Bo -> Ana -> Bo -> ... forever

On Ana and Bo, who are friends, it prints Ana, Bo, Ana, Bo, … until Python stops it with a RecursionError after about 1,000 nested calls. The walk can come back to where it started, and in an undirected graph every edge allows that: Ana → Bo → Ana.

The fix is the one from section 1: remember who you've already reached, and never go there again. Keep a visited set (often called seen) and a frontier: the nodes you've found but not yet explored.

def reach(graph, start):
    seen = {start}
    frontier = [start]              # found, but neighbours not looked at yet
    while frontier:
        node = frontier.pop()       # WHICH node we take next: sections 4 and 5
        for nxt in graph[node]:
            if nxt not in seen:     # each node gets in at most once
                seen.add(nxt)
                frontier.append(nxt)
    return seen                     # everyone reachable from start

Why it costs O(V + E)

Count the work in two piles.

  1. Nodes. A node enters the frontier only if it wasn't in seen, and it's added to seen at that moment. So each node enters at most once and is taken out at most once: at most V times.
  2. Edges. When a node is taken out, we read its neighbour list once. Add up all the lists: in a directed graph that's E entries; in an undirected one 2E (each edge sits in two lists). Each entry costs one O(1) set check.

Together: O(V + E). For the social network, about 10⁶ + 10⁸ steps instead of 10¹². And V and E only count the part the search can reach.

Every graph search is this loop: a visited set so each node is handled once, and a frontier of nodes still to explore. Each node is taken out once and each neighbour list is read once, so the cost is O(V + E).

The network has 1,000,000 people and 50 million friendships. You call reach on someone whose group (everyone they can reach) is 30 people with 4 friends each. About how much work is that?

Right. Only reachable people ever enter the frontier. 30 people come out once each, and their lists hold 30 × 4 = 120 entries. The other 999,970 are never looked at.

Follow what the loop touches. It only adds people who appear in a friend list it's reading, so it never leaves the group of 30. Each comes out once and each list of 4 is read once: 30 + 120. It never compares everyone with everyone; it only reads lists that exist. The whole-network cost only happens when the start can reach the whole network.

4Breadth-first search: rings of distance

reach tells us who is connected, but the badge needs how far. The order in which we take nodes out of the frontier decides that.

Think of news spreading at a party. You tell your friends (1 hop), then they tell theirs (2 hops). Everyone at distance 1 hears it before anyone at distance 2. Explore in that order, and the first time you reach a person is along the fewest hops.

To get that order, the frontier must be a queue: first in, first out, like a line at a shop. New nodes join at the back; we always take the node that has waited longest, from the front. This is breadth-first search (BFS): it covers the whole breadth of one distance before going one step further.

from collections import deque

def hops_from(graph, start):
    dist = {start: 0}                 # doubles as the "seen" set
    queue = deque([start])
    while queue:
        node = queue.popleft()        # oldest first = nearest first
        for nxt in graph[node]:
            if nxt not in dist:       # first time we reach it
                dist[nxt] = dist[node] + 1
                queue.append(nxt)     # mark when ADDING: it's queued once
    return dist                       # hops from start to everyone reachable

Use collections.deque, not a list. list.pop(0) shifts every remaining item one slot left: with 100,000 nodes queued, that's 100,000 moves per pop, and the search quietly becomes O(V²). deque.popleft() is O(1).

Step through it on a small friend graph. Watch the distance labels: the queue always holds nodes of one distance, then possibly some of the next distance, and nothing else.

Why the first visit is the shortest

Interviewers probe this, so let's go slowly. At any moment in the player, the queue looks like this:

front               back
[ E:2 | F:3 ]
  d     d + 1

Some nodes at distance d, then some at d + 1, never anything else. It stays that way because we take a d from the front, and everything it adds gets d + 1 and goes to the back. So nodes come out in order of distance: all the 0s, then all the 1s, then all the 2s.

Now suppose BFS first reaches X from a node at distance 3, giving X distance 4. Could X really be 2 hops away? Then X is a neighbour of some node at distance 1. That node came out before any distance-3 node, looked at X, and gave it distance 2 back then. Contradiction. The same argument works ring by ring: A labels its own neighbours 1, so those are right; then every true distance-2 node is a neighbour of a correct 1 and gets labelled 2 before any 3 comes out; and so on outward. So the first time BFS reaches a node, it has the fewest hops, and marking it right then, never to be updated, is safe.

BFS takes nodes from a queue, so they come out in rings: distance 0, then 1, then 2. The first time BFS reaches a node is along a shortest path, as long as every edge counts the same. Cost: O(V + E).

BFS from A first reaches node X while exploring a node at distance 3, so dist[X] = 4. Could there still be a 2-hop path from A to X?

Right. On a path A → Y → X, Y is at distance 1, so Y left the queue before any distance-3 node and set dist[X] = 2 back then. Neighbour order only picks between equally short paths.

Think of the queue as a line sorted by distance: every 1 is served before any 3. If X were 2 hops away, the middle node Y is at distance 1, so Y was served earlier, saw X, and gave it distance 2. Neighbour order only chooses among equally short paths. Direction doesn't matter either: on a directed graph BFS follows the arrows and the line stays sorted the same way.

Mark when you add, not when you take

hops_from records a node the moment it's added to the queue. A common bug is to mark it only when it's taken out. Then a node can be queued once for every neighbour that sees it before it comes out.

You change BFS to add a node to seen when it's taken out of the queue (skipping nodes already seen), instead of when it's put in. On a graph where every node is connected to every other, what happens?

Right. Until a node comes out, every node explored before it adds another copy. With 1,000 nodes, 499,501 entries pass through the queue instead of 1,000. Copies are skipped when they come out, and the first copy out has the right distance; it just wastes memory and time.

Picture 4 people who all know each other: A, B, C, D. From A, add B, C, D. Take B: C and D haven't come out yet, so they don't count as seen, and B adds them again. Then C adds D again. It still ends (copies are skipped once their node is seen) and the first copy out has the right distance. But at 1,000 people, 499,501 entries pass through the queue instead of 1,000.

From distances to the path itself

"Show me how I'm connected" needs the chain of people, not just a number. When a node discovers a new neighbour, write down who discovered it: parent[nxt] = node. Those are the edges highlighted at the end of the player. Following parents heads back toward the start, one ring at a time.

parent:   B←A   C←A   D←B   E←C   F←D   H←E   G←F

walk back from G:   G → F → D → B → A      (stop: A has no parent)
reverse it:         A → B → D → F → G      4 hops, a shortest path

If the goal never got a parent (and isn't the start), it's unreachable. You can also stop the moment the goal is discovered, since its distance can't improve. Exercise 4 has you write this.

Explain it another way: a flood

Pour water on the start node. Each second it flows one edge further in every direction. The second a node first gets wet is its distance, and noting where the water came from lets you trace the stream back. The BFS queue is the wet edge of the flood.

Go deeper: what the proof needs, and all shortest paths

The proof uses one fact: every edge adds exactly 1. With a 1-minute road and a 10-minute road, fewest edges isn't fastest; that's Dijkstra's algorithm (section 9). On directed graphs BFS works unchanged, following arrows only forward. To get every shortest path, keep a list of parents per node: any neighbour at distance d − 1 is a valid parent of a node at distance d.

5Depth-first search: one corridor at a time

Now flip the one choice: take the newest node instead of the oldest. The frontier becomes a stack (last in, first out, like a pile of plates). The search follows one neighbour, then its neighbour, deeper and deeper, and backs up only at a dead end. That's depth-first search (DFS): how you'd explore a maze alone, returning to the last junction with an untried corridor.

The shortest way to write DFS uses recursion: the function calls itself on each new neighbour, and Python's own call stack is the stack.

def dfs(graph, node, seen, order):
    seen.add(node)
    order.append(node)                   # entering node
    for nxt in graph[node]:
        if nxt not in seen:
            dfs(graph, nxt, seen, order) # dive; come back here when it's done
    # leaving node: everything reachable from it is now explored

Run it from A on the graph from section 4 (neighbours in alphabetical order). It dives straight down one long corridor:

A → B → C → E → D → F → G → H        (each arrow is one nested call)

BFS reached G in 4 hops: A → B → D → F → G
DFS reached G along 6:   A → B → C → E → D → F → G

That's the price of going deep: DFS finds a path, not the shortest one, and which one depends on the order of the neighbour lists. What DFS gives instead is structure. Every node has a moment you enter it and a later moment you leave it, and in between, everything reachable from it gets explored. Sections 7 and 8 are built on those two moments.

The recursion limit

Each nested call takes a slot on Python's call stack, and Python stops at about 1,000 (sys.getrecursionlimit() is 1000 by default) with a RecursionError. On a 100 × 100 grid with no walls, recursive DFS from a corner can snake through all 10,000 cells, one call inside the next. sys.setrecursionlimit raises the limit, but every frame costs memory, and on older Pythons very deep recursion can crash the interpreter outright. The robust fix is to keep the stack yourself:

def dfs_order(graph, start):
    seen, order = set(), []
    stack = [start]
    while stack:
        node = stack.pop()                  # newest first: go deep
        if node in seen:
            continue                        # pushed twice; already explored
        seen.add(node)
        order.append(node)
        for nxt in reversed(graph[node]):   # reversed, so the FIRST neighbour
            if nxt not in seen:             # is on top and explored first
                stack.append(nxt)
    return order

This version marks a node when it's popped, because a node can be pushed by several neighbours and the copy pushed last is the one DFS should follow. The duplicates cost at most O(E) stack entries, and the visit order matches the recursive version. Section 3's reach marked on push instead: it finds the same set of nodes, but not in depth-first order (A, C, E, H, G, F, D, B here). Fine for "who can I reach?", not for cycles or ordering.

DFS takes the newest node from a stack and goes deep before going wide. It finds a path, not the shortest. It costs O(V + E), like BFS. In Python, recursion stops at about 1,000 levels, so for big graphs and grids, keep your own stack.

You run recursive DFS on a 100 × 100 grid with no walls, starting in a corner, with Python's default settings. What happens?

Right. Size isn't the problem; depth is. DFS keeps finding an unvisited neighbour and snakes through the whole grid, each cell one call deeper. An explicit stack is just a list, with no such limit.

The visited set makes cycles harmless: no cell is entered twice. And 10,000 cells is tiny work. The trouble is nesting: each step to a neighbour is a call that hasn't returned yet, and on an open grid DFS can walk a very long way before a dead end. Here the chain can reach all 10,000 cells, ten times Python's limit of about 1,000.

6Grids are graphs too, and counting the pieces

Many interview graphs never appear as a list of edges. In a maze, a map or an image, each cell is a node, and its neighbours are the cells up, down, left and right that are inside the grid and not a wall. You compute neighbours when you need them instead of building lists: an implicit graph. With R rows and C columns, V = R × C and each cell has at most 4 neighbours, so O(V + E) becomes O(R × C).

def region_size(grid, r, c):
    """How many cells a paint bucket fills if you click cell (r, c)."""
    rows, cols, colour = len(grid), len(grid[0]), grid[r][c]
    seen, stack = {(r, c)}, [(r, c)]
    while stack:
        y, x = stack.pop()
        for ny, nx in ((y - 1, x), (y + 1, x), (y, x - 1), (y, x + 1)):
            inside = 0 <= ny < rows and 0 <= nx < cols
            if inside and (ny, nx) not in seen and grid[ny][nx] == colour:
                seen.add((ny, nx))
                stack.append((ny, nx))
    return len(seen)

That's the reach loop again, with the neighbours worked out from coordinates. Swap the stack for a deque and pop for popleft, and it's BFS on a grid, ready to count steps through a maze.

Both on the same grid: the number in a cell is the length of the path the search used to get there. Click cells to add or remove walls.

Connected components: counting the pieces

A connected component is a group of nodes that can all reach each other, with no edges leaving the group: separate friend circles, islands on a map, blobs in an image. One search finds exactly one component. To find all of them:

  1. Keep one visited set for the whole job.
  2. Go through every node. If it's already visited, it belongs to a component you've counted; skip it.
  3. If it isn't, you've found a new component: add 1 to the count and run a search from it, marking its whole group visited.

A search inside a loop sounds like O(V × (V + E)), but the visited set is shared, so each node is explored by exactly one search in the whole run: still O(V + E). Forgetting this loop is a classic bug elsewhere too: a search from node 0 alone misses everything node 0 can't reach.

A grid is a graph whose neighbours you compute from coordinates: O(R × C) to search. To count connected components, loop over every node with one shared visited set and start a new search at each unvisited node. Still O(V + E) in total.

Go deeper: union-find, the other way to count components

Union-find (disjoint-set union) gives each node a pointer toward its group's "leader". find(x) follows pointers to the leader; union(a, b) points one leader at the other. Union every edge, and the number of leaders is the number of components. With path compression and union by size, each operation is about O(1) amortized (the inverse Ackermann function, at most 4 for any real input).

It shines when edges arrive one at a time: "after this new friendship, how many groups are there?", or islands that grow cell by cell. A search would restart each time. It also finds undirected cycles: an edge whose ends already share a leader closes a loop (the heart of Kruskal's spanning tree algorithm). It can't give distances, paths, or anything about directed graphs.

7Finding cycles

A cycle is a route that comes back to where it started. Often the visited set just steps around cycles. Sometimes the cycle is the bug: a deadlock (thread 1 waits for thread 2, which waits for thread 1), a dependency loop (A needs B, B needs A: no install order), a spreadsheet's circular reference. Interviewers love this topic, because the obvious method works for undirected graphs and fails for directed ones.

Undirected: any other way back

In an undirected graph, the edge you walked in on leads straight back: Bo's list contains Ana. That's the same edge seen from the other end, not a cycle. So remember which node you came from. Reaching a seen node through any other edge means two different routes to it, and two routes between the same pair of nodes make a loop.

def has_cycle_undirected(graph):
    seen = set()
    for s in graph:                        # every component, not just one
        if s in seen:
            continue
        seen.add(s)
        stack = [(s, None)]                # (node, the node we came from)
        while stack:
            node, came_from = stack.pop()
            for nxt in graph[node]:
                if nxt == came_from:
                    continue               # the edge we walked in on
                if nxt in seen:
                    return True            # reached a known node another way
                seen.add(nxt)
                stack.append((nxt, node))
    return False

Directed: why "already visited" is wrong

Now the arrows have a direction, and the same test breaks. Look at this graph, a "diamond":

      A
     ↙ ↘
    B   C          A → B, A → C, B → D, C → D
     ↘ ↙
      D

A search from A goes to B, then D, a dead end. It backs up to A and tries C, which has an arrow to D: already visited. The undirected rule says "a second way to a known node: cycle!" But there's no cycle; nothing leads from D back up. Two routes into a node are fine in a directed graph. A cycle needs a route back to a node you're still inside.

DFS's enter and leave moments (section 5) tell us exactly that. Give every node one of three colours:

  • White: not visited yet.
  • Gray: entered but not left. Gray nodes are exactly the nodes on the path from the start to where you are now.
  • Black: finished. Everything reachable from it has been fully explored.

An edge to a gray node closes a cycle: walk from that node down the current path to here, then take the edge back. An edge to a black node is safe: when it finished, everything it can reach was explored and none of it led to a gray node.

Three-colour DFS. The player's diamond has one extra node, E, after D. Wait for the frame where C looks at D: D is black, and a visited-only check would report a false cycle. Then switch to "plus E → B" and watch the search hit a gray node. On screen, gray nodes are drawn orange and black ones green.
WHITE, GRAY, BLACK = 0, 1, 2

def has_cycle_directed(graph):
    colour = {node: WHITE for node in graph}
    def visit(node):
        colour[node] = GRAY              # entering: on the current path
        for nxt in graph[node]:
            if colour[nxt] == GRAY:
                return True              # back to an open node: a loop
            if colour[nxt] == WHITE and visit(nxt):
                return True
        colour[node] = BLACK             # leaving: everything below is done
        return False
    return any(colour[n] == WHITE and visit(n) for n in graph)

This recurses, so section 5's depth limit applies. An iterative version must know when a node is finished, which a stack of bare nodes doesn't tell you. The trick: for each node on the stack, also keep your place in its neighbour list (a Python iterator works well); when it runs out, the node turns black and comes off. Exercise 7 asks for this, returning the cycle itself rather than True.

Undirected: a cycle exists if the search reaches a seen node through any edge other than the one it came in on. Directed: "seen" isn't enough, because two routes into one node are fine. Use three colours; only an edge to a gray node (one on the current path) closes a cycle.
Explain it another way: a ball of string

You explore a building of one-way doors, unrolling string behind you. At a dead end you walk back, rolling it up, and chalk each room you've finished. String marks gray rooms; chalk marks black ones. A door into a room with your string in it means you walked in a circle. A door into a chalked room is harmless: you finished it, and nothing in there led to your string. The visited-only check treats string and chalk as the same mark. That's the bug.

During three-colour DFS on a directed graph, you're at node P and see an edge P → Q, where Q is black. Does this edge prove a cycle?

Right. Q turned black only after everything it reaches was explored. If Q could reach P, that search would have met P: gray (reporting the cycle then) or white (exploring and finishing P before Q). P is still gray, so neither happened. No new search needed.

Use the diamond, A → B → D and A → C → D. When C looks at D, D is black: visited, yet no arrow leads from D back to C or A. Visited is not the same as on the current path. And black already means "fully explored, and nothing in there led back to a gray node", so no fresh search is needed. Only an edge to a gray node closes a cycle.

Go deeper: edge types, repeated edges, strongly connected components

Edge types. DFS sorts directed edges into tree (to a white node), back (to a gray ancestor: a cycle), forward (to a finished descendant) and cross (to a finished node in another branch, like C → D). A cycle exists exactly when there's a back edge. Undirected graphs have only tree and back edges, which is why the simpler test works there.

Repeated edges. If the same undirected edge can be listed twice, the came-from check by node answers differently depending on which end it scans first. De-duplicate the lists, or track the edge you came in on.

Every cycle at once. A strongly connected component is a group of nodes in a directed graph that can all reach each other. Tarjan's and Kosaraju's algorithms find them all in O(V + E); any component with two or more nodes contains a cycle (and so does a single node with an edge to itself). That's how a tool can report every dependency loop, not just the first.

8Putting things in order: topological sort

A build tool has to compile packages. db needs log and cfg built first; api needs db and http; and so on. Draw an arrow from each package to the packages that need it. A topological order is a list of all the nodes in which every arrow points forward: each package comes after everything it needs.

There are usually many valid orders. One exists exactly when the graph has no directed cycle: if A needs B and B needs A, neither can go first. A directed graph with no cycles is a DAG (directed acyclic graph).

Kahn's algorithm: start with what's ready

By hand, you'd build anything with no prerequisites first. That crosses off one prerequisite for each package that needed it, and some of those become ready. The number of arrows into a node is its in-degree: how many prerequisites it still waits for.

  1. Count every node's in-degree. One pass over the edges.
  2. Put every node with in-degree 0 in a queue.
  3. Take a node from the queue and append it to the order. For each arrow out of it, subtract 1 from the target's in-degree. Any target that drops to 0 joins the queue.
  4. When the queue is empty: if the order holds all V nodes, it's valid. If not, the leftover nodes can never reach in-degree 0. There's a cycle.
Kahn's algorithm on 7 packages. The number in brackets is each package's in-degree: how many of its prerequisites aren't built yet. Run it, then tick the box and run it again: the queue empties early and the stuck packages turn red.
from collections import deque

def build_order(needed_by):
    """needed_by[p] = packages that need p first (arrows p -> q)."""
    waiting = {p: 0 for p in needed_by}         # in-degree of each package
    for p in needed_by:
        for q in needed_by[p]:
            waiting[q] += 1
    ready = deque(p for p in needed_by if waiting[p] == 0)
    order = []
    while ready:
        p = ready.popleft()
        order.append(p)                         # build p
        for q in needed_by[p]:
            waiting[q] -= 1                     # q waits for one fewer
            if waiting[q] == 0:
                ready.append(q)
    return order if len(order) == len(needed_by) else None   # None: a cycle

Each node enters the queue once and each arrow is crossed off once: O(V + E). Nodes that become ready together don't depend on each other, so a build system can compile them in parallel waves. Exercise 8 asks for those waves.

With the cycle box ticked, Kahn's algorithm builds log and http, and then the queue is empty with 5 of 7 packages left. What does that tell you about those 5?

Right. cfg → db → api → app → cfg is the cycle. docs isn't on it, but it needs db, which can never be built. To show the user the actual loop, run a three-colour DFS on the leftovers (exercise 7 returns the cycle).

A leftover still has in-degree above 0: one of its prerequisites was never built, so it's a leftover too. Keep stepping backwards through unbuilt prerequisites; with only 5 leftovers you must revisit one, and that's a cycle. But not every leftover is on it: docs waits on db, which is on cfg → db → api → app → cfg. Restarting can't help, since a leftover's in-degree only drops when a prerequisite gets built, and those are all stuck.

The DFS way: reverse the finishing order

Three-colour DFS also gives an order. A node turns black only after everything it points to is black, so writing nodes down as they turn black lists each one after everything it leads to. Reverse that list and every arrow points forward. In code: finished.append(node) where the node turns black, then return finished[::-1]. Meeting a gray node means a cycle: no order.

Both are O(V + E). Kahn's is a plain loop (no recursion limit), gives the parallel waves, and is easier to explain. The DFS version comes free with cycle detection and can point at the exact cycle.

A topological order lists every node after all its prerequisites, and it exists only if there's no directed cycle. Kahn's algorithm: repeatedly take a node with in-degree 0 and cross off its arrows. If the queue empties before all V nodes are out, there's a cycle. Both Kahn's and DFS are O(V + E).

9Choosing: BFS, DFS, or something else

Both searches cost O(V + E). What separates them is what the order of visits gives you, and how much memory the frontier needs.

Memory: rings versus corridors

BFS holds a whole ring; DFS holds the current path plus the neighbours waiting at each level. Which is smaller depends on the shape:

  • Bushy graphs: with 10 new neighbours per node, the ring 6 steps out can hold 10⁶ nodes; DFS holds a path of 6 plus about 10 waiting per level. DFS wins.
  • Grids: it flips. On an open 1,000 × 1,000 grid, BFS from the centre never queues more than 1,999 cells (a diamond-shaped ring). A stack DFS from a corner piles up 499,501 entries (region_size's loop), or 998,002 with dfs_order, which can push a cell twice.
Pick by what the question needs. Shortest with equal steps: BFS. Structure (cycles, order, finishing times): DFS. Just "reachable?" or "how many groups?": either. Weighted edges: neither; that's Dijkstra.

A delivery robot moves through a warehouse. Most aisles take 1 minute to cross, but a few crowded ones take 5. You want the fastest route. What do you use?

Right. BFS minimizes the number of aisles, so 2 crowded aisles (10 minutes) beat 4 quiet ones (4 minutes) in its eyes. Dijkstra swaps the queue for a priority queue ordered by total time: the shortest-paths chapter (02.08).

Put numbers on it. Route 1: 2 crowded aisles, 2 edges, 10 minutes. Route 2: 4 quiet aisles, 4 edges, 4 minutes. BFS returns route 1, because it guarantees fewest edges, which equals fastest only when every edge costs the same. A DFS tracking the best total must try every route, and there can be exponentially many. Dijkstra is BFS with a priority queue keyed on total time (chapter 02.08).

Go deeper: many starts at once, both ends at once, weights

Multi-source BFS. "How far is every cell from the nearest exit?" One BFS per exit costs O(exits × cells). Instead, put every exit in the queue at the start, all at distance 0, and run one ordinary BFS. Picture fires starting at every exit at once, spreading one cell per second: each cell is first reached from its nearest exit. The queue still comes out in rings, so section 4's proof holds. One search, O(V + E). This is "rotting oranges", and exercise 6.

Bidirectional BFS. For the distance between two given nodes, grow a BFS from each end, one ring at a time, until the frontiers meet. With b neighbours per node and an answer d hops away, one search touches about b^d nodes, two half-searches about 2 × b^(d/2): for b = 100, d = 6, up to 10¹² versus 2 × 10⁶. The classic follow-up to "word ladder".

Weights. Costs of only 0 or 1: 0-1 BFS puts 0-cost neighbours at the front of the deque, 1-cost at the back, still O(V + E). General non-negative weights: Dijkstra with a heap, O((V + E) log V). Negative weights: Bellman-Ford. All in chapter 02.08.

Go deeper: where these searches run in real systems
  • Build systems such as Make and Bazel build targets in dependency order and report cycles (Bazel as an error; GNU Make warns and drops an edge). Package managers vary: npm, for one, tolerates cycles.
  • Tracing garbage collectors (Java, Go, JavaScript engines) search from the roots (globals, every thread's stack) and mark what they reach; the rest is garbage.
  • Databases detect deadlock as a cycle in the "who waits for whose lock" graph, and abort one transaction to break it.
  • Web crawlers are a BFS from seed pages. The frontier grows into billions of URLs, so it lives on disk, split by domain, and the visited set may be a Bloom filter that trades a few false "seen" answers for far less memory.

10What to say in the interview

When a graph shows up, often in disguise, a strong answer sounds like this:

  1. Name the graph: "Each cell is a node; each move to an open neighbour is an edge. Undirected, unweighted, V = rows × cols, at most 4 edges per node."
  2. Pick the search and say why: "Fewest moves, all moves cost the same: BFS, because it explores in rings, so the first time I reach the exit is a shortest route." Or: "Prerequisites with a possible cycle: DFS with three colours, because in a directed graph 'already seen' isn't enough."
  3. Say the visited rule: "I mark a cell when I add it, so nothing is queued twice, and keep parent pointers to rebuild the path."
  4. Say the cost: "O(V + E) time: each node comes out once, each edge is looked at once. O(V) memory for the visited set and frontier."
  5. Cover the edge cases: "Unreachable parts: loop over every node if the question covers the whole graph. Start equals goal. No path: return None. Deep graphs in Python: my own stack, not recursion."
Go deeper: follow-up questions interviewers like
  • "The graph is huge or infinite." Generate neighbours on demand, stop at the goal, try bidirectional BFS. Short on memory: iterative deepening runs DFS with depth limits 1, 2, 3, …, finding the shortest answer with memory proportional to the depth, at the cost of repeating shallow levels.
  • "It's spread over 100 machines." One BFS ring per round: each machine expands the frontier nodes it owns and sends new neighbours to their owners. Rounds equal the farthest distance and each is a network exchange, so it suits graphs with few hops across, like social networks (the Pregel model).
  • "Word ladder: COLD to WARM, one letter at a time." Words are nodes, one-letter changes are edges, BFS. Find neighbours through patterns like C*LD instead of comparing every pair of words.
  • "Alien dictionary: find the alphabet these sorted words use." The first differing letter of each neighbouring pair gives an arrow; then topological sort. A cycle means inconsistent input, and so does a word listed before its own prefix ("abc" before "ab").
  • "Can you split them into two teams with no friends on the same team?" BFS colouring rings alternately; an edge inside one colour means no. That's checking the graph is bipartite.

✓What to remember

  1. A graph is nodes and edges. Store it as an adjacency list (dict of node → neighbours): V + E memory, versus V² for a matrix.
  2. Every search is one loop: a visited set so each node is handled once, plus a frontier. Each node comes out once and each neighbour list is read once: O(V + E).
  3. Queue (deque, never list.pop(0)) gives BFS: rings of distance, so the first visit is a shortest path when all edges cost the same. Mark on add. Parent pointers rebuild the path.
  4. Stack gives DFS: deep first, finds a path, not the shortest, but gives enter and leave moments. Python's recursion stops near 1,000 levels; keep your own stack for big inputs.
  5. Grids are implicit graphs: compute neighbours from coordinates. Count components by starting a search at every unvisited node, with one shared visited set.
  6. Undirected cycle: reaching a seen node by any edge except the one you came in on. Directed cycle: an edge to a gray node (on the current path). "Seen" alone gives false alarms.
  7. Topological order exists only without directed cycles. Kahn's: take in-degree-0 nodes, cross off their arrows; fewer than V output means a cycle. Or reverse the DFS finishing order.
  8. Weighted edges need Dijkstra, not BFS. Many sources at once: put them all in the queue at distance 0.

Warm-up · pen and paper

1. Trace both searches by hand

Use the 8-node graph from section 4 (edges A–B, A–C, B–C, B–D, C–E, D–E, D–F, E–H, F–G, G–H, neighbours in alphabetical order), but start at H. For BFS, write the queue after each node is taken out, and every node's distance and parent. For recursive DFS, write the order in which nodes are entered. How many hops does DFS take to reach G, and what is G's real distance?

Answers

BFS queue after each take: H → [E, G]; E → [G, C, D]; G → [C, D, F]; C → [D, F, A, B]; then D, F, A, B add nothing. Distances: H 0; E, G 1; C, D, F 2; A, B 3. Parents: E←H, G←H, C←E, D←E, F←G, A←C, B←C.

DFS enters H, E, C, A, B, D, F, G. It reaches G last, along H → E → C → A → B → D → F → G: 7 hops. G's real distance is 1 (it's H's neighbour). DFS only looks at H → G after the whole dive through E has finished.

(e) The cheapest flight route when every flight has a price. (f) Are any of these 30 threads deadlocked, waiting on each other's locks?

Answers

(f) Threads, with an arrow for "waits for a lock held by": directed cycle detection, three colours.

Warm-up · pen and paper

3. Break the naive versions

(a) Draw a directed graph with just 3 nodes where "reached an already-visited node" reports a cycle that isn't there. (b) Draw the smallest undirected graph where forgetting the came-from check reports a false cycle. (c) Draw an undirected graph where BFS with mark-on-take puts the same node in the queue 3 times.

Answers

(a) A → B, B → C, A → C, with A's list in the order [B, C]. DFS from A visits B, then C, finishes both, returns to A and sees A → C: C is visited (black), but there's no cycle. (b) Two nodes and one edge, A – B. From B, the list contains A, which is visited: without the came-from check, that's a false cycle. (c) S joined to A, B and C, and each of A, B, C joined to T. S adds A, B, C. Then A, B and C are each taken out before T is, and each adds T.
