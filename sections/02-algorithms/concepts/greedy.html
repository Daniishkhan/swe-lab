Chapter 2 · Part 10

Greedy algorithms, and how to prove them

P1 the "why is that right?" follow-upabout 55 minutes10 quick checks · 9 exercises

A greedy algorithm is the shortest code you'll write in an interview: sort, then one pass. It's also the easiest to get wrong without noticing, because a wrong greedy still returns a valid answer, just not the best one. So the interviewer's next question is almost always "why is that optimal?". This chapter is about answering it: two proof patterns that cover most problems, and a quick way to break a greedy rule before you bet the interview on it.

By the end you'll be able to

  1. Say what makes an algorithm greedy, and why "it gave a valid answer" proves nothing.
  2. Break a greedy rule with a counterexample of three or four items, by hand or with a brute-force hunt.
  3. Prove a greedy correct with "greedy stays ahead" or with an exchange argument, in three spoken sentences.
  4. Use those proofs on interval scheduling, deadlines, jump game, gas station, Huffman codes and the fractional knapsack.
  5. Tell when greedy fails (coins 1, 3, 4; the 0/1 knapsack) and switch to dynamic programming.

How to read this: top to bottom, like a book. It uses sorting, the meeting-room problems from intervals, and the coin story from dynamic programming. Answer each quick check before reading on; a wrong answer gets you a second explanation. "Go deeper" boxes are optional on a first read.

1The problem: one room, thirty requests

A recording studio has one room. For Saturday, 30 people have asked for a slot, each with a fixed start and end time. Two bookings can't overlap. The manager wants to say yes to as many people as possible.

The sure way is to try every subset of the 30 requests, throw out the ones with overlaps, and keep the biggest. Each request is in or out, so there are 230 ≈ 1.07 billion subsets. At 10 million subset checks a second that's nearly two minutes for 30 requests, and every extra request doubles it: 40 requests take over a day.

The manager doesn't do that. She uses a rule: "look at the requests in some order, and say yes to each one that still fits". That takes a sort and one pass, a few microseconds. The question is which order. "Earliest start first" sounds fair. "Shortest first" sounds efficient. Both are wrong, and neither one ever tells you so.

That rule is a greedy algorithm: it builds the answer one piece at a time, takes whatever piece looks best right now by a fixed rule, and never takes a piece back. It's fast because it never explores: one choice per step, no backtracking. That's also the risk. A choice that looks best now can block better choices later, and the algorithm never finds out.

Look at what a wrong greedy gives you: a schedule with no overlaps. It is a valid answer. It's just smaller than it could be. Nothing crashes, no test with a "valid?" check fails. That's why a greedy needs a proof, or at least a serious attempt to break it.

You try a greedy rule by hand on five inputs, and every time it produces a schedule with no overlaps. What have you shown?

Right. "Take each request if it still fits" can never create an overlap, whatever the order, so valid is guaranteed for free. Optimal means no other valid schedule is bigger, and to know that you need to compare against the best schedule (by brute force on small inputs) or prove it.

Separate two questions: "is this schedule allowed?" and "is there a bigger one?". Any rule of the form "take it if it doesn't clash" passes the first one every time, by construction, so checking it tells you nothing about the rule. To answer the second one you have to know the best possible size, which means trying every subset on small inputs or writing a proof. Five valid outputs answer only the first question.

2Four reasonable rules, three of them wrong

Here are four rules a sensible person might try for the studio. Each one sorts the requests somehow and then says yes to each one that doesn't clash with what's already booked. (Times are half-open, [start, end), as in the intervals chapter: a booking ending at 10 and one starting at 10 don't clash.)

  1. Earliest start first. First come, first served.
  2. Shortest first. Short bookings use up less of the day.
  3. Fewest clashes first. Take the request that overlaps the fewest others, remove what it clashes with, repeat.
  4. Earliest end first. Take the booking that frees the room soonest.

Before trying to prove any of them, try to break them. A counterexample is one input where the rule's answer is worse than the best answer. It only takes one, and it's usually tiny:

  • Earliest start dies on one long booking: [0, 10) starts first, so it's taken, and it blocks [1, 3), [4, 6) and [7, 9). The rule keeps 1; the best keeps 3.
  • Shortest first dies on a short bridge: [5, 8) is the shortest, but it overlaps both [0, 6) and [7, 13), which don't overlap each other. The rule keeps 1; the best keeps 2.
  • Fewest clashes is harder to break. The smallest trap people usually show has 11 bookings. It's in the figure.
  • Earliest end survives every attack. Sections 3 and 4 prove it can't be beaten.
rule input

Then pick a rule and press Hunt: it tries up to 20,000 random inputs of 3 to 8 bookings and shows the first one where the rule loses. Earliest start and shortest first fall at once. Greedy rules are cheap to try and cheap to break. Before proving anything, attack the rule with 3 or 4 items: one long item, one short item that bridges two others, ties. If a tiny input breaks it, you've saved yourself from proving something false.

A teammate suggests "latest start first", filling the day from the evening backwards: sort by start, from latest to earliest, and take each booking that fits. What's true?

Right. Flip the timeline, so time t becomes −t. Every start becomes an end and the other way round, and "the latest start" becomes "the earliest end". A rule that's optimal on the flipped day is optimal on the real one. Not every rule that sounds like a broken one is broken: try to break it, and if you can't, look for why.

Test it on the attackers. One long booking [0, 10) with [1, 3), [4, 6), [7, 9): the latest start is 7, so [7, 9) goes first, then [4, 6), then [1, 3); [0, 10) clashes. That keeps 3, the best. The short bridge [0, 6), [5, 8), [7, 13): latest start is 7, take [7, 13), then [5, 8) clashes, [0, 6) fits: 2, the best. Now run the clock backwards: every start becomes an end, and "latest start" becomes "earliest end", the rule that works.

3Proof one: greedy stays ahead

Earliest end survived. Why can't any plan beat it? Here's the first way to argue it, and it works by watching two plans side by side.

Picture two people booking the same room, each building a list of bookings from morning to evening. One uses the greedy rule. The other follows any valid plan you like, maybe the best one. After each of them has made k bookings, ask: whose k-th booking frees the room earlier? The claim is that greedy's always does, or ties. Greedy is never behind.

Eleven bookings sorted by end. First the greedy scan: each booking is taken (green) if it starts at or after the last taken end, or skipped (red). Then greedy's plan is lined up against another plan that also fits four bookings. Watch the two end marks at each step (green for greedy, dashed purple for the other plan): greedy's k-th end is never to the right of the other plan's.

Why can't greedy fall behind? Step by step, with gk for greedy's k-th booking and ok for the other plan's:

  1. Step 1. Greedy's first pick, g1, has the earliest end of all bookings. So it ends no later than o1, whatever o1 is.
  2. Step k. Suppose gk−1 ends no later than ok−1. The other plan's next booking ok starts at or after the end of ok−1, so it also starts at or after the end of gk−1. That means ok was still available to greedy at step k. Greedy took the available booking with the earliest end, so gk ends no later than ok.
  3. The finish. Suppose the other plan had more bookings than greedy: greedy stopped after m, but om+1 exists. Then om+1 starts at or after the end of om, which is no earlier than the end of gm, so it was available to greedy. But greedy only stops when nothing is available. That's a contradiction, so no plan has more bookings than greedy.

This pattern is called greedy stays ahead. Pick a measure of progress (here, "when does my k-th booking end?"). Show that after every step, greedy's measure is at least as good as any other plan's, by induction: step 1, then "if it was ahead before this step, it's still ahead after it". Then show that being ahead at every step means being at least as good at the end.

Greedy stays ahead: pick a progress measure, show greedy is at least as good on it after every step (induction), then show that implies the final answer is at least as good. For bookings: greedy's k-th booking always ends no later than any plan's k-th, so no plan fits more.
Explain it another way: two runners and a row of gates

Two runners race along the same track, and each must pass through gates. A gate counts only if you pass it after leaving your previous gate. The greedy runner always picks the next gate that lets them out soonest. Compare the runners after their 1st gate, their 2nd gate, and so on: the greedy runner is never further back on the track. So any gate the other runner can still use next is also still ahead of the greedy runner, and the other runner can never finish with one gate more.

Where the picture breaks: real runners can be ahead at one point and behind at another. The proof only works because greedy's lead can't shrink, and that's exactly what the induction step checks.

In the induction step, why is the other plan's booking ok available to greedy at step k?

Right. That's the whole trick: the lead from the previous step (gk−1 ends first) turns into a guarantee about this step (anything the other plan can do next, greedy can do too). Then greedy's rule, "earliest end among available", makes gk end no later than ok.

"Available" means "starts at or after greedy's last booking ends", so greedy may take it without a clash. Greedy does look at every booking, but most are not available: they clash with what it already took. And ok needn't have the earliest end; it's whatever the other plan chose. Use the numbers from the figure: greedy's 2nd booking [5, 7) ends at 7, the other plan's 2nd [5, 7) at 7, and the other plan's 3rd, [8, 12), starts at 8 ≥ 7. So greedy could have taken [8, 12), and it took [8, 11), which ends sooner.

4Proof two: the exchange argument

The second way to argue doesn't race two plans. It takes a best plan and edits it, one swap at a time, into greedy's plan, without ever making it worse.

Picture a finished jigsaw that someone else solved, and your own half-built one that follows a rule. You walk along both. At the first piece where they differ, you pull out their piece and put in yours. If the puzzle still fits together and is no worse, keep going. When you're done, their puzzle has become yours, and it was never worse than the best at any point. So yours is a best one too.

For bookings, with an optimal plan O (one with the most bookings possible):

optimal O:     [--- o1 ---)     [-- o2 --)     [-- o3 --)
greedy's g1:   [- g1 -)         ← ends no later than o1

swap o1 → g1:  [- g1 -)         [-- o2 --)     [-- o3 --)
               still no clash: o2 starts at or after o1's end,
               and o1 ends no earlier than g1
  1. Let o1 be O's earliest-ending booking. Greedy's first pick g1 has the earliest end of all, so g1 ends no later than o1.
  2. Swap o1 out and g1 in. Every other booking in O starts at or after the end of o1, so at or after the end of g1: no clash. The plan is still valid and has the same size, so it's still optimal, and now it starts with g1.
  3. Throw away g1 and every booking that clashes with it. Since no booking ends before g1 does, what's left is exactly the bookings that start at or after g1 ends: the same problem, smaller. The rest of O is a valid plan there, with one booking fewer, and greedy does exactly the same thing on it. Repeat the swap (induction), and O turns into greedy's plan without losing a booking.

The general recipe for an exchange argument:

  1. Take any optimal solution O.
  2. Find the first place where O differs from greedy's solution G.
  3. Show that swapping O's choice there for G's choice keeps O valid and doesn't make it worse.
  4. Repeat: each swap makes O agree with G in one more place, so eventually O becomes G, and G is optimal.

Which proof should you reach for? Stays-ahead fits when the answer is built step by step and you can name a running score ("how far have I got?"). An exchange fits when you can compare one choice with another directly ("this piece is at least as good as that piece"). Many problems allow both. In an interview, the exchange argument is usually quicker to say out loud.

Exchange argument: take any optimal answer, swap one of its choices for greedy's choice, and show it stays valid and no worse. Repeat until it is greedy's answer. Then greedy's answer is optimal.

In the swap, we replace o1 by g1. Why can't g1 clash with o2?

Right. A clash with o2 would need g1 to still be running when o2 starts. But g1 is over by the time o1 is over, and o2 waits for o1. Where g1 starts doesn't matter at all: only its end can bump into what comes after.

Only the end of g1 can collide with later bookings. Put numbers in: o1 = [2, 6), o2 = [6, 9), and g1 = [0, 5), which starts earlier and is longer than o1. g1 ends at 5, before o2 starts at 6, so no clash. Short or early-starting doesn't help: the shortest-first counterexample showed a short booking can clash with two. What matters is "ends no later than the booking it replaces".

Go deeper: an answer that proves itself

For closed intervals (touching counts as overlapping), greedy can hand you a certificate. Suppose you found k intervals that don't touch each other. Then any set of points that stabs every interval needs at least k points, one inside each of those k. And if you also find k points that stab every interval, then no set of non-touching intervals can have more than k members, since each one needs its own point. Two numbers that meet in the middle prove each other optimal, with no exchange argument at all. The greedy in exercise 4 finds both halves in one pass: each point it places is the right end of an interval that doesn't touch the previous one it aimed at. (The tests only ask for the points.)

This "two problems whose answers bound each other" idea is called duality. Max flow equals min cut is the famous case, and so is "rooms needed equals the biggest pile-up of overlapping meetings", from the intervals chapter.

5Exchanges for order: deadlines and lateness

Exchange arguments shine when the answer is an order. Here's a new problem. You have several jobs and one machine (or one person). Job i takes ti hours and is due at hour di. You run them one after another from hour 0, no gaps. A job that finishes at hour f is late by f − di if that's positive, and 0 otherwise. You want the order that makes the worst lateness, the biggest lateness of any job, as small as possible.

Try to break the obvious rules first, with two jobs each:

  • Shortest first. Jobs (1 hour, due 100) and (10 hours, due 10). Shortest first runs the 1-hour job, so the 10-hour job ends at 11: late by 1. The other order ends the 10-hour job at 10 and the short one at 11, well before 100: nobody late.
  • Least slack first. Slack is d − t, the spare time a job has. Jobs (1 hour, due 2) and (10 hours, due 10) have slack 1 and 0, so the 10-hour job goes first and the short job ends at 11: late by 9. Running the short job first makes the long one end at 11: late by only 1.
  • Earliest deadline first (EDD) survives both: in the first pair it runs the 10-hour job (due 10) first, and in the second it runs the 1-hour job (due 2) first. Both are the better orders.

Three jobs as (hours, due): A (2, 3), B (1, 9), C (4, 5). Run them by earliest deadline first. What's the worst lateness?

Right. Order A, C, B. A ends at 2 (due 3, fine), C ends at 6 (due 5, late by 1), B ends at 7 (due 9, fine). Worst lateness 1. A and C need 6 hours in total and the later of their deadlines is 5, so one of them must be late by at least 1: no order does better.

Write the order and the finish times out. Deadlines 3, 5, 9 give A, C, B. Finish times: 2, then 2 + 4 = 6, then 7. Compare each with its deadline: A 2 ≤ 3, C 6 > 5 (late by 1), B 7 ≤ 9. EDD minimizes the worst lateness, it doesn't promise zero: here A and C together need 6 hours before hour 5, which is impossible. And B going last doesn't make it late; its deadline is far away.

Now the proof, by exchange. Call a pair of jobs an inversion if the one with the later deadline runs first. EDD is exactly the order with no inversions. Take any order with an inversion. Somewhere in it, two neighbors must be inverted: if every neighbor pair were in deadline order, the whole list would be sorted by deadline. Swap those two neighbors, i (later deadline) and j (earlier deadline):

before:  | i: a hours, due d_i | j: b hours, due d_j |
         t                    t+a                  t+a+b

after:   | j: b hours, due d_j | i: a hours, due d_i |
         t                    t+b                  t+a+b

d_i > d_j: i is due later, yet it ran first
  • Everyone else starts and finishes at the same hours as before: the pair still fills exactly [t, t + a + b).
  • j now finishes earlier, so its lateness can only drop.
  • i now finishes at t + a + b, exactly when j used to. Same finish time, later deadline: (t + a + b) − di is smaller than (t + a + b) − dj, so i's new lateness is no more than j's old lateness. ("No more", not "less": both can be 0.)

So the pair's worst lateness after the swap is at most j's old lateness, which was already part of the old worst.

So the worst lateness doesn't go up, and there's one inversion fewer. Keep swapping and you reach an order with no inversions (there are at most n(n − 1)/2 to remove), never getting worse on the way. So EDD is at least as good as the order you started from, which could have been the best one.

One loose end an interviewer may pull: ties. Jobs with the same deadline aren't inverted either way, so there can be several "EDD orders". They all have the same worst lateness: swapping two neighbors with equal deadlines leaves the pair ending at t + a + b with the same deadline for whichever job is second, and the first one finishes earlier than that. So any order without inversions is optimal, whichever way you break ties.

Five jobs start in a bad order (deadline order reversed). Each step finds a neighbor pair whose deadlines are out of order (yellow) and swaps them. Watch the "worst lateness" number: it can stay the same or drop, but it never rises. The last frame is the EDD order.

Once you have the proof, the code is a sort:

def max_lateness_edd(jobs):               # jobs: list of (hours, due)
    t, worst = 0, 0
    for hours, due in sorted(jobs, key=lambda j: j[1]):   # earliest deadline first
        t += hours                        # this job finishes at hour t
        worst = max(worst, t - due)       # late by t - due, if that's positive
    return worst                          # O(n log n), all of it the sort
For "find the best order" problems, use the adjacent swap: take two neighbors in the wrong order, show swapping them changes nothing outside the pair and doesn't hurt inside it. Then sorting by the rule is optimal. For worst lateness, the rule is earliest deadline first.

Why does the proof swap neighbors rather than any two inverted jobs, say the 1st and the 5th?

Right. Swap jobs 1 and 5 and the jobs in between start earlier or later by the difference in their lengths, so their lateness changes in ways you'd have to track. Swap neighbors and the pair fills the same stretch of time as before. Only two numbers change, and you can compare them directly.

Inversions can be far apart (in the order due 9, due 5, due 3, the first and last jobs are inverted). The proof isn't code at all, so speed isn't the point. Picture the two jobs as two blocks on a timeline. If they're neighbors, they fill [t, t + a + b) before and after the swap, and nothing else moves. If there are jobs between them and the blocks have different lengths, every job in between shifts, and you'd have to argue about all of them.

6One pass, best so far: jumps and gas stations

Some greedy algorithms don't sort at all. They walk left to right once and keep one running number, "the best so far". Two interview favorites work this way.

Jump game: can you reach the end?

You stand on stone 0 of a row of stones. Stone i has a number nums[i]: from there you may jump forward up to that many stones. Can you reach the last stone? Trying every sequence of jumps is exponential. Instead, picture walking along the stones with a flashlight that shows the farthest stone you know you can reach. Each stone you step on may push the light farther. If you ever walk past the light, you're standing on a stone you can't actually reach, so the answer is no.

def can_jump(nums):
    reach = 0                           # farthest stone we know we can reach
    for i, step in enumerate(nums):
        if i > reach:                   # stone i is beyond every jump so far
            return False
        reach = max(reach, i + step)    # from stone i we can get this far
    return True                         # O(n) time, O(1) memory

Why is one number enough? Because the stones you can reach always form one unbroken stretch from stone 0. If you can land on stone r, you can land on any stone q before it too. Your path from 0 to r either lands on q, or jumps over it, from some stone p before q to a stone after it. A jump from p may be any length up to nums[p], so a shorter jump from p lands exactly on q. So "everything up to reach" is the whole picture, and walking past reach means you hit a gap you can never cross. The proof is stays-ahead in disguise. The claim after looking at stone i is "reach is the farthest stone reachable using jumps from stones 0 to i". Each step keeps it true: any stone reachable through stone i is at most i + nums[i]. The fewest-jumps version (exercise 5) thinks in rounds: every stone you can reach with one jump, then with two. Each round is a stretch of stones, and the next round ends at the farthest reach from inside the current one.

Gas station: where do you start?

Stations sit on a loop. Station i gives you gas[i] liters, and driving on to the next station burns cost[i]. Your tank starts empty. From which station can you drive the whole loop without running dry? Trying every start and driving until you fail is O(n²). The picture that solves it is a graph of your tank.

start at station
The line is the tank after each leg, for the start you pick. Red parts are below zero: you ran dry. These routes have exactly as much gas as they burn. Slide the start and watch the shape: it never changes, it only moves up or down and rotates around the loop. The start that works is the one right after the lowest point, because that lifts the whole line to zero or above.

Two facts fall out of the picture:

  1. If the total gas is less than the total cost, no start works. After a full loop the tank would hold total gas − total cost liters, which is negative, whatever the start.
  2. If it's at least the total cost, starting right after the lowest point works. The curve's shape is the running total of gas − cost; picking a start only shifts it. Start right after the lowest point, and that point becomes 0. Every other point was higher, so it stays at 0 or above. (If there's gas to spare, the stretch after you wrap past station 0 also gets the spare liters added, which only lifts it higher.)

You don't even need to find the lowest point by storing the curve. Start at station 0 and drive. If the tank first goes negative just after station i, then no station from your start up to i can be the answer: you arrived at each of them with a tank of zero or more, and still ran dry by i, so starting there with an empty tank would run dry by i too. Skip them all and try i + 1. One pass, O(n) time, O(1) memory; exercise 5 asks you to write it.

But the last start you try only gets driven up to station n − 1. Why trust it for the part after the wrap, without driving it? Because each reset happens exactly when the running total from station 0 drops below every value it had before: a new lowest point. So the last start is the station right after the lowest point, and fact 2 already proved that one works whenever total gas ≥ total cost. That's why the one pass needs only a check of the totals at the end, not a second lap.

Some greedy algorithms are one pass with one running number: the farthest reach, the tank level. The proof is an invariant ("after step i, this number is the best possible using items 0 to i") or a picture: start the gas loop right after the lowest point of the running total.

Starting at station 3, your tank first goes negative on the leg after station 7. Which stations can you rule out as the answer?

Right. You reached 4, 5, 6 and 7 with zero or more liters in the tank. Starting at any of them means arriving there with exactly zero, which is no better, so you'd also run dry after 7. Stations 0 to 2 are untested: the next try starts at station 8, and if the total gas covers the total cost, a start exists among the ones left.

Think about what the tank held when you passed each station. Starting at 3, you pulled into station 5 with, say, 4 liters, and still ran dry after 7. Starting at 5 instead gives you 0 liters at station 5, which is worse than 4, so you'd also run dry by 7. The same holds for 4, 6 and 7. Stations 0 to 2 come before your start, and you haven't driven through them yet in this attempt, so you know nothing about them.

7Huffman codes: greedy builds a tree

A text file has 100,000 characters, all from six letters, with these counts in thousands: a 45, b 13, c 12, d 16, e 9, f 5. Six letters need 3 bits each in a fixed-length code (23 = 8 ≥ 6), so the file is 300,000 bits. But a is nearly half the file. Giving a a 1-bit code and the rare letters longer ones should save a lot. How do you choose the codes?

First a trap. Codes a = 0, b = 01, c = 10 look fine, but the bits 010 could be "a c" (0 + 10) or "b a" (01 + 0). To read a stream of bits without separators, no code word may be the start of another. Such a code is called prefix-free.

The picture that makes prefix-free codes easy is a binary tree: start at the root, go left for 0 and right for 1, and put each letter on a leaf, a node with no children. A letter's code is the path to its leaf, so its code length is its depth. No code is the start of another because no leaf sits on the path to another leaf. Decoding is walking down from the root until you hit a leaf, then starting again.

              (100)
            0/     \1
         a 45      (55)
                 0/    \1
              (25)      (30)
             0/  \1    0/   \1
           c 12  b 13 (14)  d 16
                     0/  \1
                    f 5   e 9

codes:  a = 0   c = 100   b = 101   d = 111   f = 1100   e = 1101
total:  45·1 + (12+13+16)·3 + (5+9)·4 = 224 thousand bits, not 300

The cost of a tree is the sum of count × depth over all letters: the length of the encoded file. David Huffman found the greedy that builds the cheapest tree in 1952, as a student who chose a term paper over his final exam: take the two rarest letters, make them siblings under a new node whose count is their sum, and treat that node as one new letter. Repeat until one tree is left.

The six letters start as six one-node trees. Each step takes the two trees with the smallest counts (yellow), joins them under a new node (blue) that holds the sum, and puts it back. Five merges later one tree is left. The last frame reads off the codes: 224 thousand bits.

Why is "merge the two rarest" safe? An exchange argument, then a shrink:

  1. Some best tree has the two rarest letters as siblings at the bottom. Take any best tree. Its deepest level has two leaves that are siblings (a deepest node can't be an only child, or you could move it up and save bits). Swap the two rarest letters into those two spots. A rare letter moving deeper and a more common letter moving up can only lower count × depth in total, so the tree is still a best one. In numbers: swap a rarest letter x (count fx, depth dx) with the letter y in a deepest spot (count fy ≥ fx, depth D ≥ dx). The cost changes by (fy − fx)(dx − D), a number ≥ 0 times a number ≤ 0, so it can't go up.
  2. Merge them and the problem shrinks. Glue those two siblings into one letter whose count is their sum. Every tree for the n letters with them as siblings matches a tree for the n − 1 letters, costing exactly (sum of the two counts) more. So the best tree for n letters is the best tree for n − 1 letters with the merged node split back into two. Greedy solves the smaller problem the same way, and induction does the rest.

With the trees in a heap, each merge is two pops and a push, so n letters cost O(n log n). (If the counts arrive already sorted, two plain queues do it in O(n): the merged counts come out in increasing order, so the two smallest are always at the front of one queue or the other.) Exercise 7 has you write it, codes and all. Huffman codes are inside DEFLATE, the compression in gzip, zip and PNG, and inside JPEG. "Optimal" has a fine print an interviewer may probe: it is the best code that gives each letter its own whole number of bits. A letter that is 99% of the text still costs a full bit each time, though the theoretical floor for a letter that common is about 0.015 bits (log₂ of 1/0.99). Arithmetic coding and ANS (inside zstd) spend fractions of a bit per letter and beat Huffman there.

Huffman: repeatedly merge the two rarest trees. It's optimal because some best tree has the two rarest letters as deepest siblings (exchange), and merging them leaves the same problem with one letter fewer (shrink). Heap: O(n log n).

Counts are a 5, b 2, c 2, d 1. What does Huffman merge first, and what is a's code length?

Right. Merge d 1 + b 2 = 3. Now the counts are 5, 2 (c), 3: merge c 2 + 3 = 5. Now a 5 and 5: merge to 10. a sits right under the root (1 bit), c at depth 2, b and d at depth 3. Total: 5·1 + 2·2 + 2·3 + 1·3 = 18 bits, against 20 for two bits each.

Huffman always starts from the rarest, never the most common: the most common letter should end up near the top, so it's merged last. Two bits each is the fixed-length code, and it costs 2 × 10 = 20 bits. Run the rule: d 1 and one of the 2s merge into 3; then the other 2 and that 3 merge into 5; then a 5 and that 5 merge. a hangs directly under the root: a 1-bit code. Total 18 bits.

8When greedy breaks: coins and knapsacks

Now the cases where the exchange argument fails, because seeing where it fails tells you when to stop trusting greedy.

The fractional knapsack, where greedy works

A thief has a bag that holds 50 kg and finds three sacks: 10 kg of spice worth $60, 20 kg worth $100, and 30 kg worth $120. The dust can be poured, so he may take any part of a sack. Greedy: sort by value per kg (6, 5 and 4 dollars per kg), and pour in the best first. That's all of the first two (30 kg, $160) and 20 of the 30 kg of the third ($80): $240.

The exchange argument: suppose a best bag holds some kg of a worse sack while a better sack isn't used up. Swap one kg of the worse for one kg of the better. Same weight, more value. So a best bag never leaves a better sack unfinished while holding a worse one, and that's exactly greedy's bag.

def fractional_knapsack(items, capacity):     # items: list of (kg, value)
    total = 0.0
    for kg, value in sorted(items, key=lambda it: it[1] / it[0], reverse=True):
        if capacity <= 0:
            break
        take = min(kg, capacity)              # all of it, or the part that fits
        total += value * take / kg
        capacity -= take
    return total                              # O(n log n), for the sort

The 0/1 knapsack, where it doesn't

Now the sacks are sealed boxes: all or nothing. Same greedy: take the $60 box (10 kg) and the $100 box (20 kg). The $120 box weighs 30 kg and only 20 kg is left, so it doesn't fit: $160. But the 20 kg and 30 kg boxes fit together, exactly 50 kg: $220.

The exchange argument broke at "swap one kg". Boxes can't be split, so you can only swap whole boxes, and a better box may be too heavy for the space a worse one leaves. Choices now interact: which box you take changes what fits later. That's the signal for dynamic programming, which tries every choice but solves each "capacity left" once (the DP chapter, section 5).

Coins

"Fewest coins: take the biggest coin that fits, repeat." With US coins, 1, 5, 10 and 25 cents, it's optimal. With coins 1, 3 and 4 and an amount of 6 it isn't: greedy pays 4 + 1 + 1, three coins, while 3 + 3 is two. Even a real coin system breaks if you remove one coin: with 1, 10 and 25 cents (no nickel), 30 cents is 25 + five 1s, six coins, against three 10s.

The exchange fails because swapping one big coin for small ones isn't a fair trade in general: whether the 4 was a good idea depends on what's left after it. Greedy is optimal only for special coin systems, called canonical ones, and you need a proof (or a check) for each system.

Greedy fails when the exchange can't be done: a choice can't be split (0/1 knapsack), or its value depends on what's left (coins 1, 3, 4). If you can't make the swap fair, expect a counterexample, and switch to DP.

A bag holds 10 kg. Boxes (all or nothing): 6 kg worth $30, 5 kg worth $20, 5 kg worth $20. Greedy by value per kg takes what, and what's best?

Right. The 6 kg box has the best ratio, $5 per kg against $4, so greedy takes it first. That leaves 4 kg, and both other boxes need 5. The two 5 kg boxes fill the bag exactly for $40. The best ratio wasted 4 kg of space, and with sealed boxes there's no sliver to fill it.

Run greedy literally. Ratios: 30/6 = 5, and 20/5 = 4 for both others. So the 6 kg box goes first, and 4 kg are left. A 5 kg box doesn't fit, and you can't take part of a sealed box ($46 would be the fractional answer). So greedy ends at $30. Compare with the 5 + 5 pair: 10 kg exactly, $40. The swap "trade a kg of worse for a kg of better" is impossible here, which is exactly where the greedy proof breaks.

Go deeper: matroids, and other greedy algorithms you already know
  • Matroids. There's a precise answer to "when is 'take the most valuable item that keeps the set allowed' optimal for every choice of values?": when the allowed sets form a matroid. That means any subset of an allowed set is allowed, and if one allowed set is bigger than another, you can always add some element of the bigger one to the smaller one and stay allowed (the exchange property, built into the definition). Sets of edges with no cycle form one, which is why Kruskal's algorithm works (minimum spanning trees). Sets of one-hour jobs that can all finish by their deadlines form one too, so "take the best-paying job that still fits" is optimal for them. Jobs of different lengths don't form a matroid, which is why exercise 6 needs its own exchange argument.
  • Dijkstra's algorithm is greedy: settle the closest unsettled node. Its proof is stays-ahead ("every settled distance is final"), and it breaks with negative edges for the same reason greedy coins break: a bad-looking choice can pay off later (shortest paths).
  • Coin systems. Checking whether greedy is optimal for a coin system is easy to do by machine: compare greedy with the DP for every amount up to a bound. A known result (Kozen and Zaks, 1994) says that if greedy ever fails, it already fails for some amount below the sum of the two largest coins.
  • Greedy as an approximation. When greedy isn't optimal, it's sometimes provably close. For "cover every element with the fewest sets", greedy (take the set that covers the most new elements) is within a factor of about ln n of the best, and doing much better is believed to be impossible in polynomial time.

9The interview move: try, hunt, prove or switch

Put together, the chapter gives you a routine for any problem where a greedy rule comes to mind:

  1. Say the rule in one sentence. "Sort by end time, take every booking that starts after the last one I took."
  2. Attack it on tiny inputs. Spend a minute on 2 to 4 items: one long item, a short item that bridges two others, ties, a zero. Say the attempts out loud; interviewers like seeing it.
  3. If it breaks, switch. The counterexample usually shows why: choices interact. That points to DP (a few numbers describe "where you are") or to search.
  4. If it survives, prove it. Choose stays-ahead or exchange, and say it in three sentences.

At home, or in a practical round with a laptop, step 2 can be automated. Write the brute force, which is short and obviously right, and compare it with the greedy on thousands of random small inputs:

import itertools, random

def best_by_brute_force(bookings):            # the slow, sure answer: every subset
    for r in range(len(bookings), 0, -1):
        for plan in itertools.combinations(bookings, r):
            if all(a[1] <= b[0] or b[1] <= a[0] for a, b in itertools.combinations(plan, 2)):
                return r
    return 0

def hunt(greedy, tries=10_000, seed=1):
    rng = random.Random(seed)
    for _ in range(tries):
        starts = [rng.randint(0, 10) for _ in range(rng.randint(1, 7))]
        bookings = [(s, s + rng.randint(1, 5)) for s in starts]
        if greedy(bookings) != best_by_brute_force(bookings):
            return bookings                   # a counterexample: shrink it by hand
    return None                               # evidence, not a proof

Keep inputs small, so the brute force stays fast and the counterexample you find is easy to read. Use small value ranges, so ties and touching ends actually happen. And remember the figure in section 2: "fewest clashes" passes this hunt even though it's wrong, because its smallest traps need around ten bookings. A hunt that finds nothing raises your confidence. It doesn't replace the proof.

Try the greedy, hunt for a counterexample on tiny inputs (by hand, or brute force against greedy on random cases), then either prove it with stays-ahead or exchange, or switch to DP. Most of the credit is in the reasoning, not the sort.

Your greedy agrees with brute force on 10,000 random inputs of up to 7 items. The interviewer asks "is it correct?" What's the best answer?

Right. The hunt is how you decide the rule is worth proving. The proof is what answers the question. Inputs of up to 7 items can't contain a trap that needs ten or so, and "fewest clashes" is exactly that kind of rule.

Two separate things: evidence and proof. Random tests on small inputs are good evidence, but some wrong rules only fail on bigger inputs (fewest clashes needs around ten bookings), so "overwhelming" overstates it. And you don't need every input: a proof covers all of them at once, because it argues about an arbitrary optimal answer. Say what the hunt shows, then give the three-sentence argument.

10What to say in the interview

A strong greedy answer sounds like this, before or alongside the code:

  1. Name the brute force and its cost. "Trying every subset of bookings is 2ⁿ. I think a greedy works here."
  2. State the rule, and what you tried to break it with. "Sort by end time and take what fits. Earliest start fails on one long booking and shortest first fails on a short one bridging two others; earliest end handles both."
  3. Give the proof in three sentences. "Take any optimal plan. Its first booking ends no earlier than mine, so swapping mine in keeps it valid and the same size. Repeating that turns it into my plan, so mine is optimal."
  4. Give the cost. "O(n log n) for the sort, then one O(n) pass; O(1) extra memory beyond the sort."
  5. Name where it would break. "If bookings had values and I wanted the most total value, greedy fails and I'd do DP over bookings sorted by end, with a binary search for the last compatible one."
Go deeper: follow-up questions interviewers like
  • "What about k rooms?" The most bookings in k rooms: still sort by end, and give each booking to the room that freed up most recently among those already free, and skip it if none is (keep the rooms' end times sorted). The fewest rooms for all bookings is a different problem, solved by the sweep in the intervals chapter.
  • "Ties?" Two bookings with the same end: either works; the exchange argument doesn't care. Say so, so it's clear you thought about it.
  • "Prove EDD." Adjacent swap: an inverted neighbor pair fills the same time before and after, the earlier-due job finishes sooner, the later-due job finishes when the other one used to and has the later deadline.
  • "Why not greedy?" for a DP problem: have the counterexample ready (coins 1, 3, 4 for 6; boxes 10/20/30 kg in a 50 kg bag).
  • "The data streams in." Some greedy algorithms work online (jump game, gas station, the one-pass part of interval scheduling once sorted). Sorting needs all the data first, so say what you'd do if the bookings arrived in end order already.

✓What to remember

  1. Greedy: one choice per step by a fixed rule, never undone. Fast (usually a sort and a pass), and a wrong one still returns a valid answer.
  2. Break rules on tiny inputs first. Earliest start dies on one long booking, shortest first on a short bridge, least slack on (1 h, due 2) and (10 h, due 10).
  3. Stays ahead: a progress measure, greedy at least as good after every step (induction), so at least as good at the end. Bookings: greedy's k-th end is never later.
  4. Exchange: take an optimal answer, swap in greedy's choice, show it stays valid and no worse, repeat.
  5. Orders: swap an inverted neighbor pair. Worst lateness: earliest deadline first.
  6. One pass: jump game keeps the farthest reach; gas station starts right after the lowest point of the running total, and fails if total gas < total cost.
  7. Huffman: merge the two rarest. 224 vs 300 thousand bits for the six-letter example. O(n log n) with a heap.
  8. Greedy fails when the exchange isn't fair: 0/1 knapsack ($160 vs $220), coins 1, 3, 4 for 6. Then use DP.
  9. Interview routine: rule, hunt, prove or switch. A passed hunt is evidence, not proof.

Warm-up · pen and paper

1. Break it, or explain why you can't

For each rule, find the smallest input where it isn't optimal, or say which proof shows it is. (a) Fewest jumps to the last stone: "always jump as far as you can". (b) Fewest coins with coins 1, 5 and 12: "biggest coin first". (c) Most bookings in one room: "take the booking with the latest start first". (d) Worst lateness: "longest job first".

Answers

(a) Breaks: [2, 4, 1, 1, 1, 1]. Jumping 2 lands on a 1, then it takes 4 jumps in all; jumping 1 to the 4 reaches the end in 2. (b) Breaks at 15: greedy gives 12 + 1 + 1 + 1, four coins; 5 + 5 + 5 is three. (c) Optimal: it's earliest end on a reversed clock (the check in section 2). (d) Breaks with two jobs: (1 h, due 1) and (5 h, due 10). Longest first ends the short job at 6, late by 5; EDD makes nobody late.

Warm-up · pen and paper

2. Trace EDD and Huffman by hand

(a) Jobs as (hours, due): (3, 4), (2, 6), (1, 8), (4, 9). Write the EDD order, each finish time and lateness, and the worst lateness. Then find one inverted neighbor pair in the order "(4, 9), (3, 4), (2, 6), (1, 8)" and check that swapping it doesn't raise the worst lateness. (b) Counts: a 10, b 1, c 1, d 2, e 4. Draw the Huffman tree, list the codes, and compare the total with a fixed 3-bit code.

Answers

(a) EDD is the given order: finish times 3, 5, 6, 10; latenesses 0, 0, 0, 1; worst 1. The bad order finishes at 4, 7, 9, 10: latenesses 0, 3, 3, 2, worst 3. The first pair is inverted (due 9 before due 4). Swapping it gives (3, 4), (4, 9), (2, 6), (1, 8): finish 3, 7, 9, 10, latenesses 0, 0, 3, 2, worst 3. Not worse, and one inversion fewer. (b) Merge b + c = 2; then d 2 with that 2 = 4; then e 4 with that 4 = 8; then a 10 with 8. Codes: a 0, e 10, d 110, b 1110, c 1111 (or with 0 and 1 swapped somewhere). Total 10·1 + 4·2 + 2·3 + 1·4 + 1·4 = 32 bits, against 18 × 3 = 54.

Warm-up · pen and paper

3. Greedy or DP?

Pick the tool and give a one-line reason. (a) Fewest coins with 1, 5, 10, 25. (b) The most value in a bag of poured spice. (c) The most value in a bag of sealed boxes. (d) The most bookings in one room. (e) The most total fee from bookings, each with its own fee. (f) The fewest jumps to the last stone.

Answers

(a) Greedy: this system is canonical (DP also works). (b) Greedy by value per kg: you can swap one kg for one kg. (c) DP: boxes can't be split, so 10/20/30 kg in 50 kg breaks greedy. (d) Greedy, earliest end. (e) DP: one big fee can beat many small ones, so sort by end and take the better of "skip it" and "take it plus the best up to the last compatible booking". (f) Greedy, in rounds of reach (a BFS where each layer is a stretch of stones).

Core · code

4. fewest_stabs(intervals) and fewest_to_cover(clips, T)

Two cousins of the booking problem in greedy_intervals.py. Stabs: the fewest points that hit every closed interval (arrows through balloons). Cover: the fewest clips whose union covers [0, T]. Both are a sort and one pass, and both have a stays-ahead or exchange proof you should say out loud. The tests compare with brute force on small inputs, use big inputs whose answers are known by construction, and count comparisons on 2,000 intervals: 3 n log₂ n + 10 n is the budget, so re-scanning every interval for each new point fails.

Core · code

5. min_jumps(nums) and circuit_start(gas, cost)

The two one-pass problems from section 6, in gas_station.py. The fewest jumps is jump game in rounds; the gas station returns a start that works, or −1. The lists count every read: 3 reads per item for jumps (with a 2-second cap on 30,000 long jumps, which kills the "update every stone in reach" table), 2 reads per station per list for the loop (the adversarial input makes "try every start" read about n² items), and tracemalloc checks that both use O(1) extra memory.

Core · code

6. most_on_time(jobs) and best_weighted_order(jobs)

Exchange arguments for scheduling, in job_scheduling.py. First: skip jobs so that as many as possible finish by their deadlines. Walk in deadline order, and when the newest job would be late, drop one job. Which one, and why is it safe? Second: run every job, where each costs its weight times its finish time; derive the sort key from an adjacent swap. The tests check against brute force (every subset, every order) on small inputs and count comparisons on 3,000 jobs, including on any key you compute from the numbers.

Core · code

7. huffman_code(freqs)

Build the code words, not just the cost, in huffman_code.py. The tests check that the code is prefix-free and that the total length is the smallest possible: against brute force over every merge order on small inputs, against 2,048 equal counts (exactly 11 bits each), and against an offline total for 2,000 random counts. They count comparisons between counts, with a budget of 12 n log₂ n; scanning for the two smallest every round needs about 4 million. A timed test on 524,288 symbols also catches a sorted list kept with pop(0) or insort: few comparisons, but each call shifts every item after the spot it touches. Careful with ties in a heap of tuples: Python will try to compare your trees.
