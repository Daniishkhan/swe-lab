Chapter 2 · Part 14

Rate limiting

P1 a favourite system design follow-upabout 50 minutes10 quick checks · 9 exercises

Every public API, login page and payment endpoint has a bouncer that says "not so fast". The algorithms behind it are small: a counter, a queue, a jar of tokens. The interview questions around them are not. Why does the simple version let twice the limit through? How do you store this for 10 million users? What happens when 20 servers share one limit, or when the clock jumps? This chapter builds the four classic limiters one fix at a time, then takes them to many servers.

By the end you'll be able to

  1. Show, with numbers, why a fixed window counter lets 2× the limit through at a window boundary.
  2. Explain the sliding window log, the sliding window counter, the token bucket and the leaky bucket, and price each one's memory per key.
  3. Write the lazy refill math for a token bucket, and say why it uses a monotonic clock and no timers.
  4. Pick a limiter for a given job, and defend the pick against the obvious alternative.
  5. Share one limit across many servers with Redis without race conditions, and say what to send back to a client you turn away.

How to read this: top to bottom. It leans on the sliding window idea from Two pointers, sliding window, prefix sums and on hash maps and queues from chapter 1. Answer each quick check before reading on; a wrong answer gets you a second explanation. "Go deeper" boxes are optional on a first read.

1The problem: one noisy neighbour

You run the API for an online shop. Your servers can handle about 2,000 requests a second in total, and on a normal day they see 1,200, from about 40,000 customers.

On Friday one customer ships a bug: a retry loop with no pause. It sends 3,000 requests a second. Now the servers get 4,200 a second. Requests queue up, every page takes 10 seconds, and 39,999 customers who did nothing wrong see timeouts.

What you want is a rule like "each API key gets at most 100 requests per minute", checked at the door before any real work happens. A request over the limit gets a fast, cheap "no" (an HTTP 429, section 10), and the server keeps its capacity for everyone else. That rule is a rate limiter. A key is whatever you count by: an API key, a user id, an IP address.

The rule sounds like one line of code. It isn't, because the limiter itself has to be cheap:

  • Time: it runs on every request, so it must be O(1). A limiter that scans a user's history costs more than the request it protects.
  • Memory: it keeps something for every key. Multiply by 10 million keys before you pick what that something is.
  • Accuracy: it must not let much more than the limit through, and it must not block people who stay under it.

Why not just cap the whole server at 2,000 requests a second, instead of limiting each key?

Right. A global cap protects the server, but not the other customers. With 3,000 a second from one client and 1,200 from everyone else, a first-come cap of 2,000 admits roughly 2,000 × 3,000/4,200 ≈ 1,430 from the noisy client and only about 570 of the 1,200 good ones. Per-key limits are about fairness: one key can't eat everyone's share. Real systems often have both: per-key limits, plus overall load shedding as a last line of defence.

Picture a nightclub with a fire limit of 200 people, and one group of 150 that keeps pushing to the front of the line. The fire limit keeps the building safe, but the group still fills most of the room. Same here: a cap of 2,000 a second keeps the server alive, but about 1,430 of those slots go to the buggy client (3,000 of every 4,200 arrivals). Per-key limits are what stop one customer from taking everyone else's share. And memory isn't the issue: a global cap is one counter.

2First try: count per minute

The simplest thing that could work: give each key a turnstile counter that resets every time the clock hits a new minute. Minute 12:00 has its own count, minute 12:01 starts again from 0. This is the fixed window counter. A window is the stretch of time you count over; "fixed" means the windows are glued to the clock, 12:00–12:01, 12:01–12:02, and so on.

counts = {}                        # key -> (window number, count)

def allow(key, now, limit=100, window=60):
    w = int(now // window)         # which minute are we in?
    start, n = counts.get(key, (w, 0))
    if start != w:                 # a new minute: forget the old count
        n = 0
    if n >= limit:
        return False               # over the limit: reject, count nothing
    counts[key] = (w, n + 1)
    return True

That's O(1) time and two numbers per key. It's what many real systems ran first, and it's often good enough. But look at what happens at the edge between two windows.

The boundary burst

The limit is 100 per minute. A client sends nothing for most of minute 12:00, then 100 requests at 12:00:59. All pass: that minute's count was 0. One second later, at 12:01:00, a new window starts and the count resets. The client sends 100 more, and all of them pass too.

That's 200 requests in about 2 seconds, from a limiter that promises 100 per minute. Any 60-second stretch that straddles the boundary (12:00:30 to 12:01:30, say) holds 200. The fixed window only promises "at most 100 per calendar minute", not "per any 60 seconds".

A fixed window counter is O(1) time and O(1) memory per key, but it resets all at once at the boundary. A client who times it right gets 2× the limit in a few seconds: a full window's worth just before the reset and another just after.

Fixed window, limit 100 per minute. What's the most requests one client can get through in some 60-second stretch?

Right. 100 at the very end of one window, 100 at the very start of the next: about 200 inside a couple of seconds, and so inside one 60-second stretch. It can't be more than 200, because any 60-second stretch overlaps at most two fixed windows, and each window lets in at most 100.

Count windows, not minutes. A 60-second stretch that doesn't line up with the clock always overlaps exactly two fixed windows (unless it lines up perfectly, then one). Each fixed window lets in at most 100. So the worst case is 100 + 100 = 200, and you reach it by bunching both hundreds right next to the boundary. It's never "no limit": each window still stops at 100, so over an hour the client still gets about 6,000, not more.

3Keep every timestamp: the sliding window log

The flaw was that the count resets all at once. The fix: don't reset anything. Instead, every request "expires" on its own, exactly 60 seconds after it happened. Then the question "how many in the last 60 seconds?" has an exact answer at every moment, not just at the start of each minute.

Picture a sign-in sheet at a gym that only lets 100 visits per hour. Each visitor writes the time. When someone new arrives, the front desk first crosses out every line older than an hour, then counts the lines left. Under 100: sign in. Otherwise: come back later. This is the sliding window log: a log (list) of timestamps per key, and a window that slides along with the current time.

Old timestamps always leave from the front (they're the oldest), and new ones join at the back. That's a queue, so a deque (double-ended queue: O(1) add and remove at both ends) is the right container:

  1. Pop from the front every timestamp that is 60 seconds old or more.
  2. If fewer than limit are left, append now at the back and allow.
  3. Otherwise reject.
A sliding window log with limit 3 per 10 seconds. Red cells are timestamps falling out of the window (now − t ≥ 10), green ones are still inside, blue is the request just logged. Step through and watch the deque never hold more than 3.

What it costs

Time: one step might pop many old timestamps, which looks like O(n). But each timestamp is pushed once and popped at most once, ever. Over a million requests that's at most two million deque operations: amortized O(1) per request, the same "count the total moves" argument as the sliding window chapter.

Memory: up to limit timestamps per key. At 100 per minute that's 100 × 8 bytes = 800 bytes per busy key, raw. In Python each float is a 24-byte object plus an 8-byte slot in the deque, so about 3 KB. With 10 million keys and a limit of 1,000 per hour, the raw timestamps alone are 80 GB. Exact, but expensive. Section 11 prices all four limiters side by side.

The sliding window log is exact: it answers "how many in the last 60 seconds" by keeping each accepted request's time and dropping it when it's 60 seconds old. Amortized O(1) time, but O(limit) memory per key.

A sliding window log, limit 100 per minute, logs every request, including rejected ones. A client retries forever at 2 requests per second. What happens?

Right. At 2 a second, every 60-second stretch holds 120 logged attempts. The log never drops below 100, so every request is rejected, forever, even though the client is "only" asking for 120 a minute. That's why the usual choice is to log only accepted requests. (Logging rejected ones is a valid knob if you want to punish clients that don't back off, but choose it on purpose.)

Run the sign-in sheet, now with a one-minute window: the desk writes down everyone who tries to enter, even those turned away. A person knocking twice a second adds 120 lines every minute, and each line is only crossed out a full minute after it was written. The sheet never has fewer than 100 lines, so the door never opens again. With "log only the accepted ones", the client gets exactly 100 per minute and is turned away for the other 20.

4Two counters and a guess: the sliding window counter

The log is exact but stores up to 100 timestamps per key. The fixed window stores 2 numbers but lets 2× through. Can we keep almost the accuracy of the log at almost the cost of the counter?

Keep the fixed windows, but remember two counts per key: this minute's and last minute's. Then estimate how many requests fall in the true last 60 seconds by assuming last minute's requests were spread evenly across it.

The worked example from the sliding window chapter: limit 100 per minute. It's 15 seconds into the current minute. This minute has 30 requests so far; last minute had 80.

         previous minute (80)          current minute (30 so far)
   |------------------------------|---------------|
   0s            15s             60s     now = 75s
                 [============ last 60 seconds ====]
                 \_ 45 s of the previous minute _/  \_ 15 s _/

   estimate = 80 × 45/60 + 30 = 60 + 30 = 90     → under 100: allow

The rolling 60-second window covers the last 45 seconds of the previous minute, which is 3/4 of it. If its 80 requests were spread evenly, about 3/4 × 80 = 60 of them are still "inside". Add the 30 from this minute: about 90. This is the sliding window counter. In general:

elapsed  = time since the current window started
estimate = previous × (window − elapsed) / window  +  current

Now replay the boundary burst. 100 requests at 0:59, then 100 more at 1:00. At 1:00, elapsed is 0, so the previous minute counts in full: estimate = 100 × 60/60 + 0 = 100. Full: the second hundred is rejected. As the minute goes on, the old hundred fades out at 100/60 ≈ 1.7 requests per second, and new requests can take its place at that pace. The 2-second burst of 200 is gone.

Where the guess is wrong

The "spread evenly" assumption is the weak spot. If last minute's 80 requests all came in its final second, they're all really inside the window, and the estimate (60) is too low. If they all came in its first second, none are, and the estimate is too high. A client who knows the trick can get close to 2× over a full minute: 100 at 0:59.9, then a steady trickle that the fading estimate allows, ending near 199 inside the stretch 0:59.9 to 1:59.9. But never as a sudden burst. In practice traffic isn't that adversarial: Cloudflare, which uses this method, measured it on 400 million real requests and found 0.003% were wrongly allowed or wrongly limited.

The sliding window counter keeps two counts per key and weights last window's count by how much of it still overlaps the rolling window. O(1) time and O(1) memory, no boundary burst, and an error that only matters when traffic is bunched on purpose.

Limit 100 per minute. 45 seconds into the current minute, it has 40 requests so far; the previous minute had 80. What does the sliding window counter estimate?

Right. 45 seconds in, only the last 15 seconds of the previous minute still overlap: 15/60 = 1/4 of it. 80 × 1/4 = 20, plus the 40 from now: 60.

Draw it. The rolling window is the last 60 seconds: 45 seconds of this minute, and the 15 seconds just before it, which are the end of last minute. So only 15/60 = a quarter of last minute counts: 80 × 1/4 = 20. Add this minute's 40 in full: 60. 120 counts both minutes in full (that's a 2-minute window); 100 weights the wrong share (3/4 of 80 is the part that's already outside).

5A jar of tokens: the token bucket

All three counters answer one question: "how many in the last window?". But that's often not what you mean. A photo app wants to let you upload 20 pictures at once after a quiet hour, and still stop a script that uploads 2 a second all day. That's two separate wishes: a burst (how much at once) and a sustained rate (how much over time). A window has only one knob.

Picture a jar that holds at most 20 tokens, and a tap that drips one token into it every 0.6 seconds (that's 100 a minute). Every request must take a token out of the jar. No token: rejected. When the jar is full, extra drips spill over and are lost.

  • After a quiet spell the jar is full: 20 requests can go at once. Capacity is the burst.
  • After that, requests get through only as fast as tokens drip in: 100 a minute. The refill rate is the sustained rate.

This is the token bucket, with two knobs: capacity b and rate r. Its promise is easy to state: over any stretch of T seconds, at most b + r × T requests get through. The jar can start full (b), and the tap adds at most r × T during the stretch. The bucket can be used with a cost too: a cheap read takes 1 token, an expensive export takes 10.

Lazy refill: no tap, just arithmetic

A real tap would be a timer that adds a token to every jar every 0.6 seconds. With 1 million keys that's over a million timer wake-ups a second, most of them for jars nobody is using. Instead, store two numbers per key: how many tokens were in the jar, and when you last looked. When a request arrives, work out how much the tap would have added since then:

elapsed = now − last
tokens  = min(capacity, tokens + elapsed × rate)     # refill, but never past full
last    = now
if tokens ≥ cost: tokens −= cost; allow  else: reject

Worked numbers: capacity 4, rate 0.5 per second (one token every 2 s). The jar starts full.

Each row is a handful of arithmetic steps, however long the gap. A key idle for a week costs nothing, and its first request does one subtraction and one multiplication. Lazy refill is the reason the token bucket is O(1) time and two numbers per key.

Token bucket: capacity sets the burst, rate sets the long-run speed, and over any T seconds at most capacity + rate × T requests pass. Refill lazily from the time since the last look, so each key is two numbers and no timer.

Token bucket with capacity 20 and rate 100 per minute (one token per 0.6 s). The key has been idle for 10 minutes. Then 50 requests arrive within one second. About how many get through?

Right. The jar can't hold more than 20, however long it sat idle; the extra drips spilled over. So 20 go at once, plus whatever drips in during that second: 1/0.6 ≈ 1.7 tokens, so one more. That's the point of the cap: unused capacity doesn't pile up forever.

Two rules decide this. First, the jar has a lid: it never holds more than 20, so ten idle minutes leave it at 20, not 1,000 (that's what capacity is for). Second, the rate only limits what happens after the jar is empty: a full jar can be spent all at once. So: 20 immediately, plus about 1.7 tokens dripping in during the second, which lets one more through. About 21.

Capacity 10, rate 2 per second. At t = 4.0 the jar held 3 tokens. The next request arrives at t = 6.5. How many tokens are left after it's allowed?

Right. 2.5 seconds passed, so the tap added 2.5 × 2 = 5 tokens: 3 + 5 = 8, under the cap of 10. The request takes 1: 7 left.

Run the three lines. elapsed = 6.5 − 4.0 = 2.5 s. Refill = 2.5 × 2 = 5, so tokens = min(10, 3 + 5) = 8: the cap doesn't bite, because 8 is under 10. Then spend 1: 7. The refill isn't "back to full" and it isn't skipped; it's exactly elapsed × rate, capped at capacity.

6A bucket with a hole: the leaky bucket

The token bucket lets a burst of 20 hit your server all at once. Usually that's fine. But sometimes the thing behind the limiter can't take bursts at all: a payment partner that bans you if you send more than 10 calls in any second, or an old database that falls over when 50 queries land together. You don't want to reject the burst; you want to spread it out.

Picture a bucket with a small hole in the bottom. Requests pour in at any speed. They drip out of the hole at a steady pace, one every 0.1 seconds, and only then reach the server. If requests pour in faster than they drip out, the bucket fills; once it's full, new ones overflow and are rejected. This is the leaky bucket. Its knobs are the leak rate and the bucket's size (how many requests can wait).

In code, the bucket is a FIFO queue (first in, first out) with a fixed size, emptied at a fixed rate. You don't need a timer for that either. Each accepted request gets a leak time: the first one leaks the moment it arrives, and each later one leaks at max(its arrival, previous leak time + 1/rate). The server never sees two requests closer together than 1/rate.

TOKEN BUCKET, capacity 5, rate 2/s
burst of 8 at t = 0:
  t=0.0  ✓✓✓✓✓      5 go at once
         ✗✗✗        3 rejected
server sees: 5 requests at t = 0
LEAKY BUCKET, room for 4, rate 2/s
burst of 8 at t = 0:
  t=0.0 ✓  0.5 ✓  1.0 ✓  1.5 ✓  2.0 ✓
         ✗✗✗        3 rejected (bucket full)
server sees: one every 0.5 s

Same 5 accepted, very different experience. With the token bucket the server takes a spike and the client gets fast answers. With the leaky bucket the server sees a perfectly smooth stream, and the client pays for it in waiting: the fifth request waits 2 seconds. That delay is the leaky bucket's cost. It's great in front of a fragile downstream or for outgoing traffic you control; it's bad for a user staring at a page.

Explain it another way: the same bucket, upside down

There's a second "leaky bucket" in the textbooks: the meter. It doesn't delay anything. Each request pours one unit of water into the bucket; the bucket leaks at rate r; if a request would make it overflow, it's rejected. The water level is just "capacity minus tokens", so the meter is the token bucket turned upside down, with exactly the same behaviour. When someone says "leaky bucket", ask which one they mean: the queue (smooths and delays) or the meter (identical to a token bucket). NGINX's limit_req is a queue-style leaky bucket; its burst= option sets the size of the queue, and adding nodelay lets that burst through at once, which turns it into a token bucket.

Leaky bucket (queue version): requests wait in a fixed-size queue and leave at a constant rate. The output is perfectly smooth; the price is delay, plus rejection when the queue is full. Use it when the thing behind it can't take bursts.

Your service calls a payment partner that blocks you if you send more than 10 calls in any one second. Your own traffic arrives in bursts of 30. Which limiter goes in front of the partner?

Right. You want the bursts spread out, not rejected and not passed through. A queue leaking at 10 a second (one every 0.1 s) means the partner never sees more than 10 in any second, and the burst of 30 drains in 3 seconds instead of failing. The token bucket with capacity 30 would send all 30 at once, and the fixed window allows 20 across a second boundary.

Ask "what does the partner see?". A token bucket with capacity 30 hands it all 30 in the same instant: banned. A fixed window of 10 per second allows 10 at 0.99 s and 10 more at 1.00 s: 20 inside one second, banned. A leaky bucket queue releases one request every 0.1 s whatever comes in, so the partner sees a steady 10 per second. The burst waits up to 3 seconds instead of being lost.

8Time is harder than it looks

Every limiter here does arithmetic on "now". So it matters a lot which clock "now" comes from.

Your computer has two kinds of clock. The wall clock (Python's time.time()) is like the clock on the kitchen wall: it tells you the date, and anyone can reset it. It jumps when NTP (the protocol that keeps computer clocks in sync) corrects a drift, when an admin sets it, or when a virtual machine wakes up after being paused. The monotonic clock (time.monotonic()) is a stopwatch: it only ever moves forward, at a steady pace, whatever happens to the wall clock. Its starting point means nothing (often "when the machine booted"), so you can only subtract two readings from it. That's exactly what rate limiters do.

What a wall clock jump does, with numbers:

  • Backwards 30 s, token bucket: elapsed = now − last = −30, so the refill adds −30 × r tokens. The jar goes deeply negative and the user is locked out for most of the next 30 seconds (30 s, minus the time it would take to drip back what the jar held), through no fault of their own.
  • Forwards 1 hour: every jar refills completely and every window expires at once. Everyone gets a free burst.
  • Backwards, sliding log: new timestamps are now smaller than old ones. The deque is no longer in time order, and the old entries look younger than they are, so "pop old ones from the front" lets them out late: the key stays blocked longer than its limit says (warm-up 3 works through it).

The fix is to use the monotonic clock, and to be defensive anyway: if elapsed comes out negative, treat it as 0. Your token_bucket exercise tests both.

Two more things about time:

  • No timers. You saw this in section 5: lazy computation turns "a timer per key" into "a little arithmetic per request". Idle keys cost zero CPU. The same trick works for windows (roll the counters over when the next request arrives) and for the leaky bucket (compute leak times instead of sleeping).
  • Floating point. Adding 0.1 a million times doesn't give exactly 100,000. For a limiter that runs for months, many systems store time as integer nanoseconds (time.monotonic_ns()) and tokens as integer thousandths, so nothing drifts.
Rate limiters subtract timestamps, so use a clock that only moves forward (monotonic), clamp negative elapsed time to 0, and compute everything lazily on each request instead of running timers.

A token bucket uses time.time(). NTP moves the server's clock back by 30 seconds. What does a user with a full jar notice?

Right. On the next request, elapsed = now − last ≈ −30 s, and the refill line adds −30 × rate tokens. The full jar suddenly holds far less than zero, and it takes 30 seconds of real time to climb back to where it was. The user is turned away for most of that time: until the jar is back to at least 1. With time.monotonic() the jump never happens; with a clamp (elapsed below 0 counts as 0) it does no harm.

Plug the jump into the refill line. Say rate 2, capacity 10, full jar, last look at "12:00:00". The clock is set back 30 s, so the next request reads "11:59:30". elapsed = −30 s, refill = −60 tokens, jar = 10 − 60 = −50. It needs 25 seconds of dripping just to reach 0, so the user is rejected for about 25 of the next 30 seconds. "Full anyway" ignores that the formula can subtract. "Unlimited" is what a forward jump does (everything refills at once), not a backward one.

9Many servers, one limit

So far everything lived in one process's memory. Real APIs run on many servers behind a load balancer. Say 20 servers, limit 100 per minute per key.

Try 1: each server limits on its own

If every server allows 100, a client spread over all 20 gets 2,000. So give each server 100/20 = 5. That only works if the load balancer spreads each client perfectly evenly. It doesn't: a client with one keep-alive connection (one connection it reuses for every request) sticks to one server and gets 5 per minute instead of 100. And when you autoscale to 30 servers, every limit is suddenly wrong.

Try 2: one shared counter in Redis

Keep the counts in one place every server can reach: Redis, an in-memory key-value store that runs commands one at a time, very fast. The classic fixed window is two commands per request. The window starts at the key's first request and ends when the key expires:

n = INCR  rl:{key}               # add 1, return the new count (creates the key at 1)
if n == 1:  EXPIRE rl:{key} 60   # first request of the window: delete the key in 60 s
allow if n <= 100

This has a hole. INCR and EXPIRE are two separate commands. If the app server crashes (or the network drops) between them, the key has no expiry. It never goes away, its count only grows past 100, and that key is blocked forever. (If the key name includes the minute, rl:{key}:{minute}, the next minute gets a fresh key, so a missed EXPIRE only leaks memory. Either way it's a bug.) The fix is to make the pair one indivisible step. Redis runs a Lua script (a small program sent to Redis) as one atomic unit: no other command runs in the middle of it. (A MULTI/EXEC transaction, which queues commands and runs them together, can't run "EXPIRE only if n == 1": the commands are queued before any of them runs, so nothing can look at INCR's answer. Sending EXPIRE every time would push the expiry back on each request, so a busy client's window never ends. It works only with EXPIRE's NX option (Redis 7+: set an expiry only if the key has none). For the token bucket below, where what to write depends on what was read, the transaction route is WATCH: watch the key, read it, then MULTI/EXEC the write, which Redis aborts if anyone changed the key in between, so you retry. That's correct, but the retries pile up on exactly the hottest keys; a script never retries.)

-- KEYS[1] = "rl:{key}", ARGV[1] = limit, ARGV[2] = window seconds
local n = redis.call("INCR", KEYS[1])
if n == 1 then redis.call("EXPIRE", KEYS[1], ARGV[2]) end
return n <= tonumber(ARGV[1])

The read-modify-write race

A token bucket in Redis is worse, because it reads, computes, then writes. Two servers handle the same key at the same moment:

server A: GET tokens → 1                          SET tokens 0   → allow
server B:          GET tokens → 1        SET tokens 0           → allow
                                    two requests, one token

Both read 1, both decide "allow", both write 0. The same fix applies: put the whole read-refill-decide-write sequence in one Lua script, so Redis runs it start to finish before touching the next request for that key. The script also needs "now". If each app server sends its own clock, servers whose clocks disagree by a few milliseconds compute different refills. Better: have the script read Redis's own clock (the TIME command), so there's one clock for everyone.

Try 3: local first, global eventually

The shared store works, but now every request pays a network round trip (about 0.2–1 ms inside one data centre), and at 200,000 requests a second the store itself is a hot spot. Two common answers:

  • Shard the limiter's keys across several Redis nodes by key. Every key's script touches one key, so it stays on one node.
  • Hybrid local + global: each server keeps a local token bucket and syncs with the global count every 100 ms, or takes tokens from the global bucket in batches of 10 ("leasing"). Most requests never leave the server. The price: the limit is a little soft, and the two versions bend it in opposite directions. Syncing lets each server decide alone between syncs, so a client spread over 20 servers can get up to 20 servers' worth of local allowance before the global count catches up: it overshoots. Leasing can't overshoot, because a leased token has already left the global bucket. Instead, tokens can sit unused in leases on servers the client has stopped hitting: with a limit of 100 and leases of 10, ten such servers hold the whole limit, so the client can be turned away early, well under 100.

And decide what happens when the limiter's store is down. Fail open (allow everything, maybe with a generous local limit) keeps your API up; that's the usual choice for user-facing traffic. Fail closed (reject everything) is for limits that protect money, like a cap on outgoing SMS messages.

A shared limit needs shared state, and every read-decide-write on it must be atomic: do it in one Redis Lua script, with Redis's own clock. Then pay for the round trip with sharding or a local-plus-global hybrid, and choose fail-open or fail-closed on purpose.

Each app server runs "GET the bucket from Redis, compute the refill, SET it back". Under heavy load the limit leaks: some keys get 30% more than allowed. Why, and what's the fix?

Right. GET and SET are atomic one at a time, but the gap between them isn't. Two servers can read "1 token" in that gap and both spend it. A Lua script runs as a single step inside Redis, so no other request for that key can sneak in between the read and the write. (Clock skew is a real but smaller effect, and the fix there is Redis's own TIME, not the wall clock.)

Look at the gap between GET and SET. Server A reads 1 token. Before A writes back, server B also reads 1 token. Both allow, both write 0: two requests for one token. Under load these overlaps get common, so the limit leaks. A read replica makes it worse (its data is slightly behind, so even more stale reads). The wall clock doesn't help anything (section 8). The fix is to make read-compute-write indivisible: one Lua script, which Redis runs start to finish with nothing in between.

Go deeper: GCRA, the token bucket as one number

The generic cell rate algorithm (GCRA) comes from ATM networks in the 1990s. It stores a single timestamp per key: the TAT, "theoretical arrival time", which is when the next request would be on schedule if the client sent at exactly the allowed rate.

Let T = 1/rate (the spacing between requests at the allowed rate) and τ = (capacity − 1) × T (how far ahead of schedule a client may run). On each request: tat = max(TAT, now). If tat − now > τ, the client is too far ahead: reject, and tell it to retry in tat − τ − now seconds. Otherwise allow and set TAT = tat + T.

Check it with capacity 3, T = 1 s, an idle key at now = 0: the requests see tat = 0, 1, 2 (all within τ = 2) and pass; the fourth sees tat = 3 > 2 and is rejected. Three at once, then one per second: a token bucket, stored as one number instead of two, which halves the memory and makes the Redis script shorter. The leak-time rule in section 6 is the same idea; GCRA is the leaky bucket "meter" written as a schedule. The redis-cell Redis module and libraries such as Go's throttled use GCRA.

Go deeper: what to put in the key
  • API key or user id is the fairest, but only works after authentication. Login and signup endpoints need something else.
  • IP address works before login, but one office or mobile carrier can put thousands of people behind one IP (NAT), and one attacker can rotate through thousands of IPs. Use IP limits as a coarse outer layer.
  • Key + endpoint lets "search" be cheap and "export" expensive. Or use one bucket with a cost per request.
  • Layers: real systems stack them: per-IP at the edge, per-key at the API gateway, per-key-per-endpoint in the service, and a global load shedder that drops low-priority traffic when the whole fleet is overloaded.

10Saying no well

A rejected request should be cheap for you and useful to the client. The standard answer is HTTP status 429 Too Many Requests (defined in RFC 6585), with headers that tell the client what to do next:

HTTP/1.1 429 Too Many Requests
Retry-After: 1
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1764590460
Content-Type: application/json

{"error": "rate_limited", "message": "100 requests per minute; retry in 1 s"}
  • Retry-After is a standard HTTP header: either a whole number of seconds or a date. Compute it from the limiter: for a token bucket, (cost − tokens) / rate; for a log, the oldest timestamp + window − now. Round up: 0.3 seconds becomes 1. Rounding down to 0 tells the client to retry right away, into another 429.
  • X-RateLimit-Limit / Remaining / Reset aren't an official standard, but are widely copied (GitHub's API sends them, with its limit of 5,000 requests per hour for signed-in users). An IETF draft (draft-ietf-httpapi-ratelimit-headers, an Internet-Draft rather than an RFC at the time of writing) proposes standard ones: a RateLimit-Policy header for the rule and a RateLimit header for what's left. One detail interviewers like: GitHub's Reset is a Unix timestamp, which a client with a wrong clock misreads; the draft counts seconds from now instead, like Retry-After, so clock skew doesn't matter. Sending "Remaining" on every response, not just on 429s, lets good clients slow down before they hit the wall.
  • 429 vs 503. 429 means "you are over your limit". 503 Service Unavailable means "we are overloaded". The difference tells the client whether slowing down will help.

The client side matters too. A client that gets a 429 should wait at least Retry-After, then back off exponentially (1 s, 2 s, 4 s…) with jitter (a random part of the wait). Without jitter, every client that was limited at 12:00:00 retries at exactly 12:00:01, all together, and the stampede hits the limit again. This is the "thundering herd".

Go deeper: rate limiting vs load shedding vs backpressure

They sound alike and get mixed up in interviews. Rate limiting enforces a per-key promise ("you get 100 a minute"), whether or not the server is busy. Load shedding drops work when the server is overloaded, whoever sent it, usually lowest priority first. Backpressure pushes "slow down" back up a pipeline, like a full queue that makes producers block. A healthy system often has all three: a token bucket per key, a shedder that returns 503 when CPU is pegged, and bounded queues between internal stages. Before turning a new limit on, many teams run it in shadow mode: compute the decision and log it, but don't enforce it, to see who would be blocked.

Now the bill. 10 million keys, limit 1,000 requests per hour. Raw sizes, before any store's overhead:

The key name itself and the store's bookkeeping usually add 50–100 bytes per key, so the small limiters really cost about 1 GB, while the log costs tens of GB. That gap is why big systems use counters or buckets, and keep the log for small, exact limits like "5 login attempts per 15 minutes".

The last column is the other half of memory: most keys are idle most of the time. Delete a key's state once deleting it changes nothing. For a token bucket, that moment is when the jar would be full again: a full jar is exactly what a brand-new key starts with. So set the Redis key to expire after capacity / rate seconds, and refresh that expiry on each request.

Per-key state times the number of keys is the real cost. Counters and buckets are a few numbers per key; the log is O(limit). And expire each key at the moment its state matches a fresh key's, so idle keys cost nothing.

A token bucket has capacity 20 and rate 1 token per second. How long after a key's last request can you delete its state without changing any future decision?

Right. Even if that request emptied the jar, 20 seconds of dripping at 1 per second refills it to the cap of 20. A full jar is exactly the state a brand-new key starts with, so deleting it and recreating it later gives identical answers. That's capacity / rate, and it's the TTL (time to live: how long until Redis deletes the key by itself) to put on the key.

Ask: when does this key's state look exactly like a brand-new key's? A new key starts with a full jar. The worst case is that the last request left the jar empty; then it takes 20 tokens ÷ 1 per second = 20 seconds to be full again. After that, nothing about the past is left in the state, so deleting it loses nothing. After only 1 second the jar holds 1 token, and a recreated key would wrongly get 20.

12What to say in the interview

When "design a rate limiter" comes up, alone or inside a bigger design:

  1. Pin down the rule: "Limit by what: API key, user, IP? What numbers: 100 a minute, with or without bursts? Hard limit or soft? One server or a fleet? And what happens to rejected requests: drop, or queue?"
  2. Pick the algorithm and say why: "A token bucket: capacity for bursts, refill rate for the average, two numbers per key, refilled lazily from a monotonic clock. If the rule is literally 'N per minute', a sliding window counter. Not a fixed window, because it allows 2× at the boundary; not a log at this scale, because it's O(limit) memory per key."
  3. Say the costs: "O(1) per request, about 16 bytes per key plus the key name, so 10 million keys is around a gigabyte. Keys expire after capacity / rate."
  4. Distribute it: "State in Redis, one Lua script per check so read-refill-write is atomic, using Redis's clock. Shard by key. If Redis is down, fail open with a local fallback limit. If the round trip hurts, local buckets that sync or lease tokens, accepting a slightly soft limit."
  5. Say no well: "429 with Retry-After rounded up, and remaining-quota headers on every response, so clients back off with jitter."
Go deeper: follow-up questions interviewers like
  • "Make it thread-safe in one process." A lock per bucket (or a striped set of locks, chapter 1) around the refill-and-spend. The critical section is a few arithmetic steps, so contention is low.
  • "Different limits per plan." Store the plan's capacity and rate with the key, or look them up from config; the algorithm doesn't change.
  • "Limit across regions." A single global store is a cross-ocean round trip (around 70–150 ms). Usually each region enforces its share locally and they reconcile asynchronously; the limit becomes approximate across regions.
  • "How do you test it?" Inject the clock, exactly like this chapter's exercises: fake time makes "wait 59 seconds" instant and repeatable.
  • "Some requests take 30 seconds." A rate limit counts how many start per second, not how many are running. For slow, heavy endpoints add a concurrency limit: a counter of requests in flight per key, +1 when one starts and −1 when it finishes (with a timeout, so a crashed request doesn't hold its slot forever).
  • "Count rejected requests?" Usually no (section 3). Yes, on purpose, if you want clients who ignore 429s to stay blocked.

✓What to remember

  1. A rate limiter runs on every request, so it must be O(1) time and small memory per key; multiply by the number of keys.
  2. Fixed window counter: O(1), two numbers, but up to 2× the limit across a window boundary.
  3. Sliding window log: exact, amortized O(1) with a deque, but O(limit) memory per key. Log only accepted requests.
  4. Sliding window counter: previous × (window − elapsed) / window + current. O(1), no boundary burst, small error from assuming even spread.
  5. Token bucket: capacity = burst, rate = sustained; at most b + rT in any T seconds. Lazy refill: tokens = min(b, tokens + elapsed × r).
  6. Leaky bucket (queue): smooth output at a fixed rate, paid for in delay. The meter version is a token bucket upside down; GCRA stores it as one number.
  7. Use a monotonic clock, clamp negative elapsed time, and never run timers per key.
  8. Distributed: shared state in Redis, read-decide-write atomically in one Lua script with Redis's clock; shard, or go local + global; choose fail-open or fail-closed.
  9. Reply 429 with Retry-After (rounded up) and remaining-quota headers; clients back off with jitter.

Warm-up · pen and paper

1. Run four limiters by hand

Requests from one key arrive at t = 2, 5, 9, 10, 11, 14, 19, 21, 23 seconds. For each limiter, mark every request allowed or rejected: (a) fixed window, 3 per 10 s, windows [0, 10), [10, 20), [20, 30); (b) sliding window log, 3 per 10 s (a request at t stops counting at t + 10); (c) sliding window counter, 3 per 10 s, allowing a request when estimate + 1 ≤ 3; (d) token bucket, capacity 3, rate 0.3 per second, starting full. Which one lets the most through, and does it break its own promise?

Answers

(a) Fixed: rejects only 19 (the fourth request in [10, 20)). 8 allowed. The 10-second stretch [5, 15) holds 5 of them (5, 9, 10, 11, 14): the boundary burst, at small scale.

(b) Log: allows 2, 5, 9. At 10 and 11, the window (0, 10] or (1, 11] still holds 2, 5, 9: reject both (and don't log them). At 14, the window (4, 14] holds 5 and 9: allow. At 19, (9, 19] holds only 14 (9 leaves at exactly 19): allow. At 21, (11, 21] holds 14 and 19: allow. At 23, (13, 23] holds 14, 19, 21: reject. 6 allowed.

(c) Counter, estimates before each request: 0, 1, 2 → allow; t=10: 3 × 10/10 = 3 → reject; t=11: 3 × 9/10 = 2.7 → reject; t=14: 3 × 6/10 = 1.8 → allow; t=19: 0.3 + 1 = 1.3 → allow; t=21: window [20, 30), previous = 2, 2 × 9/10 = 1.8 → allow; t=23: 2 × 7/10 + 1 = 2.4 → reject. 6 allowed, the same as the exact log here.

(d) Token bucket, tokens before each: 3, 2.9, 3 (capped), 2.3, 1.6, 1.5, 2.0, 1.6, 1.2: all 9 allowed. It keeps its own promise, b + rT = 3 + 0.3 × 21 = 9.3 for the 21 seconds from 2 to 23. "3 per 10 s" as a token bucket is a looser rule than "3 in any 10 s", because the jar can be full at the start of a stretch and the tap keeps dripping through it.

Warm-up · pen and paper

2. Pick the limiter

Which limiter, which key, and why? (a) At most 5 failed login attempts per account per 15 minutes. (b) A public API with 10 million API keys, 600 requests per minute each, short bursts fine. (c) Your service sends emails through a provider that rejects more than 50 per second. (d) A GPU inference endpoint where one request can cost 100× another. (e) "10,000 requests per day" on a free plan, shown on a billing page.

Answers

(a) Sliding window log per account: tiny limit, must be exact, 5 timestamps per account is cheap. Count failures only. (b) Token bucket (or sliding window counter) per API key in Redis: two numbers per key, about a gigabyte in total. (c) Leaky bucket queue leaking 50 per second (with some margin, say 45), in front of the provider: emails can wait a second, but bursts would be rejected. (d) Token bucket per key with a cost per request (estimated tokens or GPU-seconds), so a heavy request spends more. (e) Fixed window counter per day: users understand "resets at midnight UTC", and a boundary burst of 2 days' quota is a billing question, not an overload one.

Warm-up · pen and paper

3. Break the naive versions

(a) A Redis fixed window does INCR, then EXPIRE in a second call. Describe the exact sequence of events that blocks a user forever. (b) Two app servers run a token bucket as GET, compute, SET. Draw a timeline where one token admits three requests. (c) Design traffic, limit 100 per minute, that gets about 199 requests into one 60-second stretch past a sliding window counter. (d) A sliding log with a 10-second window uses time.time(), and the clock steps back 5 s. Which timestamps does "pop old ones from the front" now get wrong?

Answers

(a) With the key rl:{key} from section 9: the first request of a window runs INCR, which creates the key at 1, and the app crashes before EXPIRE. The key has no expiry, so it never resets. Every request adds 1; after 100 more, every request is rejected, forever, until someone deletes the key by hand. (b) A, B, C all GET 1 before any of them SETs; each allows and writes 0. (c) 100 requests at 0:59.9, then from 1:00 send as fast as allowed: the estimate 100 × (60 − e)/60 + current lets current grow at about 1.7 per second, reaching about 99 by 1:59.9. Everything from 0:59.9 to 1:59.9 is one 60-second stretch: about 199. (d) Say the log holds [100, 101], the clock steps back, and the next request reads 97 and is appended: [100, 101, 97]. Measured by the new readings, 100 and 101 look 5 s younger than they are, so they leave 5 s late in real time. And 97 sits behind larger numbers, so it can't leave until they do (at reading 111, 4 s after its own expiry at 107). Both errors make entries leave late: the key is blocked longer than its limit says.

Core · code

4. TokenBucket: allow, tokens, retry_after

Lazy refill with an injected clock. retry_after(cost) returns how long until that cost would pass (what you'd put in Retry-After, before rounding). Tests check the b + rT promise on random traffic by brute force, a billion-second idle gap and a billion-token jar (a loop that adds one token, or one second, at a time never finishes), a clock that jumps backwards, retry_after after time has passed, at most one clock read per call, flat memory over 100,000 requests, and an AST check for threads, timers, sleeps and time.time.

Core · code

5. SlidingWindowLog for many keys

Exact limits with a deque per key, plus retry_after(key) and forget_idle(). A brute-force checker compares every decision on random traffic. Memory is measured: one busy key must never hold more than limit timestamps, and forget_idle() must really free 20,000 idle keys. A limit of 400,000 with 800,000 requests must finish well under the time cap, so filtering the log, or list.pop(0), on every request fails.

Core · code

6. SlidingWindowCounter for many keys

The weighted estimate from section 4, with windows aligned to multiples of window. Tests include the 80/30 example, the boundary burst, skipping a whole window, and a brute-force checker. Memory is the point: 300,000 requests on one key with a huge limit must not grow memory at all, and 100,000 keys must cost under 400 bytes each, so a log in disguise fails.

Core · code

7. LeakyBucket as a queue

offer(item) returns the delay or None; poll() returns the items whose leak time has come. Tests check every rule on random traffic (leak exactly 1/rate after the previous one, never accept into a full bucket, poll in order), a queue of 200,000 with waiting() asked every time and poll() called rarely (walking the queue to count it, or skipping its leaked-but-unpolled front on every call, fails the cap), and flat memory when polled.
