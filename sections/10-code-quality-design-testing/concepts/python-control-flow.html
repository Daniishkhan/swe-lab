Python control flow, loops, and functions

If you are switching to Python from Java, C++, Go, or JavaScript — or shaking off rust before timed rounds — tiny control-flow slips eat minutes you never get back. An off-by-one countdown drops index 0, a stray continue freezes a while loop, or a break exits only the inner loop of a 2D scan.   4. Package reusable logic into functions that return multiple values, reject invalid inputs loudly, and exit nested loops cleanly.

1Why do small control-flow mistakes derail timed rounds?

Picture a 45-minute bare-editor coding round with zero autocomplete and no "Run" button. You need to scan an array backwards to find a peak, then search a 2D grid for the first negative cell. You type for i in range(n - 1, 0, -1): from habit, wrap your 2D search in a messy found = False flag, and stack two if statements where you meant elif. Your algorithm is optimal — yet your hand-trace uncovers three control-flow bugs at minute 38.

Think of every Python program as a railway switchyard. Execution rolls down the main track line by line, top to bottom. Four pieces of track equipment steer every train:

  • Branch switches (if / elif / else): pick a single side track based on a condition.
  • Fixed loops (for + range): circle a known stretch of track once per item or stop number.
  • Condition loops (while) & detour switches (continue / break): keep circling until a live condition flips, skip one stop, or leave the loop right now.
  • Helper tracks (def functions): route repeated work onto a named sub-track that hands back a clean result.
Every extra flag variable or manual counter is one more line you have to trace by hand in a bare editor.

Where the switchyard analogy breaks: physical tracks sit flat on the ground, whereas a Python helper function can call itself (recursion) and stack fresh private variables on every call — and an unhandled error derails execution straight up to the nearest try / except catch net.

Let's lay this switchyard one piece at a time: branch gates first (§2), fixed for / range loops (§3), dynamic while loops and exit switches (§4), reusable functions and input guards (§5), and finally the three traps that catch engineers during dry runs (§6).

2How does Python steer decisions without braces?

Python uses indentation (4 spaces) instead of curly braces { } to mark which lines sit inside a branch or loop. Everything indented under a colon (:) runs together as one track; dedenting returns to the main line.

When a value must match at most one branch, chain if → elif → else. The instant one switch matches, Python skips every remaining elif and else below it. Stacking two separate if statements instead checks both gates independently — a classic bug when assigning grades or categories:

Use elif whenever branches are mutually exclusive; use separate if gates only when multiple rules can apply together.

Three Python branch idioms make interview code dramatically shorter and safer:

  • Chained comparisons: write if 0 <= r < rows and 0 <= c < cols: straight out of math class — no repeating r >= 0 and r < rows!
  • Short-circuit and / or: Python evaluates left to right and stops the instant the outcome is settled. In if nums and nums[0] > 0:, when nums is empty ([]), Python stops at nums and never touches nums[0] (preventing IndexError!).
  • Truthiness & 1-line conditional: in an if condition, empty or zero values (0, 0.0, "", [], {}, set(), None, False) evaluate to False ("falsy"), and almost everything else evaluates to True ("truthy"). For a simple value pick, use sign = "neg" if x < 0 else "non-neg".
# Clean Python decision idioms in grid & bounds code
if 0 <= r < rows and 0 <= c < cols:       # chained bounds check!
    cell = grid[r][c]
if nums and nums[0] < 0:                  # short-circuit guards empty list!
    label = "starts negative"
else:
    label = "empty or non-negative"

Heads-up on truthiness: checking if nums: is great for testing whether a list is non-empty, yet when a number can legally be 0 or missing (None), always write if val is not None: (we unpack why in Chapter 10.10).

Use if / elif / else for mutually exclusive branches, chained comparisons (0 <= i < n) for bounds, and left-to-right short-circuiting (if xs and xs[0] == target:) to guard empty containers before indexing.

You classify request latency with the snippet below and pass ms = 450. What value does tier hold afterward?

tier = "fast"
if ms >= 400:
    tier = "slow"
if ms >= 200:
    tier = "ok"

Spot on! Two separate if statements are two independent gates: 450 >= 400 sets "slow", then 450 >= 200 is also True and overwrites tier with "ok". Change the second if to elif.

Trace a fresh example with temp = 105: if you write if temp >= 100: state = "hot" followed by a separate if temp >= 70: state = "warm", Python checks both statements top to bottom — setting "hot" first and immediately overwriting it with "warm"! Only elif skips later checks once an earlier branch matches.

Branch switches steer one pass down the track. Next question: how do you circle a track cleanly over every element — or count backwards — without slipping past the boundary by one?

3How do for loops and range walk tracks without off-by-one bugs?

In Java or C++, you reach for an index loop (for (int i = 0; i < n; i++)) by reflex. In Python, if you only need each value, iterate the container directly — zero indices, zero off-by-one risk:

total = 0
for price in prices:            # walks every item directly, no index math!
    total += price

When you genuinely need numeric positions — like stepping by 2, counting backwards, or tracking row/column indices — Python gives you range(start, stop, step). Memorize one ironclad rule: range is always half-open [start, stop) — it includes start and stops strictly before hitting stop:

  • range(5): starts at 0, stops before 5 → yields 0, 1, 2, 3, 4 (exact valid indices of a length-5 list!).
  • range(2, 6): starts at 2, stops before 6 → yields 2, 3, 4, 5 (count = 6 - 2 = 4).
  • range(n, -1, -1): counts down from n to 0 inclusive! Because stop is excluded, you MUST set stop = -1 to include 0.

Watch the difference between safe range(4, -1, -1) and the #1 countdown bug range(4, 0, -1):

Switch the dropdown between safe range(4, -1, -1) and buggy range(4, 0, -1). Remember: the stop wall is never stepped onto — whether walking forward or backward!

That exact rule solves countdown_evens(n) in py_foundations.py cleanly in three lines (start at the largest even number <= n, step by -2, stop wall at -1 so 0 is always included!):

# py_foundations: countdown_evens(n) — even numbers from n down to 0 inclusive
def countdown_evens(n):
    if n < 0:
        raise ValueError("n must be non-negative")
    start = n if n % 2 == 0 else n - 1
    return list(range(start, -1, -2))
Iterate directly (for x in items:) whenever you don't need indices. When you use range(start, stop, step), treat stop as a wall you stop before touching — so counting down to 0 inclusive always uses stop = -1.

What list does list(range(6, 0, -2)) produce?

Exact! Half-open means stop is never included, even when stepping backward. Pass -1 as the stop value (range(6, -1, -2)) to include 0.

Check the same rule walking forward first: list(range(0, 6, 2)) yields [0, 2, 4] — it stops strictly before hitting 6. Stepping backward works the exact same way: range(6, 0, -2) yields 6, then 4, then 2, sees the wall 0 next, and halts at [6, 4, 2].

for handles every track where the stops are known upfront. What when your stopping condition changes dynamically while you run — like two pointers closing in on each other, stripping digits off a number, or exiting early the moment you spot a match?

4When do you switch from for to while — and how do break, continue, and else steer exits?

Switch from for to while condition: whenever you cannot know the exact number of iterations ahead of time — such as binary search (while lo <= hi:), two pointers converging (while left < right:), draining a work queue (while queue:), or peeling base-10 digits (while n > 0:).

# Classic while loop: sum the base-10 digits of a positive integer
digit_sum = 0
while n > 0:
    digit_sum += n % 10       # grab the last digit
    n //= 10                  # shrink n strictly toward 0 so the loop MUST end!

Inside either a for or a while loop, three switchyard commands steer early detours:

  • continue: skips the remaining lines of the current iteration and jumps straight to the next iteration.
  • break: exits the innermost enclosing loop immediately.
  • for ... else: (and while ... else:): an optional track attached to the loop that runs only if the loop finished normally without hitting break. Read else: here as "no break occurred" — eliminating awkward found = False flags!

Step through searching [3, 5, 7, 11] with for ... else: when the target is found vs. missing:

Toggle between target = 7 (hits break, so else: is skipped) and target = 9 (finishes every stop with no break, so else: runs!).

Notice the indentation carefully: else: lines up directly under for (not under if!), because it belongs to the loop as a whole:

for num in [3, 5, 7, 11]:
    if num == target:
        print("found", num)
        break
else:                         # aligned with `for` — runs only if `break` never fired!
    print("not found")
Use for for fixed sequences and while when your loop state evolves dynamically (always proving each step shrinks toward termination!). Remember for ... else: means "ran to completion without hitting break".

What does status equal after this loop finishes?

status = "init"
for x in [2, 4, 6]:
    if x == 4:
        status = "found"
        break
else:
    status = "missing"

Spot on! Because x == 4 triggered break, Python exits the entire for ... else construct without entering else:, keeping status == "found".

Compare with a second list [1, 3, 5] searching for 2: the loop checks 1, 3, and 5, never hits break, and therefore runs else:. In [2, 4, 6], finding 4 hits break, which jumps straight past else: so status stays "found".

Now imagine your search lives inside two nested loops (rows and columns of a 2D grid). Calling break inside the inner column loop only breaks out of that row! How do you exit cleanly — and package repeated logic so your code stays readable?

5How do you package tracks into reusable functions — and reject bad inputs cleanly?

A function (def name(params):) bundles a sub-track behind one clear name. Calling return value immediately hands value back to the caller — cleanly exiting every loop inside the function in one shot, zero boolean flags needed!

# py_foundations: first_negative_coords — clean early return exits BOTH loops!
def first_negative_coords(grid):
    for r in range(len(grid)):
        for c in range(len(grid[r])):
            if grid[r][c] < 0:
                return (r, c)         # packs two values into one tuple & exits now!
    return None                       # explicit fallback when no negative exists
Every Python function returns a value — if execution falls off the bottom without hitting return, Python quietly hands back None.

Four function habits make your interview code crisp from line 1:

  1. Tuple unpacking for multiple returns: returning (r, c) lets callers write row, col = pos (after checking pos is not None) without inventing a temporary wrapper object.
  2. Keyword arguments & safe defaults: give optional parameters clear immutable defaults like def paginate(items, page=1, size=20):, and pass named arguments at call sites (paginate(rows, size=50)) so readers never guess what 1, 50 means! (Always use immutable defaults like ints, strings, or None — Chapter 10.10 explains the shared-list bug if you ever write out=[].)
  3. Validate contracts loudly with raise: when an input violates a precondition (like n < 0 in countdown_evens or k <= 0 in a window size), fail fast with raise ValueError("n must be non-negative") instead of returning silent garbage.
  4. Catch only specific exceptions: when calling fallible code (like parsing text into an integer), wrap only the risky line in try / except ValueError: — never a blank except: that swallows unrelated typos:
def parse_int(token, default=None):
    try:
        return int(token)
    except ValueError:                # catches bad text only — never hides typos!
        return default
Go deeper: forwarding unknown arguments with *args and **kwargs

Sometimes you write a thin wrapper function that accepts any number of positional or named arguments and forwards them to another helper. Adding *args collects extra positional arguments into a tuple ((1, 2, 3)), and **kwargs collects extra keyword arguments into a dictionary ({"timeout": 5}). You will use def wrapper(*args): directly when building caching decorators on Day 3 (Chapter 10.12).

Use helper functions to exit nested loops with a clean early return, unpack multi-value tuple returns directly, fail fast with raise ValueError on invalid inputs, and remember that forgetting return silently returns None.

What does ans hold after calling ans = sum_evens([2, 4, 5]) on the function below?

def sum_evens(nums):
    total = 0
    for x in nums:
        if x % 2 == 0:
            total += x
    print(total)

Sharp catch! print(total) displays 6 to the console and returns None; because sum_evens falls off the end with no return total, ans receives None.

Try tracing an even shorter helper: def double(x): y = x * 2. Running val = double(5) computes 10 inside y, throws y away when the function exits, and hands back None! Printing a value only writes text to stdout — a caller only receives a value when you explicitly write return total.

6How can loops and functions trip you up in bare-editor rounds?

Every interview dry run should scan for these three control-flow failures:

Also watch for ... else: on readability — if your loop sits inside a helper function, an early return is even clearer than break + else:!

When a plain loop beats clever shortcuts: keep for ... else: for short, obvious searches — never nest for ... else: inside another loop, and never write a 3-line ternary expression nested inside another ternary (a if c1 else b if c2 else d). Clear if / elif / else tracks beat compressed one-liners in every senior rubric.

Inside a 2D scan over [[1, -2], [-3, 4]], you run ans = (r, c); break inside the inner for c loop — without breaking the outer for r loop. What does ans end up holding?

Caught it! break only exits the inner for c loop — so Python immediately advances to row 1, sees -3 at (1, 0), and overwrites ans! Wrapping the search in a helper function and writing return (r, c) exits both loops cleanly.

Trace a fresh 2×2 grid [[0, -1], [-5, 2]]: on row 0, column 1, seeing -1 sets ans = (0, 1) and runs break. That only leaves the inner column loop — the outer row loop still advances to row 1, sees -5 at (1, 0), and overwrites ans! Extract a helper and use return (r, c).

What happens when you run this while loop on nums = [2, -1, 4]?

i, total = 0, 0
while i < len(nums):
    if nums[i] < 0:
        continue
    total += nums[i]
    i += 1

Exact! At i = 1, nums[1] == -1 < 0 hits continue, jumping straight back to while i < len(nums): with i still stuck at 1 forever! Increment i += 1 before continue — or better yet, use for x in nums:.

Trace an even shorter 2-item list [-1, 5]: on the very first check, i = 0 sees -1 < 0 and hits continue, jumping right back to the while condition before ever reaching i += 1! On the next turn i is still 0, so the loop spins forever (the exact same freeze hits [2, -1, 4] at i = 1).

7How you use clean control flow in interviews

Compare porting C-style manual counters and boolean flags against writing clean Python control flow for the exact same task (finding the first negative number inside a 2D grid):

Before: manual counters + flag + double break

def first_negative_coords(grid):
    found = False
    ans = None
    r = 0
    while r < len(grid):
        c = 0
        while c < len(grid[r]):
            if grid[r][c] < 0:
                ans = (r, c)
                found = True
                break
            c += 1
        if found:
            break
        r += 1
    return ans

After: helper def + range + early return

def first_negative_coords(grid):
    for r in range(len(grid)):
        row = grid[r]
        for c in range(len(row)):
            if row[c] < 0:
                return (r, c)
    return None

Half the lines, zero flag state, zero risk of forgetting c += 1 on a branch, and fast to dry-run in a bare editor. Practice stating those choices aloud in 30 seconds before writing code.

8What to say in the interview

Before coding the first two drills in py_foundations.py and moving straight into Python's built-in data structures (Chapter 10.14), make sure you can explain these four habits clearly:

  1. Branch safety: "I'll use if / elif / else for exclusive branches, chained bounds like 0 <= r < rows, and short-circuit guards like if nums and nums[0] < 0: before indexing."
  2. Loop boundaries: "range(start, stop, step) is half-open [start, stop), so forward loops stop at n and reverse loops reaching index 0 use stop = -1."
  3. for vs. while: "I use for over fixed sequences and while only when pointers or state shift dynamically — verifying every branch makes progress toward termination."
  4. Clean exits & guards: "For nested searches I extract a small helper function so early return exits all loops cleanly without boolean flags, and I guard invalid inputs with raise ValueError."
