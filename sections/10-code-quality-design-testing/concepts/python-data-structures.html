Python's built-in data structures

P0 Phase 0 Python foundationsabout 17 minutes6 quick checks · 4 exercises

Control flow tells Python which lines to run; data structures decide how fast those lines finish. Almost every first-round timeout in Python comes from reaching for a plain list when the job calls for a set, a dict, or a tuple — or concatenating strings inside a loop. Before we zoom into memory references tomorrow, let's master Python's four core containers and text strings from one clear picture.

By the end you'll be able to

  1. Pick the right built-in container for order, uniqueness, and instant lookups.
  2. Index and slice ordered sequences cleanly, and explain why editing the back is fast while editing the front shifts every element.
  3. Use sealed records for fixed coordinates and lookup keys, and assemble text in linear time instead of repeated copying.
  4. Build frequency counts, bucket maps, instant membership checks, and set comparisons without nested loops.
  5. Avoid the four classic container traps: empty braces creating a dictionary, missing single-tuple commas, scanning a list inside a loop, and using editable lists as keys.

1Why does picking the wrong built-in container make clean code 1,000× slower?

Your service receives 100,000 unique request IDs and needs to drop duplicates while keeping first-seen arrival order. You write a clean 4-line loop: out = [], then for each ID if req_id not in out: out.append(req_id). On 10 test items it finishes instantly. On 100,000 items, every not in out scans from slot 0 — performing roughly 5 billion comparisons and timing out! Adding one helper container (seen = set()) cuts that exact loop to 100,000 constant-time checks — over 1,000× faster.

Picture Python's four built-in data structures as four storage containers on a workshop floor — each built for one job:

Pick the container by the operation your loop runs most often — especially membership checks (in) and insertions.

Where the workshop-container analogy breaks: a physical badge gate never gets confused by similar names, whereas Python's dict and set jump directly to a slot using a numeric fingerprint called a hash — making lookups O(1) on average (with a rare O(n) worst case if many keys collide, unpacked in Week 1's Hash Maps chapter).

Let's inspect each container on the workshop floor in order: growable shelves (list, §2), sealed crates and text ribbons (tuple & str, §3), labeled filing cabinets (dict, §4), badge gates and set math (set, §5), and the four traps that catch people under interview pressure (§6).

2How do lists work — and where do hidden linear costs hide?

A list is an ordered, resizable numbered shelf: slots start at index 0 from the left and -1 from the right (so nums[-1] grabs the last item cleanly without typing nums[len(nums) - 1]). Just like range(start, stop, step) from Part 1, slicing nums[start:stop:step] is half-open [start, stop) and builds a new list:

nums = [10, 20, 30, 40, 50]
nums[0], nums[-1]       # (10, 50) — first and last item in O(1)
nums[1:4]               # [20, 30, 40] — indices 1, 2, 3 (stops before 4!)
nums[:2], nums[-2:]     # ([10, 20], [40, 50]) — first 2 and last 2
nums[::-1]              # [50, 40, 30, 20, 10] — reversed copy in O(n)

Because Python stores list slots side by side in contiguous memory, which end you touch changes performance completely:

  • Back of the shelf (append(x), pop(), nums[i]): instant O(1) (amortized for append/pop() when resizing occasionally). That makes a Python list a fast ready-made stack (last-in, first-out).
  • Front or middle (insert(0, x), pop(0), x in nums): slow O(n)! Inserting or removing at index 0 forces Python to slide every remaining box one slot over — turning a queue loop into O(n²)! (On Day 4, collections.deque gives you O(1) at both ends.)
Toggle between pushing at the back (nums.append(9): 1 step) and inserting at the front (nums.insert(0, 9): shifts every existing slot right!).
A list is fast by index (nums[i], nums[-1]) and fast at the back (append / pop() in O(1) amortized). Treat front edits (insert(0, x), pop(0)) and membership scans (x in nums) as O(n) — never hide them inside a loop!

Given vals = [5, 15, 25, 35, 45], what do vals[-2] and vals[2:4] evaluate to?

Spot on! Counting from the back goes -1 → 45, -2 → 35; and half-open [2, 4) takes indices 2, 3 → [25, 35].

Check on a 4-item shelf letters = ["a", "b", "c", "d"]: letters[-1] is "d" (last), so letters[-2] is "c" (second from last). And half-open letters[1:3] starts at index 1 ("b") and stops strictly before index 3 ("d"), returning ["b", "c"]. Apply the exact same rule to vals → 35 and [25, 35].

Lists shine when items grow and change. What when you want a fixed record whose slots should never change — like a 2D coordinate (row, col) you can drop straight into a lookup table — or a sequence of characters?

3When should you reach for a sealed tuple or a text ribbon?

A tuple is a sealed shipping crate: ordered and indexable like a list (pt[0], pt[-1]), yet you cannot append, pop, or overwrite its slots after creating it. That permanence unlocks three daily interview moves:

  • Clean unpacking & swaps: r, c = (2, 5) unpacks fields by name, and a, b = b, a swaps two variables in one line without a temporary variable.
  • Legal keys for dicts and sets: because a tuple of immutable values (like (r, c)) cannot change its contents later, Python lets you store it inside a set of visited coordinates or as a dict key — whereas putting a mutable list [r, c] there crashes!
  • Watch the 1-element comma trap: parentheses alone just group math expressions — so (42) is the integer 42! A single-item tuple requires a trailing comma: (42,).

A str (string) is an immutable text ribbon of characters. You get all the same indexing and slicing (s[0], s[-1], s[::-1]) plus workhorse parsing methods: s.strip() (trim outer whitespace), s.lower() (case-fold), and s.split() (split on whitespace into a list of tokens). Because strings cannot be edited in place, building a long string via out += ch inside an n-step loop copies the entire growing ribbon over and over — 1 + 2 + ... + n = O(n²)! Collect pieces in a list and seal the ribbon once with "".join(parts) in O(n):

Same rule for joining comma-separated tags: use ", ".join(tags) instead of concatenating in a loop.
Go deeper: why CPython microbenchmarks sometimes hide s += ch costs

CPython includes an internal optimization that can resize an unreferenced string in place under narrow conditions — making s += ch look fast on tiny local tests. That optimization vanishes the moment another reference exists, under PyPy or alternative runtimes, or during senior code review. Always build strings with parts.append(...) and "".join(parts) so linear O(n) time is guaranteed everywhere.

Use tuple for fixed records and dict/set keys (remembering the trailing comma in (x,)!), and always assemble multi-step strings via parts.append(...) + "".join(parts) for guaranteed O(n) time.

You want a 1-element tuple holding 42, write single = (42), and then call len(single). What happens?

Sharp catch! Without a comma, (42) is identical to 42 (an int, which has no len()). Always add a trailing comma for a 1-tuple: single = (42,).

Test a second value in your head: in arithmetic, (3 + 4) * 2 uses parentheses to group the integer 7 — not to make a tuple! So ("hi") is just the string "hi" (length 2, not 1!) and (42) is just the integer 42, crashing on len(42) with TypeError until you add the comma: (42,).

Now you have ordered shelves (list), sealed crates (tuple), and text ribbons (str). None of them can answer "which indices did the word 'go' appear at?" without scanning from index 0. Enter the labeled filing cabinet.

4How do dictionaries give you instant key-to-value lookup?

A dict maps unique hashable keys to values in O(1) average time — and remembers insertion order (guaranteed across Python 3.7+). Memorize these four daily interview operations:

  • Safe lookup vs. strict lookup: d[key] raises KeyError if key is missing; d.get(key, default) returns default (or None) without crashing or modifying d.
  • Counting & bucketing in one pass: increment counts with counts[k] = counts.get(k, 0) + 1, or create a bucket list the first time a key appears (if w not in pos: pos[w] = [] then pos[w].append(i)).
  • Clean iteration: walk keys directly (for k in d:), values (d.values()), or both together (for k, v in d.items():) in exact insertion order.
  • Safe deletion: d.pop(key, None) removes and returns the value if present, or returns None safely if absent (whereas del d[key] raises KeyError on missing keys).
# py_foundations: word_positions — map each lowercase word to its token indices
def word_positions(text):
    positions = {}
    tokens = text.lower().split()
    for i in range(len(tokens)):
        word = tokens[i]
        if word not in positions:
            positions[word] = []
        positions[word].append(i)
    return positions
Step through word_positions("Go dog go") one token at a time. Each dictionary lookup jumps straight to that word's bucket in O(1) average time!
Reach for a dict whenever you map keys to counts, indices, or records in O(1) average time. Use d.get(k, default) for safe reads, d.pop(k, None) for safe deletes, and for k, v in d.items(): to iterate in insertion order.

Given counts = {"a": 2}, what happens when you evaluate counts["b"] vs. counts.get("b", 0)?

Exact! Direct bracket indexing counts["b"] fails loudly with KeyError when a key is absent, whereas .get("b", 0) returns the fallback 0 and leaves counts untouched.

Check a second dictionary scores = {"kim": 10} when looking up an unknown player "lee": scores["lee"] immediately crashes with KeyError: 'lee', while scores.get("lee", 0) quietly hands back 0 without adding "lee" into scores! (Day 4's defaultdict is the specialized tool that auto-inserts on read.)

A dictionary maps each key to a payload value. What when you do not need a value at all — you only care whether an item has been seen before, or which tags were added, removed, or kept between two snapshots?

5How do sets give you instant membership checks and clean set math?

A set is a badge-check gate holding unique hashable items with O(1) average membership checks (x in seen). Watch one critical syntax trap on day one: writing {} creates an empty dictionary, NOT a set — always write seen = set() for an empty set!

# py_foundations: dedupe_preserve_order — O(n) via set + list (NOT O(n²) `in out`!)
def dedupe_preserve_order(items):
    seen = set()              # MUST be set(), never {}!
    out = []
    for item in items:
        if item not in seen:  # O(1) average badge check!
            seen.add(item)
            out.append(item)
    return out

Use seen.add(x) to insert and seen.discard(x) to remove safely without crashing if x isn't there (whereas seen.remove(x) raises KeyError if missing). Better yet, Python sets support clean mathematical set algebra in one symbol — turning multi-loop comparisons into single expressions (this solves tag_diff in py_foundations.py!):

Sets do not guarantee a sorted order — wrap set results with sorted(...) whenever deterministic alphabetical output is required.
# py_foundations: tag_diff — O(n + m) set algebra + O(k log k) sort
def tag_diff(current, target):
    cur, tgt = set(current), set(target)
    return (sorted(tgt - cur), sorted(cur - tgt), sorted(cur & tgt))
Create empty sets with set() (never {}), pair a set with a list whenever you need both uniqueness and insertion order in O(n), and use &, |, -, and ^ to compare collections without nested loops.

You initialize seen = {} at the top of a loop and call seen.add("req_1") on the next line. What happens?

Spot on! Because empty braces {} belong to dict in Python, calling .add() fails with AttributeError: 'dict' object has no attribute 'add'. Always write seen = set().

Check type({}) vs. type({1}) in your head: non-empty {1} has no colons so Python knows it is a set, whereas empty {} is ambiguous and always creates an empty dict! Dictionaries don't have an .add() method, so seen = {} crashes the instant you call seen.add(...) — use seen = set().

6How do you pick the right container — and what four bugs bite hardest?

Before typing a single bracket or brace, check this quick mental filter — and watch out for the four traps below:

  • Need order, duplicates, or indexing (or a LIFO stack)? → list.
  • Need a fixed record, coordinate, or dict/set key? → tuple.
  • Need key → value lookups (counts, caches, index maps)? → dict.
  • Need unique items, fast in checks, or diffs? → set.
Also watch when a set is the wrong tool: sets drop duplicates and do not preserve insertion order, so pair set + list (or dict.fromkeys) whenever order matters.
Go deeper: frozenset and dict.fromkeys for order-preserving deduplication

frozenset: need a set of sets (for example, unordered pairs of graph nodes as dictionary keys)? A mutable set is unhashable, whereas frozenset({u, v}) is sealed and hashable!

One-line deduplication: because Python 3.7+ dictionaries preserve insertion order, list(dict.fromkeys(items)) deduplicates hashable items in O(n) while keeping first-seen order — doing the same job as our explicit seen = set() + out = [] loop in one expression.

During a grid BFS, you track visited cells with visited = set() and execute visited.add([r, c]). What happens?

Caught it! Mutable containers (list, dict, set) have no stable hash and cannot sit inside a set or serve as a dict key. Pass the sealed tuple (r, c) instead.

Imagine storing a mutable list pt = [0, 1] in a hash bucket and then mutating pt[0] = 9 — its contents would no longer match its bucket! To prevent silent corruption, Python disables hashing on lists, dicts, and sets and immediately raises TypeError: unhashable type: 'list'. Switch to visited.add((r, c)).

7How you combine all four structures in an interview

Compare doing everything with repeated list scans and += against combining list, set, dict, tuple, and ",".join() for the exact same task (returning (unique, counts, common_csv) from two tag lists):

Before: O(n² + n·m) scans & string copies

def summarize_tags(cur, tgt):
    unique, counts = [], {}
    for t in cur:
        if t not in unique:       # O(n) scan!
            unique.append(t)
            counts[t] = cur.count(t)
    common = [t for t in unique if t in tgt]
    csv = ""
    for t in sorted(common):
        if csv:
            csv += ","            # O(k²) copy!
        csv += t
    return (unique, counts, csv)

After: O(n + m + k log k) with all 4 containers

def summarize_tags(cur, tgt):
    seen, unique, counts = set(), [], {}
    for t in cur:
        counts[t] = counts.get(t, 0) + 1
        if t not in seen:         # O(1) avg!
            seen.add(t)
            unique.append(t)
    # O(n + m) set intersection + O(k log k) sort
    common = sorted(seen & set(tgt))
    csv = ",".join(common)        # O(k) copy!
    return (unique, counts, csv)  # tuple!

You deduplicate 50,000 unique IDs. Why does checking if x not in out: on the output list fail work-capped tests while checking if x not in seen: on a helper set passes instantly?

Spot on! On 50,000 unique IDs, in out compares against 0 + 1 + 2 + ... + 49,999 ≈ 1.25 billion items, whereas in seen checks one hash bucket per ID (~50,000 steps total).

Count comparisons on just 5 unique items [10, 20, 30, 40, 50]: with if x not in out:, item 5 has to check all 4 earlier items; with 50,000 items, item 50,000 checks 49,999 earlier items — summing to n(n-1)/2 (O(n²))! A helper set hashes straight to the slot in O(1) average time per item (O(n) total).
