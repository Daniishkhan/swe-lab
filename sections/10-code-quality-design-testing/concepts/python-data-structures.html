Python's built-in data structures

In Part 1, you learned how to steer Python with decisions, loops, and functions. Now you need clean places to hold groups of values — a playlist of songs, a café menu, a guest list, or a map pin. Python gives you four built-in containers (list, tuple, dict, and set) plus text strings (str). Let's make choosing and using all five feel automatic.

  3. Using locked tuples for fixed pairs and keys, and building long text strings cleanly with "".join(...).
  4. Counting items and grouping values in dictionaries without crashing on missing keys.

1Four everyday containers, four clear jobs

Think of Python's four built-in containers as four everyday organizers — each one shines at a different job:

Pick the container by what you do most often — keeping order, looking up by label, or checking whether an item is already present.

One practical speed intuition worth knowing right away: checking whether something is inside a list ("Maya" in names) walks from the first item to the last — fine for 20 items, painfully slow if you do it inside a loop over 50,000 items. A dict or set jumps straight to the answer in one step regardless of size! (In Week 1 you will learn the formal names O(1) and O(n) for this — for now, just remember "instant jump" vs. "walks the whole list".)

Let's walk through each container one at a time, starting with the one you will use every single day: list.

2Lists: ordered collections you can grow and edit

A list stores items in order inside square brackets [...]. Positions (called indices) start at 0 from the left and -1 from the right, so snacks[-1] always grabs the last item cleanly. len(snacks) tells you how many items are inside.

To grab a sub-section, use a slice: snacks[start:stop] (or snacks[start:stop:step]). It follows the exact same rule as range from Part 1 — it starts at start and stops before stop, returning a fresh list. Leave start blank to begin at index 0, leave stop blank to run to the end, and use step -1 ([::-1]) to walk backward through every item:

snacks = ["apple", "chips", "cookie", "nuts", "pear"]

snacks[0]           # "apple"  (first item)
snacks[-1]          # "pear"   (last item)
snacks[1:4]         # ["chips", "cookie", "nuts"]  (indices 1, 2, 3 — stops before 4!)
snacks[:2]          # ["apple", "chips"]           (first 2 items)
snacks[-2:]         # ["nuts", "pear"]             (last 2 items)
snacks[::-1]        # ["pear", "nuts", "cookie", "chips", "apple"]  (reversed copy)

Because a list stores items side by side in numbered slots, the back end is fast and the front end is slow:

  • Adding or removing at the back: snacks.append("tea") and snacks.pop() touch only the last slot — 1 quick step!
  • Adding or removing at the front: snacks.insert(0, "tea") and snacks.pop(0) force Python to scoot every other item one slot over! Doing that inside a big loop makes your program crawl.
Switch between adding at the back (fruits.append("kiwi"): 1 step) and inserting at the front (fruits.insert(0, "kiwi"): scoots every existing fruit one slot to the right).
Lists are great for ordered, changing sequences. Use [0], [-1], and [start:stop] to read them, and prefer editing at the back (append and pop()) rather than inserting or popping at index 0 inside loops.

Given snacks = ["apple", "chips", "cookie", "nuts", "pear"], what do snacks[-2] and snacks[1:3] return?

Spot on! From the back: -1 is "pear" and -2 is "nuts". And [1:3] takes indices 1 and 2 and stops before 3 → ["chips", "cookie"].

Check on a tiny 4-item list ["a", "b", "c", "d"]: counting from the end, -1 is "d" and -2 is "c". For slicing [1:3], start at index 1 ("b"), take index 2 ("c"), and stop strictly before index 3 ("d"). Same rule on snacks gives "nuts" and ["chips", "cookie"].

Lists are built to change. Next, what about values that should stay locked once created — like a map pin or a piece of text?

3Tuples and strings: ordered values that stay locked

A tuple looks like a list with parentheses (...) instead of square brackets — you can read spot[0] and spot[-1] just like a list, but once created, you cannot append, remove, or overwrite its items. That lock gives you three handy everyday perks:

  • Clean unpacking and 1-line swaps: assign every slot to a named variable in one line: 
    pin = (37.77, -122.42)
lat, lon = pin            # lat is 37.77, lon is -122.42

a, b = 10, 20
a, b = b, a               # swaps a and b cleanly: now 20, 10!
  • Safe inside sets and as dictionary keys: because a tuple of fixed values (like (lat, lon) or ("Maya", 2026)) cannot change later, Python lets you store it in a set or use it as a dict key — whereas editable lists are not allowed there!
  • Watch the 1-item comma catch: parentheses alone just group expressions like (2 + 3), so (42) is just the number 42! A 1-item tuple always needs a trailing comma: (42,).

A str (string of text) is also locked once created. You can index and slice it just like a list (word[0], word[-1], word[::-1]), and Python gives you friendly everyday text helpers:

raw = "  Maya@Example.COM  "
clean = raw.strip().lower()     # "maya@example.com" — trims spaces & lowercases

words = "go dog go".split()     # ["go", "dog", "go"] — splits on spaces
csv = "red,blue,green".split(",") # ["red", "blue", "green"]

Because strings cannot be edited in place, gluing text with msg += piece inside a large loop copies the entire growing text over and over! Instead, collect pieces in a list and join them once at the end with "".join(parts) (or ", ".join(names)):

Want comma-separated names? Put the separator in front of .join: ", ".join(["Maya", "Sam", "Kai"]) → "Maya, Sam, Kai".
Use tuple for fixed pairs and keys (remember the comma in a 1-item tuple (42,)!), and build multi-step strings by appending to a list and calling "".join(parts) once.

You want a 1-item tuple holding 42, write one = (42), and then call len(one). What happens?

Spot on! Without a comma, parentheses just group an expression, so (42) is a plain int (which has no length). Write one = (42,) to make a 1-item tuple.

Think about math: in (3 + 4) * 2, parentheses around 7 just keep the number 7 — they do not turn it into a tuple! So (42) is just 42, and calling len(42) crashes with TypeError until you add a trailing comma: (42,).

So far every collection looked items up by number (0, 1, 2...). What when you want to look something up directly by a label — like looking up the price of "latte" on a menu, or counting votes?

4Dictionaries: instant lookup by label

A dict pairs each unique key (label) with a value inside curly braces {key: value}. Looking up a value by its key is instant, and Python remembers the exact order you added keys. Writing key in menu (or key not in menu) checks whether a key exists in the dictionary (not a value).

menu = {"latte": 5, "tea": 3, "muffin": 4}

menu["latte"]                 # 5 (instant lookup!)
menu.get("mocha", 0)          # 0 (safe fallback if "mocha" is missing)
menu["tea"] = 3.5             # updates an existing price
menu["bagel"] = 4             # adds a new item
menu.pop("muffin", None)      # removes "muffin" safely (returns None if missing)

for item, price in menu.items():
    print(item, "costs $", price)

Crucial difference: menu["mocha"] crashes with a KeyError if "mocha" is not on the menu, whereas menu.get("mocha", 0) quietly returns 0 without changing menu.

Two dictionary patterns show up constantly in everyday Python:

  1. Counting how often items appear: 
    votes = ["tacos", "sushi", "tacos", "pizza", "tacos"]
counts = {}
for food in votes:
    counts[food] = counts.get(food, 0) + 1
# counts is {"tacos": 3, "sushi": 1, "pizza": 1}
  2. Grouping items into lists by a label: 
    people = [("Maya", "NYC"), ("Sam", "LA"), ("Kai", "NYC")]
by_city = {}
for name, city in people:
    if city not in by_city:       # checks dictionary keys!
        by_city[city] = []        # create an empty list the first time we see this city
    by_city[city].append(name)
# by_city is {"NYC": ["Maya", "Kai"], "LA": ["Sam"]}
Step through grouping [("Maya", "NYC"), ("Sam", "LA"), ("Kai", "NYC")] into a dictionary one person at a time.
Use a dict whenever you look up values by label, count items, or group items into lists. Use .get(key, default) for safe reads, .pop(key, None) for safe deletes, and for k, v in d.items(): to loop over pairs.

Given menu = {"latte": 5}, what happens when you run menu["mocha"] vs. menu.get("mocha", 0)?

Exact! Square brackets menu["mocha"] fail loudly with KeyError when a key isn't there, while .get("mocha", 0) returns your fallback value and leaves menu untouched.

Try a tiny phonebook phones = {"Maya": "555-0100"}: asking for phones["Sam"] crashes right away with KeyError: 'Sam', whereas phones.get("Sam", "unknown") hands back "unknown" cleanly without adding "Sam" to the phonebook.

A dictionary pairs each label with a value. What if you don't need values at all — you just want unique items, instant "have I seen this already?" checks, or a clean way to compare two groups?

5Sets: unique items, instant checks, and comparing two groups

A set holds unique items with zero duplicates and lets you check item in seen instantly. Memorize one syntax gotcha right away: empty curly braces {} make an empty dictionary, NOT a set — always write seen = set() for an empty set! To turn an existing list into a set (dropping duplicates), call set(my_list).

seen = set()          # empty set (NEVER {}!)
seen.add("Maya")      # adds "Maya"
seen.add("Maya")      # already there — ignored!
seen.discard("Zoe")   # safe remove (no error if "Zoe" isn't in seen)
"Maya" in seen        # True — instant check!

old = set(["latte", "tea", "mocha", "tea"])  # {"latte", "tea", "mocha"}

Because a set does not remember insertion order, a favorite everyday trick is pairing a set (for instant duplicate checks) with a list (to keep items in the order they arrived). Suppose you want to keep unique song requests in order:

requests = ["Song B", "Song A", "Song B", "Song C", "Song A"]
seen = set()
playlist = []

for song in requests:
    if song not in seen:        # instant check — even with 50,000 songs!
        seen.add(song)
        playlist.append(song)
# playlist is ["Song B", "Song A", "Song C"]

Also handy: old ^ new gives items in only one menu ({"latte", "matcha"}). Because sets don't promise alphabetical order, wrap any set result in sorted(...) whenever you want a neat sorted list back!
Create empty sets with set() (never {}), convert lists with set(items), pair a set with a list when you need both uniqueness and original order, and use -, &, |, and ^ to compare two groups cleanly.

You write guests = {} and then call guests.add("Maya"). What happens?

Caught it! Empty braces {} always belong to dict, which has no .add() method. Write guests = set() for an empty set.

Compare {"Maya"} with {}: when there is an item inside with no colon, Python knows {"Maya"} is a set. When the braces are empty, Python always creates an empty dict — so guests.add("Maya") fails immediately until you write guests = set().

Suppose you have 50,000 unique song requests and want to keep only the first occurrence of each. Why is checking if song not in seen: (a set) dramatically faster than checking if song not in playlist: (a list)?

Spot on! On 50,000 unique songs, checking the list compares against up to 49,999 earlier songs per turn (over a billion checks total!), whereas checking the helper set takes just one quick lookup per song.

Picture a paper list of 50,000 song titles in random order: to know if song #50,000 is already written down, your finger has to scan all 49,999 lines above it! A set acts like an instant index — it answers "already seen?" in one step without scanning the list.

6Choosing the right container — and four mistakes to avoid

Whenever you start a new function, ask one quick question:

  • Do I need items in order, possibly with duplicates? → list
  • Is it a fixed group of values (like a coordinate or pair) that shouldn't change? → tuple
  • Do I want to look up values by label, count items, or group things? → dict
  • Do I only care about unique items, instant in checks, or comparing two groups? → set

Watch out for these four everyday container mistakes:

Notice mistake #4: sets and dictionary keys must stay locked so Python never loses track of where it filed them (Python calls editable containers "unhashable") — use a tuple instead of a list!
Optional bonus: frozenset and a 1-line order-preserving dedupe trick

frozenset: need to put a set inside another set or use a set as a dictionary key? frozenset({"a", "b"}) is a locked version of a set.

1-line dedupe: because Python dictionaries remember insertion order, list(dict.fromkeys(items)) removes duplicates while keeping first-seen order — doing the same job as our seen = set() + playlist = [] loop in one expression.

You want to track saved map pins with pins = set() and write pins.add([37, -122]). What happens?

Spot on! Because a list can be edited later, Python calls it unhashable and refuses to put it inside a set or use it as a dict key. Switch to the locked tuple pins.add((37, -122)).

Think about filing a folder under a label written in pencil: if someone erased and changed the label after you filed it, you could never find it again! That's why Python blocks editable containers (list, dict, set) from being stored in a set or used as a dict key, raising TypeError: unhashable type right away. Use a locked tuple (37, -122) instead.
