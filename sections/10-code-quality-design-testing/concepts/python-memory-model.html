Phase 0 · Day 1 · Part 1

How Python holds data in memory

P0 Phase 0 Python foundationabout 15 minutes6 quick checks · 4 exercises

Most baffling Python interview bugs — a grid row silently overwriting another row, a snapshot mutating behind your back, a default list leaking between calls, or loop functions all returning the final number — look like four unrelated quirks. They are not. Every single one is the exact same rule showing up in four different disguises.

By the end you'll be able to

  1. Trace any Python assignment, edit, or function call using one picture: sticky notes stuck onto objects on a workshop bench.
  2. Explain why editing a shared list surprises you while reassigning an integer never does.
  3. Build independent 2D grids and real deep copies — and spot when list slicing quietly copies thousands of references inside a loop.
  4. Predict why shared default lists leak across calls and why functions built inside loops all read the final loop value — and write both clean fixes.
  5. Tell apart missing values from valid zeroes or empty lists, and avoid editing a container while looping over it.

How to read this: top to bottom on Phase 0 Day 1 before touching algorithms. Answer every quick check before moving on — a wrong answer explains the idea a second way. Skip collapsed "Go deeper" boxes on a first pass. Builds on no prior chapters.

1Why do innocent Python lines silently corrupt data?

Picture a 45-minute Google bare-editor round. You spot the optimal dynamic programming solution in 8 minutes, type dp = [[0] * cols] * rows, and start hand-tracing your table. At minute 20 your jaw drops: writing dp[0][2] = 7 somehow changed row 1, row 2, and row 3 to 7 as well. Fifteen minutes vanish hunting a bug that has nothing to do with your algorithm.

If you grew up on C, C++, or Java primitives, you probably picture a variable as a labeled box holding a value — so assigning b = a copies the value into a second box. Python does not work that way.

Instead, picture a workshop bench. Every value in Python (every number, string, list, dictionary, and even every function) is an object sitting on the bench. A variable name like a or b is not a box — it is a sticky note stuck onto an object. Running b = a never photocopies the object on the bench; it sticks a second sticky note b onto the exact same object that a points to.

In Python, assignment never copies data. It only attaches a name (sticky note) to an existing object on the bench.

Hold onto that workshop bench — we are not leaving it for the rest of this chapter. Every section below follows this single sticky-note rule one step further: first across numbers and lists, then into 2D grids and copies, and finally onto Python functions and loops.

Wait — the moment you hear "b = a puts two sticky notes on the same object," an immediate puzzle pops up: if b = a shares the object, why doesn't running a = 5; b = a; a = a + 1 change b into 6?

2Why doesn't changing an integer change its copy — while changing a list does?

Look closely at what is sitting on the bench. Python has two kinds of objects:

  • Open boxes (mutable objects): list, dict, and set. You can reach inside an open box and add, remove, or edit items without moving the sticky note. Calling a.append(3) drops 3 straight into the box — so every other sticky note stuck on that box (b!) immediately sees [1, 2, 3].
  • Sealed stones (immutable objects): int, float, str, bool, None, and tuple. Nobody can reach inside the stone 5 and carve it into a 6. So when you run a = a + 1, Python places a brand-new stone 6 on the bench, peels sticky note a off 5, and sticks a onto 6. Sticky note b never moved — it stays glued to 5!

That reveals the sharpest distinction in Python: mutating edits the box in place (a.append(3), a[0] = 9, a += [3]), while rebinding peels a sticky note off one object and sticks it onto another (a = a + 1, a = [9, 9]). Passing an argument into a function obeys the exact same rule (call by sharing): Python sticks the parameter's sticky note onto the caller's object — so mutating a passed list (nums.sort(), nums.append(x)) changes the caller's list, while rebinding the parameter (nums = sorted(nums)) only moves the local sticky note!

Step through both modes on the workshop bench. Watch sticky note a stay on the same open list box during append(3), whereas a = a + 1 peels sticky note a onto a brand-new stone 6.

Where the sealed-stone picture needs two footnotes: first, a tuple is a sealed tray whose slots cannot be pointed at different objects later (t[0] = 99 fails), yet if a slot points to an open list box (t = ([1, 2], "ok")), you can still mutate that inner list with t[0].append(3) (so a tuple is only safe as a dictionary key if every item inside it is immutable too). Second, Python sometimes reuses pre-built sealed stones behind the scenes — which is why you always compare values with == and reserve is (same exact object on the bench) for None.

Go deeper: == vs. is and CPython small-integer caching

a == b checks whether two objects hold equal values; a is b checks whether both sticky notes point to the exact same object address (id(a) == id(b)). As an optimization, CPython pre-allocates and reuses small integers (-5 to 256) and some short strings — so x = 256; y = 256; x is y is True, whereas int("1000") is int("1000") is False! Never use is to compare ints or strings — only use is None / is not None.

Assignment (=) and function calls always attach a sticky note to an object; they never copy. Mutating an open box updates every sticky note on it (including the caller's), whereas rebinding moves only one sticky note — and use == for values, is only for None.

Trace these four lines on the workshop bench. What does print(a, b) output?

a = [1, 2]
b = a
a = a + [3]
print(a, b)

Sharp eye! Unlike a.append(3) or a += [3] (which mutate the box in place), a + [3] constructs a brand-new list box [1, 2, 3], and a = ... peels only sticky note a onto it — leaving b on [1, 2].

Check object identities on a fresh pair: x = ["p"]; y = x gives id(x) == id(y). Running x = x + ["q"] allocates a second box (id(x) != id(y)) and moves only sticky note x onto it — y is never touched! So here a becomes [1, 2, 3] while b stays [1, 2].

Now you have both halves of the bench rule — open boxes versus sealed stones. Watch how they unlock our opening 2D grid disaster in ten seconds.

3Why does multiplying a 2D grid link every row together?

A list in Python doesn't store values directly inside its slots — each slot holds a sticky note pointing to an object on the bench. Now look at what Python's repeat operator * actually does: it repeats the sticky notes inside the list.

  • 1D list of ints ([0] * 3) — completely safe! All three slots stick notes onto the sealed stone 0. When you later write row[0] = 99, you cannot edit stone 0, so Python peels slot 0's sticky note onto stone 99. Slots 1 and 2 stay glued to 0!
  • 2D list of lists ([[0] * 3] * 3) — classic disaster! The inner expression builds one open list box [0, 0, 0]. The outer * 3 repeats the sticky note to that same open box three times — so g[0], g[1], and g[2] all point to one single row! Writing g[0][0] = 99 reaches inside that one box and mutates all three rows at once.
The exact same bug hits graph neighbor lists: write adj = [[] for _ in range(n)], never [[]] * n.

To give every row its own fresh box on the bench, force Python to evaluate [fill] * cols once per row inside a loop (this is make_grid in py_internals.py):

def make_grid(rows, cols, fill=0):
    if rows < 0 or cols < 0:
        raise ValueError("rows and cols must be non-negative")
    return [[fill] * cols for _ in range(rows)]   # fresh inner box per row!
Multiplying a list repeats sticky notes, not boxes. Use [0] * cols only for immutable fill values (ints, strings, bools, None), and use for _ in range(rows) whenever each slot needs its own mutable box.

You initialize an empty adjacency list for 3 graph nodes with adj = [[]] * 3, then add one edge with adj[0].append(2). What is adj now?

Caught it! [[]] * 3 puts three sticky notes onto one empty list box, so appending to adj[0] appends to adj[1] and adj[2] as well. Always write [[] for _ in range(3)].

Python allows [[]] * 3 with zero error (no TypeError!) — and you can check adj[0] is adj[1] is adj[2]: it is True! Because all three slots hold references to that one inner list, adj[0].append(2) mutates all three slots into [[2], [2], [2]].

Great — now you can build an independent 2D grid without linking its rows. Five minutes later in a backtracking problem, you need to save a snapshot of that board before mutating it. If snap = grid only adds another sticky note, how do you actually photocopy a nested box — and what does copying cost?

4How do you actually copy a box — and what does slicing quietly cost?

Every Python copying bug comes from mixing up three depths of copying on the workshop bench:

  1. Alias (snap = grid): zero new boxes. Both sticky notes point to the same outer box.
  2. Shallow copy (snap = grid[:], list(grid), or copy.copy(grid)): builds one new outer box and copies the sticky notes inside it. For a flat list of numbers ([1, 2, 3]), that's completely independent! For a 2D board, snap is a fresh outer list whose slots still point to the exact same inner row boxes — so editing grid[0][1] = "X" STILL changes snap[0][1]!
  3. Deep copy ([row[:] for row in grid] or copy.deepcopy(obj)): builds a new outer box and fresh inner boxes at every nested level. For a 2D grid of ints or strings, [row[:] for row in grid] is much faster than general copy.deepcopy().
Slicing a[:] copies only the outer layer of sticky notes. Nested mutable lists need one more layer of copying.

The hidden performance cost of slicing boxes

Notice what nums[i:j] just did on our bench: it allocated a brand-new list box and copied k = j - i sticky notes into it (taking linear work proportional to the slice length — O(k) time and space). Outside a loop, one slice is tiny. Inside a loop or recursion, it silently explodes your runtime:

  • Passing nums[1:] at every step of an n-step recursion copies n - 1, then n - 2, …, down to 1 references — about n² / 2 copies (turning a single linear pass into quadratic O(n²) work!).
  • Writing sum(nums[i:i+k]) inside a loop over n = 100,000 numbers with window size k = 50,000 builds 50,000 slice boxes of 50,000 items each — 2.5 billion copies and additions (O(n·k), hitting O(n²) when k ≈ n/2)!

The bench-aware fix: pass integer indices (lo, hi) into recursive helpers instead of slicing lists — and in Chapter 10.11 you'll see how running totals compute all 50,000 window sums in a single linear pass without slicing once.

grid[:] only shallow-copies the outer box — use [r[:] for r in grid] or copy.deepcopy() for nested mutable data. And never slice inside a tight loop or recursion when integer indices (lo, hi) avoid copying k references every step.

You snapshot a 2D board with snap = grid[:] before backtracking, then run grid[0][1] = "X". What is snap[0][1]?

Spot on! snap is not grid is True, yet snap[0] is grid[0] is also True. Use [row[:] for row in grid] or copy.deepcopy(grid) for a real snapshot.

Trace two levels on grid = [["_", "_"], ["_", "_"]]: snap = grid[:] makes a brand-new outer box, then copies the sticky notes to row0 and row1 into it. Mutating grid[0][1] = "X" edits that shared row0 box — so snap[0][1] is now "X" too.

So far we have only placed numbers and lists on our workshop bench. Ready for the twist that makes Python's functions click forever? Functions themselves are objects sitting on that exact same bench — and they obey the exact same sticky-note rule.

5Why do default arguments remember previous function calls?

When Python reads a def statement, it does not wait until you call the function to look at the header line. Right then — once, at def time — Python builds a function object on the bench, evaluates every default argument expression once, and attaches a sticky note to each default object inside the function (fn.__defaults__).

Now imagine you write def append_log(entry, bucket=[]):. Look at what sits on the bench:

  1. When def runs, Python builds one open list box [] and tucks a sticky note to it inside append_log.
  2. Call #1: append_log("first") omits bucket, so Python uses that default box and appends "first" → ["first"].
  3. Call #2: append_log("second") omits bucket again — Python hands it the exact same box, now holding ["first", "second"]!

The fix uses a sealed stone sentinel (None) as the default, then builds a fresh open list box inside the function body whenever the caller didn't pass one (this is append_log in py_internals.py):

def append_log(entry, bucket=None):
    if bucket is None:          # NOT `bucket = bucket or []`!
        bucket = []             # fresh list box created per call
    bucket.append(entry)
    return bucket

Why bucket = bucket or [] is STILL a subtle bug: suppose the caller intentionally passes their own brand-new empty list box: my_log = []; append_log("first", my_log). An empty list [] is falsy in Python! So bucket or [] sees bool(my_log) == False, throws away the caller's sticky note, creates a disconnected list, and leaves my_log empty! Testing if bucket is None: respects every real box the caller hands you — even an empty one.

Default argument expressions run once when def executes, not on each call. Never put a mutable box ([], {}, set()) as a default — use None and check if arg is None: (never arg or []).

Someone "fixes" mutable defaults by writing def append_log(entry, bucket=None): bucket = bucket or []; bucket.append(entry); return bucket. A caller runs log = []; append_log("hi", log). What is log afterward?

Nailed it! [] or [] evaluates to the second (newly created) list, so append("hi") mutates the new list and leaves the caller's log untouched at []. Always write if bucket is None:.

Evaluate bucket or [] when bucket is the caller's empty list []: Python checks bool([]), gets False, and returns the right-hand fallback — a brand-new list box! Appending "hi" edits that new box, leaving the caller's log completely empty ([]).

Default arguments aren't the only sticky note a function object holds on the bench. What happens when you create several small functions inside a loop — and each function tries to remember the loop variable?

6Why do functions created in a loop all return the last value?

Suppose you need a list of multiplier functions — one that doubles its input, one that triples it, and one that multiplies by 10 — so you write a 1-line lambda (an unnamed mini-function) inside a loop:

fns = [lambda x: x * f for f in [2, 3, 10]]
print([g(5) for g in fns])     # expected [10, 15, 50] ... actual: [50, 50, 50]!

Why on earth did all three return 50?! Put the loop on our exact same workshop bench:

  1. Regular local variables are plain sticky notes — yet the moment an inner function refers to an outer loop variable f (a closure), Python wraps f in a tiny one-slot open cell box on the bench so the loop and every inner function can share it.
  2. Each loop iteration does not build a fresh cell box; it swaps the sticky note inside that one shared cell box: 2 → 3 → 10, while all three lambdas point at the cell box itself.
  3. None of the three lambdas actually run while the loop is building them. By the time you call g(5), the loop has finished and cell f points to 10 — so all three lambdas look up f now (late binding) and compute 5 × 10 = 50!
Step through loop creation vs. calling the functions. Switch the dropdown to see how capturing f=f snapshots each stone onto the function immediately instead of pointing at the shared cell f.

And look at the poetic payoff from Section 5: the exact creation-time default-argument rule that bit us on mutable lists becomes a superpower on immutable numbers! Both standard fixes work cleanly (this is make_multipliers in py_idioms.py):

# Fix 1: default-argument snapshot (evaluates f NOW when each lambda is built!)
fns = [lambda x, f=f: x * f for f in factors]

# Fix 2: helper factory function (each call creates its own private scope cell!)
def _make_mul(factor):
    return lambda x: x * factor

fns = [_make_mul(f) for f in factors]     # also works with functools.partial

Notice why both fixes are safe even if the caller mutates factors[0] = 999 afterward or passes a one-shot generator: each created function captured its own immutable number stone at creation time.

Closures capture a sticky note to the variable cell, not the value it held during that loop step. Snapshot immutable values with a default argument (lambda x, f=f:) or a helper factory function so each function gets its own independent cell.

What does [g() for g in [lambda: i for i in [10, 20, 30]]] return?

Exactly! None of the lambdas run until the inner list finishes with i = 30, and Python keeps that closure cell alive on the bench — so all three read 30.

Separate building functions from calling them: the inner list constructs 3 uncalled lambdas pointing at one shared cell i. That loop finishes with i == 30 (and Python keeps the cell alive, so there is no NameError). Only then does the outer loop call each g(), reading 30 three times.

Now you've traced our sticky-note rule through numbers, lists, grids, copies, defaults, and closures. Two final bench habits catch even seasoned engineers under bare-editor time pressure.

7How else can objects and live boxes trip you up in interviews?

Watch out for two last object-model pitfalls on the bench:

  1. Identity (is None) vs. truthiness (if x:): Just like Section 5's empty caller box [], real objects on the bench such as 0, 0.0, "", and False evaluate to False in an if test — even though sticky note x is not pointing at the None stone! Whenever 0 or [] is a valid input, check identity (if score is not None: / if bucket is None:) or dict membership (if key in cache:) instead of truthiness.
  2. Mutating a live box while a for loop is walking it: A for loop holds a live bookmark inside a container box. Deleting or adding keys in a dict or set mid-loop triggers RuntimeError on the next loop step; removing items from a list mid-loop shifts the remaining sticky notes left under the bookmark and silently skips neighbors! Walk a snapshot (list(d)) or build a fresh filtered box instead.

Compare fragile vs. bench-safe Python side by side:

Before: shared boxes + falsy & live-delete traps

dp = [[0] * m] * n          # linked rows!
def log(x, buf=[]):         # leaked default!
    buf.append(x)
    return buf

valid = [r for r in recs if r[1]]  # drops 0!
for k in counts:            # RuntimeError!
    if counts[k] == 0:
        del counts[k]

After: bench-safe interview Python

dp = [[0] * m for _ in range(n)]
def log(x, buf=None):
    if buf is None: buf = []
    buf.append(x)
    return buf

valid = [r for r in recs if r[1] is not None]
for k in list(counts):
    if counts[k] == 0:
        del counts[k]

You want to delete every zero-count key from a dictionary counts. Why does calling del counts[k] directly inside a for k in counts: loop fail?

Exact! Snapshot the keys first with for k in list(counts): or rebuild a clean dictionary with {k: v for k, v in counts.items() if v != 0}.

Trace counts = {"a": 0, "b": 1}: on step 1, del counts["a"] shrinks the dict from size 2 to 1. On the very next step, Python's dict iterator sees the size changed and raises RuntimeError immediately (it's a list that silently skips items!). Snapshot keys with list(counts) first.

8What to say in the interview

Before moving to Part 2 (Transforming and streaming data), make sure you can speak these four rules smoothly in under 45 seconds:

  1. References & grids: "Python names are references to objects, so [[0] * cols] * rows aliases one inner row list; I'll allocate independent rows with a list comprehension."
  2. Copies & slicing: "grid[:] is only a shallow copy of outer references — I'll copy each row [r[:] for r in grid] for a 2D snapshot, and pass (lo, hi) indices instead of slicing inside loops to avoid hidden O(k) copies."
  3. Defaults & closures: "Default arguments evaluate once at def time, so I use bucket=None with is None (not or []). And loop closures share one variable cell, so I bind with lambda x, f=f: or a helper factory."
  4. Truthiness & safe deletion: "I'll check is not None whenever 0 or "" is valid, and iterate over list(d) before deleting keys."
