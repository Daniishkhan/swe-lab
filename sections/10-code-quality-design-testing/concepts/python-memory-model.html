How Python holds data in memory

P0 Python fluencyabout 15 minutes6 quick checks · 4 exercises

On Day 1, you got comfortable writing loops, functions, lists, tuples, dictionaries, and sets. Today we zoom in on one simple picture of how Python stores data in memory. Once you see this picture, Python's five sneakiest bugs — two names accidentally linked to the same list, surprise row edits, shared function defaults, loop functions reading the wrong value, and crashing loops — all make instant sense.

By the end of this chapter, you'll be comfortable with

  1. Explaining why assigning b = a shares the same list instead of copying it, and knowing when to use == vs. is.
  2. Telling the difference between editing a box in place (a += [3]) and creating a brand-new box (a = a + [3]).
  3. Building independent 2D boards safely (avoiding the [[0] * 3] * 3 trap) and choosing between shallow copies and copy.deepcopy.
  4. Avoiding the mutable default argument trap (bucket=[]) by defaulting to None.
  5. Fixing functions created inside loops and safely removing items while iterating.

Keep Python Cheatsheet (§6–§7) open whenever you want a quick lookup. This chapter builds directly on Day 1 (Control flow and Built-in data structures).

1Names are sticky notes, values are boxes

In some languages, a variable is a fixed drawer that holds a copy of your data. Python does not work that way. In Python, every value (a number, string, list, or dictionary) lives in its own box in memory, and variable names are just sticky notes stuck onto those boxes. Remember from Day 1 that some boxes are editable — Python calls editable types mutable (list, dict, set) and locked types immutable (int, float, str, tuple).

That means writing backup = cart never copies the shopping cart — it just sticks a second sticky note onto the exact same box:

cart = ["milk", "eggs"]
backup = cart                  # NO copy! Both names point to the SAME list

backup.append("bread")         # edits the shared list in place
print(cart)                    # ["milk", "eggs", "bread"] — cart changed too!

backup = ["tea"]               # peels backup off and sticks it on a NEW list
print(cart)                    # ["milk", "eggs", "bread"] — cart is safe!

Watch the difference between editing a shared box (backup.append("bread")) and moving a sticky note to a new box (backup = ["tea"]):

Switch the dropdown between editing the shared cart (backup.append("bread")) and rebinding backup = ["tea"]. Only editing in place changes what the other sticky note sees.

This also explains Python's two equality checks:

  • a == b asks: "Do these two boxes hold the same contents?" (use this 99% of the time!).
  • a is b asks: "Are these two sticky notes stuck on the exact same box?" Reserve is for checking None (if val is None:) — never use is to compare numbers or strings!
a = [1, 2]
b = [1, 2]        # a brand-new list with the same numbers
c = a             # another sticky note on a's list

a == b            # True  — same contents
a is b            # False — two separate boxes!
a is c            # True  — exact same box
Assignment (b = a) never copies data — it adds another sticky note to the same object. Editing a shared list changes what every sticky note sees; reassigning (b = ...) moves only that one sticky note.

What does songs hold after these four lines run?

songs = ["Track A", "Track B"]
queue = songs
queue.append("Track C")
queue = ["Track Z"]

Spot on! On line 3, both sticky notes sit on the same list, so queue.append("Track C") adds "Track C" to that shared list. On line 4, queue = ["Track Z"] peels queue off onto a brand-new list, leaving songs untouched with all three tracks.

Try tracing a tiny example with a = [1] and b = a: calling b.append(2) edits the single shared list to [1, 2], so a sees [1, 2]. Next, writing b = [9] just moves the b sticky note onto a fresh box [9] — it never erases a's box, so a stays [1, 2].

The exact same sticky-note rule applies when you pass a variable into a function — and when you use += on a list vs. a number.

2Passing values to functions and the += surprise

When you pass a list or dictionary to a function, Python does not copy it either — the parameter name inside the function is just one more sticky note on the caller's object! That means if a function calls items.append(...) or items.pop(), the caller's list changes too:

def add_tax_item(cart):
    cart.append("bag fee")      # edits the caller's list directly!

my_cart = ["coffee"]
add_tax_item(my_cart)
print(my_cart)                  # ["coffee", "bag fee"]

If a function shouldn't change the caller's list, either build a fresh list or make a copy first (we'll see how in §3).

Now watch one subtle difference between += and = ... + ... on lists:

a = [1, 2]
b = a
a += [3]           # edits the list IN PLACE! Now BOTH a and b are [1, 2, 3]

a = [1, 2]
b = a
a = a + [3]        # creates a NEW list [1, 2, 3] and moves a only; b stays [1, 2]!

Why does that happen? Because a list is mutable, Python lets a += [3] extend the existing list in place. On immutable (locked) types (int, float, str, tuple), the box cannot change in place — so x += 1 or name += "!" always creates a fresh box and moves only that one sticky note.

Passing a list or dict into a function shares the caller's object. On lists, a += [3] edits in place (changing aliases), while a = a + [3] creates a brand-new list.

What do x and y hold after running this snippet?

x = [10, 20]
y = x
x += [30]
y = y + [40]

Exact! x += [30] edits the shared list in place, so both x and y see [10, 20, 30]. Then y = y + [40] builds a brand-new list [10, 20, 30, 40] and moves only y to it, leaving x at [10, 20, 30].

Compare with p = ["a"]; q = p: running p += ["b"] edits the shared box in place so both see ["a", "b"]; then running q = q + ["c"] builds a fresh box ["a", "b", "c"] and points only q at it, leaving p at ["a", "b"].

Now let's see the most famous place this sticky-note rule catches people by surprise: building a 2D board or copying nested lists.

3The shared-row trap and shallow vs. deep copies

In Python, ["."] * 3 makes a neat 3-slot list [".", ".", "."] — completely safe, because strings like "." are locked and cannot be edited in place. So it feels natural to make a 3×3 tic-tac-toe board by multiplying again: [["."] * 3] * 3. Watch what goes wrong the instant you place an "X" in the top row:

# BUG: all 3 rows are sticky notes on the EXACT SAME inner list!
board = [["."] * 3] * 3
board[0][1] = "X"
print(board)
# [['.', 'X', '.'], ['.', 'X', '.'], ['.', 'X', '.']]  — ALL 3 ROWS CHANGED!

# FIX: build 3 brand-new inner lists (one per loop turn!)
# Tip: "_" is Python's convention for a loop variable whose number we don't need
board = []
for _ in range(3):
    board.append(["."] * 3)
board[0][1] = "X"
print(board)
# [['.', 'X', '.'], ['.', '.', '.'], ['.', '.', '.']]  — ONLY ROW 0 CHANGED!

Shorthand preview: you will often see that safe 3-line loop written on one line as board = [["."] * 3 for _ in range(3)] — we unpack that 1-line list comprehension style in Part 2!

Step through the difference below:

Toggle between buggy [["."] * 3] * 3 (3 sticky notes sharing 1 row box) and 3 fresh rows (each row is its own box in memory).

The exact same "outer box vs. inner boxes" surprise shows up when you copy a list. Python's import statement loads extra tools from built-in modules (like import copy below):

  • Shallow copy (a.copy() or a[:]): copies the outer list only. Perfect for a flat list of numbers or strings like [10, 20, 30]! But if your list holds nested lists inside (like a 2D board), the inner lists are still shared between the original and the copy!
  • Deep copy (copy.deepcopy(board)): loads Python's built-in copy module and clones the outer box and every nested box inside it, so editing anything in the clone can never touch the original.
import copy

# Flat list: shallow copy is completely independent
prices = [4, 5, 6]
prices_copy = prices.copy()
prices_copy[0] = 99          # prices is still [4, 5, 6]

# Nested 2D board: shallow copy STILL shares inner rows!
board = [["A", "B"], ["C", "D"]]
shallow = board.copy()
shallow[0][0] = "Z"          # board[0][0] ALSO became "Z"!

# Deep copy clones every nested layer
board = [["A", "B"], ["C", "D"]]
full = copy.deepcopy(board)
full[0][0] = "Z"             # board[0][0] is still "A"!
Never build a 2D list with [[0] * cols] * rows — create a fresh inner list per row. Use .copy() or [:] for flat lists, and copy.deepcopy(...) whenever lists or dicts are nested inside each other.

You create grid = [[0] * 2] * 3 and run grid[2][0] = 9. What does grid[0][0] equal afterward?

Spot on! * 3 repeats the reference to that single [0, 0] list three times, so editing row 2 edits rows 0 and 1 at the same time.

Picture putting 3 copies of the same house key on a keychain: unlocking the door with key #3 opens the exact same house as key #1! Multiplying [[0] * 2] * 3 copies the key to one inner list 3 times, so changing grid[2][0] to 9 makes grid[0][0] equal 9 too.

You run teams = [["Maya", "Sam"], ["Kai"]], then backup = teams.copy(), and then backup[0].append("Leo"). What does teams[0] hold?

Sharp catch! teams.copy() creates a new outer list, yet slot 0 of backup still points to the same ["Maya", "Sam"] list as slot 0 of teams. Use copy.deepcopy(teams) to clone inner lists too.

Think of copying a folder full of shortcuts: you now have two folders, yet both folders contain shortcuts to the same inner files! .copy() only duplicates the outer list — appending "Leo" inside backup[0] edits the shared inner list, so teams[0] becomes ["Maya", "Sam", "Leo"].

That sticky-note picture also explains one of the most notorious traps in all of Python: putting =[] as a function's default argument.

4Default function arguments run once (the bucket=[] trap)

Suppose you write a tiny helper to add a note to a list, defaulting to an empty list when the caller doesn't pass one:

# BUG: the default list [] is created ONCE when Python reads def!
def add_note(msg, notes=[]):
    notes.append(msg)
    return notes

print(add_note("call Mom"))    # ["call Mom"]
print(add_note("buy milk"))    # ["call Mom", "buy milk"]  — WHAT?!

Why did "call Mom" show up inside the second call? Because Python creates default argument values once when the def line runs — not fresh on each function call! Every call that omits notes shares that exact same hidden list box forever.

The standard Python fix is always the same three lines: default to None (locked!) and create a brand-new list inside the function body:

# SAFE: fresh list created inside the body whenever notes is None
def add_note(msg, notes=None):
    if notes is None:
        notes = []
    notes.append(msg)
    return notes

print(add_note("call Mom"))    # ["call Mom"]
print(add_note("buy milk"))    # ["buy milk"]  — clean!

Watch one subtle detail: always write if notes is None: — not notes = notes or []! Why? In Python, an empty list [] counts as falsy (just like 0, "", False, and None), and a or b falls back to b whenever a is falsy. So if a caller intentionally hands you their own empty list my_list = [] and calls add_note("hi", my_list), notes or [] throws away my_list and creates a separate list, leaving my_list empty!

Never put a mutable default like notes=[] or cache={} in a def line. Always default to None and guard with if notes is None: notes = [].

Someone tries to fix the default-argument bug by writing notes = notes or [] inside add_note(msg, notes=None). Then a caller runs my_log = [] followed by add_note("hi", my_log). What does my_log hold afterward?

Sharp catch! Because an empty list [] counts as falsy in Python, my_log or [] ignores my_log and creates a brand-new list, appending "hi" there instead. Writing if notes is None: keeps the caller's empty list intact!

Check what [] or ["fallback"] evaluates to in Python: since [] is falsy, or moves on to the right-hand side and returns ["fallback"]! So notes = notes or [] throws away the caller's empty my_log, appends "hi" to a fresh list, and leaves my_log empty ([]).

5Functions created in loops and editing while iterating

1. Capturing a loop variable inside a function

In Python, functions are values just like numbers or strings — you can store them inside a list! For a tiny 1-line function, Python also has lambda: writing lambda x: x * 2 creates an unnamed mini-function that takes x and returns x * 2.

Now suppose you build a list of multiplier functions in a loop — one that doubles, one that triples, and one that multiplies by 10:

# BUG: every function looks up factor LATER when called (after the loop ended at 10!)
funcs = []
for factor in [2, 3, 10]:
    funcs.append(lambda x: x * factor)

print(funcs[0](5))    # 50 (expected 10!) — factor ended the loop at 10!
print(funcs[1](5))    # 50 (expected 15!)
print(funcs[2](5))    # 50 (expected 50)

Why did all three print 50? Because an inner function does not snapshot factor when created — it keeps a sticky note pointing to the loop variable factor and reads whatever factor holds when you call the function later (which is 10, the last turn of the loop!). Python calls an inner function that remembers variables from an outer scope a closure.

Two clean fixes snapshot each turn's value immediately:

# FIX A: snapshot the value into a default parameter (defaults run at creation time!)
funcs = []
for factor in [2, 3, 10]:
    funcs.append(lambda x, f=factor: x * f)

# FIX B: build each closure inside a tiny helper (each call gets its own f box)
def make_mult(f):
    def mult(x):
        return x * f
    return mult

funcs = []
for factor in [2, 3, 10]:
    funcs.append(make_mult(factor))

2. Never delete items from a container while looping over it

Suppose you want to remove every expired item from a dictionary, or drop negative numbers from a list:

  • Deleting keys from a dict (with del menu[item]) or items from a set while looping directly over it crashes immediately with RuntimeError: dictionary changed size during iteration.
  • Removing items from a list while looping over it scoots the remaining items left, silently skipping neighbors!

Calling list(menu) makes a snapshot list of the dictionary's keys up front. Always loop over a snapshot (list(menu)) or build a fresh filtered list instead:

# SAFE dict cleanup: loop over a snapshot list of the keys
menu = {"latte": 5, "old_pie": 0, "tea": 3}
for item in list(menu):
    if menu[item] == 0:
        del menu[item]              # del removes that key safely from menu

# SAFE list cleanup: build a fresh list of items to keep
temps = [20, -4, -1, 18]
warm = []
for t in temps:
    if t >= 0:
        warm.append(t)              # [20, 18] — never skips a neighbor!
Functions built inside a loop read the loop variable's final value unless you snapshot it (lambda x, f=factor: or a helper def). And never delete from a list, dict, or set while looping over it — iterate a snapshot or build a new list.

You run this loop and call adders[0](10). What does it return?

adders = []
for n in [1, 2, 5]:
    adders.append(lambda x: x + n)

Spot on! None of the lambdas run until you call adders[0](10) — by then the loop has finished and n holds 5, so all three add 5. Writing lambda x, n=n: x + n captures each turn's n into a default parameter at creation time.

Think of n as a whiteboard that gets erased and rewritten on every turn: first 1, then 2, then 5. Each lambda just says "look at the whiteboard and add that number to x." When you call adders[0](10) after the loop finishes, the whiteboard says 5, so it returns 10 + 5 = 15!
