Chapter 10 · Part 1

Python for interviews: the toolkit

P0 every coding round is in a languageabout 40 minutes8 quick checks · 7 exercises

In a 45-minute round you don't have time to build a counter, a queue or a sorted index by hand. Python ships all of them. This chapter is the short list of tools that come up in almost every problem, what each one costs, and the few traps that turn a fast answer into a slow or wrong one.

By the end you'll be able to

  1. Say the cost of every common list, dict, set and string operation, including the hidden ones.
  2. Reach for Counter, defaultdict, deque, heapq, bisect, sorted(key=…), itertools and functools.cache without looking them up.
  3. Spot the four traps that interviewers see most: list.pop(0), in on a list, string += in a loop, and mutable default arguments.
  4. Write code that reads cleanly: good names, small helpers, dataclass for records.

How to read this: top to bottom. It builds on How fast is your code? (Big-O and amortized cost). You'll meet heaps, trees and sorting properly later this week; here you only need what each tool does and what it costs. Keep a one-page cheat sheet as you go (exercise 3).

1The problem: one line, two minutes

You're asked to process a queue of 1,000,000 print jobs in arrival order. You write the obvious thing: keep the jobs in a list, and take the next one with jobs.pop(0). It's correct. On 1,000 jobs it's instant.

On 1,000,000 jobs it takes about two minutes. Swap the list for collections.deque and change pop(0) to popleft(), and the same loop finishes in under a tenth of a second. One line, a thousand times faster.

Nothing about the algorithm changed. The difference is what the tool does underneath. A list is a row of numbered boxes. Taking the first box out means sliding every other box one place to the left, so each pop(0) touches the whole list. A million pops of a list that averages half a million items is about 5 × 10¹¹ moves. A deque is built so both ends are cheap.

Interviewers notice this. "Why a deque?" is a question you want to answer in one sentence. So for each tool below, learn two things: what problem it solves, and what it costs.

A list holds n items. Why is a.pop() O(1) but a.pop(0) O(n)?

Right. A list is one block of slots in memory. The end has no neighbors to move; the front has all of them.

Picture a row of 10 chairs, everyone seated. The person in the last chair leaves: done, nobody moves. The person in the first chair leaves: if the row must stay packed from chair 1, all 9 others shuffle over. Nothing is searched, and no new row is built; the existing items just slide. That slide is n − 1 moves.

2The four built-ins and their price list

Almost everything you write uses four built-in types. Each is a data structure you'll study this week, so the costs follow from its shape:

  • list: a row of slots (an array). Fast by position, fast at the end, slow at the front and in the middle.
  • dict and set: hash tables. Fast lookup by key, no order except insertion order.
  • str: a row of characters that can never change. Every "edit" builds a new string.

The traps are the rows that look like one step but aren't. if x in seen is O(1) when seen is a set and O(n) when it's a list; inside a loop that is the difference between O(n) and O(n²). A slice inside a loop (helper(a[1:]) in a recursion) copies on every call. And min() inside a loop rescans everything each time.

# O(n²): result grows, and each += may copy everything built so far
out = ""
for w in words:
    out += w + " "

# O(n): collect the pieces, join once at the end
out = " ".join(words)
A line of Python is not one step. Ask what the line does to the data structure underneath: jump to a slot, shift everything, scan everything, or copy.
Go deeper: CPython sometimes makes string += fast

CPython has an optimization: if the string on the left has no other references, s += t can grow it in place. That's why the slow loop above sometimes looks fine when you time it. It's an implementation detail (PyPy and other runtimes don't promise it, and any second reference to s turns it off), so in an interview say "join is O(n); += in a loop is O(n²) in general".

This loop runs over 100,000 user ids: if uid not in seen: seen.append(uid). What's the cost, and the fix?

Right. Each in on a list scans it, and the list grows to n. A set answers in in O(1) on average, so the loop becomes O(n). If you also need the first-seen order, keep both a set and a list, or use dict.fromkeys(ids), which keeps insertion order.

Count the hidden work. The append is cheap, but in on a list checks items one by one. By the 50,000th id it checks up to 50,000 items. Add those up across 100,000 ids and you get about n²/2 = 5 billion checks. A set jumps straight to where the id would be, so each check is about one step. A sorted list would let you binary search, but inserting into the middle of it shifts items, so it doesn't fix the cost.

3Counting and grouping: Counter and defaultdict

Half of all hash map problems are "count things" or "put things in buckets". You can write both with a plain dict, but every time you'll write the same three lines to handle a key you haven't seen yet. Python has two tools that remove those lines.

from collections import Counter

counts = Counter("mississippi")
# Counter({'i': 4, 's': 4, 'p': 2, 'm': 1})
counts["z"]          # 0, no KeyError
counts.most_common(2)
# [('i', 4), ('s', 4)]
from collections import defaultdict

by_len = defaultdict(list)
for w in ["hi", "yo", "cat"]:
    by_len[len(w)].append(w)
# {2: ['hi', 'yo'], 3: ['cat']}
# a missing key starts as list()

Counter is a dict from item to count. Building it is O(n). most_common(k) picks the top k with a heap in O(n log k); most_common() with no argument sorts everything, O(n log n). Ties come out in the order the items were first counted.

defaultdict(factory) is a dict that calls factory() the first time you read a missing key. defaultdict(int) starts counts at 0, defaultdict(list) starts buckets empty, defaultdict(set) builds adjacency sets.

The classic use is grouping by a signature: a key that is equal for things you consider the same. Anagrams are the same letters in a different order, so sorting the letters gives the signature: "tea", "eat" and "ate" all become "aet".

groups = defaultdict(list)
for w in words:
    groups["".join(sorted(w))].append(w)   # signature → bucket
return list(groups.values())               # dicts keep insertion order
Counting: Counter. Bucketing by a signature: defaultdict(list). Both are hash maps, so each update is O(1) on average.

d = defaultdict(list) is empty. You run if d["x"]: print("yes"). What is len(d) afterwards?

Right. Any d[key] read inserts key: list(). To ask "is it there?" without creating it, use "x" in d or d.get("x"). This bites in graph code, where checking a neighbor's list quietly adds nodes.

A defaultdict's whole job is "never raise KeyError on a read". It keeps that promise by creating the missing value and storing it, even when you only looked. So the read itself inserts "x": []. The if sees an empty list and prints nothing, but the key is now there. Use in or .get() to look without touching.

4Both ends: deque

Section 1's queue needed to take from the front and add at the back. collections.deque (say "deck", short for double-ended queue) makes all four end operations O(1): append, appendleft, pop, popleft. Think of a train where you can couple or uncouple cars at either end without touching the middle.

from collections import deque

q = deque([start])
while q:
    node = q.popleft()        # O(1): take from the front
    for nxt in neighbors(node):
        q.append(nxt)         # O(1): add at the back

recent = deque(maxlen=3)      # keeps only the newest 3
for x in [1, 2, 3, 4]:
    recent.append(x)          # deque([2, 3, 4])

What it gives up: q[i] in the middle is O(n), and you can't slice it. Use a deque when you work at the ends, a list when you jump by position. maxlen makes a "last k items" window that drops the oldest item for you.

Any time you write pop(0) or insert(0, x), you want a deque.

5Smallest first: heapq

Sometimes you don't need everything sorted. You only need to keep taking the smallest item while new items keep arriving: the next timer to fire, the closest unvisited city, the cheapest job. Sorting after every arrival costs O(n log n) each time. A heap keeps just enough order to hand you the smallest item, and costs O(log n) per push or pop. You'll see how it works inside in the heaps chapter; here is how to use it.

import heapq

h = []
heapq.heappush(h, (5, "write"))   # (priority, item): smallest priority first
heapq.heappush(h, (1, "read"))
heapq.heappop(h)                  # (1, 'read'), O(log n)
h[0]                              # peek at the smallest, O(1)
heapq.heapify(nums)               # turn a list into a heap in place, O(n)
heapq.nlargest(3, nums)           # top 3, O(n log 3)

Four habits make heapq safe:

  • It's a min-heap only. For "largest first", push -priority.
  • Push tuples: (priority, item). Tuples compare element by element, so the priority decides.
  • Add a tie-breaker when items can't be compared: (priority, counter, item). Two equal priorities would otherwise compare the items, and comparing two dicts raises TypeError.
  • The list is not sorted. Only h[0] is promised to be the smallest; h[1] is not the second smallest.

You push (2, {"id": 7}) and then (2, {"id": 9}) onto a heap. What happens?

Right. Fix it with a tie-breaker that is always different: (2, next(counter), {"id": 7}) with counter = itertools.count(). That also makes ties come out first-in, first-out.

Tuple comparison is like comparing words in a dictionary: look at the first letter; only if it's equal, look at the second. Here the first elements are both 2, so Python moves on to the second elements, the two dicts, and asks dict < dict. Dicts have no order, so that raises. Heaps don't remember arrival order, and Python doesn't look inside the dict for an "id". Put a unique counter second, and the comparison never reaches the dicts.

6Sorted data: sorted(key=…) and bisect

Sorting is often the first step that makes a problem easy: duplicates sit next to each other, intervals line up, and you can binary search. Two tools cover nearly every case.

Sort by what you mean with key. The key function turns each item into the thing to compare. A tuple key sorts by several things in order, and a minus sign flips a number.

people.sort(key=lambda p: p.age)              # by age
words.sort(key=lambda w: (-counts[w], w))     # most common first, ties A→Z
sorted(points, key=lambda p: p[0]**2 + p[1]**2)  # closest to origin first

Python's sort is stable: items with equal keys keep their original order. And list.sort() sorts in place and returns None, so a = a.sort() loses your list.

Search a sorted list with bisect. Think of a phone book: to find where "Khan" goes, open the middle, then keep halving. bisect_left(a, x) returns the first position where x could go without breaking the order; bisect_right(a, x) returns the position just after any copies of x. Both are O(log n).

from bisect import bisect_left, bisect_right
a = [10, 20, 20, 20, 30]
bisect_left(a, 20)    # 1: first 20
bisect_right(a, 20)   # 4: just past the last 20
bisect_right(a, 25) - bisect_left(a, 15)   # 3 values in [15, 25]

The last line is a pattern worth keeping: how many values fall in [lo, hi] is bisect_right(a, hi) - bisect_left(a, lo), two O(log n) searches instead of an O(n) scan.

You keep a list sorted by calling bisect.insort(a, x) for each of n arrivals. The search part is O(log n). What does the whole thing cost?

Right. Binary search finds the gap quickly, then list.insert slides everything after the gap. If you only need the smallest item, use a heap; if you need sorted order with fast inserts, that's a balanced tree (this week's trees chapter).

Split insort into its two moves. Finding where x goes: binary search, about 20 steps for a million items. Putting it there: the list is a packed row of slots, so to open a gap at position i, every item from i to the end moves right by one, like section 1's chairs. That's up to n moves per insert, and over n inserts about n²/2. The fast search doesn't save the slow shift.

7Loops without bookkeeping: enumerate, zip, itertools

Index bookkeeping (i += 1, a[i] and b[i] side by side) is where off-by-one bugs live. These tools remove it:

You wantWrite
the index and the itemfor i, x in enumerate(a)
two lists side by sidefor x, y in zip(a, b) (stops at the shorter)
each item and the next onefor x, y in itertools.pairwise(a) (Python 3.10+)
running totalsitertools.accumulate(a): 1, 2, 3 → 1, 3, 6
every pair, every order, every choicecombinations(a, 2), permutations(a), product(a, b)
runs of equal neighborsitertools.groupby(a): groups only adjacent equal items, so sort first
one long sequence from severalitertools.chain(a, b)

One warning: combinations and permutations don't make anything faster. combinations(a, 2) on 100,000 items is still 5 billion pairs. They make brute force shorter to write, which is useful when you say "the brute force is…" and want it on the screen in one line.

What does [(k, len(list(g))) for k, g in groupby("aabaa")] give?

Right. groupby starts a new group every time the value changes. That makes it perfect for run-length encoding ("aabaa" → a2 b1 a2), and wrong for counting, where you want Counter.

groupby walks the string once, left to right, and only looks at the item just before. It sees a, a (same run), then b (new run), then a, a (new run, because the last thing it saw was b). It never jumps back to merge with the first run of a's. If you want totals per letter, use Counter("aabaa"); if you want groupby to give totals, sort first so equal items are neighbors.

8Remember answers: functools.cache

Some recursive functions ask the same question many times. The textbook case is counting the ways to climb n stairs taking 1 or 2 steps: ways(n) = ways(n - 1) + ways(n - 2). Written plainly, ways(40) makes over 300 million calls, because ways(38) is computed again inside every branch that needs it. The fix is a notebook: the first time you solve ways(38), write the answer down, and look it up after that.

from functools import cache

@cache                    # a dict from arguments to the answer
def ways(n):
    if n <= 1:
        return 1
    return ways(n - 1) + ways(n - 2)

ways(40)                  # 41 distinct subproblems instead of ~330 million calls

Rules: the arguments must be hashable (pass a tuple, not a list), and Python stops deep recursion at about 1,000 nested calls by default, so ways(5000) raises RecursionError. For deep inputs, turn the recursion into a loop. You'll use this properly in the dynamic programming chapter in week 3.

9Code that reads well

The interviewer reads your code while you write it. Clear code is a scored signal ("code quality"), and it also stops you from confusing yourself at minute 30. A handful of habits do most of the work:

  • Names that say what, not how: seen, best_so_far, by_owner, never d2 or tmp.
  • Small helpers for any step you can name: def neighbors(r, c) beats four copies of a bounds check.
  • Return early for edge cases at the top: if not nums: return 0.
  • A dataclass for a record instead of a tuple whose fields you have to remember by position.
from dataclasses import dataclass

@dataclass(frozen=True)        # frozen: immutable and hashable
class Job:
    name: str
    priority: int
    minutes: float = 0.0

j = Job("render", 2)           # Job(name='render', priority=2, minutes=0.0)

Two more you'll use constantly: float("inf") (or math.inf) as a starting "best so far" for a minimum, and sys.setrecursionlimit only as a last resort, since a loop is safer.

grid = [[0] * 3] * 3, then grid[0][0] = 1. What is grid?

Right. * 3 on the outer list copies the reference to the one inner row three times. Build each row separately with a comprehension.

Think of the inner list [0, 0, 0] as one whiteboard, and the outer list as three sticky notes that each say "see that whiteboard". * 3 copies the sticky note, not the whiteboard. Writing on row 0 writes on the only whiteboard, and all three notes point at it, so every row shows the 1 in column 0. The inner [0] * 3 is fine because 0 is a number, not a box you can write in.

10What to say in the interview

When you reach for a tool, name it and its cost in the same breath. It shows you chose it, not that you remembered it:

"I'll count with a Counter, that's O(n). For the top k I'll use heapq.nlargest, O(n log k), which beats sorting when k is small. I'm using a deque here because I pop from the front; a list would make that O(n) per pop."

  • Say the hidden cost when you avoid it: "a set, not a list, so the membership check is O(1)".
  • If you use something the interviewer might not know (bisect_right, groupby), say in one sentence what it returns.
  • If asked to "do it without the library", you can: you'll build a hash map, a ring-buffer deque, a heap and the sorts by hand this week.

✓What to remember

  1. A list is a row of slots: end O(1), front and middle O(n), in O(n), slices copy.
  2. dict and set: O(1) average for lookup, insert and in. Strings never change, so build with join.
  3. Counter to count, defaultdict(list) to bucket by a signature; reading a missing defaultdict key creates it.
  4. deque for both ends (and maxlen windows); never pop(0) on a list.
  5. heapq: min-heap of tuples, negate for max, add a counter for ties, only h[0] is ordered.
  6. sorted(key=…) with tuple keys; stable; .sort() returns None. bisect for O(log n) search; insort is still O(n).
  7. enumerate, zip, pairwise, accumulate, groupby (adjacent only), combinations.
  8. @cache for repeated subproblems; recursion stops near depth 1,000.
  9. Watch for mutable defaults, [[0]*n]*m, floor division of negatives, and is vs ==.

Warm-up · pen and paper

1. Find the hidden cost

Give the Big-O of each, with n = len(a), and a one-line fix where it's worse than it needs to be. (a) for x in a: if a.count(x) > 1: return True (b) while a: total += a.pop(0) (c) def f(a): return a[0] + f(a[1:]) if a else 0 (d) best = [max(a[:i+1]) for i in range(len(a))]

Answer

(a) O(n²): count scans the list for each x. Fix: len(set(a)) < len(a), O(n). (b) O(n²): each pop(0) shifts the rest. Fix: total = sum(a), or a deque if you really need a queue. (c) O(n²) time and O(n²) memory in total, because each slice copies; it also hits the recursion limit near 1,000 items. Fix: sum(a), or pass an index instead of a slice. (d) O(n²): every a[:i+1] copies and every max rescans. Fix: list(itertools.accumulate(a, max)), O(n).

2. Predict the output

(a) Counter("banana").most_common(1) (b) bisect_left([1, 3, 3, 5], 3), bisect_right([1, 3, 3, 5], 3), bisect_left([1, 3, 3, 5], 4) (c) sorted(["bb", "a", "ccc", "dd"], key=len) (d) -9 // 4, -9 % 4

Answer

(a) [('a', 3)]. (b) 1, 3, 3: 4 would go just after the two 3s, at index 3. (c) ['a', 'bb', 'dd', 'ccc']: "bb" stays before "dd" because the sort is stable. (d) -3, 3: −9 / 4 = −2.25, floored to −3, and −3 × 4 + 3 = −9.
