1Classes in 60 seconds: bundling data and actions together

When a group of values and actions naturally belong together — like a bank account with an owner, a balance, and deposit() / withdraw() actions — bundle them into a class:

class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner         # stored on THIS specific account
        self.balance = balance
        self.history = []          # fresh list for each new account!

    def deposit(self, amount):
        self.balance += amount
        self.history.append(amount)

maya = Account("Maya", 50)         # runs __init__ automatically
maya.deposit(20)                   # passes maya in as self!
print(maya.owner, maya.balance)    # Maya 70

Two quick rules make Python classes feel effortless right away:

  • What self means: self is just the specific object being used right now (when you write maya.deposit(20), Python calls deposit(maya, 20) behind the scenes).
  • Never put an empty list or dict directly on the class body: remember Day 2's shared-box rule! If you write history = [] directly under class Account: instead of inside __init__, every account shares the exact same list! Always create per-object mutable fields inside __init__.
A class pairs attributes (stored on self inside __init__) with methods. Always create per-instance lists or dicts inside __init__ so different objects never share the same box.

What happens if you define class Cart: with items = [] directly on the class body (not inside __init__) and run a = Cart(), b = Cart(), a.items.append("apple")?

Spot on! Attributes written directly on the class body live in one shared box for the whole class. Move self.items = [] inside def __init__(self): so each cart gets its own fresh list.

Picture hanging one shared whiteboard on the wall for all shoppers instead of giving each shopper their own notepad: when shopper a writes "apple" on the shared whiteboard, shopper b sees ["apple"] too! Always put self.items = [] inside __init__.

Plain classes are great when objects hold changing state and methods. What when you just want a clean record holding a few named fields — like a support ticket or a book?

2Clean value records with @dataclass

If you write a plain class for a small data record, you have to write __init__, a readable __repr__ (for printing), __eq__ (so two tickets with the same fields compare equal with ==), and comparison methods (< for sorting) by hand. Python's built-in @dataclass reads simple name: type field hints (like priority: int or title: str) and writes all of those methods for you automatically:

from dataclasses import dataclass, field

@dataclass(frozen=True, order=True)
class Ticket:
    priority: int                  # compared 1st (smaller = more urgent)
    number: int                    # compared 2nd (breaks priority ties!)
    title: str                     # compared 3rd

t1 = Ticket(1, 102, "Fix login")
t2 = Ticket(1, 101, "Reset password")

print(t1)                          # Ticket(priority=1, number=102, title='Fix login')
print(t2 < t1)                     # True  (same priority 1, and 101 < 102!)
seen = {t1, t2}                    # Works in sets & dict keys because frozen=True!

# For an editable dataclass that needs a default list, use field(default_factory=list):
@dataclass
class ShoppingBag:
    items: list = field(default_factory=list)   # fresh list per bag!
Four lines of @dataclass(frozen=True, order=True) replace 25+ lines of hand-written boilerplate.

Look at what those options unlock:

  • frozen=True: locks every field after creation (trying t1.priority = 9 raises an error!). Just like a locked tuple from Day 1, locking fields lets Python safely store Ticket objects inside a set or use them as dict keys!
  • order=True: makes instances sortable with < and sorted(...), comparing fields strictly top to bottom in the order you listed them.
  • Mutable defaults on editable dataclasses: never write items: list = [] (Python refuses!). Use field(default_factory=list) as in ShoppingBag above so every new object gets its own fresh list!
Use @dataclass(frozen=True, order=True) whenever you want a clean, printable, sortable, locked value record that works inside sets and dicts — and use field(default_factory=list) for mutable defaults.

Given this frozen dataclass, what happens if someone writes t.priority = 5 on an existing Task?

@dataclass(frozen=True, order=True)
class Task:
    priority: int
    seq: int
    name: str

Spot on! frozen=True blocks editing fields after creation — which is exactly why Python trusts frozen dataclasses inside sets and as dictionary keys.

Remember Day 1's locked tuples: once sealed, you cannot overwrite a slot! Setting frozen=True seals every attribute on the dataclass so attempting t.priority = 5 fails loudly with a FrozenInstanceError (which is also an AttributeError).

You just used your first @ line (@dataclass). Have you wondered what the @ symbol in Python actually does? Let's demystify it — it turns out to be refreshingly simple.

3How @ decorators actually work (zero magic!)

In Python, a decorator is just a regular function that takes a function as input, wraps extra behavior around it, and returns the upgraded function. Putting @log_calls right above def greet(name): is literally shorthand for writing greet = log_calls(greet) right after it:

from functools import wraps

def log_calls(fn):
    @wraps(fn)                           # copies original __name__ and __doc__!
    def wrapper(*args, **kwargs):        # accepts ANY arguments cleanly
        print("Calling", fn.__name__)
        result = fn(*args, **kwargs)     # runs the original function
        return result
    return wrapper

@log_calls                               # same as: greet = log_calls(greet)
def greet(name):
    """Say hello to a user."""
    return "Hello, " + name

print(greet("Maya"))                     # prints "Calling greet", then "Hello, Maya"
print(greet.__name__)                    # "greet" (thanks to @wraps(fn)!)

Notice two small pieces inside wrapper:

  • *args, **kwargs: packs whatever positional or named arguments the caller passed, and forwards them straight into fn(*args, **kwargs) so one decorator works on any function!
  • @wraps(fn): without @wraps(fn), greet.__name__ becomes "wrapper" and its docstring vanishes (which confuses debuggers and tests!). Always put @wraps(fn) on your inner wrapper.

Step through definition time vs. call time below:

The decorator runs once when Python reads def to swap in the wrapper; then every time you call greet("Maya"), your wrapper runs around the original function.
Writing @dec above def f(): is just shorthand for f = dec(f). Always put @functools.wraps(fn) on the inner wrapper so the original name and docstring survive.

When does the outer decorator function log_calls(fn) itself run when you put @log_calls above def greet(name):?

Exact! Python runs greet = log_calls(greet) once at definition time. Later, each call to greet("Maya") runs the returned wrapper function.

Picture gift-wrapping a box once before putting it on a shelf: @log_calls wraps greet once the moment Python reads def greet. Afterward, whenever you call greet(...), you're calling that already-wrapped wrapper function!

If you forget to put @wraps(fn) above def wrapper(*args): inside a decorator applied to def calc_tax(x):, what does calc_tax.__name__ return?

Spot on! Because decorating rebinds calc_tax to wrapper, its __name__ becomes "wrapper" unless @functools.wraps(fn) copies the original name and docstring over.

Remember the sticky-note rule from Day 2: calc_tax = dec(calc_tax) moves the sticky note calc_tax onto the inner wrapper function! Asking that box for its .__name__ reports "wrapper" unless @wraps(fn) copies "calc_tax" onto it.

Now let's put decorators to work on one of the most practical patterns in Python: caching ("remembering") answers so slow work never runs twice for the same input.

4Caching results safely with decorators

Suppose a function does slow work — like computing a shipping quote or a big recursive calculation — and gets called repeatedly with the exact same inputs. A caching decorator stores each answer in a dictionary keyed by the input arguments so repeated calls return instantly!

In everyday code, Python's standard library already gives you ready-made caching decorators in functools:

from functools import cache, lru_cache

@cache                     # remembers every unique call (great for short scripts!)
def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

@lru_cache(maxsize=256)    # keeps only the 256 most recent results (safe for servers!)
def shipping_quote(weight_lb, zone):
    return 4 + weight_lb * zone   # pretend this calls a slow pricing formula

Understanding how to write a tiny 7-line caching decorator yourself ties together decorators, closures (where wrapper remembers the outer saved dictionary), and dictionaries. Watch the one subtle trap: checking whether an answer is already cached!

from functools import wraps

def remember(fn):
    saved = {}
    @wraps(fn)
    def wrapper(*args):            # args is a locked tuple — legal dict key!
        if args not in saved:      # SAFE! Works even if fn returns 0, False, "", or None!
            saved[args] = fn(*args)
        return saved[args]
    return wrapper

Why if args not in saved: beats if saved.get(args):: suppose fn(0) genuinely returns 0 (or None or False or ""). Because all four values are falsy, writing if saved.get(args): thinks the answer is missing and calls fn(0) all over again every single time! Checking if args not in saved: checks whether the key exists, caching every value cleanly.

Use @functools.cache (or bounded @lru_cache(maxsize=...)) for built-in caching. When writing your own cache wrapper, key by the args tuple and check if args not in cache: so falsy results like 0 and None stay cached!

Inside a custom caching decorator, someone writes if cache.get(args): return cache[args]. They decorate def count_matches(text): ... which returns 0 when nothing matches. What happens if you call count_matches("xyz") twice?

Caught it! cache.get(args) returns the cached 0, and Python evaluates if 0: as False — falling through and recomputing! Always test membership with if args not in cache:.

Check what happens if a function returns "" (empty string) or False: cache.get(args) hands back "", which is falsy, so if cache.get(args): skips the cache hit and runs the slow function again! Test if args not in cache: instead.

Our final Day 3 building block combines what you learned about decorators and yield (from Day 2) to guarantee that cleanup code always runs — even when an error happens halfway through.

5Guaranteed cleanup using with blocks and @contextmanager

You may have already seen Python's with block when opening a file:

with open("notes.txt", encoding="utf-8") as f:
    text = f.read()
# File f is automatically closed here — even if reading raised an error!

A context manager is any helper that works with a with block: it runs setup before the indented block starts, optionally hands a value to as ..., and guarantees cleanup runs when the indented block finishes (or crashes with an exception!).

The cleanest way to build your own context manager is @contextlib.contextmanager on a tiny generator function with one yield inside try ... finally:

from contextlib import contextmanager

@contextmanager
def temp_tag(tags, tag):
    tags.append(tag)          # 1. SETUP: runs when entering the with block
    try:
        yield tags            # 2. PAUSE: hands tags to "as current" and runs body!
    finally:
        tags.pop()            # 3. CLEANUP: ALWAYS runs, even after an error!

labels = ["public"]
with temp_tag(labels, "draft") as current:
    print(current)            # ["public", "draft"]
print(labels)                 # ["public"] — cleaned up automatically!

Why try ... finally around yield is non-negotiable: if the caller's code inside the with block raises an exception, Python throws that error right back into the yield line! Without finally:, Python skips your cleanup line (tags.pop() never runs!) and leaves labels stuck with "draft" forever. With finally:, cleanup runs first and the original error still propagates cleanly.

Step through both a normal run and an error inside the with block below:

Switch between a normal run and an error raised inside the with block — finally: removes "draft" in both cases before letting the error continue.
Use @contextlib.contextmanager with setup before try:, one yield inside try:, and cleanup inside finally: so resources always clean up even when exceptions occur.

Someone writes a @contextmanager helper without try ... finally: just items.append(val), then yield items, then items.pop(). What happens if code inside the with block raises a ValueError?

Spot on! When the with block raises an error, Python throws it right at the yield line. Without a try: / finally: block around yield (with items.pop() in finally:), execution jumps straight out and skips cleanup completely!

Imagine opening a locker, pausing at yield, and then a fire alarm (exception) goes off inside the with block: unless your "lock the door" step sits inside finally:, Python runs straight out the exit at yield and leaves the door open (val still stuck in items)!
