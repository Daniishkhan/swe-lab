1Why does code structure matter as much as Big-O in senior rounds?

Picture a 90-minute Anthropic 4-level build. At Level 1 you pass raw tuples (2, 1, "send_email") around, mix a manual cache = {} into your recursion, and pair path.append() with path.pop() by hand. By Level 3, an early return skips one pop(), a helper reads task[1] instead of task[2], and a cached 0 triggers exponential slowdowns. You lose 25 minutes untangling plumbing instead of shipping Level 4.

Think of Python's @ decorators as snap-on wrappers around clean core logic. Instead of burying your algorithm inside 40 lines of double-underscore special methods ("dunders" like __eq__ and __lt__), manual cache lookups, and fragile cleanup branches, you keep your core code tiny and snap three built-in wrappers onto the edges:

All three tools use the exact same @ mechanism — applied once to a class, once to a function, and once to a pausing generator.

Before snapping any of those three on, let's peel away the mystery of the @ symbol itself. Once you see it on Chapter 10.10's workshop bench, it takes ten seconds to understand completely.

2How does Python's @ syntax actually work under the hood?

Remember Chapter 10.10: in Python, a function or class is an ordinary object sitting on the workshop bench — you can pass it into another function and return a new function back out! Writing @dec directly above def foo(...): does zero compiler magic. It is literally 1-line shorthand for:

@dec                        # Python runs these two lines under the hood:
def foo(x):                 #   def foo(x): return x + 1
    return x + 1            #   foo = dec(foo)   <-- runs ONCE at def time!
@dec runs dec(foo) once when Python defines foo, then moves sticky note foo onto the returned wrapper.

Look at a tiny 6-line wrapper that counts how many times a function is called — and notice @functools.wraps(fn), which copies fn.__name__ and fn.__doc__ onto wrapper so stack traces, help text, and test suites still see the original name:

from functools import wraps

def count_calls(fn):
    calls = 0                       # private closure cell on the bench (Chapter 10.10!)
    @wraps(fn)                      # preserves fn.__name__ and fn.__doc__
    def wrapper(*args):
        nonlocal calls              # rebind outer `calls` sticky note (int is immutable!)
        calls += 1
        return fn(*args)
    return wrapper

Two quick details unlock every decorator you'll see below: nonlocal calls is required because calls points to an immutable int stone in the outer scope — without it, calls += 1 would look for a local variable inside wrapper. And when a decorator accepts options in parentheses (like @wraps(fn) or @dataclass(frozen=True)), Python runs a two-step call: factory(opts) returns a decorator, which immediately wraps the target (target = factory(opts)(target)).

Where the snap-on wrapper picture needs care: the outer decorator count_calls(fn) executes once when Python loads the def statement, setting up its closure state (like calls = 0 or a cache dict). From then on, only the inner wrapper runs each time you call the function.

A decorator is an ordinary function that takes a class or function at definition time and returns an upgraded version (@factory(opts) just calls factory(opts) first to obtain that decorator). Always put @functools.wraps(fn) on the inner wrapper so __name__ and __doc__ survive.

You decorate the function below with a custom wrapper, yet forget @wraps(fn) inside the decorator. What happens when a test checks compute.__name__ and compute.__doc__?

@count_calls
def compute(x):
    """Double x."""
    return x * 2

Spot on! Rebinding compute = count_calls(compute) moves sticky note compute onto the inner wrapper object — so unless you decorate wrapper with @wraps(fn), Python inspects wrapper's own name and missing docstring.

Try tracing a second example: suppose you write def square(n): with docstring """Square n.""" and wrap it with an undecorated inner def wrapper(*args):. After square = dec(square), sticky note square is stuck onto wrapper — so square.__name__ reads "wrapper" and square.__doc__ reads None until you add @wraps(fn).

Now that @ is completely transparent — just target = dec(target) — let's snap it onto our three targets in order: first a class (§3), next a function (§4), and finally a pausing generator (§5).

3How do you wrap a class into a safe, sortable value record?

Raw tuples like (2, 1, "send_email") work fine inside a 3-line sort (Chapter 10.11), yet once you pass tasks across functions, store them in sets/dicts, or push them into Python's priority queue (heapq, covered on Day 4), raw tuples get cryptic fast — and plain custom classes crash on comparisons (<) and sets (hash()) unless you hand-write 30 lines of dunder methods.

Snap @dataclass(frozen=True, order=True) onto a 4-line class definition instead (this is PriorityTask in py_internals.py):

from dataclasses import dataclass

@dataclass(frozen=True, order=True)
class PriorityTask:
    priority: int       # compared 1st (lower number = higher urgency)
    seq: int            # compared 2nd (breaks priority ties cleanly!)
    name: str           # compared 3rd (breaks any remaining ties)
Field declaration order IS your comparison order — put the primary sort key first and tie-breakers right underneath.

Connect frozen=True straight back to Chapter 10.10's sealed stones: being hashable means an object has a stable numeric fingerprint (hash(obj)) that never changes over its lifetime so Python's dict and set always find the same bucket. Because frozen=True blocks attribute rebinding (t.priority = 99 raises FrozenInstanceError, a subclass of AttributeError), Python safely generates __hash__ (as long as every compared field is itself hashable!), letting PriorityTask live inside sets, dictionary keys, and priority queues cleanly.

Go deeper: field(compare=False), shallow immutability, and slots=True

Non-comparable payload fields: if a task carries an unorderable payload like a dict alongside priority and seq, mark it payload: dict = field(compare=False) so ordering, equality, and hashing ignore it — preventing TypeError: unhashable type: 'dict'.

Shallow immutability: remember Chapter 10.10 §2's tuple footnote! frozen=True blocks rebinding t.payload = {}, yet it does not freeze mutations inside an open mutable box like t.payload["k"] = 1. Adding slots=True (Python 3.10+) also cuts per-instance memory and speeds attribute lookup.

@dataclass(frozen=True, order=True) turns a 4-line field list into an immutable, hashable (when compared fields are hashable), priority-queue-sortable value object — with zero hand-written boilerplate.

You define PriorityTask with @dataclass(order=True) — forgetting frozen=True — and try to put tasks into a Python set. What happens?

Exact! Adding __eq__ on a mutable class makes Python set __hash__ = None to protect hash tables from keys that mutate after insertion. Adding frozen=True seals attribute rebinding and unlocks __hash__.

Check what happens if a mutable object were allowed in a set: changing t.priority later would change its hash and strand it in the wrong bucket! So Python automatically disables __hash__ whenever a dataclass is mutable — raising TypeError: unhashable type: 'PriorityTask' until you pass frozen=True.

That's wrapping a class. Now apply the exact same @ wrapper mechanism to a recursive function — snapping on caching without touching a single line of the algorithm inside.

4How do you wrap a function with a cache safely?

Recursive problems (Fibonacci, grid paths, dynamic programming) often recompute the exact same subproblem millions of times. Instead of cluttering your recursion with manual lookups, snap a caching wrapper — called memoization (@memoize, remembering past return values by input arguments) — onto it (this is memoize in py_internals.py):

from functools import wraps

def memoize(fn):
    cache = {}                              # isolated dict box per decorated function!
    @wraps(fn)                              # keep fn.__name__ and fn.__doc__
    def wrapper(*args):
        if args not in cache:               # NOT `if cache.get(args):`!
            cache[args] = fn(*args)
        return cache[args]
    return wrapper

Look how three ideas from earlier chapters lock together here:

  1. Isolated closure box (Chapter 10.10 §6): each call to memoize(fn) creates its own fresh cache = {} box on the bench — so decorating add and mul never collides their caches!
  2. Positional tuple key args: *args packs 0 arguments into (), 1 argument into (n,), and 2 arguments into (a, b) — all immutable tuples (as long as the argument values themselves are hashable!).
  3. Membership check vs. truthiness (Chapter 10.10 §7): writing if cache.get(args): looks clever — and breaks catastrophically whenever fn legally returns a falsy value (0, False, "", or None)! Step through both versions below:
Switch the dropdown between safe args not in cache and buggy cache.get(args) when ways(2) legally returns 0 (zero paths from a dead-end state).

In real interviews and production: Python's standard library ships this exact decorator as @functools.cache (unbounded — ideal for interview DP) and @functools.lru_cache(maxsize=1024) (bounded — mandatory in long-lived production services so an unbounded cache never grows until out-of-memory!). Writing memoize once by hand makes sure you never trip over @wraps or falsy values when asked to build a custom cache, rate-limiter, or retry wrapper.

Go deeper: keyword arguments (**kwargs) and thread safety in custom caches

Supporting keyword arguments: our compact wrapper(*args) only caches positional arguments. If callers pass keyword arguments like fn(a=1, b=2), combine them into a deterministic hashable key — key = (args, tuple(sorted(kwargs.items()))) — or reach directly for @functools.lru_cache, which handles both positional and keyword arguments.

Thread safety: in multi-threaded servers, two threads missing the cache simultaneously will both run fn(*args) and race on writes. functools.lru_cache uses an internal lock to keep its LRU structure consistent; in custom multi-threaded caches, guard cache state with a threading.Lock (or a single-flight pattern in Week 4's concurrency chapter).

Inside any caching decorator, allocate cache = {} inside the outer decorator (one isolated cache per function), preserve metadata with @wraps(fn), and check key membership (if args not in cache:) — never truthiness (if cache.get(args):).

A recursive helper returns 0 for dead-end states. Your custom @memoize writes if cache.get(args): return cache[args]. What happens on big inputs?

Exact! Testing if args not in cache: checks whether the key exists in the dict — caching 0, False, "", and None cleanly.

Trace cache = {(2,): 0}: calling cache.get((2,)) returns 0, and Python evaluates if 0: as False! So the wrapper treats the cached dead-end as a cache miss, calls fn(2) all over again, and destroys your memoization speedup.

We've snapped @ onto a class (@dataclass) and onto a regular function (@memoize). One target remains — and it plugs straight into Chapter 10.11's pausing yield generators!

5How do you wrap a pausing generator for exception-safe cleanup?

In backtracking, graph DFS, locks, and file I/O, you constantly pair a setup step with a mandatory teardown step: path.append(node) before exploring, and path.pop() afterward. Write those two lines manually around a multi-branch body and one early return or unexpected exception skips path.pop() — corrupting state for every branch that follows.

Remember Chapter 10.11 §6: a generator function pauses at yield and resumes right there later! Snap @contextlib.contextmanager onto a single-yield generator and Python turns it into a bulletproof with guard (this is scoped_append in py_internals.py):

from contextlib import contextmanager

@contextmanager
def scoped_append(items, value):
    items.append(value)         # 1. runs on entering `with`
    try:
        yield items             # 2. pauses here while caller's `with` body runs!
    finally:
        items.pop()             # 3. ALWAYS runs on exit — even if body raises!

Why try ... finally around yield is non-negotiable: if the caller's indented with block raises an exception like RuntimeError, Python injects that exception straight back into the paused yield line! Without finally:, the generator aborts right at yield, skipping items.pop() completely. Notice also why items.append(value) sits above try:: if setup itself fails (say, opening a missing file or failing to acquire a lock), entering finally: must not pop or release something that was never acquired! Step through both versions below:

Switch between safe try ... finally and bare yield when the with body raises RuntimeError. Notice how finally: pops "boom" cleanly AND still lets RuntimeError propagate to the caller!
Go deeper: class-based context managers (__enter__ and __exit__)

@contextmanager is concise for one-off helpers. Reach for a class defining __enter__(self) and __exit__(self, exc_type, exc, tb) when you need a reusable stateful guard (like a transaction manager or timer object). Returning False or None from __exit__ lets any exception propagate (the safe default); returning True intentionally suppresses it.

Inside @contextmanager, setup runs above try:, the with body runs at yield, and cleanup MUST live inside finally: so exceptions never skip teardown or leak corrupted state.

Inside @contextmanager scoped_append(path, node), you forget try ... finally and put path.pop() right after yield path. What happens if the caller's with block raises RuntimeError?

Spot on! Python throws any exception from the with body straight into the yield line — only a finally: block guarantees path.pop() executes before the exception propagates out.

Trace path = ["a"] entering with scoped_append(path, "b"): → path becomes ["a", "b"]. When the body raises RuntimeError, execution aborts directly at yield: path.pop() never runs, the RuntimeError still propagates out (never swallowed!), and path stays stuck at ["a", "b"].

Those three @ wrappers replace dozens of error-prone lines — yet four subtle traps still catch engineers who use them on autopilot.

6How can these building blocks break — and when are they overkill?

Watch out for these three runtime traps — plus one design rule:

Every failure traces back to earlier rules: Chapter 10.10's immutability rules (1 & 2) or Chapter 10.11's single-use generator rule (3) — entering the same cm twice fails (AttributeError in Python 3.12+, or RuntimeError in Python 3.11 and earlier) because the single-use generator is already spent.

When decorators and dataclasses are the wrong tool: if a script parses one tiny pair inside a 5-line function, a plain tuple (dist, node) is cleaner than defining a class; and don't invent custom decorator factories for logic used only once. Use each building block when it removes real repetition or enforces an invariant (immutability, caching, guaranteed teardown).

You define the frozen dataclass below and try to add a Job instance to a Python set. What happens?

@dataclass(frozen=True)
class Job:
    id: int
    meta: dict

Sharp catch! Hashing a frozen dataclass hashes a tuple of its compared fields — so an open dict field still breaks hash()! Use immutable fields (like tuple) or exclude non-identity payloads with field(compare=False).

Recall Chapter 10.10 §2's sealed-tray rule: frozen=True prevents rebinding job.meta = ..., yet it never converts or freezes the dict inside! When hash(job) runs, Python hashes (job.id, job.meta) and immediately crashes with TypeError: unhashable type: 'dict'.

7How you use all three together in an interview

Compare both versions of the exact same priority-ordered search step (priority queue + memoized node cost + backtracking path guard) — notice how every fragile piece of manual plumbing on the left maps to one clean @ invariant on the right:

Before: raw tuples + manual cache & pop

# Cryptic index item[2], falsy cache bug, leaky pop!
memo = {}
heapq.heappush(pq, (cost, seq, node))
item = heapq.heappop(pq)
u = item[2]                  # what is slot 2?!

def best_cost(n):
    if memo.get(n):          # 0 = cache miss!
        return memo[n]
    memo[n] = eval_node(n)
    return memo[n]

path.append(u)
if u == goal:
    path.pop()               # easy to forget!
    return best_cost(u)
explore(u, path)             # error leaks u!
path.pop()

After: clean @ wrappers guarding invariants

@dataclass(frozen=True, order=True)
class Step:
    cost: int
    seq: int
    node: str

heapq.heappush(pq, Step(cost, seq, node))
u = heapq.heappop(pq).node   # self-documenting!

@memoize                     # or @functools.cache
def best_cost(n):
    return eval_node(n)      # caches 0 safely!

with scoped_append(path, u):
    if u == goal:
        return best_cost(u)  # pops on return!
    explore(u, path)         # pops on error!

8What to say in the interview

Before coding py_internals.py and moving to Day 4's standard library toolkit (Chapter 10.01), make sure you can speak these four points aloud in under 45 seconds:

  1. How @ works: "A decorator runs once at definition time (fn = dec(fn)), wrapping the target; I always include @functools.wraps(fn) so metadata like __name__ and docstrings survive."
  2. Value objects: "I'll use @dataclass(frozen=True, order=True) so records have named fields, hash safely for dicts/sets when compared fields are immutable, and break priority-queue ties left to right."
  3. Memoization: "In interviews I reach for @functools.cache on hashable args — and in a custom @memoize I always test args not in cache rather than truthiness so cached 0, False, or None stay hits."
  4. Guaranteed cleanup: "Wrapping a yield inside try ... finally with @contextmanager guarantees pop() or lock release runs even on early returns or exceptions."
