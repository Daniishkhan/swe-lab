1Why warm up Python before algorithms?

Picture a 45-minute Google bare-editor round. You spot the optimal dynamic programming solution in 8 minutes, type dp = [[0] * cols] * rows, and spend the next 15 minutes mystified during your dry run because updating row 0 silently overwrote row 3.

Senior interviewers rarely reject candidates for forgetting an obscure API — they reject candidates whose code is noisy, trips over Python's object model, or spends 20 bug-prone lines doing what Python expresses cleanly in 3.

Clean Python leaves more screen room and more mental bandwidth for edge cases and follow-ups.

Everything in this chapter rests on one physical picture: think of Python variables as sticky notes stuck onto containers sitting on a workshop bench. Assigning b = a does not photocopy the container — it sticks a second sticky note onto the exact same box. That single rule explains aliasing, shallow vs. deep copies, 2D grid bugs, mutable defaults, and late-binding loop closures all at once.

Where the sticky-note picture breaks: immutable values like integers (0, 42), strings ("hi"), and tuples can safely share sticky notes because you cannot reach inside an integer and edit it — reassigning x = x + 1 moves the sticky note onto a brand-new number.

2When should you build a list versus stream one item at a time?

Python lets you transform or filter any collection in one readable expression instead of allocating an empty container and calling .append() inside a manual loop:

# List, dict, and set comprehensions
squares = [x * x for x in nums if x % 2 == 0]
by_id   = {u.id: u.name for u in users if u.active}
domains = {email.split("@")[1] for email in emails}

# Unpack & transpose a matrix into filtered columns (py_idioms: transpose_and_filter)
cols = [[v for v in col if v >= thresh] for col in zip(*matrix)]

# Generator expression: parens () instead of [] — O(1) RAM & short-circuits!
total_bytes = sum(len(line) for line in log_stream)
has_neg     = any(x < 0 for x in nums)
first_hit   = next((x for x in nums if x > 100), None)

List comprehension [...] vs. generator expression (...): whenever values flow straight into sum(), any(), all(), min(), max(), or next(), use (...) — never [...]. Square brackets allocate all 10 million entries in RAM upfront (O(n) space, scaling with input size n) before any() even looks at item #0; parentheses pull one item at a time in constant memory (O(1) space) and stop the instant a match appears.

List comprehension:     [f(x) for x in 10M_items]  → allocates all 10M upfront (O(n) RAM)
Generator expression:   (f(x) for x in 10M_items)  → yields 1 item at a time  (O(1) RAM)
                                                     any() / next() stops on first hit!
Readability rule: if a comprehension needs more than two for clauses or nested if/else branches, write a normal for loop. Clever one-liners hurt clarity in bare-editor reviews.

Everyday iteration helpers and one-pass sliding windows

Pair enumerate(xs) (index + item) and zip(a, b) (walk two sequences in lockstep) with four itertools helpers that eliminate manual index arithmetic:

  • accumulate(nums, initial=0): builds running cumulative totals (prefix sums) in one pass: [1, 2, 3, 4] → [0, 1, 3, 6, 10].
  • islice(stream, n): grabs the first n items from any lazy or infinite iterator without converting it to a list.
  • chain.from_iterable(groups): flattens one level of lists lazily in O(1) (constant) extra memory.
  • groupby(items, key=...): groups consecutive runs sharing the same key (sort first if equal keys aren't adjacent!).

Look how cleanly accumulate + islice + zip turns a slow O(n·k) sliding-window sum (sum(nums[i:i+k]) — ~2.5 billion additions for n = 100k, k = 50k!) into a crisp single-pass O(n) linear-time two-liner (py_idioms.py's window_sums):

from itertools import accumulate, islice

def window_sums(nums, k):
    if k <= 0: raise ValueError("k must be positive")
    if k > len(nums): return []
    pref = list(accumulate(nums, initial=0))            # pref[i+k] - pref[i] = sum(nums[i:i+k])
    return [hi - lo for lo, hi in zip(pref, islice(pref, k, None))]  # one pass, no extra slice!

You have a 50-million-line log file opened as an iterator lines and want to know whether any line contains "FATAL". Which expression runs in constant O(1) memory and stops on the first hit?

Spot on! The generator expression streams one line at a time in constant O(1) memory and stops reading the file the instant it sees "FATAL".

Check the square brackets [...]: Python always finishes evaluating the inner list comprehension completely — reading all 50 million lines into RAM — before passing that giant list to any() or bool(). Removing the brackets streams lazily and short-circuits on line #1 if it matches.

3How do lambdas, multi-key sorting, and closures actually work?

A lambda is a concise one-expression function whose #1 interview job is feeding a custom sort key to sorted(), min(), or max(). Because Python compares tuples left-to-right (slot 0 first, slot 1 on ties, slot 2 next), multi-key sorting is one line — negate numeric fields to flip ascending into descending:

# py_idioms: rank_candidates — drop None scores, sort score DESC, penalty ASC, name ASC
valid = [r for r in records if r[1] is not None]        # NOT `if r[1]:` — score 0 is valid!
ordered = sorted(valid, key=lambda r: (-r[1], r[2], r[0]))
names = [r[0] for r in ordered]

Notice that guard if r[1] is not None: writing if r[1]: silently drops every candidate whose score is 0! Always test is not None whenever 0 or "" is a legal value.

The classic trap: late-binding closures inside a loop

Suppose you build three multiplier functions in a comprehension: fns = [lambda x: x * f for f in [2, 3, 10]]. You expect [g(5) for g in fns] to return [10, 15, 50]. Instead, all three return 50!

Why? Apply our sticky-note picture: a Python closure does not copy the number 2, 3, or 10 when the lambda is created — it sticks a reference onto the shared loop variable cell f. By the time you call any function, the loop has finished and f holds 10.

Step through loop creation vs. function calls. Without a snapshot, all three lambdas point to one mutable cell f; binding f=f (or a helper factory) captures each value immediately.

The two standard fixes (know both — interviewers often ask for the clean non-default-arg version too!):

# Fix 1: default-argument snapshot (evaluates NOW at lambda creation)
fns = [lambda x, f=f: x * f for f in factors]

# Fix 2: helper factory function (each call creates its own private scope cell!)
def _make_mul(f):
    return lambda x: x * f
fns = [_make_mul(f) for f in factors]          # or functools.partial(operator.mul, f)

What does [g() for g in [lambda: i for i in [10, 20, 30]]] return?

Exactly! None of the lambdas execute until the inner comprehension finishes with i = 30, so all three look up that same shared cell.

Separate defining a function from calling it: the inner list builds 3 uncalled functions pointing to one variable slot i. The loop ends with i == 30 (kept alive in the closure cell, so no NameError!). Only then does the outer loop call g(), reading 30 three times.

4How do lazy streams pause and resume without blowing memory?

Google loves lazy iterator questions ("Flatten a nested list iterator", "Zigzag iterator", "Merge k sorted streams"). A normal function computes everything and returns once; a function containing yield acts like a bookmark inside a paused book — every next() call runs only until the next yield, pauses its local variables right there, and hands back one value.

yield from sub_gen delegates directly to a nested generator without writing a manual for x in sub_gen: yield x loop. Look at recursive flattening (py_idioms.py's flatten_stream):

from collections.abc import Iterable

def flatten_stream(nested):
    for item in nested:
        if isinstance(item, Iterable) and not isinstance(item, (str, bytes)):
            yield from flatten_stream(item)     # delegate lazily to nested container
        else:
            yield item                          # pause here until caller pulls next!
Step through pulling values one by one from flatten_stream([1, (2, "hi"), 3]). Notice how "hi" is treated as an atomic leaf and 3 isn't even touched until requested.

Why the not isinstance(item, (str, bytes)) guard is mandatory: in Python there is no separate char type — iterating "hi" yields "h" (another str, which is still an Iterable!), and iterating "h" yields "h" forever until RecursionError. Always exclude (str, bytes) before recursing on an Iterable.

A generator function returns a lazy iterator object immediately without running its body until the first next(). That lets islice(gen, 6) pull six items from an infinite flatten_stream in O(d) memory for nesting depth d — completely independent of stream length.
Go deeper: flattening inputs nested deeper than Python's recursion limit

Recursive yield from keeps one active generator frame per nesting level (O(d) stack space), so an adversarial input nested more than ~1,000 levels deep hits RecursionError. If an interviewer asks how to handle arbitrary depth, swap recursion for an explicit stack of iterators: push iter(nested), call next(stack[-1], sentinel), pop exhausted iterators, and push iter(item) whenever you see a nested non-(str, bytes) iterable — still lazy and still O(d) heap memory, with no recursion limit.

You call gen = flatten_stream(infinite_nested()) and then list(islice(gen, 5)). What breaks if you write return [...] inside flatten_stream instead of yield?

Spot on! Building a list eagerly forces Python to walk every element of infinite_nested() before returning — so islice never even gets a chance to stop at 5.

Compare eager vs. lazy execution: islice works fine on finite lists, yet flatten_stream(infinite_nested()) runs completely before islice is called. With return [...], that call loops forever building an infinite list; with yield, it pauses after item #5 and stops.

5Why do Python variables share surprises — copies, grids, and defaults?

Return to our sticky-note picture: assigning b = a puts two labels on one mutable container. Four infamous bugs come straight from forgetting that rule:

[0] * 3 is safe because ints are immutable; multiplying an outer list of lists repeats the reference to one inner list.
  1. Aliased 2D grids (py_internals: make_grid): always allocate rows with a comprehension — [[fill] * cols for _ in range(rows)] — never [[fill] * cols] * rows. (And if fill itself could be mutable, construct a fresh copy per cell.)
  2. Shallow vs. deep copy: b = a[:], list(a), and copy.copy(a) build a new outer list whose slots still point to the exact same inner lists! Editing b[0].append(9) still mutates a[0]. For nested mutable structures, use [row[:] for row in grid] (fast 2D copy) or copy.deepcopy(obj) (general nested copy).
  3. Mutable default arguments (py_internals: append_log): Python evaluates default arguments once when def runs and stores them on the function object (fn.__defaults__). Never write def append_log(entry, bucket=[]): — every call omitting bucket shares that single list! Write bucket=None and allocate if bucket is None: bucket = [] inside the function body.
  4. Hidden O(k) slicing: every slice nums[i:j] allocates a brand-new list and copies j - i references. Slicing nums[1:] inside recursion or sum(nums[i:i+k]) inside a loop silently turns O(n) into O(n²) (for window sums, O(n·k) — hitting O(n²) when k ≈ n/2). Pass integer indices (lo, hi) or use Section 2's cumulative totals instead.

You snapshot a 2D board with snap = grid[:] before backtracking, then run grid[0][1] = "X". What is snap[0][1]?

Sharp catch! grid[:] is a shallow copy — it makes a new outer box whose sticky notes still point to the exact same inner row lists. Use [row[:] for row in grid] or copy.deepcopy(grid) for an independent snapshot.

Check two levels on grid = [[0, 0], [0, 0]]: snap = grid[:] creates a new outer list snap is not grid, yet snap[0] is grid[0] is True! Mutating grid[0][1] edits that shared inner list, so snap[0][1] changes to "X" too.

6How do dataclasses, decorators, and context managers cut boilerplate?

In Anthropic's 4-level practical builds and concurrency rounds, clean Python structure earns strong senior signal. Three built-in tools replace 40 lines of hand-written boilerplate with 5 rock-solid lines (all tested directly in py_internals.py) — including making value objects ready for Python's priority queue (heapq, covered in full on Day 3):

Three high-leverage Python building blocks: value objects that sort and hash safely, caching that respects falsy values, and setup/teardown that survives exceptions.
from dataclasses import dataclass
from functools import wraps
from contextlib import contextmanager

# 1. Immutable, hashable (dict/set keys!) AND priority-queue sortable in 4 lines:
@dataclass(frozen=True, order=True)
class PriorityTask:
    priority: int
    seq: int
    name: str

# 2. Custom @memoize decorator (preserves metadata + caches falsy values safely!):
def memoize(fn):
    cache = {}
    @wraps(fn)                              # preserves fn.__name__ and fn.__doc__!
    def wrapper(*args):
        if args not in cache:               # NOT `if cache.get(args):` (0/False/""/None!)
            cache[args] = fn(*args)
        return cache[args]
    return wrapper                          # in interviews, stdlib `@functools.cache` does this!

# 3. Exception-safe context manager for backtracking / locks (scoped_append):
@contextmanager
def scoped_append(items, value):
    items.append(value)
    try:
        yield items                         # caller's `with` body runs here
    finally:
        items.pop()                         # ALWAYS runs, even if body raises!
Three rules to burn into muscle memory: (1) @dataclass(frozen=True, order=True) makes an object immutable, hashable (when its compared fields are hashable), and priority-queue ready in one line; (2) check if args in cache: (never cache.get(args)) so falsy values stay cached; (3) wrap yield in try ... finally inside @contextmanager so exceptions never leak state or locks.
Go deeper: field(compare=False), slots=True, and class-based context managers

Non-comparable payload fields & shallow immutability: if a dataclass holds an unorderable payload like a dict alongside priority and seq, mark it payload: dict = field(compare=False) so ordering, equality, and hashing ignore it. Remember that frozen=True only blocks rebinding t.payload = ... — it does not freeze mutations inside a mutable dict or list field. Adding slots=True (Python 3.10+) also cuts per-instance memory and speeds attribute lookup.

When to write a class-based context manager (__enter__ / __exit__): @contextmanager is concise for one-off helpers; reach for a class with __enter__ and __exit__(self, exc_type, exc, tb) when you need reusable stateful managers (e.g., returning True from __exit__ intentionally suppresses an exception — returning None/False lets it propagate).

Inside @contextmanager scoped_append(path, node), you forget try ... finally and put path.pop() right after yield path. What happens if the caller's with block raises RuntimeError?

Spot on! Python injects any exception from the with body straight into the yield line — only a finally: block guarantees cleanup runs before the exception propagates.

Trace path = ["a"] entering with scoped_append(path, "b"): → path becomes ["a", "b"]. When the body raises RuntimeError, execution aborts directly at yield: path.pop() never runs, the RuntimeError still propagates out (never swallowed!), and path stays stuck at ["a", "b"].

A recursive helper returns 0 for dead-end states. Your custom @memoize writes if cache.get(args): return cache[args]. What happens on big inputs?

Exact! Testing if args in cache: (or using stdlib @functools.cache) checks key presence, not truthiness — caching 0, False, "", and None cleanly.

Evaluate bool(cache.get(args)) when cache[args] == 0: cache.get(args) returns 0, and in Python if 0: is False! So the decorator thinks args wasn't cached, calls fn(*args) again, and destroys memoization.

7How can idiomatic Python break — and how do you use it in interviews?

Even fluent Python writers hit four subtle traps under interview time pressure:

  1. Truthiness bugs on valid falsy values: writing if score:, if lo:, or if cache.get(k): breaks whenever 0, False, or "" is a real value. Write is not None or in cache.
  2. Mutating a container while iterating over it: removing keys from a dict or set inside for k in d: raises RuntimeError; removing from a list silently skips elements. Iterate over a snapshot (list(d)) or rebuild with a comprehension.
  3. Priority-queue tuple tie-break crashes: pushing (priority, obj) onto Python's heapq priority queue (Chapter 10.01) crashes with TypeError when two priorities tie and obj has no <. Fix with (priority, seq, obj) or Section 6's @dataclass(frozen=True, order=True)!
  4. When a plain loop beats a clever comprehension: if an expression needs side effects, multiple state updates, or more than one nested for + complex if, write a clean for loop. Interviewers score readability over code golf.

Compare how these Day 1–2 idioms clean up noisy interview boilerplate in real bare-editor code:

Before: fragile defaults + slow window slice

def add_event(ev, log=[]):
    log.append(ev)
    return log

# O(n·k) repeated list slicing
avgs = [
    sum(xs[i:i+k]) / k
    for i in range(len(xs) - k + 1)
]

After: safe default + one-pass prefix sums

def add_event(ev, log=None):
    if log is None: log = []
    log.append(ev)
    return log

# O(n) single pass via accumulate + islice
p = list(accumulate(xs, initial=0))
avgs = [
    (b - a) / k
    for a, b in zip(p, islice(p, k, None))
]

You want to delete every zero-count key from a dictionary counts. Why does calling del counts[k] directly inside a for k in counts: loop fail?

Exact! Loop over list(counts) or build a clean replacement counts = {k: v for k, v in counts.items() if v != 0}.

Trace counts = {"a": 0, "b": 1}: on iteration 1, del counts["a"] shrinks the dict from size 2 to 1. On the next step, Python's dict iterator sees the size changed and raises RuntimeError immediately (unlike a list, which silently skips the next element!). Snapshot keys with list(counts) first.

8What to say (and check) before Week 1 starts

Before moving to Day 3's standard library toolkit (Chapter 10.01), make sure you can explain these four ideas aloud in 60 seconds without peeking:

  1. Memory & streams: "Generator expressions (...) run in O(1) extra memory and recursive yield / yield from uses O(d) stack for nesting depth d (not O(n)), short-circuiting on any/next/islice — while excluding (str, bytes) prevents infinite recursion when flattening."
  2. Closures & sorting: "Tuple keys handle multi-rule sorting in one line (negate numbers to reverse). Loop closures capture one shared variable cell, fixed by default-arg binding (lambda x, f=f:) or a helper factory."
  3. Object model: "Python variables are references to objects, so [[0]*m]*n aliases rows, grid[:] is only a shallow copy, mutable default args persist across calls, and inner-loop slicing quietly adds O(k) copies."
  4. Clean structure: "@dataclass(frozen=True, order=True) gives hashable priority-queue-safe objects; custom decorators use @wraps and in cache (not truthiness); @contextmanager guards cleanup with try/finally."
