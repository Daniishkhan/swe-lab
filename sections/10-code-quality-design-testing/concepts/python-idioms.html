2Comprehensions vs. lazy generators

Whenever you transform or filter a collection, Python lets you write the transformation as a single readable expression instead of allocating an empty container and calling .append() in a loop:

# List, dict, and set comprehensions
evens   = [x * x for x in nums if x % 2 == 0]
by_id   = {u.id: u.name for u in users if u.active}
domains = {email.split("@")[1] for email in emails}

# Matrix transpose with zip(*matrix)
cols = [list(col) for col in zip(*grid)]

# Generator expression: parens () instead of brackets [] — O(1) memory & short-circuits!
total_bytes = sum(len(line) for line in log_stream)
has_neg     = any(x < 0 for x in nums)
first_hit   = next((x for x in nums if x > 100), None)

When to use a generator instead of a list: if you are feeding values straight into sum(), any(), all(), min(), max(), or next(), use (...)—never [...]. A list builds all 10 million entries in RAM first; a generator yields one value at a time and stops the instant any() or next() finds a match.

List comprehension:       [f(x) for x in 10M_items]  → allocates all 10M upfront (O(n) RAM)
Generator expression:     (f(x) for x in 10M_items)  → yields 1 item at a time  (O(1) RAM)
                                                       any() stops on item #3!
Watch the readability line: if a comprehension has more than two for clauses or complex branching, write a normal for loop instead. Clever one-liners hurt you in code reviews and bare editors.

You have a 50-million-line log file opened as an iterator lines and want to check whether any line contains "FATAL". Which is best?

Spot on. The generator expression streams one line at a time in O(1) memory and stops reading the file on the very first "FATAL" line.

Square brackets [...] force Python to read all 50 million lines into a giant list in RAM before any() or len() even starts. Drop the brackets so any() pulls lazily and short-circuits immediately.

3Lambdas, multi-key sorting & the late-binding trap

A lambda is just a short anonymous one-expression function—and its #1 job in interviews is giving sorted(), min(), and max() a custom key tuple. Because Python compares tuples lexicographically (first element, then second on ties, then third), multi-key sorting is one line:

# Sort tasks: highest priority first, then earliest deadline, then name A->Z
ordered = sorted(tasks, key=lambda t: (-t.priority, t.deadline, t.name))

# Need a pairwise comparator (like Largest Number: "9" before "34")?
from functools import cmp_to_key
nums_str.sort(key=cmp_to_key(lambda a, b: -1 if a + b > b + a else 1))

The classic trap: late-binding closures inside a loop

Suppose you build a list of callback functions in a loop: fns = [lambda x: x + k for k in range(3)]. You expect fns[0](10) to return 10—instead, all three functions return 12!

Python closures capture the variable cell, not its value at creation. Binding a default argument k=k (or using functools.partial) snapshots the value immediately.

What does [f() for f in [lambda: i for i in [10, 20, 30]]] return?

Exactly. None of the lambdas run until the loop has already finished with i = 30, so all three look up that same final cell.

Inside a loop, Python reuses one variable slot i. Each lambda: i holds a reference to that slot—not a copy of 10, 20, or 30. When called after the loop ends, i holds 30. Writing lambda i=i: i snapshots the value on each iteration.

4Lazy streams with yield and yield from

Google loves iterator questions ("Design a zigzag iterator", "Flatten a nested list iterator", "Merge k sorted streams"). A regular function computes everything and returns once; a function containing yield pauses its stack frame on every item and resumes right where it left off on the next next() call:

def walk_inorder(node):
    if node is None:
        return
    yield from walk_inorder(node.left)   # delegates cleanly to sub-generator
    yield node.val                       # pauses here until caller asks for next
    yield from walk_inorder(node.right)

Compare that to building a full list of 10 million tree nodes just to grab the first 5 values: with yield from, pulling 5 items visits only the leftmost branch and uses O(h) stack space instead of O(n).

Go deeper: strings are iterables too!

When writing a recursive flattener (like flatten_stream in Exercise 1), checking isinstance(item, Iterable) matches "hello" too—and iterating a 1-character string "h" yields "h" again, causing infinite recursion! Always exclude (str, bytes) before recursing on an iterable.

Why does isinstance("a", Iterable) cause infinite recursion in a naive recursive flattener?

Right! list("a") == ["a"], so recursing on every Iterable without excluding (str, bytes) loops forever until RecursionError.

In Python there is no separate char type: iterating "hi" produces "h" (a str), and iterating "h" produces "h" again—another Iterable! Guard with not isinstance(x, (str, bytes)).

5The four Python gotchas that cause silent interview bugs

Python variables are name tags stuck onto objects in memory—not boxes holding raw bytes. Assigning b = a sticks a second tag onto the exact same object. That single rule explains four infamous traps:

[0] * 3 is fine because ints are immutable; multiplying a list copies the reference, not the list.
  1. Aliased 2D grids: Always write [[0] * cols for _ in range(rows)], never [[0] * cols] * rows.
  2. Mutable default arguments: Default arguments are created once at def time, not on every call. Never write def add(x, buf=[]):; write buf=None and allocate if buf is None: buf = [] inside.
  3. Hidden O(k) slicing: nums[i:j] allocates and copies j - i elements. Passing nums[1:] in recursion or computing sum(nums[i:i+k]) in a sliding window quietly turns O(n) into O(n²). Pass start/end indices or use prefix sums (itertools.accumulate) instead.
  4. Tuple tie-breaks in heapq: Pushing (priority, node) crashes with TypeError when two priorities tie and Python tries to compare two custom Node objects! Fix: include a monotonic counter (priority, seq, node) or use an orderable frozen dataclass (next section).

With def push(x, out=[]): out.append(x); return out, what does calling push(1) then push(2) return?

Exactly! Python creates the empty list once when executing the def statement, so every call that omits out mutates the exact same list.

Default values live on the function object itself (push.__defaults__), evaluated once at definition time. Use out=None and create a fresh [] inside the body.

6Dataclasses, decorators & exception-safe with blocks

In Anthropic's 4-level builds and concurrency rounds, clean Python structure earns huge signal. Three built-in tools replace 40 lines of boilerplate with 5 lines of rock-solid code:

from dataclasses import dataclass
from functools import wraps
from contextlib import contextmanager

# 1. Immutable, hashable (dict/set keys!) AND heap-sortable in 4 lines:
@dataclass(frozen=True, order=True)
class Job:
    priority: int
    seq: int
    name: str

# 2. Custom decorator (always keep @wraps so __name__/__doc__ survive):
def trace_calls(fn):
    @wraps(fn)
    def wrapper(*args, **kwargs):
        return fn(*args, **kwargs)
    return wrapper

# 3. Context manager (try/finally guarantees cleanup even on exception!):
@contextmanager
def temporary_flag(state, key):
    state.add(key)
    try:
        yield state
    finally:
        state.discard(key)
In a custom memoizer, always test if args in cache:—never if cache.get(args):—or falsy return values (0, False, "", None) will recompute every single time.

In a @contextmanager function, what happens if an exception is raised inside the caller's with block and you forgot try ... finally around yield?

Spot on. Whatever follows yield only runs on exceptions if it sits inside a finally: block—critical for releasing locks or popping backtracking state.

When the body of a with block raises, Python injects that exception straight into the generator at the yield statement. Without try: yield ... finally: cleanup(), the generator aborts immediately and leaks state.

A recursive DP helper returns 0 for unreachable states. Your memoizer writes if cache.get(key): return cache[key]. What happens?

Exactly! Check membership with if key in cache: (or use @functools.cache) so 0, False, "", and None stay cached.

In Python, 0, None, False, and "" are all falsy. Testing if cache.get(key): treats a stored 0 identically to a cache miss!

✓What to remember

  1. Use generator expressions (...) inside sum/any/all/next for O(1) memory and short-circuiting.
  2. Multi-key sorting is one tuple key: key=lambda x: (-x.score, x.penalty, x.name).
  3. Closures capture variables, not values—bind loop values via default args (lambda x, f=f: ...).
  4. yield / yield from builds O(h)-space lazy streams; exclude (str, bytes) when flattening.
  5. Never use [[0]*m]*n or mutable defaults (buf=[]); avoid O(n²) inner-loop slicing.
  6. @dataclass(frozen=True, order=True) gives instant hashable + heap-ready objects; guard @contextmanager cleanup with try/finally.
