Transforming and streaming data

P0 Phase 0 Python pipelinesabout 16 minutes6 quick checks · 4 exercises

Half of every coding interview is reshaping data: filtering invalid rows, sorting by two rules, flipping rows into columns, sliding a window over 100,000 numbers, or flattening nested streams. Writing manual index loops for every step eats half your clock — and building giant intermediate lists eats your memory. Python gives you one clean pipeline vocabulary that moves smoothly from small in-memory batches to endless lazy streams.

By the end you'll be able to

  1. Filter, reshape, and rank collections in one readable pass using comprehensions and multi-rule sort keys.
  2. Walk parallel sequences in lockstep and transpose 2D tables cleanly without manual index math.
  3. Flip an eager in-memory list into a constant-memory lazy stream by swapping square brackets for parentheses.
  4. Combine prebuilt stream helpers to replace slow sliding-window slicing with a single linear pass.
  5. Write custom pausing streams that flatten arbitrarily nested or infinite inputs without hanging.

1Why do giant intermediate lists stall (or blow up) your code?

Your service opens a 50-million-line production log file to check one question: "Does any line contain FATAL?" The very third line is FATAL: disk full. Yet if you write any(["FATAL" in line for line in lines]), Python reads and allocates all 50 million booleans in RAM before any() ever inspects line 1 — burning over 400 MB of RAM and seconds of latency to find an answer sitting three lines in.

Every data-processing move in Python comes down to one physical choice: are you filling a batch warehouse or running a conveyor belt?

  • Batch warehouse (eager lists, dicts, sets): builds every finished item upfront and stores them all on shelves in memory. Great when you need random access (arr[i]), sorting, len(), or multiple passes over the data.
  • Conveyor belt (lazy iterators & generators): produces one item at a time only when the next station pulls it — and halts immediately the moment you find your match or reach your limit.
Pick the warehouse when you need the whole result stored; pick the conveyor belt when items only flow forward once.

Where the conveyor-belt analogy breaks: a real factory belt runs on its own motor even if nobody picks up boxes. A Python iterator is pull-driven — zero work happens until the caller pulls the next item via next(), a for loop, any(), or list().

Let's walk this pipeline in order: first, shaping and ranking clean in-memory batches (§2–§3); then flipping the exact same syntax onto a lazy conveyor belt (§4); snapping on prebuilt itertools stations (§5); and finally building your own pausing stations with yield (§6).

2How do you filter, shape, and rank a batch in one pass?

When you genuinely want a finished list, dictionary, or set in memory, Python's comprehensions replace 5 lines of out = []; for ...: if ...: out.append(...) with one scannable expression:

# List, dict, and set comprehensions — build a finished batch cleanly
squares = [x * x for x in nums if x % 2 == 0]
by_id   = {u.id: u.name for u in users if u.active}
domains = {email.split("@")[1] for email in emails}

Once you've filtered a batch of records, the very next interview move is usually ranking them by multiple rules — without mutating the caller's list. Pass a 1-line lambda (an unnamed rule function) returning a tuple to sorted(). Because Python compares tuples left-to-right (slot 0 first, slot 1 on ties, slot 2 next), negating numeric fields flips ascending into descending in one line:

# py_idioms: rank_candidates — drop None scores, sort score DESC, penalty ASC, name ASC
valid   = [r for r in records if r[1] is not None]      # Chapter 10.10: NOT `if r[1]:` (keeps 0!)
ordered = sorted(valid, key=lambda r: (-r[1], r[2], r[0]))
names   = [name for name, _, _ in ordered]

Trace three records through that key tuple: ("b", 90, 5) → (-90, 5, "b"), ("c", 90, 2) → (-90, 2, "c"), and ("a", 90, 2) → (-90, 2, "a"). Slot 0 ties at -90, so slot 1 puts penalty 2 ahead of 5, and slot 2 breaks the final tie alphabetically → ["a", "c", "b"]. Notice also how Chapter 10.10's truthiness rule plugs in: checking if r[1] is not None keeps a legal score of 0 while sorted() returns a fresh batch, leaving records untouched.

Use comprehensions to filter and reshape a batch in one line, test is not None whenever 0 or "" is legal, and pass a tuple-returning lambda to sorted() for multi-rule ranking (negating numbers to sort descending).

You want to rank (name, score, penalty) records by score descending, penalty ascending, then name A→Z. What breaks if you write sorted(valid, key=lambda r: (r[1], r[2], r[0]), reverse=True) instead of negating r[1]?

Sharp catch! Passing reverse=True reverses the entire tuple comparison — putting higher penalties and "z" before "a". Negating only descending numeric fields inside the key ((-r[1], r[2], r[0])) keeps every rule's direction independent.

Trace two tied records: ("a", 90, 2) vs. ("b", 90, 5). Their keys are (90, 2, "a") and (90, 5, "b"). With reverse=True, Python puts the larger tuple first — ranking penalty 5 ahead of penalty 2! Negate only score ((-r[1], r[2], r[0])) so penalty and name stay ascending.

That shapes and ranks one flat list of records. What when your input arrives across two parallel lists — or as a 2D table of rows that you need to read column by column?

3How do you walk multiple sequences — or flip rows into columns?

Manual index loops (for i in range(len(arr)):) are an off-by-one magnet in bare-editor rounds. Instead, pair parallel sequences directly:

  • enumerate(xs): pairs each item with its index (0, x0), (1, x1), … without maintaining a counter.
  • zip(names, scores): walks two or more sequences in lockstep, stopping at the shortest one (pass strict=True in Python 3.10+ if unequal lengths should raise an error).
  • zip(*matrix): the * unpacks each row of a 2D matrix as a separate argument to zip — tipping rows sideways into columns in three tokens!

Better yet, both enumerate and zip already return lazy iterators — they pull one paired tuple at a time, and wrapping them in [...] or list(...) packs the stream into a batch warehouse whenever you need a finished list.

zip(*[[1, 5, 3], [4, 2, 6]]) is identical to zip([1, 5, 3], [4, 2, 6]) — pairing slot 0 with slot 0, slot 1 with slot 1, and slot 2 with slot 2.

Combine that with a 1-line comprehension and transpose_and_filter in py_idioms.py shrinks to two readable lines (and handles empty [] or [[], []] cleanly):

def transpose_and_filter(matrix, threshold):
    if not matrix:
        return []
    return [[v for v in col if v >= threshold] for col in zip(*matrix)]
Use enumerate for index + item, zip for lockstep traversal, and zip(*matrix) to transpose rows into columns without a single nested index loop.

What does list(zip(*[[10, 20], [30, 40], [50, 60]])) return?

Exact! The * unpacks all three rows as separate arguments — zip([10, 20], [30, 40], [50, 60]) — grouping index 0 together as (10, 30, 50) and index 1 together as (20, 40, 60).

Try tracing a smaller 2×3 table first: zip(*[[1, 2, 3], [4, 5, 6]]) unpacks into zip([1, 2, 3], [4, 5, 6]), producing three column pairs [(1, 4), (2, 5), (3, 6)]. Flip the shape to 3 rows × 2 columns and zip(*...) produces 2 column triples: [(10, 30, 50), (20, 40, 60)].

Notice what Sections 2 and 3 had in common: square brackets [...] always filled the entire batch warehouse upfront. Now watch what happens when your input holds 50 million lines and you only care about the first match — or the running sum.

4How do you switch from a warehouse to a conveyor belt with two characters?

Take any list comprehension and swap the outer square brackets [...] for parentheses (...). You just turned a batch warehouse into a generator expression — a pull-on-demand conveyor belt! Whenever values flow straight into sum(), any(), all(), min(), max(), or next(), drop the brackets completely:

# Generator expressions: constant O(1) extra memory & instant short-circuiting!
total_bytes = sum(len(line) for line in log_stream)
has_fatal   = any("FATAL" in line for line in log_stream)
first_big   = next((x for x in nums if x > 100), None)   # fallback None if none match

Step through the exact difference between any([...]) and any(...) on a 6-line log where "FATAL" sits at line index 2 (the 3rd line):

Switch the dropdown between the batch warehouse [...] and the conveyor belt (...). Notice how brackets force Python to finish reading every remaining line before any() even wakes up!
Swap [...] for (...) whenever a sequence feeds sum, any, all, min, max, or next. You keep the exact same readability while dropping memory from O(n) to constant O(1) and short-circuiting on the first match.

A streaming database cursor rows yields 10 million (user_id, bytes_sent) pairs, and you want the first user_id with bytes_sent > 1_000_000 (or None). Which expression runs in constant O(1) memory and stops on the first hit?

Spot on! The generator expression (u for u, b in rows if b > 1_000_000) pulls one row at a time in constant O(1) memory, and next(..., None) halts the instant the first oversized transfer appears.

Trace a 3-row stream [("u1", 50), ("u2", 2_000_000), ("u3", 10)]: square brackets [...] force Python to pull all three rows (and all 10 million in production!) to finish building a list before next(iter(...)) or [0] even looks at element 0. Swapping [...] for (...) lets next() return "u2" immediately without ever pulling "u3".

Generator expressions handle simple 1-to-1 transforms on a belt. Next question: what when you want to take only the first k items from an endless belt, splice belts together, group runs, or compute running totals without Chapter 10.10's slow list-slicing loops?

5How do prebuilt conveyor stations eliminate slow slicing loops?

Python's itertools module gives you four C-speed conveyor stations that snap onto any iterator without copying data into temporary lists:

  • islice(stream, start, stop): skips ahead and pulls only a slice of a lazy or infinite belt — without allocating a list or exhausting the rest of the stream.
  • chain.from_iterable(groups): splices a sequence of lists (one level deep) into one continuous belt in constant O(1) extra memory.
  • groupby(items, key=...): bundles consecutive runs sharing the same key (always sort by that key first if matching items aren't already adjacent!).
  • accumulate(nums, initial=0): emits running cumulative totals (prefix sums) in one pass: [1, 2, 3, 4] → [0, 1, 3, 6, 10].

Remember Chapter 10.10 §4's hidden slicing trap? Computing every length-k window sum with sum(nums[i:i+k]) copies and adds k items per window — 2.5 billion steps for n = 100,000, k = 50,000 (O(n·k)). Now align the prefix sums pref against themselves shifted forward by k with islice(pref, k, None) — every window sum pops out in one subtraction:

pref[i + k] - pref[i] cancels everything before index i, leaving the exact sum of window nums[i : i + k] in 1 subtraction.

That turns window_sums in py_idioms.py into four crystal-clear lines:

from itertools import accumulate, islice

def window_sums(nums, k):
    if k <= 0:
        raise ValueError("k must be positive")
    if k > len(nums):
        return []
    pref = list(accumulate(nums, initial=0))
    return [hi - lo for lo, hi in zip(pref, islice(pref, k, None))]

Why materialize pref into a list instead of keeping accumulate lazy? Because zip(pref, islice(pref, k, None)) reads two different offsets from pref at the same time — passing a single-use iterator to both slots would advance the same belt twice and corrupt every window! And since window_sums already returns an O(n) output list, one O(n) prefix list keeps total memory asymptotic at O(n).

Go deeper: O(k) streaming windows and the groupby sub-iterator trap

True O(k) memory over an endless stream: if nums arrives as a billion-item stream that doesn't fit in RAM, keep a fixed ring buffer buf = collections.deque(maxlen=k) (covered on Day 4) and a single integer running = 0. Each step, subtract buf[0] if len(buf) == k, append the new item, add it to running, and yield running once full — O(k) RAM and O(1) per item!

The groupby sub-iterator trap: groupby shares its underlying conveyor belt with every group sub-iterator g. Writing groups = [(k, g) for k, g in groupby(data)] stores exhausted sub-iterators because advancing the outer loop drains earlier groups! Always materialize immediately — [(k, list(g)) for k, g in groupby(data)] — if you need the items later.

Reach for itertools before hand-rolling index arithmetic: islice slices any lazy stream, chain.from_iterable flattens one level lazily, groupby groups sorted runs, and accumulate + islice + zip computes sliding-window sums in one linear O(n) pass.

You run [k for k, _ in groupby(["cat", "dog", "cat"])] without sorting first. What does it return?

Spot on! Because groupby is a streaming conveyor station (constant O(1) memory, no global hash table), it only watches the key immediately beside it — splitting non-adjacent "cat" entries into two runs unless you sort first.

Walk the belt one item at a time: item 0 starts run "cat"; item 1 switches to run "dog" (closing the first "cat" run!); item 2 sees "cat" again and opens a brand-new "cat" run. That's why groupby never raises an error — and why you sort first (or use defaultdict) when matching items aren't consecutive.

Prebuilt itertools stations cover flat belts and single-level chains. Now ask the classic Google interview follow-up: what when items rolling down your belt contain nested belts inside nested belts to arbitrary depth — or an infinite stream of nested tuples?

6How do you build your own pausing station for nested or infinite streams?

A one-line generator expression (...) cannot call itself recursively. To build a custom conveyor station with arbitrary logic, write a regular def containing yield.

The moment Python sees yield inside a function, calling that function runs zero lines of its body — it hands back a paused generator object parked at line 1. Each time the caller pulls with next(gen), execution advances only to the next yield, freezes every local variable right where it stands, and hands back one item.

And when a station spots a nested container inside the stream, yield from sub_gen connects that sub-belt directly to the caller without writing a manual forwarding loop (this is flatten_stream in py_idioms.py):

from collections.abc import Iterable

def flatten_stream(nested):
    for item in nested:
        if isinstance(item, Iterable) and not isinstance(item, (str, bytes)):
            yield from flatten_stream(item)     # wire nested sub-belt straight to caller
        else:
            yield item                          # pause right here until next() pulls!
Step through pulling items one by one from flatten_stream([1, (2, "hi"), 3]). Notice how "hi" stays intact as an atomic leaf and 3 is never even visited until pull #4.

Why excluding (str, bytes) is mandatory: Python has no separate char type — iterating "hi" yields "h" (another str, which is still an Iterable!), and iterating "h" yields "h" forever until RecursionError. Always check not isinstance(item, (str, bytes)) before recursing on an Iterable.

A generator function returns a lazy iterator immediately without running its body until the first next(). That lets islice(gen, 6) pull six items from an infinite flatten_stream using only O(d) memory for nesting depth d — completely independent of stream length.
Go deeper: flattening inputs nested deeper than Python's recursion limit

Recursive yield from keeps one active generator frame per nesting level (O(d) call-stack space), so an adversarial input nested more than ~1,000 levels deep hits RecursionError. If an interviewer asks how to handle arbitrary depth, swap recursion for an explicit stack of iterators: push iter(nested), pull with next(stack[-1], sentinel), pop exhausted iterators, and push iter(item) whenever you hit a nested non-(str, bytes) iterable — still lazy and still O(d) heap memory, with no recursion limit.

You call gen = flatten_stream(infinite_nested()) and then list(islice(gen, 5)). What breaks if you write return [...] inside flatten_stream instead of yield?

Spot on! Building a list eagerly forces Python to walk every element of infinite_nested() before returning — so islice never even gets a chance to stop at 5.

Compare warehouse vs. conveyor belt: islice works fine on finite lists, yet Python evaluates flatten_stream(infinite_nested()) completely before passing the result into islice. With return [...], that call loops forever trying to finish an infinite list; with yield, it pauses after item #5 and stops.

Conveyor belts save hundreds of megabytes of RAM and unlock infinite streams — yet because they pull items one by one instead of storing them on shelves, they break in three ways that surprise engineers mid-interview.

7How can lazy pipelines break — and when should you write a plain loop?

Keep these three conveyor-belt limits front of mind:

  1. Single-use exhaustion (the #1 generator bug): once a generator runs to the end — even because you ran a quick debug print(list(gen)) or called max(gen) before min(gen) — the belt is empty forever! A second loop over the same generator silently sees zero items. If you need two passes, materialize into a list or tuple once.
  2. No len() and no random indexing: calling len(gen) or gen[0] raises TypeError because a conveyor belt hasn't pulled future items yet.
  3. When a plain for loop beats a clever comprehension: if a pipeline needs side effects, multiple accumulators, or more than two nested for/if clauses, write a clean for loop. Interviewers reward readability over code golf.

Before: manual loops + slow window slice

cols = []

You create vals = (x * 2 for x in [1, 2, 3]), print sum(vals) (which prints 12), and on the very next line print list(vals). What prints?

Caught it! Generators are one-way conveyor belts: once sum(vals) pulls all three items, vals is exhausted and every later consumer receives []. Store vals = [x * 2 for x in ...] if you need multiple passes.

Follow the belt position: sum(vals) pulls 2, then 4, then 6, until the generator hits the end and stops. There is no rewind button — so when list(vals) pulls from the same exhausted generator, zero items remain and it quietly returns [] (never raising StopIteration).

8What to say in the interview

Before coding py_idioms.py and moving to Day 3's building blocks (Chapter 10.12), make sure you can explain these four ideas aloud in 45 seconds:

  1. Batches vs. streams: "I'll use a list comprehension when I need random access or sorting, and a generator expression (...) for single-pass reductions like any/sum/next so extra memory stays O(1) and it short-circuits on the first hit."
  2. Ranking & transposing: "Tuple keys rank by multiple rules in one pass (negate numbers for descending, guard is not None to keep 0), and zip(*matrix) transposes rows into columns cleanly."
  3. itertools & sliding windows: "Using accumulate with islice and zip computes every length-k window sum in one O(n) pass instead of O(n·k) repeated slicing."
  4. Custom generators: "yield and yield from flatten nested streams lazily in O(d) stack space for nesting depth d, excluding (str, bytes) so strings stay atomic leaves."
