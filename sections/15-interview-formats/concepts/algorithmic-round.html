Phase 0 · Day 4

How to run an algorithmic coding round

Format the method for every drill and mockabout 15 minutes7 quick checks · 5 exercises

Strong senior engineers fail 45-minute coding rounds every week — not because they can't code, but because they improvise under a ticking clock. This chapter gives you a repeatable 45-minute playbook you will run on every timed drill and mock from Week 1 onward.

By the end you'll be able to

  1. Budget a 45-minute coding round into five clear phases so you never panic at minute zero.
  2. Ask only high-signal clarifying questions and lock in three tiny examples before designing.
  3. Turn a brute-force idea into an agreed optimal plan without going silent.
  4. Catch your own off-by-one and edge-case bugs with a literal trace table in a bare editor (before any Run button).
  5. Recover calmly when you get stuck, receive a hint, or hit a broken invariant mid-code.

How to read this: top to bottom on Phase 0 Day 4, answering every quick check before moving on (skip collapsed "Go deeper" boxes on a first pass). Reread section 8 the morning of every mock or screen, and open the Practice hub whenever you run a timed bare-editor drill or mock. Builds on no prior chapters.

1Why do strong engineers still fail coding rounds?

A staff-level engineer enters a 45-minute screen. At minute 2 they start typing without checking constraints. At minute 24 they realize duplicates break their loop and rewrite half the file in silence. At minute 42 they click Run for the first time, crash on an empty list, and run out of time. Verdict: No Hire — even though they knew the algorithm.

Compare that with running a repeatable 5-phase loop on the exact same 45-minute clock:

The disciplined candidate writes code for only ~17 minutes — and finishes with verified, senior-bar signal on every axis.

This loop unlocks three immediate advantages:

  • Zero blank-page panic: you always know the next small action, even on a brand-new problem.
  • Active evidence on all four grading axes: interviewers score Problem Solving, Code Quality, Testing & Edge Cases, and Communication from 1 to 4 (1 = No Hire, 2 = Lean No, 3 = Hire — requires active positive evidence, not just zero crashes — 4 = Strong Hire). Typing fast only feeds one axis.
  • Self-caught bugs: walking a literal trace table catches off-by-one bugs before the interviewer sees a failed test run.

Carry one physical picture through the chapter: a commercial pilot's 45-minute flight plan. A pilot never rolls onto the runway at minute 2 hoping the weather clears — they run a pre-flight check, file the route with air-traffic control (your interviewer), fly smoothly calling out turns, run the landing checklist before touching down, and follow a calm drill if turbulence hits.

Where the analogy breaks: air-traffic control wants a routine flight; an interviewer may deliberately change the destination mid-flight (adding a scale-up or constraint twist) to see how you adapt.

A coding round isn't a typing race — it is a 45-minute live collaboration scored 1–4 across problem solving, code quality, testing & edge cases, and communication.

Candidate A finishes coding in 20 silent minutes and says "looks good" without testing. Candidate B finishes in 36 minutes, explains the brute force first, confirms the improved plan, and catches an empty-input bug during a hand trace. Who clears the senior bar?

Exactly! Catching your own bug during verification is positive senior signal, whereas shipping untested code in silence leaves three of the four rubric boxes empty or weak.

Read the interviewer's scorecard after Candidate A hangs up: "Trade-offs explained? No evidence. Edge-case discipline? None. Debugging poise? Unknown." At senior level, a 3 (Hire) demands active evidence on every axis — and catching your own bug while tracing proves rigor rather than failing coding.

3What must you check before takeoff?

Prompts are intentionally underspecified — just like real engineering tickets. At minute 0, confirm the round shape in one breath ("One problem with follow-ups, or two problems? Will we run code or dry-run only?"), then run a 5-point pre-flight check in under three minutes:

  1. Scale (n): "How large can the input be?" Sets your Big-O target (which you'll formalize in Week 1's Chapter 02.01).
  2. Order & values: "Is the input already sorted? Can items be negative, strings, or duplicated?"
  3. Empty / tiny cases: "What should empty or 1-item input return?" (-1, 0, None?)
  4. Ties & output definition: "What exact metric do we return — index gap j - i (adjacent = 1) or items between (adjacent = 0)?"
  5. Mutation: "Is it okay to sort or modify the input list in place?"

Then write three tiny examples (3–6 elements) at the top of the editor and confirm outputs — locking down both the metric (j - i) and subtle invariants:

[5, 1, 5, 5] → 1 does double duty: it confirms adjacent distance = 1 (j - i), and it catches any buggy map that keeps the first index instead of updating to the latest (keeping first would wrongly return 2!).
Ask only questions that can change your algorithm or return contract, then lock in three tiny examples (normal, empty/missing, tricky) before designing.

Prompt: "Given a list of integers and a target, count how many pairs sum to target." Which clarifying question changes your algorithm and space complexity the most?

Bullseye! A sorted distinct list unlocks inward two pointers in O(n) time and O(1) extra space (which you'll formalize in Week 1's Chapter 02.01) — whereas an unsorted list forces sorting or O(n) extra memory. Negative or zero values don't change the algorithm at all.

Use the flip test: "If the answer flips from Yes to No, do I choose a different algorithm?" Adding two numbers works identically whether values or target are negative or zero. Knowing whether the list is sorted and how large n is directly picks between O(n²) pairs, O(n) space, and O(1)-space two pointers.

4How do you pick a plan without freezing?

This is the hardest ten minutes of the round. Never sit silent hoping a trick falls from the sky — file your route with ATC in four spoken steps:

Ask for sign-off before coding. If you missed a constraint or there's a tighter path, the interviewer will steer you here — when pivoting costs 30 seconds instead of 15 minutes.

When the jump from Step 1 to Step 3 isn't obvious, ask yourself three concrete bottleneck questions out loud:

  1. What am I re-scanning? If an inner loop searches for something you already walked past, remember it in a dict or running variable.
  2. Would order help? Ask if sorting first (O(n log n)) puts matching or neighboring items right next to each other.
  3. Still blank? Solve a 4-item example by hand and watch what your own eyes keep jumping back to look at — that repeated glance is the data structure you're missing.

Explain it another way: why saying the brute force out loud finds the optimal answer

Your brain struggles to invent a clever trick from thin air, but it excels at spotting wasted work. The second you say "my inner loop scans backward looking for the last occurrence of x," the fix almost says itself: "wait — I can remember the last index of x as I walk!" Brute force isn't filler; it's your compass.

Speak the brute force and Big-O in 30 seconds, pinpoint the repeated work, propose the improved invariant, and get explicit sign-off before typing code.

You spot the optimal O(n) solution in the first 60 seconds. How should you open Phase 2?

Spot on! That takes 25 seconds, proves structured trade-off thinking, and confirms you aren't missing a hidden constraint before you spend 15 minutes typing.

Check both pitfalls: jumping straight into code without sign-off risks missing a constraint ("wait, can we keep space O(1)?"), while spending 10 minutes coding a brute force you already outgrew burns half your Phase 3 budget! Summarize brute force in one sentence, state the optimal plan, and get the nod.

5How do you write clean code without sounding robotic?

Once ATC clears your route, fly smoothly. Avoid both extremes: 12 minutes of dead air AND reading syntax aloud ("now I type f-o-r, space, i…"). Narrate intent at each decision point:

Hard to follow (cryptic names, magic sentinel)

def f(a):
    d, m = {}, 10**9
    for i in range(len(a)):
        if a[i] in d:
            if i - d[a[i]] < m: m = i - d[a[i]]
        d[a[i]] = i
    return -1 if m == 10**9 else m

Senior signal (clear names, safe sentinel, early exit)

def min_duplicate_gap(ids):
    last_seen = {}            # id -> latest index
    best = float("inf")
    for idx, req_id in enumerate(ids):
        if req_id in last_seen:
            best = min(best, idx - last_seen[req_id])
            if best == 1: return 1   # shortest possible
        last_seen[req_id] = idx
    return -1 if best == float("inf") else best

Three habits earn immediate Code Quality and Communication credit:

  • Names carry the invariant: last_seen explains what the dict holds without comments; float("inf") never breaks on huge inputs, and [] / [x] naturally return -1 without special-case clutter.
  • Skeleton first, helpers second: if a sub-step is messy (parsing timestamps, checking grid bounds), call a clean helper like is_valid(r, c) and write its body right after.
  • Headline your quiet pauses: need 30 seconds to verify an index? Say "Give me 30 seconds to double-check this boundary." Announced thinking feels calm; unexplained silence feels stuck.
Narrate why each block exists, not the characters you're typing. Intent-revealing names, safe sentinels, and small helpers win Coding and Communication together.

Midway through writing a loop, you aren't sure whether the boundary condition should be < or <=. What is the strongest move?

Textbook senior behavior! A 15-second check on 2 items resolves the fencepost cleanly and shows method rather than guesswork.

Picture an interviewer watching both alternatives: guessing < and hoping Run saves you fails on no-Run screens and looks careless; unannounced silence looks like freezing. Plugging in [3, 7] (indices 0 and 1) out loud takes 10 seconds and turns a snag into positive signal.

6How do you catch your own bugs in a bare editor?

When you finish typing the last line, do not say "I'm done" — and in a bare editor with no Run button, your literal trace table IS your compiler (on platforms that do offer Run, finish this trace before clicking it). Draw a tiny trace table and execute your code literally — acting like a dumb computer obeying only the exact tokens on screen.

Watch how a literal trace immediately catches setting best = 0 instead of float("inf") on [4, 1, 4]:

Execute the literal tokens on screen (min(0, 2)), never what you meant to write. Then check your 3 edge cases ([], [1, 2], [5, 1, 5, 5]).
Walk 1 normal input through a literal variable table plus 3 edge cases (empty/1-item, no-match, tricky) in your bare editor — before saying "done" or touching Run. Self-caught bugs raise your Testing score.

What bug does a literal trace on [4, 1, 4] catch immediately in this version of min_duplicate_gap?

def min_duplicate_gap(ids):
    last_seen, best = {}, float("inf")
    for idx, req_id in enumerate(ids):
        last_seen[req_id] = idx
        if req_id in last_seen:
            best = min(best, idx - last_seen[req_id])
    return -1 if best == float("inf") else best

Caught on row 0 of the trace! At idx = 0, req_id = 4, line 4 inserts {4: 0}, so line 5 is immediately True and sets best = min(inf, 0 - 0) = 0! Checking before overwriting fixes it.

Step row 0 literally: idx = 0, req_id = 4. Line 4 runs first: last_seen = {4: 0}. Now evaluate line 5 literally: is 4 in last_seen? YES — you just put it there! So line 6 computes 0 - 0 = 0, poisoning best to 0 on every non-empty list.

7How can a coding round break — and how do you recover?

Even top pilots hit turbulence. What separates Hire from No Hire is a calm drill for the five mid-flight emergencies:

EmergencyWhat panicking looks likeThe calm recovery drill
1. Blank mind at min 10Staring silently for 5 minutes hoping a trick appearsSolve a 4-item example by hand, circle what your eyes re-scan, and pick a structure to remember it.
2. Approach breaks at min 22Silently deleting and panic-rewriting half the filePause, name the exact counterexample aloud, and ask whether to patch the invariant or pivot cleanly.
3. Interviewer drops a hintBrushing it off ("I'll check later") or fighting itStop immediately — treat hints as ATC warning of terrain. Echo it back and trace it on a tiny input.
4. Bug surfaces at min 38Randomly flipping +1 / -1 and hoping tests passShrink to a 2–3 item failing input, find the first line where actual ≠ expected, state root cause, fix once.
5. Clock hits min 41 mid-codeFrantic typing leaving broken half-syntax everywhereFinish the core loop cleanly and explain the stubbed helper + exact complexity — coherent beats broken.

When this 5-phase clock isn't the right fit: In a 2-problem 45-minute screen (such as Meta-style two-problem screens when an interviewer announces two problems at minute 0), split the clock into ~20 minutes per problem (2m clarify / 5m plan / 9m code / 4m trace). And in practical multi-level coding (15.02) or debugging rounds (15.03), run tests continuously after every small step instead of waiting until Phase 4.

Go deeper: runnable editors, "why not sorting?", and production testing

Runnable vs. bare editors: Google screens disable code execution completely — making Section 6's literal trace table your only compiler. On platforms that do provide a Run button, still complete the literal trace first so your very first run comes back green.

"Why a dict instead of sorting?" Be ready for the obvious alternative: sorting (val, idx) pairs costs O(n log n) time AND still takes O(n) space to keep original indices, so the dict wins on time without losing on space (sorting only beats hashing on guaranteed worst-case O(n log n) if adversarial hash collisions are a threat).

"How would you test this in production?" Name four distinct buckets beyond a quick dry run: happy path, boundaries (empty, 1 item, adjacent/3+ repeats), invalid/malformed types, and scale/stress tests.

Hints aren't penalties — ignoring a hint is. Pause cleanly if an invariant breaks, shrink any late bug to 2–3 items, and adapt the clock for 2-problem or practical rounds.

While coding this loop, your interviewer asks: "Wait — what happens on line 4 if input is [5, 1, 5, 5]?"

for idx, req_id in enumerate(ids):
    if req_id in last_seen:
        best = min(best, idx - last_seen[req_id])
    else:
        last_seen[req_id] = idx

Spot on! Tracing [5, 1, 5, 5] exposes the bug in 10 seconds: last_seen[5] stays stuck at 0, returning 2 instead of 1! Removing else: so last_seen[req_id] = idx always updates fixes it with full understanding.

Never brush off ATC pointing at a specific line, and never blindly edit without seeing why. Tracing [5, 1, 5, 5] takes 10 seconds: at idx=2, 5 is in last_seen so else doesn't run, leaving last_seen[5] = 0 — then at idx=3 you compute 3 - 0 = 3 instead of 3 - 2 = 1!

8What to say — your pre-round checklist

Skim this 60-second checklist right before every timed drill, mock, or live screen:

  1. Minute 0–5 (Clarify): "Quick format check: one problem or two, and will we run code? Before designing, let me check max n, sortedness, duplicates/negatives, empty-input return, and mutation — then verify three tiny examples."
  2. Minute 5–15 (Plan): "The brute force is [X] in O(…) time and O(…) space. The repeated work is [Y]. If I maintain [Z], it drops to O(…) time and O(…) space. Does that look good before I code?"
  3. Minute 15–32 (Code): Name variables for their invariant; narrate intent per block; announce 30-second boundary checks openly.
  4. Minute 32–40 (Verify): "Let me walk [normal example] through a literal trace table by hand, then verify empty, 1-item, and boundary cases."
  5. Minute 40–45 (Wrap): "Final cost is O(…) time and O(…) auxiliary space (including recursion stack). Happy to explain why this beats [obvious alternative] or walk through scale follow-ups."

✓What to remember

  1. Interviewers score 1–4 across four equal axes: Problem Solving, Code Quality, Testing & Edge Cases, and Communication (3 = Hire requires active evidence).
  2. Run the 5-phase flight plan every time: Clarify (5m) → Plan & Sign-off (10m) → Code (17m) → Trace & Test (8m) → Wrap (5m).
  3. Check minute-0 format (1 vs 2 problems, runnable?) and only high-signal constraints (n, sortedness, value range, empty behavior, mutation) + 3 tiny examples.
  4. State brute force + Big-O in 30 seconds, pinpoint the repeated work, propose the improvement, and get ATC sign-off before typing.
  5. Narrate intent, not keystrokes; verify with a literal trace table + 3 edge cases in your bare editor before wrapping up (or running code).
  6. Absorb hints immediately, pause cleanly if an invariant breaks, and shrink any late bug to a 2–3 item trace instead of guess-editing.

Answer

Prompt B: Questions: (1) Return the character or its index, and what if every character repeats? (2) Case-sensitive ('A' vs 'a') and ASCII or Unicode? (3) Max length n? Examples: "swiss" → 'w'; "aabb" → None/-1; "a" → 'a'.

Warm-up · pen and paper

2. Catch two bugs with a literal trace table

Draw a literal trace table for this intended "return index of first occurrence of target, or -1" function on ([7, 7, 5], 7) and ([5, 7], 7) — without running Python — and find both bugs:

def first_index(nums, target):
    ans = -1
    for i in range(len(nums) - 1):
        if nums[i] == target:
            ans = i
    return ans
Answer

Trace 1 — ([7, 7, 5], 7): i=0 → ans=0; i=1 → ans=1 (overwrites 0!) → returns 1 instead of 0. Bug 1: missing early return i (or break).
Trace 2 — ([5, 7], 7): range(1) visits only i=0 (5 ≠ 7) and stops → returns -1 instead of 1. Bug 2: range(len(nums) - 1) skips the last element.
