Bare-editor coding playbook

about 10 minutes3 quick checks · interactive 45-min timer

Google L5 coding rounds are not speed-typing contests. You get one open-ended Medium–Hard problem in a plain shared editor (no autocomplete, no run button, often in person) followed by 2 to 3 escalating follow-ups. Read this protocol once, then use it on every single timed drill for the next ten weeks until it runs on autopilot.

By the end you'll have

  1. A repeatable 45-minute clock budget so you never rush coding or run out of time for dry-running.
  2. The exact 5-step sequence Google L5 rubrics grade: clarify → brute force → optimize → clean code → manual hand trace.
  3. A mental checklist for the four follow-up axes interviewers love to pivot toward.

How to read this: read once in Phase 0, then reopen the timer below whenever you run a timed drill or before any coding mock.

2The 5-step protocol (what L5 rubrics grade)

  1. Clarify before touching code (min 0–5): Google prompts are intentionally vague. Ask 3–4 sharp questions: input size & bounds (fits in RAM?), value types (negatives, duplicates, empty, Unicode?), mutability (may I mutate input?), tie-breaking, and expected error behavior. Write one small concrete example in comments and confirm the output.
  2. Brute force first, then improve (min 5–15): State the naive approach and its exact time/space cost in two sentences ("Brute force checks all pairs in O(n²); the repeated work is scanning for the complement…"). Name the bottleneck, propose the optimal data structure/algorithm, state its complexity, and get explicit buy-in ("Does this approach look good before I code?").
  3. Write clean, structured code (min 15–30): Use descriptive variable names (never single-letter soup for non-indices), pull out helper functions early so the main loop reads like prose, and narrate invariants rather than reading syntax aloud.
  4. Dry-run line by line before saying "I'm done" (min 30–35): Never say "looks good" without tracing! Maintain a small variable table in comments and step through (a) the normal example, (b) empty/single-element input, and (c) a boundary case (all duplicates, negative numbers, disconnected graph, tie). Catching your own off-by-one bug during a dry run is a positive senior signal.
  5. Expect 2–3 escalating follow-ups (min 35–45): At L5, finishing the base problem is only half the evaluation. Interviewers immediately shift a constraint:
    • Scale / memory: "Now the input is 100 TB on disk or arrives as an infinite stream." (External merge sort, reservoir sampling, Bloom filter, Count-Min Sketch, map-reduce partitioning.)
    • Dynamic updates: "Now queries interleave with writes." (Balanced tree / Fenwick tree / Union-Find / cache invalidation.)
    • Concurrency: "Now 100 threads call this simultaneously." (Lock granularity, striping, read-write lock, immutable snapshots.)
    • Strict guarantees: "Optimize worst-case space to O(1), or return the actual path, not just the count."
At senior level, clean structure + proactive edge-case testing + calm adaptation to follow-ups beat memorizing an obscure trick every single time.

3Quick checks

An interviewer asks: "Given a list of meetings, return the minimum rooms needed." What should you do in the first 2 minutes?

Exactly. Whether touch-at-endpoint intervals count as overlapping changes < vs <=—catching that upfront shows senior discipline.

Jumping straight into code on an underspecified prompt is one of the fastest ways to code the wrong edge-case behavior and lose L5 problem-solving signal. Spend 2–3 minutes clarifying constraints and agreeing on an example.

You finish writing your solution at minute 29 in a plain text editor (no run button). What is the best next move?

Spot on. Finding and fixing your own bug in a structured dry run counts for you; letting the interviewer find an obvious boundary crash counts heavily against you.

In a bare-editor round, your manual dry run is the compiler and test runner. Always step through the actual lines you wrote—not what you meant to write—on at least one normal and one boundary case.

You solved a "top-k frequent words" problem in RAM, and at minute 37 the interviewer asks: "Now the log stream is 50 TB across 100 machines." What are they testing?

Exactly! Reaching the scale follow-up means you're doing well—they want to see how smoothly you bridge algorithmic thinking to real distributed systems constraints.

Scale follow-ups are a classic Google L5 calibration probe, usually discussed verbally or with lightweight pseudocode. Think: partition by key, aggregate locally, merge top-k (or approximate with sketches if RAM is tight).
